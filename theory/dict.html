Session 2D — Dict (Deep)  ·  Part 1, Chunk A — Theory: The Model + Method Surface

The finale of Session 2, and the most important data structure in Python. The dict is how Python represents objects, namespaces, keyword arguments, JSON, and most real-world data. It ties together everything from Session 2: it's a hash table like a set (2C), its keys must be hashable like tuple/frozenset keys (2B), and its values can be anything including lists (2A).

1. Theory — Chunk A

1.1 What a dict is — a hash table mapping keys to values

A dict is an unordered-by-hash but insertion-ordered collection of key→value pairs, built on a hash table. If a set (2C) is a hash table of keys, a dict is a hash table of keys where each key also carries an associated value. Everything you learned about set performance applies to dict keys, plus you get a value attached.

Three defining properties:

Property 1 O(1) key access

d[key] computes hash(key), jumps to the bucket, returns the value. Constant time regardless of dict size — same mechanism as set membership. The live proof was dramatic:

d = {i: i for i in range(1_000_000)}
d[999999]        # 7.07 µs  - one hash lookup
# vs scanning a list of (key,value) pairs for the same key: 56 ms
A ~7,900× speedup. SQL/Power BI anchor: a dict is a lookup table with a primary-key index. d[key] is an indexed seek; scanning a list of pairs is a full table scan. It's also exactly a DAX LOOKUPVALUE — fetch a value by its key.
Property 2 Keys must be hashable

Same rule as set elements (2C) and tuple dict-keys (2B): keys must be immutable-enough to have a stable hash. Strings, numbers, tuples-of-immutables, frozensets — fine. Lists, dicts, sets — not.

{[1,2]: "x"} raises unhashable type: 'list'. Values, by contrast, can be anything — lists, other dicts, objects, whatever.
Property 3 Insertion-ordered (Python 3.7+)

Unlike sets, dicts preserve the order keys were inserted. Inserting z, a, m, b iterates back as z, a, m, b. This was an implementation detail in 3.6 and became a language guarantee in 3.7. It's why dicts can replace OrderedDict for most uses now, and why dict.fromkeys works as an order-preserving dedup (2A/2B/2C callback).

1.2 The complete method surface

Dicts have a rich method set. Here's every one that matters, with what it does, what it returns, and complexity. All verified.

Access methods
d[key] — get the value for key. O(1). Raises KeyError if missing.
d.get(key, default=None) — get the value, or default if missing. O(1). Never raises — the safe accessor. d.get("z") → None, d.get("z", 0) → 0.
d.setdefault(key, default) — return d[key] if present; else set d[key] = default and return it. O(1). Sets c when new, leaves a unchanged when present. The workhorse for "get-or-initialize" (grouping patterns).
View methods — return dynamic views, not lists
d.keys() — a view of keys.
d.values() — a view of values.
d.items() — a view of (key, value) tuples. All O(1) to create (they're lazy views over the live dict). The (key, value) tuples from .items() are the 2B tuples you unpack in loops.
Mutation methods
d[key] = value — insert or overwrite. O(1) amortized.
d.update(other) — merge another dict/iterable of pairs in; existing keys overwritten. O(k). update({"d":4,"a":10}) added d, overwrote a.
d.pop(key, default) — remove and return the value; default avoids KeyError. O(1). pop("d") → 4; pop("z", "none") → "none".
d.popitem() — remove and return the last inserted (key, value) pair (LIFO, 3.7+). O(1). Returns ('c', 3).
d.clear() — empty the dict. O(n).

1.3 The single most important distinction: [] vs .get()

This is the dict equivalent of list's None-returning-methods trap — the thing that most separates fluent from beginner code:

d = {"a": 1}
d["missing"]          # KeyError: 'missing'   - RAISES
d.get("missing")      # None                   - safe
d.get("missing", 0)   # 0                       - safe with default
Use d[key] when the key must exist (you want to fail loudly if it doesn't). Use .get() when the key might not exist and you have a sensible fallback. Reaching for d[key] on uncertain data is the #1 source of KeyError crashes; .get() with a default is the fix. This choice — fail-loud vs. safe-default — is a real design decision you make constantly.

1.4 The setdefault pattern — get-or-initialize

setdefault deserves special mention because it powers grouping — one of the most common real tasks:

groups = {}
for word in words:
    groups.setdefault(word[0], []).append(word)   # first letter -> list of words
For each word: setdefault(key, []) returns the existing list if the key's been seen, or creates a new empty list, stores it, and returns it — either way you get a list to .append to. This is the 2C anagram-grouping pattern from 2C, now with its proper tool. (Chunk B shows defaultdict, which makes this even cleaner.)

1.5 Dict comprehensions — build, filter, invert

Like lists (2A) and sets (2C), dicts have a comprehension form. The syntax adds the key: value pair:

{x: x*x for x in range(5)}                    # {0:0, 1:1, 2:4, 3:9, 4:16}

Three common patterns, all verified:

Build Transform an iterable into a mapping
{x: x*x for x in range(5)}    # number -> its square
Filter Keep only pairs matching a condition — iterate .items()
prices = {"apple": 3, "banana": 1, "cherry": 5}
{k: v for k, v in prices.items() if v > 2}     # {'apple':3, 'cherry':5}
This is SELECT key, value FROM prices WHERE value > 2.
Invert Swap keys and values
{v: k for k, v in prices.items()}    # {3:'apple', 1:'banana', 5:'cherry'}
Inverting is common for reverse lookups (value→key), but note the catch: if values aren't unique, later pairs overwrite earlier ones (duplicate values collapse — since keys must be unique). Fine when values are unique (like an index map); lossy otherwise.

1.6 Iteration — keys by default, items for pairs

The one thing that trips people up: iterating a dict directly gives keys, not pairs.

d = {"a": 1, "b": 2}
for k in d:              # iterates KEYS -> 'a', 'b'
    ...
for k in d.keys():      # same thing, explicit
    ...
for v in d.values():    # iterates VALUES -> 1, 2
    ...
for k, v in d.items():  # iterates (key, value) TUPLES -> ('a',1), ('b',2)
    ...
The rule: for x in d gives keys. When you want both key and value, use .items() and unpack the tuple in the loop header (for k, v in d.items()) — this is the 2B tuple-unpacking pattern, and it's the most common dict loop in real code. A frequent beginner bug is for k, v in d: (without .items()), which tries to unpack each key and fails.

1.7 The collections power tools — Counter and defaultdict

These two are specialized dicts that eliminate boilerplate you'd otherwise write constantly. They're heavily used in ML data prep and interviews.

Counter Counting made trivial — a dict subclass that counts hashable items
from collections import Counter
c = Counter("mississippi")        # Counter({'i':4, 's':4, 'p':2, 'm':1})
c.most_common(2)                  # [('i',4), ('s',4)] - top 2 by count
Counter("aab") + Counter("abb")   # Counter({'a':3, 'b':3}) - counters add!
Counter gives you frequency counting in one line (vs. a manual setdefault/get loop), most_common(n) for top-n (already sorted by count), and arithmetic (+, -, &, |) between counters. This is the tool for word frequencies, label distributions, vote tallies. Directly relevant to OpsRAG — token/tag frequency analysis is a one-liner.
defaultdict Grouping without the setdefault dance — auto-creates default values for missing keys
from collections import defaultdict


groups = defaultdict(list)                    # missing key -> new empty list
for word in ["apple","ant","banana","bear"]:
groups[word[0]].append(word)              # no setdefault needed!
# {'a':['apple','ant'], 'b':['banana','bear']}


counts = defaultdict(int)                     # missing key -> 0
for ch in "hello":
counts[ch] += 1                           # no get(ch,0) needed
# {'h':1, 'e':1, 'l':2, 'o':1}

You give defaultdict a factory (list, int, set, etc.); when you access a missing key, it calls the factory to create the default automatically. defaultdict(list) for grouping, defaultdict(int) for counting (though Counter is cleaner for pure counting). This turns the setdefault grouping pattern from Chunk A into cleaner code — compare groups.setdefault(k, []).append(x) vs groups[k].append(x).

1.8 Dict merging (Python 3.9+)

Modern syntax for combining dicts:

a = {"x": 1, "y": 2}
b = {"y": 3, "z": 4}
a | b        # {'x':1, 'y':3, 'z':4}  - b wins on conflict
y takes b's value (3), because the right operand wins on key conflicts. Also a |= b to merge in place, and the older {**a, **b} unpacking form (works pre-3.9). This is the fix for the mutable-default config bug from 2A — merge a user config over defaults: config = DEFAULTS | user_overrides.

1.9 Key views are set-like

A subtle but useful feature: d.keys() returns a view that supports set operations (because keys are unique and hashable, just like a set):

d = {"a": 1, "b": 2, "c": 3}
d.keys() & {"a", "c", "z"}    # {'a', 'c'} - intersection with a set!
You can do &, |, -, ^ directly on .keys() — "which keys do these two dicts share?" is d1.keys() & d2.keys(). This is 2C's set algebra reaching into dicts. Views are also dynamic — they reflect live changes to the dict, and are O(1) to create since they don't copy.

1.10 The complexity table

Operation Example Complexity Note
Key access d[k] O(1) hash lookup; KeyError if missing
Safe access d.get(k) O(1) never raises
Insert / update d[k] = v O(1) amortized resizes rarely
Delete del d[k] / pop O(1)
Membership (keys) k in d O(1) checks KEYS (not values!)
Membership (values) k in d.values() O(n) values aren't indexed — scan
Iterate for k in d O(n) insertion order
Length len(d) O(1) stored
Views d.keys / .values / .items O(1) lazy views
The interview-critical row: k in d checks keys in O(1), but v in d.values() scans values in O(n) — values aren't hash-indexed. If you need fast value→key lookups, build an inverted dict.

2. Example

Example 1 Word frequency, three ways (the counting task)
words = "the cat the dog the cat".split()


# 1. manual with .get(key, 0) - the fundamental pattern
f1 = {}
for w in words:
f1[w] = f1.get(w, 0) + 1          # {'the':3, 'cat':2, 'dog':1}


# 2. defaultdict(int) - no .get needed
from collections import defaultdict, Counter
f2 = defaultdict(int)
for w in words:
f2[w] += 1                        # missing key auto-starts at 0


# 3. Counter - one line
Counter(words)                        # Counter({'the':3, 'cat':2, 'dog':1})

All three identical. This progression is the dict learning arc: .get(k, 0) teaches the mechanism, defaultdict(int) removes boilerplate, Counter is the production one-liner. Know all three — interviewers sometimes ask you to do it without Counter to see if you understand the mechanism.
Example 2 Grouping records (the setdefault/defaultdict task)
people = [("eng","Alice"), ("sales","Bob"), ("eng","Cara"), ("sales","Dan")]
groups = defaultdict(list)
for dept, name in people:            # unpack each tuple (2B)
    groups[dept].append(name)
# {'eng': ['Alice','Cara'], 'sales': ['Bob','Dan']}
Group items by a key into lists — defaultdict(list) auto-creates the empty list. This is the C7 anagram pattern from 2C, now with its natural tool. SQL anchor: GROUP BY dept. One of the most common real data tasks, period.
Example 3 Nested dicts (JSON-shaped data)
users = {
    "u1": {"name": "Alice", "roles": ["admin", "dev"]},
    "u2": {"name": "Bob",   "roles": ["dev"]},
}
users["u1"]["name"]                        # "Alice"  - chained access
users["u1"]["roles"][0]                    # "admin"  - dict->list->index
users.get("u3", {}).get("name", "unknown") # "unknown" - safe nested access
This is the shape of essentially all API/JSON data — dicts nested in dicts, with lists inside. The safe-nested pattern d.get("k", {}).get("inner", default) avoids KeyError when a level might be missing — critical for real-world data where fields are optional. Values being "anything" (2D's rule) is what makes this work: a value can be a dict, a list, or a list of dicts.
Example 4 Index map and inversion (the ML vocabulary task)
vocab = ["cat", "dog", "bird"]
word_to_idx = {w: i for i, w in enumerate(vocab)}   # {'cat':0,'dog':1,'bird':2}
idx_to_word = {i: w for w, i in word_to_idx.items()} # {0:'cat',1:'dog',2:'bird'}
Building a token→integer map (and its inverse) is step one of every embedding/NLP pipeline — the exact continuation of 2C's vocabulary-building example. enumerate supplies the indices, the comprehension builds the map, and inverting via .items() gives you decode-back capability.
Example 5 Merging configs (the reproducibility fix)
DEFAULTS = {"lr": 0.01, "epochs": 100, "batch": 32}
user     = {"lr": 0.001, "batch": 64}
config = DEFAULTS | user     # {'lr':0.001, 'epochs':100, 'batch':64}
User values override defaults, epochs falls back to the default. This is the clean, immutable-friendly way to layer configuration, and it structurally avoids the mutable-shared-config bug from 2A's ML section.

3. Edge Cases

Seven cases, all verified.

Edge 1 d[key] raises, .get() is safe
d = {"a": 1}
d["b"]              # KeyError: 'b'
d.get("b", 0)       # 0
Why it matters: the dict's headline trap. d[key] on a missing key crashes; .get(key, default) returns the default. Use [] when the key must exist (fail loud), .get() when it might not (safe fallback). This single choice prevents most dict-related crashes.
Edge 2 for k, v in d: fails without .items()
d = {"a": 1, "b": 2}
for k, v in d:      # ValueError: not enough values to unpack (expected 2, got 1)
    ...
Why it matters: iterating a dict yields keys, not pairs. Trying to unpack each key (a single string) into two variables fails. You must use .items(): for k, v in d.items(). This is a top beginner bug, and the error message ("expected 2, got 1") is the tell.
Edge 3 Duplicate keys collapse (last wins)
{"a": 1, "a": 2, "a": 3}          # {'a': 3}
dict([("x", 1), ("x", 2)])        # {'x': 2}
Why it matters: keys are unique — a later assignment to the same key overwrites, silently. This bites when building a dict from pairs that have duplicate keys (you lose data without warning), and it's why inverting a dict with non-unique values is lossy (Chunk B).
Edge 4 Mutable default value aliasing (the 2A trap, in dict form)
d = dict.fromkeys(["a", "b"], [])   # BOTH keys share ONE list!
d["a"].append(1)
print(d)                            # {'a': [1], 'b': [1]}  -- b changed too!


d2 = {k: [] for k in ["a", "b"]}    # comprehension -> distinct lists
d2["a"].append(1)
print(d2)                           # {'a': [1], 'b': []}   -- correct

Why it matters: dict.fromkeys(keys, []) evaluates [] once and gives every key the same list object (Session 1 aliasing, exactly like [[0]*3]*3). Appending to one appends to all. Fix: a comprehension {k: [] for k in keys} creates a fresh list per key. This is a genuinely nasty bug because fromkeys looks like the obvious tool.
Edge 5 Modifying a dict during iteration raises
d = {"a": 1, "b": 2, "c": 3}
for k in d:
    if d[k] == 2:
        del d[k]          # RuntimeError: dictionary changed size during iteration
Why it matters: like sets (2C Trap 3), dicts raise RuntimeError if you change their size mid-iteration — stricter than lists (which fail silently). Fix: build a new dict with a comprehension ({k:v for k,v in d.items() if v != 2}) or iterate over a copy of the keys (for k in list(d):).
Edge 6 1 and 1.0 are the same key; membership checks keys
d = {1: "a", "1": "b", 1.0: "c"}
# -> {1: 'c', '1': 'b'}   -- 1 and 1.0 collapsed (1 == 1.0, same hash)
"a" in d                  # False -- 'in' checks KEYS, not values
Why it matters: two subtleties. First, 1 and 1.0 are equal and hash identically, so they're the same key — 1.0: "c" overwrote 1: "a". (The string "1" is distinct.) Second, x in d tests keys, not values — checking for a value requires x in d.values() (O(n)).
Edge 7 .get() with a default doesn't store; setdefault does
d = {}
d.get("k", [])            # returns [] but d is STILL {}
d.setdefault("k", []).append(1)   # stores [] AND returns it -> d = {'k': [1]}
Why it matters: a subtle distinction that trips people building nested structures. .get(k, default) returns the default but doesn't insert it — the dict is unchanged. .setdefault(k, default) inserts the default (if missing) and returns it, so you can immediately mutate what it returns. For "get-or-create-then-modify," you need setdefault (or defaultdict), not .get().

4. Golden Rules

Rule 1 The .get() vs [] decision — fail-loud or safe-default (full depth)
This is the dict decision you make most often, so it deserves proper treatment rather than a one-liner. The choice encodes intent about whether a key is expected to exist, and getting it right is a real signal of fluency.

Use d[key] when the key must exist. If a missing key means something is genuinely wrong — a bug, corrupt data, a broken contract — you want the KeyError. Failing loudly at the point of the problem is better than silently continuing with wrong data. Example: looking up a required config value you know you set. If it's missing, crash now with a clear error, don't paper over it.

Use d.get(key, default) when the key might legitimately be absent. If absence is a normal, expected case with a sensible fallback, .get() handles it cleanly. Example: reading an optional field from API data, or counting with d.get(k, 0) + 1 where a new key naturally starts at zero.

The anti-pattern that reveals inexperience is the try/except KeyError wrapper around d[key] when you just want a default — that's what .get() is for: 
# clumsy
try:
    x = d[key]
except KeyError:
    x = 0
# fluent
x = d.get(key, 0)
And the deeper rule: don't check-then-access when one call does it. if key in d: x = d[key] is two hash lookups; d.get(key) is one. For get-or-create, setdefault/defaultdict beats if key not in d: d[key] = [].
Rule 2 Reach for Counter to count, defaultdict to group.
Manual .get(k,0)+1 loops and setdefault(k,[]).append work and are worth understanding, but the collections tools are cleaner and signal you know the stdlib. Use Counter(items) for frequencies, defaultdict(list) for grouping.
Rule 3 Never use a mutable default with dict.fromkeys.
dict.fromkeys(keys, []) shares one list across all keys (aliasing). Use a comprehension {k: [] for k in keys} for distinct values.
Rule 4 Use .items() to iterate key+value; plain iteration gives keys only.
for k, v in d.items(), not for k, v in d.
Rule 5 Merge with | (3.9+) or {**a, **b}; right side wins.
Clean way to layer configs over defaults.
Rule 6 Remember membership and in check keys, not values.
k in d is O(1) on keys; v in d.values() is O(n). Need fast value lookups? Build an inverted dict.
Rule 7 To modify while iterating, iterate a copy or build a new dict.
for k in list(d): or a comprehension. Modifying size mid-iteration raises RuntimeError.

5. Common Traps

Trap 1 KeyError on d[key]. (the classic)
value = d[user_input]     # crashes if user_input isn't a key
The most common dict crash. The tell: KeyError in a traceback. Fix: .get(key, default) when absence is possible, or validate with if key in d first when you need to branch.
Trap 2 for k, v in d: instead of d.items(). (tight)
for k, v in d:            # ValueError: not enough values to unpack
Iterating a dict yields keys, not pairs. Fix: for k, v in d.items(). The tell: "not enough values to unpack (expected 2, got 1)."
Trap 3 dict.fromkeys with a mutable default shares one object. (full depth — it's the dict version of a Session 1 trap)
d = dict.fromkeys(["a", "b", "c"], [])
d["a"].append(1)
print(d)     # {'a':[1], 'b':[1], 'c':[1]}  -- ALL changed!
fromkeys evaluates the default [] once and points every key at that single list object — the exact aliasing from [[0]*3]*3 (2A Edge 6) and the mutable-default-argument trap (Session 1). Append through one key, all keys see it, because they're one list. The tell: setting a value on one key mysteriously changes others. Fix: comprehension {k: [] for k in keys} — gives distinct lists. This is nasty precisely because fromkeys looks like the right tool for "initialize these keys to empty lists."
Trap 4 Silent key overwrite from duplicates. (tight)
dict([("x", 1), ("x", 2)])    # {'x': 2}  -- first value lost silently
Building a dict from pairs with duplicate keys keeps only the last — no warning, data lost. The tell: a dict smaller than the input, or missing values you expected. Fix: if you need to keep all values per key, group into lists with defaultdict(list) instead.
Trap 5 Modifying during iteration. (tight)
for k in d:
    if cond(d[k]): del d[k]    # RuntimeError: dictionary changed size
Stricter than lists (raises rather than misbehaving silently). Fix: for k in list(d): or build a new dict with a comprehension.
Trap 6 Assuming .get() inserts the default. (tight)
d.get("k", []).append(1)      # appends to a throwaway list; d unchanged!
.get() returns the default but doesn't store it — the append is lost. For get-or-create-then-mutate, use setdefault or defaultdict. The tell: a nested structure you thought you were building stays empty.

7. ML Real-World Connection

The dict is the backbone of ML code — more than any other structure. Features, configs, vocabularies, class distributions, and caches are all dicts.

ML 1 A feature vector / data row is a dict

Before data becomes a NumPy array, it's usually a dict of named features:

sample = {"age": 34, "income": 55000, "region": "south", "score": 0.87}
sample["age"]                    # 34
sample.get("missing_feat", 0)    # 0 - safe default for absent features

This is how a single record looks coming out of a database, an API, or a pandas row (.to_dict()). The .get(feat, default) pattern handles missing features gracefully — critical when different records have different available fields.

ML 2 Class distribution with Counter — the first thing you check before training
labels = ["spam","ham","spam","spam","ham","spam"]
dist = Counter(labels)                          # {'spam':4, 'ham':2}
total = sum(dist.values())
balance = {k: round(v/total, 2) for k, v in dist.items()}   # {'spam':0.67, 'ham':0.33}

Checking class balance is step zero of any classification task — a 67/33 split tells you whether you need class weighting, resampling, or stratified splitting. Counter + a comprehension gives you the distribution in two lines. Directly relevant to any classifier you build.

ML 3 Vocabulary encoding — the tokenizer core
vocab = {}
for doc in corpus:
    for tok in doc.split():
        if tok not in vocab:
            vocab[tok] = len(vocab)      # next token gets the next integer id
def encode(doc):
    return [vocab[t] for t in doc.split()]   # "deploy docker" -> [0, 1]

The vocab[tok] = len(vocab) trick assigns sequential integer IDs as new tokens appear — the exact mechanism inside every tokenizer and embedding layer. This is 2C's vocabulary-building and 2D's index-map examples combined into the real thing. Central to OpsRAG's retrieval side.

ML 4 Memoization — caching with a dict
cache = {}
def fib(n):
    if n < 2: return n
    if n in cache: return cache[n]           # O(1) cache hit
    cache[n] = fib(n-1) + fib(n-2)
    return cache[n]
fib(30)      # 832040, computed with only 29 cached entries

A dict cache turns exponential recomputation into linear — the essence of dynamic programming and of functools.lru_cache. In ML this is how you cache expensive embeddings, API responses, or feature computations. The O(1) key lookup is what makes it worthwhile.

ML 5 Config as a dict, merged over defaults
DEFAULTS = {"lr": 0.01, "epochs": 100, "optimizer": "adam"}
run_config = DEFAULTS | {"lr": 0.001, "epochs": 50}
# {'lr':0.001, 'epochs':50, 'optimizer':'adam'}

Every experiment config, every hyperparameter set, every JSON settings file is a dict. Merging experiment overrides over defaults (|, 3.9+) is the clean, reproducible pattern — and structurally avoids the mutable-shared-config bug from 2A.

8. Interview Questions

8a — Conceptual Q&A (12 questions)

1 How is a dict implemented, and why is key access O(1)?
A As a hash table. d[k] computes hash(k), jumps to the bucket, returns the value — no scan. Average O(1) regardless of size.
2 What can be a dict key? A value?
A Keys must be hashable (immutable-enough): strings, numbers, tuples-of-immutables, frozensets. Values can be anything, including lists, dicts, and objects.
3 d[key] vs d.get(key)?
A d[key] raises KeyError if missing; .get(key, default) returns the default (or None) and never raises. Use [] when the key must exist, .get() when absence is expected.
4 Do dicts preserve order?
A Yes, insertion order, guaranteed since Python 3.7 (implementation detail in 3.6). Unlike sets, which are unordered.
5 What does iterating a dict give you?
A Keys by default (for k in d). Use .items() for (key, value) pairs, .values() for values.
6 Counter vs defaultdict?
A Counter is a dict specialized for counting (most_common, arithmetic). defaultdict(factory) auto-creates a default for missing keys — defaultdict(list) for grouping, defaultdict(int) for counting. Use Counter for pure counts, defaultdict for grouping.
7 What's wrong with dict.fromkeys(keys, [])?
A All keys share one list object (the default is evaluated once). Mutating one mutates all. Use {k: [] for k in keys} for distinct lists.
8 Does x in d check keys or values? Complexity of each?
A Keys, O(1). Checking values (x in d.values()) is O(n) — values aren't hash-indexed.
9 How do you invert a dict with non-unique values?
A Not with a plain comprehension (last-wins loses data). Use defaultdict(list) and append each key to its value's list.
10 What happens with duplicate keys when building a dict?
A The last value wins, silently. {"a":1, "a":2} is {"a":2}.
11 How do you merge two dicts?
A a | b (3.9+, right wins), a |= b (in place), or {**a, **b} (older). Or a.update(b) to mutate a.
12 Why can't you modify a dict while iterating it?
A Changing its size mid-iteration raises RuntimeError (dicts detect the change). Iterate list(d) or build a new dict with a comprehension.

1. Theory

🔹 A string is an immutable sequence

A str is an ordered sequence of characters you can index and slice like a list (2A) — but you cannot change it in place, exactly like a tuple (2B). Any "edit" builds a new string object and rebinds your name to it.

This one fact drives the whole session: methods, formatting, and the big performance trap all fall out of immutability.

💡 SQL / Power BI anchor: like a text value in a column — you don't mutate a cell's characters, you compute a new value and overwrite. REPLACE() / DAX SUBSTITUTE() return a new string; they never edit the original in place.
s = "hello"
s[0] = "H" # attempt to edit in place
s = "H" + s[1:] # rebuild -> a brand-new object
TypeError: 'str' object does not support item assignment
>>> s
'Hello'
🔒 Immutable (str, like tuple)
indexable, sliceable
hashable → dict key / set member
every "change" = new object
🔓 Build with list, then join
parts = []
parts.append(chunk)
"".join(parts) # O(n)
Why it matters (callback to 2A): because a string can't grow in place, s += chunk inside a loop rebuilds the entire string every iteration — the O(n²) accumulator trap from Lists. The fix is the same shape: collect in a list, then "".join(parts) once — O(n).
💡 Immutability is also why strings are hashable — that's what lets them be dict keys and set members (2C/2D). Same immutability → hashability chain as tuples.
