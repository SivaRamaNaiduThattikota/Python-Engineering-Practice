12.4 Configuration and secrets

The same code runs on a laptop, in CI and in production with different models, limits and keys, so configuration must live outside the code, and secrets must never be in it. Environment variables and their parsing, .env files, TOML with tomllib, layering defaults, files and environment with clear precedence, keeping secrets out of reprs, logs and git, and test hygiene. Applied to LLM settings, model registries and secret scanning.

18 problems4 easy · 10 medium · 4 hard

1Configuration lives outside the code

Configuration is everything that differs between deployments of the same code: the model name, the temperature, the database URL, timeouts, feature flags, log level, and the credentials to reach other services. Hard-coding it means editing and redeploying code to change a timeout, and hard-coding a secret means everyone with access to the repository, its forks, its CI logs and its history has the key. The widely followed "twelve-factor" rule is to keep configuration in the environment: the code reads it at start-up, and each environment (developer laptop, CI, staging, production) supplies its own values.

In practice, configuration comes in layers, from most general to most specific: defaults in the code (safe values that work for development), a configuration file checked into the repository for non-secret settings (config.toml), environment variables set by the deployment, and sometimes command-line flags for one run (15.3). Each layer overrides the ones before it, and secrets come only from the environment or a secret manager. The rest of this lesson builds each layer.

2Environment variables

os.environ is a mapping of the process's environment variables. os.environ["KEY"] raises KeyError if the variable is missing, os.environ.get("KEY", default) (or the identical os.getenv) returns a default instead, and assigning os.environ["KEY"] = "value" changes it for this process and the child processes it starts, never for the parent shell. Every value is a string: assigning an int raises TypeError, and reading "8" or "false" gives strings that must be parsed. That parsing is where most configuration bugs come from: bool("false") is True, int("8.0") fails, and an empty string is not the same as a missing variable.

Two habits follow. Parse and validate once, at start-up, into a typed settings object (a frozen dataclass or a Pydantic model, 11.P), so the rest of the program never touches os.environ and a bad value fails immediately with a clear message instead of an hour later. And read the environment when the settings are created, not at import time: a module that evaluates os.getenv in a global freezes whatever was set when it was first imported, which breaks tests and anything that changes configuration (problem 15).

3.env files

Typing a dozen export commands before every run is tedious, so development tools read a .env file in the project folder: one KEY=value per line, # comments, optional quotes. The python-dotenv package loads it into os.environ; Docker Compose, VS Code and many frameworks read the same format. The file holds real secrets for your machine, so it is listed in .gitignore and never committed; instead the repository contains a .env.example with every variable name and dummy values, which documents what the application needs. Problem 5 implements the parser, to see exactly what the format means: export prefixes, quotes, escapes in double quotes, and comments.

By convention, values loaded from .env do not override variables already set in the real environment, so a deployment can always win over a stray file. In production, there is no .env file at all: the platform (Kubernetes, a cloud service, CI) injects environment variables, ideally fetched from a secret manager such as AWS Secrets Manager, Azure Key Vault, GCP Secret Manager or HashiCorp Vault, which stores secrets encrypted, controls who can read them, logs every access and supports rotation.

4Configuration files with tomllib

Non-secret settings with structure (several models, retrieval parameters, prompt names) are clearer in a file than in dozens of variables. TOML is the Python ecosystem's format: pyproject.toml uses it, and since Python 3.11 the standard library reads it with tomllib. Unlike .env and environment variables, TOML values are typed: 8 is an int, 0.2 a float, true a bool, "text" a string, 2025-03-01 a date, [...] an array, and [section] headers and [[array.of.tables]] create nested dicts and lists of dicts. tomllib.loads(text) parses a string and tomllib.load(f) a file opened in binary mode ("rb"), returning plain dicts; errors raise tomllib.TOMLDecodeError, a subclass of ValueError. tomllib only reads; writing TOML needs a third-party package such as tomli-w.

toml_config.py
import tomllib

text = '''
service = "support-rag"
debug = false

[retrieval]
top_k = 8
min_score = 0.35
sources = ["faq", "terms"]

[[models]]
name = "small"
context_window = 8_192

[[models]]
name = "large"
context_window = 128_000
'''
cfg = tomllib.loads(text)
print(cfg["retrieval"], type(cfg["retrieval"]["min_score"]).__name__)
print([m["name"] for m in cfg["models"]], cfg["models"][1]["context_window"])
try:
    tomllib.loads("top_k = 8\ntop_k = 9")
except tomllib.TOMLDecodeError as e:

5Layering and precedence

Combining the layers is a merge, and its rules should be explicit. A shallow merge, {**defaults, **file_cfg, **env_cfg} or defaults | file_cfg, replaces whole nested sections: a file that sets only model.name would wipe out the default model.temperature. Configuration needs a deep merge: nested dicts are merged key by key, and other values (including lists) are replaced. collections.ChainMap(env, file_cfg, defaults) gives a read-only-looking view that searches the maps in order without copying, which suits flat settings; writes go to the first map (problem 9).

Environment variables are flat strings, so nested keys need a naming convention, usually a prefix and a double underscore for each level: APP_MODEL__TEMPERATURE=0.7 sets model.temperature. Their values need types; a neat trick is to parse each one as a TOML value and fall back to the raw string, so 0.7 becomes a float, true a bool and ["a", "b"] a list (problem 6). Whatever the scheme, a good settings loader can also report where each value came from (problem 14), the first thing you want to know when production behaves differently from your laptop.

layers.py
import copy

def deep_merge(base, override):
    out = copy.deepcopy(base)
    for key, value in override.items():
        if isinstance(value, dict) and isinstance(out.get(key), dict):
            out[key] = deep_merge(out[key], value)
        else:
            out[key] = copy.deepcopy(value)
    return out

defaults = {"model": {"name": "small", "temperature": 0.0}, "retrieval": {"top_k": 5, "sources": ["faq"]}}
file_cfg = {"model": {"name": "large"}, "retrieval": {"sources": ["faq", "terms"]}}
print({**defaults, **file_cfg}["model"])
merged = deep_merge(defaults, file_cfg)
print(merged)
print(defaults["retrieval"]["sources"])
Output
{'name': 'large'}
{'model': {'name': 'large', 'temperature': 0.0}, 'retrieval': {'top_k': 5, 'sources': ['faq', 'terms']}}
['faq']

6Keeping secrets secret

A secret leaks in more ways than being committed. The rules: never write a secret in source code, notebooks, tests or config files that are committed; keep .env in .gitignore; read secrets from the environment or a secret manager at start-up; never log or print them, which includes the accidental cases: an exception message that contains a URL with a password, a repr of a settings object in a log line, a debug dump of request headers, or a notebook cell output saved into the repository. Give secrets their own type whose repr and str are masked (Pydantic has SecretStr; problem 10 builds one), so printing the settings is safe.

Assume a leak will happen and limit its damage: use separate keys per environment and per service, give each key the narrowest permissions and spending limits the provider allows, and rotate them regularly. Add automated secret scanning (GitHub's push protection, gitleaks, detect-secrets, or a pre-commit hook like problem 13) so a key is caught before it is pushed. If a key is committed anyway, revoke and rotate it first: deleting the commit does not help, because forks, clones, CI caches and bots that scan public repositories for keys within minutes may already have it.

import os

_TRUE = {"1", "true", "yes", "on"}
_FALSE = {"0", "false", "no", "off"}


def _raw(name, environ):
    env = os.environ if environ is None else environ
    return env.get(name, "").strip()


def env_bool(name, default=False, environ=None):
    raw = _raw(name, environ)
    if not raw:
        return default
    if raw.lower() in _TRUE:
        return True
    if raw.lower() in _FALSE:
        return False
    raise ValueError(f"{name} must be a boolean (true/false, 1/0, yes/no, on/off), got {raw!r}")


def env_int(name, default, min_value=None, max_value=None, environ=None):
    raw = _raw(name, environ)
    if not raw:
        return default
    try:
        value = int(raw)
    except ValueError:
        raise ValueError(f"{name} must be an integer, got {raw!r}") from None
    if min_value is not None and value < min_value or max_value is not None and value > max_value:
        raise ValueError(f"{name} must be between {min_value} and {max_value}, got {value}")
    return value

Parsing settings is validation (7.1): accept an explicit set of spellings, reject everything else with a message that names the variable and shows the bad value, so the operator knows exactly what to fix. Treating empty as missing matches how deployment tools often define unset variables (KEY=). Passing environ as a parameter, defaulting to os.environ, makes the functions testable with a plain dict and no global state. int("8.0") failing is deliberate: a fractional value for a count is a configuration mistake, not something to truncate quietly.

5. Parse a .env file

Write parse_dotenv(text) returning a dict. Ignore blank lines and lines starting with #, and allow an export prefix. Each other line is KEY=VALUE with a key matching [A-Za-z_][A-Za-z0-9_]* (spaces around = allowed). Values: in double quotes, \n becomes a newline and \" a quote; in single quotes, the text is literal; after a closing quote, only spaces or a # comment may follow. Unquoted values are stripped, and # starts a comment (a # without a space before it is part of the value). Later keys override earlier ones. An invalid line or an unterminated quote raises ValueError starting with f"line {n}: ".

solution.py
import re

_LINE = re.compile(r"(?:export\s+)?([A-Za-z_][A-Za-z0-9_]*)\s*=(.*)")
_ESCAPES = {"n": "\n", '"': '"', "\\": "\\"}


def _rest_ok(rest):
    rest = rest.strip()
    return not rest or rest.startswith("#")


def _value(raw, n):
    raw = raw.strip()
    if raw.startswith('"'):
        out, i = [], 1
        while i < len(raw):
            ch = raw[i]
            if ch == "\\" and i + 1 < len(raw) and raw[i + 1] in _ESCAPES:
                out.append(_ESCAPES[raw[i + 1]])
                i += 2
                continue
            if ch == '"':
                if not _rest_ok(raw[i + 1:]):
                    raise ValueError(f"line {n}: unexpected text after closing quote")
                return "".join(out)
            out.append(ch)
            i += 1
        raise ValueError(f"line {n}: unterminated double quote")
    if raw.startswith("'"):
        end = raw.find("'", 1)
        if end == -1:
            raise ValueError(f"line {n}: unterminated single quote")
        if not _rest_ok(raw[end + 1:]):
            raise ValueError(f"line {n}: unexpected text after closing quote")
        return raw[1:end]
    return re.split(r"\s#", raw, maxsplit=1)[0].strip()


def parse_dotenv(text):
    env = {}
    for n, line in enumerate(text.splitlines(), start=1):
        stripped = line.strip()
        if not stripped or stripped.startswith("#"):
            continue
        m = _LINE.fullmatch(stripped)
        if not m:
            raise ValueError(f"line {n}: expected KEY=VALUE")
        env[m.group(1)] = _value(m.group(2), n)
    return env

Writing the parser shows what the format really promises. Quotes exist so values can hold spaces, # and newlines; double quotes interpret a few escapes, single quotes nothing, which is why passwords with backslashes belong in single quotes. The comment rule ( # needs a space before it) is what keeps URLs with fragments intact. Strict errors with line numbers turn a typo in a 40-line .env into a one-second fix. Dict insertion order keeps the first position of a key even when a later line overrides its value. Real loaders such as python-dotenv add variable expansion (${HOME}) and multi-line values, and, by default, do not override variables that are already set in the environment.

solution.py
import copy, tomllib


def _merge(target, src):
    for key, value in src.items():
        if isinstance(value, dict) and isinstance(target.get(key), dict):
            _merge(target[key], value)
        else:
            target[key] = copy.deepcopy(value)


def _parse(raw):
    try:
        return tomllib.loads(f"v = {raw}")["v"]
    except tomllib.TOMLDecodeError:
        return raw


def load_config(defaults, toml_text, environ, prefix="APP_"):
    cfg = copy.deepcopy(defaults)
    _merge(cfg, tomllib.loads(toml_text))
    for name, raw in environ.items():
        if not name.startswith(prefix):
            continue
        *parents, last = name[len(prefix):].lower().split("__")
        node = cfg
        for part in parents:
            node = node.setdefault(part, {})
        node[last] = _parse(raw)
    return cfg

Each layer is more specific than the last, so later layers win, but only for the keys they mention: the deep merge keeps the default temperature when the file changes only the model name. Lists are replaced, not concatenated, because "the sources are faq and terms" is one setting. The __ convention maps flat variable names onto the nested structure, and parsing values as TOML gives them types for free while plain words stay strings; the trade-off is that a value such as 2025-01-01 becomes a date, so a validating model (11.4) should still check the final result. The deep copy keeps the module's defaults pristine, which matters when the loader runs more than once, as in tests.

Hint 2Open a hint

SolutionShow the solution and why
solution.py
import os
from contextlib import contextmanager

def _apply(values):
    for k, v in values.items():
        if v is None:
            os.environ.pop(k, None)
        else:
            os.environ[k] = v

@contextmanager
def temp_env(**changes):
    old = {k: os.environ.get(k) for k in changes}
    try:
        _apply(changes)
        yield
    finally:
        _apply(old)

os.environ is process-wide state, so a test that changes it and does not restore it changes every later test, the source of failures that depend on test order. Recording the previous value as None for missing variables lets one rule handle both directions: None means "absent", so it is popped, never assigned (assigning None raises TypeError). The finally (10.2) restores the state even when the block fails, which is exactly when a test has failed and the next one must not inherit its mess. pytest's monkeypatch.setenv and monkeypatch.delenv (13.2) do this for you.

import tomllib

ALLOWED = {"name", "provider", "context_window", "cost_per_1k"}


def load_models(toml_text):
    data = tomllib.loads(toml_text)
    defaults = data.get("defaults", {})
    models = {}
    for i, entry in enumerate(data.get("models", []), start=1):
        name = entry.get("name")
        if not name:
            raise ValueError(f"model {i}: missing name")
        if name in models:
            raise ValueError(f"duplicate model {name!r}")
        merged = {**defaults, **entry}
        for key in merged:
            if key not in ALLOWED:
                raise ValueError(f"model {name!r}: unknown key {key!r}")
        window = merged.get("context_window")
        if window is not None and (not isinstance(window, int) or isinstance(window, bool) or window <= 0):
            raise ValueError(f"model {name!r}: context_window must be a positive int")
        models[name] = merged
    return models

TOML's typed values and [[array of tables]] make a registry like this readable and diff-friendly, and the defaults table removes repetition. Checking the merged settings means defaults are validated too. In a larger system this is where a Pydantic model (11.4) would take over; the shape of the code stays the same: parse, merge, validate, then hand out trusted objects.

import math, re
from collections import Counter

PATTERNS = [
    ("openai_key", re.compile(r"\bsk-[A-Za-z0-9_-]{20,}")),
    ("aws_access_key", re.compile(r"\bAKIA[0-9A-Z]{16}\b")),
    ("private_key", re.compile(r"-----BEGIN [A-Z ]*PRIVATE KEY-----")),
    ("password_assignment", re.compile(r"(?i)(?:password|passwd|secret|api_key|token)\w*['\"]?\s*[:=]\s*['\"][^'\"]{6,}['\"]")),
]
TOKEN = re.compile(r"[A-Za-z0-9+/=_-]{24,}")


def entropy(s):
    if not s:
        return 0.0
    n = len(s)
    return -sum(c / n * math.log2(c / n) for c in Counter(s).values())


def scan_for_secrets(text, min_entropy=4.5):
    findings = set()
    for n, line in enumerate(text.splitlines(), start=1):
        if "# allow-secret" in line:
            continue
        hits = {kind for kind, pattern in PATTERNS if pattern.search(line)}
        findings.update((n, kind) for kind in hits)
        if not hits and any(entropy(tok) >= min_entropy for tok in TOKEN.findall(line)):
            findings.add((n, "high_entropy"))
    return sorted(findings)

Secret scanners combine two signals. Patterns catch secrets with a known shape, such as provider key prefixes and private-key headers, with few false alarms, and an assignment pattern catches hard-coded passwords while ignoring os.environ["TOKEN"] (no quoted literal) and short dummy values. Entropy catches unknown formats: random keys use many different characters evenly, so they score near log2 of their length (5.0 for the 32 distinct characters here), while identifiers and English score lower (the long function name is about 3.8). The threshold is a trade-off: hex digests score about 4.0, so lowering it to 3.9 flags line 9, a false alarm for a checksum but a hit for a hex-encoded key. An explicit allow marker keeps test fixtures from blocking every commit. Real tools (gitleaks, detect-secrets, GitHub push protection) add hundreds of provider patterns and run on every commit and push.

import copy


def _drop(origin, dotted):
    for key in [k for k in origin if k == dotted or k.startswith(dotted + ".")]:
        del origin[key]


def _merge(target, src, name, origin, prefix):
    for key, value in src.items():
        path = prefix + (key,)
        dotted = ".".join(path)
        if isinstance(value, dict) and isinstance(target.get(key), dict):
            _merge(target[key], value, name, origin, path)
            continue
        _drop(origin, dotted)
        if isinstance(value, dict):
            target[key] = {}
            _merge(target[key], value, name, origin, path)
        else:
            target[key] = copy.deepcopy(value)
            origin[dotted] = name


def resolve(layers):
    merged, origin = {}, {}
    for name, layer in layers:
        _merge(merged, layer, name, origin, ())
    return merged, dict(sorted(origin.items()))

Every bug comes from treating configuration as constants. Module-level reads freeze the environment as it was at the first import, so tests that set variables, and a .env loaded after the import, have no effect; reading at call time (and, in an application, calling once at start-up and passing the result around) fixes that. The parsing bugs are the string traps of this lesson: bool("false") is True, a timeout that stays "2.5" breaks the HTTP client later and far away, and "".split(",") is [""], which would allow an empty origin in a CORS list. 16. How do you manage API keys and other secrets for an LLM application across development, CI and production?

SolutionModel answer

Secrets never live in code, notebooks or committed files. In development, each developer keeps their own keys in a git-ignored .env file (with a committed .env.example listing the names), loaded into the environment by the tooling. In CI, keys are stored as the CI system's encrypted secrets, exposed only to the jobs that need them and masked in logs; tests mostly use fakes, so few jobs need real keys. In production, a secret manager (AWS Secrets Manager, Azure Key Vault, GCP Secret Manager, Vault) stores them, and the platform injects them as environment variables or mounted files, or the application fetches them at start-up with its own identity, with access logged. Across all three: separate keys per environment and service, least privilege and spending limits on each key, regular rotation (two valid keys during a switch), masked types so settings can be logged safely, and secret scanning in pre-commit hooks and on push. The application reads everything once into a validated settings object at start-up and fails fast if a required secret is missing.

Interview

17. Why is configuration usually passed through environment variables, and what are their downsides?

SolutionModel answer

Environment variables are supported by every operating system, language, container runtime, CI system and cloud platform, so the same build artefact (a Docker image, say) can run anywhere and only its environment changes, which is the "twelve-factor" principle of strict separation of config from code. They are easy to override for one run and are not committed by accident the way files are. Their downsides: everything is a flat string, so types and nesting need conventions and careful parsing; there is no schema, so typos (APP_TEMPRATURE) are silently ignored unless the loader rejects unknown prefixed variables; they are inherited by child processes and can show up in crash reports, debug pages and /proc listings, so they are not perfect for secrets; and long structured settings are unreadable as variables. Hence the usual combination: typed defaults in code, a committed TOML or YAML file for structured non-secret settings, environment variables for per-deployment values and secrets, all validated into one settings object.

18. A teammate just pushed a commit containing a production API key. What do you do?

SolutionModel answer

Treat the key as compromised the moment it was pushed, because public repositories are scanned by bots within minutes and private ones are copied to clones, forks, CI caches and backups. First revoke or rotate the key at the provider, deploy the new key from the secret manager, and confirm the old one no longer works; this is the only step that actually stops misuse. Then check the provider's usage logs and billing for activity since the push, and follow the incident process if anything is suspicious. Next, clean up: remove the key from the code and read it from the environment, and if needed rewrite history (git filter-repo or BFG) and ask the hosting provider to purge cached views, knowing this only reduces exposure. Finally prevent a repeat: enable push protection and secret scanning on the repository, add a pre-commit scanner, move the value into the secret manager, and review why the key was in a file in the first place. Blameless and quick beats perfect and slow: rotation first, investigation second.

Recap

  • Keep configuration outside the code: defaults in code, non-secret structure in TOML, per-deployment values and secrets in the environment.
  • os.environ holds strings only: parse strictly (bool("false") is True), treat empty versus missing deliberately, and read at start-up, not at import.
  • .env files are for local development and are git-ignored; tomllib reads typed TOML (binary mode for files) but does not write it.
  • Layer with a deep merge (or ChainMap for flat settings), map APP_SECTION__KEY variables to nested keys, and be able to say where each value came from.
  • Never put secrets in code, logs or reprs; use masked types, secret managers, scanning, least privilege and rotation, and rotate first when a key leaks.
