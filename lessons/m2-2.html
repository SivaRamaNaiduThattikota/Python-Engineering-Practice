2.2 Mutable and immutable objects, and aliasing

Some objects can change in place, some never can. When two names point at one object that can change, a change through one name shows up everywhere. This lesson is about seeing that coming, in plain Python, in numpy and in pandas 3.

21 problems4 easy · 10 medium · 7 hard

1Objects that can change and objects that cannot

Every object is either mutable (it can be changed in place after it is created) or immutable (it can never change). When an object changes in place, its identity stays the same: same id(), same object, new contents. When you "change" an immutable value, Python builds a new object and moves the name, exactly like the rebinding you saw in 2.1.

Mutable: can change in placeImmutable: never changes
list, dict, set, bytearrayint, float, bool, complex, None
most objects of your own classesstr, bytes
numpy arrays, pandas DataFrames and Seriestuple, frozenset (but see the tuple trap below)
in_place.py
xs = [1, 2]
before = id(xs)
xs.append(3)               # changes the list itself
print(xs, id(xs) == before)

s = "data"
before = id(s)
s = s.upper()              # str cannot change: a new string, name moved
print(s, id(s) == before)
Output
[1, 2, 3] True
DATA False

A useful convention follows from this: in the standard library, methods that change an object in place return None. list.sort(), list.append(), dict.update(), set.add() and random.shuffle() all return None. Functions that leave their input alone and build something new return it: sorted(), reversed(), str.upper(). Writing xs = xs.sort() therefore replaces your list with None (problem 3).

It is worth knowing the full list of in-place list operations, because each one changes the object every alias sees: append, extend, insert, pop, remove, clear, sort, reverse, del xs[i], xs[i] = v, and slice assignment, xs[:] = new_items. The last one is the subtle one. xs = new_items rebinds the name and leaves the old list alone, while xs[:] = new_items keeps the same list object and replaces its contents, so every alias sees the new items. Code that "resets" a shared list has to choose between the two on purpose.

slice_assign.py
shared = [1, 2, 3]
alias = shared
shared = [9]                   # rebinding: alias still sees the old list
print(alias)

shared = alias
shared[:] = [9]                # slice assignment: same object, new contents
print(alias, alias is shared)
Output
[1, 2, 3]
[9] True

Why have immutable types at all? Three reasons, all practical. An immutable object can be shared safely: you can pass a string or a tuple anywhere without worrying that someone will change it under you. It can be hashed, which is what dict keys and set members need: a key's hash must never change, or the dict could no longer find it (4.5). And it is simpler to reason about in concurrent code, since two threads cannot race to change it. When you need a read-only version of a mutable type, Python has some: tuple for lists, frozenset for sets, and types.MappingProxyType(d), a read-only view of a dict that reflects changes to d but refuses writes through itself.

read_only.py
from types import MappingProxyType

_settings = {"model": "small"}
SETTINGS = MappingProxyType(_settings)
try:
    SETTINGS["model"] = "large"
except TypeError as e:
    print("TypeError:", e)
_settings["model"] = "medium"            # the owner can still change it
print(SETTINGS["model"], frozenset({"a", "b"}) == frozenset({"b", "a"}))
Output
TypeError: 'mappingproxy' object does not support item assignment
medium True

2Aliasing: one object, several names

Aliasing means two or more names, or container slots, point at the same object. With immutable objects aliasing is harmless, because nobody can change the object. With mutable objects every change made through any of the names is visible through all of them, because there is only one object.

aliasing.py
config = {"model": "small", "temperature": 0.2}
run_a = config                 # an alias, not a copy
run_a["temperature"] = 0.9
print(config["temperature"])   # the "original" changed too

defaults = {"retries": 3}
settings = {"api": defaults, "batch": defaults}   # both slots point at one dict
settings["api"]["retries"] = 5
print(settings["batch"]["retries"])
Output
0.9
5

Aliases hide in places that do not look like assignment:

  • Containers: putting the same list or dict into two slots (above), or dict.fromkeys(keys, []), which uses one list for every key (problem 5).
  • Return values: a function that returns its internal list hands the caller a way to change its state (problem 6).
  • Repetition: [[]] * 3 repeats one inner list three times (the grid trap; lesson 2.3 shows the fix).
  • Default arguments and function arguments (lesson 2.4).
≈
SQL / Power BI

An alias is like two Power BI visuals bound to the same measure. Edit the measure and both visuals change, because there is one measure, not two. A copy is like duplicating the measure under a new name: editing one no longer touches the other.

Aliasing also happens in time: the same list being changed while it is being read. Removing items from a list while a for loop walks over it skips items, because the loop keeps an index into the list and every removal shifts the remaining items one place to the left, under the index. The loop then steps over the item that moved into the gap. The fix is to build a new list (a comprehension, 6.1), or to loop over a copy, for x in xs[:].

mutate_while_iterating.py
scores = [0.2, 0.1, 0.9, 0.3, 0.05]
for s in scores:
    if s < 0.5:
        scores.remove(s)               # changing the list being iterated
print(scores)                          # 0.1 and 0.05 survived

scores = [0.2, 0.1, 0.9, 0.3, 0.05]
print([s for s in scores if s >= 0.5]) # a new list instead
Output
[0.1, 0.9, 0.05]
[0.9]

Step by step: the loop reads index 0 (0.2), removes it, and everything shifts left, so 0.1 is now at index 0. The loop moves on to index 1, which now holds 0.9, so 0.1 is never checked. The same happens to 0.05 after 0.3 is removed. Dicts and sets protect themselves: changing their size during iteration raises RuntimeError: dictionary changed size during iteration, which is noisier but much safer.

3Changing versus rebinding: +=, + and friends

For a list, x += y changes the list in place (it is x.extend(y) under the hood), while x = x + y builds a new list and moves the name. With an alias around, they give different results. For immutable types there is no in-place version, so += on a str, tuple or int always builds a new object.

plus_equals.py
x = [1]; y = x
x += [2]                      # in place: y sees it
print(x, y, x is y)

x = [1]; y = x
x = x + [2]                   # new list: y keeps the old one
print(x, y, x is y)

t = (1,); u = t
t += (2,)                     # tuple: always a new object
print(t, u)
Output
[1, 2] [1, 2] True
[1, 2] [1] False
(1, 2) (1,)

The mechanism behind this: x += y first asks the type of x for an in-place add (the method __iadd__). Lists, dicts (|=), sets (|=, &=, -=), numpy arrays and DataFrames provide one, so the object changes and the name is then re-bound to the same object. If the type has no in-place version, as for int, str and tuple, Python falls back to x = x + y: it builds a new object and rebinds the name. The same rule covers -=, *=, |= and the others.

One famous consequence combines everything so far. t[0] += [3], where t is a tuple holding a list, first extends the list in place (that succeeds), then tries to store the result back into t[0] (that fails, because tuples cannot be assigned to). You get a TypeError and the list has changed.

iadd_details.py
t = ([1, 2], "label")
try:
    t[0] += [3]
except TypeError as e:
    print("TypeError:", e)
print(t)                              # the list changed anyway

import numpy as np
a = np.array([1.0, 2.0]); b = a
a *= 10                               # in place on the shared array
print(b)
Output
TypeError: 'tuple' object does not support item assignment
([1, 2, 3], 'label')
[10. 20.]

4Tuples are immutable, their contents may not be

A tuple cannot change which objects it holds: you cannot assign t[0] = .... But if one of those objects is mutable, that object can still change in place. So a tuple is only "frozen" all the way down if everything inside it is immutable too. That is also the rule for using a tuple as a dict key or set member: (1, "a") works, ([1], "a") raises TypeError: unhashable type: 'list'.

tuple_contents.py
t = ([1, 2], "label")
t[0].append(3)                # the list inside can change
print(t)
try:
    hash(t)
except TypeError as e:
    print("TypeError:", e)
print(hash((1, "label")) == hash((1, "label")))
Output
([1, 2, 3], 'label')
TypeError: unhashable type: 'list'
True

The hash rule is the reason. A tuple's hash is computed from the hashes of its items, so if an item could change, the tuple's hash would change with it, and a dict that stored the tuple as a key would look for it in the wrong place. Python therefore refuses to hash a tuple that contains anything unhashable. When you need a composite key with a "set-like" part, such as a combination of tags, use a frozenset, which is hashable and ignores order.

hashable_keys.py
runs = {}
runs[("small", frozenset({"eu", "prod"}))] = 0.91
print(runs[("small", frozenset({"prod", "eu"}))])     # order of tags does not matter
Output
0.91

5numpy views and pandas 3 Copy-on-Write

Data libraries make aliasing more important, because copying big arrays is expensive. numpy returns a view for basic slicing: a new array object that looks at the same memory. Changing the view changes the original. Boolean masks and lists of indexes ("fancy indexing") return a copy instead.

numpy_views.py
import numpy as np

a = np.arange(6)
first = a[:3]                 # basic slice: a view
first[0] = 99
print(a, np.shares_memory(a, first))

picked = a[a > 3]             # boolean mask: a copy
picked[0] = -1
print(a, np.shares_memory(a, picked))
Output
[99  1  2  3  4  5] True
[99  1  2  3  4  5] False

Other numpy operations return views too: reshape (when the memory layout allows it), the transpose a.T, and a.ravel() in the common case. When you need an independent array, call .copy() explicitly. That is cheap insurance in two situations: when you slice a small part of a huge array and want to keep only the part (the view keeps the whole big buffer alive, 2.1), and when you hand an array to code that might change it.

numpy_more_views.py
import numpy as np

big = np.zeros(1_000_000)
small_view = big[:3]
small_copy = big[:3].copy()
print(small_view.base is big, small_copy.base is None)
m = np.arange(6).reshape(2, 3)
m.T[0, 0] = 42
print(m[0, 0], np.shares_memory(m, m.T))
Output
True True
42 True

pandas used to behave in a confusing mix of views and copies, which is what SettingWithCopyWarning was about. pandas 3.0 made Copy-on-Write the only behaviour: anything you take out of a DataFrame (a column, a filtered subset) acts as its own copy, so changing it never changes the original. To change the original, change it directly with .loc.

pandas_cow.py
import pandas as pd

df = pd.DataFrame({"x": [1, 2, 3]})
sub = df[df["x"] > 1]
sub["x"] = 0                  # changes sub only
col = df["x"]
col.iloc[0] = 100             # changes col only
print(df["x"].tolist(), sub["x"].tolist(), col.tolist())

df.loc[df["x"] > 1, "x"] = 7  # the way to change df itself
print(df["x"].tolist())
print(pd.__version__)
Output
[1, 2, 3] [0, 0] [100, 2, 3]
[1, 7, 7]
3.0.2
!
Old tutorials are wrong now

Many tutorials, Stack Overflow answers and older code were written for pandas 1.x and 2.x, where col = df["x"]; col.iloc[0] = 100 did change df, and chained assignment like df["x"][1] = 5 sometimes worked. In pandas 3 that chained form silently does nothing to df and only emits a ChainedAssignmentError warning. Always write df.loc[row, "x"] = value.

Hint 2Open a hint

SolutionShow the solution and why
solution.py
def normalise_inplace(weights):
    total = sum(weights)
    if total == 0:
        raise ValueError("weights sum to 0")
    weights[:] = [w / total for w in weights]

weights[:] = new_list replaces the contents of the existing list, so every alias sees the new values. A plain weights = [...] inside the function would create a new list visible only inside the function, and the caller's list would stay unchanged (lesson 2.4 explains why). Returning None signals "I changed your object", the same promise list.sort() makes. Choosing in place versus returning a new list is an API decision: in place saves memory for huge data, returning new is safer to reason about.

_store = {"c1": [{"role": "user", "content": "hi"}, {"role": "assistant", "content": "Hello!"}]}

t[0] += [3] runs as tmp = t[0]; tmp = tmp.__iadd__([3]); t[0] = tmp. The first part extends the list in place, and it succeeds. Then Python tries to store the result back into t[0], which a tuple refuses, so you get the TypeError. But the list already changed. An operation that raises and still has its effect is very surprising, and this is a famous interview puzzle. t[0].extend([3]) does the same change without the error.

16. Read the code: embedding batches

This splits texts into batches for an embedding API, with at most max_items texts and at most max_tokens (rough count: words) per batch. Each batch also gets a small metadata dict. The output is wrong in two ways that both come from aliasing. Read the whole function, find both bugs and fix them.

Hint 1Open a hint

After batches.append({"texts": batch, ...}), what does batch.clear() do to the list just stored?

Hint 2Open a hint

The same question for meta: how many meta dicts exist in the whole run?

Hint 3Open a hint

SolutionShow the solution and why
solution.py
def count_tokens(text):
    return len(text.split())


def make_batches(texts, max_items, max_tokens):
    batches = []
    batch = []
    meta = {"tokens": 0, "items": 0}
    for text in texts:
        n = count_tokens(text)
        if batch and (len(batch) == max_items or meta["tokens"] + n > max_tokens):
            batches.append({"texts": batch, "meta": meta})
            batch = []
            meta = {"tokens": 0, "items": 0}
        batch.append(text)
        meta["tokens"] += n
        meta["items"] += 1
    if batch:
        batches.append({"texts": batch, "meta": meta})
    return batches

batches.append({"texts": batch, ...}) stores a reference to the list, not a snapshot. batch.clear() then empties that very list, and the loop keeps appending to it, so every stored batch is the same list. The metadata has the same bug: one meta dict is shared by all batches and reset in place. The fix is to bind the names to new objects (batch = [], meta = {...}) so the stored ones are left alone. "Reuse and clear" is a common habit from languages without garbage collection, and in Python it turns into aliasing bugs. Sent to a real embedding API, the buggy version would embed the wrong texts with no error at all.

17. Hashable cache keys from tool arguments

An agent caches tool results keyed by the tool's arguments, which arrive as JSON-like data: dicts, lists, strings, numbers, booleans and None, nested to any depth. Dicts and lists are mutable, so they cannot be dict keys. Write freeze(value) that turns such data into an equivalent hashable value: lists become tuples, dicts become a tuple of (key, frozen_value) pairs sorted by key, and everything else stays as it is. Two inputs that are equal (whatever the key order) must give equal results.

TestsThe 6 checks Run tests uses

assert cache[freeze(b)] == "result"
assert freeze({"q": ["x", "y"]}) != freeze({"q": ["y", "x"]})
assert freeze([1, [2, None]]) == (1, (2, None))
assert freeze("text") == "text"
Hint 1Open a hint

Handle three cases: dict, list, anything else. The dict and list cases call freeze on their contents.

Hint 2Open a hint

sorted(d.items()) sorts the pairs by key. Freeze each value inside the pairs.

SolutionShow the solution and why
solution.py
def freeze(value):
    if isinstance(value, dict):
        return tuple(sorted((k, freeze(v)) for k, v in value.items()))
    if isinstance(value, list):
        return tuple(freeze(v) for v in value)
    return value

Hashing needs the value to never change, so every mutable layer has to become an immutable one, at every depth: that is why it must recurse. Sorting the dict pairs makes key order irrelevant, matching dict equality, while list order is kept because ["x", "y"] and ["y", "x"] are different arguments. A common shortcut is json.dumps(value, sort_keys=True) as the key, which also works and is easy to log. It is slower and treats 1 and 1.0 differently, while freeze treats them as equal, which is the same rule dicts use. Pick the one whose equality matches what you want cached.

Interview

19. Which built-in types are mutable, and why does it matter?

SolutionModel answer

Mutable: list, dict, set, bytearray, and most user-defined objects. Immutable: int, float, bool, complex, str, bytes, tuple, frozenset, None. It matters in three places. First, aliasing: any name or container that shares a mutable object sees every change, which causes action-at-a-distance bugs. Second, hashing: only values that cannot change can be dict keys or set members, because a key whose hash changed could never be found again. Third, defaults and arguments: a mutable default argument is created once and shared between calls (lesson 2.4). A strong answer adds that a tuple is only as immutable as its contents, and mentions numpy views and pandas Copy-on-Write for data roles.

Interview

20. Explain what happens in t = ([1], 2); t[0] += [3].

SolutionModel answer

It raises TypeError: 'tuple' object does not support item assignment, and t becomes ([1, 3], 2). Augmented assignment on an item is two steps: call t[0].__iadd__([3]), which extends the list in place and succeeds, then assign the result back to t[0], which the tuple refuses. The interviewer wants to hear that you know += on a list is in place, and that a tuple's immutability only covers which objects it holds, not those objects' contents. Mention that t[0].extend([3]) makes the same change without raising.

Interview

21. What was SettingWithCopyWarning, and what changed in pandas 3?

SolutionModel answer

In pandas 1.x and 2.x, indexing could return either a view of the DataFrame or a copy, and it was hard to predict which. Writing to a result that might be a copy, such as sub = df[mask]; sub["x"] = 0 or chained assignment df[mask]["x"] = 0, raised SettingWithCopyWarning because the write might or might not reach df. pandas 3.0 made Copy-on-Write the only behaviour: every object you derive from a DataFrame behaves as its own copy, copying lazily only when one side is changed. So writes to derived objects never reach the original, the warning is gone, and chained assignment never works (it warns with ChainedAssignmentError). The correct way to change df in every version is df.loc[mask, "x"] = 0. Bonus: Copy-on-Write also saves memory, because derived objects share data until someone writes.

Recap

  • Mutable objects (list, dict, set, arrays, DataFrames) change in place and keep their identity. Immutable ones never change: "changing" them builds a new object.
  • Standard-library methods that change an object in place return None: xs = xs.sort() loses your list. Use sorted() for a new one.
  • Aliases hide in containers, return values, dict.fromkeys(keys, []) and [[]] * n. Return new objects when callers should not change yours.
  • On a list, x += y changes the shared object; x = x + y builds a new one. xs[:] = ... replaces the contents in place.
  • numpy basic slices are views; masks and .copy() are copies. pandas 3 is always Copy-on-Write: change a DataFrame only through df.loc[...].
