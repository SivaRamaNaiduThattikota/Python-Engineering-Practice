4.3 Tuples and unpacking

What makes something a tuple (the comma, not the brackets), how packing and unpacking work step by step, star unpacking, named tuples as lightweight records, and tuples as composite keys, the Python version of a SQL composite primary key.

19 problems4 easy · 9 medium · 6 hard

1What a tuple is, and what makes one

A tuple is an immutable sequence: a fixed-size array of references (like a list, 4.1) that can never change after it is created. You cannot assign to a position, append, remove or sort it in place. Indexing, slicing, len, in, count and index all work as for lists, and slicing a tuple returns a new tuple.

The part that trips people up: the comma makes the tuple, not the parentheses. Parentheses are only needed when the expression would otherwise be ambiguous, and for the empty tuple (). A one-item tuple needs a trailing comma, and a stray trailing comma creates a tuple you did not mean to create.

comma.py
a = (1)          # just the number 1 in brackets
b = (1,)         # a one-item tuple
c = 1, 2         # a tuple without any brackets
d = ()           # the empty tuple
e = "rag",       # a trailing comma: a tuple again
print(type(a).__name__, type(b).__name__, c, d, e)

config_name = "prod",       # a typo that makes a tuple instead of a string
print(f"loading {config_name}")
Output
int tuple (1, 2) () ('rag',)
loading ('prod',)

Why choose a tuple over a list? Three concrete reasons. Safety: nobody can change it, so it can be shared and returned without the copying worries of Module 2. Hashability: a tuple of hashable items can be a dict key or a set member (the last section). Meaning: by convention, a list is "many items of the same kind" and a tuple is "a fixed record whose positions mean different things", like (latitude, longitude) or (name, score). Tuples are also slightly smaller and faster to create, and a tuple of constants is built once at compile time (problem 7).

≈
SQL / Power BI

A tuple is like one row of a table: a fixed set of columns in a fixed order, each with its own meaning. A list is like a column: many values of the same kind. A list of tuples is a small table, which is exactly what a database driver returns from cursor.fetchall().

2Packing and unpacking, step by step

Unpacking assigns the items of any iterable to several names: x, y = point. Step by step, Python evaluates the whole right-hand side first, then checks that it yields exactly as many items as there are names, then assigns them from left to right. Too many or too few items raise ValueError with a message that says which.

unpacking.py
point = 3, 4                    # packing
x, y = point                    # unpacking
name, (lo, hi) = "latency", (12, 48)   # nested: the shape on the left matches the right
print(x, y, name, lo, hi)

for i, (doc, score) in enumerate([("faq", 0.9), ("guide", 0.7)], start=1):
    print(i, doc, score)

for bad in ["a, b = (1, 2, 3)", "a, b, c = (1, 2)", "a, b = 5"]:
    try:
        exec(bad)
    except (ValueError, TypeError) as e:
        print(f"{bad:18} -> {type(e).__name__}: {e}")
Output
3 4 latency 12 48
1 faq 0.9
2 guide 0.7
a, b = (1, 2, 3)   -> ValueError: too many values to unpack (expected 2, got 3)
a, b, c = (1, 2)   -> ValueError: not enough values to unpack (expected 3, got 2)
a, b = 5           -> TypeError: cannot unpack non-iterable int object

Swapping two variables is the most famous use: a, b = b, a. The right side b, a is evaluated completely first, using the old values, and only then are the names assigned. That is why no temporary variable is needed. The same rule makes a, b = b, a + b (the Fibonacci step) correct: both new values are computed from the old ones before either name changes.

swap.py
a, b = 0, 1
for _ in range(6):
    a, b = b, a + b
print(a, b)
Output
8 13

3Star unpacking

A starred name on the left collects all the leftover items into a list. It can appear at the start, the end or the middle, but only once, because otherwise the split would be ambiguous. If nothing is left over it is an empty list, never None, and it is always a list, even when the right side is a tuple or a string.

star_unpacking.py
first, *rest = ["system", "user", "assistant", "user"]
*history, last = ["system", "user", "assistant", "user"]
head, *middle, tail = "abcde"
only, *nothing = ("x",)
print(first, rest)
print(history, last)
print(head, middle, tail, only, nothing)

header, *rows = [("id", "score"), (1, 0.9), (2, 0.4)]   # a CSV-like table
print(header, rows)
Output
system ['user', 'assistant', 'user']
['system', 'user', 'assistant'] user
a ['b', 'c', 'd'] e x []
('id', 'score') [(1, 0.9), (2, 0.4)]

The same star works in literals and calls, in the other direction: it spreads an iterable into separate items. [*a, *b] concatenates any iterables into a list, (*a, x) builds a tuple, {**d1, **d2} merges dicts, and f(*args) spreads arguments (3.2). And zip(*rows) uses it to turn rows into columns: each row becomes one argument of zip, which then pairs up the first items, the second items and so on (problem 13).

star_spread.py
rows = [("faq", 0.9, 120), ("guide", 0.7, 340), ("terms", 0.2, 80)]
names, scores, tokens = zip(*rows)
print(names, scores, tokens)
print([*names, "extra"], (*scores, 1.0))
Output
('faq', 'guide', 'terms') (0.9, 0.7, 0.2) (120, 340, 80)
['faq', 'guide', 'terms', 'extra'] (0.9, 0.7, 0.2, 1.0)

4Named tuples: records without a class

Positions are fine for two or three fields, but result[2] says nothing about what the value is. A named tuple gives each position a name while staying a real tuple: immutable, hashable, unpackable, and comparable to plain tuples. typing.NamedTuple is the modern way to write one, with type hints; collections.namedtuple is the older factory function.

named_tuple.py
from typing import NamedTuple

class Metrics(NamedTuple):
    precision: float
    recall: float
    support: int = 0

m = Metrics(0.82, 0.61, support=140)
print(m.recall, m[1], m)
p, r, n = m                                  # still a tuple: unpacks by position
print(p, r, n, m == (0.82, 0.61, 140))
better = m._replace(recall=0.7)              # "changing" means building a new one
print(better, m.recall, m._asdict())
try:
    m.recall = 0.9
except AttributeError as e:
    print("AttributeError:", e)
Output
0.61 0.61 Metrics(precision=0.82, recall=0.61, support=140)
0.82 0.61 140 True
Metrics(precision=0.82, recall=0.7, support=140) 0.61 {'precision': 0.82, 'recall': 0.61, 'support': 140}
AttributeError: can't set attribute

Named tuples shine for function results (return Metrics(p, r, n) instead of a bare tuple whose order a caller can confuse, problem 4) and for rows of fixed shape. Their limits: they are immutable (_replace builds a new one), and because they are tuples, m == (0.82, 0.61, 140) is True: they compare equal to any tuple with the same values, which can hide mix-ups between two different record types. When you need mutability, validation or methods, use a dataclass (Module 11).

5Tuples as keys

A tuple is hashable when all its items are hashable, so it can be a dict key or a set member. That makes tuples the natural composite key: "one entry per user per day" is a dict keyed by (user_id, day), exactly like a composite primary key in SQL. Tuples also compare lexicographically: first items first, and only if they are equal, the second items, and so on, which is why tuple keys sort by several rules at once (3.5).

tuple_keys.py
usage = {}
events = [("ana", "2025-06-01", 120), ("ben", "2025-06-01", 50), ("ana", "2025-06-01", 30), ("ana", "2025-06-02", 70)]
for user, day, tokens in events:
    key = (user, day)                     # composite key
    usage[key] = usage.get(key, 0) + tokens
print(usage)

print((1, "b") < (1, "c"), (1, 2) < (1, 2, 0), (2,) > (1, 99))
try:
    hash(("ana", ["tag"]))
except TypeError as e:
    print("TypeError:", e)
Output
{('ana', '2025-06-01'): 150, ('ben', '2025-06-01'): 50, ('ana', '2025-06-02'): 70}
True True True
TypeError: unhashable type: 'list'

Remember the caveat from 2.2: a tuple is only as immutable as its contents. ("ana", ["tag"]) cannot be a key, because the list inside could change. When building cache keys from data that may contain lists or dicts, convert them first (2.2, freeze).

HintOpen a hint

first, *rest = words puts everything after the first word in rest. The last name is then rest[-1] if there is one.

SolutionShow the solution and why
solution.py
def first_last(full_name):
    words = full_name.split()
    if not words:
        return "", ""
    first, *rest = words
    return first, rest[-1] if rest else ""

split() with no argument splits on any run of whitespace and ignores leading and trailing spaces. Real names are messier (prefixes, particles such as "de la", non-Western order), which is why CRM systems store name parts separately instead of splitting them.

4. Metrics returned in a confusing order

evaluate returns (recall, precision, f1), and callers keep unpacking it as precision, recall, f1, reporting swapped numbers. Return a NamedTuple called Metrics with fields precision, recall, f1, so callers can use names.

HintOpen a hint

Define class Metrics(NamedTuple): with three float fields, in the order precision, recall, f1, and return Metrics(...).

SolutionShow the solution and why
solution.py
from typing import NamedTuple

class Metrics(NamedTuple):
    precision: float
    recall: float
    f1: float

def evaluate(tp, fp, fn):
    precision = tp / (tp + fp) if tp + fp else 0.0
    recall = tp / (tp + fn) if tp + fn else 0.0
    f1 = 2 * precision * recall / (precision + recall) if precision + recall else 0.0
    return Metrics(precision, recall, f1)

A bare tuple forces every caller to remember positions, and precision and recall are both floats between 0 and 1, so a swap never raises an error: it just produces a wrong report. With a named tuple, m.precision cannot be confused, and old callers that unpack still work because it is still a tuple. Fixing the order to precision, recall also matches the usual convention (scikit-learn's precision_recall_fscore_support returns them in that order).

Hint 1Open a hint

for name, _args, (latency, tokens) in calls: unpacks the nested tuple directly. _args signals "not used".

Hint 2Open a hint

Keep the running tuple in the dict and rebuild it each time: tuples cannot be changed in place.

SolutionShow the solution and why
solution.py
def summarise(calls):
    out = {}
    for name, _args, (latency, tokens) in calls:
        count, total, worst = out.get(name, (0, 0, 0))
        out[name] = (count + 1, total + tokens, max(worst, latency))
    return out

The loop header mirrors the shape of each record, so the body works with names instead of call[2][1]. Because a tuple cannot change, each update unpacks the current totals and stores a new tuple; for many updates a small mutable object (a list, a dict or a dataclass) would avoid rebuilding, but the immutable version cannot be corrupted by another part of the code holding a reference. The leading underscore in _args is a convention that tells readers and linters the value is intentionally unused.

7. Creating a tuple or a list of constants

Both build a small record of five constants a million times. Which loop is faster?

setup

HintOpen a hint

A tuple of constants can never change. What can the compiler do with it?

SolutionShow the solution and why

Because a tuple of constants is immutable, the compiler builds it once, when the code is compiled, and stores it as a constant: each pass of the loop just loads that one object. A list must be a new object every time (someone might change it), so each pass allocates a list and fills five slots. This is a small effect per object, but it is one reason tuples suit fixed records and constant tables.

HintOpen a hint

The day is the part before "T". Keep a set of (user, day) tuples you have already seen.

SolutionShow the solution and why
solution.py
def first_per_day(events):
    seen = set()
    out = []
    for e in events:
        key = (e["user"], e["ts"].split("T")[0])
        if key not in seen:
            seen.add(key)
            out.append(e)
    return out

The tuple (user, day) is the composite key: two events collide only when both parts match, which a single string key would also do (f"{user}|{day}") but with the risk of a separator appearing inside a value. Tuples need no separator and keep the parts typed. This is SQL's ROW_NUMBER() OVER (PARTITION BY user, day ORDER BY ts) = 1; in pandas, df.drop_duplicates(subset=["user", "day"]).

SolutionShow the solution and why
solution.py
_cache = {}

def cache_key(model, prompt, stop):
    return (model, prompt, tuple(stop))

def cached(model, prompt, stop, compute):
    key = cache_key(model, prompt, stop)
    if key not in _cache:
        _cache[key] = compute(prompt)
    return _cache[key]

Dict keys must be hashable, so the outer list must become a tuple. But (model, prompt, stop) would still fail, because a tuple is only hashable when everything inside it is, and stop is a list (2.2). tuple(stop) fixes the inner level. Including the model in the key matters: the same prompt sent to a different model must not reuse an answer, as the third call shows. For nested argument dicts, use the recursive freeze from 2.2.

Hint 2Open a hint

SolutionShow the solution and why
solution.py
def columns(rows):
    return list(zip(*rows, strict=True))

def unzip_pairs(pairs):
    if not pairs:
        return [], []
    names, scores = zip(*pairs)
    return list(names), list(scores)

zip(*rows) spreads the rows into separate arguments, and zip then yields the first items of every row, then the second items, which is a transpose. strict=True turns a ragged table into an error instead of silently dropping the extra values. The empty case is the classic trap: zip(*[]) is zip(), which yields nothing, so names, scores = ... raises "not enough values to unpack". The guard makes the function total. For real tables, pandas.DataFrame(rows).T or numpy.array(rows).T do this on whole arrays.

DEFAULT_TOOLS = ("search",)


def parse(line, allowed=DEFAULT_TOOLS):
    tool, *args = line.split()
    if tool not in allowed:
        raise ValueError(f"unknown tool {tool!r}")
    return tool, tuple(args)


_results = {}


def run(line, impl):
    call = parse(line)
    if call not in _results:
        tool, args = call
        _results[call] = impl(tool, *args)
    return _results[call]

("search") is just a string, so tool not in allowed became a substring test: "s", "ear" and "search" all passed as tools, a real security hole for an agent that should only run allowed tools. The trailing comma makes it a one-item tuple, where in checks whole items. Bug two: star unpacking always gives a list, so (tool, args) contains a list and cannot be a dict key. Converting with tuple(args) makes the call hashable and also matches what the tests expect from parse. Allow-lists should be sets ({"search", "calc"}, 4.4), which avoids the comma trap entirely and makes membership O(1).

15. A confusion matrix from pairs

Write confusion(pairs) for (actual, predicted) label pairs, returning a dict keyed by (actual, predicted) tuples with counts, and per_class(conf, label) returning a NamedTuple PRF(precision, recall, support) for one label, where support is the number of items whose actual label is label. Hint 1Open a hint

Count with conf[(a, p)] = conf.get((a, p), 0) + 1.

Hint 2Open a hint

True positives are conf.get((label, label), 0). Predicted-as-label sums keys whose second item is label; support sums keys whose first item is label.

SolutionShow the solution and why
solution.py
from typing import NamedTuple


class PRF(NamedTuple):
    precision: float
    recall: float
    support: int


def confusion(pairs):
    conf = {}
    for actual, predicted in pairs:
        conf[(actual, predicted)] = conf.get((actual, predicted), 0) + 1
    return conf


def per_class(conf, label):
    tp = conf.get((label, label), 0)
    predicted = sum(n for (a, p), n in conf.items() if p == label)
    support = sum(n for (a, p), n in conf.items() if a == label)
    precision = tp / predicted if predicted else 0.0
    recall = tp / support if support else 0.0
    return PRF(precision, recall, support)

The tuple key (actual, predicted) is one cell of the confusion matrix, and unpacking (a, p), n in the comprehensions reads each cell by name. Precision divides by everything predicted as the label (a column of the matrix), recall by everything actually the label (a row). Returning a named tuple keeps the three numbers from being confused (problem 4) while still comparing equal to a plain tuple, which the last test uses. scikit-learn's confusion_matrix and classification_report compute the same numbers on arrays.

Tuples compare position by position and stop at the first difference: (1, 2) < (1, 2, 0) because a shorter tuple that is a prefix of a longer one comes first, and (2,) > (1, 99) is decided by 2 > 1 alone. Comparing (1, None) with (1, 2) reaches None < 2, which Python refuses. (1, None) < (2, None) never compares the Nones, because the first items already differ, so it works. That is why a tuple sort key with None in it can work on one dataset and crash on another. Hashing a tuple hashes every item, so a list anywhere inside makes it unhashable.

9Interview questions

Interview

17. When do you use a tuple, and when a list?

SolutionModel answer

A list is for a variable-length collection of similar items that you add to, remove from or sort. A tuple is for a fixed-length record whose positions mean different things, and for anything that must not change: return values, constants, composite dict keys and set members. Tuples are immutable (safe to share, no defensive copies), hashable when their contents are, slightly smaller, and a tuple of constants is built once at compile time. Caveats: a tuple's immutability is shallow (a list inside can still change and makes it unhashable), and for records with more than two or three fields a named tuple or dataclass is clearer than positions.

Interview

18. Why can a tuple be a dict key but a list cannot? Can every tuple be a key?

SolutionModel answer

Dict keys are found by hash, and the hash must never change while the key is in the dict, so keys must be immutable in everything that affects equality. A list can change, so lists are unhashable by design. A tuple cannot change which objects it holds, so its hash is computed from its items' hashes. But that only works if every item is hashable: (1, "a") is a valid key, (1, [2]) raises TypeError: unhashable type: 'list'. To key by nested data, convert inner lists to tuples (and dicts to sorted item tuples or frozensets) first.

Interview

19. How does a, b = b, a work, and is it the same as a = b; b = a?

SolutionModel answer

No. In a, b = b, a, the entire right side is evaluated first, producing the old values of b and a; only then are the targets assigned, left to right. So the values swap without a temporary variable. a = b; b = a assigns a first, and the second statement then copies the new a back into b, so both end up with the old value of b. Under the hood CPython does not even build a tuple for a two- or three-item swap: it evaluates both values onto its stack and swaps them there. Mention the left-to-right assignment order, which explains surprises like i, xs[i] = 1, 9.

Recap

  • The comma makes a tuple, not the brackets: (1,) is a tuple, (1) is not, and a stray trailing comma creates one.
  • Unpacking evaluates the whole right side first, then assigns left to right; counts must match exactly.
  • first, *rest = items collects leftovers into a list; * in literals and calls spreads; zip(*rows) transposes.
  • Named tuples give positions names while staying tuples: immutable, hashable, and equal to plain tuples with the same values.
  • Tuples of hashable items make composite keys, like a SQL composite primary key, and compare position by position.
