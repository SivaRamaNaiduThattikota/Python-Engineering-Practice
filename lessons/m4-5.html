4.5 Dicts: the basics

A dict maps keys to values with O(1) lookups and keeps insertion order. How to read values safely, why views are live and why you cannot change a dict while looping over it, merging with clear precedence, and the hash join: the SQL join you can write in four lines.

19 problems4 easy · 10 medium · 5 hard

1What a dict is

A dict maps keys to values. Under the hood it is a hash table, like a set (4.4), where each key's slot also stores its value. So d[key], d[key] = value, del d[key] and key in d are all O(1) on average, however many items the dict holds. Keys must be hashable (strings, numbers, tuples of those, frozensets); values can be anything at all, including lists and other dicts.

Since Python 3.7 dicts also keep insertion order: iterating gives keys in the order they were first added. CPython achieves this with a "compact" layout: a small hash index points into a separate array of entries stored in insertion order, which also uses less memory than the old design. Assigning a new value to an existing key keeps its position; deleting a key and adding it again moves it to the end.

dict_basics.py
prices = {"basic": 0, "pro": 20, "team": 50}
print(prices["pro"], "team" in prices, 20 in prices, len(prices))   # `in` checks keys, not values
prices["enterprise"] = 200          # new key: goes at the end
prices["basic"] = 5                 # existing key: same position
del prices["pro"]
prices["pro"] = 25                  # re-added: now at the end
print(list(prices))
Output
20 True False 3
['basic', 'team', 'enterprise', 'pro']

SQL / Power BI

A dict is a lookup table with a primary key: prices["pro"] is SELECT price FROM prices WHERE plan = 'pro' against an indexed key, and a missing key is "no row". In Power BI it is the dimension side of a relationship: you look up attributes by the key, and the key must be unique, which a dict guarantees (a repeated key overwrites).

cfg = {"model": "small", "timeout": 0, "stop": None}

Two subtleties. d.get(k, default) returns the default only when the key is absent; if the key is present with the value None, you get None. When "absent" and "present but None" must be distinguished, use k in d or a sentinel default (2.1). And never write d.get(k) or default for values that can legitimately be 0, "" or []: or replaces them too (1.1).

For nested JSON, chained get calls with {} defaults avoid a crash at each level: resp.get("usage", {}).get("total_tokens", 0). That works for one or two levels; for deep paths, write a helper (problem 6).

3Iterating, and changing a dict safely

Looping over a dict gives its keys. d.items() gives (key, value) pairs, which you unpack in the loop header (4.3), and d.values() gives the values. These three are views: live windows onto the dict, not copies. They are cheap, they reflect later changes, and keys() and items() support set operations (4.4).

views.py
counts = {"refund": 3, "login": 0, "invoice": 7}
keys = counts.keys()
counts["shipping"] = 2
print(list(keys))                          # the view sees the new key
for word, n in counts.items():
    print(f"{word}:{n}", end=" ")
print()
print(sum(counts.values()), sorted(counts.keys() - {"login"}))
Output
['refund', 'login', 'invoice', 'shipping']
refund:3 login:0 invoice:7 shipping:2 
12 ['invoice', 'refund', 'shipping']

Because a view is live, you cannot add or remove keys while iterating over a dict or its views: Python detects the size change and raises RuntimeError: dictionary changed size during iteration. Changing the value of an existing key is fine. To delete while looping, loop over a snapshot (list(d)), or better, build a new dict with a comprehension.

change_while_iterating.py
vocab = {"the": 120, "refund": 9, "xqzt": 1, "a": 95, "tyop": 1}
try:
    for word, n in vocab.items():
        if n < 2:
            del vocab[word]
except RuntimeError as e:
    print("RuntimeError:", e)

vocab = {"the": 120, "refund": 9, "xqzt": 1, "a": 95, "tyop": 1}
kept = {w: n for w, n in vocab.items() if n >= 2}        # a new dict
for word in list(vocab):                                  # or: loop over a snapshot
    if vocab[word] < 2:
        del vocab[word]
print(kept == vocab, list(kept))
Output
RuntimeError: dictionary changed size during iteration
True ['the', 'refund', 'a']

4Merging and updating

All the ways of combining dicts follow one rule: for a repeated key, the later value wins. They differ in whether they build a new dict or change an existing one:

  • New dict: a | b (Python 3.9+), {**a, **b}, dict(a, **b) (only for string keys).
  • Change a in place: a |= b or a.update(b). update also accepts keyword arguments and lists of pairs.
merging.py
defaults = {"model": "small", "temperature": 0.2, "stop": ["###"]}
env = {"model": "medium"}
user = {"temperature": 0.9}
merged = defaults | env | user                 # later wins: user over env over defaults
print(merged)
print(merged["stop"] is defaults["stop"])      # shallow: nested values are shared (2.3)
defaults.update(max_tokens=512)
print(list(defaults))
Output
{'model': 'medium', 'temperature': 0.9, 'stop': ['###']}
True
['model', 'temperature', 'stop', 'max_tokens']

Write the layers from lowest to highest priority, left to right, and the precedence reads naturally. Getting the order backwards (overrides | defaults) silently makes the defaults win, a bug that produces no error (problem 10). Every one of these merges is shallow: nested dicts and lists are shared, so use a recursive merge for nested settings (2.3, merge_settings).

5Building and reshaping dicts

Common ways to build a dict: a literal, dict(zip(keys, values)) for two parallel lists, dict(pairs) for a list of (key, value) pairs, and a comprehension {k: f(k) for k in items} when you compute values. Two reshaping patterns come up constantly:

building.py
classes = ["eggs", "ham", "spam"]
label_to_id = {label: i for i, label in enumerate(classes)}
id_to_label = dict(enumerate(classes))
print(label_to_id, id_to_label)

scores = {"faq": 0.71, "guide": 0.93, "terms": 0.12}
by_score = dict(sorted(scores.items(), key=lambda kv: kv[1], reverse=True))
print(by_score, next(iter(by_score)))

owners = {"faq": "ana", "guide": "ben", "terms": "ana"}
inverted = {owner: doc for doc, owner in owners.items()}   # duplicates: the last one wins
print(inverted)
Output
{'eggs': 0, 'ham': 1, 'spam': 2} {0: 'eggs', 1: 'ham', 2: 'spam'}
{'guide': 0.93, 'faq': 0.71, 'terms': 0.12} guide
{'ana': 'terms', 'ben': 'guide'}

Inverting a dict (values become keys) silently loses entries when values repeat: "ana" owns two documents but the inverted dict keeps only the last. When values can repeat, invert into lists ({owner: [docs]}, 4.6), or check for duplicates and raise (problem 2). Sorting a dict means building a new dict from sorted items: the dict itself has no sort method, but it keeps whatever insertion order you build it with.

•
Equality ignores order

Two dicts are equal when they have the same keys with equal values, in any order: {"a": 1, "b": 2} == {"b": 2, "a": 1} is True. So insertion order affects iteration and printing, never equality. (collections.OrderedDict is the exception: comparing two OrderedDicts also compares order.)

2. Invert a label map, refusing duplicates

TestsThe 3 checks Run tests uses
def raises(exc, f, *args):
    try:
        f(*args)
    except exc as e:
        return str(e)
    return False
assert invert({"ham": 0, "spam": 1}) == {0: "ham", 1: "spam"}
assert invert({}) == {}

HintOpen a hint

Build the result in a loop; before storing out[value] = key, check whether value is already a key of out.

SolutionShow the solution and why
solution.py
def invert(mapping):
    out = {}
    for key, value in mapping.items():
        if value in out:
            raise ValueError(f"id {value!r} is used by both {out[value]!r} and {key!r}")
        out[value] = key
    return out

A comprehension {v: k for k, v in mapping.items()} would be shorter, but it silently keeps only the last label for a repeated id, which in a label map means one class disappears from decoded predictions. Checking value in out is O(1) per item, so the safe version is still O(n). The error message names both labels, which is what you need to fix the data.

5. Pruning a vocabulary while looping over it

prune(vocab, min_count) should remove rare words from the vocabulary dict in place. It raises RuntimeError. Fix it, keeping it in place (the same dict object).

TestsThe 2 checks Run tests uses
v = {"the": 120, "refund": 9, "xqzt": 1, "a": 95, "tyop": 1}
ref = v
prune(v, 2)
assert v == {"the": 120, "refund": 9, "a": 95} and v is ref
prune(v, 1000)
assert v == {}
HintOpen a hint

You cannot delete keys while iterating over the dict itself. Collect the keys to delete first, or loop over a copy of the keys.

SolutionShow the solution and why
solution.py
def prune(vocab, min_count):
    for word in [w for w, c in vocab.items() if c < min_count]:
        del vocab[word]

Deleting during iteration changes the dict's size under the running iterator, which Python refuses to continue with. Building the list of rare words first finishes the iteration before any deletion starts. If the function did not have to work in place, {w: c for w, c in vocab.items() if c >= min_count} would be the clearest version. Pruning rare tokens is a standard step when building a vocabulary for bag-of-words features (scikit-learn's min_df).

HintOpen a hint

Walk the path one step at a time. For each step, the current value must be a dict containing the key, or a list where the position is in range.

SolutionShow the solution and why
solution.py
def dig(data, path, default=None):
    current = data
    for step in path:
        if isinstance(current, dict) and step in current:
            current = current[step]
        elif isinstance(current, list) and isinstance(step, int) and -len(current) <= step < len(current):
            current = current[step]
        else:
            return default
    return current

LLM API responses are deeply nested and their shape varies (a refusal has no tool_calls, an error has no choices), so a single helper beats a pyramid of if "choices" in resp and resp["choices"] and .... Checking before stepping (look before you leap) keeps the logic explicit; the other style, try: ... except (KeyError, IndexError, TypeError): return default, is shorter but can hide a real bug inside a step (Module 8 compares the two). The path as a list also makes the lookup easy to log when it fails.

solution.py
def label_maps(labels):

    label_to_id = {label: i for i, label in enumerate(classes)}

A key of (value, negated key) is not possible for strings. nsmallest with (-value, key) is.

SolutionShow the solution and why
solution.py
import heapq

def top_k(scores, k):
    best = heapq.nsmallest(k, scores.items(), key=lambda kv: (-kv[1], kv[0]))
    return dict(best)

Strings cannot be negated, so "value descending, key ascending" is expressed as the smallest (-value, key) tuples, which nsmallest returns already in that order. Building a dict from the ordered pairs keeps that order, so the result reads highest first. nsmallest(0, ...) is an empty list, so k = 0 needs no special case (unlike the -0 slice trap, 4.1). Retrieval code does this after scoring chunks: keep the top few, in a deterministic order.

solution.py
def record(usage, user, model, tokens):
    per_user = usage.setdefault(user, {})
    per_user[model] = per_user.get(model, 0) + tokens


def report(usage):
    lines = []
    for user in sorted(usage):
        total = sum(usage[user].values())
        top = max(usage[user], key=usage[user].get, default="none")
        lines.append(f"{user}: {total} tokens, mostly {top}")
    return lines


def drop_unused(usage):
    for user in [u for u, per_model in usage.items() if sum(per_model.values()) == 0]:
        del usage[user]

Bug one: get(user, {}) returns a fresh dict that is never put into usage, so all usage of a new user (and each later call) vanishes; setdefault(user, {}) returns the existing inner dict or stores and returns a new one, which is exactly "get or create" (4.6). Bug two: max over a user with no models raises ValueError; default= handles it. Bug three: deleting during iteration over items() raises RuntimeError; collect the users first. Billing code is where "silently lost" is the worst kind of bug, which is why the first one matters most.

solution.py
def inner_join(left, right, key):
    index = {}
    for row in right:
        if key in row:
            index.setdefault(row[key], []).append(row)
    out = []
    for row in left:
        for match in index.get(row.get(key), []) if key in row else []:
            out.append({**row, **match})
    return out

A nested loop join compares every left row with every right row: O(n × m). Building a dict index on one side makes each lookup O(1), so the whole join is O(n + m + output): this is the hash join that databases use when joining on equality without a usable index. The index maps each key value to a list because keys can repeat on the right, which produces one output row per match, exactly like SQL. {**row, **match} builds new dicts, so the inputs are untouched (2.4), and the right side wins on clashing column names. pandas merge does this on whole columns.

9Interview questions

Interview

17. How does a Python dict give O(1) lookups and keep insertion order at the same time?

SolutionModel answer

It is a hash table: the key's hash picks a slot, collisions are resolved by probing, and the table resizes as it fills, so lookups, inserts and deletes are O(1) on average. Since CPython 3.6 (and guaranteed by the language from 3.7), it uses a compact layout: a small index array of slots points into a separate, dense array of entries stored in insertion order. Lookups go through the index; iteration walks the dense entries, which gives insertion order and uses less memory than storing entries directly in the sparse table. Keys must be hashable and must not change their hash. Mention that deleting and re-inserting a key moves it to the end, and that equality ignores order.

Interview

18. A key might be missing. When do you use d[k], get, setdefault, defaultdict or try/except KeyError?

SolutionModel answer

d[k] when the key must exist and a missing key is a bug you want to surface. d.get(k, default) for optional keys when you only read. setdefault(k, default) when you want to read and create the entry if absent in one step, typically to append to a list (d.setdefault(k, []).append(x)). collections.defaultdict(factory) when a whole dict should create entries on first access, such as counters and grouping (4.6). try/except KeyError when the key is normally present and the missing case is rare and needs special handling (EAFP style, Module 8). Pitfalls worth mentioning: get(k) or default swallows falsy values, and defaultdict creates entries even on plain reads.

Interview

19. Explain the hash join. When is it better than a nested loop join, and what does it cost?

SolutionModel answer

For an equality join, build a hash table (a dict) from the smaller input, keyed by the join column, mapping each key to its rows; then scan the larger input and look each row's key up. That is O(n + m) time plus the output, versus O(n × m) for comparing every pair in nested loops. The cost is memory for the hash table, which is why databases build it on the smaller side and spill to disk when it does not fit. It only works for equality conditions (not < or ranges, where sort-merge joins or indexes are used). In Python this is the dict-of-lists index pattern, and pandas merge does the same on whole columns. Mention duplicates on both sides multiply output rows, exactly as in SQL.

Recap

  • A dict is a hash table of keys with values: lookups by key are O(1), keys must be hashable, and insertion order is kept.
  • d[k] for required keys, get for optional ones, in to test, setdefault to read-or-create. Never get(k) or default for values that can be 0.
  • Views (keys, values, items) are live. Never add or delete keys while iterating: loop over a snapshot or build a new dict.
  • Merges are later-wins and shallow: write layers from lowest to highest priority, defaults | env | user.
  • Inverting loses repeated values; sorting builds a new dict; a dict index of lists turns a nested-loop join into a hash join.
