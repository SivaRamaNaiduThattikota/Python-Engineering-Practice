7.4 Errors in LLM and API code

Calls to models and APIs fail in ways local code does not: timeouts, rate limits, overloaded servers, truncated or refused answers, output that does not parse, and batches where some items fail. How to tell transient from permanent errors, retry with backoff and jitter within a deadline, repair invalid output, and handle partial failures, with everything testable through injected clocks and fakes.

1How remote calls fail

A call to a model API crosses the network to a service you do not control, so it can fail in many more ways than a local function. It helps to sort failures by what you should do about them, because that, not the exception's name, decides the handling code.

Three of these deserve emphasis. A timeout does not mean the request failed on the server: the model may have finished and billed you, and only the answer was lost. Retrying is usually fine for reading or generating, but not for operations with side effects such as "send this email" unless they are idempotent (below). A rate limit is the provider telling you how to behave, often with the exact wait in the Retry-After header; ignoring it gets you limited for longer. And the two "successful" failures, truncated and refused answers, arrive with HTTP 200, so no exception is raised unless your code checks finish_reason or the content and raises one itself (problem 12).

class APIError(Exception):

2Retrying: exponential backoff and jitter

Retrying immediately after a transient failure usually fails again: the server is still overloaded, the rate limit window has not passed. Exponential backoff waits longer after each failure, typically doubling from a base delay up to a cap: with a base of 1 second and a cap of 30, the waits are 1, 2, 4, 8, 16, 30, 30... seconds. The total wait grows quickly, so a few attempts cover a long outage without hammering the service.

Backoff alone has a flaw. When a provider has a hiccup, thousands of clients fail at the same moment, and with identical backoff they all retry at exactly 1 s, then exactly 2 s later, in synchronised waves that knock the service over again: the thundering herd. Jitter fixes it by randomising each delay. The widely used "full jitter" scheme picks a random delay between 0 and the exponential value, which spreads retries evenly over the window. If the server sends Retry-After, wait at least that long.

backoff_schedule.py
import random

def delays(attempts, base, cap, rng=None):
    out = []
    for attempt in range(attempts):
        ceiling = min(cap, base * 2 ** attempt)
        out.append(round(rng.uniform(0, ceiling), 2) if rng else ceiling)
    return out

print(delays(7, base=1, cap=30))
print(delays(7, base=1, cap=30, rng=random.Random(42)))
print(sum(delays(7, base=1, cap=30)))
Output

[0.64, 0.05, 1.1, 1.79, 11.78, 20.3, 26.77]

Note the seeded random.Random(42): passing the random generator in (instead of calling random.uniform directly) makes the function reproducible in tests, the same idea as injecting the clock in 7.3's circuit breaker. Real code also injects sleep, so tests can run a full retry sequence instantly and check the delays that would have been waited (problem 5).

Idempotency decides whether a retry is safe. Reading, embedding and generating text are idempotent in effect: doing them twice just costs twice. Creating something (a payment, a ticket, a message to a user) is not: a timeout followed by a retry can create it twice. APIs solve this with idempotency keys: the client generates a unique id per logical operation and sends it with every attempt, and the server performs the operation only once per key. Generate the key once, before the first attempt, never inside the retry loop.

3Timeouts and deadlines

Every network call needs a timeout: without one, a stuck connection can block a worker forever. SDKs accept a timeout per request (the OpenAI and Anthropic clients default to 10 minutes, far too long for an interactive feature), and many distinguish a connect timeout (how long to wait to establish the connection, usually a few seconds) from a read timeout (how long to wait for the response, which for long generations can legitimately be a minute).

Retries multiply waiting: three attempts with a 30 s timeout and backoff can keep a user waiting two minutes. So the policy that matters to callers is a deadline: a total time budget for the whole operation, including all attempts and waits. Before each wait, check whether waiting and trying again could still finish before the deadline; if not, give up now and raise the last error, instead of sleeping only to fail anyway (problem 6). Pass the remaining time as the timeout of the next attempt, so a single slow attempt cannot overrun the budget either.

deadline.py
def plan(deadline, delays, attempt_time):
    # simulate: each attempt takes attempt_time seconds and fails
    now, timeline = 0.0, []
    for delay in delays:
        now += attempt_time
        timeline.append(f"fail@{now:g}")
        if now + delay + attempt_time > deadline:
            timeline.append("give up")
            return timeline
        now += delay
    return timeline

print(plan(deadline=10, delays=[1, 2, 4, 8], attempt_time=1.5))
print(plan(deadline=30, delays=[1, 2, 4, 8], attempt_time=1.5))

4When the answer itself is wrong

Many failures arrive as a successful response. Check the finish reason first: "stop" (or "end_turn") means the model finished normally; "length" (or "max_tokens") means it was cut off at the token limit, so JSON will be incomplete and a summary will end mid-sentence; "content_filter" or a refusal means the provider or model declined. Treat a truncated answer as an error, not as data: raise a specific exception so the caller can raise the limit or ask the model to continue.

Then validate the content. When output must follow a format (JSON with certain fields, one of a few labels), parse it and raise ValueError (or your own InvalidOutputError) when it does not fit. Unlike most errors, this one can often be fixed by the model itself: a repair loop sends the conversation back with the invalid reply and a short message describing the problem ("Your reply was not valid JSON: Expecting ',' delimiter at line 3. Reply with JSON only."), and asks again, for a limited number of attempts (problem 7). Structured output features (JSON mode, tool calling with a schema) reduce how often this is needed, but do not remove the need to validate.

finish_reason.py
import json

class TruncatedError(Exception):
    pass

class RefusalError(Exception):
    pass

def content_of(response):
    choice = response["choices"][0]
    reason = choice["finish_reason"]
    if reason == "length":
        raise TruncatedError("answer cut off at the token limit")
    if reason == "content_filter":
        raise RefusalError("answer blocked by the content filter")
    return choice["message"]["content"]

    {"choices": [{"finish_reason": "length", "message": {"content": '{"label": "sp'}}]},
    {"choices": [{"finish_reason": "content_filter", "message": {"content": ""}}]},
]

5Partial failures in batches

When you process many items (embed 10,000 chunks, classify a dataset, call a tool for each search result), some will fail while others succeed. The rule is to keep every success, record every failure with its item and reason, and decide separately what to do with the failures: retry the transient ones in a later round (with backoff between rounds), report the permanent ones, and abort only if the failure rate shows a systemic problem (the error budget of 7.3).

Batch APIs add a twist: one call sends many items, and a single bad item (an empty string, a text over the token limit) can make the whole call fail with a 400. Retrying the batch is pointless. The usual remedy is to split: retry the batch in halves, or item by item, which isolates the bad items and saves the good ones (problem 9). Keep results keyed by item id, not by position, so retries and reordering cannot misalign them.

split_batch.py
def embed_batch(texts):
    if any(not t.strip() for t in texts):
        raise ValueError("400: input contains an empty string")
    return [[len(t)] for t in texts]

def embed_all(items):
    vectors, failed = {}, {}
    try:
        for (item_id, _), vec in zip(items, embed_batch([t for _, t in items]), strict=True):
            vectors[item_id] = vec
    except ValueError:
        for item_id, text in items:              # isolate the bad items
            try:
                vectors[item_id] = embed_batch([text])[0]
            except ValueError as e:
                failed[item_id] = str(e)
    return vectors, failed

print(embed_all([("a", "refund"), ("b", "reset")]))
print(embed_all([("a", "refund"), ("b", "  "), ("c", "invoice")]))
Output
({'a': [6], 'b': [5]}, {})
({'a': [6], 'c': [7]}, {'b': '400: input contains an empty string'})

6Errors you can debug later

API failures are often intermittent, so you debug them from logs long after they happened. For every failed call, record the error type and status, the provider's request id (support teams need it), the attempt number, the latency, the model name, and token counts if available. Do not log API keys, and be careful with prompts and outputs, which may contain personal data: log their length or a hash, or redact them (5.5), unless you have a policy that allows storing them.

Keep two messages apart: the internal one, with every detail, goes to logs; the user-facing one says what happened in plain words and what the user can do ("The assistant is busy, please try again in a minute"), never a traceback or a provider's raw error. And count failures by type in metrics, so a rising rate limit or timeout rate is visible on a dashboard before users complain.

structured_log.py
import json, time

def log_failure(log, *, exc, attempt, started, model, request_id=None, prompt=""):
    log.append(json.dumps({
        "event": "llm_call_failed",
        "error": type(exc).__name__,
        "status": getattr(exc, "status", None),
        "attempt": attempt,
        "latency_ms": round((time.perf_counter() - started) * 1000),
        "model": model,
        "request_id": request_id,
        "prompt_chars": len(prompt),            # size, not content
    }))

log = []
start = time.perf_counter()

            request_id="req_123", prompt="My card number is 4111 1111 1111 1111")

solution.py
def backoff(attempts, base, cap):
    if base <= 0 or cap <= 0 or attempts < 0:
        raise ValueError("base and cap must be positive, attempts non-negative")
    return [min(cap, base * 2 ** i) for i in range(attempts)]

The doubling comes from 2 ** i, and the cap keeps late waits bounded, which is why the second schedule flattens at 4. Note the mix of 1.0 and 4: min returns whichever argument is smaller, unchanged, so the result is the float product or the integer cap; equality still works because 4 == 4.0. Production code adds jitter on top of this ceiling (problem 5), and validates its configuration up front so a zero base does not turn into a tight retry loop.

3. Retries that stop one attempt early

call(fn, max_retries) should make one first attempt plus up to max_retries retries when fn raises TimeoutError, and re-raise the last timeout if all fail. It gives up one attempt too early, and with max_retries=0 it never calls fn at all. Fix it.

solution.py
def call(fn, max_retries):
    last = None
    for attempt in range(max_retries + 1):
        try:
            return fn()
        except TimeoutError as e:
            last = e
    raise last

"Retries" counts the attempts after the first, so the loop must run max_retries + 1 times. With range(max_retries), max_retries=0 meant zero attempts, and the final raise last then raised None, which is itself a TypeError: exceptions must derive from BaseException, a confusing error that hides the real problem. Naming parameters precisely (max_attempts versus max_retries) prevents this whole class of bug; SDKs use max_retries meaning retries after the first call.

def wait_for(headers, default=1.0, cap=60.0):
    raw = headers.get("retry-after")
    try:
        value = float(raw)
    except (TypeError, ValueError):
        return default
    return min(max(value, 0.0), cap)

solution.py
class RateLimitError(Exception):
    def __init__(self, message, retry_after=None):
        super().__init__(message)
        self.retry_after = retry_after


RETRYABLE = (TimeoutError, ConnectionError, RateLimitError)


def retry(fn, max_attempts, sleep, rng, base=1.0, cap=30.0):
    for attempt in range(1, max_attempts + 1):
        try:
            return fn()
        except RETRYABLE as e:
            if attempt == max_attempts:
                raise
            delay = rng.uniform(0, min(cap, base * 2 ** (attempt - 1)))
            server_wait = getattr(e, "retry_after", None) or 0
            sleep(max(delay, server_wait))

Injecting sleep and rng is what makes this testable: the test passes waits.append as sleep, so the whole retry sequence runs instantly and the delays can be checked, and an rng whose uniform always returns the upper bound turns the random jitter into predictable numbers. In production you pass time.sleep and random.Random(). The server's Retry-After wins when it is longer than our own backoff, because the provider knows its rate-limit window. A bare raise on the last attempt preserves the final error. No wait happens after the last failure, since there is no next attempt to wait for. The tenacity library offers all of this as configurable decorators (8.3).

6. Retries that ignore the deadline

call_within(fn, deadline, delays, clock, sleep) retries fn on TimeoutError, waiting delays[i] before retry i + 1. It must never start a wait that would end after deadline seconds from the start (measured with clock()): in that case it re-raises the last timeout immediately. solution.py
def call_within(fn, deadline, delays, clock, sleep):
    start = clock()
    for delay in delays:
        try:
            return fn()
        except TimeoutError:
            if clock() - start + delay > deadline:
                raise
            sleep(delay)
    return fn()

Trace the first test. Attempt 1 fails at 2 s; a 1 s wait would end at 3, within the 10 s deadline, so it waits. Attempt 2 fails at 5 s; 5 + 2 = 7 still fits, so it waits again. Attempt 3 fails at 9 s, and a 4 s wait would end at 13, past the deadline, so it gives up immediately and re-raises the timeout from 9 s, instead of sleeping and trying again. The original slept through every delay and only stopped after the fifth attempt, at 25 s, two and a half times the budget. The check uses the clock at the moment of failure, because attempts take variable time. A complete version would also pass the remaining time, deadline - (clock() - start), as the timeout of each attempt, so that one slow attempt cannot overrun the budget on its own.

solution.py
import json

def ask_json(ask, messages, required, max_attempts):
    history = list(messages)
    last_error = None
    for attempt in range(1, max_attempts + 1):
        reply = ask(history)
        try:
            data = json.loads(reply)
            if not isinstance(data, dict):
                raise ValueError("reply is not a JSON object")
            missing = [k for k in required if k not in data]
            if missing:
                raise ValueError(f"missing keys: {', '.join(missing)}")
            return data, attempt
        except ValueError as e:
            last_error = e
            history = history + [
                {"role": "assistant", "content": reply},
                {"role": "user", "content": f"Your reply was invalid: {e}. Reply with only a JSON object with keys: {', '.join(required)}."},
            ]
    raise ValueError(f"no valid JSON after {max_attempts} attempts") from last_error

Showing the model its own invalid reply and the precise error ("Expecting value", "missing keys: confidence") usually fixes the output on the next try, which is far more effective than asking the identical question again. json.JSONDecodeError is a ValueError, so parse errors and the hand-written checks share one handler. The history is copied and extended with +, so the caller's list is never modified and a retry from outside starts clean (2.4). The final error is chained from the last specific failure, so logs show why the model kept failing. Libraries such as Instructor implement this loop on top of Pydantic validation errors (11.4).

class APIError(Exception):
    def __init__(self, message, status):
        super().__init__(message)
        self.status = status


RETRY_STATUS = {408, 409, 429}
CONTEXT_HINTS = ("context_length", "maximum context")


def policy(exc):
    if isinstance(exc, (TimeoutError, ConnectionError)):
        return "retry"
    if not isinstance(exc, APIError):
        return "raise"
    if exc.status in RETRY_STATUS or exc.status >= 500:
        return "retry"

        return "alert"
    return "raise"

solution.py
def run_batch(items, call, max_rounds, on_round=None):
    results, failures = {}, {}
    pending = list(items)
    for round_number in range(1, max_rounds + 1):
        if not pending:
            break
        if round_number > 1 and on_round is not None:
            on_round(round_number, list(pending))
        still_pending = []
        for item_id in pending:
            try:
                results[item_id] = call(items[item_id])
            except TimeoutError:
                still_pending.append(item_id)
            except ValueError as e:
                failures[item_id] = type(e).__name__
        pending = still_pending
    for item_id in pending:
        failures[item_id] = "TimeoutError"
    return results, failures

Retrying in rounds instead of retrying each item immediately has two advantages for batch work: one slow item does not hold up the rest, and the wait between rounds (via on_round, where a real job sleeps with backoff) gives an overloaded service time to recover before the stragglers are retried together. Permanent failures are recorded on first sight and never retried. Iterating over ids in insertion order keeps rounds deterministic, which the rounds check depends on. Every item ends up in exactly one of the two dicts, which is the property a batch report needs: processed = succeeded + failed.

SolutionShow the solution and why
solution.py
def make_limiter(rate, burst, clock):
    tokens = float(burst)
    last = clock()

    def acquire(cost=1):
        nonlocal tokens, last
        if cost > burst:
            raise ValueError(f"cost {cost} exceeds burst size {burst}")
        now = clock()
        tokens = min(burst, tokens + (now - last) * rate)
        last = now
        if tokens >= cost:
            tokens -= cost
            return 0.0
        return (cost - tokens) / rate

    return acquire

A token bucket allows short bursts (up to burst requests at once) while enforcing an average rate, which matches how providers express limits (requests or tokens per minute). Refilling lazily from the elapsed time, instead of with a timer, keeps it simple and exact. Returning the wait instead of sleeping keeps the limiter testable and lets the caller decide: sleep that long, or reject the request. Not taking tokens on a failed attempt is important; otherwise waiting callers would push each other further back. cost lets you meter tokens rather than requests: pass the estimated prompt tokens to respect a tokens-per-minute limit. In async code (14.5) the same bucket guards concurrent tasks with a lock.

Interview

17. Which errors from an LLM API should you retry, and how?

SolutionModel answer

Retry transient failures: connection errors, timeouts, 429 rate limits, and server errors (500, 502, 503, 504 and overloaded responses such as 529). Do not retry 400-level errors other than 408, 409 and 429, because the same request will fail again: bad parameters, too many tokens (shorten the input instead), authentication and permission errors (alert instead). Retry with exponential backoff and jitter, honour Retry-After when the server sends it, cap the number of attempts, and wrap it all in an overall deadline so callers are not kept waiting longer than the feature can afford. Only retry operations that are safe to repeat, or use idempotency keys for ones that are not, because a timeout can happen after the server has done the work. Log each attempt with its error type and request id, and track retry and failure rates in metrics.

Interview

18. Why add jitter to retry delays?

SolutionModel answer

Because failures are correlated. When a service hiccups, many clients fail at the same moment; with plain exponential backoff, they all wait exactly the same delays and retry in synchronised waves, each wave hitting the recovering service with the full load at once (the thundering herd problem). Jitter randomises each client's delay, typically choosing uniformly between zero and the exponential ceiling ("full jitter"), which spreads the retries evenly over time and lets the service recover. It also prevents accidental synchronisation of periodic jobs. AWS's architecture guidance on backoff and jitter showed that full jitter completes the work with far fewer total calls than backoff without jitter.

Interview

19. A nightly job sends 50,000 documents to an LLM for classification, and about 2% fail in different ways. How would you make it robust?

SolutionModel answer

Classify the failures first, because each kind needs different handling. Transient errors (timeouts, rate limits, 5xx) get retries with backoff, ideally in rounds so stragglers do not block the batch, under a client-side rate limiter sized to the provider's limits, and with a circuit breaker so an outage pauses the job instead of burning through every document. Invalid output gets a repair attempt (send the error back to the model), then is recorded as failed. Truncated answers raise the token limit or shorten the input; context-length errors trim the document. Permanent failures (bad input) go to a dead-letter table with the document id, error type and request id. The job keeps every success, writes results idempotently keyed by document id with the model and prompt version, checkpoints progress so a crash resumes instead of restarting, and stops early if the failure rate exceeds an error budget, which signals a systemic issue. At the end it reports counts by outcome and error type, and a separate step reprocesses the dead-letter items after a fix. Finally, it samples outputs for quality evaluation, since a "successful" classification can still be wrong.

Recap

  • Sort failures by reaction: retry transient ones (timeouts, connection errors, 429, 5xx), fix bad requests, alert on auth errors, handle truncation and refusals explicitly.
  • Retry with exponential backoff, jitter and Retry-After, a capped number of attempts and an overall deadline; inject sleep, clock and rng to test it.
  • Retries are only safe for idempotent operations; use idempotency keys for the rest.
  • Check finish_reason, validate output, and repair by sending the error back to the model a limited number of times.
  • In batches, keep every success, isolate bad items, retry stragglers in rounds, and log type, status, request id and latency, never keys or raw personal data.
