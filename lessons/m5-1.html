5.1 Strings: indexing, slicing, immutability

A string is an immutable sequence of Unicode code points. What that means for indexing, slicing, comparing and building text, the literal syntax that hides real bugs (a missing comma, a stray backslash), and why len is neither "characters on screen" nor "LLM tokens".

19 problems4 easy · 10 medium · 5 hard

1What a string is

A Python str is an immutable sequence of Unicode code points. A code point is one number from the Unicode table ("A" is 65, "é" is 233, "€" is 8364), and ord and chr convert between a one-character string and its number. There is no separate "char" type: indexing a string gives you another string, of length 1. Because a string is a sequence, everything from 4.1 applies: len, indexing, slicing, in, iteration, count and index.

str_basics.py
s = "Refund €20"
print(len(s), s[0], s[-3:], type(s[0]).__name__, len(s[0]))
print(ord("R"), ord("€"), chr(8364), s[0][0][0])
for ch in "ab€":
    print(ch, ord(ch), end=" | ")
print()
Output
10 R €20 str 1
82 8364 € R
a 97 | b 98 | € 8364 |

A string is not a sequence of bytes. How a code point is stored as bytes (UTF-8, UTF-16 and so on) is a separate question that only matters when text crosses a boundary: a file, a network socket, a database. Lesson 5.4 covers encodings; for now, think of a string as a list of Unicode numbers that cannot change.

≈
SQL / Power BI

A Python str is like SQL Server's NVARCHAR (Unicode text), not VARCHAR with a code page. s[0] is LEFT(s, 1), s[-3:] is RIGHT(s, 3), s[2:5] is SUBSTRING(s, 3, 3) (SQL counts from 1, Python from 0) and len(s) is LEN(s) (which, unlike Python, ignores trailing spaces in SQL Server).

2Indexing and slicing strings

Strings follow exactly the list rules from 4.1: positions start at 0, negative positions count from the end, stop is never included, slices are clamped and never raise, a step can skip or reverse. Two things are specific to strings: every slice is a new string, and a string reversed with [::-1] is reversed by code point, which can break text that uses several code points for one visible character (the last section).

slicing.py
ref = "INV-2025-000731"
print(ref[:3], ref[4:8], ref[-6:], ref[::-1][:6])
print(ref[100:], ref[-100:3], "abc"[1:1] == "")
try:
    ref[50]
except IndexError as e:
    print("IndexError:", e)
Output
INV 2025 000731 137000
 INV True
IndexError: string index out of range

Fixed positions such as ref[4:8] are only safe for strings whose format you control, like your own ids. For text from users, files or LLMs, the positions move, and code that slices at fixed offsets silently returns the wrong field (problem 15). Splitting on a separator (5.2) or a regex (5.5) is more robust.

3Immutability, and building strings efficiently

You cannot change a string in place: s[0] = "r" raises TypeError. Every method that seems to change a string, upper, replace, strip, returns a new string and leaves the original alone, so you must use the return value (s.strip() on its own line does nothing useful). The benefits are the ones from Module 2: strings can be shared freely, used as dict keys and set members, and cached.

immutable.py
s = "refund"
try:
    s[0] = "R"
except TypeError as e:
    print("TypeError:", e)
s.upper()                # returns a new string, which is thrown away here
print(s)
s = s.upper()            # rebinding the name to the new string
print(s, s.replace("F", "f"), s)
Output
TypeError: 'str' object does not support item assignment
refund
REFUND REfUND REFUND

Building a long string from many pieces is where immutability costs. Each a + b creates a new string and copies both sides, so adding pieces one at a time in a loop copies the growing text again and again: O(n²) characters in the worst case. The idiomatic fix is to collect the pieces in a list and join once: "".join(pieces) computes the total length, allocates one string and copies each piece exactly once, O(n).

join.py
lines = [f"[{i}] chunk {i}" for i in range(5)]
context = "\n".join(lines)           # one allocation, one copy of each piece
print(context)
print(len(context), context.count("\n"))
Output
[0] chunk 0
[1] chunk 1
[2] chunk 2
[3] chunk 3
[4] chunk 4
59 4

Why += sometimes looks fast

CPython has an optimisation: when a string has no other references, s += piece may grow it in place instead of copying. So a += loop can be fast in one program and slow in another (for example as soon as another name points at the string, or with f-strings, or on other Python implementations). Do not rely on it: join is fast everywhere (problem 8).

4Comparing and searching

== compares strings code point by code point, exactly and case-sensitively. < and > compare lexicographically by code point, the dictionary order of the Unicode numbers, which is not human alphabetical order: all uppercase letters (65 to 90) come before all lowercase ones (97 to 122), and digits compare as characters, so "10" < "9". For case-insensitive comparison, use casefold(), a stronger lower() designed for exactly this (it maps the German "ß" to "ss", for example).

compare.py
print("Zebra" < "apple", "10" < "9", "apple" < "apples")
print(sorted(["banana", "Apple", "cherry"]), sorted(["banana", "Apple", "cherry"], key=str.casefold))
print("Straße".lower() == "STRASSE".lower(), "Straße".casefold() == "STRASSE".casefold())
Output
True True True
['Apple', 'banana', 'cherry'] ['Apple', 'banana', 'cherry']
False True

Searching: sub in s tests for a substring. s.find(sub) returns the first position or -1, while s.index(sub) returns the position or raises ValueError; choose find when absence is normal and index when absence is a bug. s.count(sub) counts non-overlapping occurrences, and startswith / endswith accept a tuple of options.

search.py
log = "ERROR 2025-06-01 timeout after 30s; retry; ERROR again"
print("timeout" in log, log.find("ERROR"), log.find("ERROR", 1), log.find("WARN"))
print(log.count("ERROR"), "aaaa".count("aa"), log.startswith(("ERROR", "WARN")))
try:
    log.index("WARN")
except ValueError as e:
    print("ValueError:", e)
Output
True 0 43 -1
2 2 True
ValueError: substring not found

5String literals and their traps

Single and double quotes are the same; triple quotes ("""...""") allow line breaks, which is how long prompts are usually written. Inside normal quotes, a backslash starts an escape sequence: \n is a newline, \t a tab, \\ one backslash. A raw string, r"...", keeps backslashes as they are, which is what you want for regex patterns (5.5) and Windows paths.

escapes.py
print(len("a\tb"), len(r"a\tb"), "C:\\data\\new.csv", r"C:\data\new.csv")
print(repr("line1\nline2"), "it's", 'say "hi"')
Output
3 4 C:\data\new.csv C:\data\new.csv
'line1\nline2' it's say "hi"

Implicit concatenation: Python joins adjacent string literals at compile time, so "Hello " "world" is one string. It is handy for splitting a long literal over lines, and a source of silent bugs in lists of strings: a missing comma merges two items into one, the list is one item shorter, and nothing raises (problem 2).

implicit_concat.py
stop_sequences = [
    "###",
    "END"          # missing comma
    "Human:",
]
print(len(stop_sequences), stop_sequences)

long_prompt = (
    "You are a support assistant. "
    "Answer only from the provided context."
)
print(long_prompt)
Output
2 ['###', 'ENDHuman:']
You are a support assistant. Answer only from the provided context.

6What len counts, and what it does not

len(s) counts code points. That is often, but not always, what a person would call characters. A visible character can be several code points: "é" can be stored as one code point (U+00E9) or as "e" plus a combining accent (U+0301), and an emoji with a skin tone is two code points. Those strings look identical but have different lengths, and reversing one with [::-1] can move the accent onto the wrong letter.

length.py
precomposed = "café"
decomposed = "cafe\u0301"          # e + combining acute accent: looks the same
print(precomposed, decomposed, len(precomposed), len(decomposed), precomposed == decomposed)
import unicodedata
print(unicodedata.normalize("NFC", decomposed) == precomposed)
thumbs = "\U0001F44D\U0001F3FD"    # thumbs up + medium skin tone
print(len(thumbs), len(thumbs.encode("utf-8")))
Output
café café 4 5 False
True
2 8

So there are at least four different "lengths" of a text: code points (len), bytes in an encoding (what a database column limit or an HTTP size limit counts, 5.4), graphemes (what a reader sees), and tokens (what an LLM counts and bills: roughly 3 to 4 characters of English per token, more for other languages and code). Normalise text with unicodedata.normalize("NFC", s) before comparing or deduplicating it, and count tokens with the model's own tokenizer, never with len.

TestsThe 5 checks Run tests uses

HintOpen a hint

"*" * n repeats a string. Take the tail with a slice, but watch the -0 trap from 4.1.

SolutionShow the solution and why
solution.py
def mask(secret, visible=4):
    if len(secret) <= visible:
        return "*" * len(secret)
    return "*" * (len(secret) - visible) + secret[len(secret) - visible:]

Short secrets are fully masked, because showing the last 4 characters of a 4-character key would reveal all of it. secret[len(secret) - visible:] avoids the -0 slice trap if someone passes visible=0 (4.1). Masking secrets in logs and traces is a basic requirement for LLM applications, whose tracing tools often log every request header by default (3.2, problem 12).

5. A palindrome check that ignores punctuation

Write is_palindrome(text) that returns True if the letters and digits of text, ignoring case, read the same backwards. Spaces and punctuation are ignored. Use two positions moving towards each other, so no cleaned copy of the whole string is built.

TestsThe 5 checks Run tests uses

assert is_palindrome("No 'x' in Nixon")
assert not is_palindrome("refund")
assert is_palindrome("") and is_palindrome(".,!")
assert is_palindrome("12321") and not is_palindrome("123")
Hint 1Open a hint

Start i at 0 and j at the last position. Skip characters that are not isalnum() on either side, then compare casefold() versions.

Hint 2Open a hint

Stop when the positions meet.

SolutionShow the solution and why
solution.py
def is_palindrome(text):
    i, j = 0, len(text) - 1
    while i < j:
        if not text[i].isalnum():
            i += 1
        elif not text[j].isalnum():
            j -= 1
        elif text[i].casefold() != text[j].casefold():
            return False
        else:
            i += 1
            j -= 1
    return True

The two-pointer version uses O(1) extra memory and stops at the first mismatch. The one-liner, cleaned = [c.casefold() for c in text if c.isalnum()]; return cleaned == cleaned[::-1], is also correct and fine in most code, but builds two copies; interviewers often ask for the pointer version as a follow-up. isalnum is Unicode-aware, so accented letters count as letters. A string with no letters at all is a palindrome by this definition.

SolutionShow the solution and why
solution.py
def build_context(chunks):
    blocks = [f"[{i}] {c['source']}\n{c['text']}" for i, c in enumerate(chunks, start=1)]

join places the separator only between items, so there is never a leading or trailing one and the empty case is the empty string, with no special handling. It also builds the result in one allocation. Numbering the chunks [1], [2] lets the model cite its sources ("according to [2]"), and a clean, consistent format measurably helps models follow citation instructions.

9. Truncate at a word boundary

Write truncate(text, max_chars, ellipsis="…") that shortens text so the result, including the ellipsis, is at most max_chars characters. Cut at the last space that fits, so no word is broken, and strip trailing spaces before adding the ellipsis. Text that already fits is returned unchanged. If even the first word does not fit, cut it hard.

TestsThe 6 checks Run tests uses
t = "Refunds are processed within five business days."
assert truncate(t, 100) == t
assert truncate(t, 20) == "Refunds are…"
assert len(truncate(t, 20)) <= 20
assert truncate(t, 12) == "Refunds are…"
assert truncate("Supercalifragilistic", 8) == "Superca…"
assert truncate(t, 25, ellipsis="...") == "Refunds are processed..."
Hint 1Open a hint

The text you may keep is text[:limit] with limit = max_chars - len(ellipsis). Find its last space with rfind.

Hint 2Open a hint

If the character right after that part is a space, the cut already falls between words: keep it whole.

Hint 3Open a hint

If there is no space in that part, keep it as it is (a hard cut).

SolutionShow the solution and why
solution.py
def truncate(text, max_chars, ellipsis="…"):
    if len(text) <= max_chars:
        return text
    limit = max_chars - len(ellipsis)
    room = text[:limit]
    if text[limit] == " ":
        kept = room
    else:
        cut = room.rfind(" ")
        kept = room[:cut] if cut > 0 else room
    return kept.rstrip() + ellipsis

Reserving room for the ellipsis first guarantees the length limit, and rfind finds the last space inside that room so the cut lands between words. The check on text[limit] handles the boundary case the tests probe: when the room ends exactly at the end of a word, cutting back to the previous space would throw away a whole word for nothing. cut > 0 covers a room whose only space is at position 0. This is how search snippets and previews are made. For LLM context limits you would truncate by tokens with the model's tokenizer instead (the last section), because characters and tokens are not proportional.

HintOpen a hint

SolutionShow the solution and why
solution.py
def parse_contact(text):
    start = text.find("<")
    end = text.find(">", start + 1)
    if start == -1 or end == -1:
        return "", text.strip()
    return text[:start].strip(), text[start + 1:end].strip()

index is the right call when a missing separator is an error, but here the bare-email form is valid input, so absence is normal and find with a -1 check expresses that. Searching for > only after the < avoids matching a > that appears earlier in the name. Real email address parsing has many more rules; the standard library's email.utils.parseaddr handles them.

14. Longest common prefix

TestsThe 5 checks Run tests uses

assert common_prefix(["same", "same"]) == "same"

Hint 1Open a hint

zip(*strings) yields tuples of the characters at each position, and stops at the shortest string.

Hint 2Open a hint

A position is common when its tuple has one distinct character: len(set(chars)) == 1.

SolutionShow the solution and why
solution.py
def common_prefix(strings):
    prefix = []
    for chars in zip(*strings):
        if len(set(chars)) != 1:
            break
        prefix.append(chars[0])
    return "".join(prefix)

zip(*strings) transposes the strings into columns of characters (4.3) and stops at the shortest one, so the "end of the shortest string" rule comes for free. A column is common when its set has one element. The work is O(total characters examined), and the prefix is collected in a list and joined once. A neat alternative uses the sort order: the common prefix of a whole list equals the common prefix of its lexicographically smallest and largest strings (min and max), which is a nice follow-up answer. The standard library also has os.path.commonprefix, which does this character by character despite its name.

def parse_line(line):
    date, level, model, request_id, *extra = line.split()
    user = None
    for part in extra:
        if part.startswith("user="):
            user = part[len("user="):]
    return {"date": date, "level": level, "model": model, "request_id": request_id, "user": user}

Fixed slices encode assumptions about field widths, so any change in a model name or id length shifts every later field without an error: the worst kind of parser bug, because it produces plausible garbage. Splitting on whitespace uses the actual separators, star unpacking (4.3) collects the optional fields, and part[len("user="):] avoids a hard-coded 5. Optional fields become None instead of a crash. For logs you control, write JSON lines instead (Module 12), and the parsing problem disappears.

text.find(sub, start) searches from start. After a match at i, continue from i + 1 to allow overlaps.

SolutionShow the solution and why
solution.py
def find_all(text, sub):
    if not sub:
        raise ValueError("sub must not be empty")
    positions = []
    i = text.find(sub)
    while i != -1:
        positions.append(i)
        i = text.find(sub, i + 1)
    return positions

Restarting the search at i + 1 (rather than i + len(sub)) is what allows overlaps, which str.count and re.finditer do not report: the test shows count finding only 2. The empty-substring guard matters, because "" is found at every position and the loop would never end (an infinite-loop bug, the kind 4.2 warned about). Each find is fast C code; for many patterns at once, an Aho-Corasick automaton is the standard algorithm.

17. Why are Python strings immutable, and what does that imply for your code?

SolutionModel answer

Immutability makes strings safe to share between names, functions and threads, lets them be hashed once and used as dict keys and set members, and allows Python to intern and cache them. The implications: every operation that "changes" a string returns a new one, so you must use the return value (s = s.strip()); building a long string piece by piece with + copies the growing text again and again, so collect pieces and "".join them; and there is no in-place character assignment, so for heavy character-level editing you would work on a list of characters or an io.StringIO. Mention that CPython's in-place += optimisation is an implementation detail you should not rely on.

Interview

18. How do you build a large string efficiently, and why can repeated + be slow?

SolutionModel answer

Each a + b allocates a new string and copies both operands, so appending n pieces one at a time copies about n²/2 pieces' worth of characters. "".join(pieces) computes the total size, allocates once and copies each piece once, O(total length). Alternatives: io.StringIO for writing text incrementally, or building lines and writing them to a file directly. CPython sometimes resizes a string in place for s += t when nothing else refers to s, so a += loop can look fast in a micro-benchmark, but that breaks with f-strings, extra references, or other interpreters such as PyPy, so join is the portable answer.

19. Does len(text) tell you how long text is for a user, a database column or an LLM?

SolutionModel answer

None of them reliably. len counts Unicode code points. A user sees graphemes: an accented letter can be two code points, and emoji with skin tones or flags are several, so visible length and len differ (use the grapheme or regex library's \X to count them). A database or protocol limit usually counts bytes in an encoding: UTF-8 uses 1 to 4 bytes per code point, so len(text.encode("utf-8")) is what a VARBINARY limit or a payload size cares about. An LLM counts tokens from its own tokenizer (subword pieces, roughly 3 to 4 English characters each, far fewer characters per token for code, numbers or many languages), and both context limits and cost are in tokens, so count with the model's tokenizer (for example tiktoken). Also mention Unicode normalisation (NFC) before comparing text.

Recap

  • A str is an immutable sequence of Unicode code points: indexing gives one-character strings, and every "change" builds a new string.
  • Slicing follows the list rules. Prefer separators (split, partition, regex) over fixed positions for text you do not control.
  • Build long strings with "".join(pieces), not repeated + or f-strings in a loop.
  • Strings compare by code point: capitals sort first and "10" < "9". Use casefold for case-insensitive comparison.
  • Watch the literal traps: a missing comma concatenates, \ starts escapes (use r"..."), triple quotes keep indentation. len counts code points, not graphemes, bytes or tokens.
