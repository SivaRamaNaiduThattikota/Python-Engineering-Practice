8.1 Functions that wrap functions

A decorator is a function that takes a function and returns a replacement for it. What @ really does and when it runs, the wrapper pattern with *args and **kwargs, functools.wraps and why frameworks need it, state kept by a decorator, and the traps: lost return values, swallowed errors, generators. Applied to timing, tracing and validating calls, the way LLM observability tools do.

19 problems4 easy · 10 medium · 5 hard

1A function that takes and returns functions

Everything in this lesson rests on two facts from Module 3. Functions are objects: you can pass them to other functions, return them, and store them in variables and dicts (3.5). And an inner function remembers the variables of the function that created it, even after that function has returned: a closure (3.4). Put together, you can write a function that receives a function and returns a new function that calls the original with something extra around it.

wrapping.py
def shout(func):
    def wrapper(text):
        return func(text).upper() + "!"      # call the original, then change its result
    return wrapper

def greet(name):
    return f"hello {name}"

loud_greet = shout(greet)
print(greet("ana"), "|", loud_greet("ana"))
print(loud_greet is greet, loud_greet.__name__)
Output
hello ana | HELLO ANA!
False wrapper

shout(greet) did not call greet; it built and returned wrapper, a new function that, when called, calls greet (which it remembers through the closure) and transforms the result. That pattern, "take a function, return a function that adds behaviour around it", is a decorator. Very often you want the new behaviour to replace the old function under the same name, so you write greet = shout(greet). Python has syntax for exactly that line:

at_syntax.py
def shout(func):
    def wrapper(text):
        return func(text).upper() + "!"
    return wrapper

@shout
def greet(name):                 # the same as: greet = shout(greet), right after the def
    return f"hello {name}"

print(greet("bo"))
Output
HELLO BO!

@shout on the line above a def means: define the function, pass it to shout, and bind the result to the name greet. Nothing more. After that line, the name greet refers to wrapper, and the original function is reachable only through the closure. Any expression that evaluates to a callable can follow the @, which is how decorators with arguments work (8.2).

2When decorator code runs

A decorator has two separate moments, and mixing them up causes most decorator bugs. The decorator function runs once, at definition time: when Python executes the def statement, which for a module-level function is when the module is imported. The wrapper runs at call time, every time someone calls the decorated name. Code in the decorator's body (outside the wrapper) runs once; code inside the wrapper runs on every call.

two_moments.py
events = []

def announce(func):
    events.append(f"decorating {func.__name__}")      # definition time: once
    def wrapper(*args, **kwargs):
        events.append(f"calling {func.__name__}")     # call time: every call
        return func(*args, **kwargs)
    return wrapper

@announce
def embed(text):
    return [len(text)]

events.append("module loaded")
embed("a"); embed("bc")
print(events)
Output
['decorating embed', 'module loaded', 'calling embed', 'calling embed']

The decoration happened before the module even finished loading, before any call. Frameworks rely on this: a FastAPI route decorator or an agent's tool registry records the function at import time, so by the time the app starts serving, every route and tool is known (8.4). It also means expensive work in the decorator body (opening a connection, loading a model) happens at import, whether or not the function is ever called, which is usually not what you want.

3The wrapper pattern

Almost every decorator has the same shape. The wrapper accepts any arguments with *args and **kwargs (3.2), does something before the call, calls the original with exactly those arguments, does something after, and returns the result. Using *args, **kwargs instead of copying the original's parameters is what lets one decorator work on any function: positional and keyword arguments, defaults, and keyword-only parameters all pass straight through (problem 6).

wrapper_pattern.py
import time

def timed(func):
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        try:
            return func(*args, **kwargs)                 # pass everything through, return the result
        finally:
            elapsed = time.perf_counter() - start
            wrapper.timings.append(round(elapsed, 6))    # runs on success and on failure
    wrapper.timings = []
    return wrapper

@timed
def score(text, *, threshold=0.5):
    if not text:
        raise ValueError("empty text")
    return len(text) > 10 * threshold

print(score("refund request", threshold=0.2), score("hi"))
try:
    score("")
except ValueError as e:
    print("ValueError:", e)
print(len(score.timings), all(t >= 0 for t in score.timings))
Output
True False
ValueError: empty text
3 True

Three details make this wrapper correct, and each one is a common bug when missing. It returns what the original returned; a wrapper that forgets return turns every result into None (problem 3). It lets exceptions pass through: the try/finally records the time even when the call fails, but does not catch anything, so callers still see the ValueError (problem 10). And it passes the arguments unchanged, including keyword-only ones like threshold.

The wrapper.timings list shows one way to keep state in a decorator: functions are objects and can have attributes, so the decorated function carries its own measurements, separate for every function decorated. A closure variable updated with nonlocal works too, but is invisible from outside; an attribute can be read by tests and dashboards.

4functools.wraps: keep the original's identity

After decoration, the name score refers to wrapper. Unless you do something about it, the decorated function looks like wrapper: its __name__ is "wrapper", its docstring is gone, and help() and inspect.signature() describe (*args, **kwargs). That breaks more than cosmetics. Logs and tracebacks show wrapper for every decorated function, test tools list them all under the same name, and frameworks that read a function's signature to decide what it accepts (FastAPI building an API from parameters, agent frameworks building a tool schema, pytest injecting fixtures) see the wrong one.

functools.wraps(func) is a decorator for the wrapper: it copies __name__, __qualname__, __doc__, __module__ and the __dict__ of the original onto the wrapper, and sets wrapper.__wrapped__ = func. inspect.signature follows __wrapped__, so it reports the original parameters. Write @functools.wraps(func) on every wrapper you write; there is no good reason to leave it out.

wraps.py
import functools, inspect

def plain(func):
    def wrapper(*args, **kwargs):
        return func(*args, **kwargs)
    return wrapper

def proper(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        return func(*args, **kwargs)
    return wrapper

def search(query: str, k: int = 3) -> list:
    """Search the knowledge base."""
    return [query] * k

a, b = plain(search), proper(search)
print(a.__name__, a.__doc__, inspect.signature(a))
print(b.__name__, b.__doc__, inspect.signature(b))
print(b.__wrapped__ is search, b("x", k=1))
Output
wrapper None (*args, **kwargs)
search Search the knowledge base. (query: str, k: int = 3) -> list
True ['x']

__wrapped__ also gives you the undecorated function when you need it, for example to test the original logic without the decorator's side effects (no caching, no logging): score.__wrapped__("text"). Note that wraps copies metadata; the wrapper still runs its own code, so calling b still goes through the decorator.

5Decorator traps

Beyond forgetting return and wraps, three traps come up again and again.

Recursion goes through the wrapper. Inside a decorated recursive function, the recursive call looks up the function's name at call time (3.3), and that name now refers to the wrapper. So every recursive call is also decorated: a counting decorator counts all of them, a logging decorator logs every level, a timing decorator times each nested call. Sometimes that is exactly what you want (memoization relies on it, 8.3); sometimes it is a flood (problem 16).

Generators finish later. A generator function returns its generator immediately (6.3), so a wrapper that times or logs "after the call" measures only the creation of the generator, not the streaming. To wrap a generator properly, the wrapper must itself be a generator that iterates the original and yields each item (problem 15). The same applies to async def functions, whose wrapper must be async too (14.4).

generator_trap.py
import functools

def log_after(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        result = func(*args, **kwargs)
        print(f"  {func.__name__} returned {type(result).__name__}")
        return result
    return wrapper

@log_after
def stream(n):
    for i in range(n):
        print(f"  producing {i}")
        yield i

g = stream(2)                    # "returned generator" is printed now, before any item exists
print(list(g))
Output
  stream returned generator
  producing 0
  producing 1
[0, 1]

Decorating changes the object. The decorated name is a different function, so is comparisons with the original fail, and attributes set on the original before decoration are only visible if wraps copied them. Decorators that return the original function unchanged (after registering it somewhere) avoid this entirely, which is the pattern of 8.4.

6What decorators are used for

Decorators are the standard way to add cross-cutting behaviour, the kind that is the same for many functions and unrelated to what each one does: timing, logging, tracing, counting, caching (8.3), retrying (8.3), rate limiting, checking permissions, validating arguments, and registering functions (8.4). The function keeps only its real logic, and the decorator line documents the extra behaviour where everyone reads it.

In GenAI code you meet them constantly. Observability tools trace LLM calls with a decorator: LangSmith's @traceable, Langfuse's @observe and OpenTelemetry's span decorators wrap a function, record its inputs, outputs, duration and errors, and send them to a dashboard. Agent frameworks turn plain functions into tools with @tool. Web frameworks map URLs to functions with @app.get("/path"). And the standard library offers @functools.cache, @property, @classmethod, @staticmethod and @dataclass (Modules 9 and 11), all built on exactly the mechanism of this lesson.

tracing.py
import functools

TRACE = []

def traced(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        entry = {"name": func.__name__, "args": [repr(a)[:20] for a in args]}
        try:
            result = func(*args, **kwargs)
        except Exception as e:
            entry["error"] = type(e).__name__
            raise
        else:
            entry["output"] = repr(result)[:30]
            return result
        finally:
            TRACE.append(entry)
    return wrapper

@traced
def retrieve(query):
    return ["Refunds take 5 days.", "No refunds after 30 days."]

@traced
def generate(query, context):
    if not context:
        raise ValueError("no context")
    return f"Answer based on {len(context)} chunks"

generate("refund time?", retrieve("refund time?"))
try:
    generate("x", [])
except ValueError:
    pass
for entry in TRACE:
    print(entry)
Output
{'name': 'retrieve', 'args': ["'refund time?'"], 'output': "['Refunds take 5 days.', 'No r"}
{'name': 'generate', 'args': ["'refund time?'", "['Refunds take 5 day"], 'output': "'Answer based on 2 chunks'"}
{'name': 'generate', 'args': ["'x'", '[]'], 'error': 'ValueError'}

Each entry records the function name (correct thanks to wraps), a shortened view of the inputs (never log full prompts containing personal data without a policy, 7.4), and either the output or the error type. The exception is re-raised, so tracing never changes the program's behaviour, which is the one rule an observability decorator must obey.

A function without a return statement returns None.

SolutionShow the solution and why
solution.py
import functools

log = []

def log_call(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        result = func(*args, **kwargs)
        log.append((func.__name__, result))
        return result

The wrapper is what callers actually call, so whatever it returns is what they get. It computed the result and recorded it, then fell off the end, which returns None. solution.py
import functools

TRACE = []

def traced(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        entry = {
            "name": func.__name__,
            "args": [repr(a)[:30] for a in args],

            raise
        finally:
            TRACE.append(entry)
    return wrapper

repr (not str) shows quotes and escape characters, so 'x' is distinguishable from x in the trace, and cutting to 30 characters keeps a huge prompt from bloating the log. The except records the type and then re-raises with a bare raise, so the caller gets the original exception and traceback; finally appends the entry on both paths. This is the skeleton of LangSmith's @traceable and Langfuse's @observe, which also record timings, nest child calls under their parent, and send the entries to a server instead of a list.

SolutionShow the solution and why
solution.py
import functools
import math

def check_finite(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        result = func(*args, **kwargs)
        if not math.isfinite(result):
            raise ValueError(f"{func.__name__} returned {result}")
        return result
    return wrapper

A wrapper with fixed parameters only fits functions with the same signature: weighted(2, 4) passed two arguments to a wrapper that takes one, and w=1 was rejected too. *args collects every positional argument into a tuple and **kwargs every keyword argument into a dict, and the call func(*args, **kwargs) unpacks them back exactly as given (3.2), so the original function does its own argument checking. Checking for NaN and infinity after a loss computation is a cheap guard that catches a diverging training run at the first bad step.

SolutionShow the solution and why
solution.py
import functools, inspect

def no_none(func):
    sig = inspect.signature(func)

    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        bound = sig.bind(*args, **kwargs)
        bound.apply_defaults()
        for name, value in bound.arguments.items():
            if value is None:
                raise TypeError(f"{name} must not be None")
        return func(*args, **kwargs)
    return wrapper

*args and **kwargs alone do not tell the wrapper which parameter a value belongs to; binding them to the signature does, exactly as Python would when calling the function, and apply_defaults fills in parameters that were not passed. The signature is computed once, at decoration time, because inspecting a function is comparatively slow and the result never changes. The check runs before the call, so the function body never sees bad input, which the calls list confirms. This is a tiny version of what Pydantic's @validate_call does with full type checking (11.4).

10. A tracing decorator that swallows errors

observe records each call's outcome in EVENTS. When the decorated function fails, the error is recorded but the caller receives None instead of the exception, so a failed model call looks like an empty answer. Fix it: record, then let the exception propagate unchanged.

TestsThe 2 checks Run tests uses
@observe

    if prompt == "timeout":
        raise TimeoutError("model did not answer")
    return prompt.upper()

try:
    complete("timeout")
    assert False, "the error must reach the caller"
except TimeoutError as e:

HintOpen a hint

After recording, a bare raise re-raises the exception being handled.

SolutionShow the solution and why
solution.py
import functools

EVENTS = []

def observe(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        try:
            result = func(*args, **kwargs)
        except Exception as e:
            EVENTS.append((func.__name__, f"error: {e}"))
            raise
        EVENTS.append((func.__name__, "ok"))
        return result
    return wrapper

An except block that does not re-raise handles the exception; after it, the wrapper fell off the end and returned None. An observability decorator must never change behaviour, so it records and re-raises with a bare raise, which keeps the original type, message and traceback (7.2). Moving the success bookkeeping out of the try block also keeps a failure in the logging itself from being reported as a failure of the function.

13. A small memoizer

Write a decorator memo that caches results by arguments. The key combines the positional arguments and the keyword arguments sorted by name, so f(1, b=2) and f(1, b=2) share an entry (but f(1, 2) is a different key). If the arguments are unhashable (a list, a dict), call the function without caching. Expose the cache as wrapper.cache (a dict) and a wrapper.cache_clear() function. Use functools.wraps.

    return [len(text), len(model)]

embed("hi", model="large"); embed("hi", model="large")

    calls.append(tuple(xs))

Hint 1Open a hint

Hint 2Open a hint

SolutionShow the solution and why
solution.py
import functools

def memo(func):
    cache = {}

    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        key = (args, tuple(sorted(kwargs.items())))
        try:
            hash(key)
        except TypeError:
            return func(*args, **kwargs)
        if key not in cache:
            cache[key] = func(*args, **kwargs)
        return cache[key]

    wrapper.cache = cache
    wrapper.cache_clear = cache.clear
    return wrapper

A dict lookup by the argument tuple is the whole idea of memoization, and it only works for hashable keys, which is why lists bypass the cache instead of crashing. Sorting the keyword items makes f(a=1, b=2) and f(b=2, a=1) the same key. The hash(key) check is done separately so that a TypeError raised inside func is never mistaken for an unhashable key. Note that the cache returns the same list object each time, so a caller that modifies the returned list modifies the cached value too (2.2); caching functions that return mutable objects needs care. functools.lru_cache (8.3) is the production version, with a size limit and statistics; it treats f(1, 2) and f(1, b=2) as different keys too.

solution.py
import functools

STATS = {}


def with_stats(func, clock):
    entry = STATS.setdefault(func.__name__, {"calls": 0, "errors": 0, "seconds": 0.0})

    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        start = clock()
        entry["calls"] += 1
        try:
            return func(*args, **kwargs)
        except Exception:
            entry["errors"] += 1
            raise
        finally:
            entry["seconds"] += clock() - start
    return wrapper

Three bugs. The stats were keyed by wrapper.__name__, which is "wrapper" for every decorated function (no wraps), so all functions shared one entry; keying by func.__name__ gives each its own. Failed calls skipped all the bookkeeping, because the exception left the wrapper before the counting lines: the dashboard showed a 100% success rate for a function that was failing. With try/except/finally, every call is counted, errors are counted, the elapsed time is always added, and the exception still propagates. Finally, functools.wraps restores the names for tracebacks and frameworks. Creating the stats entry once at decoration time also means functions that have never been called appear on the dashboard with zeros. Taking the clock as a second parameter means this cannot be used with @ directly; 8.2 shows how a decorator factory fixes that.

15. Decorate a generator properly

Streaming functions are generators, and a normal wrapper finishes before the stream starts. Inside the wrapper, for item in func(*args, **kwargs): count += 1; yield item.

Hint 2Open a hint

Closing a generator raises GeneratorExit at its paused yield (6.3); catch it to record "closed", then re-raise. Append in finally.

SolutionShow the solution and why
solution.py
import functools

STREAMS = []

def stream_stats(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        count, status = 0, "complete"
        try:
            for item in func(*args, **kwargs):
                count += 1
                yield item
        except GeneratorExit:
            status = "closed"
            raise
        except Exception as e:
            status = type(e).__name__
            raise
        finally:
            STREAMS.append((func.__name__, count, status))
    return wrapper

Because the wrapper contains yield, it is a generator function itself, so calling tokens(...) creates a generator and runs nothing, exactly like the original; the test checks that STREAMS is still empty at that point. The bookkeeping happens when the wrapper's loop ends, which is when the stream really ends. GeneratorExit is how Python tells a paused generator it is being closed (by close(), or when it is garbage collected after the consumer breaks out of a loop); it is a BaseException, not an Exception, so it needs its own clause and must be re-raised. Counting items as they pass is exactly how streaming LLM tracers measure time to first token and the number of chunks. yield from func(...) would forward items more simply but would not let the wrapper count them.

16. Recursion through the wrapper

import functools

def counted(func):
    @functools.wraps(func)
    def wrapper(*args):
        wrapper.calls += 1
        return func(*args)
    wrapper.calls = 0
    return wrapper

@counted
def fib(n):
    return n if n < 2 else fib(n - 1) + fib(n - 2)

print(fib(5), fib.calls)
fib.calls = 0
print(fib.__wrapped__(5), fib.calls)

Every recursive call looks up the global name fib, which is the wrapper, so all 15 calls of the recursion tree for fib(5) are counted. This is why memoizing a recursive function with a decorator works (each nested call can hit the cache, 8.3), and why logging decorators on recursive functions produce floods of entries.

Interview

17. What is a decorator in Python, and what exactly does the @ syntax do?

SolutionModel answer

A decorator is a callable that takes a function (or class) and returns a replacement, usually a wrapper that calls the original with extra behaviour before or after. @decorator on the line above a def is pure syntax: after the function is defined, Python calls decorator(func) and binds the function's name to whatever it returns. So @d / def f is equivalent to def f followed by f = d(f). The decorator runs once, at definition time (usually import time); the wrapper runs on every call. With several decorators, they are applied bottom-up (8.2). Because the result can be anything, a decorator can return a wrapper, the original function unchanged (registration), or even a different kind of object (property returns a descriptor). It relies on functions being first-class objects and on closures to remember the original.

Interview

18. Why should every wrapper use functools.wraps?

SolutionModel answer

Without it, the decorated name refers to a wrapper that presents itself as the wrapper: __name__ is "wrapper", the docstring is lost, __module__ and __qualname__ are wrong, and inspect.signature reports (*args, **kwargs). That breaks logs and tracebacks (every decorated function appears as "wrapper"), documentation and help(), test reports, and any tool that keys on the name (metrics, registries, caches). It also breaks frameworks that introspect signatures, such as FastAPI's dependency injection, pytest fixtures and agent frameworks that build tool schemas from parameters. functools.wraps(func) copies the metadata and the function's __dict__, and sets __wrapped__, which inspect follows to find the real signature, and which gives tests access to the undecorated function.

Interview

19. How would you add tracing to every LLM call in a codebase with a decorator, and what can go wrong?

SolutionModel answer

Write a decorator that, around each call, records the function name, a sanitised view of the inputs, the output or error type, duration, and model metadata such as token usage, and sends it to a tracing backend (or use an existing one: LangSmith's @traceable, Langfuse's @observe, OpenTelemetry spans), nesting child calls under the current trace so a RAG request shows retrieval, reranking and generation as one tree. Pitfalls: the decorator must never change behaviour, so it re-raises exceptions and returns results untouched, and failures in the tracing itself must be contained; it must use functools.wraps so names and signatures survive for frameworks; generator and async functions need generator and async wrappers, or streaming calls are measured wrongly; logging full prompts and outputs can leak personal data, so redact or sample; it adds overhead on hot paths, so keep the wrapper cheap and send data asynchronously; and recursion or retries inside a decorated function produce many nested entries, which should be grouped. Finally, test it with a fake backend to confirm that results, exceptions and streaming are unchanged.

Recap

  • A decorator takes a function and returns a replacement; @d above def f means f = d(f), run once at definition time.
  • The wrapper pattern: def wrapper(*args, **kwargs), work before, result = func(*args, **kwargs), work after, return result.
  • Never lose the result or the exception: return what the function returned, and re-raise with a bare raise; use finally for work that must always happen.
  • Always @functools.wraps(func): it keeps the name, docstring and signature (via __wrapped__) that logs, tests and frameworks rely on.
  • Recursive calls go through the wrapper; generators and async functions need wrappers of the same kind.
