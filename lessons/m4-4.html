4.4 Sets and hashing

How a hash table finds an item without searching, why that makes membership O(1), set algebra as SQL's UNION, INTERSECT and EXCEPT, why set order can change between runs (a reproducibility trap), frozenset, and the rule that equal values must hash alike.

1How a set finds an item without searching

A set is a hash table: an array of slots where each value's position is computed from the value itself. Step by step, adding or looking up x works like this:

  • 1. Hash. Python calls hash(x), which turns the value into a large integer. Equal values always give equal hashes.
  • 2. Pick a slot. The hash is reduced to a slot number in the table (think hash % number_of_slots).
  • 3. Compare. If that slot is empty, x is not in the set. If it holds an item, Python checks identity, then equality (2.1). If it holds a different item (a collision), it probes a few other slots in a fixed pattern.
  • 4. Grow. When the table gets about two-thirds full, it is rebuilt with more slots, like a list resize (4.1).

Because the slot is computed rather than searched for, x in s, s.add(x) and s.discard(x) are O(1) on average, whether the set holds ten items or ten million. The price: a set has no meaningful order (items sit wherever their hashes put them), it uses more memory than a list, and it can only store hashable values.

SQL / Power BI

A set is like a column with a unique index: duplicates are rejected and a lookup by value is a single seek instead of a table scan. x in my_list is the full-scan query; x in my_set is the indexed one. Power BI's DISTINCT() and relationship lookups rely on the same idea.

2Membership at scale: when to convert

The most common speed-up in data code is replacing a list membership test inside a loop with a set. Checking 100,000 ids against a list of 100,000 known ids is 100,000 × O(n) = billions of comparisons; against a set it is 100,000 × O(1). Building the set costs one pass, O(n), so it pays off as soon as you test membership more than a few times.

membership.py
import time

known = list(range(0, 100_000, 2))
queries = list(range(0, 1_000))

start = time.perf_counter()
hits_list = sum(1 for q in queries if q in known)
t_list = time.perf_counter() - start

known_set = set(known)
start = time.perf_counter()
hits_set = sum(1 for q in queries if q in known_set)
t_set = time.perf_counter() - start

print(hits_list == hits_set, f"set is about {t_list / t_set:.0f}x faster here")
Output
True set is about 1990x faster here

The exact factor depends on the data and the machine, but it grows with the size of the list: the list scan gets slower as the list grows, while the set lookup does not. Convert once, outside the loop; if q in set(known) inside the loop rebuilds the set every time and is even slower than the list.

4Order and determinism

A set has no guaranteed order. Iterating over a set of small integers often looks sorted, which misleads people, but that is a side effect of small integers hashing to themselves. For strings, Python randomises the hash function per process (a protection against attacks that feed a server many colliding keys), so the iteration order of a set of strings can differ from one run of your program to the next. The values are the same; only the order changes.

order.py
import os
print(os.environ.get("PYTHONHASHSEED", "not set (random per run)"))

words = ["refund", "invoice", "login", "agent", "embedding", "chunk"]
unique = set(words)
print(len(unique), sorted(unique))          # sorted: the same every run
print(list(dict.fromkeys(words)))           # first-seen order, the same every run
Output
not set (random per run)
6 ['agent', 'chunk', 'embedding', 'invoice', 'login', 'refund']
['refund', 'invoice', 'login', 'agent', 'embedding', 'chunk']
!
A reproducibility trap in ML

Code like labels = list(set(df["label"])) gives the classes an order that can change between runs, so "class 0" may be "spam" today and "ham" tomorrow, and a saved model's outputs get mapped to the wrong names. Build anything that needs a stable order with sorted(set(...)) or dict.fromkeys(...). Setting PYTHONHASHSEED makes the order repeatable, but does not make it meaningful.

5frozenset, and the rule that equal values hash alike

A set is mutable, so it is not hashable: you cannot put a set inside a set or use it as a dict key. A frozenset is the immutable version, with the same operations except those that change it, and it is hashable. It is the right key for anything unordered: a pair of documents {a, b} where (a, b) and (b, a) should be the same, a combination of tags, the set of tools an agent may use.

frozenset.py
similar = {}
for a, b, score in [("d1", "d2", 0.91), ("d2", "d1", 0.91), ("d3", "d1", 0.40)]:
    similar[frozenset((a, b))] = score       # (d1, d2) and (d2, d1) are one key
print(len(similar), similar[frozenset(("d1", "d2"))])
print(frozenset("ab") == frozenset("ba"), {frozenset({1, 2}), frozenset({2, 1})})
Output
2 0.91
True {frozenset({1, 2})}

Hashing relies on one contract: if a == b, then hash(a) == hash(b). Python's numbers keep it across types, so 1, 1.0 and True are equal, hash alike, and count as the same element: the set keeps whichever arrived first. That surprises people who mix flags and numbers in one collection. NaN is the opposite case: it is not equal to itself, so separate NaN objects are separate elements (2.1).

eq_hash.py
print({1, 1.0, True}, {True, 1, 1.0}, len({0, False, 0.0, "0"}))
print({float("nan"), float("nan")}, len({float("nan"), float("nan")}))
Output
{1} {True} 2
{nan, nan} 2

HintOpen a hint

SolutionShow the solution and why
solution.py
def check_fields(record, required, optional=()):
    keys = set(record)
    required = set(required)
    return {
        "missing": sorted(required - keys),
        "unexpected": sorted(keys - required - set(optional)),
    }

Difference answers both questions in one expression each: required minus present is missing, present minus allowed is unexpected. Sorting the results makes the output deterministic, which matters for logs and for tests (the set order could differ between runs). Validating an LLM's JSON this way before using it, and sending the missing/unexpected lists back to the model, is a common repair loop; schema validators like Pydantic report the same information in more detail (Module 11).

def new_customers(today, known):

5. Agreement between two annotators

Two annotators tagged the same documents. Each gives a dict from document id to a set of tags. Write agreement(a, b) returning, for every document in both, the Jaccard similarity of the two tag sets: size of the intersection divided by size of the union (1.0 when both are empty). Return a dict, and include only shared document ids.

TestsThe 2 checks Run tests uses
ann1 = {"d1": {"refund", "billing"}, "d2": {"login"}, "d3": set(), "d9": {"x"}}
ann2 = {"d1": {"refund", "eu"}, "d2": {"login"}, "d3": set()}
out = agreement(ann1, ann2)
assert out == {"d1": 1 / 3, "d2": 1.0, "d3": 1.0}
assert agreement({}, ann2) == {}
HintOpen a hint

The shared ids are a.keys() & b.keys(). For each, len(x & y) / len(x | y), with a guard for an empty union.

SolutionShow the solution and why
solution.py
def agreement(a, b):
    out = {}
    for doc in a.keys() & b.keys():
        x, y = a[doc], b[doc]
        union = x | y
        out[doc] = len(x & y) / len(union) if union else 1.0
    return out

Dict key views support set operations directly, so a.keys() & b.keys() finds the shared documents without building lists. Jaccard similarity is the standard way to compare two sets: it is used for annotator agreement on multi-label data, for near-duplicate detection (MinHash approximates it at scale), and for comparing retrieved document sets between two RAG configurations. The guard defines two empty tag sets as full agreement, a choice worth stating explicitly because 0 / 0 has no natural answer.

6. Classes in a different order every run

encode_labels maps each class name to an integer for training. On some runs "spam" is 0, on others it is 1, so a saved model's predictions get decoded to the wrong names. Make the mapping deterministic: classes numbered in sorted order.

HintOpen a hint

list(set(...)) has no guaranteed order. Which function gives a stable order of the distinct labels?

SolutionShow the solution and why
solution.py
def encode_labels(labels):
    classes = sorted(set(labels))
    mapping = {c: i for i, c in enumerate(classes)}
    return [mapping[l] for l in labels], classes

The iteration order of a set of strings depends on the per-process hash seed, so list(set(labels)) can order the classes differently on different runs, and the integer codes change with it. sorted(set(labels)) is deterministic. scikit-learn's LabelEncoder does exactly this, keeping the sorted classes in classes_; saving that list together with the model is how predictions are decoded back to names later.

9. Changed, added and removed documents

A RAG index must be refreshed. Given old and new, dicts from document id to a content hash, write diff_index(old, new) returning a dict with sorted lists "added", "removed" and "changed" (in both, different hash). Only these documents need re-embedding or deleting.

TestsThe 2 checks Run tests uses
old = {"a": "h1", "b": "h2", "c": "h3"}
new = {"b": "h2", "c": "h9", "d": "h4"}
assert diff_index(old, new) == {"added": ["d"], "removed": ["a"], "changed": ["c"]}
assert diff_index({}, {}) == {"added": [], "removed": [], "changed": []}
HintOpen a hint

Use the key views: new.keys() - old.keys(), old.keys() - new.keys(), and old.keys() & new.keys() for the candidates for "changed".

SolutionShow the solution and why
solution.py
def diff_index(old, new):
    both = old.keys() & new.keys()
    return {
        "added": sorted(new.keys() - old.keys()),
        "removed": sorted(old.keys() - new.keys()),
        "changed": sorted(k for k in both if old[k] != new[k]),
    }

Set differences on the key views find added and removed documents in O(n), and only the shared ids need a value comparison. Comparing content hashes (for example a SHA-256 of the text) instead of the text itself keeps the stored state small. Re-embedding only what changed is the difference between an index refresh that costs a few cents and one that re-embeds the whole corpus; incremental indexing in LlamaIndex and LangChain's indexing API work this way.

count_pairs counts how often two products are bought together. ("milk", "bread") and ("bread", "milk") are counted as different pairs. Fix it so the order inside a pair does not matter.

TestsThe 4 checks Run tests uses

c = count_pairs(baskets)
assert c[frozenset({"milk", "bread"})] == 2
assert c[frozenset({"milk", "eggs"})] == 2
assert c[frozenset({"bread", "eggs"})] == 1
assert len(c) == 3
HintOpen a hint

Use a key that is the same whatever the order: a frozenset of the two items.

SolutionShow the solution and why
solution.py
def count_pairs(baskets):
    counts = {}
    for basket in baskets:
        items = list(basket)
        for i in range(len(items)):
            for j in range(i + 1, len(items)):
                pair = frozenset((items[i], items[j]))
                counts[pair] = counts.get(pair, 0) + 1
    return counts

A tuple remembers order, so the same pair in two orders makes two keys. A frozenset has no order and is hashable, so both orders give one key. tuple(sorted(...)) would also work and is easier to read in printed output. This co-occurrence counting is the first step of market-basket analysis (association rules) and of building co-occurrence features for recommendation; itertools.combinations(items, 2) replaces the two index loops.

SolutionShow the solution and why
Real output

solution.py
def shingles(text, k=3):
    words = text.lower().split()
    if len(words) < k:
        return {tuple(words)}
    return {tuple(words[i:i + k]) for i in range(len(words) - k + 1)}

def near_duplicates(chunks, threshold):
    sets = [shingles(c) for c in chunks]
    out = []
    for i in range(len(sets)):
        for j in range(i + 1, len(sets)):
            union = sets[i] | sets[j]
            if union and len(sets[i] & sets[j]) / len(union) >= threshold:
                out.append((i, j))
    return out

Word shingles turn "how similar is this text" into "how much do these sets overlap", and tuples are used because a list cannot go in a set. Chunks 0 and 1 differ in one word, so most shingles survive; chunk 3 is a truncated copy, so its shingles are a subset of chunk 0's, and shares the same five shingles with chunk 1. Comparing every pair is O(n²), fine for hundreds of chunks; at corpus scale, MinHash with locality-sensitive hashing estimates Jaccard similarity and only compares likely candidates. Removing near-duplicate chunks before indexing stops a RAG system from filling its context with the same passage several times.

14. Read the code: an allow-list with three holes

This guards which tools an agent may call. A security review found three problems: a tool can be enabled for everyone at run time by mistake, a tool name with different case or spaces slips past the deny-list, and the user's effective permissions are printed in a different order on each run, which breaks the audit log diff. Fix all three without changing which tools are allowed.

TestsThe 7 checks Run tests uses
assert tools_for(["weather"]) == {"search", "calculator", "weather"}
assert tools_for([]) == {"search", "calculator"}
assert not can_call(["Delete_Files "], "delete_files")

Hint 1Open a hint

allowed = BASE_TOOLS is an alias, and |= changes that shared set in place (2.2).

Hint 2Open a hint

Normalise names (strip().lower()) before comparing them with the deny-list and the allow-list.

Hint 3Open a hint

SolutionShow the solution and why
solution.py
BASE_TOOLS = frozenset({"search", "calculator"})
DENIED = frozenset({"delete_files", "send_email"})


def normalise(name):
    return name.strip().lower()


def tools_for(user_extra):
    return (BASE_TOOLS | {normalise(t) for t in user_extra}) - DENIED


def can_call(user_extra, tool):
    return normalise(tool) in tools_for(user_extra)


def audit_line(user, user_extra):
    return f"{user}: {', '.join(sorted(tools_for(user_extra)))}"

Hole one is aliasing (2.2): allowed = BASE_TOOLS then allowed |= ... adds the user's extra tools to the global base set, so one user's grant leaks to every later user. The | operator builds a new set, and making the base a frozenset turns any future in-place change into an error. Hole two is normalisation: sets compare exactly, so "Delete_Files " is not "delete_files"; normalising both the grants and the requested tool closes the bypass. Hole three is order: joining a set gives a hash-dependent order, so the audit text changes between runs; sorted makes it deterministic. All three are real classes of bugs in agent permission code.

solution.py
def to_hashable(value):
    return frozenset(value) if isinstance(value, list) else value

def dedupe_rows(rows, keys):
    seen = set()
    out = []
    for row in rows:
        key = tuple(to_hashable(row.get(k)) for k in keys)
        if key not in seen:
            seen.add(key)
            out.append(row)
    return out

Rows are dicts, which cannot go in a set, so deduplication needs a hashable key that captures exactly what "the same" means: a tuple over the chosen columns, with lists converted to frozenset to ignore their order. Choosing frozenset also ignores duplicates inside the list; if ["eu", "eu"] must differ from ["eu"], use tuple(sorted(value)) instead. Defining equality explicitly like this is the core of record linkage. In pandas, drop_duplicates fails on list columns for the same unhashable reason, and the fix is the same conversion.

Interview

16. Why is x in some_set O(1) but x in some_list O(n)?

SolutionModel answer

A list stores items in order with no index of values, so finding x means comparing it with items one by one. A set is a hash table: Python computes hash(x), maps it to a slot and compares only the item(s) there, so the cost does not depend on how many items the set holds. It is O(1) on average; with many collisions (bad hash functions, or adversarial keys) it degrades, which is why Python randomises string hashes. The trade-offs: sets use more memory, keep no order, and need hashable items. Mention the practical rule: build the set once outside a loop.

Interview

17. What does it mean for an object to be hashable, and what is the contract between __eq__ and __hash__?

SolutionModel answer

Hashable means the object has a hash value that never changes during its lifetime, so it can be found again in a set or dict. The contract: objects that compare equal must have equal hashes (the reverse need not hold; different objects may collide). That is why mutable containers like lists, dicts and sets are unhashable: their equality depends on contents that can change. It also explains {1, 1.0, True} having one element, since those are equal and hash alike. For your own classes (Module 9), defining __eq__ without __hash__ makes instances unhashable, and you should only define __hash__ from fields that never change; frozen dataclasses do this for you.

Interview

18. A model's predicted class names come out wrong after you reload it. What might sets have to do with it?

SolutionModel answer

If the class list was built with list(set(labels)), its order depends on the per-process string hash seed (PYTHONHASHSEED), so the integer each class received during training can differ from the one assumed at prediction time, and predictions get decoded to the wrong names. No error is raised; accuracy just looks terrible or labels are swapped. Fixes: build the class list with sorted(set(...)) or first-seen order, save it with the model (as scikit-learn does in classes_), and add a test that decodes known examples after reload. The general lesson: never let anything that must be reproducible depend on set or hash iteration order.

Recap

  • A set is a hash table: in, add and discard are O(1) on average because the slot is computed from the value.
  • Only hashable values can go in a set. Equal values must hash alike, so 1, 1.0 and True are one element.
  • Replace list membership in loops with a set built once. dict.fromkeys deduplicates while keeping order.
  • |, &, -, ^ are UNION, INTERSECT, EXCEPT and "in exactly one". Dict key views support them too.
  • Set order is not meaningful and string order can change between runs: sort before you print, number or save anything.
