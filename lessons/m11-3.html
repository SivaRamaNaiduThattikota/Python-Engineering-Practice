11.3 Dataclasses

@dataclass writes the boilerplate of data-holding classes from their type hints: __init__, __repr__, __eq__, and optionally ordering, hashing and slots. Fields and defaults (and the mutable-default rule), field() options, __post_init__ for validation and derived values, frozen instances and replace, asdict and fields, inheritance and keyword-only fields, and what dataclasses do not do (validate types). Applied to documents, configs, chunks and experiment records.

19 problems4 easy · 10 medium · 5 hard

1From boilerplate to one decorator

Many classes are mainly data: a document with an id, text and tags; a configuration; an evaluation result; a record from a file. Writing them by hand means an __init__ that copies every parameter to an attribute, a __repr__ that shows them, and an __eq__ (and maybe __hash__) that compares them, all of which must be updated every time a field is added (9.1, 9.2). @dataclass generates those methods from the class's annotated attributes, so the class body states only what matters: the fields, their types and their defaults.

first_dataclass.py
from dataclasses import dataclass

@dataclass
class Document:
    id: str
    text: str
    score: float = 0.0

d = Document("faq-1", "Refunds take 5 days.")
print(d)
print(d == Document("faq-1", "Refunds take 5 days."), d.score, Document("x", "y", score=0.9))
try:
    Document("only-id")
except TypeError as e:
    print("TypeError:", e)
Output
Document(id='faq-1', text='Refunds take 5 days.', score=0.0)
True 0.0 Document(id='x', text='y', score=0.9)
TypeError: Document.__init__() missing 1 required positional argument: 'text'

The generated __init__ takes the fields in the order they are declared, with the declared defaults, exactly as if you had written it; the __repr__ shows class name and fields, readable in logs and test failures; __eq__ compares instances of the same class field by field, as a tuple. Everything is normal Python afterwards: you can add methods, properties and class methods (9.3, 9.6). Note that the type hints are not checked: Document(1, None) is accepted. Dataclasses generate code from hints; validation is Pydantic's job (11.4).

2Defaults, default_factory and field()

A field's default is evaluated once, when the class is defined, and shared by every instance, which is safe for numbers, strings and None but would be the mutable-default bug of 2.4 for a list or dict. Dataclasses refuse it outright: tags: list[str] = [] raises ValueError: mutable default <class 'list'> for field tags is not allowed when the class is created. Use field(default_factory=list) instead: the factory is called for every new instance, so each gets its own list (problem 3).

dataclasses.field(...) customises a field in other ways too. repr=False hides it from the repr (secrets, huge embeddings). compare=False leaves it out of __eq__ (and of ordering and hashing): for caches, timestamps or metadata that should not affect identity. init=False removes it from __init__, for values computed in __post_init__ (below). kw_only=True makes it keyword-only. metadata={...} attaches arbitrary information that tools can read through dataclasses.fields().

defaults.py
from dataclasses import dataclass, field

@dataclass
class Chunk:
    doc_id: str
    text: str
    tags: list[str] = field(default_factory=list)
    embedding: list[float] = field(default_factory=list, repr=False, compare=False)
    source: str = field(default="unknown", metadata={"help": "where the text came from"})

a, b = Chunk("d1", "Refunds"), Chunk("d1", "Refunds")
a.tags.append("billing")
print(a, b.tags)
b.embedding = [0.1, 0.2]
a.tags.clear()
print(a == b)

try:
    @dataclass
    class Bad:
        tags: list[str] = []
except ValueError as e:
    print("ValueError:", e)
Output
Chunk(doc_id='d1', text='Refunds', tags=['billing'], source='unknown') []
True
ValueError: mutable default <class 'list'> for field tags is not allowed: use default_factory

a == b is true even though only b has an embedding, because compare=False excluded it: two chunks with the same document and text are the same chunk whatever their cached vectors. The order rule for defaults is the same as for function parameters: fields without defaults must come before fields with defaults, or the class definition fails. Keyword-only fields lift that restriction (problem 6).

3__post_init__: validation and derived fields

The generated __init__ only assigns fields. If you define __post_init__(self), the generated __init__ calls it at the end, after all fields are set. It is the place to validate (raise ValueError for impossible values), to normalise (strip text, lower-case labels, sort tags) and to compute derived fields, declared with field(init=False) so they are not constructor arguments. For values needed only during construction, not stored, declare them as InitVar[...]: they are passed to __init__ and then to __post_init__ as arguments.

post_init.py
from dataclasses import dataclass, field, InitVar

@dataclass
class Prediction:
    label: str
    probs: dict[str, float]
    threshold: InitVar[float] = 0.5
    confident: bool = field(init=False)

    def __post_init__(self, threshold):
        self.label = self.label.strip().lower()
        if self.label not in self.probs:
            raise ValueError(f"label {self.label!r} has no probability")
        total = sum(self.probs.values())
        if abs(total - 1) > 1e-6:
            raise ValueError(f"probabilities sum to {total}, not 1")
        self.confident = self.probs[self.label] >= threshold

p = Prediction(" Spam ", {"spam": 0.8, "ham": 0.2})
print(p, Prediction("ham", {"spam": 0.45, "ham": 0.55}, threshold=0.6).confident)
try:
    Prediction("phish", {"spam": 1.0})
except ValueError as e:
    print("ValueError:", e)
Output
Prediction(label='spam', probs={'spam': 0.8, 'ham': 0.2}, confident=True) False
ValueError: label 'phish' has no probability

__post_init__ runs only at construction. Assigning a field later (p.label = "x") bypasses it, so derived fields can go stale and invariants can be broken. For data that changes, use properties (9.3) for derived values, or make the dataclass frozen so that it cannot change at all.

4Frozen dataclasses, replace, ordering and slots

@dataclass(frozen=True) makes instances immutable: assigning a field raises FrozenInstanceError. Because equal frozen objects can never change, the dataclass also gets a __hash__ built from the compared fields, so instances work in sets and as dict keys (9.2). To "change" a frozen object, dataclasses.replace(obj, field=new) builds a new instance with some fields changed, calling __init__ (and __post_init__) again, so validation applies to the copy too. Inside __post_init__ of a frozen class, normalising a field requires object.__setattr__(self, "name", value), since normal assignment is blocked (9.3).

frozen.py
import dataclasses
from dataclasses import dataclass

@dataclass(frozen=True, slots=True, order=True)
class Version:
    major: int
    minor: int = 0
    patch: int = 0

v = Version(1, 9)
print(v, sorted([Version(1, 10), v, Version(0, 9, 3)]), v < Version(1, 10))
try:
    v.minor = 10
except dataclasses.FrozenInstanceError as e:
    print("FrozenInstanceError:", e)
w = dataclasses.replace(v, minor=10)
print(w, v, {v, Version(1, 9)}, hasattr(v, "__dict__"))
Output
Version(major=1, minor=9, patch=0) [Version(major=0, minor=9, patch=3), Version(major=1, minor=9, patch=0), Version(major=1, minor=10, patch=0)] True
FrozenInstanceError: cannot assign to field 'minor'
Version(major=1, minor=10, patch=0) Version(major=1, minor=9, patch=0) {Version(major=1, minor=9, patch=0)} False

order=True generates __lt__ and friends comparing the fields as a tuple, in declaration order, which is right for a version but a trap for records whose first field is a name: sorting would then be alphabetical, not by score (problem 10). slots=True (Python 3.10+) generates __slots__ (9.3): smaller instances and no accidental new attributes. unsafe_hash=True adds a hash to a mutable dataclass, which is only safe if the compared fields are never changed while the object is in a set or dict (problem 14).

5Inspecting and converting: fields, asdict, astuple

The dataclasses module exposes the structure it generated. fields(obj_or_class) returns Field objects with each field's name, type, default and metadata, which is how generic code (serialisers, config loaders, CLI builders) works with any dataclass. asdict(obj) converts an instance into a dict, recursively: nested dataclasses, and lists and dicts containing them, become plain dicts and lists, ready for json.dumps. astuple does the same into tuples. Both deep-copy the values, so the result is independent of the object. Going the other way, from a dict to nested dataclasses, needs a little code, usually a classmethod from_dict (9.6, problem 7).

utilities.py
import json
from dataclasses import dataclass, field, fields, asdict

@dataclass
class Metric:
    name: str
    value: float

@dataclass
class Run:
    run_id: str
    params: dict[str, float]
    metrics: list[Metric] = field(default_factory=list)

r = Run("r1", {"lr": 0.1}, [Metric("f1", 0.81), Metric("loss", 0.42)])
print([(f.name, f.type) for f in fields(Run)])
data = asdict(r)
print(json.dumps(data))
data["params"]["lr"] = 999
print(r.params["lr"], type(data["metrics"][0]).__name__)
Output
[('run_id', <class 'str'>), ('params', dict[str, float]), ('metrics', list[__main__.Metric])]
{"run_id": "r1", "params": {"lr": 0.1}, "metrics": [{"name": "f1", "value": 0.81}, {"name": "loss", "value": 0.42}]}

6Inheritance, keyword-only fields, and limits

Dataclasses can inherit: the subclass's fields come after the base's, and the generated __init__ takes them all. The rule that fields without defaults must come first applies across the whole hierarchy, so a base class with a default field followed by a subclass with a required one fails at class creation (TypeError: non-default argument follows default argument). kw_only=True, on the decorator or on individual fields, solves it: keyword-only fields may be declared in any order, and calls become self-documenting, Config(model="small", retries=3).

inheritance.py
from dataclasses import dataclass, KW_ONLY

@dataclass(kw_only=True)
class BaseConfig:
    timeout: float = 30.0

@dataclass(kw_only=True)
class LLMConfig(BaseConfig):
    model: str
    temperature: float = 0.0

@dataclass
class Request:
    prompt: str
    _: KW_ONLY
    stream: bool = False
    user: str = "anon"

print(LLMConfig(model="small"), Request("hi", stream=True))
try:
    Request("hi", True)
except TypeError as e:
    print("TypeError:", str(e)[:60])
Output
LLMConfig(timeout=30.0, model='small', temperature=0.0) Request(prompt='hi', stream=True, user='anon')
TypeError: Request.__init__() takes 2 positional arguments but 3 were g

Know the limits. Dataclasses do not validate types (hints are documentation, 11.1), they do not parse or convert input, and they do not serialise anything more complex than asdict. That is what makes them fast and simple, and what Pydantic adds (11.4). Compared with typing.NamedTuple, a dataclass is mutable by default, can have defaults computed per instance, __post_init__, slots and ordering control; a named tuple is an immutable tuple (it can be unpacked and indexed), lighter, but less flexible. Use dataclasses for internal structured data, Pydantic models at boundaries, TypedDict for dicts that stay dicts (11.2).

from dataclasses import dataclass, field

@dataclass
class Document:
    id: str
    text: str
    tags: list[str] = field(default_factory=list)
    score: float = 0.0
    embedding: list[float] = field(default_factory=list, repr=False, compare=False)

    def word_count(self):
        return len(self.text.split())

    def tag(self, label):
        label = label.lower()
        if label not in self.tags:
            self.tags.append(label)
        return self

default_factory=list gives each document its own tag list, so tagging a leaves b untouched, the bug that mutable defaults cause in hand-written classes (9.1) is impossible here. Methods live in the class as usual; @dataclass only adds the generated ones.

solution.py
import dataclasses
from dataclasses import dataclass

@dataclass(frozen=True, slots=True)
class GenerationConfig:
    model: str
    temperature: float = 0.0
    max_tokens: int = 512
    stop: tuple[str, ...] = ()

    def __post_init__(self):
        if not self.model.strip():
            raise ValueError("model must not be blank")
        if not 0 <= self.temperature <= 2:
            raise ValueError(f"temperature must be in [0, 2], got {self.temperature}")
        if self.max_tokens < 1:
            raise ValueError(f"max_tokens must be positive, got {self.max_tokens}")
        object.__setattr__(self, "stop", tuple(dict.fromkeys(self.stop)))

    def with_changes(self, **changes):
        return dataclasses.replace(self, **changes)

Immutability plus validation in __post_init__ gives the strongest guarantee a plain Python object can have: every config that exists is valid, and stays valid, because nothing can change it, and every "change" goes through replace, which constructs a new instance and validates it again. Frozen dataclasses block self.stop = ..., so normalisation uses object.__setattr__, the same escape hatch as 9.3. dict.fromkeys removes duplicate stop sequences in order (4.5). Being frozen also makes configs hashable, so they can key caches of model responses, and slots make them small. This is the hand-made version of a Pydantic model with frozen=True and validators (11.4).

solution.py
import json
from dataclasses import dataclass, field, asdict

@dataclass
class Metric:
    name: str
    value: float

@dataclass
class Run:
    run_id: str
    params: dict[str, float]
    metrics: list[Metric] = field(default_factory=list)

    @classmethod
    def from_dict(cls, data):
        missing = {"run_id", "params"} - data.keys()
        if missing:
            raise KeyError(f"missing keys: {', '.join(sorted(missing))}")
        return cls(data["run_id"], dict(data["params"]), [Metric(**m) for m in data.get("metrics", [])])

    def to_json(self):
        return json.dumps(asdict(self), sort_keys=True)

    def best(self, name):
        values = [m.value for m in self.metrics if m.name == name]
        return max(values) if values else None

asdict converts nested dataclasses to plain dicts and lists recursively, which makes saving runs to JSON one line, but it is one-way: going back requires knowing which dicts should become Metrics, which is what from_dict encodes. The round trip test (from_dict(asdict(r)) == r) is the check every serialisable class should have. Metric(**m) unpacks each dict into the constructor, so an unexpected key in the data raises TypeError, a cheap guard against silently dropping fields. Experiment trackers store run records in exactly this shape; Pydantic does the reverse conversion automatically from the type hints (11.4).

asdict is general: for every field it checks whether the value is a dataclass, a list, a tuple or a dict, recurses into it, and deep-copies what it finds, so that the result shares nothing with the object. For flat records of strings and numbers that machinery is pure overhead; a dict built directly reads three attributes. Use asdict when you need its guarantees (nested dataclasses, an independent copy), and build dicts directly, or use vars(row) for a shallow copy of the fields, on hot paths such as serialising every row of an export.

SolutionShow the solution and why
solution.py
import dataclasses, typing
from dataclasses import dataclass, field


def flatten(obj, prefix=""):
    out = {}
    for f in dataclasses.fields(obj):
        value = getattr(obj, f.name)
        if dataclasses.is_dataclass(value):
            out.update(flatten(value, prefix + f.name + "."))
        else:
            out[prefix + f.name] = value
    return out


def _convert(value, hint):
    if not isinstance(value, str) or hint is str:
        return value
    if hint is bool:
        if value.lower() in ("true", "false"):
            return value.lower() == "true"
        raise ValueError(f"not a bool: {value!r}")
    if hint in (int, float):
        return hint(value)
    return value


def unflatten(cls, flat, _prefix=""):
    hints = typing.get_type_hints(cls)
    names = {f.name for f in dataclasses.fields(cls)}
    if not _prefix:
        for key in flat:
            head = key.split(".", 1)[0]
            if head not in names:
                raise KeyError(f"unknown config key: {key}")
    kwargs = {}
    for f in dataclasses.fields(cls):
        key = _prefix + f.name
        hint = hints[f.name]
        if dataclasses.is_dataclass(hint):
            sub_names = {g.name for g in dataclasses.fields(hint)}
            for k in flat:
                if k.startswith(key + ".") and k[len(key) + 1:].split(".", 1)[0] not in sub_names:
                    raise KeyError(f"unknown config key: {k}")
            if any(k.startswith(key + ".") for k in flat):
                kwargs[f.name] = unflatten(hint, flat, key + ".")
        elif key in flat:
            kwargs[f.name] = _convert(flat[key], hint)
    return cls(**kwargs)

dataclasses.fields and the type hints are all a generic tool needs: flatten walks the fields and recurses into nested dataclasses, producing the flat keys that trackers like MLflow and Weights & Biases expect, and unflatten uses each field's annotated type to decide whether to recurse (a dataclass) or to convert (a string from the command line to int, float or bool). Fields not present keep their defaults, because they are simply not passed to the constructor, and unknown keys are rejected so that a typo like model.layerz=3 fails instead of being silently ignored, the most common way hyperparameter overrides go wrong. This is the core of what configuration libraries such as Hydra and OmegaConf structured configs, and simple_parsing, do with dataclasses.

solution.py
import dataclasses

def diff(a, b, prefix=""):
    if type(a) is not type(b) or not dataclasses.is_dataclass(a):
        raise TypeError(f"cannot diff {type(a).__name__} with {type(b).__name__}")
    changes = {}
    for f in dataclasses.fields(a):
        if not f.compare:
            continue
        old, new = getattr(a, f.name), getattr(b, f.name)
        path = prefix + f.name
        if dataclasses.is_dataclass(old) and dataclasses.is_dataclass(new) and type(old) is type(new):
            changes.update(diff(old, new, path + "."))
        elif old != new:
            changes[path] = (old, new)
    return changes

Lists are compared by value and reported whole, which is the useful granularity for schedules and layer sizes. Tools such as MLflow's run comparison and deepdiff provide richer versions.

Interview

17. What does @dataclass generate, and when would you not use it?

SolutionModel answer

From the annotated class attributes it generates __init__ (fields in declaration order, with defaults and default_factory), __repr__ and __eq__; with options, ordering methods (order=True), immutability plus __hash__ (frozen=True), __slots__ (slots=True) and keyword-only parameters (kw_only=True); __post_init__ hooks into construction for validation and derived fields, and fields, asdict, astuple and replace work with any dataclass. Do not use it when you need validation or conversion of untrusted input (use Pydantic), when the object is mostly behaviour with internal state rather than data (a client, a cache: write a normal class), when the data should stay a plain dict for an API (TypedDict), or for huge numbers of records where columnar structures (DataFrames, arrays) are far more efficient.

Interview

18. Explain the hashing rules of dataclasses: eq, frozen and unsafe_hash.

SolutionModel answer

With the default eq=True and frozen=False, a dataclass defines value-based __eq__ and sets __hash__ to None, so instances are unhashable: a mutable object whose equality depends on its fields must not live in a set, since changing a field would break the set. With frozen=True (and eq=True), fields cannot be reassigned, so the dataclass generates __hash__ from the same fields as __eq__ (those with compare=True), and instances work as set members and dict keys. unsafe_hash=True forces a field-based hash on a mutable dataclass; it is only correct if the compared fields are never changed while the object is stored, which is easy to violate. eq=False keeps identity-based equality and hashing from object. Use compare=False on fields that should not affect identity, such as timestamps or caches.

19. How would you model configuration for ML experiments, and why?

SolutionModel answer

Use typed, nested, structured objects instead of loose dicts: one dataclass (or Pydantic model) per component (data, model, optimiser, training, evaluation), composed into a root config, with types and defaults in one place. Make configs immutable (frozen) so a run cannot change its own settings halfway, and derive variants with replace or overrides; validate values when the config is built (ranges, allowed choices with Literal), failing before any expensive work starts. Support overrides from the command line or files by flattening to dotted keys and converting strings to the annotated types, rejecting unknown keys so typos fail. Serialise the fully resolved config (asdict to JSON or YAML) and log it with every run, together with the code version and data version, so results are reproducible, and diff configs to explain differences between runs. Libraries such as Hydra and OmegaConf structured configs, or Pydantic settings, implement these patterns; at the boundary where configs are loaded from files or environment variables, Pydantic's validation and error messages are especially valuable.

Recap

  • @dataclass generates __init__, __repr__ and __eq__ from annotated fields; hints are not validated.
  • Mutable defaults need field(default_factory=list); field() also offers repr=False, compare=False, init=False, kw_only and metadata.
  • __post_init__ validates, normalises and computes init=False fields; InitVar passes construction-only values.
  • frozen=True makes instances immutable and hashable; replace builds validated copies; order=True compares fields in declaration order; slots=True saves memory.
  • fields, asdict and astuple make generic tools possible; use kw_only for inheritance with defaults, and Pydantic when input must be validated.
