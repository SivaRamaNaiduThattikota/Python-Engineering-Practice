15.1 Imports and modules

Every Python project is a tree of modules, and many confusing errors (ModuleNotFoundError, circular imports, a patch that does nothing, a local file shadowing a library) come from not knowing what import actually does. Module objects and sys.modules, the search path, packages and relative imports, __name__ and python -m, circular imports and how to break them, import-time side effects, __all__, and dynamic imports for plugins. Problems build real package folders with lessontools.make_tree, which writes files and puts their folder on sys.path.

1What import does

import shop does three things. It looks in sys.modules, a dict of every module already imported, and if shop is there, simply binds the name. Otherwise it finds the module by searching the folders in sys.path in order (the folder of the script you ran, or the current folder for python -m and the REPL, then the PYTHONPATH entries, then the standard library and site-packages). Then it executes the module's code from top to bottom in a fresh namespace, stores the module object in sys.modules before running it, and binds the name. So a module's top-level code runs once per process, however many files import it, and every importer shares the same module object.

from shop import price imports shop the same way and then binds the name price in the importing module to the object shop.price refers to at that moment. If shop later rebinds price, the importer still holds the old object, which is why patching must happen where a name is looked up (13.3), and why import shop then shop.price(...) sees updates. import shop.cart as cart binds a short name; from shop import * imports the names listed in shop.__all__, or all public names if it is not defined.

import_once.py
import sys
from lessontools import make_tree, forget

make_tree({"pricing_demo.py": '''
print("  running pricing_demo top-level code")
TAX = 0.2

def price(net):
    return round(net * (1 + TAX), 2)
'''})
print("before:", "pricing_demo" in sys.modules)
import pricing_demo
import pricing_demo as again
from pricing_demo import price, TAX
print(again is pricing_demo is sys.modules["pricing_demo"], price(10))
pricing_demo.TAX = 0.1
print(pricing_demo.price(10), TAX)
forget("pricing_demo")
import pricing_demo
print(pricing_demo.TAX, pricing_demo is again)
Output

The top-level code ran once for three import statements; all names refer to the same module object. Changing TAX on the module changed price's result, because price reads the module global at call time, while the copied name TAX kept the old value. Removing the entry from sys.modules (what forget does) makes the next import run the file again and create a new module object; importlib.reload(module) re-runs the code into the existing object instead.

2Packages and relative imports

A package is a folder of modules. With an __init__.py file it is a regular package: importing shop runs shop/__init__.py, and import shop.cart imports shop first and then shop/cart.py as shop.cart. __init__.py is often empty, or re-exports the package's public API (from .cart import Cart) so users can write from shop import Cart. Folders without __init__.py can still be imported as namespace packages, which exist so that several distributions can share one package name; for your own code, add __init__.py to avoid surprises.

Inside a package, modules refer to each other with absolute imports (from shop.cart import Cart) or relative ones (from .cart import Cart, from ..utils import slugify), where dots count package levels from the current module. Relative imports only work in modules that are part of a package, so running a package module as a script (python shop/cart.py) breaks them: the file runs as __main__ with no parent package. Run it as python -m shop.cart instead, which imports the package properly and runs the module as __main__. A project's code usually lives in a src/ folder with the package inside (src/shop/...), and is installed in development mode (15.2) so import shop works from anywhere, including tests.

3__name__ and running modules

Every module has __name__: its import name ("shopkit.cart"), except the module Python was asked to run, which is called "__main__". The idiom if __name__ == "__main__": therefore separates code to run when the file is executed (a command-line entry point, a quick demo) from definitions that importers need, and it is essential for multiprocessing (14.3). Two related attributes: __file__ is the path the module was loaded from, and __package__ is the package used to resolve relative imports. A file run directly and the same file imported are two different module objects (__main__ and shopkit.cart), each with its own globals, a classic source of "my singleton exists twice" bugs.

4Circular imports

If a imports b and b imports a, importing a starts running a, which reaches import b, which starts running b, which reaches import a. Because a is already in sys.modules (it is put there before its code runs), Python hands b the partially initialised a, whose code stopped at the import b line. import a succeeds, but from a import helper fails with ImportError: cannot import name 'helper' from partially initialized module 'a' (most likely due to a circular import) if helper is defined below that line, and a.helper raises AttributeError if used at b's top level.

The fixes, from best to most tactical: restructure so the dependency goes one way (move the shared code both modules need into a third module that imports neither); depend on the module rather than the name (import a and use a.helper inside functions, which runs after both modules finished loading); move the import inside the function that needs it; or, for imports needed only by type hints, guard them with if typing.TYPE_CHECKING: (11.1). A circular import is usually a design smell: two modules that need each other's internals are really one module, or both need a third (problem 6).

5Import-time side effects and dynamic imports

Because importing runs a module's top-level code, anything slow or stateful there runs whenever anyone imports the module, including tests, linters, documentation tools and multiprocessing workers: connecting to a database, loading a 2 GB model, reading environment variables (12.4), configuring logging (12.3), or printing. Keep the top level to definitions and cheap constants; put setup in functions (get_client(), load_model()), called once, often cached with functools.cache (problem 12).

Imports can also be computed at run time: importlib.import_module("plugins.csv_loader") imports a module by its name string, which is how plugin systems, framework settings ("myapp.handlers.classify") and optional backends work. pkgutil.iter_modules(package.__path__) lists the modules in a package, so a registry can discover every plugin in a folder (problem 5). Importing a heavy optional dependency inside the function that uses it keeps start-up fast and lets the rest of the library work without it; catching ImportError there can give a helpful message such as "install the pdf extra" (problem 9). Packaging tools can also declare plugins as entry points (15.2), found with importlib.metadata.entry_points(group=...).

import importlib


def load_tool(dotted):
    module_name, sep, attr = dotted.partition(":")
    if not sep or not module_name or not attr:
        raise ValueError(f"expected 'module:function', got {dotted!r}")
    module = importlib.import_module(module_name)
    fn = getattr(module, attr, None)
    if fn is None or not callable(fn):
        raise LookupError(f"{module_name} has no {attr}")
    return fn

"module:attribute" strings are how configuration files refer to code: entry points in pyproject.toml (15.2), ASGI servers (uvicorn app.main:app), task queues and agent tool registries all use them. import_module performs a normal import from a string, so the module is cached in sys.modules and its own imports work as usual. Separate errors for "malformed string", "no such module" and "no such function" tell whoever wrote the configuration exactly what to fix.

solution.py
import importlib, inspect, pkgutil


def discover_tools(package_name):
    package = importlib.import_module(package_name)
    found = {}
    for info in pkgutil.iter_modules(package.__path__):
        if info.name.startswith("_"):
            continue
        module = importlib.import_module(f"{package_name}.{info.name}")
        for _, cls in inspect.getmembers(module, inspect.isclass):
            if cls.__module__ != module.__name__ or not isinstance(getattr(cls, "tool_name", None), str):
                continue
            if cls.tool_name in found:
                other = found[cls.tool_name].__module__
                raise ValueError(f"tool {cls.tool_name!r} defined in {other} and {module.__name__}")
            found[cls.tool_name] = cls
    return dict(sorted(found.items()))

Plugin discovery turns "add a file to this folder" into "add a tool to the agent", without editing a central list. pkgutil.iter_modules lists the modules inside the package's folder, import_module loads each, and inspect.getmembers finds the classes. Checking cls.__module__ matters: calc.py imports WebSearch, so it is visible there too, and without the check it would look like a duplicate. Private modules are skipped by convention, and a real duplicate is an error that names both places, because silently letting one plugin shadow another is a hard bug to find.

SolutionShow the solution and why
solution.py
import importlib, importlib.util


class _Missing:
    def __init__(self, name, extra):
        self._name, self._extra = name, extra

    def __getattr__(self, attr):
        raise ImportError(f"{self._name} is required for this feature: pip install 'mylib[{self._extra}]'")

    def __repr__(self):
        return f"<missing optional module {self._name}>"


def optional_import(name, extra):
    try:
        return importlib.import_module(name)
    except ImportError:
        return _Missing(name, extra)


def has_module(name):
    try:
        return importlib.util.find_spec(name) is not None
    except ModuleNotFoundError:
        return False

Optional features (PDF parsing, GPU backends, a specific vector store) should not force every user to install their dependencies, nor fail with a bare ModuleNotFoundError deep inside the code. The placeholder delays the failure until the feature is actually used and turns it into instructions, naming the extra that installs it (15.2). __getattr__ is only called for attributes that are not found normally (9.3), so _name and _extra still work. find_spec answers "is it installed?" without running the module's import-time code; it raises ModuleNotFoundError when a parent package is missing, hence the try.

FILES = {
    "textkit_f10.py": '''
import json, re

__all__ = ["clean", "tokenize"]

def normalise(text):
    return re.sub(r"[ ]+", " ", text).strip()

def clean(text):
    return normalise(text).lower()

Renaming the helper to _normalise would also hide it from star imports and signal that it is private.

11. Find import cycles in a project

Write import_graph(root, package) that reads every .py file under root/package with ast (without importing), and returns a dict from each module's dotted name to the sorted list of modules inside the package it imports (via import x or from x import y, resolving relative imports; from . import name refers to the submodule name if such a file exists). solution.py
import ast
from pathlib import Path


def _module_name(path, root):
    parts = list(path.relative_to(root).with_suffix("").parts)
    if parts[-1] == "__init__":
        parts.pop()
    return ".".join(parts)


def import_graph(root, package):
    root = Path(root)
    files = {_module_name(p, root): p for p in (root / package).rglob("*.py")}
    graph = {}
    for name, path in files.items():
        pkg = name if path.name == "__init__.py" else name.rpartition(".")[0]
        deps = set()
        for node in ast.walk(ast.parse(path.read_text(encoding="utf-8"))):
            if isinstance(node, ast.Import):
                targets = [alias.name for alias in node.names]
            elif isinstance(node, ast.ImportFrom):
                if node.level:
                    parts = pkg.split(".")
                    base = parts[: len(parts) - (node.level - 1)]
                    mod = ".".join(base + ([node.module] if node.module else []))
                else:
                    mod = node.module
                targets = []
                for alias in node.names:
                    full = f"{mod}.{alias.name}"
                    targets.append(full if full in files else mod)
            else:
                continue
            for t in targets:
                if t in files and t != name:
                    deps.add(t)
        graph[name] = sorted(deps)
    return dict(sorted(graph.items()))


def find_cycles(graph):
    cycles = set()

    def dfs(node, path, on_path):
        for nxt in graph.get(node, []):
            if nxt in on_path:
                cycle = path[path.index(nxt):]
                i = cycle.index(min(cycle))
                cycles.add(tuple(cycle[i:] + cycle[:i]))
            elif len(path) < len(graph) + 1:
                on_path.add(nxt)
                path.append(nxt)
                dfs(nxt, path, on_path)
                path.pop()
                on_path.discard(nxt)

    for start in graph:
        dfs(start, [start], {start})
    return [list(c) for c in sorted(cycles)]

Reading imports with ast shows a project's structure without running it, which is safe on code with import-time side effects and is how tools such as pydeps, import-linter and Ruff's import rules work. Relative imports are resolved with the module's package and the number of leading dots, and from . import tax counts as a dependency on the submodule tax (not on the package) because that file exists, while from .api import charge depends on billing.api. The cycle search is a depth-first search that notices when it reaches a module already on the current path (16.4); rotating each cycle to start at its smallest name makes the same cycle found from different starting points identical. Running this in CI and failing on new cycles keeps a growing codebase layered.

Interview

14. What happens when Python executes import x?

SolutionModel answer

Python first checks sys.modules; if x is already imported, it binds the name to that module object and does nothing else. Otherwise it finds the module: for a dotted name it imports the parent packages first, then asks the finders in sys.meta_path (which search sys.path entries: the script's folder, PYTHONPATH, the standard library, site-packages, and handle built-in, frozen, extension and zip modules) for a spec describing how to load it. It creates a module object, inserts it into sys.modules before executing (which is what makes circular imports partially work), and executes the module's code in the module's namespace, compiling it to bytecode and caching that in __pycache__. Finally it binds the name in the importer's namespace. Consequences: module code runs once per process, all importers share the module object, from x import y copies a reference at import time, and import-time side effects run wherever the module is imported.

Interview

15. How do you fix a circular import?

SolutionModel answer

First understand it: module A imports B at the top, B imports A, so B receives a partially initialised A and fails when it asks for a name A has not defined yet. The best fix is structural: find what both modules need from each other and move it into a third module that both import (shared types, constants, interfaces), or merge two modules that are really one; this restores a one-way dependency graph. Tactical fixes: import the module rather than names (import a and use a.helper inside functions), move the import into the function that needs it, or, when the dependency exists only for type annotations, import under if TYPE_CHECKING: and use string or lazy annotations. Dependency injection (passing the object in instead of importing it) also breaks cycles. Tools such as import-linter or a CI check of the import graph prevent new cycles.

Interview

16. Your package imports fine in tests but fails with ModuleNotFoundError in production (or the reverse). What do you check?

SolutionModel answer

Check how the code is found. Tests often pass because pytest inserts the project root (or test folders) into sys.path, or because the current working directory is the repository root, while production runs an installed package from another directory. Use a src/ layout and install the project (pip install -e . or uv sync) so tests import the installed package exactly as production does. Check packaging: is the module included in the built wheel (package discovery settings in pyproject.toml, missing __init__.py, data files), and are optional dependencies installed in that environment? Check for shadowing: a local file or folder named like a dependency (requests.py, config/ without __init__.py), or two installed distributions providing the same package. Check which interpreter and environment run the code (sys.executable, sys.path, pip list in that environment), and relative imports in modules run as scripts instead of with python -m. Printing module.__file__ and sys.path at the failure point usually settles it in minutes.

Recap

  • import checks sys.modules, searches sys.path, runs the module once, and caches it; every importer shares the one module object.
  • from m import name copies a reference at import time; read changing values through the module (m.name).
  • Packages are folders with __init__.py; use relative (from . import x) or absolute imports inside them, and python -m pkg.module to run their modules.
  • Circular imports hand a partially initialised module to the other side: restructure, import modules instead of names, or import inside functions.
  • Keep import time free of side effects (lazy get_client()), use __all__ for public APIs, importlib.import_module for plugins, and never name files after libraries.
