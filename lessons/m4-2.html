1sort, sorted and stability

xs.sort() sorts the list in place and returns None; sorted(iterable) builds a new list from any iterable (2.2). Both take key= (3.5) and reverse=True. Both are stable: items whose keys are equal keep the order they had before the sort. Stability is what lets you sort by several rules in separate passes, least important first, and it holds even with reverse=True.

stability.py
tickets = [("billing", "B-7"), ("auth", "A-2"), ("billing", "B-3"), ("auth", "A-9")]
print(sorted(tickets, key=lambda t: t[0]))                 # B-7 stays before B-3, A-2 before A-9
print(sorted(tickets, key=lambda t: t[0], reverse=True))   # still stable within each team

by_id = sorted(tickets, key=lambda t: t[1])                # secondary rule first
print(sorted(by_id, key=lambda t: t[0]))                   # primary rule second: both hold
Output
[('auth', 'A-2'), ('auth', 'A-9'), ('billing', 'B-7'), ('billing', 'B-3')]
[('billing', 'B-7'), ('billing', 'B-3'), ('auth', 'A-2'), ('auth', 'A-9')]
[('auth', 'A-2'), ('auth', 'A-9'), ('billing', 'B-3'), ('billing', 'B-7')]
≈
SQL / Power BI

ORDER BY team, id in SQL is one tuple key in Python: key=lambda t: (t[0], t[1]). SQL makes no promise about the order of rows with equal sort values unless you list enough columns; Python's stability is that promise, which is why the two-pass trick works and why a sort never shuffles ties.

2How the sort behaves on real data

Python uses Timsort. Step by step: it scans the list for runs, stretches that are already ascending (or strictly descending, which it reverses), extends short runs with insertion sort, and then merges runs pairwise, much like merge sort. The consequences you can rely on:

  • Worst case O(n log n) comparisons, and never the O(n²) worst case some quicksorts have.
  • Adaptive: already sorted or reversed data takes about n comparisons, O(n). Data that is "mostly sorted" (log lines appended in time order with a few late arrivals, scores that change a little between runs) is much cheaper than random data.
  • Stable, as above, and it only uses < between keys.

You can watch this by counting comparisons. functools.cmp_to_key wraps an old-style comparison function, and ours counts every call:

comparisons.py
import random
from functools import cmp_to_key

def count_comparisons(data):
    calls = 0
    def cmp(a, b):
        nonlocal calls
        calls += 1
        return (a > b) - (a < b)
    sorted(data, key=cmp_to_key(cmp))
    return calls

n = 1000
ordered = list(range(n))
random.seed(0)
shuffled = random.sample(ordered, n)
nearly = ordered[:]
for i in range(0, n, 100):                 # a few items out of place
    nearly[i], nearly[i + 1] = nearly[i + 1], nearly[i]
print("sorted  ", count_comparisons(ordered))
print("reversed", count_comparisons(ordered[::-1]))
print("nearly  ", count_comparisons(nearly))
print("shuffled", count_comparisons(shuffled))
Output
sorted   999
reversed 999
nearly   1255
shuffled 8667

Sorted and reversed input cost about n comparisons; random input costs many more, roughly n * log2(n), and the nearly sorted case sits in between. The rule of thumb: sorting is cheap, but not free. Sort once and reuse the result rather than sorting inside a loop, and do not sort at all when you only need the minimum, the maximum or a few top items (next sections).

3Searching: linear scans and binary search

x in xs, xs.index(x) and xs.count(x) scan from the front: O(n). If you search a list many times, either put the values in a set or dict (O(1) per lookup, 4.4) or, when you need order-based questions ("where would this value go?", "how many values are below 0.5?", "all events between two times"), keep the list sorted and use binary search.

Binary search step by step: look at the middle item of the range. If the target is smaller, keep only the left half; otherwise keep the right half. Repeat until the range is empty. Each step halves the range, so a million items need about 20 steps. The bisect module implements it correctly (writing it yourself is a famous source of off-by-one bugs, problem 8):

  • bisect_left(xs, x): the first position where x could be inserted and keep xs sorted, which is before any items equal to x.
  • bisect_right(xs, x) (or plain bisect): the position after any items equal to x.
  • insort(xs, x): insert x at the right place. Finding the place is O(log n), but inserting still shifts items, O(n).
bisect_basics.py
from bisect import bisect_left, bisect_right, insort

latencies = [12, 15, 15, 15, 20, 31, 48]       # sorted
print(bisect_left(latencies, 15), bisect_right(latencies, 15))
print(bisect_right(latencies, 15) - bisect_left(latencies, 15))   # how many are exactly 15
print(bisect_left(latencies, 30), len(latencies) - bisect_left(latencies, 30))  # values >= 30
insort(latencies, 18)
print(latencies)
Output
1 4
3
5 2
[12, 15, 15, 15, 18, 20, 31, 48]

The two "how many" lines are the useful pattern: with a sorted list, counts in a range are a subtraction of two bisect positions, O(log n) each, instead of a scan. Since Python 3.10 the bisect functions also take key=, so you can search a sorted list of records by one field.

4Top-k without sorting everything

To get the 10 best of a million scores, sorting all of them is O(n log n) work to keep 10 items. heapq.nlargest(k, xs) walks the data once while keeping only the best k in a small heap, about O(n log k) time and O(k) memory, and it works on any iterable, including a generator that never fits in memory (Module 6). heapq.nsmallest is the mirror. For a single best item, max and min are O(n) and simplest of all.

top_k.py
import heapq

scores = {"d1": 0.31, "d2": 0.92, "d3": 0.77, "d4": 0.92, "d5": 0.15}
print(heapq.nlargest(3, scores.items(), key=lambda kv: kv[1]))
print(heapq.nsmallest(2, scores, key=scores.get))
print(max(scores, key=scores.get))
Output
[('d2', 0.92), ('d4', 0.92), ('d3', 0.77)]
['d5', 'd1']
d2

Rules of thumb for k

For k = 1, use max / min. For small k (say up to a few hundred) on big data, use heapq.nlargest. When k is a large fraction of n, plain sorted(...)[:k] is just as fast. For numpy arrays, np.argpartition(arr, -k)[-k:] finds the top-k positions in O(n), then you sort only those k.

5What breaks a sort: NaN and mixed types

A sort assumes its comparisons are consistent: if a < b and b < c, then a < c. NaN breaks that, because every comparison with NaN is False (2.1). Python does not raise an error; it just produces an order that is not sorted, and where the NaNs end up depends on the input. Mixed types fail loudly instead: Python 3 refuses to compare, say, None with a number (3.5).

nan_sort.py
nan = float("nan")
scores = [0.3, nan, 0.9, 0.1, nan, 0.5]
print(sorted(scores))                          # NOT sorted, and no error
import math
clean = sorted(s for s in scores if not math.isnan(s))
print(clean)
print(sorted(scores, key=lambda s: (math.isnan(s), s)))   # NaNs last, the rest in order
Output
[0.3, nan, 0.1, 0.9, nan, 0.5]
[0.1, 0.3, 0.5, 0.9]
[0.1, 0.3, 0.5, 0.9, nan, nan]

This matters in ML, where a model can output NaN for a bad input and a ranking step silently mis-orders every item around it. Filter NaNs out, or sort with a key that puts them in a group of their own, as above. (numpy's np.sort and pandas put NaN at the end by design.)

bisect_right(cutoffs, score) counts how many cutoffs are less than or equal to the score. That count is the label index.

SolutionShow the solution and why
solution.py
from bisect import bisect_right

def band(score, cutoffs, labels):
    return labels[bisect_right(cutoffs, score)]

bisect_right returns the number of cutoffs <= score, which is exactly the index of the band, so a score equal to a cutoff moves up into the next band (0.4 is "medium"). 5. Rank with ties

Write ranks(scores) that returns the rank of each score in the original order, where rank 1 is the highest and tied scores share the best rank they would get (competition ranking: 1, 2, 2, 4). Do it with one sort.

TestsThe 4 checks Run tests uses
assert ranks([0.9, 0.7, 0.8, 0.7]) == [1, 3, 2, 3]
assert ranks([5, 5, 5]) == [1, 1, 1]
assert ranks([1, 2, 3, 4]) == [4, 3, 2, 1]
assert ranks([]) == []
Hint 1Open a hint

Sort the positions by score, highest first: order = sorted(range(len(scores)), key=lambda i: -scores[i]).

Hint 2Open a hint

Walk order; when a score equals the previous one, reuse the previous rank, otherwise the rank is the current position + 1.

SolutionShow the solution and why
solution.py
def ranks(scores):
    order = sorted(range(len(scores)), key=lambda i: -scores[i])
    out = [0] * len(scores)
    for pos, i in enumerate(order):
        if pos > 0 and scores[i] == scores[order[pos - 1]]:
            out[i] = out[order[pos - 1]]
        else:
            out[i] = pos + 1
    return out

Sorting the positions (an "argsort") rather than the scores keeps track of where each score came from, so the ranks can be written back in the original order. Equal scores are adjacent after the sort, so one comparison with the previous item detects ties. This is SQL's RANK() window function; DENSE_RANK() would give 1, 2, 2, 3. In pandas, s.rank(method="min", ascending=False) does this one, and numpy's argsort is the array version of order.

7. Events in a time range

times is a sorted list of event timestamps (seconds). Write count_between(times, start, end) returning how many events have start <= t < end, and events_between(times, start, end) returning them as a list. Both must use bisect, so each query is O(log n) plus the size of the answer.

TestsThe 5 checks Run tests uses

assert count_between(t, 12, 20) == 3
assert events_between(t, 12, 20) == [12, 12, 15]

assert events_between(t, 20, 21) == [20, 20]

HintOpen a hint

For a half-open range [start, end), both bounds use bisect_left: the first position >= start and the first position >= end.

SolutionShow the solution and why
solution.py
from bisect import bisect_left

def count_between(times, start, end):
    return max(0, bisect_left(times, end) - bisect_left(times, start))

def events_between(times, start, end):
    return times[bisect_left(times, start):bisect_left(times, end)]

bisect_left(times, start) is the first event at or after start, and bisect_left(times, end) the first event at or after end, which is exactly where the half-open range stops: events at end are excluded. Counting is a subtraction, with no scan. max(0, ...) handles a backwards range. This is how time-series stores answer "events in the last hour" on sorted data, and the same reason a database index on a timestamp makes range queries fast.

8. A binary search that misses items

This hand-written binary search should return the position of target in the sorted list, or -1. It reports -1 for some items that are in the list. Fix it.

TestsThe 3 checks Run tests uses
xs = [2, 5, 8, 12, 16, 23, 38]
assert [find(xs, x) for x in xs] == list(range(len(xs)))
assert find(xs, 7) == -1 and find(xs, 1) == -1 and find(xs, 40) == -1
assert find([], 3) == -1 and find([4], 4) == 0
Hint 1Open a hint

hi = mid - 1 throws away position mid. What if xs[mid] is the target?

Hint 2Open a hint

Use the half-open convention: lo, hi = 0, len(xs), while lo < hi, then lo = mid + 1 or hi = mid.

SolutionShow the solution and why
solution.py
def find(xs, target):
    lo, hi = 0, len(xs)
    while lo < hi:
        mid = (lo + hi) // 2
        if xs[mid] < target:
            lo = mid + 1
        else:
            hi = mid
    return lo if lo < len(xs) and xs[lo] == target else -1

When xs[mid] equals the target, the else branch runs hi = mid - 1 and the target's own position is excluded, so the search can finish on a neighbour and report -1. The other classic mistake is the mirror image, lo = mid, which never shrinks the range once hi == lo + 1 and loops forever. The half-open version avoids both with one invariant: the answer is always in [lo, hi), every pass strictly shrinks it, and at the end lo is the leftmost position where target could go, exactly what bisect_left returns. In real code call bisect_left; in interviews, state the invariant out loud, because that is what they are checking.

13. The k-th smallest in average O(n)

Pick a random pivot, split into items less than, equal to and greater than it, and continue only in the part that contains the answer. Raise ValueError if k is out of range.

TestsThe 5 checks Run tests uses

Hint 1Open a hint

Three lists: lows, pivots, highs. If k <= len(lows), the answer is in lows; if it is within the pivots, it is the pivot; otherwise look in highs with k reduced.

Hint 2Open a hint

A loop that keeps replacing xs and k avoids deep recursion.

SolutionShow the solution and why
solution.py
import random

def kth_smallest(xs, k):
    if not 1 <= k <= len(xs):
        raise ValueError("k out of range")
    items = xs
    while True:
        pivot = random.choice(items)
        lows = [x for x in items if x < pivot]
        pivots = [x for x in items if x == pivot]
        if k <= len(lows):
            items = lows
        elif k <= len(lows) + len(pivots):
            return pivot
        else:
            k -= len(lows) + len(pivots)
            items = [x for x in items if x > pivot]

Each pass keeps only the part that can contain the answer, so on average the work is n + n/2 + n/4 + ... = O(2n), compared with O(n log n) for sorting. The random pivot makes the bad case (always picking the extreme) very unlikely; the pivots group handles duplicates, which would otherwise make a two-way split loop forever on data like [4, 4, 4]. The input is never changed, because each pass builds new lists. In practice, heapq.nsmallest(k, xs)[-1] or numpy's np.partition do this job; quickselect is the classic interview follow-up to "can you do better than sorting?".

    bisect.insort(board, (name, score), key=lambda entry: -entry[1])


def top(board, k):
    """The k best runs as (name, score), best first."""
    return board[:k]


def rank_of(board, name):
    """1 for the best run."""
    for i, (n, score) in enumerate(board):
        if n == name:
            return i + 1
    raise KeyError(name)

The original stored (score, name) ascending, so the best runs were at the end: rank_of counted from the worst, and top had to slice from the end, where board[-0:] returned the whole board (4.1). Equal scores were also ordered by name, not by when they were added, because the name was part of the tuple being compared. Storing (name, score) with key=-score fixes all three at once: ascending order of the key means best first, insort puts ties after existing entries (arrival order), and top becomes a plain front slice. Choosing the storage order so that the common query is the simple one is a general design habit.

solution.py
import heapq
from itertools import islice

def merge_shards(shards, limit):
    merged = heapq.merge(*shards, key=lambda r: r[0], reverse=True)
    return list(islice(merged, limit))

heapq.merge keeps one candidate per shard in a heap and repeatedly yields the best, so producing each result costs O(log k), and it is lazy: islice stops after limit items, so most of the data is never touched. Total work is about O(limit · log k) instead of sorting everything, O(N log N). reverse=True is needed because the inputs are sorted highest first. This is the merge step of distributed search (each shard returns its local top results, a coordinator merges them) and of external sorting when data does not fit in memory.

Because NaN compares False with everything, the sort cannot place it and the values around it end up out of order: 0.9 sits after 0.4. Worse, sorting the broken result again gives back the same list (True), so "re-sort and compare" cannot detect the problem, and nothing raises an error. max and min are just as fragile: they keep the first item unless a later one compares strictly better, so a NaN in first place "wins", while a NaN later on is ignored. 17. What are the properties of Python's sort, and why do they matter?

SolutionModel answer

Python's sort/sorted use Timsort: O(n log n) in the worst case, O(n) on already sorted or reverse-sorted data (it is adaptive, finding existing runs and merging them), and stable, so equal keys keep their original order, even with reverse=True. Stability enables multi-key sorting in passes (least important key first) and makes results deterministic for ties. It compares keys only with <, so inconsistent comparisons, such as NaN or mixed types, give wrong orders or TypeError. key= is computed once per item (decorate-sort-undecorate), which is why a key function is much cheaper than a comparison function. sort is in place and returns None; sorted returns a new list from any iterable.

Interview

18. When would you use binary search (bisect) in real code?

SolutionModel answer

Whenever data is sorted and you ask order-based questions repeatedly: where a value would go, how many values fall in a range, which bucket a value belongs to. Examples: mapping scores to bands or grades with cutoffs, counting events in a time window from a sorted log, looking up the version or price that applies at a date, percentiles in a sorted sample, and keeping a sorted list up to date with insort. Each query is O(log n) instead of an O(n) scan. Mention the difference between bisect_left and bisect_right (which side of equal values), the key= parameter since Python 3.10, and that insort still costs O(n) to insert, so for heavy insert workloads a heap or a sorted container library is better.

19. You need the top 100 of 100 million scores that arrive as a stream. How do you do it?

SolutionModel answer

Do not collect and sort everything. Keep a min-heap of size 100: push the first 100 scores, then for each new score compare it with the heap's smallest; if it is larger, replace the smallest (heapq.heappushpop). That is O(n log k) time and O(k) memory, and it works on a stream because it never holds more than 100 items. heapq.nlargest(100, stream) implements exactly this. If the data is already in a numpy array, np.argpartition finds the top-k in O(n). If it is distributed, compute a local top-100 per partition and merge them (as in problem 15). Mention ties and NaN handling, and that approximate methods are acceptable when exact top-k is not needed.

Recap

  • sort (in place, returns None) and sorted (new list) are stable, O(n log n), and close to O(n) on partly sorted data.
  • Stability enables multi-key sorts in passes: least important key first, most important last.
  • in, index and count scan: O(n). On a sorted list, bisect answers "where" and "how many in a range" in O(log n).
  • For top-k, use max/min (k = 1), heapq.nlargest (small k), or np.argpartition; do not sort everything to keep a few.
  • NaN silently breaks sorting, max and min. Filter it or give it its own key group.
