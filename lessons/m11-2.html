11.2 Advanced typing

The typing tools that describe real data and APIs: TypedDict for JSON-shaped dicts, Literal for fixed sets of values, Callable for callbacks, generic functions and classes with type parameters, NewType, Annotated metadata and Final, and exhaustiveness checks with assert_never. What each does at run time (often nothing) and how libraries read them. Applied to chat messages, events, tool schemas and structured LLM output.

1TypedDict: the shape of a dict

Much data in Python code is a dict with a fixed set of string keys: a chat message {"role": ..., "content": ...}, a JSON payload, a row from a database, an API response. dict[str, str] cannot describe it, because the keys are not arbitrary and the values have different types. TypedDict does: you declare the keys and their types in class syntax, and a type checker then knows that msg["role"] is a string, that msg["contnet"] is a typo, and that a dict missing content is not a valid message.

typeddict.py
from typing import TypedDict, NotRequired, get_type_hints

class ChatMessage(TypedDict):
    role: str
    content: str
    name: NotRequired[str]          # may be absent

msg: ChatMessage = {"role": "user", "content": "Refund?"}
print(msg, type(msg).__name__, isinstance(msg, dict))
print(sorted(ChatMessage.__required_keys__), sorted(ChatMessage.__optional_keys__))
print(get_type_hints(ChatMessage))
bad: ChatMessage = {"role": 1}      # a type checker reports this; Python does not
print(bad)
Output
{'role': 'user', 'content': 'Refund?'} dict True
['content', 'role'] ['name']
{'role': <class 'str'>, 'content': <class 'str'>, 'name': <class 'str'>}
{'role': 1}

At run time a TypedDict is just a dict: ChatMessage(...) builds a plain dict, nothing is validated, and isinstance(x, ChatMessage) is not allowed. Its value is static: the checker verifies every place that builds or reads such dicts. Keys are required by default; NotRequired[...] marks one as optional, and class Options(TypedDict, total=False) makes all keys optional (with Required[...] for exceptions). The class keeps __required_keys__, __optional_keys__ and its hints, which is enough for a runtime validator (problem 5). Choose a TypedDict for data that stays a dict (JSON in and out); choose a dataclass or a Pydantic model for objects with behaviour or validation (11.3, 11.4).

2Literal: a fixed set of values

Many strings in real code are not arbitrary: a message role is "system", "user", "assistant" or "tool"; a finish reason is one of a few values; a mode is "fast" or "accurate". Literal["user", "assistant"] is a type whose only members are those exact values, so a type checker rejects role="admin" or the typo "asistant" at the call site. It works with strings, integers, booleans, enums and None, and combines with unions. Give the type a name with an alias so the set of values is defined once.

literal.py
from typing import Literal, get_args

Role = Literal["system", "user", "assistant", "tool"]
FinishReason = Literal["stop", "length", "tool_calls", "content_filter"]

def message(role: Role, content: str) -> dict:
    if role not in get_args(Role):              # runtime check from the same definition
        raise ValueError(f"role must be one of {get_args(Role)}, got {role!r}")
    return {"role": role, "content": content}

print(get_args(Role), message("user", "hi"))
try:
    message("admin", "x")
except ValueError as e:
    print("ValueError:", e)
print(get_args(Literal["a", 1, None]))
Output
('system', 'user', 'assistant', 'tool') {'role': 'user', 'content': 'hi'}
ValueError: role must be one of ('system', 'user', 'assistant', 'tool'), got 'admin'
('a', 1, None)

Because get_args returns the allowed values, the same alias can drive both static checking and runtime validation: there is one source of truth, so adding "tool" to the alias updates the validator too. A separate hard-coded list of valid roles is a classic drift bug: someone adds a role to the type and forgets the list (problem 3). LLM structured-output schemas turn Literal into a JSON Schema enum, which constrains the model to the listed values (problem 12).

3Callable: functions as values

Functions passed as arguments (callbacks, key functions, scorers, hooks, retry predicates) are typed with Callable[[arg types], return type] from collections.abc: Callable[[str], None] is "a function taking one string and returning nothing", like a streaming on_token callback; Callable[[str, list[str]], float] is a scorer. Callable[..., T] accepts any arguments. The checker then verifies both sides: that you pass a compatible function, and that you call it with the right arguments (problem 9). Objects with __call__ (9.2) satisfy Callable too.

callable.py
from collections.abc import Callable

def stream(text: str, on_token: Callable[[str], None]) -> int:
    count = 0
    for token in text.split():
        on_token(token)
        count += 1
    return count

def rank(docs: list[str], score: Callable[[str], float], k: int = 2) -> list[str]:
    return sorted(docs, key=score, reverse=True)[:k]

received: list[str] = []
print(stream("refunds take five days", received.append), received)
print(rank(["short", "a much longer document", "medium one"], score=len))
Output
4 ['refunds', 'take', 'five', 'days']
['a much longer document', 'medium one']

For decorators, which must accept "any function" and return "a function with the same signature", plain Callable[..., Any] loses the parameter types; typing.ParamSpec captures them, so a type checker still knows the decorated function's arguments. Library code uses it; in application code, functools.wraps plus Callable is usually enough.

4Generics: functions and classes with type parameters

Some functions work for any element type but connect their inputs and outputs: first(items) returns an element of the same type as the items; a cache maps keys of one type to values of another. Writing def first(items: list[Any]) -> Any loses that connection, so the checker no longer knows that first(["a"]) is a string. A type parameter keeps it: def first[T](items: Iterable[T]) -> T | None says "for some type T, given items of type T, return a T (or None)". The square brackets after the name are Python 3.12 syntax (PEP 695); older code declares T = TypeVar("T") at module level and uses it the same way.

generics.py
from collections.abc import Iterable, Hashable

def first[T](items: Iterable[T]) -> T | None:
    for item in items:
        return item
    return None

def group_by[K: Hashable, V](items: Iterable[V], key) -> dict[K, list[V]]:
    out: dict = {}
    for item in items:
        out.setdefault(key(item), []).append(item)
    return out

class Registry[K, V]:
    def __init__(self) -> None:
        self._items: dict[K, V] = {}
    def add(self, key: K, value: V) -> None:
        self._items[key] = value
    def get(self, key: K) -> V | None:
        return self._items.get(key)

print(first(["refund", "reset"]), first([]), first(x * 2 for x in [3, 4]))
print(group_by(["refund", "reset", "invoice"], key=lambda w: w[0]))
r: Registry[str, float] = Registry()
r.add("small", 0.002)
print(r.get("small"), first.__type_params__, Registry.__type_params__)
Output
refund None 6
{'r': ['refund', 'reset'], 'i': ['invoice']}
0.002 (T,) (K, V)

[K: Hashable, V] adds a bound: K may be any type that is hashable, because it is used as a dict key. A constraint list, [T: (int, float)], allows exactly the listed types. At run time the parameters exist as objects (__type_params__) but nothing is checked; generics are for the type checker, which can now tell that r.get("small") returns float | None, and that r.add(1, "x") is wrong. Library containers are generic in the same way: list[T], dict[K, V], and the Sequence and Mapping of 11.1.

5NewType, Annotated and Final

NewType("UserId", str) creates a distinct type for the checker that is the same as str at run time: a function taking a UserId rejects a plain str (or an OrderId) unless you wrap it with UserId(value), which simply returns the value. It is a zero-cost way to stop ids, tokens or currencies of different kinds being mixed up. Final marks a name as a constant that must not be reassigned, and the checker enforces it. Annotated[T, metadata...] is the type T for the checker, with arbitrary extra metadata attached for libraries: Pydantic reads Annotated[int, Field(gt=0)] as "a positive int", FastAPI reads Annotated[str, Query(max_length=50)] as a query parameter constraint, and you can read it yourself with get_type_hints(func, include_extras=True).

extras.py
from typing import Annotated, Final, NewType, get_args, get_type_hints

UserId = NewType("UserId", str)
MAX_TOKENS: Final = 4096

def load_profile(user: UserId) -> str:
    return f"profile of {user}"

uid = UserId("u-123")
print(load_profile(uid), uid == "u-123", type(uid).__name__, UserId.__name__)

def search(query: Annotated[str, "the user's question"], k: Annotated[int, "between 1 and 20"] = 5) -> list[str]:
    return []

plain = get_type_hints(search)
extras = get_type_hints(search, include_extras=True)
print(plain["k"], extras["k"])
print(get_args(extras["query"]))
Output
profile of u-123 True str UserId
<class 'int'> typing.Annotated[int, 'between 1 and 20']
(<class 'str'>, "the user's question")

Without include_extras=True, get_type_hints strips the metadata and returns the plain type; with it, get_args returns the type followed by its metadata. That is how a schema generator can take parameter descriptions from Annotated instead of parsing docstrings, and how LLM tool frameworks let you write city: Annotated[str, "city name, e.g. Paris"] (problem 12).

6Exhaustiveness with assert_never

When code branches on a Literal or a union, you want to know that every case is handled, especially when a new case is added later (a new finish reason, a new event type). typing.assert_never(value) is the tool: put it in the final else branch. A type checker narrows the value through the earlier branches; if any member remains unhandled, the checker reports an error at assert_never, pointing at the forgotten case. At run time, reaching it raises AssertionError, which is the right behaviour for a value that should be impossible (problem 10).

assert_never.py
from typing import Literal, assert_never

Finish = Literal["stop", "length", "tool_calls"]

def handle(reason: Finish, text: str) -> str:
    if reason == "stop":
        return text
    elif reason == "length":
        return text + " [truncated]"
    elif reason == "tool_calls":
        return "(calling a tool)"
    else:
        assert_never(reason)          # a checker errors here if a case is missing

print(handle("stop", "done"), "|", handle("length", "half"))
try:
    handle("content_filter", "")      # a value the type does not allow
except AssertionError as e:
    print("AssertionError:", str(e)[:40])
Output
done | half [truncated]
AssertionError: Expected code to be unreachable, but got

match statements (Python 3.10) work the same way: case _: assert_never(reason). Together with Literal aliases and tagged TypedDicts (a "type" key whose value is a literal), this gives "discriminated unions", the pattern used for events in streaming APIs and for tool-call payloads: the tag says which shape the rest of the data has (problem 14).

from typing import Literal, TypedDict, get_args

Role = Literal["system", "user", "assistant", "tool"]


class Message(TypedDict):
    role: Role
    content: str


def make_message(role: Role, content: str) -> Message:
    if role not in get_args(Role):
        raise ValueError(f"role must be one of {get_args(Role)}, got {role!r}")
    if not content.strip():
        raise ValueError("content must not be empty")
    return {"role": role, "content": content}

The Literal alias is the single source of truth for valid roles: the type checker uses it at every call site, and the runtime check reads the same values with get_args, so the two can never disagree. The TypedDict describes the dict the function returns, so code that reads msg["role"] later is checked too. Returning a plain dict keeps the message ready to send to a chat API, which expects exactly this JSON shape. The SDKs of OpenAI and Anthropic define their message parameters as TypedDicts with Literal roles for this reason.

Hint 2Open a hint

Format union hints with str(hint) and literals with their get_args tuple.

SolutionShow the solution and why
solution.py
import types, typing


def _ok(value, hint):
    origin, args = typing.get_origin(hint), typing.get_args(hint)
    if origin is typing.Literal:
        return value in args
    if origin in (types.UnionType, typing.Union):
        return any(_ok(value, a) for a in args)
    if hint is type(None):
        return value is None
    if hint is int and isinstance(value, bool):
        return False
    return isinstance(value, hint)


def _describe(hint):
    if typing.get_origin(hint) is typing.Literal:
        return f"one of {typing.get_args(hint)}"
    return getattr(hint, "__name__", str(hint)) if typing.get_origin(hint) is None else str(hint)


def check(data, td):
    hints = typing.get_type_hints(td)
    problems = [f"missing key: {k}" for k in sorted(td.__required_keys__ - data.keys())]
    problems += [f"unknown key: {k}" for k in sorted(data.keys() - hints.keys())]
    for key in sorted(data.keys() & hints.keys()):
        value, hint = data[key], hints[key]
        if not _ok(value, hint):
            problems.append(f"{key}: expected {_describe(hint)}, got {value!r}" if typing.get_origin(hint) is typing.Literal
                            else f"{key}: expected {_describe(hint)}, got {type(value).__name__}")
    return problems

A TypedDict carries everything a validator needs: its hints (types per key) and its required and optional key sets, with NotRequired keys allowed to be absent. Literals are checked by membership in their options, unions by trying each member, and bool is excluded from int because JSON booleans should not pass as indexes. Collecting all problems in a predictable order produces one complete error report, which is far more useful when the data came from a model and you want to send the errors back for repair (7.4). This is a small version of what Pydantic's TypeAdapter(ToolCall).validate_python(data) does, including turning the TypedDict into a validator.

6. A helper that forgets what type it returns

first and pick are annotated with Any, so a type checker cannot tell that first(["a"]) is a str. Rewrite their annotations as generic functions with type parameters (Python 3.12 syntax): first[T](items: Iterable[T]) -> T | None and pick[K, V](mapping: Mapping[K, V], keys: Iterable[K]) -> dict[K, V]. Keep the behaviour.

TestsThe 3 checks Run tests uses

HintOpen a hint

def first[T](items: Iterable[T]) -> T | None: declares T for this function only.

SolutionShow the solution and why
solution.py
from collections.abc import Iterable, Mapping

def first[T](items: Iterable[T]) -> T | None:
    for item in items:
        return item
    return None

def pick[K, V](mapping: Mapping[K, V], keys: Iterable[K]) -> dict[K, V]:
    return {k: mapping[k] for k in keys if k in mapping}

Any switches checking off, so the information "the result has the same type as the elements" was lost, and a caller doing first(names).upper() or first(scores) + 1 got no help at all. Type parameters keep the link: for first(["a"]) the checker solves T = str and knows the result is str | None, so it also insists on the None check. pick relates three types at once: the keys you pass must match the mapping's key type, and the result keeps both. The parameters are visible at run time in __type_params__, but only the checker uses them.

7. A typed cache class

Write a generic class LRU[K, V] (Python 3.12 syntax) with __init__(self, maxsize: int), get(self, key: K) -> V | None (marks the key as recently used), put(self, key: K, value: V) -> None (evicts the least recently used key when full), __len__ and __contains__. Annotate every method.

TestsThe 5 checks Run tests uses

assert c.get("a") == [0.1]

HintOpen a hint

class LRU[K, V]: declares the parameters for the whole class. Store self._data: dict[K, V] = {}; dict order tracks recency (9.2).

SolutionShow the solution and why
solution.py
class LRU[K, V]:
    def __init__(self, maxsize: int) -> None:
        self.maxsize = maxsize
        self._data: dict[K, V] = {}

    def get(self, key: K) -> V | None:
        if key not in self._data:
            return None
        value = self._data.pop(key)
        self._data[key] = value
        return value

    def put(self, key: K, value: V) -> None:
        if key in self._data:
            del self._data[key]
        elif len(self._data) >= self.maxsize:
            del self._data[next(iter(self._data))]
        self._data[key] = value

    def __len__(self) -> int:
        return len(self._data)

    def __contains__(self, key: object) -> bool:
        return key in self._data

With the class parameterised, a variable annotated LRU[str, list[float]] lets the checker verify every use: put(1, [0.1]) is a wrong key type, get("a") returns list[float] | None, so callers must handle a miss. The implementation is the dict-ordering LRU of 9.2. __contains__ takes object because in may be asked about anything; restricting it to K would make harmless checks a type error. Generic containers are everywhere in library code (vector stores keyed by id, caches, registries), and typing them once makes every user's code checked.

HintOpen a hint

SolutionShow the solution and why
solution.py
from collections.abc import Callable

def stream_reply(tokens: list[str], on_token: Callable[[str], None]) -> int:
    for token in tokens:
        on_token(token)
    return len(tokens)

Callable[[str], None] is a contract in both directions: callers may pass any function that takes one string, and the function promises to call it that way. Calling it with an index as well broke every conforming callback, here list.append, which takes exactly one argument. A type checker would report the call on_token(i, token) as having too many arguments, before the code ever ran. If the index were really needed, the right change is to the hint, Callable[[int, str], None], and to every caller, which the checker would then list.

from typing import Literal, assert_never

Finish = Literal["stop", "length", "tool_calls", "content_filter"]

def postprocess(reason: Finish, text: str) -> str:
    match reason:
        case "stop":
            return text.strip()
        case "length":
            return text.strip() + " ..."
        case "tool_calls":
            return ""
        case "content_filter":
            return "[filtered]"
        case _:
            assert_never(reason)

solution.py
import types, typing

SIMPLE = {str: "string", int: "integer", float: "number", bool: "boolean"}


def _schema(hint):
    origin, args = typing.get_origin(hint), typing.get_args(hint)
    if origin in (typing.NotRequired, typing.Required):
        return _schema(args[0])               # kept by include_extras; the key set already says it
    if origin is typing.Annotated:
        schema = _schema(args[0])
        descriptions = [m for m in args[1:] if isinstance(m, str)]
        if descriptions:
            schema["description"] = descriptions[0]
        return schema
    if origin in (types.UnionType, typing.Union):
        members = [a for a in args if a is not type(None)]
        if len(members) != 1 or len(members) == len(args):
            raise TypeError(f"only X | None unions are supported: {hint!r}")
        schema = _schema(members[0])
        schema["type"] = [schema["type"], "null"]
        return schema
    if origin is typing.Literal:
        return {"type": "string", "enum": list(args)}
    if origin is list:
        return {"type": "array", "items": _schema(args[0])}
    if hint in SIMPLE:
        return {"type": SIMPLE[hint]}
    raise TypeError(f"unsupported type: {hint!r}")


def json_schema(td):
    hints = typing.get_type_hints(td, include_extras=True)
    return {
        "type": "object",
        "properties": {name: _schema(h) for name, h in hints.items()},
        "required": sorted(td.__required_keys__),
        "additionalProperties": False,
    }

This is the bridge between Python types and constrained LLM output: the TypedDict describes the answer you want, and the generated schema is what you send as the response format or tool parameters, so the model can only produce the listed labels (enum), a number for confidence, and a list of strings for reasons. Annotated carries the per-field descriptions into the schema, where they act as instructions to the model. include_extras=True is essential, or the metadata is stripped; it also keeps the NotRequired wrapper, which the schema unwraps because the class's key sets already record which keys are optional. NotRequired keys are left out of required, and additionalProperties: False forbids invented fields, which strict structured-output modes require. Pydantic's model_json_schema() and TypeAdapter(...).json_schema() do this generation for you (11.4), but this is what they produce.

from typing import Annotated, Literal, get_args, get_type_hints

EventType = Literal["text", "tool_call", "error", "done"]
EVENT_TYPES = frozenset(get_args(EventType))


def build_dispatcher(handlers):
    missing = EVENT_TYPES - handlers.keys()
    extra = handlers.keys() - EVENT_TYPES
    if missing or extra:
        raise ValueError(f"handlers do not match EventType: missing {sorted(missing)}, unknown {sorted(extra)}")

    def dispatch(event):
        etype = event.get("type")
        if etype not in EVENT_TYPES:
            raise ValueError(f"unknown event type {etype!r}")
        return handlers[etype](event)
    return dispatch


def describe_handlers(handlers):
    out = {}
    for etype, fn in handlers.items():
        hint = get_type_hints(fn, include_extras=True).get("event")
        meta = getattr(hint, "__metadata__", ())
        out[etype] = meta[0] if meta else ""
    return out

Unknown event types returned None silently, so a new event type from a provider (or a typo in your own code) disappeared without a trace; rejecting values outside the Literal turns it into an immediate, named error. Completeness was only discovered at run time, when an error event finally arrived and found no handler; checking the registered types against get_args(EventType) when the dispatcher is built is the runtime version of assert_never's exhaustiveness, and it also catches handlers registered under misspelt types. And get_type_hints strips Annotated metadata by default, so __metadata__ was never there; include_extras=True keeps it. The Literal alias is the single source of truth for all three checks.

import typing
from typing import Literal, TypedDict


class TextEvent(TypedDict):
    type: Literal["text"]
    text: str


class ToolEvent(TypedDict):
    type: Literal["tool"]
    name: str
    args: dict


class DoneEvent(TypedDict):
    type: Literal["done"]
    tokens: int


EVENTS = {typing.get_args(typing.get_type_hints(cls)["type"])[0]: cls for cls in (TextEvent, ToolEvent, DoneEvent)}


def parse_event(data):
    if "type" not in data:
        raise ValueError("event has no 'type' tag")
    cls = EVENTS.get(data["type"])
    if cls is None:
        raise ValueError(f"unknown event type {data['type']!r}; expected one of {sorted(EVENTS)}")
    hints = typing.get_type_hints(cls)
    for key in sorted(cls.__required_keys__ - {"type"}):
        if key not in data:
            raise ValueError(f"{cls.__name__}: missing key {key!r}")
        expected, value = hints[key], data[key]
        if (expected is int and isinstance(value, bool)) or not isinstance(value, expected):
            raise ValueError(f"{cls.__name__}: {key!r} must be {expected.__name__}, got {type(value).__name__}")
    return cls.__name__, data

A discriminated union is a set of shapes distinguished by one tag field, and the tag tells you which shape to validate against: exactly how streaming events, tool calls and many JSON APIs are structured. Building the tag-to-class mapping from the classes' own Literal hints keeps it in sync with the definitions, so adding a fourth event type is a new class plus one name in the tuple. Each kind of failure gets its own message (unknown tag, missing key, wrong type), which is what you want in logs when a provider changes its format. For a type checker, after checking data["type"] == "tool" on a TextEvent | ToolEvent | DoneEvent, the value narrows to ToolEvent, so data["name"] is known to be a string. Pydantic supports this pattern directly with Field(discriminator="type") (11.4).

Interview

16. When would you use a TypedDict, a dataclass, or a Pydantic model?

SolutionModel answer

A TypedDict is for data that should stay a dict: JSON payloads, API parameters, messages passed straight to an SDK. It costs nothing at run time and gives static checking of keys and value types, but no validation, no methods and no defaults. A dataclass is for structured objects inside your program: it generates __init__, __repr__ and __eq__ from typed fields, supports defaults, immutability and slots, and is fast, but it does not validate or convert input. A Pydantic model is for data crossing a boundary: requests, configuration, files, LLM output; it validates and converts at run time, collects errors, serialises to and from JSON and generates JSON Schema, at some cost per object. A common architecture validates external data into Pydantic models at the edges, uses dataclasses or plain typed objects internally, and keeps TypedDicts for the exact JSON shapes that third-party SDKs expect.

Interview

17. What are generic types and type parameters for?

SolutionModel answer

They let one piece of code work for many types while keeping the relationships between types visible to the checker. Without them, a function like first(items) or a container like a cache must use Any, and the checker forgets that first(list_of_str) returns a str or that cache.get(key) returns the cached value's type, so errors downstream go unnoticed. With a type parameter, def first[T](items: Iterable[T]) -> T | None, the checker solves T from each call; with a generic class, class Cache[K, V], each instance is checked against its declared key and value types. Bounds ([K: Hashable]) and constraints ([T: (int, float)]) restrict what T may be. The standard collections (list[T], dict[K, V], Sequence[T]) are generic in exactly this way. At run time nothing is enforced: generics are a static tool, introspectable through __type_params__.

Interview

18. How do Python types relate to structured output from LLMs?

SolutionModel answer

Structured output (JSON mode with a schema, tool calling, "response format") constrains the model to produce JSON matching a JSON Schema, and that schema is best generated from Python types rather than written by hand: a TypedDict, dataclass or Pydantic model describes the fields, Literal becomes an enum so the model can only choose valid labels, X | None becomes nullable, list[X] becomes an array, and Annotated metadata or field descriptions become instructions the model reads. Required keys and additionalProperties: false keep it from omitting or inventing fields. The reply must still be validated against the same types (constraints can fail or be unsupported on some models, and values can be semantically wrong), usually by parsing into a Pydantic model, with a repair or retry loop that sends the validation errors back (7.4). Using the types as the single source of truth keeps the prompt, the schema, the validator and the code that consumes the result in agreement.

Recap

  • TypedDict types JSON-shaped dicts (required and NotRequired keys); at run time it is a plain dict and validates nothing.
  • Literal[...] lists exact allowed values; read them with get_args so runtime checks and the type share one definition.
  • Callable[[args], ret] types callbacks; type parameters (def f[T], class C[K, V]) keep input and output types linked.
  • NewType makes distinct ids for the checker at zero cost; Annotated attaches metadata for libraries; Final marks constants.
  • assert_never makes branches over literals and unions exhaustive; tagged TypedDicts form discriminated unions.
