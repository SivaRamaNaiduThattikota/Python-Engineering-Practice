3.1 Defining and calling functions

What def really does, how Python matches arguments to parameters and what its error messages mean, the missing-return bug, and the function metadata that frameworks like FastAPI read to call your code.

18 problems4 easy · 9 medium · 5 hard

1What def does, step by step

def is not a declaration that exists before the program starts. It is a statement that runs, at the moment Python reaches it, like an assignment. Running it does four things, in this order:

  • 1. Evaluate the defaults. Every default value in the signature is computed now, once (this is the 2.4 rule about mutable defaults).
  • 2. Build a function object. It holds the compiled body (__code__), the defaults (__defaults__), the docstring (__doc__), the name (__name__) and a link to the module's global names.
  • 3. Bind the name. The function's name is pointed at that object, exactly like name = object (2.1).
  • 4. Do not run the body. The body runs only when the function is called, and it runs again from the top on every call.
def_object.py
def greet(name):
    return f"Hi, {name}"

print(type(greet).__name__, greet.__name__)
print(greet)                     # the object itself; nothing has run yet
print(greet("Ana"))              # calling it runs the body
Output
function greet
<function greet at 0x1207530>
Hi, Ana

Step 4 surprises people: an error inside the body is not found when def runs, only when the faulty line is actually reached during a call. A function can sit in a module for months with a typo in a branch that is rarely taken.

body_runs_later.py
def risky(flag):
    if flag:

    return "fine"

Output

Because def is an assignment in disguise, everything from Module 2 applies to function names too. Running def again builds a new function object and moves the name; anything still holding the old object keeps the old code. A def inside a loop builds a new function on every pass. And a function cannot be called before its def has run.

def_rebinds.py
def greet():

def is like CREATE OR REPLACE PROCEDURE: it runs when the script reaches it, and running it again replaces the definition. One difference matters: in Python, an old reference (here old) keeps calling the old version, while SQL always calls the current procedure by name. In notebooks this is how a stale version of a function keeps running inside a list, a dict or a callback that captured it before you edited it.

2How a call fills the parameters

When you call a function, Python builds the parameter values in a fixed order. Knowing the order lets you predict any call, and read any error message, without guessing:

  • 1. Positional arguments fill the positional parameters from left to right. If there are more positional arguments than positional slots, the extras go into *args if the function has it, otherwise it is an error.
  • 2. Keyword arguments fill parameters by name. A name that was already filled in step 1 is an error ("multiple values"); a name that matches no parameter goes into **kwargs if there is one, otherwise it is an error ("unexpected keyword").
  • 3. Defaults fill any parameter that is still empty.
  • 4. Anything still empty is an error ("missing required argument").

Here is that algorithm worked through for one call to embed(texts, model="small", *, batch_size=32). The * makes batch_size keyword-only: after the *, no positional argument can reach it (lesson 3.2 covers *, /, *args and **kwargs in depth).

Call: embed(["a", "b"], batch_size=8)textsmodelbatch_size
1. positional, left to right["a", "b"](empty)(not reachable by position)
2. keywords, by name["a", "b"](empty)8
3. defaults["a", "b"]"small"8
4. anything missing?no, so the body runs

def embed(texts, model="small", *, batch_size=32):

1 texts, small, batch 4

Each error message names the function and the exact parameter, and each one is a failed step of the algorithm: missing (step 4), takes from 1 to 2 positional arguments but 3 were given (step 1: batch_size cannot be filled by position), multiple values (step 2: texts was already filled by position) and unexpected keyword (step 2: a typo). When an LLM tool call or a framework call fails, one of these four messages is usually the whole story, so it pays to read them word by word instead of skimming.

One rule is enforced even before the call runs: in the call itself, positional arguments must come before keyword arguments. embed(model="large", ["a"]) is a SyntaxError, found when the code is compiled, not when it runs.

3What return does

return expression does three things: it evaluates the expression, ends the function immediately (no line after it in that call runs), and hands the resulting object back to the caller. Nothing is copied: the caller receives the very object the function built or was given (2.4). If the function reaches the end of its body without a return, or runs a bare return, the result is None.

return_ends.py
def first_long_word(words, n):
    for w in words:
        if len(w) > n:
            return w            # ends the whole function, not just the loop
    return None                 # explicit: nothing matched

print(first_long_word(["rag", "retrieval", "embedding"], 5))
print(first_long_word(["rag"], 5))

def no_return():
    x = 1 + 1                   # computed, then thrown away

print(no_return())
Output
retrieval
None
None

A function returns exactly one object. return a, b builds one tuple, and the caller can unpack it into names. That is convenient for two or three values, and it is also where the most common return bug shows up: a branch that forgets to return, so some inputs silently get None.

missing_return.py
def label(score):
    if score > 0.6:
        return "positive"
    elif score < 0.4:
        return "negative"
    # no return here: scores from 0.4 to 0.6 fall off the end

print(label(0.9), label(0.1), label(0.5))

def bounds(xs):
    return min(xs), max(xs)     # one tuple
lo, hi = bounds([4, 1, 9])
print(bounds([4, 1, 9]), lo, hi)
Output
positive negative None
(1, 9) 1 9

Two habits prevent the missing-return bug. Make every path end in an explicit return, writing the last case as the plain fall-through (return "neutral") rather than another elif. And use guard clauses: handle the special cases first with an early return or raise, so the main logic is not buried in nested ifs.

guard_clauses.py
def safe_ratio(hits, total):
    if total < 0 or hits < 0:
        raise ValueError("counts must be non-negative")
    if total == 0:
        return 0.0              # guard clause: special case handled first
    return hits / total         # the main case, not nested

print(safe_ratio(3, 4), safe_ratio(0, 0))
Output
0.75 0.0
!
print is not return

In a notebook, a function that prints its result looks exactly like one that returns it, because both show the value under the cell. But only a returned value can be stored, compared, tested or passed on. total = report(rows) gives None if report only printed. Library functions return; printing is for the outermost layer that talks to a person.

•
Choosing what to return

Return a tuple for two or three closely related values (lo, hi = bounds(xs)). Beyond that, callers have to remember positions, so return a dict or, better, a dataclass or NamedTuple with named fields (Module 11). And return the same kind of thing from every path: a function that returns a list in one branch and None in another forces every caller to check (problem 8).

4Docstrings, type hints and signatures

The first string in a function body is its docstring: Python stores it as __doc__, and help(f) and every editor show it. Type hints (query: str, -> list) are stored in __annotations__. Python itself does not check them at run time; they are information for people, editors, type checkers (Module 11) and frameworks.

hints_not_enforced.py
def double(x: int) -> int:
    "Return twice x."
    return x * 2

print(double.__doc__, double.__annotations__)
print(double(21), double("ab"))    # the hint says int, but nothing stops a str
Output
Return twice x. {'x': <class 'int'>, 'return': <class 'int'>}
42 abab

inspect.signature(f) turns a function's parameters into objects you can examine: each parameter's name, its kind (positional, keyword-only and so on), its default and its annotation.

signature.py
import inspect

def search(query: str, k: int = 5, *, rerank: bool = False):
    "Search the index and return the top k chunks."
    return []

sig = inspect.signature(search)
print(sig)
for name, param in sig.parameters.items():
    print(f"{name:7} {param.kind.name:22} default={param.default!r:8} type={param.annotation.__name__}")
Output
(query: str, k: int = 5, *, rerank: bool = False)
query   POSITIONAL_OR_KEYWORD  default=<class 'inspect._empty'> type=str
k       POSITIONAL_OR_KEYWORD  default=5        type=int
rerank  KEYWORD_ONLY           default=False    type=bool

This is exactly how FastAPI works out that k is an optional query parameter with default 5 that must be an int: it reads the signature of your endpoint function when you register it. Agent frameworks do the same to turn a Python function into a tool description for an LLM, using the docstring as the tool's description. Because functions are objects that describe themselves, a framework can call your code correctly without you writing any glue (problem 15).

5Recursion, step by step

A function can call itself. Recursion fits data that is nested to an unknown depth, such as JSON from an API or a document tree: handle one level, call the same function on each child, and stop at a base case that needs no further call. You already wrote two recursive functions in 2.3 (freeze and with_override).

What happens on each call: Python creates a new frame (a private set of local variables) for that call and puts it on top of the call stack. The caller's frame waits underneath, paused at the call. When the inner call returns, its frame is removed and the caller continues with the result. Printing the depth makes the stack visible:

recursion_trace.py
def depth(obj, level=0):
    pad = "  " * level
    if isinstance(obj, dict):
        print(f"{pad}dict with {len(obj)} keys")
        result = 1 + max((depth(v, level + 1) for v in obj.values()), default=0)
    elif isinstance(obj, list):
        print(f"{pad}list with {len(obj)} items")
        result = 1 + max((depth(v, level + 1) for v in obj), default=0)
    else:
        print(f"{pad}value {obj!r}")
        result = 0              # base case: a plain value needs no further call
    return result

print("depth =", depth({"a": {"b": [1, 2]}, "c": 3}))
Output
dict with 2 keys
  dict with 1 keys
    list with 2 items
      value 1
      value 2
  value 3
depth = 3

Each indented line is one frame deeper on the stack. The plain values are the base cases; every dict or list waits for its children and then adds 1. The default=0 matters: an empty dict or list has no children, and max of nothing would otherwise raise (problem 6).

Two limits come with recursion in Python. Each frame costs memory and time, and CPython caps the depth (1,000 frames by default; sys.getrecursionlimit() shows the value). Python also does not optimise tail calls, so even a recursion whose last action is the recursive call still uses one frame per level. A missing or unreachable base case therefore ends in a RecursionError rather than running forever:

recursion_limit.py
def countdown(n):
    if n == 0:                  # base case, but a negative start never reaches it
        return "done"
    return countdown(n - 1)

print(countdown(5))
try:
    countdown(-1)
except RecursionError as e:
    print("RecursionError:", e)
Output
done
RecursionError: maximum recursion depth exceeded

For very deep data, or for simple repetition, write a loop. A tree can be walked without recursion by keeping your own stack in a list, which has no depth limit:

explicit_stack.py
def max_depth(obj):
    best = 0
    stack = [(obj, 0)]          # (value, depth so far): our own call stack
    while stack:
        value, d = stack.pop()
        if isinstance(value, dict):
            children = value.values()
        elif isinstance(value, list):
            children = value
        else:
            best = max(best, d)
            continue
        if not children:
            best = max(best, d + 1)
        for child in children:
            stack.append((child, d + 1))
    return best

print(max_depth({"a": {"b": [1, 2]}, "c": 3}), max_depth([]), max_depth(42))
Output
3 1 0
≈
SQL / Power BI

A recursive Python function over a tree is the same idea as a SQL recursive CTE walking an org chart or a bill of materials: an anchor query (the base case) plus a recursive part that joins one level deeper, with a depth limit (MAXRECURSION in SQL Server) to stop runaway recursion.

def parse_label(text):
    label_part, conf_part = text.split(",")
    label = label_part.split(":")[1].strip().lower()

Write chunk_words(text, size, overlap=0) that splits text into chunks of size words, where each chunk starts size - overlap words after the previous one, and the last chunk may be shorter. Use guard clauses: raise ValueError if size < 1, if overlap < 0, or if overlap >= size. Empty text gives [].

SolutionShow the solution and why
solution.py
def chunk_words(text, size, overlap=0):
    if size < 1:
        raise ValueError("size must be at least 1")
    if overlap < 0 or overlap >= size:
        raise ValueError("overlap must be between 0 and size - 1")
    words = text.split()
    step = size - overlap
    chunks = []
    for start in range(0, len(words), step):
        chunks.append(" ".join(words[start:start + size]))
        if start + size >= len(words):
            break
    return chunks

The guard clauses turn settings that would loop forever (overlap == size means a step of 0, and range rejects a step of 0 with its own unclear error) or make no sense into clear errors at the top, before any work. The break is the subtle part: without it, the overlap example would produce a fourth chunk "g" that is entirely overlap with the previous one, which wastes an embedding call and adds a duplicate result to retrieval. Real chunkers (for example in LangChain or LlamaIndex) count tokens rather than words, but follow the same structure.

6. The depth of an empty object

depth measures how deeply nested a JSON value is: plain values have depth 0, and each dict or list adds one. It crashes on empty dicts and lists. Fix it without special-casing every caller.

TestsThe 5 checks Run tests uses
assert depth(5) == 0
assert depth({"a": 1}) == 1

assert depth({"a": [], "b": {"c": {}}}) == 3
HintOpen a hint

What does max() do with an empty sequence? Check its default parameter.

SolutionShow the solution and why
solution.py
def depth(obj):
    if isinstance(obj, (dict, list)):
        children = obj.values() if isinstance(obj, dict) else obj
        return 1 + max((depth(c) for c in children), default=0)
    return 0

max() of an empty iterable raises ValueError: max() iterable argument is empty, and a recursive function meets empty containers constantly, at every leaf of real JSON. default=0 says "an empty container has no deeper children". Recursive functions need their base cases to cover every kind of leaf, and empty containers are the one people forget.

SolutionShow the solution and why
solution.py
def validate_scores(scores):
    if not scores:
        raise ValueError("no scores")
    for s in scores:
        if not 0 <= s <= 1:
            raise ValueError(f"bad score {s}")


def summarise(scores):
    return sum(scores) / len(scores), max(scores), len(scores)


def report(name, scores):
    validate_scores(scores)
    mean, best, n = summarise(scores)
    return f"{name}: mean {mean:.2f}, best {best:.2f}, n={n}"

Each small function now has one reason to change and can be tested and reused alone: summarise can feed a dashboard, validate_scores can guard other metrics. The loops became sum and max, and the range check became a chained comparison (1.1). Splitting is worth it when the pieces have names that explain them; a function you can only name step2 is usually not a real job.

solution.py
def build_messages(question, *, system=None, history=(), context=None):
    messages = []
    if system is not None:
        messages.append({"role": "system", "content": system})
    messages.extend(history)
    content = f"Context:\n{context}\n\nQuestion: {question}" if context is not None else question
    messages.append({"role": "user", "content": content})
    return messages

Keyword-only options make calls readable (build_messages(q, context=c)) and protect against mistakes: with three optional parameters, a positional call like build_messages(q, "Be brief.") would silently put a system prompt where history belongs. history=() is an immutable default (2.4), and extend copies the history's messages into a new list, so the caller's list is never changed. Checking is not None (not truthiness) means an empty-string system prompt is still sent, which is the caller's choice to make.

HintOpen a hint

One comprehension: min(cap, base * factor ** i) for each i in range(attempts).

SolutionShow the solution and why
solution.py
def backoff_delays(attempts, *, base=0.5, factor=2.0, cap=8.0):
    return [min(cap, base * factor ** i) for i in range(attempts)]

Waiting longer after each failure stops your client from hammering an API that is already overloaded, and the cap keeps the wait from growing without limit. The tuning knobs are keyword-only with sensible defaults, so the usual call is just backoff_delays(5). Real clients also add random jitter (random.uniform(0, delay)) so that many clients that failed at the same moment do not all retry at the same moment; libraries such as tenacity and the OpenAI and Anthropic SDKs do this for you.

12. Flatten nested JSON into columns

LLM extraction returns nested JSON, but the report needs flat columns. Write flatten(obj, prefix="") that returns a dict from dotted paths to plain values: dict keys join with ., list positions become numbers. Empty dicts and lists produce no columns.

Hint 1Open a hint

Recursive case: for each key (or index) and child, call flatten(child, new_prefix) and merge the result.

Hint 2Open a hint

Build new_prefix as f"{prefix}.{key}" when prefix is not empty, otherwise just str(key).

SolutionShow the solution and why
solution.py
def flatten(obj, prefix=""):
    if isinstance(obj, dict):
        pairs = obj.items()
    elif isinstance(obj, list):
        pairs = enumerate(obj)
    else:
        return {prefix: obj}
    out = {}
    for key, child in pairs:
        path = f"{prefix}.{key}" if prefix else str(key)
        out.update(flatten(child, path))
    return out

The function has one base case (a plain value becomes one column) and one recursive case that treats dicts and lists the same way by turning both into (key, child) pairs. That unification is what keeps it short. The default prefix="" is immutable and safe (2.4), and empty containers produce no pairs, so no columns. pandas has this built in as pd.json_normalize, which flattens dicts but keeps lists as values by default; knowing how to write it yourself helps when you need a different rule.

13. Read the code: an evaluation that stops early

This scores an LLM's answers against gold answers for an evaluation run. It reports 100% accuracy on sets the model obviously gets wrong, and crashes on an empty set. Read the whole function, find both bugs, and fix them so it returns {"accuracy": ..., "errors": [...]} for any input.

TestsThe 3 checks Run tests uses

assert r == {"accuracy": 2 / 3, "errors": [1]}
assert evaluate(["x"], ["y"]) == {"accuracy": 0.0, "errors": [0]}

Hint 1Open a hint

Look at the indentation of the return. How many items does the loop really check?

Hint 2Open a hint

When the lists are empty, the loop body never runs. What does the function return then, and what would the division do?

SolutionShow the solution and why
solution.py
def normalise(answer):
    return " ".join(answer.lower().split())


def evaluate(predictions, gold):
    if len(predictions) != len(gold):
        raise ValueError("predictions and gold differ in length")
    if not gold:
        return {"accuracy": 0.0, "errors": []}
    correct = 0
    errors = []
    for i, (pred, ref) in enumerate(zip(predictions, gold)):
        if normalise(pred) == normalise(ref):
            correct += 1
        else:
            errors.append(i)
    return {"accuracy": correct / len(gold), "errors": errors}

The return is indented inside the loop, so the function returns after the first item: if that one is correct, the "accuracy" is 1 / len(gold) at best, and here the first answer matched, so the reported number depended only on item 0. With an empty set the loop never runs, the function falls off the end and returns None; after moving the return out, it would divide by zero instead. The guard clause handles the empty case explicitly. An evaluation that looks better than reality is the most dangerous kind of bug in ML work, because nobody goes looking for it.

15. Call a tool with only the arguments it accepts

LLMs often add extra fields when they call a tool. Write call_with(fn, data) that calls fn using only the keys of the dict data that match fn's parameter names, passed as keyword arguments, and ignores the rest. If fn accepts **kwargs, pass everything. Missing required arguments must still raise TypeError, the normal Python way.

Hint 1Open a hint

inspect.signature(fn).parameters maps names to parameter objects. A parameter's .kind tells you whether it is VAR_KEYWORD (**kwargs).

Hint 2Open a hint

Keep a key if its name is in the parameters. Then call fn(**kept) and let Python raise for anything missing.

SolutionShow the solution and why
solution.py
import inspect

def call_with(fn, data):
    params = inspect.signature(fn).parameters
    if any(p.kind is inspect.Parameter.VAR_KEYWORD for p in params.values()):
        return fn(**data)
    kept = {k: v for k, v in data.items() if k in params}
    return fn(**kept)

The signature is read from the function object itself, so the same call_with works for any tool without a list of allowed fields. Filtering extra keys tolerates harmless LLM noise (a "reason" field), while a missing required argument still fails loudly, because the call itself is a normal Python call. This is a simplified version of what FastAPI does for request parameters and what agent frameworks do for tools. Real versions also validate types from the annotations (Pydantic), and should log dropped keys, since a dropped key can also be a misspelled real argument.

Interview

16. What does a function return without a return statement, and how does that cause bugs?

SolutionModel answer

It returns None, and so does a bare return. Bugs come from paths that forget to return: an if/elif chain without a final return, an expression written where a return was meant, or a return indented inside a loop so it exits early. The None then travels far from its cause and fails later, as TypeError: cannot unpack non-iterable NoneType object or a silently wrong metric. Prevent it by ending every function with an explicit return for the default case, using guard clauses, returning the same kind of value on every path, and letting a type checker (mypy, pyright) flag Optional results that are not checked (Module 11).

Interview

17. Recursion or a loop in Python: how do you choose?

SolutionModel answer

Recursion is natural for nested or tree-shaped data of moderate depth: JSON documents, file trees, parse trees, divide-and-conquer algorithms. But CPython limits recursion depth (1,000 by default), does not optimise tail calls, and every call has overhead, so deep recursion raises RecursionError and long recursions are slower than loops. Use a loop for linear repetition, and an explicit stack (a list you push and pop) to walk very deep trees iteratively. Mention that sys.setrecursionlimit exists but only moves the problem, and that functools.cache makes recursive solutions with repeated subproblems fast (dynamic programming, Module 16).

Interview

18. How does a framework like FastAPI know which query parameters your endpoint takes?

SolutionModel answer

Functions are objects that describe themselves. When you register an endpoint, FastAPI calls inspect.signature on your function and reads each parameter's name, its default, and its type annotation. A parameter with a default becomes an optional query parameter, one without becomes required, and the annotation (for example int or a Pydantic model) tells it how to parse and validate the incoming value, which also generates the OpenAPI docs. Nothing runs your function until a request arrives. Mention that the same idea powers agent tools: the signature and docstring of a Python function become the JSON schema the LLM sees, which is why docstrings and type hints matter in GenAI code.

Recap

  • def runs: it builds a function object and binds the name. Old references keep the old function.
  • Arguments fill parameters by position, then by name, then from defaults. The four TypeError messages (missing, too many, multiple values, unexpected) tell you exactly which rule broke.
  • Every path should end in an explicit return. Use guard clauses, and return the same kind of value from every path.
  • Function objects carry their docstring, defaults and signature. FastAPI and agent frameworks read them to call your code.
  • Recursion suits nested data of moderate depth: cover every base case (including empty containers), and use a loop for deep or long repetition.
