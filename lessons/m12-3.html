12.3 logging

When a service misbehaves at 3 a.m., its logs are the only witness. The logging module from the ground up: loggers and their hierarchy, levels, handlers and formatters, lazy formatting, exceptions with tracebacks, configuration for applications versus libraries, filters for redaction and request context, and structured JSON logs. Applied to LLM calls, retrieval libraries and ETL jobs.

1Why logging instead of print

print writes text to standard output and that is all. A real program needs more from its diagnostic messages: a severity so routine chatter can be hidden and errors cannot, a source (which module said it), a destination that may be a console, a file, or a log service, a format with timestamps and context, and the ability to change all of that without editing the code that emits the messages, because the same library runs inside a notebook, a test and a production server. The logging module separates those concerns: code calls a logger, and the application decides, once, where records go and which ones are kept.

The five standard levels are numbers, so they compare: DEBUG (10) for detail useful while diagnosing, INFO (20) for normal milestones (a job started, a model loaded), WARNING (30) for something unexpected that was handled (a retry, a fallback), ERROR (40) for an operation that failed, and CRITICAL (50) for a failure of the whole program. A logger or handler set to a level drops everything below it.

2Loggers, the hierarchy and levels

Every module gets its own logger with log = logging.getLogger(__name__). __name__ is the module's dotted import name (myapp.retrieval.search), so loggers form a tree that mirrors the package, and getLogger returns the same object for the same name, wherever it is called. A record created on a logger is checked against that logger's effective level (its own level, or if it has none, NOTSET, the nearest ancestor's), then passed to the logger's handlers and, because propagate is True by default, to the handlers of every ancestor up to the root logger. That is why an application usually attaches handlers only to the root (or to its top package logger), and every module's messages arrive there.

Call the level methods with a format string and separate arguments: log.info("loaded %d docs from %s", n, path). The message is only formatted if a handler will actually emit it, and the arguments are kept in the record, which structured logging uses. An f-string, log.debug(f"state {state}"), is formatted before the call, even when debug logging is off. Note that arguments are still evaluated: log.debug("%s", expensive()) runs expensive() every time, so guard truly expensive work with if log.isEnabledFor(logging.DEBUG): (problem 8).

hierarchy.py
import io, logging

stream = io.StringIO()
handler = logging.StreamHandler(stream)
handler.setFormatter(logging.Formatter("%(levelname)-7s %(name)s: %(message)s"))
app = logging.getLogger("shop")
app.addHandler(handler)
app.setLevel(logging.INFO)
app.propagate = False

db = logging.getLogger("shop.db")
print(db.parent.name, db.level, db.getEffectiveLevel(), logging.getLogger("shop.db") is db)
db.debug("SELECT * FROM orders")
db.info("loaded %d orders in %.1f ms", 120, 4.25)
db.warning("slow query: %s", "orders by customer")
app.error("checkout failed for order %s", "A-17")
print(stream.getvalue(), end="")

shop.db has no level of its own (0, NOTSET), so it inherits INFO from shop; the debug message is dropped, the others travel up to the handler on shop, and the format shows which logger produced each one. The examples here attach handlers to their own loggers and set propagate = False, so they do not depend on the root logger; an application would normally configure the root instead.

3Handlers, formatters and configuration

A handler delivers records: StreamHandler (standard error by default, or any file-like stream), FileHandler, RotatingFileHandler and TimedRotatingFileHandler (start a new file at a size or time and keep a fixed number of old ones), logging.handlers.QueueHandler for handing records to a background thread, and handlers for syslog, HTTP and cloud log services. Each handler has its own level, so one logger can send everything to a file and only errors to the console. A formatter turns a record into text with %-style fields: %(asctime)s, %(levelname)s, %(name)s, %(message)s, %(module)s, %(funcName)s, %(lineno)d, %(process)d, %(threadName)s.

Applications configure logging once, at start-up; libraries never do. In a script, logging.basicConfig(level=logging.INFO, format=...) adds one handler to the root logger; larger applications use logging.config.dictConfig(config), a dict (often loaded from a file) describing formatters, handlers and logger levels (problem 14), including quieting chatty dependencies such as logging.getLogger("httpx").setLevel(logging.WARNING). A library only creates loggers and, by convention, attaches a logging.NullHandler() to its top-level logger, so it stays silent unless the application asks to see its messages. A library calling logging.basicConfig, or the module-level shortcuts logging.info(...) (which log to the root and configure it if it has no handlers), takes that decision away from the application (problem 10).

import io, logging

stream = io.StringIO()

alerts.setLevel(logging.ERROR)
alerts.setFormatter(logging.Formatter("ALERT %(message)s"))

4Logging exceptions

Inside an except block, log.exception("message") logs at ERROR level with the traceback, which is what makes the record useful later; log.error("failed: %s", e) keeps only the exception's message and loses where it happened (problem 3). Any level method accepts exc_info=True to attach the current exception (log.warning("retrying", exc_info=True)), and stack_info=True adds the current call stack even without an exception. Log an exception once, where it is handled; logging and re-raising at every layer prints the same traceback five times.

5Extra fields, filters and request context

Every record carries standard attributes, and extra={"request_id": "r-42", "latency_ms": 812} adds your own, available to formatters as %(request_id)s and to handlers as record.request_id. A filter, either an object with a filter(record) method or a plain function, is attached to a logger or a handler and returns False to drop a record; it may also modify the record, which is how you add context to every message or redact secrets (problems 7 and 11). Filters on a handler see every record that reaches it, including those propagated from child loggers; filters on a logger only see records created on that logger.

In a web service, the context you need on every line is the request: its id, the user or tenant, the model. Passing it to every call is impractical, so it is stored in a contextvars.ContextVar, which behaves like a global variable but has a separate value per request, even when requests interleave in threads or asyncio tasks (14.4), and a filter copies it onto each record.

context.py
import io, logging
from contextvars import ContextVar

request_id = ContextVar("request_id", default="-")

def add_request_id(record):
    record.request_id = request_id.get()
    return True

stream = io.StringIO()
h = logging.StreamHandler(stream)
h.addFilter(add_request_id)
h.setFormatter(logging.Formatter("%(request_id)s %(levelname)s %(message)s"))
log = logging.getLogger("api")
log.handlers[:] = [h]
log.setLevel(logging.INFO)
log.propagate = False

log.info("server started")
token = request_id.set("r-7")
log.info("retrieved %d chunks", 5, extra={"latency_ms": 41})
request_id.reset(token)
log.info("idle")
print(stream.getvalue(), end="")

6Structured logs

Text logs are written for people; production logs are read by machines first. Log platforms (Elasticsearch and Kibana, Datadog, Grafana Loki, CloudWatch) work best with structured logs: one JSON object per line with consistent fields such as time, level, logger, message, request_id, model, latency_ms and tokens, so you can filter "all errors for tenant X with latency above 2 s" instead of grepping. In Python that is a formatter whose format(record) returns json.dumps of the fields you choose (problem 5); libraries such as structlog and python-json-logger provide one.

Two rules apply to every log line. Never log secrets (API keys, passwords, tokens) or more personal data than you need; full prompts and documents often contain both, so log ids, sizes and hashes instead of content by default, and redact patterns such as keys and e-mail addresses with a filter as a safety net. And log at boundaries: one line when a request or job starts and ends, one per external call (model, database, tool) with its latency and outcome, and one per handled failure. Logging inside tight loops slows the program and buries the lines that matter.

solution.py
import logging


def make_logger(name, stream, level="INFO"):
    log = logging.getLogger(name)
    log.handlers.clear()
    handler = logging.StreamHandler(stream)
    handler.setFormatter(logging.Formatter("%(levelname)s %(name)s: %(message)s"))
    log.addHandler(handler)
    log.setLevel(level)
    log.propagate = False
    return log

Loggers are process-wide singletons per name, so configuration done inside a function accumulates: a factory that only calls addHandler gives every message twice after the second call, three times after the third, the classic "duplicate log lines" bug in notebooks, where cells are re-run. Clearing the handlers makes the function idempotent. propagate = False stops the records from also reaching the root logger's handlers. In an application this configuration belongs in one start-up function; a factory like this is handy for scripts and tests.

solution.py
import json, logging


class JsonFormatter(logging.Formatter):
    def __init__(self, fields=()):
        super().__init__()
        self.fields = tuple(fields)

    def format(self, record):
        data = {"level": record.levelname, "logger": record.name, "message": record.getMessage()}
        for name in self.fields:
            if hasattr(record, name):
                data[name] = getattr(record, name)
        if record.exc_info:
            data["exc"] = self.formatException(record.exc_info)
        return json.dumps(data, default=str, ensure_ascii=False)

A formatter is the single place where a record becomes text, so switching an application to structured logs is one class, with no change to the code that logs. getMessage() merges the arguments into the message; extra= values are plain attributes of the record, included only when present, so the schema stays stable. The traceback, which a text formatter would print over several lines, becomes one escaped string field, keeping the one-record-per-line guarantee that log shippers rely on. default=str makes sure a strange value never breaks logging, which must not crash the program it is observing. A real formatter would also add time from record.created.

import logging

def setup(stream):
    handler = logging.StreamHandler(stream)
    handler.setFormatter(logging.Formatter("%(name)s %(message)s"))

solution.py
import logging, re

_PATTERNS = [
    re.compile(r"sk-[A-Za-z0-9_-]{8,}"),
    re.compile(r"[\w.+-]+@[\w-]+(\.[\w-]+)+"),
]


class RedactFilter(logging.Filter):
    def filter(self, record):
        message = record.getMessage()
        for pattern in _PATTERNS:
            message = pattern.sub("[REDACTED]", message)
        record.msg = message
        record.args = None
        return True

Secrets usually arrive through the arguments, not the format string, so redacting record.msg alone would miss the key; formatting first with getMessage() and then redacting covers both. Storing the result with args = None stops the message from being formatted a second time, which matters because %% has already been turned into % and a stray % would break a second formatting pass. Attached to the handler, the filter sees records propagated from every child logger; on the w7 logger it would only see records created there. Redaction is a safety net, not a licence: the first defence is not passing secrets to log calls at all.

import logging
from contextvars import ContextVar

request_id = ContextVar("request_id", default="-")


class ContextFilter(logging.Filter):
    def filter(self, record):
        record.request_id = request_id.get()
        return True


def handle(rid, fn, *args):
    token = request_id.set(rid)
    try:
        return fn(*args)
    finally:
        request_id.reset(token)

SolutionShow the solution and why
solution.py
import functools, logging, time


def log_llm_calls(logger, model, clock=time.perf_counter):
    def decorator(fn):
        @functools.wraps(fn)
        def wrapper(prompt, **kwargs):
            start = clock()
            try:
                result = fn(prompt, **kwargs)
            except Exception:
                fields = {"model": model, "latency_ms": round((clock() - start) * 1000), "prompt_chars": len(prompt)}
                logger.exception("llm_call failed", extra=fields)
                raise
            fields = {"model": model, "latency_ms": round((clock() - start) * 1000), "prompt_chars": len(prompt)}
            logger.info("llm_call", extra=fields)
            return result
        return wrapper
    return decorator

Every external call should produce one record with its outcome and latency, and a decorator (8.2) adds that to any client function without touching its code. The message is a fixed event name, llm_call, and the variable data travels in extra fields, which is what structured logs need: a dashboard can then group by model and chart latency_ms without parsing text. The clock is injectable so the test is deterministic, and the failure path logs the traceback once and re-raises, so the caller can still retry or handle it (7.3). The prompt's length is logged, not its content, which may contain personal data.

solution.py
import json, logging, logging.config, sys


class JsonFormatter(logging.Formatter):
    def format(self, record):
        return json.dumps({"level": record.levelname, "logger": record.name, "message": record.getMessage()})


NOISY = ("httpx", "urllib3", "openai")


def configure_logging(level="INFO", json_format=False, stream=None):
    config = {
        "version": 1,
        "disable_existing_loggers": False,
        "formatters": {
            "plain": {"format": "%(levelname)s %(name)s: %(message)s"},
            "json": {"()": JsonFormatter},
        },
        "handlers": {
            "main": {
                "class": "logging.StreamHandler",
                "formatter": "json" if json_format else "plain",
                "stream": stream if stream is not None else sys.stderr,
            },
        },
        "root": {"level": level, "handlers": ["main"]},
        "loggers": {name: {"level": "WARNING"} for name in NOISY},
    }
    logging.config.dictConfig(config)

dictConfig describes the whole logging setup as data, which is why real applications load it from a YAML or TOML file and adjust it per environment. It replaces the root's handlers each time, so the function is idempotent. disable_existing_loggers: False is essential: the default True silently disables every logger created before the call, typically all module-level loggers of already-imported modules, and their messages vanish. An invalid level fails loudly at start-up with ValueError, which is where configuration errors should surface.

import logging


def get_logger(stream):
    log = logging.getLogger("f15.chat")
    if not log.handlers:
        handler = logging.StreamHandler(stream)
        handler.setFormatter(logging.Formatter("%(levelname)s %(message)s"))

        log.setLevel(logging.INFO)

    return log

    log.info("calling model with key ...%s", api_key[-4:])
    log.debug("question: %s", question)
    try:
        return client(question, api_key)
    except Exception:
        log.exception("model call failed")
        return None

Interview

17. Why use logging instead of print, and what would you log in an LLM-backed service?

SolutionModel answer

logging gives every message a severity, a source (the logger name), a timestamp and context, and lets the application decide at run time where messages go and which levels are kept, without changing the code that emits them; libraries can log without forcing output on their users. print has none of that and mixes diagnostics with real output. In an LLM service I would log, at boundaries: request start and end with a request id, route, status and total latency; every model call with model name, latency, token counts, cost estimate, retries and finish reason; retrieval with the number of chunks and top scores; tool calls with name, outcome and latency; validation failures of structured output with error types; and every handled exception with its traceback, once. I would not log raw prompts, documents or answers by default (personal data, secrets, volume), only their ids, sizes or hashes, with content sampling behind an explicit, access-controlled switch. Logs go out as structured JSON with a request id on every line.

Interview

18. Should a library configure logging? What should it do instead?

SolutionModel answer

No. Configuration (handlers, formats, levels, destinations) belongs to the application, because only it knows whether it runs in a notebook, a test, a CLI or a server with a log shipper. A library that calls logging.basicConfig, adds handlers to the root, or prints, overrides or duplicates the application's choices, and module-level logging.info(...) calls can configure the root logger implicitly. A library should create loggers with logging.getLogger(__name__), so its messages are namespaced under the package and can be tuned with one line by the application; log with lazy arguments at sensible levels (DEBUG for detail, WARNING for handled problems, never ERROR for something it re-raises); attach a logging.NullHandler() to its top-level logger so nothing is printed when the application has not configured logging; and never log secrets passed to it.

Interview

19. How do you debug one failing request in a busy, concurrent service from its logs?

SolutionModel answer

Without correlation, lines from hundreds of interleaved requests are useless, so every request gets an id at the edge (or reuses an incoming X-Request-ID or trace id), stored in a ContextVar and attached to every record by a filter, so it survives threads and asyncio tasks. The id is returned to the client and passed to downstream services in headers, so one search in the log platform shows the whole story across services. Logs are structured JSON with consistent fields (request id, user or tenant, model, latency, error type), so you can filter instead of grep. Each boundary logs one line with its outcome and latency, and each handled exception logs its traceback once. For latency questions, logs are complemented by tracing (OpenTelemetry spans for each step, model call and tool call), and by metrics for rates and percentiles, since logs are expensive to aggregate. Finally, sample verbose debug logs, keep retention and access controls on logs that may contain personal data, and make log levels adjustable at run time so you can raise detail for one component while investigating.

Recap

  • Use logging.getLogger(__name__) per module; loggers form a dotted tree, inherit levels, and propagate records to ancestors' handlers.
  • Levels DEBUG < INFO < WARNING < ERROR < CRITICAL filter on loggers and handlers; pass arguments lazily, and guard expensive ones with isEnabledFor.
  • Applications configure once (basicConfig, dictConfig with disable_existing_loggers: False); libraries only add a NullHandler.
  • log.exception in except keeps the traceback; log each exception once, where it is handled.
  • Filters add context (request ids via ContextVar) and redact secrets; structured JSON logs with consistent fields serve machines and people.
