9.1 Classes and instances

A class bundles data with the functions that work on it. What happens step by step when you create an object and call a method, what self really is, where attributes live and how Python finds them, class attributes and the shared-mutable trap, bound methods, and when a class is the right tool. Applied to conversations, running statistics, token budgets and a small search index.

18 problems4 easy · 9 medium · 5 hard

1Why classes

You have used objects from the first lesson: a list holds items and has methods such as append and sort that work on those items; a string has split and upper. A class lets you define your own kind of object in the same way: some data (attributes) and the functions that work on that data (methods), kept together. The class is the blueprint; each object made from it is an instance, with its own data but the same methods.

Without classes, the same program is a dict plus loose functions that all take the dict as their first argument: add_message(conv, role, text), last_messages(conv, n). That works, and for small scripts it is fine. Classes become worth it when the data has rules that must always hold (a role must be valid, a budget must not go negative), when several functions share and change the same state, and when you want many independent objects of the same kind. The class puts the rules in one place, and code that uses it can only change the data through its methods.

first_class.py
class Conversation:
    def __init__(self, system_prompt):
        self.messages = [{"role": "system", "content": system_prompt}]

    def add(self, role, content):
        if role not in ("user", "assistant"):
            raise ValueError(f"bad role {role!r}")
        self.messages.append({"role": role, "content": content})

    def last(self, n):
        return self.messages[-n:]

chat.add("user", "Refund?")
chat.add("assistant", "5 days.")
print(len(chat.messages), chat.last(1))
other = Conversation("Be formal.")

A class is like a table definition and its instances are rows: the definition says which columns exist (attributes) and the rules they follow (constraints), and every row has its own values. Methods are like stored procedures bound to the table: the only sanctioned way to change the data, so the rules are always applied.

2What happens when you create an object and call a method

The class statement runs once, like def: it executes the class body and creates a class object (here Conversation) that holds the functions defined inside it. Calling the class, Conversation("Be brief."), then does three things in order. First Python creates a new, empty instance. Then it calls __init__ with that instance as the first argument, followed by the arguments you passed: Conversation.__init__(new_object, "Be brief."). __init__ sets up the instance's attributes and must return None. Finally the call returns the new instance. __init__ is often called the constructor; strictly it is the initialiser, since the object already exists when it runs.

self is simply the name, by convention, of that first parameter: the instance the method is working on. When you call a method on an instance, chat.add("user", "Hi"), Python looks up add on the class and calls it with the instance inserted as the first argument: Conversation.add(chat, "user", "Hi"). That is the whole mechanism. Inside the method, self.messages means "the messages attribute of whichever instance this call is for", which is how one method serves every instance.

The TypeError at the end is what happens when the instance is missing: calling the function through the class without one leaves self unfilled. 3Where attributes live, and how Python finds them

Instance attributes are stored in a dict on each instance, obj.__dict__ (also available as vars(obj)). Assigning self.messages = [...] in __init__ adds the key "messages" to that dict. Methods are not stored on the instance; they live in the class's own namespace, Conversation.__dict__, shared by every instance. So each instance carries only its own data.

Reading obj.name follows a fixed lookup order: first the instance's __dict__, then the class (and then the class's base classes, 9.4). The first place that has the name wins; if none has it, Python raises AttributeError. Assigning obj.name = value is different: it always writes to the instance's dict, never to the class. That asymmetry explains most of the surprises with class attributes, below.

Python also lets you add attributes to an instance anywhere, m.anything = 1, even outside the class. That flexibility is useful occasionally, but it also means a typo such as self.mesages = [] silently creates a new attribute instead of raising an error. A good habit is to create every instance attribute in __init__, even if only as None, so a reader can see the complete state of the object in one place. (__slots__, 9.3, can enforce it.)

4Class attributes and the shared-mutable trap

A name assigned in the class body, outside any method, is a class attribute: one value stored on the class and shared by all instances. Class attributes are right for constants that belong to the type (VALID_ROLES, DEFAULT_MODEL) and for data that is genuinely shared (a count of instances created). Reading them through self works because of the lookup order; changing a shared value deliberately is done through the class, Counter.created += 1.

The trap is a mutable class attribute used as if it were per instance. history = [] in the class body creates one list, and self.history.append(x) does not assign anything, it reads self.history, which finds the class's list, and changes it in place. Every instance appends to the same list (2.2). Assignment would have created an instance attribute; mutation does not. The fix is to create mutable state in __init__, so each instance gets its own (problem 6).

shared_mutable.py
class Bad:
    history = []                          # ONE list, shared by every instance
    def record(self, x):
        self.history.append(x)            # reads the class list and mutates it

class Good:
    MAX = 3                               # an immutable class constant: fine to share
    def __init__(self):
        self.history = []                 # a new list per instance
    def record(self, x):
        self.history.append(x)
        del self.history[:-self.MAX]      # keep the last MAX items

a, b = Bad(), Bad()
a.record("a1"); b.record("b1")
print(a.history, b.history, a.history is Bad.history)

g, h = Good(), Good()
for i in range(5):
    g.record(i)
h.record("only")
print(g.history, h.history)
Output
['a1', 'b1'] ['a1', 'b1'] True
[2, 3, 4] ['only']

del self.history[:-self.MAX] deletes everything except the last MAX items, in place, keeping the same list. Notice self.MAX reads the class constant through the instance; a subclass could override MAX (9.4) and the method would follow. The same trap exists for default argument values (2.4): def __init__(self, tags=[]) shares one list between all instances created without tags (problem 9).

5Methods are functions, bound to an instance

A method is an ordinary function stored on the class. Accessing it through an instance, chat.add, produces a bound method: a small object that remembers both the function (__func__) and the instance (__self__), so calling it later inserts the instance automatically. You can store a bound method in a variable, pass it as a callback, or put it in a list, and it keeps working on its instance. That is why sorted(items, key=obj.score) or button.on_click(handler.save) style code works.

bound_methods.py
class Scorer:
    def __init__(self, keywords):
        self.keywords = set(keywords)

    def score(self, text):
        return len(self.keywords & set(text.lower().split()))

refunds = Scorer(["refund", "money", "return"])
s = refunds.score                          # a bound method: remembers refunds
docs = ["How to reset a password", "Refund your money", "Return and refund policy"]
print(sorted(docs, key=s, reverse=True))
print(s.__self__ is refunds, s.__func__ is Scorer.score, s("refund refund"))
print([refunds.score(d) for d in docs] == list(map(refunds.score, docs)))
Output
['Refund your money', 'Return and refund policy', 'How to reset a password']
True True 1
True

Methods call each other through self (self.validate(x) inside add), which also means a subclass can replace one of them and the others will use the new version (9.4). A method that does not use self at all is a hint that it might be a plain function, or a staticmethod (9.6).

6When a class is the right tool

Use a class when you have state plus rules: data that must stay consistent and several operations that change it (a conversation history with a token limit, a cache with statistics, a rate limiter, a client holding a connection and settings). Use a class when you need many independent objects of the same kind with the same behaviour. And use one when a library expects it: PyTorch models are classes with a forward method, scikit-learn estimators are classes with fit and predict, and Pydantic models are classes (11.4).

Do not use a class just to group functions that share no state: a module does that. Do not write a class with only __init__ and one method: that is a function, or a closure (3.4), in disguise. And for objects that are mainly data with little behaviour (a record, a config, an API response), a dataclass (11.3) writes __init__, __repr__ and __eq__ for you. The closures of 7.3 and 7.4 (the circuit breaker, the token bucket) are a good test: they are state plus operations, and as classes they become easier to read, inspect and extend (problem 14).

running_mean.py
class RunningMean:
    """Mean of a stream of numbers, without storing them."""

    def __init__(self):
        self.count = 0
        self.total = 0.0

    def update(self, x):
        self.count += 1
        self.total += x
        return self

    def mean(self):
        return self.total / self.count if self.count else 0.0

latency = RunningMean()
for ms in [120, 95, 300]:
    latency.update(ms)
print(round(latency.mean(), 2), latency.count, vars(latency))
print(RunningMean().update(1).update(3).mean())     # update returns self, so calls chain

solution.py
class Conversation:
    ROLES = ("user", "assistant")

    def __init__(self, system_prompt):
        self.messages = [{"role": "system", "content": system_prompt}]

    def add(self, role, content):
        if role not in self.ROLES:
            raise ValueError(f"role must be one of {self.ROLES}, got {role!r}")
        text = content.strip()
        if not text:
            raise ValueError("content must not be empty")
        self.messages.append({"role": role, "content": text})

    def turns(self):
        return len(self.messages) - 1

    def last(self, n):
        return self.messages[1:][-n:]

All rules live in add, so no message can get into the history without passing them; code that uses the class cannot forget a check. The valid roles are a class constant, shared and immutable. last returns a slice, a new list, so a caller clearing it cannot damage the conversation; returning self.messages itself would hand out the internal list (2.4), though the dicts inside are still shared, which 9.3 addresses. turns is computed rather than stored, so it can never get out of sync with the messages.

class Inventory:
    def __init__(self):
        self.items = {}

    def add(self, item, qty):
        self.items[item] = self.items.get(item, 0) + qty

    def total(self):
        return sum(self.items.values())

SolutionShow the solution and why
solution.py
class RunningStats:
    def __init__(self):
        self.count = 0
        self._mean = 0.0
        self._m2 = 0.0

    def update(self, x):
        self.count += 1
        delta = x - self._mean
        self._mean += delta / self.count
        self._m2 += delta * (x - self._mean)
        return self

    def mean(self):
        return self._mean

    def variance(self):
        return self._m2 / (self.count - 1) if self.count > 1 else 0.0

    def merge(self, other):
        out = RunningStats()
        out.count = self.count + other.count
        if out.count == 0:
            return out
        delta = other._mean - self._mean
        out._mean = self._mean + delta * other.count / out.count
        out._m2 = self._m2 + other._m2 + delta ** 2 * self.count * other.count / out.count
        return out

The state (count, _mean, _m2) and the rules for updating it belong together, and no caller can update one without the others. Welford's update avoids the cancellation error of the naive sum(x**2) - n * mean**2 formula, which loses precision badly for large values with small spread. merge lets you compute statistics per data shard or per worker and combine them exactly, which is how distributed feature statistics are computed. The leading underscore on _mean and _m2 is the convention for "internal, do not touch from outside" (9.3). Returning self from update allows chaining, as pandas and query builders do.

class LLMClient:
    DEFAULTS = {"temperature": 0.0}

    def __init__(self, model):
        self.model = model
        self.history = []
        self.settings = dict(self.DEFAULTS)

    def ask(self, prompt, **overrides):
        settings = {**self.settings, **overrides}
        self.history.append((self.model, prompt))
        return f"{self.model}: {prompt} @ {settings['temperature']}"

Two shared mutable class attributes caused two bugs. history was one list for every client, so small.history contained the large model's request too. settings.update(overrides) changed the shared dict, so after large asked with temperature=0.7, small silently used 0.7 as well, a bug that would make an evaluation run non-reproducible. Creating both in __init__ gives each client its own; keeping the defaults as an immutable-by-convention class constant (DEFAULTS) and copying them is the usual pattern. The per-request overrides now build a new dict and leave the client's settings alone (2.4).

solution.py
class BudgetExceeded(Exception):
    pass


class TokenBudget:
    def __init__(self, limit):
        self.limit = limit
        self._by_label = {}

    def spent(self):
        return sum(self._by_label.values())

    def remaining(self):
        return self.limit - self.spent()

    def spend(self, tokens, label):
        if isinstance(tokens, bool) or not isinstance(tokens, int) or tokens <= 0:
            raise ValueError(f"tokens must be a positive integer, got {tokens!r}")
        if tokens > self.remaining():
            raise BudgetExceeded(f"cannot spend {tokens} tokens on {label!r}: only {self.remaining()} left")
        self._by_label[label] = self._by_label.get(label, 0) + tokens

    def breakdown(self):
        return dict(self._by_label)

    def reset(self):
        self._by_label = {}

The class enforces its invariant, "spent never exceeds the limit", in the only method that changes the state, and it validates before modifying anything, so a rejected charge leaves the budget exactly as it was (the all-or-nothing rule of 7.3). The custom exception tells an agent loop precisely why it must stop, and its message includes both the request and what was left. breakdown returns a copy so callers cannot alter the records. Storing only the per-label totals is enough for this interface; keeping a list of every charge would allow an audit trail, at the cost of memory.

HintOpen a hint

The default list is created once, when def __init__ runs (2.4). Use None and copy what the caller passes.

SolutionShow the solution and why
solution.py
class Document:
    def __init__(self, text, tags=None):
        self.text = text
        self.tags = list(tags) if tags is not None else []

    def tag(self, label):
        if label not in self.tags:
            self.tags.append(label)
        return self

Methods are functions, so their defaults follow the rule of 2.4: tags=[] is evaluated once and every Document created without tags received the same list. The None default plus a new list inside __init__ fixes that. Copying a caller's list with list(tags) fixes a second, quieter aliasing bug: without it, c.tag("new") would also have changed the caller's shared list. An object should own its mutable state, which usually means copying mutable inputs at construction.

solution.py
class KeywordIndex:
    def __init__(self):
        self.docs = {}
        self.postings = {}

    @staticmethod
    def _words(text):
        return {w.strip(".,!?").lower() for w in text.split()} - {""}

    def add(self, doc_id, text):
        self.remove(doc_id)
        words = self._words(text)
        self.docs[doc_id] = words
        for w in words:
            self.postings.setdefault(w, set()).add(doc_id)

    def remove(self, doc_id):
        for w in self.docs.pop(doc_id, set()):
            ids = self.postings[w]
            ids.discard(doc_id)
            if not ids:
                del self.postings[w]

    def search(self, query):
        words = self._words(query)
        if not words:
            return []
        sets = sorted((self.postings.get(w, set()) for w in words), key=len)
        return sorted(set.intersection(*sets))

The two dicts must always agree, which is exactly the kind of invariant a class protects: only add and remove change them, and add reuses remove so a replaced document leaves no stale postings. Deleting empty posting sets keeps the index from growing with words that no longer appear anywhere. Search looks up only the query words and intersects their sets, starting from the smallest, so its cost depends on how common the words are, not on how many documents exist; that is the core of a search engine's inverted index (and of BM25 libraries). @staticmethod (9.6) marks _words as a helper that does not need the instance.

solution.py
class ChatSession:
    def __init__(self, system_prompt, max_tokens):
        self._system = {"role": "system", "content": system_prompt}
        self._turns = []
        self.max_tokens = max_tokens
        self.dropped = 0

    @staticmethod
    def _tokens(message):
        return len(message["content"].split())

    def total_tokens(self):
        return self._tokens(self._system) + sum(self._tokens(m) for m in self._turns)

    def add(self, role, content):
        message = {"role": role, "content": content}
        if self._tokens(self._system) + self._tokens(message) > self.max_tokens:
            raise ValueError("message does not fit in the budget even on its own")
        self._turns.append(message)
        while self.total_tokens() > self.max_tokens:
            self._turns.pop(0)
            self.dropped += 1

    def messages(self):
        return [dict(self._system)] + [dict(m) for m in self._turns]

Keeping the system message apart from the turns makes "never drop the system prompt" structural rather than a condition checked in a loop. The window slides by dropping the oldest turns until the total fits, the simplest context-management strategy (others summarise old turns instead). The oversize check happens before appending, so a rejected message leaves the session unchanged. messages() returns copies of the list and of each dict, because a shallow copy of the list alone would still let callers edit the stored messages (2.3); that is encapsulation in Python: not enforced by the language, but by never handing out your internal mutable objects. Real code counts tokens with the model's tokenizer, and pop(0) on a list is O(n), fine for chat-sized histories (a deque would make it O(1)).

solution.py
class ResultCache:
    def __init__(self, name, max_entries=100):
        self.name = name
        self.max_entries = max_entries
        self.hits = 0
        self.misses = 0
        self.entries = {}

    def get(self, key, compute):
        if key in self.entries:
            self.hits += 1
            return self.entries[key]
        self.misses += 1
        value = compute(key)
        if len(self.entries) >= self.max_entries:
            oldest = next(iter(self.entries))
            del self.entries[oldest]
        self.entries[key] = value
        return value

    def snapshot(self):
        return {k: list(v) for k, v in self.entries.items()}

Three bugs, each from this lesson. The class-level entries dict was shared, so the embedding cache answered "refund" with the search cache's result (and every cache evicted the others' entries); creating it in __init__ gives each instance its own. hits = self.hits + 1 assigned a local variable that vanished when the method returned, so the hit count stayed 0, a typo-level bug that a metrics dashboard would show as a 0% hit rate; attributes are only changed through self.. And snapshot() returned the internal dict, so a caller's clear() emptied the cache and the appended "junk" corrupted a cached value; returning a copy with copied values protects the cache. Note that get still returns the cached list itself, which a caller could mutate; caching immutable values (tuples) avoids that entirely.

solution.py
class TokenBucket:
    def __init__(self, rate, burst, clock):
        if rate <= 0 or burst < 1:
            raise ValueError("rate must be positive and burst at least 1")
        self.rate = rate
        self.burst = burst
        self.clock = clock
        self._tokens = float(burst)
        self._last = clock()
        self._granted = 0
        self._denied = 0

    def _refill(self):
        now = self.clock()
        self._tokens = min(self.burst, self._tokens + (now - self._last) * self.rate)
        self._last = now

    def available(self):
        self._refill()
        return self._tokens

    def acquire(self, cost=1):
        if cost > self.burst:
            raise ValueError(f"cost {cost} exceeds burst size {self.burst}")
        self._refill()
        if self._tokens >= cost:
            self._tokens -= cost
            self._granted += 1
            return 0.0
        self._denied += 1
        return (cost - self._tokens) / self.rate

    def stats(self):
        return {"granted": self._granted, "denied": self._denied}

The closure version of 7.4 kept its state in nonlocal variables, invisible from outside. As a class, the state is named and inspectable, the shared refill step is one private method used by both public ones, and new operations (available, stats) are added without restructuring anything: this is the usual point at which a closure should become a class. Each instance has its own tokens and counters, so one bucket per provider or per API key is just one object each. The injected clock keeps it testable, and validating rate and burst in __init__ means a bucket can never exist in an invalid state.

16. What is self in Python, and what exactly happens when you call a method?

SolutionModel answer

self is the conventional name for a method's first parameter, which receives the instance the method was called on. It is not a keyword, and Python never adds it implicitly inside the body: every attribute access goes through it explicitly. When you write obj.method(a), Python looks up method on obj's class (via the instance first, then the class and its bases), and because it is a function found on the class, the access produces a bound method that remembers obj; calling it runs Class.method(obj, a). So obj.method(a) and Class.method(obj, a) are the same call. This is why forgetting self in a definition gives "takes 1 positional argument but 2 were given", and why bound methods can be passed around as callbacks that keep working on their instance.

Interview

17. What is the difference between class attributes and instance attributes, and what is the classic bug?

SolutionModel answer

Instance attributes are stored in each object's __dict__, usually set in __init__ via self.x = ..., and are separate per object. Class attributes are assigned in the class body and stored once on the class, shared by all instances. Reading obj.x checks the instance first, then the class; assigning obj.x = ... always writes to the instance, shadowing the class attribute for that object only. The classic bug is a mutable class attribute, such as history = [], used as if it were per instance: self.history.append(...) reads the shared list and mutates it, so every instance appends to the same list. The same happens with a mutable default argument in __init__. Use class attributes for constants and genuinely shared data, and create mutable per-object state in __init__.

18. In ML and GenAI code, when would you use a class, a dataclass, or plain functions and dicts?

SolutionModel answer

Plain functions are best for stateless transformations (cleaning text, computing a metric, building a prompt), since they are the easiest to test and compose. Dicts suit loosely structured data that crosses boundaries, such as parsed JSON, but their keys are not checked, so typos become silent bugs. A dataclass (or a Pydantic model when validation is needed) fits structured data with little behaviour: configs, records, API responses, evaluation results; it gives an __init__, a readable repr, equality and type hints for free. A full class is worth it when there is state plus rules plus operations: a conversation buffer with a token limit, a cache with statistics, a rate limiter, a client holding a session and settings, or when a framework requires it (PyTorch nn.Module, scikit-learn estimators with fit/predict). Signs that a class is too much: it has only __init__ and one method, or no state. Signs that a dict should become a class: several functions taking the same dict and maintaining rules about its contents.

Recap

  • A class bundles data (attributes) with the functions that work on it (methods); each instance has its own data and shares the methods.
  • C(args) creates an empty instance, calls C.__init__(instance, args), and returns it. obj.m(x) is C.m(obj, x): self is that instance.
  • Instance attributes live in obj.__dict__. Reading looks in the instance, then the class; assigning always writes to the instance.
  • Class attributes are shared: fine for constants, a bug for mutable per-object state. Create lists and dicts in __init__, never as class or default values.
  • Methods accessed through an instance are bound methods; protect your state by validating in methods and returning copies, not internal objects.
