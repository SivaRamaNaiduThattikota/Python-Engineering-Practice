The with statement pairs setup with guaranteed cleanup. What with does step by step, writing context managers as classes with __enter__ and __exit__, deciding whether to suppress exceptions, the contextlib.contextmanager shortcut and its try/finally rule, several managers at once and their exit order, and reentrant managers. Applied to timers, temporary settings, atomic writes, transactions and tracing spans.

1Setup and guaranteed cleanup

Many operations come in pairs: open a file and close it; acquire a lock and release it; start a timer and stop it; begin a transaction and commit or roll back; change a setting and restore it. The second half must happen even if the work in between fails, or you leak file handles, deadlock other threads, leave half-written data or keep a temporary setting forever. Lesson 7.1 showed the tool for that, try/finally; a context manager packages the pair once so every user gets it right with one line: with open(path) as f:.

why_with.py
import os, tempfile

path = os.path.join(tempfile.mkdtemp(), "log.txt")

f = open(path, "w", encoding="utf-8")      # by hand: easy to forget the finally
try:
    f.write("first\n")
finally:
    f.close()

with open(path, "a", encoding="utf-8") as f:    # the same guarantee, built in
    f.write("second\n")
print(f.closed, open(path, encoding="utf-8").read().splitlines())

try:
    with open(path, encoding="utf-8") as f:
        raise ValueError("failed while reading")
except ValueError:
    print("file closed anyway:", f.closed)
Output
True ['first', 'second']
file closed anyway: True

2What with does, step by step

with EXPR as name: BODY runs these steps. Python evaluates EXPR, which gives the context manager object. It calls the manager's __enter__() method and binds the return value of __enter__ to name (not the manager itself, unless __enter__ returns self). It runs the body. Then, however the body ends (normally, with return, break or an exception), it calls __exit__(exc_type, exc_value, traceback). If the body finished without an exception, the three arguments are None. If an exception occurred, they describe it, and the return value of __exit__ decides what happens: a true value suppresses the exception, so execution continues after the with; anything else (including None, the default return) lets it propagate.

with_steps.py
class Show:
    def __init__(self, name, suppress=False):
        self.name, self.suppress = name, suppress

    def __enter__(self):
        print(f"  enter {self.name}")
        return f"resource:{self.name}"         # this is what `as` receives

    def __exit__(self, exc_type, exc, tb):
        print(f"  exit {self.name}, exception={exc_type.__name__ if exc_type else None}")
        return self.suppress

with Show("a") as r:
    print("  body got", r)

with Show("b", suppress=True):
    raise KeyError("swallowed")
print("after b: continued")

try:
    with Show("c"):
        raise KeyError("propagates")
except KeyError:
    print("after c: caught outside")
Output
  enter a
  body got resource:a
  exit a, exception=None
  enter b
  exit b, exception=KeyError
after b: continued
  enter c
  exit c, exception=KeyError
after c: caught outside

The as target is whatever __enter__ returns: for open, the file object (which is also the manager); for a lock, True; for a database transaction, often a connection or cursor. __exit__ is guaranteed to run once __enter__ has succeeded; if __enter__ itself raises, the body never runs and __exit__ is not called, which is why __enter__ should acquire the resource as its last step.

3Writing a context manager class

A class with __enter__ and __exit__ is a context manager. __enter__ does the setup and returns whatever the block should use, very often self, so the block can read results from the manager later. __exit__ does the cleanup and, in nearly all cases, returns False or nothing, so exceptions continue to the caller after the cleanup has happened. Returning True swallows every exception from the block, including bugs, so a manager should suppress only specific, intended exception types, as contextlib.suppress does (problem 3).

class_manager.py
import time

class Timer:
    def __init__(self, clock=time.perf_counter):
        self.clock = clock
        self.elapsed = None

    def __enter__(self):
        self.start = self.clock()
        return self

    def __exit__(self, exc_type, exc, tb):
        self.elapsed = self.clock() - self.start
        return False                        # never hide errors

ticks = iter([10.0, 10.25, 20.0, 21.5])
with Timer(lambda: next(ticks)) as t:
    pass
print(t.elapsed)
try:
    with Timer(lambda: next(ticks)) as t2:
        raise TimeoutError("model too slow")
except TimeoutError:
    print("timed the failure too:", t2.elapsed)
Output
0.25
timed the failure too: 1.5

The timer records the duration in __exit__, so slow failures are measured as well as successes, which matters for latency dashboards (8.3). Context managers that should react to errors can inspect exc_type in __exit__: a transaction commits when it is None and rolls back otherwise; a tracing span marks itself as failed; a test helper checks that an expected error occurred (pytest.raises is a context manager, 13.1).

4contextlib.contextmanager: a generator with one yield

Writing a class is verbose for simple pairs. The decorator contextlib.contextmanager turns a generator function with exactly one yield into a context manager. The code before yield is the setup (__enter__), the value yielded is what as receives, and the code after yield is the cleanup (__exit__). If the with body raises, the exception is re-raised inside the generator, at the yield. So the cleanup must sit in a finally block around the yield; otherwise an error in the body skips it entirely (problem 6).

contextmanager.py
from contextlib import contextmanager

@contextmanager
def temporary(obj, **changes):
    old = {k: getattr(obj, k) for k in changes}
    for k, v in changes.items():
        setattr(obj, k, v)
    try:
        yield obj
    finally:
        for k, v in old.items():
            setattr(obj, k, v)

class Settings:
    temperature = 0.2
    model = "small"

s = Settings()
with temporary(s, temperature=0.9) as cfg:
    print("inside:", cfg.temperature, cfg.model)
print("after:", s.temperature)
try:
    with temporary(s, model="large"):
        raise RuntimeError("request failed")
except RuntimeError:
    print("restored after error:", s.model)
Output
inside: 0.9 small
after: 0.2
restored after error: small

To react to the exception instead of just cleaning up, catch it around the yield: except SomeError: ... lets you log it, and then either raise (propagate) or not (suppress). As with classes, suppress only on purpose. A @contextmanager function can also be used as a decorator above another function, @temporary(s, temperature=0), which wraps every call of that function in the block (a fresh generator is created per call). But a manager object obtained by calling it, cm = temporary(s, ...), is single-use: its generator can run only once, so each with needs a fresh call (problem 16).

5Several managers, nesting and exit order

One with statement can open several managers, separated by commas; since Python 3.10 they can be wrapped in parentheses across lines. They are entered left to right and exited in reverse order, like nested with blocks, so a resource acquired later (a cursor) is released before one acquired earlier (its connection). If one of them fails to enter, those already entered are exited properly.

several.py
from contextlib import contextmanager

log = []

@contextmanager
def step(name):
    log.append(f"enter {name}")
    try:
        yield name
    finally:
        log.append(f"exit {name}")

with (
    step("connection") as conn,
    step("transaction") as tx,
    step("cursor") as cur,
):
    log.append(f"work with {conn}, {tx}, {cur}")
print(log)
Output
['enter connection', 'enter transaction', 'enter cursor', 'work with connection, transaction, cursor', 'exit cursor', 'exit transaction', 'exit connection']

Context managers also compose with everything else in this course: a decorator (8.1) can wrap a function body in a with block; a generator (6.3) can hold a with open while it yields, keeping a file open exactly as long as the stream is consumed; and when the number of managers is only known at run time (open N files), contextlib.ExitStack collects them dynamically (10.3).

6Single-use, reusable and reentrant managers

Context managers differ in whether one object can be used more than once. Single-use managers work in one with only: file objects (once closed, they stay closed) and every @contextmanager object. Reusable managers can be used in several consecutive with blocks, like a Timer instance that resets on each enter. Reentrant managers can even be used in a with inside another with of the same object, which requires keeping a stack of saved state instead of one attribute: threading.RLock is reentrant, threading.Lock is not (it would deadlock). A manager that stores its saved state in a single attribute silently breaks when nested (problem 10).

reentrant.py
class Indent:
    """Reentrant: nested blocks increase the indent, exits restore it."""

    def __init__(self):
        self.level = 0
        self._saved = []

    def __enter__(self):
        self._saved.append(self.level)
        self.level += 2
        return self

    def __exit__(self, *exc):
        self.level = self._saved.pop()
        return False

    def line(self, text):
        return " " * self.level + text

ind = Indent()
out = [ind.line("start")]
with ind:
    out.append(ind.line("retrieve"))
    with ind:
        out.append(ind.line("rerank"))
    out.append(ind.line("generate"))
out.append(ind.line("done"))
print(out)
Output
['start', '  retrieve', '    rerank', '  generate', 'done']

The standard library is full of context managers worth knowing: open, threading.Lock and RLock, tempfile.TemporaryDirectory, decimal.localcontext, warnings.catch_warnings (7.3), contextlib.suppress and redirect_stdout, unittest.mock.patch (13.3), and in async code async with for HTTP sessions and locks (14.4). LLM SDKs make clients and streaming responses context managers, so connections are released even when a loop is abandoned midway.

class Gate:

HintOpen a hint

Record self.start in __enter__; in __exit__, failed = exc_type is not None; return False.

SolutionShow the solution and why
solution.py
class Timer:
    def __init__(self, clock, sink=None):
        self.clock = clock
        self.sink = sink
        self.elapsed = None
        self.failed = None

    def __enter__(self):
        self.start = self.clock()
        return self

    def __exit__(self, exc_type, exc, tb):
        self.elapsed = self.clock() - self.start
        self.failed = exc_type is not None
        if self.sink is not None:
            self.sink.append((self.elapsed, self.failed))
        return False

All the measuring happens in __exit__, which runs on success and on failure alike, so slow timeouts are recorded rather than vanishing from the statistics. exc_type is not None is the standard test for "the block raised". Returning False lets the exception continue to the caller after it has been timed. Because every __enter__ records a fresh start, the same timer can be reused for consecutive blocks (but not nested, since there is only one start). The injected clock makes all of it testable to the exact value.

SolutionShow the solution and why
solution.py
class ignore_missing:
    def __enter__(self):
        return self

    def __exit__(self, exc_type, exc, tb):

Hint 2Open a hint

SolutionShow the solution and why
solution.py
from contextlib import contextmanager

_MISSING = object()

@contextmanager
def overrides(obj, **changes):
    private = [k for k in changes if k.startswith("_")]
    if private:
        raise ValueError(f"refusing to override private attributes: {private}")
    saved = {k: getattr(obj, k, _MISSING) for k in changes}
    for k, v in changes.items():
        setattr(obj, k, v)
    try:
        yield obj
    finally:
        for k, old in saved.items():
            if old is _MISSING:
                delattr(obj, k)
            else:
                setattr(obj, k, old)

Saving the old values before changing anything and restoring them in finally guarantees the object returns to its exact previous state, whether the request succeeds or times out, so a per-request override cannot leak into later requests (9.1's shared-state problem in another form). A sentinel distinguishes "the attribute did not exist" from "it existed and was None" (2.1), so new attributes are removed rather than left behind as None. Validation happens before the yield and before any change, so a rejected call leaves the object untouched. unittest.mock.patch.object (13.3) is the industrial version of this manager, used in tests to replace attributes temporarily.

solution.py
import os
from contextlib import contextmanager

@contextmanager
def atomic_write(path, encoding="utf-8"):
    tmp = path + ".tmp"
    f = open(tmp, "w", encoding=encoding)
    try:
        yield f
    except BaseException:
        f.close()
        os.remove(tmp)
        raise
    else:
        f.close()
        os.replace(tmp, path)

The context manager turns the atomic-write pattern of 7.3 into one line for every caller: they write normally, and either the complete new file appears at path or nothing changes. except BaseException makes even Ctrl+C clean up the temporary file, and the bare raise keeps the original error. The replace happens in else, so it runs only when the block succeeded, and only after the file is closed (flushing everything to disk). Model checkpoints, evaluation results and index files should be written this way, since a crash mid-write would otherwise leave a corrupt file that the next run tries to load.

10. A manager that breaks when nested

no_grad mimics a framework's "disable gradients" switch: inside the block, STATE["grad"] is False, and afterwards it is restored to its previous value. Nested use leaves gradients disabled after the outer block ends. Make it reentrant: each exit restores exactly the value that its own enter replaced.

TestsThe 2 checks Run tests uses

    assert STATE["grad"] is False
    with guard:
        assert STATE["grad"] is False
    assert STATE["grad"] is False
assert STATE["grad"] is True

    pass
assert STATE["grad"] is True
HintOpen a hint

One previous attribute is overwritten by the inner __enter__. Keep a stack (a list) of saved values: push in __enter__, pop in __exit__.

SolutionShow the solution and why
solution.py
STATE = {"grad": True}

class no_grad:
    def __init__(self):
        self._saved = []

    def __enter__(self):
        self._saved.append(STATE["grad"])
        STATE["grad"] = False
        return self

    def __exit__(self, *exc):
        STATE["grad"] = self._saved.pop()
        return False

guard = no_grad()

The outer __enter__ saved True; the inner one, on the same object, overwrote previous with False; the inner exit restored False, and the outer exit then restored the overwritten value, also False, so gradients stayed off for the rest of the program. A stack of saved values gives each enter its own slot, popped by the matching exit in reverse order, which is what makes a manager reentrant. Such global-switch managers are common in ML frameworks (torch.no_grad(), torch.inference_mode()), and nesting them happens naturally when one helper that disables gradients calls another.

@contextmanager def span(name): appends the start event, then try: yield / finally: appends the end event.

SolutionShow the solution and why
solution.py
from contextlib import contextmanager

EVENTS = []

@contextmanager
def span(name):
    EVENTS.append(("start", name))
    try:
        yield
    finally:
        EVENTS.append(("end", name))

def retrieve(query):
    with span("retrieve"):
        if not query:
            raise ValueError("empty query")
        return [f"doc about {query}"]

def generate(query, docs):
    with span("generate"):
        return f"answer from {len(docs)} docs"

The begin/end pairing now lives in one place, and each function body contains only its work, inside a with that reads as "this is the retrieve span". A return inside the with block still triggers the exit, exactly like finally. Adding timing or error status to every span is now one change. Tracing libraries expose exactly this API: OpenTelemetry's with tracer.start_as_current_span("retrieve"):, Langfuse and LangSmith's context-manager spans.

Hint 2Open a hint

solution.py
from contextlib import contextmanager

class Tracer:
    def __init__(self, clock):
        self.clock = clock
        self.spans = []
        self._stack = []

    @contextmanager
    def span(self, name):
        record = {"name": name, "parent": self._stack[-1] if self._stack else None,
                  "start": self.clock(), "end": None, "error": None}
        self.spans.append(record)
        self._stack.append(name)
        try:
            yield record
        except BaseException as e:
            record["error"] = type(e).__name__
            raise
        finally:
            record["end"] = self.clock()
            self._stack.pop()

The stack of open span names is what turns flat timing into a tree: each new span takes the current top as its parent, and its exit pops itself, so nesting in the code becomes nesting in the trace, the structure a tracing UI draws as a waterfall. Recording the error type and then re-raising keeps the manager transparent to the program while making failures visible in the trace. @contextmanager works on methods too: self is just the first argument of the generator function. Yielding the record lets the body attach attributes such as token counts or the number of documents, as OpenTelemetry's span.set_attribute does. In concurrent code the stack would live in a contextvars.ContextVar so that parallel requests do not share it (14.4).

14. Read the code: a transaction manager

Transaction(store) should apply a batch of changes to a dict-like store atomically: inside the block, writes go to a staging dict obtained from as; on success they are committed to the store; on any exception the store is left unchanged and the exception propagates. The code commits after failures, binds None to the as name, and swallows exceptions. Read it, find the bugs and fix them.

Hint 1Open a hint

__enter__ must return the staging dict.

Hint 2Open a hint

Commit only when exc_type is None; return False so exceptions propagate.

SolutionShow the solution and why
solution.py
class Transaction:
    def __init__(self, store):
        self.store = store
        self.commits = 0

    def __enter__(self):
        self.staged = {}
        return self.staged

    def __exit__(self, exc_type, exc, tb):
        if exc_type is None:
            self.store.update(self.staged)
            self.commits += 1
        self.staged = {}
        return False

Three bugs, each a rule of this lesson. __enter__ returned nothing, so as staged received None and the first write raised TypeError. __exit__ committed unconditionally, so a declined payment was written to the store anyway, the exact opposite of a transaction. And returning True swallowed every exception, so the caller believed the declined payment succeeded. The fixed manager commits only on a clean exit, discards the staged changes in every case, and returns False so failures reach the caller after the rollback. Database libraries follow this pattern: with connection: in sqlite3 commits on success and rolls back on an exception; SQLAlchemy's session.begin() does the same.

A handler subclass with emit(self, record) can append (record.levelname, record.getMessage()) to a list (12.3).

Hint 2Open a hint

Save logger.level and logger.propagate in __enter__; restore them and removeHandler in __exit__.

SolutionShow the solution and why
solution.py
import logging

class _ListHandler(logging.Handler):
    def __init__(self, records, level):
        super().__init__(level)
        self.records = records

    def emit(self, record):
        self.records.append((record.levelname, record.getMessage()))


class capture_logs:
    def __init__(self, logger, level=logging.INFO):
        self.logger = logger
        self.level = level

    def __enter__(self):
        self.records = []
        self._handler = _ListHandler(self.records, self.level)
        self._old_level = self.logger.level
        self._old_propagate = self.logger.propagate
        self.logger.addHandler(self._handler)
        if self.logger.getEffectiveLevel() > self.level:
            self.logger.setLevel(self.level)
        self.logger.propagate = False
        return self.records

    def __exit__(self, exc_type, exc, tb):
        self.logger.removeHandler(self._handler)
        self.logger.setLevel(self._old_level)
        self.logger.propagate = self._old_propagate
        return False

The manager changes three pieces of global state (the handler list, the level, and propagation) and puts all three back on every exit, so a test or a debugging session cannot leave the application's logging configuration altered, even when the block fails. Lowering the logger's level matters: a logger set to WARNING drops INFO records before any handler sees them, so the capture would silently miss them; the handler's own level then filters to what was asked for. Stopping propagation keeps captured records out of other handlers during the block. record.getMessage() applies the %-style arguments, which is why the message reads "retrieved 3 docs". pytest's caplog fixture and unittest's assertLogs are built the same way.

Interview

17. What does the with statement do, exactly?

SolutionModel answer

It evaluates the expression to get a context manager, calls its __enter__() and binds the return value to the as target, runs the block, and then always calls __exit__(exc_type, exc_value, traceback), whether the block finished normally, returned, broke out of a loop, or raised. For a normal exit the three arguments are None; for an exception they describe it, and if __exit__ returns a true value the exception is suppressed, otherwise it propagates after the cleanup. If __enter__ raises, the block does not run and __exit__ is not called. With several managers in one statement, they enter left to right and exit in reverse. It is equivalent to a carefully written try/finally (with exception information passed to the cleanup), packaged so that callers cannot forget the cleanup.

Interview

18. When would you write a context manager as a class, and when with contextlib.contextmanager?

SolutionModel answer

@contextmanager is best for simple setup/cleanup pairs: a generator function with setup before a single yield, the value to bind yielded, and cleanup after it inside finally (mandatory, because exceptions from the block are re-raised at the yield). It is short and readable, but each call produces a single-use manager. A class with __enter__ and __exit__ fits when the manager has state or behaviour beyond the block: it is reused or must be reentrant (keeping a stack of saved state), it exposes results after the block (a timer's elapsed time), it is also an ordinary object with methods (a file, a client, a lock), it needs fine-grained exception handling in __exit__, or it will be subclassed. Either way, suppress exceptions only deliberately and for specific types, and use contextlib.suppress, ExitStack and nullcontext from the standard library before writing your own.

Interview

19. How do you make sure resources such as HTTP clients, streaming responses and connection pools are cleaned up in an LLM service?

SolutionModel answer

Tie every resource to a scope with a context manager. Create long-lived resources (an HTTP client with its connection pool, a database pool, a vector store client) once at application start-up and close them at shutdown, using the framework's lifespan hook, which is itself a context manager (FastAPI's lifespan), rather than creating a client per request, which wastes connections. For per-request resources, use with (or async with): streaming responses from LLM SDKs are context managers that close the underlying connection even if the consumer stops reading early, temporary files go through tempfile managers, and locks are always taken with with. Make sure cleanup also runs on cancellation: when a client disconnects, the framework cancels the task, which raises inside your code, and only finally blocks and context managers still run, so put the release logic there. Use ExitStack (10.3) when the number of resources is dynamic, set timeouts so a stuck resource cannot block forever, and monitor pool usage to catch leaks early.

Recap

  • with mgr as x: calls __enter__ (its return value becomes x), runs the block, then always calls __exit__(type, value, tb).
  • __exit__ returning true suppresses the exception: do it only for specific types; return False to propagate after cleanup.
  • @contextmanager turns a one-yield generator into a manager; put the cleanup in finally around the yield, or errors skip it.
  • Several managers enter left to right and exit in reverse; a return inside the block is a normal exit.
  • Generator managers are single-use; a reusable or reentrant class keeps a stack of saved state for nested use.
