Mixed problems from all of Module 10: iterator classes and re-iterable containers, context managers written as classes and generators, and resource patterns with ExitStack. 1How to use this page

For anything that is iterated, ask: one pass or many? Containers hand out a fresh iterator each time (usually from a generator __iter__); streams are their own iterator and are used once (10.1). For anything that is acquired, ask: who releases it, and when? Tie the release to a scope with a context manager, put cleanup in finally, suppress nothing by accident (10.2), and use ExitStack when the number of resources or undo steps is decided at run time (10.3).

The problems mix the lessons on purpose, and the mini project combines all three in one job of the kind data and LLM pipelines run every day.

2. A reader that counts what it consumed

Write a context manager class CountingReader(lines) whose __enter__ returns the reader itself, which is an iterator over the non-blank lines (stripped). HintOpen a hint

Keep self._it = iter(lines); __next__ loops, counting blanks, until it finds a non-blank line (or StopIteration propagates).

SolutionShow the solution and why
solution.py
class CountingReader:
    def __init__(self, lines):
        self._it = iter(lines)
        self.consumed = 0
        self.skipped = 0
        self.closed = False

    def __enter__(self):
        return self

    def __exit__(self, exc_type, exc, tb):
        self.closed = True
        return False

    def __iter__(self):
        return self

    def __next__(self):
        if self.closed:
            raise ValueError("reader is closed")
        for line in self._it:
            if line.strip():
                self.consumed += 1
                return line.strip()
            self.skipped += 1
        raise StopIteration

The class is both a context manager (its scope) and an iterator (its content), like a file object. Looping over the shared self._it inside __next__ keeps the position across calls, and the for loop simply continues where the last call stopped. When the source runs out, the method raises StopIteration explicitly, the correct signal for an iterator class (unlike a generator, 10.1). Raising ValueError after close mirrors files ("I/O operation on closed file") and turns use-after-close into a clear error. The counters make it easy to report how much of an input a job actually processed.

class ChatScope:
    def __init__(self):
        self.saved = []

    def __enter__(self):
        self.buffer = []

    def __exit__(self, exc_type, exc, tb):

4. ExitStack with a generator source

from contextlib import ExitStack, contextmanager

@contextmanager
def opened(name, items):
    print(f"  open {name}")
    try:
        yield (f"{name}:{x}" for x in items)
    finally:
        print(f"  close {name}")

with ExitStack() as stack:
    streams = [stack.enter_context(opened(n, items)) for n, items in [("a", [1, 2]), ("b", [3])]]
    merged = [x for s in streams for x in s]
    again = [x for s in streams for x in s]
print(merged, again)
HintOpen a hint

The managers close in reverse order. Generator expressions are one-shot.

SolutionShow the solution and why
Real output
  open a
  open b
  close b
  close a
['a:1', 'a:2', 'b:3'] []

Both sources are opened in order and closed in reverse when the stack exits. The first comprehension drains both generator expressions; the second finds them exhausted and produces nothing, the one-shot rule of 6.3 and 10.1: a stream handed out by a resource can be read once, so code that needs two passes must keep the values (here, merged) rather than re-reading the streams.

5. Epochs over a dataset

Write a class Epochs(rows, batch_size, epochs, seed) that is re-iterable and yields (epoch, batch) pairs: for each epoch from 0, it shuffles a copy of the rows with random.Random(seed + epoch) (so every epoch has its own, reproducible order), then yields batches of batch_size rows (the last may be shorter). len() returns the total number of batches across all epochs, computed arithmetically. solution.py
import random

class Epochs:
    def __init__(self, rows, batch_size, epochs, seed):
        self.rows = list(rows)
        self.batch_size = batch_size
        self.epochs = epochs
        self.seed = seed

    def __len__(self):
        per_epoch = (len(self.rows) + self.batch_size - 1) // self.batch_size
        return per_epoch * self.epochs

    def __iter__(self):
        for epoch in range(self.epochs):
            order = list(self.rows)
            random.Random(self.seed + epoch).shuffle(order)
            for start in range(0, len(order), self.batch_size):
                yield epoch, order[start:start + self.batch_size]

A private random.Random per epoch makes the shuffle reproducible (the same seed always gives the same order, so two iterations of the object agree), different between epochs, and independent of the global generator (10.3). The shuffle of epoch 0 does not depend on the batch size, which the last test checks by regrouping the same order into batches of 3. Shuffling a copy leaves the caller's rows untouched (2.4). The generator __iter__ makes the object re-iterable, and len is cheap arithmetic, so a training loop can show progress without materialising anything: the job of PyTorch's sampler and DataLoader with shuffle=True and a seeded generator.

This is why frameworks such as Hugging Face datasets with streaming, or tf.data, describe data as a recipe to produce records rather than as an already-open stream.

SolutionShow the solution and why
solution.py
import os

def tee_to_file(chunks, path):
    tmp = path + ".part"
    f = open(tmp, "w", encoding="utf-8")
    try:
        for chunk in chunks:
            f.write(chunk)
            yield chunk
    except BaseException:
        f.close()
        os.remove(tmp)
        raise
    f.close()
    os.replace(tmp, path)

The generator keeps the file open exactly as long as the stream is being consumed (6.3), and three endings are handled differently. A complete stream falls out of the loop, so the file is closed and atomically swapped into place. A consumer that stops early closes the generator, which raises GeneratorExit at the paused yield; it is a BaseException, so the cleanup branch removes the partial file and re-raises it, as generators must. A source error takes the same branch and reaches the caller. Saving a streamed LLM answer this way means a cancelled or failed request never leaves a truncated answer on disk that a later step might mistake for a complete one.

class Server:
    def __init__(self, make_client):
        self.make_client = make_client
        self.client = None

    def __enter__(self):
        self.client = self.make_client()
        return self

    def __exit__(self, *exc):
        if self.client is not None:
            self.client.close()
            self.client = None
        return False

    def handle(self, prompt):
        with self.client.stream(prompt) as stream:
            return "".join(stream)

    def handle_first(self, prompt, n):
        chunks = []
        with self.client.stream(prompt) as stream:
            for chunk in stream:
                chunks.append(chunk)
                if len(chunks) == n:
                    break
        return chunks

Three resource bugs, each a lesson of this module. A client per request means a new connection pool per call, slow and wasteful; the client's lifetime belongs to the server's scope, so it is created in __enter__ and closed in __exit__ (10.3). Cleanup skipped on error: when the stream failed, client.close() was never reached; now the client's cleanup no longer depends on each request at all. Streams left open: handle_first stopped reading but never closed the stream, so a real provider would keep generating (and billing) the rest of the answer; with ... as stream closes it on the normal path, after a break, and when the stream raises (10.2). The event list in the test is the whole lifecycle in order: one client, three streams each closed exactly once, then one client close.

Interview

10. When do you write a generator, an iterator class, or a context manager?

SolutionModel answer

A generator (function or __iter__ method) is the default for producing a sequence: it is short, lazy, and manages its own position and StopIteration; containers use a generator __iter__ to be re-iterable. An iterator class with __next__ is for streams that need more than iteration: extra methods (peek, close), state that other code reads during iteration (text so far, pages fetched), or careful control of reading ahead. A context manager is about scope, not sequence: something acquired must be released (files, clients, locks, transactions, temporary settings), so the release is guaranteed by __exit__ or a finally around a yield. They combine naturally: a file or SDK stream is both an iterator and a context manager, a generator can hold a with open while it yields, and ExitStack manages several resources whose number is known only at run time.

11. A user disconnects while your service is streaming an LLM answer. What happens to your resources, and how do you make it safe?

SolutionModel answer

The web framework notices the disconnect and stops consuming the response generator, typically by closing it (sync) or cancelling the task (async), which raises GeneratorExit or CancelledError at the point where your code is paused. Nothing after that point runs, except finally blocks and __exit__ methods: so every resource opened during the request must be scoped with with or try/finally. The upstream LLM stream must be closed (the SDK stream as a context manager does it), or the provider keeps generating and billing the full answer; temporary files must be removed or committed atomically only on completion; spans and logs should record that the request was cancelled; locks and pooled connections must be returned. Do not catch GeneratorExit or CancelledError and continue, and do not do slow work in cleanup. Long-lived resources (the client and its connection pool) belong to the application scope and are unaffected. Test it by closing the response generator after a few chunks with fakes that record what was closed, as in the projects of this module.

from contextlib import ExitStack, suppress

class Ticker:

13. Export records from several sources

Implement three classes and a function.

  • Source(name, lines): a context manager whose __enter__ marks it open (appending f"open {name}" to a shared EVENTS list) and returns itself; __exit__ closes it (appending f"close {name}") and propagates errors; iterating an open source yields (name, line_number, text) for each line that is not blank and does not start with #, stripped, with line numbers counted from 1 over all lines. Iterating a closed or never-opened source raises ValueError.
  • Batches(iterable, size): an iterator class yielding lists of up to size items lazily, counting self.made.
  • Destination(): a context manager for one transaction: __enter__ returns itself; write(batch) stages a batch; on a clean exit the staged batches are appended to self.committed and self.commits is incremented; on an exception nothing is committed and self.rollbacks is incremented; errors propagate.
  • export(sources, destination, batch_size): inside one ExitStack, enter every source and the destination, chain the sources' records in order, write them in batches, and return {"records": n, "batches": b}. If anything fails, all sources are closed, the destination rolls back, and the error propagates with the note f"export failed after {n} records".

SolutionShow the solution and why
solution.py
from contextlib import ExitStack
from itertools import chain

EVENTS = []


class Source:
    def __init__(self, name, lines):
        self.name = name
        self.lines = list(lines)
        self._open = False

    def __enter__(self):
        self._open = True
        EVENTS.append(f"open {self.name}")
        return self

    def __exit__(self, exc_type, exc, tb):
        self._open = False
        EVENTS.append(f"close {self.name}")
        return False

    def __iter__(self):
        if not self._open:
            raise ValueError(f"source {self.name} is not open")
        for number, line in enumerate(self.lines, start=1):
            text = line.strip()
            if text and not text.startswith("#"):
                yield self.name, number, text


_DONE = object()


class Batches:
    def __init__(self, iterable, size):
        self._it = iter(iterable)
        self.size = size
        self.made = 0

    def __iter__(self):
        return self

    def __next__(self):
        batch = []
        for _ in range(self.size):
            item = next(self._it, _DONE)
            if item is _DONE:
                break
            batch.append(item)
        if not batch:
            raise StopIteration
        self.made += 1
        return batch


class Destination:
    def __init__(self):
        self.committed = []
        self.commits = 0
        self.rollbacks = 0
        self._staged = []

    def __enter__(self):
        self._staged = []
        return self

    def write(self, batch):
        self._staged.append(list(batch))

    def __exit__(self, exc_type, exc, tb):
        if exc_type is None:
            self.committed.extend(self._staged)
            self.commits += 1
        else:
            self.rollbacks += 1
        self._staged = []
        return False


def export(sources, destination, batch_size):
    count = 0

    def counted(records):
        nonlocal count
        for record in records:
            count += 1
            yield record

    try:
        with ExitStack() as stack:
            opened = [stack.enter_context(s) for s in sources]
            dest = stack.enter_context(destination)
            batches = Batches(counted(chain.from_iterable(opened)), batch_size)
            for batch in batches:
                dest.write(batch)
            return {"records": count, "batches": batches.made}
    except Exception as e:
        e.add_note(f"export failed after {count} records")
        raise

Every lesson of the module has a job here:

  • Iterator classes (10.1): Source is a re-iterable container whose generator __iter__ refuses to run while closed; Batches is a one-shot iterator class because it carries state (made) that the job reports; counted is a pass-through generator that measures the stream without materialising it, and chain.from_iterable (6.4) joins the sources lazily, so records flow from source to batch to destination one batch at a time.
  • Context managers (10.2): sources open and close as scopes, and Destination is a transaction: staged batches are committed only on a clean exit and discarded on an exception, which still propagates.
  • Resource patterns (10.3): one ExitStack holds a run-time number of sources plus the destination, so a failure anywhere unwinds everything in reverse order, the destination first (rolling back) and then the sources (closing), exactly as the event log shows.

The note added outside the stack tells the operator how far the job got, without changing the exception type (7.2). In production the sources would be file readers, API paginators or database cursors, the destination a database transaction or an atomic file write, and the same structure would hold.

Recap

  • Containers return a fresh iterator per loop (generator __iter__); streams are one-shot iterators, and re-iterable data needs a re-openable source all the way down.
  • Context managers tie release to scope: as gets __enter__'s return value, cleanup goes in __exit__ or a finally around the yield.
  • Suppress exceptions only on purpose; commit on clean exit, roll back on error, and let the error propagate.
  • ExitStack manages any number of resources and undo callbacks, unwinding in reverse; pop_all hands them over.
  • Close half-consumed streams explicitly; share long-lived clients per application and scope everything else per request.
