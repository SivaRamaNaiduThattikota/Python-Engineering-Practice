1. Alias, shallow and deep in one go

import copy

a = {"k": [1]}
b = a
c = dict(a)
d = copy.deepcopy(a)
a["k"].append(2)
a["new"] = 0
print(b)
print(c)
print(d)
HintOpen a hint

Two kinds of change happen: one to the inner list, one to the outer dict.

SolutionShow the solution and why
Real output
{'k': [1, 2], 'new': 0}
{'k': [1, 2]}
{'k': [1]}

b is an alias, so it sees both changes. c is a shallow copy: it shares the inner list, so it sees the append, but adding "new" changed only a's outer dict. d is a deep copy and shares nothing. Every Module 2 bug is one of these three relationships.

2. Default tags that pile up

tag_doc(doc, tags=["general"]) should return a new document with the given tags plus a "seen" tag. Calls without tags keep collecting "seen" tags, and the caller's document changes too. Fix both.

TestsThe 3 checks Run tests uses
d = {"id": 1}
out = tag_doc(d)
assert out == {"id": 1, "tags": ["general", "seen"]} and d == {"id": 1}
assert tag_doc({"id": 2}) == {"id": 2, "tags": ["general", "seen"]}
mine = ["faq"]
assert tag_doc({"id": 3}, mine)["tags"] == ["faq", "seen"] and mine == ["faq"]
Hint 1Open a hint

Never change the default or the caller's list: build a new list with +.

Hint 2Open a hint

Return {**doc, "tags": ...} instead of writing into doc.

SolutionShow the solution and why
solution.py
def tag_doc(doc, tags=("general",)):
    return {**doc, "tags": list(tags) + ["seen"]}

Three separate side effects: appending to the default, appending to a caller's list, and writing into the caller's dict. Building the result with list(tags) + ["seen"] and {**doc, ...} removes all three. The default became a tuple: an immutable default can never be changed by accident, so it is safe to leave in the signature, which reads better than None when there is a real default value.

3. Equal tuples and NaN

t1 = (1, [2])
t2 = (1, [2])
print(t1 == t2, t1 is t2)
x = float("nan")
print((x, 1) == (x, 1))
print((float("nan"), 1) == (float("nan"), 1))
print(x in {x}, float("nan") in {x})
HintOpen a hint

Tuples compare item by item with "identity, then equality". Sets look items up by hash, then identity, then equality.

SolutionShow the solution and why
Real output
True False
True
False
True False

t1 and t2 are equal but separate. (x, 1) == (x, 1) is True because both tuples hold the same NaN object and the identity check comes first, while two separate NaNs are never equal. Sets follow the same rule: the same NaN object is found, a new one is not. A dataset deduplicated with a set can keep "duplicate" rows that both contain NaN, which is exactly what you see when deduplicating feature tuples with missing values.

4. Group ids by category

Write group_ids(records) that takes (id, category) pairs and returns a dict from category to the list of ids in that category, in input order. Each category must have its own list.

TestsThe 3 checks Run tests uses
out = group_ids([(1, "a"), (2, "b"), (3, "a")])
assert out == {"a": [1, 3], "b": [2]}
out["a"].append(99)
assert out["b"] == [2]
assert group_ids([]) == {}
HintOpen a hint

Start with {} and create a list the first time you meet a category. dict.setdefault does it in one call.

SolutionShow the solution and why
solution.py
def group_ids(records):
    out = {}
    for rid, cat in records:
        out.setdefault(cat, []).append(rid)
    return out

setdefault(cat, []) returns the existing list or stores a new one, and the [] is evaluated on each call, so each category gets its own list. The tempting dict.fromkeys(categories, []) would share one list between all categories (2.2). collections.defaultdict(list) is the other standard way (lesson 4.6).

Each call without seen makes a new list. Passing s hands the function that exact list.

With the None default, the first two calls each build their own list, so t is independent of s. This is the correct version of the mutable-default pattern: fresh by default, shared only when the caller asks for it.

7. Train and test splits that share rows

make_splits splits rows into train and test. Later, the training rows are normalised in place, and the original dataset changes with them, so re-running the experiment gives different numbers. Fix make_splits so each split owns its rows. Do not change normalise_inplace.

TestsThe 3 checks Run tests uses
data = [[1, 1], [1, 3], [2, 2]]
train, test = make_splits(data, 2)
normalise_inplace(train)
assert train == [[0.5, 0.5], [0.25, 0.75]]
assert data == [[1, 1], [1, 3], [2, 2]]
assert test == [[2, 2]] and test[0] is not data[2]
Hint 1Open a hint

A slice is a shallow copy: the split lists are new, but the row lists inside are the dataset's rows.

Hint 2Open a hint

Copy each row as you build the splits.

SolutionShow the solution and why
solution.py
def make_splits(rows, n_train):
    return [r[:] for r in rows[:n_train]], [r[:] for r in rows[n_train:]]


def normalise_inplace(rows):
    for row in rows:
        total = sum(row)
        row[:] = [v / total for v in row]

Slicing creates new outer lists, which looks like a copy, but the rows inside are the dataset's own row objects. Normalising them in place reaches straight into data. Copying each row makes the splits own their data, so in-place work on them is safe. In numpy the same trap is worse, because X[:n] is a view of the whole array (2.2): normalising X_train = X[:n] in place changes X. That is why scikit-learn's train_test_split returns copies.

8. Drop repeated messages, keep the originals

A client sometimes sends the same message twice in a row. Write drop_repeats(history) that returns a new list without messages that are equal to the message right before them. The messages you keep must be the original objects, not copies, because other code tracks them by identity.

TestsThe 3 checks Run tests uses
m1 = {"role": "user", "content": "hi"}
m2 = {"role": "user", "content": "hi"}
m3 = {"role": "assistant", "content": "Hello!"}
m4 = {"role": "user", "content": "hi"}
out = drop_repeats([m1, m2, m3, m4])
assert out == [m1, m3, m4]
assert out[0] is m1 and out[1] is m3 and out[2] is m4
assert drop_repeats([]) == []
HintOpen a hint

Compare each message with the last kept message using ==, and append the message object itself.

SolutionShow the solution and why
solution.py
def drop_repeats(history):
    out = []
    for msg in history:
        if not out or msg != out[-1]:
            out.append(msg)
    return out

Two different questions in one function. Whether to keep a message is a value question, so it uses == (two equal "hi" messages in a row are a repeat). What to keep is the identity question, so the original object goes in the result instead of a copy. m4 equals m1 but is kept, because only consecutive repeats count. Good code in this module keeps those two questions apart.

9. Slice assignment versus rebinding a parameter

def f(a, b):
    a[:] = [9]
    b = [9]
    return a, b

x, y = [1, 2], [1, 2]
ra, rb = f(x, y)
print(x, y)
print(ra is x, rb is y)
HintOpen a hint

a[:] = ... changes the object a points at. b = ... moves the local name b.

SolutionShow the solution and why
Real output
[9] [1, 2]
True False

a[:] = [9] replaces the contents of the caller's list, so x becomes [9] and the returned a is x itself. b = [9] only moves the local name, so y is untouched and the returned list is a new one. The same two lines look almost identical and do opposite things to the caller.

10. Rename a key without copying everything

This renames one key in a record. It deep-copies the whole record to stay safe, which is slow for records with big nested values, and it fails the test that the values must be shared, not copied. Rewrite it so the input is still never changed and the values are not copied.

TestsThe 4 checks Run tests uses
rec = {"id": 7, "meta": {"src": "crm", "rows": list(range(5))}}
out = rename_key(rec, "meta", "metadata")
assert out == {"id": 7, "metadata": {"src": "crm", "rows": [0, 1, 2, 3, 4]}}
assert "meta" in rec and "metadata" not in rec
assert out["metadata"] is rec["meta"]
assert rename_key(rec, "nope", "x") == rec
Hint 1Open a hint

Build the new dict directly: keep every value, change only the one key name.

Hint 2Open a hint

A dict comprehension with a conditional key: {(new if k == old else k): v for ...}.

SolutionShow the solution and why
solution.py
def rename_key(record, old, new):
    return {(new if k == old else k): v for k, v in record.items()}

The function never changes any value, so there is nothing to protect inside them: building a new dict that points at the same values is enough to leave the input untouched. Sharing the values is safe as long as callers do not change them in place, the same contract as structural sharing. "Deep-copy everything defensively" is a common over-correction after an aliasing bug. It costs time and memory and hides the real design question: who is allowed to change this data?

11. Which settings changed?

Write changed_paths(old, new) that compares two nested configs (dicts of dicts and plain values) and returns a sorted list of key paths (tuples) whose values differ, including keys that were added or removed. When a nested dict is the same object in both configs, skip it without looking inside: with structural sharing (2.3), that is most of the config.

TestsThe 3 checks Run tests uses
retr = {"k": 5, "index": {"name": "docs", "shards": 4}}
old = {"retriever": retr, "llm": {"model": "small", "params": {"temperature": 0.2, "top_p": 1.0}}}
new = {"retriever": retr, "llm": {"model": "small", "params": {"temperature": 0.9}}, "debug": True}
assert changed_paths(old, new) == [("debug",), ("llm", "params", "temperature"), ("llm", "params", "top_p")]
assert changed_paths(old, old) == []
assert changed_paths({"a": {"x": 1}}, {"a": 2}) == [("a",)]
Hint 1Open a hint

Recurse into a key only when both sides hold a dict; check is first and return early when they are the same object.

Hint 2Open a hint

A key present on one side only is a change. Use the union of both key sets.

SolutionShow the solution and why
solution.py
MISSING = object()

def changed_paths(old, new, prefix=()):
    if old is new:
        return []
    out = []
    for key in set(old) | set(new):
        a, b = old.get(key, MISSING), new.get(key, MISSING)
        path = prefix + (key,)
        if isinstance(a, dict) and isinstance(b, dict):
            out.extend(changed_paths(a, b, path))
        elif a != b:
            out.append(path)
    return sorted(out)

The is check at the top is the point: comparing shared branches by identity is O(1), so diffing two variants built with structural sharing costs time only for the parts that were actually rebuilt. == would walk every shared branch to find out it is equal to itself. A sentinel (2.1) marks missing keys, because None could be a real setting value. The prefix parameter has an immutable tuple as its default, which is safe. Config diffs like this are what experiment trackers show when you compare two runs.

Interview

12. A notebook gives different results when you run its cells a second time. What would you look for?

SolutionModel answer

Something is being changed in place and reused. In order: a function with a mutable default (a list or dict that keeps collecting across calls); a transform that changes its input in place, so running it twice transforms twice (scaling, appending features, filling missing values); an alias between "raw" and "processed" data, such as a slice or a numpy view, so processing changed the raw data; shared nested config copied shallowly between experiments; and global state (a cache or counter at module level). How to confirm: snapshot the input with copy.deepcopy before a step and compare after, check id() or is between raw and processed objects, and restart the kernel and run top to bottom. The fix is the module's theme: pure functions by default, explicit in-place operations, copies at the right depth, None defaults.

Interview

13. How do you make sure a function does not change its inputs, and how would you test it?

SolutionModel answer

Design first: write it as a pure function that builds new objects ({**d, ...}, xs + [...], comprehensions) instead of changing old ones, and pass read-only data where you can (tuples, MappingProxyType, frozen dataclasses). To test it: make a deep copy of the input before the call and assert the input still equals that snapshot afterwards; also assert that the result is not the same object as the input (out is not inp) where a new object is promised. For data code, test with nested inputs, because shallow copies only fail there. Property-based testing (Hypothesis) can check "input unchanged" across many generated inputs automatically.

3Mini project: a safe conversation store

A chat service keeps sessions in memory. Earlier versions had every bug from this module: users saw each other's messages, deleting one "ok" deleted another, editing a returned history changed the stored one, and forking a session for an A/B test changed the original. Build the store so none of that can happen. The tests check every rule.

Project

14. A safe conversation store

Implement these functions over a plain dict store (session id to session):

1. start_session(store, session_id, system, settings=None): create a session with a system message {"role": "system", "content": system} and settings made from DEFAULTS with settings merged on top (one level of nesting, like DEFAULTS["llm"]). Starting an existing id raises ValueError. No session may share any list or dict with DEFAULTS or with another session.

2. add_message(store, session_id, role, content): append a new message and return that message object.

3. get_history(store, session_id): return the messages so the caller can freely append to the list or edit any message without changing the store.

4. delete_message(store, session_id, msg): delete exactly that message object. Deleting the system message, or a message that is not in the session, raises ValueError.

5. fork_session(store, source_id, new_id): create new_id as an independent copy of source_id, messages and settings included. Later changes to either session must not show in the other.

SolutionShow the solution and why
solution.py
import copy

DEFAULTS = {"llm": {"model": "small", "temperature": 0.2}, "tags": ["chat"]}


def start_session(store, session_id, system, settings=None):
    if session_id in store:
        raise ValueError(f"session {session_id!r} already exists")
    merged = copy.deepcopy(DEFAULTS)
    for key, value in (settings or {}).items():
        if isinstance(merged.get(key), dict) and isinstance(value, dict):
            merged[key] = {**merged[key], **value}
        else:
            merged[key] = copy.deepcopy(value)
    store[session_id] = {
        "messages": [{"role": "system", "content": system}],
        "settings": merged,
    }


def add_message(store, session_id, role, content):
    msg = {"role": role, "content": content}
    store[session_id]["messages"].append(msg)
    return msg


def get_history(store, session_id):
    return [dict(m) for m in store[session_id]["messages"]]


def delete_message(store, session_id, msg):
    messages = store[session_id]["messages"]
    for i, m in enumerate(messages):
        if m is msg:
            if i == 0:
                raise ValueError("the system message cannot be deleted")
            del messages[i]
            return
    raise ValueError("message is not in this session")


def fork_session(store, source_id, new_id):
    if new_id in store:
        raise ValueError(f"session {new_id!r} already exists")
    store[new_id] = copy.deepcopy(store[source_id])

Every function uses a different tool from the module:

  • start_session deep-copies DEFAULTS so no session shares its nested llm dict or tags list with the defaults or with other sessions (2.2, 2.3). The None default for settings avoids a shared default dict (2.4), and settings or {} is safe here because an empty dict and None both mean "no overrides". Values taken from settings are deep-copied too, so a caller who changes their own dict later cannot reach into the session.
  • add_message returns the stored object on purpose: callers use it as a handle for delete_message.
  • get_history copies two levels, exactly as deep as the data (2.3): a new list and a new dict per message.
  • delete_message searches by identity, so an equal message (the second "ok", or an outside copy) is never deleted by mistake (2.1).
  • fork_session is the one place where a full deepcopy is the right tool: the goal is total independence and sessions are small.

A production version would store messages in a database with real ids instead of using object identity, lock sessions for concurrent requests (Module 14) and validate settings with Pydantic (Module 11). The ownership rules stay exactly the same.

Recap

  • Name the relationship first: alias, shallow copy or deep copy. Most Module 2 bugs are one of the three in the wrong place.
  • Value questions use ==, identity questions use is. Many real functions need both: decide by value, keep the original object.
  • Copy as deep as the data needs and no deeper. Deep copies fix aliasing but cost time and hide the real design question: who may change this?
  • Functions get your actual objects: pure by default, in place only when explicit, None or immutable defaults.
