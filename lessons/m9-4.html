9.4 Inheritance and super

A subclass reuses and specialises another class. How attribute lookup walks the class chain, overriding and extending methods with super(), what super() really calls (the method resolution order), the template-method pattern, the substitution rule that keeps hierarchies honest, cooperative multiple inheritance and mixins, __init_subclass__, and why subclassing dict misleads. Applied to retrievers, providers, metrics and loaders.

1Subclasses inherit, and can specialise

class KeywordRetriever(Retriever): defines a subclass: every attribute and method of Retriever, the base class, is available on instances of KeywordRetriever without being written again. The subclass can add new methods, and it can override inherited ones by defining a method with the same name. The relationship should read as "is a": a keyword retriever is a retriever, so anywhere code expects a Retriever, a KeywordRetriever can be used.

Inheritance works through attribute lookup (9.1). For obj.name, Python searches the instance's __dict__, then the object's class, then that class's base, and so on up the chain, ending at object, the root of every class. The first match wins, which is exactly why overriding works: the subclass is searched before the base.

inherit.py
class Retriever:
    def __init__(self, docs):
        self.docs = list(docs)

    def score(self, query, doc):
        return 0

    def retrieve(self, query, k=2):
        ranked = sorted(self.docs, key=lambda d: self.score(query, d), reverse=True)
        return ranked[:k]

class KeywordRetriever(Retriever):
    def score(self, query, doc):                      # override
        return len(set(query.lower().split()) & set(doc.lower().split()))

docs = ["Refund policy for orders", "Reset your password", "Refund window is 30 days"]
kr = KeywordRetriever(docs)
print(kr.retrieve("refund window"))
print(isinstance(kr, Retriever), issubclass(KeywordRetriever, Retriever), type(kr) is Retriever)
print([c.__name__ for c in KeywordRetriever.__mro__])
Output
['Refund window is 30 days', 'Refund policy for orders']
True True False
['KeywordRetriever', 'Retriever', 'object']

retrieve is defined once, in the base class, and it calls self.score(...). For a KeywordRetriever, self.score finds the subclass's override first. So the base class's algorithm uses the subclass's scoring without knowing it exists: the base defines the steps, the subclass fills in one of them. That is the template method pattern, the most useful thing inheritance does (problem 2). isinstance respects the hierarchy, while type(x) is Base does not, which is why isinstance is the right check in almost all code.

2Extending a method with super()

Often a subclass wants to add to an inherited method rather than replace it: do what the base does, plus something more. super().method(...) calls the next class's version of the method on the same instance. The most important case is __init__: if a subclass defines its own __init__, the base's __init__ is not called automatically, so the base's attributes are never set unless the subclass calls super().__init__(...). Forgetting it is the most common inheritance bug, and it fails later, with an AttributeError far from the cause (problem 3).

super_extend.py
class Retriever:
    def __init__(self, docs):
        self.docs = list(docs)
        self.calls = 0

    def retrieve(self, query, k=2):
        self.calls += 1
        return [d for d in self.docs if query.lower() in d.lower()][:k]

class FilteredRetriever(Retriever):
    def __init__(self, docs, banned):
        super().__init__(docs)                 # set up everything the base needs
        self.banned = set(banned)

    def retrieve(self, query, k=2):
        results = super().retrieve(query, k=len(self.docs))   # reuse, then extend
        return [d for d in results if not self.banned & set(d.lower().split())][:k]

fr = FilteredRetriever(["Refund policy", "Refund scam alert", "Refund window"], banned=["scam"])
print(fr.retrieve("refund"), fr.calls, sorted(vars(fr)))
Output
['Refund policy', 'Refund window'] 1 ['banned', 'calls', 'docs']

super() without arguments works inside methods because Python knows which class the method was defined in and which instance it was called on. The extension pattern is: call super() to get the base behaviour, then add or adjust. Calling Retriever.retrieve(self, ...) by name also works with single inheritance, but it breaks the cooperation that multiple inheritance needs (below), so super() is the habit to build.

3What super() really calls: the MRO

With single inheritance, super() means "the parent". In general it means something more precise: the next class in the method resolution order of the instance's class. The MRO is the list Python searches for attributes, available as Class.__mro__. For multiple inheritance, class D(B, C), Python computes it with the C3 linearisation algorithm, which guarantees that every class appears before its bases, that the order of bases you wrote is respected, and that each class appears exactly once.

mro.py
class Base:
    def greet(self):
        return ["Base"]

class Polite(Base):
    def greet(self):
        return ["Polite"] + super().greet()

class Brief(Base):
    def greet(self):
        return ["Brief"] + super().greet()

class Assistant(Polite, Brief):
    def greet(self):
        return ["Assistant"] + super().greet()

print([c.__name__ for c in Assistant.__mro__])
print(Assistant().greet())
print(Polite().greet())
Output
['Assistant', 'Polite', 'Brief', 'Base', 'object']
['Assistant', 'Polite', 'Brief', 'Base']
['Polite', 'Base']

In Assistant, super() inside Polite.greet does not go to Base, even though Base is Polite's parent: it goes to Brief, the next class in Assistant's MRO. Only Brief's super() reaches Base. That is how every class in a "diamond" gets called exactly once, in a predictable order. It also means a class using super() does not know which method it will call next; that is decided by the class of the actual instance. For this to work, every method in the chain must call super() and accept the arguments the others might pass, usually through **kwargs (problem 11).

4The substitution rule

Inheritance is a promise: an instance of the subclass can be used wherever the base class is expected, without the caller noticing a difference in the rules. This is the Liskov substitution principle. In practice an override must accept the same arguments as the base method (it may accept more, with defaults), return the same kind of result, and not raise errors that callers of the base would not expect, or demand more of its inputs. Breaking the promise makes the base class's own code fail: the template method calls the hook with the base's signature (problem 9).

substitution.py
class Loader:
    def load(self, path, encoding="utf-8"):
        return f"text of {path}"

    def load_many(self, paths):
        return [self.load(p, encoding="utf-8") for p in paths]

class BrokenPDFLoader(Loader):
    def load(self, path):                       # dropped the encoding parameter
        return f"pdf text of {path}"

class PDFLoader(Loader):
    def load(self, path, encoding="utf-8", password=None):   # same contract, plus an optional extra
        return f"pdf text of {path}"

print(PDFLoader().load_many(["a.pdf", "b.pdf"]))
try:
    BrokenPDFLoader().load_many(["a.pdf"])
except TypeError as e:
    print("TypeError:", e)
Output
['pdf text of a.pdf', 'pdf text of b.pdf']
TypeError: BrokenPDFLoader.load() got an unexpected keyword argument 'encoding'

A classic violation is a "read-only list" that subclasses list and raises on append: any function that receives a list and appends to it breaks. If the subclass cannot honour the base's interface, it is not an "is a" relationship, and composition (9.5), holding the other object instead of inheriting from it, is the right design.

5Multiple inheritance and mixins

Python allows several base classes. The common, safe use is mixins: small classes that each add one capability and are combined with a main class: a JsonMixin that adds to_json(), a ReprMixin that adds a generic __repr__, a TimestampMixin that records creation time. Mixins usually have no state of their own, or initialise it cooperatively: their __init__ takes **kwargs, picks out what it needs, and passes the rest on with super().__init__(**kwargs), so that every class in the MRO gets its arguments.

mixins.py
import json

class JsonMixin:
    def to_json(self):
        return json.dumps({k: v for k, v in vars(self).items() if not k.startswith("_")}, sort_keys=True)

class TaggedMixin:
    def __init__(self, *, tags=(), **kwargs):
        super().__init__(**kwargs)
        self.tags = sorted(set(tags))

class Record:
    def __init__(self, *, id, text):
        self.id = id
        self.text = text

class Document(JsonMixin, TaggedMixin, Record):
    pass

d = Document(id=7, text="Refund policy", tags=["billing", "faq", "billing"])
print(d.to_json())
print([c.__name__ for c in Document.__mro__])
Output
{"id": 7, "tags": ["billing", "faq"], "text": "Refund policy"}
['Document', 'JsonMixin', 'TaggedMixin', 'Record', 'object']

Calling Document(...) runs the first __init__ found in the MRO, TaggedMixin.__init__, which takes tags and forwards id and text to the next class, Record. Keyword-only arguments make this forwarding safe. Mixins are how frameworks compose behaviour: Django's class-based views, scikit-learn's ClassifierMixin and TransformerMixin (which add score and fit_transform), and socketserver.ThreadingMixIn. Deep or tangled multiple inheritance, with state in several bases, is hard to reason about; keep mixins small and focused.

6Two specialised tools: __init_subclass__ and subclassing built-ins

A base class can react whenever a subclass is defined, by defining the class method __init_subclass__(cls, **kwargs). Python calls it at class-creation time with the new subclass. It is the class-based version of registration decorators (8.4): a plugin base class can register every subclass automatically, validate that subclasses define required attributes, or accept keyword arguments in the class line, class EchoProvider(Provider, name="echo"): (problem 13).

init_subclass.py
class Provider:
    registry = {}

    def __init_subclass__(cls, *, name, **kwargs):
        super().__init_subclass__(**kwargs)
        if name in Provider.registry:
            raise ValueError(f"duplicate provider {name!r}")
        cls.name = name
        Provider.registry[name] = cls

    def complete(self, prompt):
        raise NotImplementedError

class Echo(Provider, name="echo"):
    def complete(self, prompt):
        return prompt

class Shout(Provider, name="shout"):
    def complete(self, prompt):
        return prompt.upper()

print(sorted(Provider.registry), Provider.registry["shout"]().complete("hi"), Echo.name)
Output
['echo', 'shout'] HI echo

Subclassing built-in types needs care. A subclass of dict that overrides __setitem__ (to lower-case keys, say) does not affect dict.__init__, update or setdefault, because the C implementation of those methods does not call your __setitem__. The object then holds keys that bypassed your rule (problem 6). The collections module offers UserDict, UserList and UserString, written in Python precisely so that every operation goes through the methods you override.

builtin_subclass.py
from collections import UserDict

class LowerDict(dict):
    def __setitem__(self, key, value):
        super().__setitem__(key.lower(), value)

class LowerUserDict(UserDict):
    def __setitem__(self, key, value):
        super().__setitem__(key.lower(), value)

a = LowerDict({"Model": "small"})
a.update({"TEMP": 0.2})
a["Seed"] = 1
b = LowerUserDict({"Model": "small"})
b.update({"TEMP": 0.2})
b["Seed"] = 1
print(sorted(a), sorted(b))
Output
['Model', 'TEMP', 'seed'] ['model', 'seed', 'temp']

7When not to inherit

Inheritance couples the subclass tightly to the base: every change to the base's internals can break subclasses, subclasses depend on which methods the base calls internally, and deep hierarchies make it hard to see where a method comes from. Use it when there is a genuine "is a" relationship, a shared contract, and the base was designed for extension (it documents which methods to override). Typical good uses: exception hierarchies (7.2), a framework's base classes (nn.Module, BaseEstimator, a provider base), and mixins.

Prefer composition, holding another object and calling it, when you want to reuse code without promising the whole interface, when the relationship is "has a" or "uses a" (a chat session has a client; a cached retriever uses a retriever), or when the behaviour should be swappable at run time. Lesson 9.5 shows composition and protocols, which most modern Python code prefers for flexibility. A useful smell test: if you are overriding methods to make them raise or do nothing, inheritance is the wrong tool.

solution.py
class Retriever:
    def __init__(self, docs):
        self.docs = list(docs)

    def score(self, query, doc):
        raise NotImplementedError(f"{type(self).__name__} must implement score()")

    def retrieve(self, query, k=3):
        scored = [(self.score(query, d), d) for d in self.docs]
        ranked = sorted((pair for pair in scored if pair[0] > 0), key=lambda p: p[0], reverse=True)
        return [d for _, d in ranked[:k]]


class OverlapRetriever(Retriever):
    def score(self, query, doc):
        return len(set(query.lower().split()) & set(doc.lower().split()))


class PrefixRetriever(Retriever):
    def score(self, query, doc):
        return int(doc.lower().startswith(query.lower()))

The base owns the algorithm (score, filter, sort, cut), and each subclass supplies only the step that differs. Adding a third strategy means writing one small method. The base's score raises NotImplementedError with the subclass's name, so forgetting to override it fails loudly with a clear message; 9.5 shows how an abstract base class turns this into an error at instantiation. Scoring each document once matters when scoring is expensive (an embedding call), which is also why the scores are computed before sorting rather than inside the sort key.

solution.py
class Client:
    def __init__(self, model, timeout=30):
        self.model = model
        self.timeout = timeout

    def ask(self, prompt):
        return f"[{self.model}, {self.timeout}s] {prompt}"

class StreamingClient(Client):
    def __init__(self, model, buffer_size=64, timeout=30):
        super().__init__(model, timeout)
        self.buffer_size = buffer_size

    def ask(self, prompt):
        return super().ask(prompt) + f" (streamed in {self.buffer_size}-char chunks)"

Python does not call a base __init__ automatically when the subclass has its own; the subclass's __init__ is simply found first in the MRO and runs alone. So model and timeout were never set, and the error appeared only when an inherited method used them. super().__init__(...) runs the base's setup on the same instance. Calling it first is the usual order, so the subclass can rely on the base's attributes; occasionally a subclass must prepare something before, which is fine as long as it calls it at all.

solution.py
class Provider:
    def __init__(self, model):
        self.model = model
        self.calls = 0

    def complete(self, prompt):
        prompt = prompt.strip()
        if not prompt:
            raise ValueError("prompt must not be empty")
        text = self._call(prompt).strip()
        self.calls += 1
        return {"model": self.model, "text": text}

    def _call(self, prompt):
        raise NotImplementedError(f"{type(self).__name__} must implement _call()")


class EchoProvider(Provider):
    def _call(self, prompt):
        return prompt


class ReverseProvider(Provider):
    def _call(self, prompt):
        return " ".join(reversed(prompt.split()))

The public method is defined once and handles everything that must be the same for every provider (validation, counting, the result shape); subclasses implement only the one step that differs. The underscore on _call marks it as a hook for subclasses, not part of the public interface, so callers always go through complete and its rules. Real client libraries use this split: LangChain's chat models implement _generate while the base class handles callbacks, retries and output formatting; adding a new provider means implementing one method. Rejected prompts never reach _call or the counter.

solution.py
from collections import UserDict

class CaseInsensitiveHeaders(UserDict):
    def __setitem__(self, key, value):
        self.data[key.lower()] = value

    def __getitem__(self, key):
        return self.data[key.lower()]

    def __contains__(self, key):
        return key.lower() in self.data

dict's constructor and update are implemented in C and write directly into the hash table, so they never call a subclass's __setitem__; the rule "keys are lower-cased" held only for one way of adding data, which is the worst kind of invariant. UserDict is a plain Python class that stores the real dict in self.data and implements every method in terms of a few core ones, so overriding __setitem__, __getitem__ and __contains__ covers construction, update, get and in. HTTP headers are a real case: requests uses a similar case-insensitive mapping, because header names are case-insensitive by the HTTP standard.

solution.py
class Metric:
    name = "metric"

    def update(self, y_true, y_pred):
        if len(y_true) != len(y_pred):
            raise ValueError(f"length mismatch: {len(y_true)} vs {len(y_pred)}")
        self._update(y_true, y_pred)

    def _update(self, y_true, y_pred):
        raise NotImplementedError

    def compute(self):
        raise NotImplementedError

    def reset(self):
        self.__init__()


class Accuracy(Metric):
    name = "accuracy"

    def __init__(self):
        self.correct = 0
        self.total = 0

    def _update(self, y_true, y_pred):
        self.correct += sum(t == p for t, p in zip(y_true, y_pred))
        self.total += len(y_true)

    def compute(self):
        return self.correct / self.total if self.total else 0.0


class MeanAbsoluteError(Metric):
    name = "mae"

    def __init__(self):
        self.error = 0.0
        self.total = 0

    def _update(self, y_true, y_pred):
        self.error += sum(abs(t - p) for t, p in zip(y_true, y_pred))
        self.total += len(y_true)

    def compute(self):
        return self.error / self.total if self.total else 0.0


def evaluate(metrics, batches):
    for m in metrics:
        m.reset()
        for y_true, y_pred in batches:
            m.update(y_true, y_pred)
    return {m.name: round(m.compute(), 4) for m in metrics}

Every metric follows the same contract, so evaluate works with any of them, and with metrics not written yet: that is the payoff of a shared base. Validation lives once in the base's update; subclasses implement only accumulation and the final formula. Metrics that accumulate across batches (rather than averaging per-batch values) give the exact result for the whole dataset, which matters when batches have different sizes. reset reusing __init__ keeps the initial state defined in one place. torchmetrics and Keras metrics use this exact update/compute/reset design.

solution.py
class Chunker:
    def chunk(self, text, size):
        return [text[i:i + size] for i in range(0, len(text), size)]

    def chunk_all(self, texts, size=40):
        return [c for t in texts for c in self.chunk(t, size)]

class SentenceChunker(Chunker):
    def chunk(self, text, size):
        sentences = [s.strip() for s in text.split(". ") if s.strip()]
        chunks, current = [], ""
        for s in sentences:
            candidate = f"{current}. {s}" if current else s
            if current and len(candidate) > size:
                chunks.append(current)
                current = s
            else:
                current = candidate
        if current:
            chunks.append(current)
        return chunks

The base class's chunk_all is written against the base contract, chunk(text, size); any subclass must accept those arguments, or the base's own code breaks for it, which is the substitution rule in practice. Accepting size and using it keeps the meaning too: a chunk never exceeds the limit unless a single sentence is longer than it, in which case it stays whole (the second test), a deliberate choice for sentence-based chunking. This is exactly how LangChain-style text splitters are organised: one base interface, several strategies.

        self.rows_written = 0

class TimestampMixin:
    def __init__(self, *, created_at=0.0, **kwargs):
        self.created_at = created_at
        super().__init__(**kwargs)

class ValidateMixin:
    def __init__(self, **kwargs):
        super().__init__(**kwargs)
        problems = self.validate()
        if problems:
            raise ValueError("; ".join(problems))

    def validate(self):
        return []

class Record:
    def __init__(self, *, id, text):
        self.id = id
        self.text = text

    def to_dict(self):
        return dict(vars(self))

class Note(TimestampMixin, ValidateMixin, Record):
    def validate(self):
        problems = []
        if not self.text.strip():
            problems.append("empty text")
        if isinstance(self.id, bool) or not isinstance(self.id, int) or self.id <= 0:
            problems.append("bad id")
        return problems

Note(...) runs TimestampMixin.__init__ first (the start of the MRO), which takes created_at and passes the rest along; ValidateMixin passes everything on to Record, which sets the fields; control then returns to ValidateMixin, which can now validate a complete object. Each class handles only its own keyword arguments, and none of them needs to know which classes come next: that is cooperative multiple inheritance. validate is a hook with a harmless default, overridden by Note, and collecting all problems before raising gives a complete error message (7.2). Keyword-only arguments are essential here, since positional arguments cannot be safely forwarded through a chain whose order depends on the final class.

class Tool:
    registry = {}

    def __init_subclass__(cls, *, name, **kwargs):
        super().__init_subclass__(**kwargs)
        if name in Tool.registry:
            raise ValueError(f"tool {name!r} is already registered by {Tool.registry[name].__name__}")
        if cls.run is Tool.run:
            raise TypeError(f"{cls.__name__} must implement run()")
        cls.name = name
        Tool.registry[name] = cls

    def __init__(self, **config):
        self.config = config

    def run(self, *args, **kwargs):
        raise NotImplementedError

    @classmethod
    def create(cls, name, **config):
        return cls.registry[name](**config)

__init_subclass__ runs when each class statement finishes, so registration and checks happen at import time, like the registration decorators of 8.4 but without a decorator line: subclassing is registering. The registry is a class attribute of the base on purpose: shared by all subclasses, which is the one case where a mutable class attribute is the design (always written as Tool.registry, never through self). create builds instances by name, the way configuration files select a component.

solution.py
import json


class BaseLoader:
    def __init__(self, encoding="utf-8"):
        self.encoding = encoding
        self.loaded = []

    def read(self, path, files):
        return files[path]

    def load(self, path, files):
        return [(path, self.read(path, files))]

    def load_all(self, paths, files):
        docs = []
        for p in paths:
            docs.extend(self.load(p, files))
            self.loaded.append(p)
        return docs


class JsonLoader(BaseLoader):
    def load(self, path, files):
        data = json.loads(self.read(path, files))
        return [(path, item["text"]) for item in data]


class TextLoader(BaseLoader):
    def __init__(self, strip=True, encoding="utf-8"):
        super().__init__(encoding)
        self.strip = strip

    def read(self, path, files):
        text = super().read(path, files)
        return text.strip() if self.strip else text

Three bugs, all about the base-subclass relationship. loaded = [] on the base class was one list shared by every loader of every subclass (9.1), so each loader's history included the others'; it belongs in __init__. TextLoader.__init__ replaced the base's without calling it, so encoding (and, after the first fix, loaded) never existed; calling super().__init__(encoding) and accepting encoding as a parameter keeps the subclass substitutable. And JsonLoader.load returned a joined string where the base contract promises a list of documents: load_all then extended the result list with individual characters, a silent corruption that a substitution check catches immediately. Returning one (source, text) tuple per JSON item honours the contract and keeps each item a separate document for retrieval.

solution.py
class Retriever:
    def __init__(self, docs):
        self.docs = list(docs)
        self.searches = 0

    def add(self, doc):
        self.docs.append(doc)

    def retrieve(self, query, k=2):
        self.searches += 1
        words = set(query.lower().split())
        scored = [(len(words & set(d.lower().split())), d) for d in self.docs]
        return [d for s, d in sorted(scored, key=lambda p: -p[0]) if s > 0][:k]


class CachingRetriever(Retriever):
    def __init__(self, docs, max_entries=128):
        super().__init__(docs)
        self.max_entries = max_entries
        self._cache = {}
        self.hits = 0
        self.misses = 0

    def retrieve(self, query, k=2):
        key = (" ".join(query.lower().split()), k)
        if key in self._cache:
            self.hits += 1
            return list(self._cache[key])
        self.misses += 1
        result = super().retrieve(query, k)
        if len(self._cache) >= self.max_entries:
            del self._cache[next(iter(self._cache))]
        self._cache[key] = list(result)
        return list(result)

    def add(self, doc):
        super().add(doc)
        self._cache.clear()

The subclass extends two methods with super(): retrieve adds a cache around the base's search, and add adds invalidation after the base's update, so a new document is visible immediately. Because it overrides methods with the same signatures and results, a CachingRetriever can replace a Retriever anywhere. Copies on the way in and out protect the cache from callers modifying lists (the junk test). The counters show the cache working: only misses reach super().retrieve, which increments the base's searches. The same behaviour could be built by composition, a CachedRetriever that holds any retriever and wraps it, which works for every retriever class at once; 9.5 compares the two.

17. What does super() do, and what is the MRO?

SolutionModel answer

The method resolution order is the sequence of classes Python searches for an attribute: the class itself, then its bases in an order computed by the C3 linearisation algorithm, ending with object; Class.__mro__ shows it. C3 guarantees each class comes before its bases, the written order of bases is respected, and each class appears once. super().method() calls the version of method in the next class after the current one in the MRO of the instance's actual class, not necessarily the current class's parent. With single inheritance those are the same; with multiple inheritance, it lets every class in a diamond run exactly once in a defined order, provided every method calls super() and passes along arguments it does not use, usually via keyword arguments. The most common use is extending __init__: a subclass that defines __init__ must call super().__init__(...), or the base's setup never runs.

Interview

18. Inheritance versus composition: when do you use each?

SolutionModel answer

Inheritance models "is a": the subclass promises the whole interface of the base and can be substituted for it everywhere, reusing its code and overriding parts. It fits exception hierarchies, framework base classes designed for extension (template methods with documented hooks) and small mixins. Its cost is tight coupling: subclasses depend on the base's internals, deep hierarchies obscure where behaviour comes from, and violating the base's contract breaks code that uses the base. Composition models "has a" or "uses a": an object holds another and delegates to it, so components can be swapped at run time, tested separately with fakes, and combined freely (a retriever wrapped by a cache, a client with a retry policy). Prefer composition by default, and inherit when there is a genuine substitutable relationship or a framework requires it. Overriding methods to disable them is a sign inheritance was wrong.

19. Design a class hierarchy for supporting several LLM providers. What pitfalls would you avoid?

SolutionModel answer

Define a small base contract (an abstract base class or a protocol, 9.5) with one public method such as complete(messages, **params) returning a provider-neutral response object, and put shared behaviour in the base: input validation, retries and timeouts, usage accounting, tracing. Each provider subclass implements one protected hook that translates to its API and back, and maps its SDK's errors into your exception hierarchy (7.2). Register providers by name (__init_subclass__ or a decorator) so configuration can pick one. Pitfalls: subclasses that change the public method's signature or return provider-specific types, which breaks substitutability; forgetting super().__init__; mutable class attributes shared across providers; deep hierarchies built per model version instead of configuration; putting provider-specific features in the base. Often composition is better for cross-cutting features (wrap any provider with a caching or fallback layer) than adding them as subclasses, so the hierarchy stays one level deep.

Recap

  • class Child(Base) inherits everything; lookup searches instance, class, then bases (the MRO). Overrides win because the subclass is searched first.
  • Template method: the base defines the algorithm and calls hooks (self.score); subclasses override only the hooks.
  • A subclass __init__ must call super().__init__(...). super() calls the next class in the instance's MRO, which makes cooperative multiple inheritance work.
  • Honour the base contract (same arguments, same kind of result): substitutability is the point of inheritance.
  • Mixins and __init_subclass__ are the specialised tools; subclass UserDict rather than dict; prefer composition when there is no real "is a".
