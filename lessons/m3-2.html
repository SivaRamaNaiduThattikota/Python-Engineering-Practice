3.2 Flexible arguments

*args, **kwargs, keyword-only and positional-only parameters, and unpacking at the call site: what each one does step by step, why they exist, and the real bugs they cause and prevent in LLM clients, wrappers and config code.

1The five kinds of parameters

A signature can contain up to five kinds of parameters, always in this order. Each kind answers one question: how may a caller pass this value?

Here is one signature using all five, so you can see the order rule in action. It is the shape of a small database helper: the SQL text first, optional parameters, any extra statements, a timeout that must be named, and driver options passed through untouched:

five_kinds.py
def run_query(sql, /, params=None, *more_sql, timeout=30, **driver_opts):
    return {"sql": sql, "params": params, "more_sql": more_sql,
            "timeout": timeout, "driver_opts": driver_opts}

print(run_query("SELECT 1"))
print(run_query("SELECT 1", {"id": 7}, "SELECT 2", timeout=5, fetch_size=500))
Output
{'sql': 'SELECT 1', 'params': None, 'more_sql': (), 'timeout': 30, 'driver_opts': {}}
{'sql': 'SELECT 1', 'params': {'id': 7}, 'more_sql': ('SELECT 2',), 'timeout': 5, 'driver_opts': {'fetch_size': 500}}

Walk through the second call with the algorithm from 3.1. Positional arguments fill left to right: "SELECT 1" goes to sql, {"id": 7} to params, and "SELECT 2", the extra one, is collected into the tuple more_sql. Then keywords by name: timeout=5 fills the keyword-only timeout, and fetch_size=500 matches no parameter, so it is collected into the dict driver_opts. Anything after *more_sql can only be reached by name, which is why timeout is safe from being filled by accident. In practice you rarely use all five in one function, but every signature you meet in a library is some subset of this table.

2*args: collecting extra positional arguments

A parameter written *name (by convention *args) collects every positional argument that no earlier parameter took. Step by step, on every call Python builds a new tuple from the leftover positional arguments and binds the name to it. With no leftovers it is the empty tuple (), never None. Being a tuple, it cannot be changed, but its items are the caller's own objects (2.4).

star_args.py
def merge_tags(*tag_lists):
    print("received:", tag_lists)
    merged = []
    for tags in tag_lists:
        for t in tags:
            if t not in merged:
                merged.append(t)
    return merged

print(merge_tags(["faq", "billing"], ["billing", "eu"], ["faq"]))
print(merge_tags())
groups = [["a"], ["b", "a"]]
print(merge_tags(groups))      # one argument: a list of lists
print(merge_tags(*groups))     # spread: two arguments
Output
received: (['faq', 'billing'], ['billing', 'eu'], ['faq'])
['faq', 'billing', 'eu']
received: ()
[]
received: ([['a'], ['b', 'a']],)
[['a'], ['b', 'a']]
received: (['a'], ['b', 'a'])
['a', 'b']

The last two calls show the most common *args mistake. merge_tags(groups) passes one argument, a list that contains lists, so tag_lists is a tuple holding that one list and the loop sees the inner lists as "tags". merge_tags(*groups) spreads the list, so each inner list becomes its own argument. When a function takes *args and you already have the values in a list, you almost always want the * at the call.

•
When *args is the right design

Use *args when "any number of the same kind of thing" is the natural way to call the function: print(a, b, c), max(x, y, z), os.path.join("a", "b", "c"), merge_tags(t1, t2). If callers will usually have a list already, take the list as one normal parameter instead. It is simpler, and it does not copy a large list into a tuple on every call (problem 8).

3**kwargs: collecting extra keyword arguments

A parameter written **name (by convention **kwargs) collects every keyword argument that did not match a named parameter. On each call Python builds a new dict from those leftovers, with the keys in the order the caller wrote them, and binds the name to it. With no leftovers it is an empty dict. Because it is a new dict, the function may add or remove keys freely without affecting the caller; the values are still the caller's objects.

star_kwargs.py
def make_request(prompt, **params):
    params.setdefault("temperature", 0.2)     # changes only this call's dict
    return {"prompt": prompt, **params}

settings = {"max_tokens": 256, "stop": ["###"]}
print(make_request("hi"))
print(make_request("hi", **settings, top_p=0.9))
print(settings)                               # untouched: params was a new dict
Output
{'prompt': 'hi', 'temperature': 0.2}
{'prompt': 'hi', 'max_tokens': 256, 'stop': ['###'], 'top_p': 0.9, 'temperature': 0.2}
{'max_tokens': 256, 'stop': ['###']}

Two rules limit what can go into **kwargs. Keys must be strings, because they become parameter names. And a key can never be the name of another parameter of the same function, because then it would not be "extra": Python would try to give that parameter two values. The second rule causes a real bug, shown in the next section.

!
The cost of **kwargs

**kwargs makes a function accept anything, which also means typos are accepted silently: make_request("hi", temprature=0.9) sends a misspelled key to the API instead of failing in your code. Use it where you truly pass options through to other code (an SDK, a driver, a model constructor). For your own options, prefer named keyword-only parameters, which catch typos at the call.

4Why * and / exist

A bare * in a signature collects nothing: it only marks every parameter after it as keyword-only. The main reason is the boolean trap. A call like train(X, y, True, False) is unreadable, and swapping the two booleans changes behaviour without any error. With keyword-only flags, the call must say train(X, y, normalize=True, verbose=False), and the positional version fails immediately.

keyword_only.py
def train(X, y, *, normalize=True, verbose=False):
    return f"normalize={normalize}, verbose={verbose}"

print(train([[1]], [0], verbose=True))
try:
    train([[1]], [0], True, False)
except TypeError as e:
    print("TypeError:", e)
Output
normalize=True, verbose=True
TypeError: train() takes 2 positional arguments but 4 were given

A / marks every parameter before it as positional-only: callers cannot use its name. That sounds like a restriction, but it solves a real problem: a function with **kwargs cannot accept a key that is also the name of one of its parameters. Step by step: Python fills name from the first positional argument, then meets the keyword name=... from the dict and tries to fill name again, which is the "multiple values" error. Making name positional-only takes it out of the keyword namespace, so **fields can receive a name key.

positional_only.py
def tag_v1(name, **fields):
    return name, fields

def tag_v2(name, /, **fields):       # name can only be passed by position
    return name, fields

row = {"name": "Ana", "tier": "gold"}
try:
    tag_v1("customer", **row)
except TypeError as e:
    print("TypeError:", e)
print(tag_v2("customer", **row))
Output
TypeError: tag_v1() got multiple values for argument 'name'
('customer', {'name': 'Ana', 'tier': 'gold'})

Positional-only parameters also let a library rename a parameter later without breaking anyone, because no caller can have used the name. Many built-ins are positional-only for that reason: you cannot write len(obj=x).

5Unpacking at the call site

The same symbols work in the opposite direction in a call. f(*seq) spreads any iterable into separate positional arguments; f(**mapping) spreads a dict into keyword arguments. You can use several of each, mixed with normal arguments, and Python processes them left to right with the same matching algorithm as always.

unpacking.py
def connect(host, port, *, user, timeout=10):
    return f"{user}@{host}:{port} (timeout {timeout})"

addr = ["db.local", 1521]
base = {"user": "etl"}
print(connect(*addr, **base))
print(connect(*addr, **base, timeout=3))

defaults = {"user": "etl", "timeout": 10}
override = {"timeout": 3}
try:
    connect(*addr, **defaults, **override)
except TypeError as e:
    print("TypeError:", e)
print(connect(*addr, **(defaults | override)))
Output
etl@db.local:1521 (timeout 10)
etl@db.local:1521 (timeout 3)
TypeError: __main__.connect() got multiple values for keyword argument 'timeout'
etl@db.local:1521 (timeout 3)

The TypeError is worth understanding. In a call, **defaults, **override are spread one after the other, and each key becomes a keyword argument; a key that appears in both is the same keyword given twice, which Python refuses with "got multiple values for keyword argument". In a dict display, {**defaults, **override} (or defaults | override), a repeated key is allowed and the later value wins. So when you mean "defaults, then overrides", merge first into one dict and spread that dict once.

6Forwarding: wrappers that accept anything

Collecting and spreading combine into the forwarding pattern: accept *args, **kwargs and pass them on unchanged with fn(*args, **kwargs). A wrapper written this way works for any function, whatever its signature, which is how retry helpers, timers, caches, loggers and decorators (Module 7) are built.

forwarding.py
import time

def timed(fn, *args, **kwargs):
    start = time.perf_counter()
    result = fn(*args, **kwargs)         # forward exactly what was given
    elapsed = time.perf_counter() - start
    print(f"{fn.__name__} took {'under' if elapsed < 0.1 else 'over'} 0.1 s")
    return result

def embed(texts, *, model="small"):
    return [len(t) for t in texts]

print(timed(embed, ["a", "bcd"], model="large"))
print(timed(sorted, [3, 1, 2], reverse=True))
Output
embed took under 0.1 s
[1, 3]
sorted took under 0.1 s
[3, 2, 1]

Forwarding has two costs to know about. First, a parameter of the wrapper itself (here fn) can collide with a keyword the wrapped function needs: timed(f, fn=3) gives timed two values for fn. Making the wrapper's own parameters positional-only (def timed(fn, /, *args, **kwargs)) avoids that. Second, *args, **kwargs hides the real signature from editors, type checkers and frameworks that read signatures (3.1). Decorators fix the second problem with functools.wraps (Module 7), and type checkers with ParamSpec (Module 11).

In a call, the same keyword twice is an error. In a dict display, the later key wins.

solution.py
BASE = {"model": "small", "temperature": 0.2}

SolutionShow the solution and why
solution.py
def with_retry(fn, /, *args, attempts=3, retry_on=(ValueError,), **kwargs):
    last = None
    for _ in range(attempts):
        try:
            return fn(*args, **kwargs)
        except retry_on as e:
            last = e
    raise last

The signature does the hard work. fn is positional-only, so the wrapped function can have its own keyword called fn (the second test) and it is forwarded instead of colliding. attempts and retry_on sit after *args, so they are keyword-only and can never swallow one of the wrapped function's positional arguments. Everything else is forwarded untouched with fn(*args, **kwargs). The remaining collision is real: a wrapped function that itself needs a keyword named attempts cannot get it through this wrapper, which is why libraries like tenacity configure retries in a decorator instead of in the call.

solution.py
LOG = []
SECRET_KEYS = {"api_key", "authorization"}


def traced(fn, /, *args, **kwargs):
    shown = {k: ("***" if k in SECRET_KEYS else v) for k, v in kwargs.items()}
    LOG.append(f"call {fn.__name__} args={args} kwargs={shown}")
    result = fn(*args, **kwargs)
    LOG.append(f"done {fn.__name__}")
    return result


def complete(prompt, *, model="small", api_key):
    return f"{model} answered {prompt!r} (key ends {api_key[-4:]})"

fn(args, kwargs) passes the tuple as the first positional argument and the dict as the second, so complete gets prompt=("hi",) and complains about a missing api_key: forwarding needs the stars, fn(*args, **kwargs). The log leak is the more serious bug. The fix builds a separate redacted dict for logging; deleting the key from kwargs would also hide it from the log, but then the real call would fail. Secrets in logs are a common finding in LLM application reviews, because tracing wrappers like this one log every argument by default. A real version would also redact secrets inside positional arguments and nested values, and would use the logging module (Module 12).

import inspect

def bind(fn, *args, **kwargs):
    bound = inspect.signature(fn).bind(*args, **kwargs)
    bound.apply_defaults()
    return dict(bound.arguments)

Signature.bind runs the same matching algorithm Python uses for a real call (positional, then keywords, then the *args and **kwargs collectors) and raises the same kind of TypeError for a bad call, but without running the function. apply_defaults then fills the defaults, including () for *more and {} for **opts. This is how caching decorators build a key that treats f(1, b=2) and f(1, 2) as the same call, and how validation layers check a tool call from an LLM before executing it. Knowing the matching rules well enough to predict this table is also a frequent interview question.

SolutionShow the solution and why
solution.py
import inspect

def to_value(text, default):
    if isinstance(default, bool):
        if text.lower() in {"true", "1"}:
            return True
        if text.lower() in {"false", "0"}:
            return False
        raise ValueError(f"not a boolean: {text!r}")
    if isinstance(default, (int, float)):
        return type(default)(text)
    return text

def call_from_strings(fn, pairs):
    params = inspect.signature(fn).parameters
    kwargs = {}
    for pair in pairs:
        name, value = pair.split("=", 1)
        param = params.get(name)
        default = param.default if param is not None else inspect.Parameter.empty
        kwargs[name] = value if default is inspect.Parameter.empty else to_value(value, default)
    return fn(**kwargs)

This is a tiny version of what Typer and Click do: they read the signature (3.1) and turn strings into typed keyword arguments. Three details matter. split("=", 1) keeps any later = in the value. The bool check comes before the int check, because bool is a subclass of int (1.1), and bool("false") would be True, so booleans need their own parsing. And unknown names are passed through unconverted, so the normal call raises the usual TypeError instead of the helper inventing its own error. Building on **kwargs and the signature means the same helper works for any function.

16. What do / and * mean in a function signature, and why would you use each?

SolutionModel answer

Parameters before / are positional-only: callers cannot pass them by name. Parameters after * (or after *args) are keyword-only: callers must pass them by name. Use * for options and especially boolean flags, so calls are readable and arguments cannot be swapped silently (the boolean trap); scikit-learn made most estimator options keyword-only for this reason. Use / when a function also takes **kwargs and must accept keys that match its own parameter names (PEP 570's motivating case), or when you want freedom to rename a parameter later without breaking callers. Mention that many built-ins are positional-only, which is why len(obj=x) fails.

Interview

17. Why does f(**a, **b) fail when the dicts share a key, and how should you merge settings for a call?

SolutionModel answer

In a call, **a, **b spreads both dicts into keyword arguments one after the other, so a key present in both is the same keyword passed twice, and Python raises "got multiple values for keyword argument". The fix is to merge first into one dict where the later value wins, a | b or {**a, **b}, and spread that once: f(**(a | b)). Being explicit about precedence (defaults, then environment, then per-call overrides) avoids silent surprises, and for nested settings you need a recursive merge (2.3), because | replaces nested dicts wholesale.

Interview

18. What is the downside of a public function with the signature def f(*args, **kwargs)?

SolutionModel answer

It hides the real interface. Editors cannot autocomplete or show the parameters, type checkers cannot check calls, typos in keyword names are accepted silently and fail later (or never, if the value is just passed on), the docs and help() say nothing, and frameworks that read signatures (FastAPI, Typer, agent tool builders) cannot use it. Errors appear deep inside the function instead of at the call. It is fine for forwarding wrappers, which should then restore the wrapped function's metadata with functools.wraps and its types with typing.ParamSpec, or for true pass-through of options to another API, ideally after validating them. For your own public functions, name the parameters and make options keyword-only.

Recap

  • Five kinds, in order: positional-only (/), normal, *args, keyword-only, **kwargs. Each answers "how may a caller pass this?"
  • *args is a new tuple and **kwargs a new dict on every call. Their values are still the caller's objects.
  • Use * to make options and flags keyword-only (the boolean trap), and / when **kwargs must accept your own parameter names.
  • In a call, * and ** spread. A repeated keyword is an error, so merge settings first (a | b) and spread once.
  • Forwarding with *args, **kwargs makes generic wrappers, at the cost of hiding the signature. Keep the wrapper's own parameters positional-only or keyword-only.
