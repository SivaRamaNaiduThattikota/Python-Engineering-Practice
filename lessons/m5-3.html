5.3 f-strings and formatting

How f-strings evaluate, the format-spec mini-language part by part (width, alignment, precision, separators, types), how formatting rounds, dates, the other formatting tools and when each is right, and why logs should not use f-strings.

19 problems4 easy · 10 medium · 5 hard

1f-strings: expressions inside text

An f-string is a string literal with an f prefix. Each {...} field holds a Python expression: a name, an arithmetic expression, a function call, an index, a conditional expression. Step by step, when the line runs, Python evaluates each expression, converts the result to text (by calling format(value, spec), which usually means str), and joins the pieces. It happens every time the line runs, and only then: an f-string is not a template that can be filled later (problem 12).

fstring_basics.py
model, tokens, price = "small", 1234, 0.15
print(f"{model} used {tokens} tokens costing ${tokens * price / 1000:.4f}")
docs = [{"id": "faq"}, {"id": "terms"}]
print(f"top doc: {docs[0]['id']}, total {len(docs)}, {'ok' if tokens < 4000 else 'too long'}")
print(f"{{literal braces}} and a value: {tokens}")
Output
small used 1234 tokens costing $0.1851
top doc: faq, total 2, ok
{literal braces} and a value: 1234

To put a literal { or } in an f-string, double it: {{ and }}. That matters for prompts that contain JSON examples (problem 3). Since Python 3.12 you can also reuse the same quote character inside a field (f"{d["id"]}"), but code that must run on older versions should use the other quote type.

Two field features are especially useful. A conversion !r formats repr(value) instead of str(value), which shows quotes and escape characters, so stray spaces and newlines become visible in logs (5.1). And the = specifier (f"{x=}") prints the expression's text, an equals sign and its value: the fastest debugging print there is.

debug_specifier.py
label = "spam "
print(f"[{label}]", f"[{label!r}]")
tokens, limit = 4200, 4096
print(f"{tokens=}, {limit=}, {tokens > limit=}")
print(f"{tokens / limit = :.2f}")
Output
[spam ] ['spam ']
tokens=4200, limit=4096, tokens > limit=True
tokens / limit = 1.03

2The format spec, part by part

After the colon in a field comes the format spec, a small language with a fixed order: [[fill]align][sign][#][0][width][grouping][.precision][type]. Every part is optional. Reading a spec left to right:

PartExamplesMeaning
fill + align< > ^, *^left, right, centre; an optional fill character before the alignment
sign+, -, spacealways show the sign; only for negatives (default); a space for positives
width10, 08minimum total width; a leading 0 pads numbers with zeros after the sign
grouping, _thousands separators
precision.2digits after the point (f, %, e), significant digits (g), or maximum length for strings
typef e g % d x b sfixed point, exponent, general, percentage, integer, hex, binary, string
format_spec.py
x = 1234567.891
print(f"[{x:,.2f}] [{x:_.0f}] [{x:.3e}] [{x:.3g}]")
print(f"[{0.4567:.1%}] [{-3:05d}] [{42:+d}] [{255:#x}] [{5:08b}]")
print(f"[{'left':<10}] [{'right':>10}] [{'mid':^10}] [{'mid':*^10}]")
print(f"[{'a long description':.8}] [{'cut':>6.2}]")
width = 12
print(f"[{x:>{width},.1f}]")       # a nested field supplies part of the spec
Output
[1,234,567.89] [1_234_568] [1.235e+06] [1.23e+06]
[45.7%] [-0003] [+42] [0xff] [00000101]
[left      ] [     right] [   mid    ] [***mid****]
[a long d] [    cu]
[ 1,234,567.9]

A few rules worth remembering. Numbers right-align by default and strings left-align. Width is a minimum: a value longer than the width is never cut, except strings with a precision (.8 keeps the first 8 characters). The g type picks fixed or exponent notation depending on the size and drops trailing zeros. A nested {width} inside the spec lets you compute alignment at run time, which is how aligned tables of unknown widths are built (problem 14).

≈
SQL / Power BI

The format spec is Python's version of Excel and Power BI format strings: :,.2f is #,##0.00, :.1% is 0.0%, :08d is 00000000. Like those, formatting changes only the text, never the stored value, so format at the very end, in the report, not in the data.

3How formatting rounds

Precision rounds (it never truncates), and it rounds the exact binary value of the float, with ties to even. So formatting shows the same surprises as round in 1.1: 2.675 is stored as 2.67499999..., so f"{2.675:.2f}" is "2.67", and exact halves like 0.5 and 2.5 go to the even neighbour. For displaying measurements this is fine. For money, where a report must match an accounting system to the cent, round with Decimal first (1.1, problem 12) and then format.

rounding.py
from decimal import Decimal, ROUND_HALF_UP

print(f"{2.675:.2f} {0.5:.0f} {1.5:.0f} {2.5:.0f}")
amount = Decimal("2.675").quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)
print(f"{amount}", f"{amount:,.2f}", f"{Decimal('1234567.5'):,.2f}")
print(f"{0.1 + 0.2}", f"{0.1 + 0.2:.2f}", f"{1e-7:.3f}", f"{1e-7:.3g}")
Output
2.67 0 2 2
2.68 2.68 1,234,567.50
0.30000000000000004 0.30 0.000 1e-07

The last line shows two more things: formatting is the right way to hide float noise (0.30000000000000004 displays as 0.30), and fixed-point formatting of a tiny number can show 0.000 and hide that it is not zero, where g or e keeps the information. Pick f for amounts and percentages of normal size, g or e for values that span many magnitudes, such as learning rates and p-values.

4Dates and times

datetime objects have their own format codes, the same as strftime, and an f-string field passes them through: f"{dt:%Y-%m-%d %H:%M}". For machine-readable text (logs, APIs, file names that must sort), use ISO 8601, dt.isoformat(), which sorts correctly as text and includes the time zone offset when the datetime has one. Never build dates by concatenating numbers: f"{d.year}-{d.month}-{d.day}" gives 2025-6-1, which neither sorts nor parses reliably.

dates.py
from datetime import datetime, timezone

dt = datetime(2025, 6, 1, 9, 5, 7, tzinfo=timezone.utc)
print(f"{dt:%Y-%m-%d %H:%M:%S}", f"{dt:%d %b %Y}", f"{dt:%A}")
print(dt.isoformat(), f"{dt.year}-{dt.month}-{dt.day}")
print(sorted(["2025-10-01", "2025-9-30", "2025-09-30"]))
Output
2025-06-01 09:05:07 01 Jun 2025 Sunday
2025-06-01T09:05:07+00:00 2025-6-1
['2025-09-30', '2025-10-01', '2025-9-30']

5The other formatting tools, and when to use each

Python has four ways to put values into text. They overlap, but each has a job:

  • f-strings: your own code, values known at that line. Fastest and most readable.
  • str.format / format_map: a template that is defined in one place and filled later, such as a prompt template loaded from a file (template.format_map(values), 5.2). The template must be trusted: format can read attributes of the values.
  • % formatting: mostly legacy, but still the standard for logging, because the logger only builds the message if it will actually be emitted.
  • string.Template: templates written by users or non-programmers. Its $name syntax cannot evaluate expressions or read attributes, and safe_substitute leaves unknown names alone instead of raising.
tools.py
import logging
from string import Template

prompt = "Answer in {lang}: {question}"
print(prompt.format(lang="French", question="Refund time?"))
print("%-8s|%6.2f|%03d" % ("small", 3.14159, 7))

user_tpl = Template("Dear $name, your ticket $ticket is $status.")
print(user_tpl.safe_substitute(name="Ana", ticket="T-42"))

log = logging.getLogger("demo")
log.debug("expensive value: %s", list(range(5)))    # not formatted at all: DEBUG is off
Output
Answer in French: Refund time?
small   |  3.14|007
Dear Ana, your ticket T-42 is $status.
!
Why not log with f-strings

log.debug(f"state: {big_object}") builds the string (calling repr of big_object) even when debug logging is off, every time the line runs. log.debug("state: %s", big_object) passes the value along, and the text is only built if the message is emitted. Log aggregators can also group messages by their unchanged template. In hot paths the difference is large (problem 8).

HintOpen a hint

Loop over the units, dividing while the value is at least 1024 and there is a bigger unit left.

SolutionShow the solution and why
solution.py
def human_size(n):
    if n < 1024:
        return f"{n} B"
    value = n / 1024
    for unit in ["KB", "MB", "GB", "TB"]:
        if value < 1024 or unit == "TB":
            return f"{value:.1f} {unit}"
        value /= 1024

Each pass divides by 1024 and moves to the next unit; the unit == "TB" check stops at the largest unit instead of running out of names. Bytes stay integers, everything else gets one decimal with :.1f. (Strictly, powers of 1024 are KiB, MiB and so on; many tools say KB anyway. Disk vendors use 1000, so pick one and label it.)

5. An aligned metrics report

Write metrics_report(metrics) for a dict from metric name to value. Return lines "<name> <value>" with names left-aligned to the longest name, values right-aligned in a column of width 8: values between 0 and 1 (exclusive of 1 only when the name ends with "_rate") are shown as percentages with one decimal, everything else with three decimals. Keep the dict's order.

TestsThe 2 checks Run tests uses
m = {"precision": 0.8231, "recall": 0.61, "error_rate": 0.0425, "n": 1400}
assert metrics_report(m) == (
    "precision      0.823\n"
    "recall         0.610\n"
    "error_rate      4.2%\n"
    "n           1400.000"
)
assert metrics_report({}) == ""
Hint 1Open a hint

Compute width = max(map(len, metrics)) (guard the empty dict).

Hint 2Open a hint

Choose the spec per value: f"{v:8.1%}" for rates, f"{v:8.3f}" otherwise, and the name with f"{name:<{width}}".

SolutionShow the solution and why
solution.py
def metrics_report(metrics):
    if not metrics:
        return ""
    width = max(map(len, metrics))
    lines = []
    for name, value in metrics.items():
        text = f"{value:8.1%}" if name.endswith("_rate") else f"{value:8.3f}"
        lines.append(f"{name:<{width}}  {text}")
    return "\n".join(lines)

A nested field, {name:<{width}}, computes the alignment from the data, so the report adapts to long metric names. Choosing the presentation by the metric's name, not its value, keeps a rate of 1.0 (100%) consistent with its neighbours. Formatting is the last step: the dict keeps full precision for anything that compares or plots it later.

6. Invoice totals off by a cent

format_total(amounts) should sum line amounts given as strings like "19.99" and print the total with thousands separators and exactly two decimals, rounding half up as the accounting system does. It uses floats and gets some totals wrong by a cent. Fix it.

TestsThe 4 checks Run tests uses
assert format_total(["1.005"]) == "1.01"
assert format_total(["2.675", "0"]) == "2.68"
assert format_total(["1000000.10", "234567.80"]) == "1,234,567.90"
assert format_total([]) == "0.00"
Hint 1Open a hint

Parse with Decimal(a) (from the strings, not from floats), sum, then quantize(Decimal("0.01"), rounding=ROUND_HALF_UP).

Hint 2Open a hint

f-strings format Decimal values with the same ,.2f spec.

SolutionShow the solution and why
solution.py
from decimal import Decimal, ROUND_HALF_UP

def format_total(amounts):
    total = sum((Decimal(a) for a in amounts), Decimal("0"))
    return f"{total.quantize(Decimal('0.01'), rounding=ROUND_HALF_UP):,.2f}"

float("1.005") is stored as 1.00499999..., so formatting rounds it down, and summing floats accumulates further binary error. Decimal built from the strings keeps the exact decimal values, quantize applies the business rounding rule explicitly, and the f-string only adds separators. Starting sum with Decimal("0") avoids mixing an int start value into the arithmetic and makes the empty case 0.00.

def cost_line(tokens_in, tokens_out, price_in, price_out):
    cost = tokens_in / 1_000_000 * price_in + tokens_out / 1_000_000 * price_out

13. A text progress bar

Write progress(done, total, width=20) returning "[########------------] 40.0% (4/10)": # for the done fraction of width (rounded down), - for the rest, then the percentage with one decimal and the counts. Clamp done to the range 0 to total, and show an empty bar at 0.0% when total is 0.

TestsThe 6 checks Run tests uses
assert progress(4, 10) == "[########------------] 40.0% (4/10)"
assert progress(10, 10, width=5) == "[#####] 100.0% (10/10)"
assert progress(15, 10, width=4) == "[####] 100.0% (10/10)"
assert progress(-3, 10, width=4) == "[----] 0.0% (0/10)"
assert progress(0, 0, width=3) == "[---] 0.0% (0/0)"
assert progress(1, 3, width=10) == "[###-------] 33.3% (1/3)"
HintOpen a hint

Clamp with max(0, min(done, total)), compute fraction = done / total if total else 0.0, then filled = int(fraction * width).

SolutionShow the solution and why
solution.py
def progress(done, total, width=20):
    done = max(0, min(done, total))
    fraction = done / total if total else 0.0
    filled = int(fraction * width)
    bar = "#" * filled + "-" * (width - filled)
    return f"[{bar}] {fraction:.1%} ({done}/{total})"

Clamping first means every later step can trust its input (a guard clause, 3.1). int(...) rounds the filled length down, so the bar is only full at exactly 100%; with round, 97.5% would already look complete. :.1% formats the fraction directly. Libraries such as tqdm do this (plus rates and time estimates) for training loops and batch jobs.

Hint 2Open a hint

SolutionShow the solution and why
solution.py
def render(lines):
    out = []
    for desc, qty, price in lines:
        total = qty * price
        out.append(f"{desc:20.20} {qty:>4} {price:>10,.2f} {total:>10,.2f}")

    out.append(f"{'TOTAL':20} {'':4} {'':10} {grand:>10,.2f}")

Four spec bugs, each producing plausible output. And the total line lacked the thousands separator that the line totals had. When you build fixed-width reports, test against exact expected text, as here: a misaligned column is invisible in a quick glance at small numbers.

solution.py
def duration(seconds):
    if seconds < 1:
        return f"{round(seconds * 1000)}ms" if seconds > 0 else "0s"
    total = int(seconds)
    days, rest = divmod(total, 86_400)
    hours, rest = divmod(rest, 3_600)
    minutes, secs = divmod(rest, 60)
    parts = [(days, "d"), (hours, "h"), (minutes, "m"), (secs, "s")]
    for i, (value, unit) in enumerate(parts):
        if value:
            if i == len(parts) - 1:
                return f"{value}{unit}"
            nxt, nxt_unit = parts[i + 1]
            return f"{value}{unit} {nxt:02d}{nxt_unit}"
    return "0s"

The divmod chain is the 1.1 pattern: each step takes off the largest unit and passes the remainder on. Showing the two largest units keeps the text short and meaningful: nobody cares about the seconds of a two-day job. Zero-padding the second unit (03h, 05s) keeps columns aligned in logs, and 1h 00m still shows the second unit because it is the one after the first non-zero unit, which is the readable choice. This is the kind of helper that turns raw latency and job-duration numbers into dashboards and agent progress messages.

Halves round to even: 2.5 gives 2, 3.5 gives 4, and -0.4 rounds to -0, keeping its sign. 0.125 is exactly representable, so it rounds to even, 0.12. Default f has 6 decimals, which shows 0.000000 for 1e-7, while g keeps it visible as 1e-07 and writes large integers in exponent form. True formats as 1 with d and as True otherwise; a string precision of 0 gives the empty string. The space sign leaves room for a minus. nan and inf ignore precision, and -0.0 keeps its minus sign, which surprises people in reports: add z (f"{-0.0:z.1f}", Python 3.11+) to normalise it.

17. f-strings, str.format, % formatting or string.Template: when do you use each?

SolutionModel answer

f-strings for almost all of your own code: the values are known where the text is built, they are the most readable and the fastest, and they support the full format-spec language plus = for debugging. str.format or format_map when the template is defined separately and filled later, such as prompt templates stored in files; the template must be trusted, since format fields can access attributes. % formatting mainly for logging calls, where the logger formats lazily only when the message is emitted. string.Template for templates written by users or non-programmers: $name placeholders cannot run expressions, and safe_substitute tolerates missing values. For HTML or anything needing escaping, use a real template engine such as Jinja2 with autoescaping.

Interview

18. Why should log messages use %s arguments instead of f-strings?

SolutionModel answer

An f-string is evaluated before the logging call, so the message text (including repr of large objects) is built even when that log level is disabled, every time the line runs. Passing arguments (log.debug("x=%s", x)) lets the logger check the level first and format only when the record is actually emitted, which matters in hot paths. It also keeps the message template constant, so log aggregators (Datadog, ELK, Sentry) can group occurrences and extract the values as fields. Exceptions: f-strings are fine for messages that are always emitted and cheap to build, and structured logging libraries take keyword fields instead (log.info("retrieved", n=len(chunks))).

19. How do you format floats for financial reports correctly?

SolutionModel answer

Do not do money arithmetic in binary floats: values like 2.675 or 1.005 are not exactly representable, so sums drift and formatting can round the "wrong" way, and format specs round half to even. Parse amounts as Decimal from strings (or store integer cents), do the arithmetic in that type, round once at the defined point with an explicit rule (quantize(Decimal("0.01"), rounding=ROUND_HALF_UP) or banker's rounding if the business requires it), and only then format for display with :,.2f. Keep full precision in storage, format at the edge, and be aware that thousands and decimal separators are locale-specific (babel or locale for non-English reports). Test against totals produced by the accounting system, because "matches Excel" is usually the real requirement.

Recap

  • f-string fields are expressions evaluated when the line runs. Use {{ }} for literal braces, !r to see quotes and whitespace, {x=} to debug.
  • Format spec order: fill, align, sign, #, 0, width, grouping, .precision, type. Width is a minimum; only a string precision cuts.
  • Formatting rounds the binary value with ties to even. For money, round with Decimal first, then format.
  • Dates: f"{dt:%Y-%m-%d}" or isoformat(), never concatenated numbers.
  • f-strings for your code, format_map for templates filled later, % arguments for logging, Template for user-written templates.
