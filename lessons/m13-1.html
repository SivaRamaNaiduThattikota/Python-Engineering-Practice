13.1 pytest basics

Tests are how you know code works today and still works after the next change, and in interviews and code reviews they are how others judge your engineering. pytest from the ground up: test discovery, plain assert with rewriting, floats with approx, exceptions with raises, parametrised cases, marks, and what makes a test worth having. Most problems here ask you to write the tests, and they are graded by running real pytest against a correct implementation and several buggy ones.

1What a test is and how pytest finds it

A test is code that runs other code with a known input and checks the output. Written once, it runs in a second every time anything changes, so regressions are caught before users or downstream jobs find them, and refactoring becomes safe. A good test reads as a specification: its name states a behaviour (test_slugify_collapses_repeated_separators), and its body follows arrange, act, assert: set up the input, call the code, check the result.

pytest finds tests by convention: files named test_*.py or *_test.py, functions named test_* in them, and methods named test_* in classes named Test* that have no __init__. You check results with the plain assert statement; pytest rewrites asserts in test files when it imports them, so a failure shows the values involved (assert 4 == 5 with where 4 = add(2, 2)) instead of a bare AssertionError. A test passes if it returns without an exception and fails if anything raises, so a test with no assert passes whenever the code merely does not crash, which is rarely enough.

On your machine you run pytest in the project folder (or python -m pytest); useful options are -q (quiet), -v (one line per test), -x (stop at the first failure), -k "slug and not unicode" (select by name), --lf (rerun last failures) and a node id such as tests/test_text.py::test_slugify to run one test. On this site, the helper run_pytest(source) from lessontools writes source to a fresh folder as test_main.py, runs real pytest on it in the browser, and returns a dict with each test's outcome, the counts and pytest's output. swap_impl(source, code) replaces the section between the comments # --- code under test and # --- tests with other code, which is how your tests are run against buggy versions.

2Writing assertions: values, floats and exceptions

Assert the most specific thing you can. assert result == {"label": "spam", "score": 0.9} checks everything at once and pytest prints a diff of the dicts; assert result or assert "spam" in str(result) pass for many wrong results. Compare whole values where possible, check types when they matter (isinstance), and use is only for None, True and False.

Floats need tolerance, because arithmetic in binary rounds: 0.1 + 0.2 == 0.3 is False. pytest.approx(expected) compares within a relative tolerance of one millionth by default (rel=1e-6), plus an absolute tolerance of 1e-12 for values near zero; set rel= or abs= explicitly when you know the precision you need. It works for single numbers, and element-wise for lists, tuples and dict values, and NumPy arrays, so assert metrics == pytest.approx({"precision": 0.667, "recall": 0.5}, abs=1e-3) checks a whole metrics dict.

Errors are behaviour too. with pytest.raises(ValueError, match="overlap"): passes only if the block raises ValueError (or a subclass) whose message matches the regular expression; if nothing is raised, the test fails with DID NOT RAISE. Use as excinfo to inspect the exception afterwards (excinfo.value, excinfo.type). Keep only the raising call inside the block: anything after it never runs. pytest.warns(DeprecationWarning) does the same for warnings.

import pytest

3Parametrize: one test, many cases

Edge cases are where bugs live, and writing a separate function for each is tedious. @pytest.mark.parametrize("text,expected", [...]) runs one test function once per tuple, each as a separate test with its own outcome and an id built from the values (test_slugify[Hello World-hello-world]), so one failing case does not hide the others. Give readable ids with ids=[...] or pytest.param(value, id="unicode"), and attach marks to single cases with pytest.param(..., marks=pytest.mark.xfail). Stacking two parametrize decorators runs every combination, which suits checks such as every model with every temperature.

Choose cases deliberately: the normal case, the empty input, a single element, boundaries (exactly at a limit, one below, one above), invalid input that must raise, unusual characters (Unicode, whitespace, very long strings), and anything a past bug taught you. That list is more valuable than many random normal cases.

parametrize.py
from lessontools import run_pytest

SRC = '''
import pytest

def word_count(text):
    return len(text.split())

@pytest.mark.parametrize("text,expected", [
    ("refund window", 2),
    ("", 0),
    ("  spaced   out  ", 2),
    pytest.param("tab\\tand\\nnewline", 3, id="whitespace"),
    pytest.param("don't stop", 3, id="apostrophe", marks=pytest.mark.xfail(reason="counts words, not tokens")),
])
def test_word_count(text, expected):
    assert word_count(text) == expected
'''

4Marks: skipping and expected failures

Marks attach metadata to tests. @pytest.mark.skip(reason=...) never runs a test; @pytest.mark.skipif(condition, reason=...) skips it when the condition is true, for example on another operating system, without a GPU, or without an API key in the environment. @pytest.mark.xfail(reason=...) documents a known bug: the test runs, a failure is reported as xfailed (expected), and if it unexpectedly passes it is xpassed; with strict=True, an unexpected pass is a failure, which forces you to remove the mark once the bug is fixed. Custom marks (@pytest.mark.slow, @pytest.mark.integration) are registered in the configuration and selected with -m "not slow", so a fast suite runs on every change and the slow one in CI.

5What makes a test worth having

A test is worth having if it fails when the code is wrong and passes when the code is right, every time. That gives the checklist. It tests behaviour through the public interface, not implementation details, so a refactor does not break it. It is deterministic: no dependence on the clock, randomness without a seed, the network, test order or leftover files (13.2 and 13.3 show how to control those). It is fast, so people run it constantly. It checks one behaviour, so its name says what broke. And it would have caught a real bug: the grading of this lesson's problems, mutation testing, measures exactly that by running your tests against deliberately broken versions of the code.

# --- code under test (do not edit) ---
def mean_reciprocal_rank(ranks):
    # ranks: 1-based position of the first relevant result per query, or None if there was none
    return sum(1 / r for r in ranks if r is not None) / len(ranks)


# --- tests ---
import pytest


def test_mrr_of_ranks():
    assert mean_reciprocal_rank([1, 2, 3]) == pytest.approx(11 / 18)


def test_queries_without_a_hit_count_as_zero():
    assert mean_reciprocal_rank([1, None]) == pytest.approx(0.5)

(1 + 1/2 + 1/3) / 3 is 0.6111... with many more digits, so an exact comparison against a rounded literal fails although the code is right; approx compares within a relative tolerance, and writing the exact fraction 11 / 18 makes the intent clear. The second test adds the case the first could not see: a query with no relevant result must count as a reciprocal rank of 0, which is what makes MRR penalise a retriever that finds nothing. With only "every query has a hit" in the suite, both versions agree and the bug ships. A green test suite is only as strong as its cases.

# --- code under test (do not edit) ---
def chunk_words(text, size, overlap=0):
    if size < 1:
        raise ValueError("size must be at least 1")
    if not 0 <= overlap < size:
        raise ValueError("overlap must be in [0, size)")
    words = text.split()
    step = size - overlap
    chunks = []
    for start in range(0, len(words), step):
        chunks.append(" ".join(words[start:start + size]))
        if start + size >= len(words):
            break
    return chunks


# --- tests ---
import pytest

TEN = "w0 w1 w2 w3 w4 w5 w6 w7 w8 w9"


def test_chunks_without_overlap():
    assert chunk_words(TEN, 4) == ["w0 w1 w2 w3", "w4 w5 w6 w7", "w8 w9"]


def test_chunks_with_overlap():
    assert chunk_words(TEN, 4, overlap=1) == ["w0 w1 w2 w3", "w3 w4 w5 w6", "w6 w7 w8 w9"]


def test_no_redundant_tail_chunk():
    assert chunk_words("a b c d e", 3, overlap=1) == ["a b c", "c d e"]


def test_empty_text():
    assert chunk_words("", 3) == []


@pytest.mark.parametrize("overlap", [-1, 3, 4])
def test_rejects_bad_overlap(overlap):
    with pytest.raises(ValueError, match="overlap"):
        chunk_words(TEN, 3, overlap=overlap)


def test_rejects_bad_size():
    with pytest.raises(ValueError, match="size"):
        chunk_words(TEN, 0)

Writing the expected chunks out by hand for one well-chosen input (ten numbered words) checks the step, the overlap and the final chunk together, and numbered words make mistakes easy to see. The redundant-tail case is the subtle one: with overlap, a naive loop emits a last chunk made only of words already included, which wastes an embedding and double-counts text in retrieval. match= matters for errors: the version without the overlap check still raises ValueError for overlap == size, but from range() ("arg 3 must not be zero"), and for overlap > size it silently loops backwards; checking the message proves the error comes from your validation. Parametrising the bad values keeps each case visible in the report.

def parametrize(*cases):
    def decorator(fn):
        fn.params = list(cases)
        return fn
    return decorator


def _outcome(fn, args):
    try:
        fn(*args)
    except AssertionError:
        return "failed"
    except Exception as e:
        return f"error: {type(e).__name__}"
    return "passed"


def run_tests(namespace):
    results = {}
    for name, fn in namespace.items():
        if not name.startswith("test") or not callable(fn):
            continue
        params = getattr(fn, "params", None)
        if params is None:
            results[name] = _outcome(fn, ())
        else:
            for i, args in enumerate(params):
                results[f"{name}[{i}]"] = _outcome(fn, args)
    return results

This is pytest's core loop in miniature: discovery by naming convention (test_value is skipped because it is not callable), one isolated call per test with exceptions turned into outcomes, and parametrisation implemented as metadata attached by a decorator (8.3) that the runner reads, which is literally how pytest.mark.parametrize works: marks are stored on the function and expanded at collection time. Distinguishing a failed assertion from another exception mirrors pytest's report, where a KeyError points to a broken test or code rather than a wrong value. 15. What makes a good unit test?

SolutionModel answer

A good unit test fails when the behaviour it covers is broken and passes otherwise, reliably. Concretely: it tests one behaviour through the public interface, with a name that states that behaviour, so a failure explains itself; it follows arrange, act, assert and asserts the specific expected value, not just "something truthy"; it is deterministic (no real clock, network, unseeded randomness, shared state or test order) and fast, so it can run on every change; it is independent of other tests and cleans up after itself; it covers edge cases and error paths, not only the happy path; and it is resilient to refactoring because it checks outcomes, not implementation details such as which private helper was called. A useful check of a test's value is whether it would catch a plausible bug: break the code deliberately and see it fail. Coverage percentages measure what code ran, not what was verified.

Interview

16. Why does pytest use plain assert statements, and how does it show useful failure messages?

SolutionModel answer

Plain assert keeps tests short and readable: assert result == expected instead of a family of methods such as assertEqual, assertIn, assertAlmostEqual. Normally a failed assert only raises a bare AssertionError, so pytest rewrites the assert statements in test modules when it imports them, through an import hook that transforms the module's syntax tree: each assert is expanded into code that saves intermediate values, and on failure builds a message showing them, such as assert 4 == 5 where 4 = add(2, 2), and diffs for long strings, lists and dicts. That is why it only works in test files and modules registered for rewriting (helpers can be registered with pytest.register_assert_rewrite), and why running Python with -O, which strips asserts, must never be used for tests.

Interview

17. What is a flaky test, what causes it, and what do you do about it?

SolutionModel answer

A flaky test passes and fails on the same code. Common causes: dependence on test order or shared state (module globals, files, databases, environment variables left behind); time (the current date, time zones, timeouts, sleep-based waits); unseeded randomness; concurrency races; real network calls and external services; floating-point comparisons that depend on platform; and leaking resources. Flaky tests are harmful because people learn to ignore red builds and rerun until green, so real failures get missed. Fix them rather than retrying: isolate state with fixtures and temporary directories (13.2), freeze or inject the clock, seed randomness, replace network calls with fakes or mocks (13.3), wait on conditions instead of sleeping, and use approx for floats. To find them, run the suite in random order (pytest-randomly) and repeatedly, and quarantine (mark and track) a flaky test only as a short-term measure with an owner and a deadline. For LLM-dependent tests, keep model calls out of unit tests entirely (13.4).

Recap

  • pytest collects test_* functions in test_*.py files (and test_* methods of Test* classes); any exception fails a test, so assert something specific.
  • Plain assert is rewritten to show values; compare whole results, use pytest.approx for floats, and set abs= near zero.
  • pytest.raises(Type, match=...) checks errors; keep only the raising call inside the block.
  • @pytest.mark.parametrize turns a table of cases into separate tests; choose empty, boundary, invalid and unusual inputs deliberately.
  • Marks skip or expect failures (strict=True keeps xfail honest); judge tests by whether they catch real bugs, as mutation testing does.
