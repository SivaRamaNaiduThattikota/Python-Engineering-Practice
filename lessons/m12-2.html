12.2 csv, json and JSON Lines

The three text formats that move most data between tools: CSV for tables, JSON for nested records and API payloads, and JSON Lines for datasets, logs and LLM batch files. Readers and writers, quoting and dialects, JSON type mapping and its traps, custom encoders and decoders, and streaming JSONL with bad-line handling. Applied to labels, metrics, evaluation exports, chunked corpora and event logs.

1CSV with the csv module

CSV looks simple enough to split on commas, and that is the bug: a field can contain a comma, a quote or even a newline, in which case it is wrapped in double quotes and inner quotes are doubled (a field Smith, "Jr" is written as "Smith, ""Jr"""). The csv module implements those rules. csv.reader(f) yields each row as a list of strings, csv.writer(f).writerow(values) writes one, and the dictionary versions are what you usually want: csv.DictReader uses the header row as keys, and csv.DictWriter(f, fieldnames=...) writes dicts, with writeheader() for the header line and extrasaction="ignore" to skip keys that are not columns (by default extra keys raise ValueError).

Three rules make CSV code correct. Open files with newline="", so the csv module, not text mode, handles line endings, including newlines inside quoted fields (the writer ends rows with \r\n, as the format specifies). Remember that every value read is a string, so convert types yourself: int(row["id"]), float(row["score"]), and treat "" as missing. And pick the encoding deliberately: files saved by Excel as "CSV UTF-8" start with a byte-order mark, which encoding="utf-8-sig" removes (problem 10). Other dialects are options: delimiter=";" for European exports, delimiter="\t" for TSV, and quoting=csv.QUOTE_ALL or QUOTE_NONNUMERIC to control quoting.

csv_basics.py
import csv, io

rows = [{"id": 1, "question": "Refund, or credit?", "answer": 'She said "5 days"', "score": 0.9},

writer = csv.DictWriter(buf, fieldnames=["id", "question", "answer", "score"])
writer.writeheader()

2JSON: type mapping and options

json.dumps(obj) turns Python data into a JSON string and json.loads(text) parses one; json.dump(obj, f) and json.load(f) do the same with a file. The mapping is: dict to object, list and tuple to array, str to string, int and float to number, True/False to true/false, None to null. It is lossy in ways that matter: tuples come back as lists, dictionary keys become strings ({1: "a"} round-trips to {"1": "a"}), and anything else, such as datetime, Decimal, set, NumPy numbers and your own classes, raises TypeError: Object of type ... is not JSON serializable.

Useful options: indent=2 for human-readable output, sort_keys=True for stable output that diffs cleanly, ensure_ascii=False to write é instead of \u00e9 (keep the file UTF-8), and separators=(",", ":") for the most compact form. One trap deserves its own line: by default Python writes float("nan") and infinities as NaN and Infinity, which are not valid JSON: JavaScript's JSON.parse, many databases and strict parsers reject them. Pass allow_nan=False to make that an error and replace such values deliberately (problem 7).

3Custom encoders and decoders

To serialise other types, pass default= to dumps: a function called for every object the encoder does not know, which must return something it does know (a string, number, list or dict), or raise TypeError. A single default handles dates (isoformat()), Decimal (str, to keep exact digits), sets (a sorted list), dataclasses (dataclasses.asdict), paths, and NumPy values, which are the commonest cause of "not JSON serializable" in ML code, since np.float32(0.9) is not a Python float (problem 6). Subclassing json.JSONEncoder and overriding its default method does the same thing in class form.

In the other direction, object_hook= is called with every decoded object (as a dict), and whatever it returns replaces it, which lets you turn tagged dicts back into rich types (problem 14). parse_float=Decimal parses every number with a fraction as an exact Decimal, useful for money. Note what cannot be customised: default is never called for types JSON already handles, so a tuple always becomes an array, and dict keys must be strings, numbers, booleans or None; any other key raises TypeError even with a default.

custom.py
import json
from dataclasses import dataclass, asdict
from datetime import datetime
from decimal import Decimal

@dataclass
class Run:
    name: str
    started: datetime
    cost: Decimal
    tags: set

def default(o):
    if isinstance(o, datetime):
        return o.isoformat()
    if isinstance(o, Decimal):
        return str(o)
    if isinstance(o, set):
        return sorted(o)
    if hasattr(o, "__dataclass_fields__"):
        return asdict(o)
    raise TypeError(f"cannot serialise {type(o).__name__}")

run = Run("exp-1", datetime(2025, 3, 1, 9, 30), Decimal("0.10"), {"rag", "eval"})
print(json.dumps(run, default=default))
print(json.loads('{"price": 0.10}', parse_float=Decimal))
Output
{"name": "exp-1", "started": "2025-03-01T09:30:00", "cost": "0.10", "tags": ["eval", "rag"]}
{'price': Decimal('0.10')}

4JSON Lines: streaming records

A big JSON array must be parsed whole before you can use its first element. JSON Lines puts one JSON object per line instead: a reader handles one line at a time with constant memory, a writer appends records as they are produced, a crash loses at most the last line, and files can be split, concatenated and counted with ordinary line tools. That is why datasets (Hugging Face), fine-tuning data, LLM batch request and result files, evaluation sets and structured logs are almost always .jsonl.

Write each record with json.dumps(record, ensure_ascii=False) followed by "\n" (no indent, which would spread one record over many lines). Read by iterating over the file, skipping blank lines, and decide what a bad line means: in a pipeline over millions of records, one broken line should usually be counted and reported with its line number, not crash the job; for a hand-edited evaluation set, it should fail loudly. Compressed files stream the same way with gzip.open(path, "rt", encoding="utf-8").

jsonl.py
import gzip, json, os, tempfile

path = os.path.join(tempfile.mkdtemp(), "batch.jsonl.gz")
requests = [{"custom_id": f"req-{i}", "body": {"prompt": f"Summarise ticket {i}"}} for i in range(3)]
with gzip.open(path, "wt", encoding="utf-8") as f:
    for r in requests:
        f.write(json.dumps(r, ensure_ascii=False) + "\n")
    f.write('{"custom_id": "req-3", "body": {"prom\n')
good, bad = [], []
with gzip.open(path, "rt", encoding="utf-8") as f:
    for number, line in enumerate(f, start=1):
        if not line.strip():
            continue
        try:
            good.append(json.loads(line))
        except json.JSONDecodeError as e:
            bad.append((number, e.msg))
print(len(good), good[-1]["custom_id"], bad)

import csv


def read_examples(path):
    out = []
    with open(path, encoding="utf-8", newline="") as f:
        for row in csv.DictReader(f):
            text = row["text"].strip()
            if not text:
                continue
            score = row["score"].strip()
            out.append({"id": int(row["id"]), "text": text, "label": row["label"].strip(),
                        "score": float(score) if score else None})
    return out

DictReader handles the quoting, so a comma or a newline inside a quoted text stays part of the field, which a split(",") would break. Everything arrives as a string, so the function converts each column explicitly and decides what an empty cell means (None, not 0.0, which would be a wrong score). Stripping matters because hand-edited CSVs are full of stray spaces, and "spam " would become a separate class in a training set.

solution.py
import json


def write_jsonl(path, records):
    count = 0
    with open(path, "w", encoding="utf-8") as f:
        for record in records:
            f.write(json.dumps(record, ensure_ascii=False) + "\n")
            count += 1
    return count


def read_jsonl(path, errors=None):
    with open(path, encoding="utf-8") as f:
        for n, line in enumerate(f, start=1):
            if not line.strip():
                continue
            try:
                obj = json.loads(line)
                message = None if isinstance(obj, dict) else "not an object"
            except json.JSONDecodeError as e:
                message = e.msg
            if message is None:
                yield obj
            elif errors is not None:
                errors.append((n, message))
            else:
                raise ValueError(f"line {n}: {message}")

The writer produces exactly one line per record because dumps without indent never emits a newline (newlines inside strings are escaped as \n). The reader is a generator, so a file of any size is processed one line at a time, and the caller chooses the policy: collect bad lines with their numbers (an ingestion job reports "2 bad lines" and continues) or fail at the first one (a test set). Blank lines are skipped without counting, but line numbers still count them, so the reported number is the one an editor shows. The truncated last line, typical of a crashed writer or an interrupted download, is reported instead of losing the whole file.

solution.py
import json
from dataclasses import asdict, is_dataclass
from datetime import date, datetime
from decimal import Decimal
from pathlib import PurePath

import numpy as np


def _default(o):
    if isinstance(o, (datetime, date)):
        return o.isoformat()
    if isinstance(o, Decimal):
        return str(o)
    if isinstance(o, (set, frozenset)):
        return sorted(o)
    if is_dataclass(o) and not isinstance(o, type):
        return asdict(o)
    if isinstance(o, PurePath):
        return o.as_posix()
    if isinstance(o, np.generic):
        return o.item()
    if isinstance(o, np.ndarray):
        return o.tolist()
    raise TypeError(f"Object of type {type(o).__name__} is not JSON serializable")


def to_json(obj, **kwargs):
    return json.dumps(obj, default=_default, **kwargs)

The encoder calls default only for objects it cannot handle, and then encodes whatever default returns, recursively. That is why the dataclass works in two steps: asdict returns a dict that still holds a date, and the encoder calls default again for it. NumPy is the everyday case in ML: metrics computed with NumPy are np.float32 or np.int64, not Python numbers, so json.dumps(metrics) fails at the end of a training run unless they are converted with .item(); arrays become nested lists with .tolist(). Decimals become strings to keep their exact digits. Raising TypeError for unknown types keeps the standard error instead of silently writing something like str(obj).

solution.py
import json
import math

def _clean(value):
    if isinstance(value, float) and not math.isfinite(value):
        return None
    if isinstance(value, dict):
        return {k: _clean(v) for k, v in value.items()}
    if isinstance(value, (list, tuple)):
        return [_clean(v) for v in value]
    return value

def metrics_json(metrics):
    return json.dumps(_clean(metrics), sort_keys=True, allow_nan=False)

Python's json module happily writes NaN and Infinity because JavaScript has those values, but the JSON standard does not, so browsers' JSON.parse, many databases and strict parsers reject the document. The default hook cannot help, because floats are a type JSON "already handles", so the values must be cleaned before encoding, recursively and without mutating the caller's metrics (which still hold the NaN, as the last assert shows). null is the honest value for an undefined metric, and allow_nan=False turns any future slip into an exception instead of a broken dashboard.

deepcopy is general: for every object it looks up a copier, records the object in a memo dictionary (so shared and recursive references survive), and runs in Python code. json.dumps and json.loads run in C and only understand plain data, which makes the round trip faster for exactly this kind of payload. import csv, json


def csv_to_chunks(csv_path, out_path, max_words=50):
    documents = chunks = 0
    with open(csv_path, encoding="utf-8-sig", newline="") as src, open(out_path, "w", encoding="utf-8") as out:
        for row in csv.DictReader(src):
            words = row["body"].split()
            if not words:
                continue
            documents += 1
            for k, start in enumerate(range(0, len(words), max_words)):
                record = {"doc_id": row["id"], "chunk": k, "title": row["title"], "text": " ".join(words[start:start + max_words])}
                out.write(json.dumps(record, ensure_ascii=False) + "\n")
                chunks += 1
    return documents, chunks

The two formats meet in one streaming loop: DictReader parses quoted bodies with commas, quotes and newlines correctly, and each chunk is written as soon as it is made, so a corpus of any size needs memory for one document only. split() also normalises whitespace, which is why the newline inside the body disappears from the chunk text. Each record carries its document id, chunk number and title, the metadata a RAG system stores next to the embedding so that answers can cite their source (5.P). Real chunkers split on tokens or sentences and overlap neighbouring chunks, but the file handling stays exactly this.

import gzip, json


def _good(obj):
    if not isinstance(obj, dict) or not isinstance(obj.get("type"), str):
        return False
    tokens = obj.get("tokens", 0)
    return isinstance(tokens, int) and not isinstance(tokens, bool)


def summarise_events(path):
    opener = gzip.open if str(path).endswith(".gz") else open
    events = tokens = 0
    by_type, bad = {}, []
    with opener(path, "rt", encoding="utf-8") as f:
        for n, line in enumerate(f, start=1):
            if not line.strip():
                continue
            try:
                obj = json.loads(line)
            except json.JSONDecodeError:
                bad.append(n)
                continue
            if not _good(obj):
                bad.append(n)
                continue
            events += 1
            by_type[obj["type"]] = by_type.get(obj["type"], 0) + 1
            tokens += obj.get("tokens", 0)
    return {"events": events, "by_type": dict(sorted(by_type.items())), "tokens": tokens, "bad_lines": bad}

gzip.open in text mode returns a file object that decompresses as it is read, so the same streaming loop handles both files, and choosing the opener once keeps the loop free of special cases. Validation is explicit because JSON gives no guarantees: an array, a missing type, a token count written as a string, and true (a bool, which Python counts as an int) are all rejected and reported by line number, and the truncated last line from an interrupted writer is just another bad line. Usage dashboards built from LLM gateway logs are computed exactly like this; with tens of gigabytes, the same loop runs per file in parallel (14.3) and the summaries are merged.

solution.py
import json
from datetime import date, datetime
from decimal import Decimal


def _encode(o):
    if isinstance(o, datetime):
        return {"__type__": "datetime", "value": o.isoformat()}
    if isinstance(o, date):
        return {"__type__": "date", "value": o.isoformat()}
    if isinstance(o, Decimal):
        return {"__type__": "decimal", "value": str(o)}
    if isinstance(o, set):
        return {"__type__": "set", "value": sorted(o)}
    if isinstance(o, complex):
        return {"__type__": "complex", "value": [o.real, o.imag]}
    raise TypeError(f"Object of type {type(o).__name__} is not JSON serializable")


_DECODERS = {
    "datetime": datetime.fromisoformat,
    "date": date.fromisoformat,
    "decimal": Decimal,
    "set": set,
    "complex": lambda v: complex(v[0], v[1]),
}


def _decode(d):
    if set(d) == {"__type__", "value"}:
        kind = d["__type__"]
        if kind not in _DECODERS:
            raise ValueError(f"unknown __type__: {kind!r}")
        return _DECODERS[kind](d["value"])
    return d


def dumps_tagged(obj):
    return json.dumps(obj, default=_encode)


def loads_tagged(text):
    return json.loads(text, object_hook=_decode)

default and object_hook are the two halves of a custom format: the encoder replaces each unknown object with a tagged plain object, and the decoder sees every decoded object (innermost first, so nested values are already converted) and turns tags back into rich types. Checking datetime before date matters because datetime is a subclass of date; the other order would silently drop the time. Requiring exactly the two keys avoids misreading ordinary data that happens to contain a __type__ field, and unknown tags fail loudly. The tuple shows the limit: JSON already "handles" tuples as arrays, so default is never called and they come back as lists. Serialisation libraries (and job queues such as Celery and Kombu) use this same tagging trick.

Duplicate keys: the last one wins. Python ints have unlimited size. Keys may be str, int, float, bool or None; anything else is an error.

SolutionShow the solution and why
Real output

JSON allows duplicate keys and Python keeps the last, silently, which can hide a bug in a generated document. Python parses big integers exactly (JavaScript would round this one, the reason APIs send large ids as strings). A number too large for a float becomes infinity; floats are written with the shortest repr that round-trips, so 0.1 + 0.2 shows its binary error; and \u00e9 escapes decode to é. int, None and float keys are converted to strings, but a tuple key raises TypeError even though tuples are valid values. Finally, a newline inside a string is written as the escape \n, which is why one record always fits on one line in JSONL.

8Interview questions

Interview

17. CSV, JSON, JSON Lines or Parquet: how do you choose a format?

SolutionModel answer

CSV is for flat tables exchanged with people and spreadsheet tools: universal, but untyped (everything is a string), ambiguous in encoding and dialect, and unable to hold nested data. JSON suits nested records, configuration and API payloads, with basic types, but a single document must be parsed whole. JSON Lines keeps JSON's flexibility while streaming: one record per line, appendable, splittable and robust to a truncated last line, which is why datasets, fine-tuning files, LLM batch jobs and logs use it. Parquet is a typed, compressed, columnar binary format for large analytical tables: reading two columns of a billion rows reads only those columns, with types preserved, which makes it the default for data lakes and feature tables (pandas, Polars, Spark, DuckDB). Rule of thumb: Parquet for analytics at scale, JSONL for record streams and ML/LLM data, JSON for configs and APIs, CSV only at the human or legacy boundary.

Interview

18. What can go wrong when data round-trips through JSON?

SolutionModel answer

Types are lost or changed: tuples become lists, integer dict keys become strings, sets, dates, Decimal, bytes and NumPy values cannot be serialised without a default, and floats that were Decimal lose exactness. Numbers have edge cases: Python writes NaN and Infinity, which are not valid JSON and are rejected elsewhere (use allow_nan=False); integers beyond 2**53 are exact in Python but rounded in JavaScript, so large ids should travel as strings. Duplicate keys are silently resolved by keeping the last. Encoding matters: ensure_ascii=True escapes everything, False requires the file to be UTF-8. And structure is not validated, so a parsed value can be an array where you expected an object; validate it with a schema or Pydantic model (11.4) at the boundary.

Interview

19. An ingestion job reads millions of JSONL records and some are malformed. How do you handle them?

SolutionModel answer

Stream the file line by line so memory stays constant, and separate the policy from the parsing. Parse each line inside try, then validate its shape (an object, required fields, types, ideally a Pydantic model). Bad records should not crash the job at hour three, but they must not disappear either: count them, log the line number, file and error type (not the full content if it may hold personal data), and write the raw line to a dead-letter or quarantine file so it can be inspected and replayed after a fix. Define a threshold: if more than, say, 0.1% of records are bad, fail the run, because that signals an upstream schema change rather than noise. Make the job idempotent and resumable (record the last committed offset or batch, write outputs atomically), and report the counts (read, good, bad, by error type) as metrics, so a jump is visible on a dashboard.

Recap

  • Use the csv module, never split(","); open files with newline="", convert types yourself, and use utf-8-sig for files from Excel.
  • DictReader and DictWriter map rows to dicts; call writeheader(), and set extrasaction deliberately.
  • JSON loses types: tuples become lists, keys become strings; NaN is not valid JSON, so clean it and pass allow_nan=False.
  • default= serialises unknown types (dates, Decimal, NumPy) and object_hook= decodes them; neither applies to types JSON already handles.
  • JSON Lines streams one record per line: write without indent, read line by line, and report bad lines with their numbers.
