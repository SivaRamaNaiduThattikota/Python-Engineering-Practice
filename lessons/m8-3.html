8.3 Caching, retries and timing

The decorators every production codebase has: caching with functools.lru_cache and how it really works, time-limited caches, what makes a cache key correct, retry decorators with backoff, why a decorator cannot enforce a timeout on its own, and measuring latency with percentiles. Applied to embeddings, model calls and service metrics.

1functools.lru_cache: how it works

Memoization, which you built by hand in 8.1, is in the standard library: @functools.lru_cache(maxsize=128) and its unbounded form @functools.cache. On each call, the wrapper builds a key from the arguments, looks it up in a dict, and returns the stored result on a hit; on a miss it calls the function, stores the result and returns it. With a maxsize, the cache also tracks the order in which entries were used, and when it is full it evicts the least recently used entry, the one that has gone longest without a hit. cache_info() reports hits, misses and sizes, and cache_clear() empties it.

lru.py
import functools

calls = []

@functools.lru_cache(maxsize=2)
def tokens(text):
    calls.append(text)
    return len(text.split())

for t in ["refund policy", "reset password", "refund policy", "invoice copy", "reset password"]:
    tokens(t)
print(calls)
print(tokens.cache_info())
tokens.cache_clear()
print(tokens.cache_info().currsize, tokens.__wrapped__("a b c"))
Output
['refund policy', 'reset password', 'invoice copy', 'reset password']
CacheInfo(hits=1, misses=4, maxsize=2, currsize=2)
0 3

Follow the calls: two misses fill the cache, the repeated "refund policy" is a hit and becomes the most recently used, so when "invoice copy" arrives, "reset password" is the least recently used and is evicted. Asking for it again is therefore a miss and it is computed a second time. lru_cache uses functools.wraps, so __wrapped__ gives the undecorated function, handy in tests that should not touch the cache.

The key rules matter in practice. Every argument must be hashable, or the call raises TypeError: unhashable type: 'list' (problem 3). Positional and keyword forms are different keys: f(1, 2) and f(1, b=2) are cached separately, even though they mean the same thing. Equal values of different types are a grey area: the documentation says they are "usually" treated as the same call, but CPython has a fast path that uses a single int or str argument directly as the key, so f(1) gets its own entry while f(1.0) and f(True) share one. Never rely on either behaviour; pass typed=True when the type of an argument matters (problem 16). And the cache stores the object returned, so a mutable result such as a list is shared by every caller that gets a hit: a caller that appends to it changes the cached value for everyone (problem 4).

2When caching is safe, and what it costs

Caching is only correct for functions whose result depends only on their arguments: the same arguments must always produce the same answer, and calling it must have no side effects that callers rely on. Pure computations (parsing, tokenising, formatting, feature extraction) qualify. Functions that read the clock, random numbers, files, databases or the network do not, because the world changes while the cache keeps the old answer; caching them is a decision about staleness, which a time-limited cache makes explicit (below).

LLM calls sit in between. With temperature 0, a provider usually returns the same answer for the same request, though not guaranteed; with temperature above 0, answers vary by design, and caching freezes one sample. Embeddings for a given model are deterministic in practice, which is why embedding caches are everywhere: re-embedding an unchanged document costs money and time for nothing. In both cases the key must include everything that affects the result: the model, the full prompt including the system message, and every parameter. A cache keyed only on the user's question returns a cheap model's answer to a request for the expensive one (problem 6).

The costs are memory and correctness. @functools.cache never evicts, so a function called with ever-new arguments (request ids, timestamps, user texts) grows until the process runs out of memory; give long-running services a maxsize (problem 10). A cache also keeps every argument and result alive (2.1), including large arrays. And a decorated method caches on self, keeping every instance it has seen alive for as long as the cache exists (Module 9 shows the alternatives).

SQL / Power BI

A cache is a materialised result: Power BI's import mode or a materialised view in SQL stores the answer so queries do not recompute it. The same trade-off applies: fast reads, but the result is only as fresh as the last refresh, and a refresh policy (a TTL, a schedule, invalidation on change) is part of the design, not an afterthought.

3Time-limited caches

A TTL ("time to live") cache stores each entry together with the time it was created, and treats entries older than the TTL as missing. It makes staleness a number: "an exchange rate may be up to 60 seconds old", "a retrieved document list may be up to 10 minutes old". lru_cache has no TTL, so it is a common hand-written decorator. Injecting the clock makes it testable without waiting (problem 5).

ttl.py
import functools

def ttl_cache(seconds, clock):
    def decorator(func):
        store = {}

        @functools.wraps(func)
        def wrapper(*args):
            now = clock()
            if args in store:
                value, created = store[args]
                if now - created < seconds:
                    return value
            value = func(*args)
            store[args] = (value, now)
            return value
        wrapper.cache_clear = store.clear
        return wrapper
    return decorator

now = [0.0]
fetched = []

@ttl_cache(seconds=60, clock=lambda: now[0])
def exchange_rate(currency):
    fetched.append((currency, now[0]))
    return {"EUR": 1.08, "GBP": 1.27}[currency]

exchange_rate("EUR"); now[0] = 30; exchange_rate("EUR"); now[0] = 61; exchange_rate("EUR")
print(fetched)
Output
[('EUR', 0.0), ('EUR', 61)]

Expired entries in this simple version stay in memory until they are next requested; production caches also bound their size and purge old entries. Libraries such as cachetools (TTLCache, LRUCache) and external stores such as Redis (with per-key expiry) provide this, and Redis also lets several processes share one cache, which lru_cache cannot.

4Retry as a decorator

Lesson 7.4 built the retry logic: transient errors only, exponential backoff with jitter, a maximum number of attempts, and re-raising the last error. As a decorator factory it becomes a one-line policy on any function: @retry(attempts=4, on=(TimeoutError, ConnectionError)). Keep sleep and the random generator injectable (with production defaults) so tests can run the whole sequence instantly.

retry_decorator.py
import functools, random, time

def retry(*, attempts=3, on=(TimeoutError, ConnectionError), base=0.5, cap=8.0, sleep=time.sleep, rng=random.Random()):
    if attempts < 1:
        raise ValueError("attempts must be at least 1")

    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            for attempt in range(1, attempts + 1):
                try:
                    return func(*args, **kwargs)
                except on:
                    if attempt == attempts:
                        raise
                    sleep(rng.uniform(0, min(cap, base * 2 ** (attempt - 1))))
        return wrapper
    return decorator

waits = []
failures = iter([TimeoutError("t1"), ConnectionError("c1")])

@retry(attempts=3, sleep=waits.append, rng=random.Random(7))
def ask(q):
    err = next(failures, None)
    if err:
        raise err
    return f"answer: {q}"

print(ask("refund?"), [round(w, 3) for w in waits])
Output
answer: refund? [0.162, 0.151]

The tenacity library is the full-featured version: @retry(stop=stop_after_attempt(4), wait=wait_random_exponential(max=30), retry=retry_if_exception_type(TimeoutError)), plus callbacks before sleeping, statistics, and support for async functions. Most LLM SDKs already retry internally (the OpenAI and Anthropic clients retry twice by default); adding your own decorator on top multiplies the attempts, so decide which layer owns retries.

A word on timeouts. A decorator cannot safely stop a synchronous function that is already running: Python has no way to interrupt a thread from outside. The Unix-only signal.alarm trick works only in the main thread, and running the function in a helper thread with a timeout abandons the thread rather than stopping it. So timeouts belong inside the I/O call: pass timeout= to the HTTP client or SDK, which can give up on the network operation itself. With async code (14.5), asyncio.timeout() can cancel a waiting coroutine, which is one of the reasons LLM services are often written with asyncio.

5Timing and latency statistics

For measuring durations, use time.perf_counter(): a high-resolution clock meant for intervals that never jumps backwards. time.time() is wall-clock time, which can jump when the system clock is adjusted (NTP corrections, daylight saving changes on some systems), producing negative or huge "durations". time.monotonic() also never goes backwards and is the right clock for timeouts and deadlines.

A single average hides what users feel. Latencies are usually skewed: most calls are fast and a few are very slow, and those few are the ones users complain about. Services therefore report percentiles: p50 (the median, a typical call), p95 and p99 (the slow tail). An LLM endpoint with a mean of 1.2 s can have a p99 of 9 s. statistics.quantiles(data, n=100) returns the 99 cut points between percentiles; for small samples, the simple nearest-rank method (sort, then take the value at position ceil(p * n)) is easy to reason about (problem 15).

percentiles.py
import math, statistics

latencies = [0.8, 0.9, 1.0, 1.1, 0.9, 1.0, 1.2, 0.95, 8.5, 1.05]

def nearest_rank(data, p):
    ordered = sorted(data)
    return ordered[max(0, math.ceil(p * len(ordered)) - 1)]

print(round(statistics.mean(latencies), 3), statistics.median(latencies))
print(nearest_rank(latencies, 0.50), nearest_rank(latencies, 0.95), nearest_rank(latencies, 0.99))
q = statistics.quantiles(latencies, n=100, method="inclusive")
print(round(q[49], 3), round(q[94], 3))
Output
1.74 1.0
1.0 8.5 8.5
1.0 5.215

One slow call (8.5 s) pulls the mean to almost twice the median, while the median still describes a typical call. The p95 and p99 by nearest rank both land on the slow call, because with ten samples the top 5% is a single value; percentiles of tiny samples are noisy, so dashboards compute them over many calls. statistics.quantiles interpolates between neighbouring values, so its p95 here lands between the second-slowest call and the outlier (5.215 s) rather than on the outlier. Both methods are standard; on small samples they can differ a lot, so state the method next to the number.

SolutionShow the solution and why
solution.py
import functools

calls = []

@functools.lru_cache(maxsize=128)
def _embed_many(texts):
    calls.append(texts)
    return [[len(t)] for t in texts]

def embed_many(texts):
    return _embed_many(tuple(texts))

lru_cache builds its key from the arguments, and lists are unhashable because they can change (4.5): a list used as a key could be modified after storing, and the cache would never find it again. Converting to a tuple produces an immutable, hashable key with the same contents. The public function keeps accepting lists, so callers do not change. For large inputs, a key built from a hash of the contents (hashlib.sha256) keeps the cache's memory smaller than storing every tuple.

solution.py
import functools

def ttl_cache(seconds, clock):
    def decorator(func):
        store = {}
        counts = {"hits": 0, "misses": 0}

        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            key = (args, tuple(sorted(kwargs.items())))
            now = clock()
            entry = store.get(key)
            if entry is not None and now - entry[1] < seconds:
                counts["hits"] += 1
                return entry[0]
            counts["misses"] += 1
            value = func(*args, **kwargs)
            store[key] = (value, now)
            return value

        wrapper.cache_clear = store.clear
        wrapper.stats = lambda: dict(counts)
        return wrapper
    return decorator

Each entry carries its creation time, and validity is a comparison with the injected clock, so the test controls time exactly: at 9.9 s the entry is still valid, at 10.0 it has expired and is refetched. Sorting keyword items makes the key independent of keyword order, and k=2 is a separate key from the default k=3 because the parameters genuinely differ. stats returns a copy so callers cannot alter the counters. The hit rate, hits / (hits + misses), is the number to watch when tuning a TTL: longer TTLs raise it at the price of staler answers.

solution.py
CACHE = {}
calls = []

def call_model(prompt, model, temperature):
    calls.append((prompt, model, temperature))
    return f"{model}@{temperature}: {prompt}"

def complete(prompt, model="small", temperature=0.0):
    if temperature != 0:
        return call_model(prompt, model, temperature)
    key = (prompt, model, temperature)
    if key not in CACHE:

solution.py
import functools

def retry(*, attempts, on, base, sleep, rng):
    if attempts < 1:
        raise ValueError("attempts must be at least 1")

    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            for attempt in range(1, attempts + 1):
                wrapper.last_attempts = attempt
                try:
                    return func(*args, **kwargs)
                except on:
                    if attempt == attempts:
                        raise
                    sleep(rng.uniform(0, base * 2 ** (attempt - 1)))
        wrapper.last_attempts = 0
        return wrapper
    return decorator

The retry logic of 7.4, packaged so the policy is one line above any function. In the second call, the ConnectionError is retried (one wait of 1.0), and the KeyError on the second attempt is not in on, so it propagates immediately, with last_attempts showing where it stopped. Settings are keyword-only and validated at decoration time. Recording the attempt count on the wrapper is a cheap metric: a function that regularly needs three attempts is a sign of an unhealthy dependency long before it fails outright.

solution.py
import functools

LOG = []

@functools.lru_cache(maxsize=1000)
def _score_text(text):

Two problems in one: the key included an argument (request_id) that does not affect the result but is unique per call, so the hit rate was zero; and functools.cache has no size limit, so every request added an entry forever, a memory leak. A side effect such as logging must never be inside a cached function either, because on a hit it would silently not happen; here the log stays in the uncached outer function, so every request is still logged.

Note the loads.append: a side effect in a cached function runs only on misses, which is what this test wants (counting loads), but would be a bug if the side effect were something callers rely on every time. maxsize=None is equivalent to functools.cache; unbounded is fine here because the set of schema names is small and fixed.

SolutionShow the solution and why
solution.py
def make_cached_embedder(embed_batch):
    cache = {}

    def embed(texts):
        missing = list(dict.fromkeys(t for t in texts if t not in cache))
        if missing:
            vectors = embed_batch(missing)
            for text, vec in zip(missing, vectors, strict=True):
                cache[text] = vec
        return [cache[t] for t in texts]

    embed.cache = cache
    return embed

A decorator like lru_cache keys on the whole argument, so a batch with one new text would be a miss for all of them. Caching per item and sending only the missing ones keeps the batching benefit (one API call per request) while never paying twice for the same text. dict.fromkeys removes duplicates inside one batch while keeping order, so "refund policy" appearing twice is embedded once, and zip(..., strict=True) checks the API returned one vector per text. In production the cache key would be a hash of the model name and the exact text, stored in a shared store (Redis, a database table) so all workers and future runs benefit, and the cache would be invalidated when the embedding model changes, since vectors from different models are not comparable.

solution.py
import functools


def retry(attempts=3, on=(TimeoutError, ConnectionError), delay=1.0, sleep=None):
    if attempts < 1:
        raise ValueError("attempts must be at least 1")

    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            for attempt in range(1, attempts + 1):
                try:
                    return func(*args, **kwargs)
                except on:
                    if attempt == attempts:
                        raise
                    sleep(delay * 2 ** (attempt - 1))
        return wrapper
    return decorator

Four bugs. on=Exception as the default retried everything, including ValueError for bad input and bugs, so failures were delayed by seconds of pointless waiting and repeated calls. Sleeping after the last attempt wasted the longest wait of the sequence for nothing. return None after the loop turned "all attempts failed" into a normal-looking None result, the swallowed-error bug of 7.3; re-raising the last exception on the final attempt fixes both of these at once. And without functools.wraps, every retried function was named wrapper in logs and traces. Validating attempts up front turns retry(attempts=0), which would never call the function at all, into an error at import.

15. Latency percentiles per function

Hint 1Open a hint

Hint 2Open a hint

SolutionShow the solution and why
solution.py
import functools, math
from collections import deque

def track_latency(clock, window=1000):
    def decorator(func):
        durations = deque(maxlen=window)

        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            start = clock()
            try:
                return func(*args, **kwargs)
            finally:
                durations.append(clock() - start)

        def latency():
            if not durations:
                return {"count": 0, "p50": None, "p95": None, "max": None}
            s = sorted(durations)
            rank = lambda p: s[math.ceil(p * len(s)) - 1]
            return {"count": len(s), "p50": rank(0.50), "p95": rank(0.95), "max": s[-1]}

        wrapper.latency = latency
        return wrapper
    return decorator

The durations are 1, 2, 3, 4 for the first four calls (the failed one included, thanks to finally), so p50 is the 2nd sorted value and p95 the 4th. The fifth call takes 10, and deque(maxlen=4) drops the oldest duration (1), so the window becomes 2, 3, 4, 10: p50 is now 3 and p95 is 10. A bounded window keeps memory constant and makes the statistics describe recent behaviour, which is what an alert should react to. Failed calls must be included: timeouts are often the slowest calls, and excluding them makes a degrading service look healthy. Production systems use histograms (Prometheus, OpenTelemetry) rather than raw samples, but the percentiles mean the same thing.

Interview

17. When is it safe to cache a function's results?

SolutionModel answer

When the result depends only on the arguments and the function has no side effects that callers rely on: the same arguments always give the same answer, and skipping the call changes nothing else. Pure computations qualify. Functions that depend on time, randomness, files, databases or the network can be cached only if you accept staleness, made explicit with a TTL or invalidation when the source changes. The key must include every input that affects the result: for LLM calls the model, the full prompt including system messages, tools and all parameters; sampling with temperature above 0 should usually not be cached. Arguments must be hashable, returned mutable objects are shared by all callers, the cache needs a size bound in long-running processes, and caches that cross users must not leak one user's data to another.

Interview

18. How does functools.lru_cache work, and what are its pitfalls?

SolutionModel answer

It wraps the function and keeps a dict from a key built from the positional and keyword arguments to the result, plus a doubly linked list that records usage order. A hit moves the entry to the most recent end and returns the stored object; a miss calls the function, stores the result and, if maxsize is exceeded, evicts the least recently used entry. Lookups and updates are O(1), it is thread-safe, and cache_info() and cache_clear() are available. Pitfalls: arguments must be hashable; f(1, 2) and f(1, b=2) are different keys; equal values of different types may or may not share a key unless typed=True; the returned object is shared, so mutating it corrupts the cache; @cache (unbounded) leaks memory when arguments keep changing; side effects inside the function run only on misses; decorating methods keeps every self alive; and the cache is per process, so it does not help other workers and disappears on restart.

Interview

19. Design the caching layer for an LLM application.

SolutionModel answer

Separate the caches by what they store. An exact response cache keyed by a hash of the canonical request (model, system prompt version, messages, tools, parameters), used only for deterministic requests, with a TTL that reflects how fresh answers must be, scoped per tenant or user when responses can contain private data, and stored in a shared store such as Redis so all workers benefit. An embedding cache keyed by model and text hash, long-lived, and invalidated by model version, which often saves the most money in RAG ingestion. A retrieval cache for search results with a short TTL, invalidated when the index is updated. A semantic cache (match similar rather than identical questions via embeddings) can raise the hit rate but risks returning an answer to a subtly different question, so it needs a strict similarity threshold and evaluation. Measure hit rate, savings and staleness, protect against cache stampedes when a popular entry expires, provider prompt caching (cached prefixes billed at a discount) complements but does not replace an application cache, and make it easy to bypass the cache for debugging and evaluation runs.

Recap

  • functools.lru_cache(maxsize=...) memoizes by hashable arguments and evicts the least recently used entry; cache_info() shows hits and misses.
  • Cache only results that depend on the arguments alone; the key must include everything that changes the answer (for LLMs: model, full prompt, parameters).
  • Bound caches in long-running code, never mutate returned objects, keep side effects outside cached functions, and use a TTL when freshness matters.
  • A retry decorator packages 7.4's policy; a decorator cannot stop a running synchronous call, so pass timeouts to the I/O itself.
  • Time with perf_counter, include failures, and report percentiles (p50, p95, p99), not just the mean.
