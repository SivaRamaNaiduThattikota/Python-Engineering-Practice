8.2 Decorators with arguments

@retry(times=3) has one more layer than a plain decorator: a factory that takes the settings and returns the decorator. The three levels step by step, validating settings at import time, decorators that work with and without parentheses, stacking several decorators and why their order matters, and what settings capture. Applied to validation, deprecation, rate limiting and fallbacks.

19 problems4 easy · 10 medium · 5 hard

1Three levels: settings, function, call

A plain decorator receives the function and nothing else. Many decorators need settings: how many times to retry, which range is valid, which role is required. The @ line can contain any expression that evaluates to a decorator, so the solution is a function that takes the settings and returns a decorator: a decorator factory. @retry(times=3) is evaluated in two steps: first retry(times=3) is called, returning a decorator; then that decorator is applied to the function below.

three_levels.py
import functools

def clip(lo, hi):                          # level 1: the settings
    def decorator(func):                   # level 2: the function
        @functools.wraps(func)
        def wrapper(*args, **kwargs):      # level 3: each call
            return max(lo, min(hi, func(*args, **kwargs)))
        return wrapper
    return decorator

@clip(0.0, 1.0)
def confidence(raw):
    return raw / 10

print(confidence(4), confidence(15), confidence(-3))

def similarity(a, b):
    return a - b
clipped = clip(-1, 1)(similarity)          # the same thing without @
print(clipped(5, 1), clipped(0.25, 0))
Output
0.4 1.0 0.0
1 0.25

Read it from the outside in. clip(0.0, 1.0) runs once, creates a decorator function that remembers lo and hi in its closure, and returns it. The @ then calls decorator(confidence), which creates a wrapper that remembers func, lo and hi, and binds confidence to it. Each call of confidence runs only the innermost level. Writing clip(-1, 1)(similarity) spells out the two calls that @clip(-1, 1) performs. Every level is an ordinary closure (3.4); there is no special decorator machinery.

Because the settings are fixed when the decorator is applied, which is usually at import time, it is the right moment to validate them. A factory that checks if times < 1: raise ValueError(...) before returning the decorator makes a misconfigured function fail as soon as the module is imported, with a clear message, instead of misbehaving on the first call in production. Taking settings as keyword-only arguments (def retry(*, times, on)) makes every decorator line self-describing: @retry(times=3, on=(TimeoutError,)).

validate_settings.py
import functools

def validate_range(**ranges):
    for name, (lo, hi) in ranges.items():          # checked once, at decoration time
        if lo > hi:
            raise ValueError(f"bad range for {name}: {lo} > {hi}")

    def decorator(func):
        @functools.wraps(func)
        def wrapper(**kwargs):
            for name, (lo, hi) in ranges.items():
                if name in kwargs and not lo <= kwargs[name] <= hi:
                    raise ValueError(f"{name} must be in [{lo}, {hi}], got {kwargs[name]}")
            return func(**kwargs)
        return wrapper
    return decorator

@validate_range(temperature=(0, 2), top_p=(0, 1))
def generate(**settings):
    return settings

print(generate(temperature=0.7, top_p=0.9))
for bad in [{"temperature": 3}, {"top_p": -0.1}]:
    try:
        generate(**bad)
    except ValueError as e:
        print("ValueError:", e)
try:
    validate_range(temperature=(2, 0))
except ValueError as e:
    print("at import:", e)
Output
{'temperature': 0.7, 'top_p': 0.9}
ValueError: temperature must be in [0, 2], got 3
ValueError: top_p must be in [0, 1], got -0.1
at import: bad range for temperature: 2 > 0

2What the settings capture

The factory's arguments are evaluated once, when the @ line runs, and stored in closures. So @log(level=LEVEL) captures the value LEVEL had at import time; changing the global variable later has no effect on already-decorated functions. That is usually what you want for fixed configuration, and occasionally a surprise. When a setting must be read at call time (a feature flag, a per-request limit), pass something the wrapper can call or look up on each call, such as a function or a config object, instead of a plain value.

capture.py
import functools

LEVEL = "info"
LOG = []

def log(level):
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            current = level() if callable(level) else level     # a callable is read on every call
            LOG.append((func.__name__, current))
            return func(*args, **kwargs)
        return wrapper
    return decorator

@log(LEVEL)
def fixed():
    return 1

@log(lambda: LEVEL)
def dynamic():
    return 2

fixed(); dynamic()
LEVEL = "debug"
fixed(); dynamic()
print(LOG)
Output
[('fixed', 'info'), ('dynamic', 'info'), ('fixed', 'info'), ('dynamic', 'debug')]

This is also why decorating functions in a loop with a factory works as expected, unlike the lambdas in a comprehension of 6.1. Each call of the factory creates a new closure with its own copy of the setting, so [clip(0, n)(f) for n in range(3)] gives three functions with three different limits. The late-binding problem only appears when several functions share one variable that changes after they were created (problem 16).

3Decorators that work with and without parentheses

With a factory, @log (no parentheses) is a bug: Python calls log(func), passing the function as the settings, and binds the name to the decorator that comes back. The function is then never called; calling it returns a wrapper (problem 3). Some libraries let both forms work, @log and @log(level="debug"), so users do not have to remember. The trick is to make the first parameter the optional function, and the settings keyword-only:

optional_parens.py
import functools

def log(func=None, *, level="info"):
    def decorator(f):
        @functools.wraps(f)
        def wrapper(*args, **kwargs):
            wrapper.events.append(level)
            return f(*args, **kwargs)
        wrapper.events = []
        return wrapper
    if func is None:            # called with settings: @log(level=...)
        return decorator
    return decorator(func)      # used bare: @log

@log
def a():
    return "a"

@log(level="debug")
def b():
    return "b"

print(a(), a.events, b(), b.events, a.__name__, b.__name__)
Output
a ['info'] b ['debug'] a b

Used bare, log receives the function as func and decorates it immediately. Called with keyword settings, func is None, so it returns the decorator, which @ then applies. The keyword-only marker * is what makes this unambiguous: a setting can never be passed positionally and mistaken for the function. pytest's @pytest.fixture and @pytest.fixture(scope="module"), and @dataclass versus @dataclass(frozen=True), work exactly this way. For your own code, supporting only one form is simpler and perfectly fine (problem 14 shows how easily the dual form goes wrong).

4Stacking decorators: order matters

Several decorators can sit on one function. They are applied from the bottom up: the one closest to the def wraps the function first, and the next one wraps that result. So @a / @b / def f means f = a(b(f)). At call time the order is the reverse: the outermost wrapper (a) runs first, calls b's wrapper, which calls the original; on the way back, results pass through b first and a last, like layers of an onion.

stacking.py
import functools

events = []

def layer(name):
    def decorator(func):
        events.append(f"apply {name}")
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            events.append(f"{name} before")
            result = func(*args, **kwargs)
            events.append(f"{name} after")
            return result
        return wrapper
    return decorator

@layer("outer")
@layer("inner")
def answer():
    events.append("answer runs")
    return 42

events.append("---")
answer()
print(events)
Output
['apply inner', 'apply outer', '---', 'outer before', 'inner before', 'answer runs', 'inner after', 'outer after']

The order changes behaviour, not just the log. A few combinations that come up in practice:

  • Timing and retries. @timed above @retry measures the whole operation including all attempts and waits, which is what a user experiences; below it, it times each attempt separately. Decide which number you want (problem 10).
  • Caching and everything else. A cache placed outermost answers repeated calls without running any inner layer: no logging, no rate limiting, no retries. Placed innermost, every call still goes through the outer layers, and only the function body is skipped (problem 8).
  • Permission checks and caching. An authorisation check must run before a cache, or a cached result computed for one user could be returned to another who is not allowed to see it.
  • Validation and retries. Validate outside the retry: retrying a call whose arguments are invalid can only fail again.

5Other ways to configure a decorator

A factory is not the only way to give a decorator settings. functools.partial can pre-fill the settings of a function that takes them along with the function: strict = partial(validate, strict=True), then @strict. Classes can act as decorators too, since any callable works after @: a class whose __init__ stores the settings and whose __call__ method takes the function is a factory with named, inspectable state; Module 9 covers __call__. And many frameworks hang decorators off an object, as in @app.get("/users") or @router.post(...): the object (app) holds the shared state, here the table of routes, and its method is the factory (8.4).

partial_and_metadata.py
import functools

def tag(func=None, **labels):
    if func is None:
        return functools.partial(tag, **labels)    # remember the settings, wait for the function
    func.labels = {**getattr(func, "labels", {}), **labels}
    return func                                    # metadata only: no wrapper at all

@tag(team="search", cost="low")
@tag(owner="ana")
def rerank(docs):
    return sorted(docs)

print(rerank.labels, rerank(["b", "a"]), rerank.__name__)
Output
{'owner': 'ana', 'team': 'search', 'cost': 'low'} ['a', 'b'] rerank

tag returns the original function after attaching metadata, so stacking two of them merges the labels, and there is no wrapper and no call overhead. functools.partial(tag, **labels) is the factory: it returns a callable that, when @ passes it the function, calls tag(func, **labels). Attaching metadata this way is how test frameworks mark tests (@pytest.mark.slow) and how some agent frameworks annotate tools with descriptions.

@retry calls retry(fetch_answer), passing the function as times. Write @retry(times=2) (or @retry()).

SolutionShow the solution and why
solution.py
import functools

def retry(times=2, on=(TimeoutError,)):
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            for attempt in range(1, times + 1):
                try:
                    return func(*args, **kwargs)
                except on:
                    if attempt == times:
                        raise
        return wrapper
    return decorator

state = {"calls": 0}

@retry(times=2)
def fetch_answer(q):
    state["calls"] += 1
    if state["calls"] == 1:
        raise TimeoutError("slow")
    return f"answer to {q}"

@retry without parentheses evaluates to retry(fetch_answer): the function was passed as times, and the result, the inner decorator, was bound to the name fetch_answer. Calling it with "refund?" treated the string as the function to decorate and returned a wrapper; the original never ran. With parentheses, the factory is called with the settings and its decorator is applied to the function. Making settings keyword-only (def retry(*, times=2, on=...)) turns this mistake into an immediate TypeError at import instead of a silent bug.

solution.py
import functools, inspect

def in_range(**ranges):
    def decorator(func):
        sig = inspect.signature(func)
        unknown = set(ranges) - set(sig.parameters)
        if unknown:
            raise TypeError(f"{func.__name__} has no parameter(s): {sorted(unknown)}")

        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            bound = sig.bind(*args, **kwargs)
            bound.apply_defaults()
            for name, (lo, hi) in ranges.items():
                value = bound.arguments[name]
                if not lo <= value <= hi:
                    raise ValueError(f"{name} must be in [{lo}, {hi}], got {value!r}")
            return func(*args, **kwargs)
        return wrapper
    return decorator

The factory holds the ranges; the decorator, which is the first level that sees the function, checks that every named range matches a real parameter, so a misspelling like temprature fails at import instead of silently never validating anything. Binding to the signature is what lets the check work no matter how the argument was passed, positionally (2.5) or by keyword (top_p=-1), and with defaults filled in. The signature is computed once per decorated function. The test re-decorates the original through __wrapped__, which wraps provides.

6. Decorated functions that share one cache

cached(maxsize) should give each decorated function its own cache of at most maxsize entries (dropping the oldest). Two decorated functions return each other's results for the same argument. Fix it.

Hint 1Open a hint

A mutable default (store={}) is created once, when def cached runs, and shared by every call of the factory (2.4).

Hint 2Open a hint

Create the dict inside decorator, so each decorated function gets a new one.

SolutionShow the solution and why
solution.py
import functools

def cached(maxsize):
    def decorator(func):
        store = {}

        @functools.wraps(func)
        def wrapper(x):
            if x not in store:
                if len(store) >= maxsize:
                    store.pop(next(iter(store)))
                store[x] = func(x)
            return store[x]
        wrapper.store = store
        return wrapper
    return decorator

store={} is a mutable default argument (2.4): one dict, created when def cached ran, shared by every call of the factory, so square(3) and double(3) used the same key 3 in the same dict and the second got the first's answer. State that belongs to one decorated function must be created in the decorator level, which runs once per function; state that belongs to one call goes in the wrapper. Dicts keep insertion order, so next(iter(store)) is the oldest key, which gives a simple first-in-first-out eviction; functools.lru_cache (8.3) evicts the least recently used instead.

SolutionShow the solution and why
solution.py
import functools, warnings

def deprecated(reason, alternative=None):
    def decorator(func):
        message = f"{func.__name__} is deprecated: {reason}"
        if alternative:
            message += f"; use {alternative}"

        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            if not wrapper.warned:
                wrapper.warned = True
                warnings.warn(message, DeprecationWarning, stacklevel=2)
            return func(*args, **kwargs)
        wrapper.warned = False
        return wrapper
    return decorator

The message is built once per function, at decoration time. stacklevel=2 makes the warning report the line that called embed_v1, which is the line someone needs to change, instead of the line inside the wrapper (7.3). Warning only once avoids flooding logs from a hot loop; the warnings module also deduplicates by location by default, but the test switches that off with simplefilter("always"), which is why the flag matters. Python 3.13 added warnings.deprecated as a ready-made decorator with the same idea, which type checkers also understand.

Both decorate an expensive function with a slow logging layer and a cache, then call it 20,000 times with 10 distinct arguments. Which order is faster?

10. Timing that measures the wrong thing

ask is meant to record one timing per call, covering all retries, so the dashboard shows what the user waited. It records one timing per attempt instead. Fix the decorator order (nothing else).

TestsThe 3 checks Run tests uses
assert ask("refund?") == "ok"
assert TIMINGS == [1]
assert ask.__name__ == "ask"
HintOpen a hint

The decorator listed first is the outermost. Which one should wrap the other?

SolutionShow the solution and why
solution.py
import functools

TIMINGS = []
ticks = iter([0, 1, 1, 3, 3, 4, 10, 11])
clock = lambda: next(ticks)

def timed(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        start = clock()
        try:
            return func(*args, **kwargs)
        finally:
            TIMINGS.append(clock() - start)
    return wrapper

def retry(times):
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            for attempt in range(1, times + 1):
                try:
                    return func(*args, **kwargs)
                except TimeoutError:
                    if attempt == times:
                        raise
        return wrapper
    return decorator

outcomes = iter([TimeoutError(), TimeoutError(), "ok"])

@timed
@retry(times=3)
def ask(q):
    out = next(outcomes)
    if isinstance(out, Exception):
        raise out
    return out

With @timed below @retry, the timing wrapper sat inside the retry loop, so each of the three attempts was timed separately and the user-visible total was never recorded. Moving @timed to the top makes it the outermost layer: one clock() before the whole retry sequence and one after, here the ticks 0 and 1. Both orders are legitimate measurements; per-attempt latency is useful for spotting a slow provider. The decorator order is the place to say which one you mean.

Hint 2Open a hint

SolutionShow the solution and why
solution.py
import functools
from collections import deque


class RateLimitExceeded(Exception):
    def __init__(self, message, retry_after):
        super().__init__(message)
        self.retry_after = retry_after


def rate_limited(calls, per, clock):
    if calls < 1 or per <= 0:
        raise ValueError("calls must be >= 1 and per > 0")

    def decorator(func):
        times = deque()

        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            now = clock()
            while times and times[0] <= now - per:
                times.popleft()
            if len(times) >= calls:
                wait = times[0] + per - now
                raise RateLimitExceeded(f"{func.__name__}: {calls} calls per {per}s exceeded", retry_after=wait)
            times.append(now)
            return func(*args, **kwargs)
        return wrapper
    return decorator

A sliding window keeps the exact times of recent calls, so the limit holds for any per-second window, not just fixed minutes on the clock. A deque makes dropping expired times from the left O(1). The deque is created in the decorator level, so embed and other have independent limits. Raising instead of sleeping keeps the decorator honest and testable, and retry_after gives the caller (or a retry decorator stacked outside it) the exact wait, like the server's Retry-After header (7.4). Rejected calls are not recorded, so waiting callers do not extend each other's wait. At now = 10, the call from time 0 has left the window (0 <= 10 - 10), which is why "d" is allowed.

SolutionShow the solution and why
solution.py
import functools

def with_fallbacks(*fallbacks, on=(TimeoutError, ConnectionError)):
    def decorator(func):
        chain = (func, *fallbacks)

        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            notes, last = [], None
            for f in chain:
                try:
                    result = f(*args, **kwargs)
                except on as e:
                    if last is not None:
                        notes.append(f"{last[0]}: {type(last[1]).__name__}: {last[1]}")
                    last = (f.__name__, e)
                    continue
                wrapper.last_source = f.__name__
                return result
            for note in notes:
                last[1].add_note(note)
            raise last[1]
        wrapper.last_source = None
        return wrapper
    return decorator

The primary and its fallbacks form one chain, tried in order with identical arguments, so fallbacks must accept the same call signature (canned takes **kwargs to ignore extras). Only the listed transient errors move on to the next option; a KeyError from a bug propagates from the first function that has it, as fallbacks must never hide bugs (7.3). When everything fails, the caller receives the last real exception, with each earlier failure recorded as a note, so the traceback tells the whole story without inventing a new exception type. last_source makes degradation visible to the caller and to metrics. This is the decorator form of the provider fallback in the 7.P client.

9Interview questions

Interview

17. Explain how a decorator with arguments works, level by level.

SolutionModel answer

It is a function that returns a decorator. @retry(times=3) is evaluated in two steps: first retry(times=3) is called (level one, the factory) and returns a decorator that has times in its closure; then that decorator is called with the function below (level two), and returns a wrapper that has both times and the function in its closure; the name is bound to that wrapper. At call time only level three, the wrapper, runs. So @retry(times=3) def f equals f = retry(times=3)(f). The factory is the right place to validate settings (fail at import), the decorator level the place for per-function state (a cache, counters, an inspected signature), and the wrapper the place for per-call work. Making settings keyword-only prevents @retry without parentheses from silently passing the function as a setting.

Interview

18. Does the order of stacked decorators matter? Give examples.

SolutionModel answer

Yes. Decorators are applied bottom-up, so @a @b def f is a(b(f)), and at call time a's wrapper runs first and sees everything b does. Examples: a timer outside a retry measures total latency including waits, inside it measures each attempt; a cache outside logging or rate limiting short-circuits them on hits, inside it does not; authorisation must sit outside a cache, or a cached result could be served to a user who is not allowed to see it; validation should sit outside retries, since retrying invalid input is pointless; a retry outside a rate limiter will retry rate-limit rejections, while inside it may hammer the limiter. Choosing the order is part of the design, and it is worth a comment when it matters.

Interview

19. You are asked to write a reusable @llm_call(model=..., retries=..., timeout=...) decorator for your team. What would you consider?

SolutionModel answer

Settings: keyword-only arguments validated in the factory, so a bad model name or negative retry count fails at import; sensible defaults; and the ability to read some settings at call time (a feature flag, a per-request timeout) through callables or a config object rather than values frozen at import. Behaviour: retries only on transient errors with backoff, jitter and a deadline (7.4), the timeout passed to every attempt, and clear exceptions from one hierarchy. Correctness: functools.wraps for names and signatures, support for both sync and async functions (detect with inspect.iscoroutinefunction and return the matching wrapper), and streaming generators. Observability: one trace span per logical call with attempts, latency, tokens, model and errors, without logging secrets or raw personal data. Testability: injectable clock, sleep and transport, and access to the undecorated function through __wrapped__. Composition: document how it should be ordered with caching and rate limiting. Finally, consider whether an explicit client object with methods is clearer than a decorator for this much configuration; the decorator is best when it stays thin.

Recap

  • A decorator with arguments is a factory: @retry(times=3) calls retry(times=3), which returns the decorator applied to the function.
  • Three levels, three jobs: validate settings in the factory, create per-function state in the decorator, do per-call work in the wrapper.
  • Settings are captured when the @ line runs; pass a callable to read a value at call time. Never use a mutable default for shared state.
  • Optional parentheses need func=None plus keyword-only settings; supporting one form is often simpler.
  • Stacked decorators apply bottom-up and run top-down: order decides what a timer measures, what a cache skips and where checks happen.
