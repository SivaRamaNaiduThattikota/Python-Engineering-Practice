2.3 Copies: shallow and deep

An alias, a shallow copy and a deep copy are three different things, and nested data (configs, chat messages, JSON, grids) is where the difference bites. Also: how to avoid copying at all.

20 problems4 easy · 9 medium · 7 hard

1Alias, shallow copy, deep copy

There are three different things people mean by "copy", and choosing the wrong one is behind most of the aliasing bugs from 2.2:

  • Alias: b = a. No copy at all, just a second name for the same object.
  • Shallow copy: a new outer container whose slots point at the same inner objects. list(a), a[:], a.copy(), dict(d), d.copy(), {**d}, set(s) and copy.copy(x) are all shallow.
  • Deep copy: copy.deepcopy(x) copies the outer container and everything inside it, at every level, so the result shares nothing mutable with the original.
shallow_deep.py
import copy

a = [[1, 2], [3]]
shallow = a.copy()
deep = copy.deepcopy(a)

shallow.append([4])          # outer level: only shallow changes
shallow[0].append(99)        # inner level: shared with a!
deep[1].append(7)            # deep shares nothing with a
print(a)
print(shallow)
print(deep)
print(a[0] is shallow[0], a[0] is deep[0])
Output
[[1, 2, 99], [3]]
[[1, 2, 99], [3], [4]]
[[1, 2], [3, 7]]
True False

A shallow copy is enough when the inner objects are immutable (a list of numbers or strings, a dict of strings), because nobody can change them anyway. You need a deep copy, or a smarter design, as soon as there is a mutable object inside: a list of dicts, a dict of lists, a nested config.

A shallow copy is like a new table of foreign keys pointing at the same dimension rows: add a row to your copy and the original does not see it, but edit a dimension row and both tables see it. A deep copy also duplicates the dimension rows.

2Building nested lists safely

The multiplication operator repeats references. [0] * 3 is fine because 0 is immutable. [[0] * 3] * 3 repeats one inner list three times, so the "grid" has a single row shared three times. Build each inner object separately with a comprehension, so the inner expression runs once per row.

grids.py
bad = [[0] * 3] * 3
bad[0][0] = 1
print(bad)

good = [[0] * 3 for _ in range(3)]
good[0][0] = 1
print(good)
print(len({id(r) for r in bad}), len({id(r) for r in good}))

3What deepcopy does for you, and what it costs

copy.deepcopy walks the whole structure and keeps a memo: a dict from the id of each object it has already copied to its copy. That gives it two properties you rarely think about, but rely on:

  • Shared objects stay shared inside the copy. If two slots of the original point at one list, the two slots of the copy point at one (new) list. The structure is preserved, not just the values.
  • Cycles work. A list that contains itself is copied without looping forever.
deepcopy_memo.py
import copy

shared = [0]
data = {"a": shared, "b": shared}
clone = copy.deepcopy(data)
clone["a"].append(1)
print(clone, data)
print(clone["a"] is clone["b"], clone["a"] is data["a"])
Output
{'a': [0, 1], 'b': [0, 1]} {'a': [0], 'b': [0]}
True False

The costs: deepcopy is pure Python and visits every object, so it is slow on big data (problem 8). It cannot copy some objects at all, such as open files, network connections, locks and generators, and it copies objects you may have wanted to share, like a large read-only lookup table or a loaded model. Classes can control this with __copy__ and __deepcopy__ methods (Module 9).

4Often the best copy is no copy

Copying is a defence against changes. Two designs need much less of it:

  • Build new values instead of changing old ones. cfg | {"temperature": 0.9}, row + [1.0], sorted(xs) and comprehensions all build new objects and leave the input alone, so there is nothing to protect.
  • Make shared data read-only. Tuples, frozenset and types.MappingProxyType (a read-only view of a dict) cannot be changed, so they can be shared freely (problem 17).
  • Copy only the path that changes. To change one nested value, copy the dicts along the path to it and reuse every other branch. This is called structural sharing, and it is how immutable data libraries stay fast (problem 14).
•
numpy and pandas

arr.copy() copies a numeric numpy array completely. df.copy() (deep by default) copies the data and the index, but not Python objects stored inside an object column, such as lists in a tags column (problem 13). With pandas 3 Copy-on-Write (2.2) you rarely need df.copy() just to protect a DataFrame from changes made through a derived one.

HintOpen a hint

* rows repeats one inner list. Make the inner list once per row instead.

SolutionShow the solution and why
solution.py
def make_grid(rows, cols):
    return [[0] * cols for _ in range(rows)]

In the comprehension, [0] * cols is evaluated once per row, so every row is its own list. [0] * cols itself is still fine, because the zeros are immutable ints: sharing them is harmless. The rule: multiplying a list is safe only when its items are immutable. For real numeric grids, np.zeros((rows, cols)) avoids the question completely.

SolutionShow the solution and why
solution.py
import copy

BASE = {"model": "small", "params": {"temperature": 0.0, "max_tokens": 256}, "tags": ["sweep"]}

def make_variants(temps):
    variants = []
    for t in temps:
        v = copy.deepcopy(BASE)
        v["params"]["temperature"] = t
        v["tags"].append(f"t={t}")
        variants.append(v)
    return variants

Each BASE.copy() is a new outer dict, but "params" and "tags" are the same objects in every variant and in BASE, so every change lands in one shared dict and one shared list. deepcopy gives each variant its own. A version without deepcopy builds the inner objects fresh: {**BASE, "params": {**BASE["params"], "temperature": t}, "tags": BASE["tags"] + [f"t={t}"]}. It is faster and shows exactly what changes, but it must be updated whenever BASE gains another nested value.

10. Merge layered settings

Settings come in layers: defaults, then environment, then the user's choices. Write merge_settings(base, override) that returns a new dict: nested dicts are merged key by key (recursively), any other value in override replaces the one in base. Neither input may change, and the result must not share any nested dict with base that the merge touched.

TestsThe 5 checks Run tests uses
base = {"llm": {"model": "small", "params": {"temperature": 0.2, "top_p": 1.0}}, "k": 5}

assert out == {"llm": {"model": "small", "params": {"temperature": 0.7, "top_p": 1.0}}, "k": 8, "debug": True}

Hint 1Open a hint

Start with out = dict(base). For each key in override: if both sides hold a dict, merge them by calling merge_settings again; otherwise take the override value.

Hint 2Open a hint

The recursive call returns a new dict, which is why the merged branches are not shared with base.

SolutionShow the solution and why
solution.py
def merge_settings(base, override):
    out = dict(base)
    for key, value in override.items():
        if isinstance(out.get(key), dict) and isinstance(value, dict):
            out[key] = merge_settings(out[key], value)
        else:
            out[key] = value
    return out

dict(base) copies one level, and each recursive call copies the next level down only along keys that are being merged. Branches that the override does not touch stay shared with base, which is safe as long as nobody changes the result in place. The last test shows the type rule: a non-dict override replaces a whole dict. This is how configuration libraries (Hydra, Pydantic settings, Helm values files) layer settings, and base | override would be wrong here because it replaces "llm" entirely.

14. Change one nested value, share the rest

Write with_override(config, path, value) that returns a new config where the nested key at path (a tuple of keys) is set to value. Copy only the dicts along the path, and reuse every other branch as it is (structural sharing). Missing dicts along the path are created. The input must not change.

Hint 1Open a hint

One level at a time: copy the current dict, then set its key to the result of the same operation one level down.

Hint 2Open a hint

When path has one key left, that key simply gets value. Use config.get(key, {}) for missing levels.

SolutionShow the solution and why
solution.py
def with_override(config, path, value):
    key, rest = path[0], path[1:]
    new = dict(config)
    if rest:
        new[key] = with_override(config.get(key, {}), rest, value)
    else:
        new[key] = value
    return new

Each call copies exactly one dict, and only the dicts on the path get copied, so the cost depends on the depth, not the size of the config. Everything else is shared, which is safe because nothing is changed in place. This is structural sharing, the idea behind Redux-style state updates, Clojure's data structures and pyrsistent. Compared to deepcopy of a big config for each of 1,000 sweep variants, it is both faster and lighter on memory, and new["retriever"] is base["retriever"] proves nothing was copied needlessly.

solution.py
TEMPLATES = {
    "qa": {
        "messages": [
            {"role": "system", "content": "Answer from the context only."},
            {"role": "user", "content": "Context: {context}\nQuestion: {question}"},
        ],
        "examples": [{"q": "What is RAG?", "a": "Retrieval-augmented generation."}],
    }
}


def build_prompt(name, context, question, extra_examples=()):
    template = TEMPLATES[name]
    messages = [
        {**m, "content": m["content"].format(context=context, question=question)}
        for m in template["messages"]
    ]
    examples = template["examples"] + list(extra_examples)
    return {"messages": messages, "examples": examples}

Two different copying mistakes. list(...) is a shallow copy, so the loop rewrites the template's message dicts: after the first request, {question} is gone from the template and every later user gets the first user's question. And examples = template["examples"] is a plain alias, so extend grows the template's list on every request. The fix builds new objects instead of copying and then changing: a new dict per message with {**m, "content": ...}, and template["examples"] + list(extra_examples) for a new list. In a web server these bugs are worse than here, because one user's data leaks into other users' prompts. Treating templates as read-only data (tuples, MappingProxyType) would make Python raise instead.

Hint 1Open a hint

Recursion again: a dict becomes MappingProxyType({k: freeze_config(v) for ...}), a list becomes a tuple of frozen items.

Hint 2Open a hint

Building new inner dicts is what stops later changes to cfg showing through.

SolutionShow the solution and why
solution.py
from types import MappingProxyType

def freeze_config(cfg):
    if isinstance(cfg, dict):
        return MappingProxyType({k: freeze_config(v) for k, v in cfg.items()})
    if isinstance(cfg, list):
        return tuple(freeze_config(v) for v in cfg)
    return cfg

MappingProxyType is a read-only window onto a dict: reading works, and assigning raises TypeError. A window onto the original dict would still show changes made to that dict, so the function builds a new dict at every level and only then wraps it. Lists become tuples, which have no append at all. The result can be passed around freely: there is nothing left to copy defensively. Pydantic's frozen=True models and frozen dataclasses (Module 11) give the same guarantee for typed configs.

18. What is the difference between a shallow and a deep copy, and when do you need each?

SolutionModel answer

A shallow copy creates a new outer container but fills it with references to the same inner objects (list(x), x[:], dict.copy(), copy.copy). A deep copy (copy.deepcopy) recursively copies the inner objects too, using a memo so shared references and cycles are preserved. Shallow is enough when the contents are immutable, or when you will only change the outer container. Deep is needed when you will change nested mutable objects and must not affect the original. Mention the costs of deepcopy (slow, cannot copy files, locks, connections, copies large shared objects needlessly), the cheaper alternatives (copy exactly as deep as the data, build new values instead of changing old ones, read-only structures), and the pandas detail that df.copy() does not copy Python objects inside object columns.

19. You need 1,000 variants of a large nested config, each changing a few values. How do you build them efficiently?

SolutionModel answer

Deep-copying the whole config 1,000 times works but costs time and memory proportional to the full size each time. Better: structural sharing. Copy only the dicts along the path you change and reuse untouched branches, which makes each variant cost proportional to the depth of the change. This is safe only if nobody changes configs in place, so make them read-only (MappingProxyType, frozen dataclasses or Pydantic models) or agree that configs are treated as immutable values. If the variants come from a grid of options, generate them lazily with itertools.product and build each one only when a run starts, so 1,000 configs never sit in memory at once. Hyperparameter sweep tools also create each trial's settings when the trial starts, for the same reason.

20. Does df.copy() give you a completely independent DataFrame?

SolutionModel answer

Mostly. df.copy() defaults to deep=True, which copies the underlying data arrays and the index, so writes to the copy's columns do not affect the original. But for object columns, the copied array holds references to the same Python objects: lists, dicts or custom objects in the cells are shared, so changing one of them in place through the copy changes the original as well. The pandas docs state that Python objects are not copied recursively. copy.deepcopy(df) does not fully solve this either, because pandas implements it as df.copy(deep=True). You would apply copy.deepcopy to those cells yourself. Also mention that with pandas 3 Copy-on-Write you rarely need df.copy() to protect against changes through a derived DataFrame, since that can no longer happen.

Recap

  • b = a is no copy. Shallow copies (list(a), a[:], dict(d), copy.copy) duplicate one level. copy.deepcopy duplicates every level.
  • A shallow copy is enough when the contents are immutable. Nested mutable data (configs, messages, JSON) needs a deeper copy or a different design.
  • Multiplying a list repeats references: [[0] * 3] * 3 is one row three times. Build nested lists with a comprehension.
  • deepcopy keeps shared objects shared and handles cycles, but it is slow and copies everything. Copy exactly as deep as the data needs.
  • Often the best copy is none: build new values, share read-only data, and copy only the path that changes. df.copy() does not copy Python objects inside cells.
