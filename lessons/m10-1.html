1The protocol, by hand

Lesson 6.3 showed what a for loop does: it calls iter(obj) once to get an iterator, then next(iterator) repeatedly until StopIteration is raised. In terms of the data model (9.2), iter(obj) calls obj.__iter__() and next(it) calls it.__next__(). So to make your own objects work with for, list(), sum(), unpacking and comprehensions, you implement those two methods. An iterator class keeps the position of the walk as state: __next__ returns the next item and advances, or raises StopIteration when there is nothing left; its __iter__ returns self, so an iterator can be used wherever an iterable is expected.

by_hand.py
class Countdown:
    """An iterator: it remembers where it is."""

    def __init__(self, start):
        self.current = start

    def __iter__(self):
        return self

    def __next__(self):
        if self.current <= 0:
            raise StopIteration
        value = self.current
        self.current -= 1
        return value

c = Countdown(3)
print(next(c), next(c), list(c), list(c))
print(sum(Countdown(4)), [x * 10 for x in Countdown(2)], max(Countdown(5)))
Output
3 2 [1] []
10 [20, 10] 5

next(c) twice takes 3 and 2; list(c) drains what is left, 1; and a second list(c) gets nothing, because the iterator's state is exhausted and nothing resets it. That is the defining property of an iterator: one pass. Raising StopIteration is the only correct way to say "no more items"; returning None would be treated as an item, and a loop would never end.

2Iterable containers and one-shot iterators

A list can be looped over any number of times because it is not an iterator itself: each iter(my_list) creates a new list iterator starting at the beginning. Your container classes should work the same way. Their __iter__ must return a fresh iterator each time, not self, so that two loops (or a nested loop over the same object) each get their own position. Making a container its own iterator is a classic bug: the second loop silently sees nothing (problem 3).

There are therefore two separate roles, often played by two classes: the iterable (the container, holding the data, with an __iter__ that builds an iterator) and the iterator (a lightweight object holding only a reference to the data and a position). Python's built-ins follow this split: list and list_iterator, dict and dict_keyiterator, range and range_iterator.

iterable_vs_iterator.py
class Playlist:
    def __init__(self, songs):
        self._songs = list(songs)

    def __iter__(self):
        return PlaylistIterator(self._songs)     # a new iterator every time

class PlaylistIterator:
    def __init__(self, songs):
        self._songs = songs
        self._i = 0

    def __iter__(self):
        return self

    def __next__(self):
        if self._i >= len(self._songs):
            raise StopIteration
        song = self._songs[self._i]
        self._i += 1
        return song

p = Playlist(["intro", "verse", "outro"])
print(list(p), list(p))
print([(a, b) for a in p for b in p if a < b][:3])     # nested loops need independent iterators
it = iter(p)
print(next(it), iter(it) is it, iter(p) is iter(p))
Output
['intro', 'verse', 'outro'] ['intro', 'verse', 'outro']
[('intro', 'verse'), ('intro', 'outro'), ('outro', 'verse')]
intro True False

3Generators: the easy way to write __iter__

Writing a separate iterator class is a lot of ceremony for "walk my items". A generator function returns a new generator, which is an iterator, every time it is called (6.3), so making __iter__ itself a generator gives you exactly the fresh-iterator behaviour of a container, with the position and the StopIteration handled for you. In most code this is the right way to make a class iterable.

generator_iter.py
class Playlist:
    def __init__(self, songs):
        self._songs = list(songs)

    def __iter__(self):
        for song in self._songs:          # or simply: yield from self._songs
            yield song

    def __len__(self):
        return len(self._songs)

class Dataset:
    def __init__(self, rows):
        self._rows = rows

    def __iter__(self):
        for row in self._rows:
            if row.get("label") is not None:     # iteration can filter or transform lazily
                yield row["text"], row["label"]

p = Playlist(["intro", "verse"])
print(list(p), list(p), len(p))
d = Dataset([{"text": "win now", "label": 1}, {"text": "?", "label": None}, {"text": "lunch", "label": 0}])
print(list(d), dict(d))
Output
['intro', 'verse'] ['intro', 'verse'] 2
[('win now', 1), ('lunch', 0)] {'win now': 1, 'lunch': 0}

Write a class with __next__ by hand when the iterator needs more than iteration: extra methods such as peek() or close(), state that callers inspect while iterating (how many pages fetched, the text accumulated so far), or a way to be passed around and resumed by several consumers. Otherwise, a generator method is shorter, harder to get wrong, and faster (problem 8).

4Useful forms: iter(callable, sentinel) and peeking

iter() has a second form: iter(func, sentinel) creates an iterator that calls func() with no arguments on every step and stops when the result equals sentinel. It turns "call this until it returns the end marker" into a loop, and the classic use is reading a binary stream in fixed-size chunks: iter(lambda: f.read(8192), b"") yields chunks until read returns empty bytes. Combined with functools.partial, it reads queues, sockets and paginated APIs in the same way.

iter_sentinel.py
import io
from functools import partial

stream = io.BytesIO(b"abcdefghij")
print(list(iter(partial(stream.read, 4), b"")))

queue = ["job1", "job2", "STOP", "job3"]
for job in iter(lambda: queue.pop(0), "STOP"):
    print("processing", job)
print("left in queue:", queue)
Output
[b'abcd', b'efgh', b'ij']
processing job1
processing job2
left in queue: ['job3']

Another common need is to look at the next item without consuming it: a parser deciding what to do based on the next token, a merge step comparing heads of streams. Plain iterators cannot do that, so a small wrapper class keeps one item in a buffer: peek() fills the buffer if needed and returns it; __next__ returns the buffered item first. Because it needs an extra method, this is a case where a hand-written iterator class is the right tool (problem 7).

5Lazy objects: computing on demand

An iterable does not have to hold its items. range(10**12) uses almost no memory because it computes each number when asked. Your classes can do the same: a paginated API client fetches one page of results at a time while the caller loops, and stops fetching as soon as the caller stops; a sliding window over a token list computes each window on the fly; a dataset reads rows from disk as they are needed. Laziness means the first item is available immediately and memory does not grow with the total size (problem 5).

lazy_pages.py
class Pages:
    """Iterate over all items of a paginated API, fetching pages only as needed."""

    def __init__(self, fetch):
        self.fetch = fetch                 # fetch(cursor) -> (items, next_cursor or None)
        self.pages_fetched = 0

    def __iter__(self):
        cursor = None
        while True:
            items, cursor = self.fetch(cursor)
            self.pages_fetched += 1
            yield from items
            if cursor is None:
                return

DATA = {None: (["a", "b"], "p2"), "p2": (["c", "d"], "p3"), "p3": (["e"], None)}
pages = Pages(lambda cursor: DATA[cursor])
print(list(pages), pages.pages_fetched)
pages.pages_fetched = 0
first_three = []
for item in pages:
    first_three.append(item)
    if len(first_three) == 3:
        break
print(first_three, pages.pages_fetched)
Output
['a', 'b', 'c', 'd', 'e'] 3
['a', 'b', 'c'] 2

Stopping after three items fetched only two pages, because the generator inside __iter__ was simply never resumed. A lazy class can still offer __len__ when the length can be computed without iterating (a window count from the list length, 9.2); if it cannot, it should not pretend, since len() is expected to be cheap.

6Iteration traps

StopIteration inside a generator. Calling next(it) without a default inside a generator body, when it is exhausted, raises StopIteration inside the generator. Before Python 3.7 that silently ended the generator; since PEP 479 it is turned into a RuntimeError: generator raised StopIteration, because silently ending hid bugs. Use next(it, default) or catch StopIteration explicitly and return (problem 6).

pep479.py
def pairs(items):
    it = iter(items)
    for first in it:
        second = next(it)            # raises StopIteration when the length is odd
        yield first, second

def safe_pairs(items):
    it = iter(items)
    for first in it:
        second = next(it, None)
        yield first, second

print(list(safe_pairs([1, 2, 3])))
try:
    list(pairs([1, 2, 3]))
except RuntimeError as e:
    print("RuntimeError:", e)
Output
[(1, 2), (3, None)]
RuntimeError: generator raised StopIteration

Changing what you are iterating. Adding to or removing from a list while looping over it skips or repeats items (2.2), and changing a dict's or set's size during iteration raises RuntimeError: dictionary changed size during iteration. Iterate over a copy (list(d)) or collect changes and apply them after the loop. Your own iterators should either detect such changes or document that the underlying data must not change during iteration (problem 12).

Sharing one iterator. Two consumers of the same iterator split its items between them, which is sometimes the point (zip(it, it), 6.4) and usually a bug. Hand each consumer its own iterator from the iterable, or use itertools.tee if the source can only be read once.

solution.py
import datetime as dt

class DayRange:
    def __init__(self, start, end):
        self.start = start
        self.end = end

    def __len__(self):
        return max(0, (self.end - self.start).days + 1)

    def __iter__(self):
        for i in range(len(self)):
            yield self.start + dt.timedelta(days=i)

    def __contains__(self, day):
        return self.start <= day <= self.end

    def __repr__(self):
        return f"DayRange({self.start}, {self.end})"

Because __iter__ is a generator function, every loop gets a new generator starting at day 0, so the range can be iterated twice, as the test does. The dates are computed on demand, like range, so a range of ten years costs nothing until it is used. __contains__ answers with two comparisons instead of walking every day, which is what in would do by default (9.2). Month and year boundaries are handled by timedelta arithmetic, never by hand. Date ranges like this drive backfills and daily evaluation jobs.

solution.py
from itertools import islice

class SearchResults:
    def __init__(self, fetch, page_size):
        self.fetch = fetch
        self.page_size = page_size
        self.offsets = []

    def __iter__(self):
        offset = 0
        while True:
            self.offsets.append(offset)
            page = self.fetch(offset, self.page_size)
            yield from page
            if len(page) < self.page_size:
                return
            offset += self.page_size

    def first(self, n):
        return list(islice(self, n))

The generator fetches a page, hands its results out one at a time, and fetches the next page only when the consumer asks for more, so first(4) stops after two pages: islice simply stops pulling. A short page signals the end; when the total is an exact multiple of the page size, one extra fetch returns an empty page, which is unavoidable without a total count (the last test). Each for loop gets a new generator starting at offset 0, so the object is re-iterable. Vector database clients, Slack and GitHub API wrappers, and boto3 paginators expose large result sets exactly this way.

HintOpen a hint

next(it, None) returns None instead of raising when the iterator is exhausted.

SolutionShow the solution and why
solution.py
def key_values(tokens):
    it = iter(tokens)
    for key in it:
        value = next(it, None)
        yield key, value

Inside a generator, an exhausted next(it) raises StopIteration from the generator's own body. Since Python 3.7 (PEP 479), Python converts that into a RuntimeError, because silently ending the generator early used to hide real bugs: the caller would just see fewer items. next(it, default) handles "no more items" explicitly. SolutionShow the solution and why
solution.py
_MISSING = object()


class Peekable:
    def __init__(self, iterable):
        self._it = iter(iterable)
        self._buffer = []

    def __iter__(self):
        return self

    def __next__(self):
        if self._buffer:
            return self._buffer.pop()
        return next(self._it)

    def peek(self, default=_MISSING):
        if not self._buffer:
            try:
                self._buffer.append(next(self._it))
            except StopIteration:
                if default is _MISSING:
                    raise
                return default
        return self._buffer[0]

    def __bool__(self):
        try:
            self.peek()
        except StopIteration:
            return False
        return True

Peeking needs state that survives between calls (the buffered item) and an extra method, so this is a job for an iterator class rather than a generator. The buffer holds at most one item, and next drains it first, so the order of items is preserved and the source is never read more than one item ahead, which the read list checks; that matters when the source is a network stream. __bool__ peeks to answer "anything left?". The sentinel default distinguishes peek() (raise) from peek(None) (return None). The more-itertools package ships this as peekable, which parsers and tokenisers use constantly.

Make __iter__ a generator over range(0, len(self.rows), self.size) (6.1); drop pos and __next__.

Hint 2Open a hint

The number of batches is a ceiling division: -(-n // size) or (n + size - 1) // size.

SolutionShow the solution and why
solution.py
class Batches:
    def __init__(self, rows, size):
        if size < 1:
            raise ValueError("size must be at least 1")
        self.rows = list(rows)
        self.size = size

    def __iter__(self):
        for start in range(0, len(self.rows), self.size):
            yield self.rows[start:start + self.size]

    def __len__(self):
        return (len(self.rows) + self.size - 1) // self.size

Two bugs. The end test pos + size > len(rows) refused to produce a batch unless a full one fitted, so the last row was silently never trained on, and __len__ used floor division and agreed with the bug. And the object was its own iterator, so after the first epoch pos stayed at the end and every later epoch iterated nothing, which in a training loop looks like "the model stopped improving". Generating batches with a stepped range and slices (which stop safely at the end) fixes both, and __len__ now uses ceiling division, so progress bars and learning-rate schedules based on len(batches) are right. PyTorch's DataLoader has a drop_last option precisely because dropping the partial batch should be a choice, not an accident.

Regular window starts: range(0, n - size + 1, stride), whose length you can take with len(range(...)) without iterating.

Hint 2Open a hint

There is an extra final window when the last regular start plus size is less than n.

SolutionShow the solution and why
solution.py
class Windows:
    def __init__(self, tokens, size, stride):
        if not 1 <= stride <= size:
            raise ValueError("need 1 <= stride <= size")
        self.tokens = list(tokens)
        self.size = size
        self.stride = stride

    def _starts(self):
        return range(0, len(self.tokens) - self.size + 1, self.stride)

    def __len__(self):
        n = len(self.tokens)
        if n == 0:
            return 0
        if n <= self.size:
            return 1
        starts = self._starts()
        return len(starts) + (starts[-1] + self.size < n)

    def __iter__(self):
        n = len(self.tokens)
        if n == 0:
            return
        if n <= self.size:
            yield list(self.tokens)
            return
        starts = self._starts()
        for s in starts:
            yield self.tokens[s:s + self.size]
        if starts[-1] + self.size < n:
            yield self.tokens[-self.size:]

The windows are computed lazily, one slice per step, so a long document never has all its windows in memory at once; the generator __iter__ makes the object re-iterable. len() is answered by arithmetic on a range object (whose own len and indexing are O(1)), plus one for the end-aligned window, so it is cheap and always agrees with the iteration, which the tests check case by case. The boolean in len(starts) + (condition) counts as 0 or 1. Embedding pipelines use the length to size progress bars and to batch requests before reading any window.

Hint 1Open a hint

Keep a deque of iterators. __next__ pops one from the left, tries next on it, and appends it back on the right if it produced an item.

Hint 2Open a hint

If it is exhausted, drop it and try the next; raise StopIteration when the deque is empty.

SolutionShow the solution and why
solution.py
from collections import deque

class RoundRobin:
    def __init__(self, *iterables):
        self._queue = deque(iter(it) for it in iterables)

    @property
    def active(self):
        return len(self._queue)

    def __iter__(self):
        return self

    def __next__(self):
        while self._queue:
            it = self._queue.popleft()
            try:
                item = next(it)
            except StopIteration:
                continue
            self._queue.append(it)
            return item
        raise StopIteration

A deque of iterators rotates in O(1): take the front one, get one item, put it at the back, which produces the round-robin order. An exhausted iterator is simply not put back, so active (a property over the deque's length, 9.3) shrinks as streams end. Because each step pulls exactly one item from exactly one iterator, infinite sources work and nothing is read ahead. Interleaving like this is used to mix training data sources fairly, to merge results from several retrievers, and in schedulers that give tasks equal turns. A generator could produce the same order, but the class exposes active while iterating.

SolutionShow the solution and why
solution.py
class LineReader:
    def __init__(self, text):
        self._lines = [line.strip() for line in text.splitlines() if line.strip()]

    def __iter__(self):
        yield from self._lines

    def numbered(self):
        return list(enumerate(self, start=1))

    def __len__(self):
        return len(self._lines)

Three bugs grew from one decision: storing an iterator in __init__ made the object one-shot. len() counted by iterating, which consumed every line, so the very first list(r) after len(r) was empty, a destructive len that no caller would expect. numbered() called next(self) to "skip" something, which threw away the first line, and enumerate without start=1 numbered from 0. Storing the cleaned list makes iteration repeatable, len O(1) and non-destructive, and numbered a one-liner. For huge files, where storing every line is not an option, the class would keep the path and open the file afresh in each __iter__ (10.2), still re-iterable, and len would have to be dropped or documented as expensive.

class TokenStream:
    def __init__(self, deltas):
        self._source = deltas
        self._it = iter(deltas)
        self._pieces = []
        self.finished = False
        self._closed = False

    @property
    def text(self):
        return "".join(self._pieces)

    @property
    def count(self):
        return len(self._pieces)

    def __iter__(self):
        return self

    def __next__(self):
        if self._closed or self.finished:
            raise StopIteration
        try:
            piece = next(self._it)
        except StopIteration:
            self.finished = True
            raise
        self._pieces.append(piece)
        return piece

    def close(self):
        self._closed = True
        close = getattr(self._it, "close", None)
        if close is not None:
            close()

    def read_all(self):
        for _ in self:
            pass
        return self.text

A streaming response is consumed incrementally, but other code (a UI, a logger, a token counter) needs to ask during the stream how much has arrived, and the handler needs to stop it when the user cancels. That combination of iteration plus inspectable state plus extra methods is exactly when a hand-written iterator class beats a generator. finished is set only when the source itself is exhausted, so a closed stream is distinguishable from a completed one, which matters when logging whether an answer was cut short. close() forwards to the source's close, which for a generator runs its finally block (6.3), releasing the HTTP connection in a real SDK. The OpenAI and Anthropic SDKs return stream objects with this shape (iterable, closable, with accumulated state).

Interview

17. When you design a class that should be iterable, how do you decide between returning self from __iter__ and returning a new iterator?

SolutionModel answer

Containers (objects that hold or can recompute their items: a collection, a dataset, a range, a result set that can be fetched again) should return a new iterator from every __iter__ call, so that several loops, nested loops and repeated epochs each get their own position, like lists do; the simplest implementation is a generator method. An object should return self only if it is itself a one-shot stream whose state is the position: a network stream, a file object, a token stream, a peekable wrapper, a cursor. Such iterators must also implement __next__ and raise StopIteration at the end. The classic bug is a container that returns self and keeps a position attribute: the second loop is silently empty. If re-iteration is expensive (re-fetching pages), document it, or cache the results deliberately.

Interview

18. What happens when StopIteration is raised inside a generator, and why?

SolutionModel answer

Since Python 3.7 (PEP 479), if a StopIteration propagates out of a generator's body, for example from a bare next(it) on an exhausted iterator, Python replaces it with RuntimeError: generator raised StopIteration. Before that change, the stray StopIteration simply ended the generator, so a bug in the middle of the generator looked like a normal, shorter stream, and loops consuming it silently lost data. The correct ways to end a generator are to fall off the end of its body or to return (whose value becomes the StopIteration.value, used by yield from). When pulling from another iterator inside a generator, use next(it, default) or catch StopIteration and return explicitly. In hand-written iterator classes, raising StopIteration from __next__ is still the correct signal.

Interview

19. How would you expose a large remote result set (a paginated API or a database cursor) as a Python iterable?

SolutionModel answer

Wrap it in a class whose __iter__ is a generator that fetches one page (or batch of rows) at a time and yields its items, so memory stays bounded, the first results arrive immediately, and the consumer stopping early (a break, islice) stops the fetching. Use the API's cursor or continuation token rather than offsets where possible, since offsets shift when data changes and get slower deep into the set. Handle transient errors per page with retries and backoff, respect rate limits between pages, and set timeouts (7.4). Decide and document whether the object is re-iterable (each loop re-queries from the start) or a one-shot stream (like a DB cursor); offer a first(n) helper and avoid __len__ unless the API reports a total cheaply. Make sure resources are released when iteration stops early: closing the generator runs its finally, and a context manager (10.2) makes that explicit. Expose counters such as pages fetched for observability.

Recap

  • for calls iter(obj) then next(it) until StopIteration; implement __iter__ (and, for iterators, __next__ raising StopIteration).
  • Containers return a new iterator from every __iter__ (usually a generator method); only one-shot streams return self.
  • Prefer a generator __iter__; write an iterator class when you need extra methods (peek, close) or inspectable state.
  • iter(func, sentinel) loops until a sentinel; lazy classes fetch or compute on demand and can offer an arithmetic __len__.
  • Traps: exhausted iterators, StopIteration inside generators becomes RuntimeError (use next(it, default)), and changing collections while iterating.
