7.3 Designing error handling

The decisions behind good error handling: asking permission or forgiveness, where in a program to handle each error, why swallowed errors are the worst bugs, logging a traceback once, keeping data consistent when a step fails halfway, and degrading gracefully with fallbacks and warnings. Applied to agents, batch jobs and LLM features.

1Asking permission or forgiveness

There are two styles of dealing with operations that may fail. LBYL, "look before you leap", checks every condition first: if key in d: value = d[key]. EAFP, "easier to ask forgiveness than permission", just does it and handles the failure: try: value = d[key] / except KeyError: .... Python's culture leans towards EAFP, and there are good reasons, but neither is always right.

eafp_lbyl.py
import os, tempfile

config = {"model": "small"}

# LBYL: check, then act
if "temperature" in config:
    t = config["temperature"]
else:
    t = 0.7

# EAFP: act, then handle failure
try:
    t2 = config["temperature"]
except KeyError:
    t2 = 0.7

t3 = config.get("temperature", 0.7)      # the best tool when it exists
print(t, t2, t3)

path = os.path.join(tempfile.mkdtemp(), "cache.json")
try:
    with open(path, encoding="utf-8") as f:   # EAFP for files: no gap between check and use
        data = f.read()
except FileNotFoundError:
    data = "{}"
print(data)
Output
0.7 0.7 0.7
{}

EAFP wins in three situations. Races: with files, network resources and anything shared, the world can change between the check and the action. if os.path.exists(p): open(p) can still fail if another process deletes the file in between, a class of bug called TOCTOU ("time of check to time of use"). Only the try version is correct. Duck typing: instead of checking isinstance(x, list), just use x the way you need and handle the error, so tuples, generators and custom types work too. Many conditions: when validity depends on several things (the key exists, the value is a dict, it has the right field), one try around the access is clearer than a pyramid of ifs (problem 10).

LBYL wins in others. When failure is common, raising and catching costs far more than a test (7.1). When the failure would happen after side effects, for example halfway through writing a file or sending a batch, checking first avoids leaving things half done. And when the check is a built-in, such as dict.get, getattr(obj, name, default) or str.isdigit, it is both clear and fast. The best code often uses both: check what can be checked cheaply up front, and still handle the failures that only reality can reveal.

2Where to handle each error

Every exception is eventually handled somewhere, even if "somewhere" is the top level, where Python prints a traceback and stops. The design question is which layer should handle it. The rule of thumb: handle an error at the lowest level that knows what to do about it, and let it travel up until then. A function that parses a date does not know whether a bad date should skip the record, ask the user again or abort the import, so it should raise; the import loop knows, so it handles.

In a typical application the layers look like this. The lowest layer (parsing, database or API access) raises specific errors and translates library exceptions into the application's own types (7.2). The middle layer (business logic) handles what it can (retry a transient failure, use a default) and lets the rest pass. The boundary (the HTTP handler, the CLI's main, the loop of a batch job or an agent) catches broadly, logs the traceback, and converts the error into a result for the outside world: an HTTP 400 or 500 response, an exit code, a failed-record entry, or an error message for the model.

layers.py
class NotFoundError(Exception):
    pass

DB = {"u1": {"name": "Ana", "plan": "pro"}}

def get_user(user_id):                       # lowest layer: raise specific errors
    try:
        return DB[user_id]
    except KeyError:
        raise NotFoundError(f"no user {user_id!r}") from None

def plan_limit(user_id):                     # middle layer: logic, no handling it cannot do
    return {"pro": 1000, "free": 50}[get_user(user_id)["plan"]]

def handle_request(user_id):                 # boundary: turn errors into responses
    try:
        return 200, {"limit": plan_limit(user_id)}
    except NotFoundError as e:
        return 404, {"error": str(e)}
    except Exception as e:
        return 500, {"error": "internal error"}   # and log the traceback (below)

print(handle_request("u1"), handle_request("u9"))
Output
(200, {'limit': 1000}) (404, {'error': "no user 'u9'"})

The middle function contains no try at all, and that is correct: it has nothing useful to do with a missing user. A common anti-pattern is the opposite, try/except in every function "to be safe", each one logging, wrapping or returning None. It makes the code longer, hides the real origin of errors and produces the same failure logged five times. Fail fast at the bottom, handle once at the right level.

A stored procedure that hits a constraint violation should not catch it and carry on; it raises, the transaction rolls back, and the application that called it decides whether to show "this email already exists". 3Never swallow errors

The most damaging error-handling bug is the swallowed exception: except Exception: pass, or except: return None. The program keeps running, nothing is logged, and the output is quietly wrong, sometimes for months. A crash is visible and gets fixed; a swallowed error produces a dashboard that is 3% too low with no trace of why. If you genuinely want to ignore one specific, expected error, make it explicit and narrow, so a reader can see the decision. contextlib.suppress exists for exactly that (10.3).

suppress_vs_swallow.py
import contextlib, os, tempfile

path = os.path.join(tempfile.mkdtemp(), "lock.tmp")

with contextlib.suppress(FileNotFoundError):   # "it is fine if the file is already gone"
    os.remove(path)
print("cleanup done, nothing to remove")

def risky_average(values):
    try:
        return sum(values) / len(values)
    except Exception:
        return None                            # swallowed: callers cannot tell why

print(risky_average([]), risky_average(["3", "4"]), risky_average([3, 4]))
Output
cleanup done, nothing to remove
None None 3.5

risky_average returns None for an empty list (a normal edge case) and for strings (a bug in the caller) alike, and the None will cause a TypeError somewhere far away. Better: decide what the normal edge case should return, make that explicit (if not values: return 0.0 or raise ValueError("no values")), and let the bug crash where it happens (problem 3).

Returning None for failure has one more problem: callers forget to check it. When a function can fail in a way callers must handle, raising is usually safer than a special return value. When "no result" is a normal answer, such as a search with no match, None is fine, but document it, and use a type hint like str | None (11.1) so tools remind callers to check.

4Logging an exception, once

When you handle an error at a boundary, record it with its traceback, not just its message. str(e) for a KeyError is only 'model', which tells you nothing about where it happened. The logging module (12.3) has logger.exception(message), which logs at error level and automatically appends the full traceback of the exception being handled; outside an except block, pass exc_info=True or exc_info=e. Use it once, at the place that handles the error.

log_exception.py
import io, logging

stream = io.StringIO()
logger = logging.getLogger("demo")
logger.addHandler(logging.StreamHandler(stream))
logger.propagate = False

def load(cfg):
    return cfg["model"]["name"]

try:
    load({"model": None})
except Exception as e:
    logger.error("load failed: %s", e)           # message only
    logger.exception("load failed")               # message and traceback
lines = stream.getvalue().splitlines()
print(lines[0])
print(lines[1], "| has traceback:", any(l.startswith("Traceback") for l in lines[2:]), "| last:", lines[-1])
Output
load failed: 'NoneType' object is not subscriptable
load failed | has traceback: True | last: TypeError: 'NoneType' object is not subscriptable

The first line says only that 'NoneType' object is not subscriptable; the second gives the traceback with the function and line. The opposite mistake is logging at every level: each function catches, logs and re-raises, so one failure produces five log entries with five partial tracebacks, and on-call engineers count five incidents. Either handle an error (and log it there) or let it pass untouched (problem 6). Adding context on the way up is better done with add_note or a translated exception (7.2) than with extra log lines.

5Leaving data consistent

An exception can interrupt a function halfway through a change: three of five orders applied, half of a file written, the cache updated but not the database. The caller then holds data in a state that no code path was designed for. The defence is to make changes all or nothing, using one of three patterns:

  • Validate everything first, then change. Check every input before the first modification, so the change itself cannot fail halfway for a predictable reason (problem 7).
  • Build new, then swap. Compute the complete new state in a separate object (a copy, a new list, a temporary file), and only when it is complete, replace the old one in a single step. If anything fails, the old state is untouched.
  • Undo on failure. If changes must happen in place, record what was done and reverse it in an except block, then re-raise. Databases do this for you with transactions.
all_or_nothing.py
def apply_discounts_in_place(prices, discounts):
    for item, pct in discounts.items():
        prices[item] = round(prices[item] * (1 - pct), 2)    # fails halfway on an unknown item

def apply_discounts(prices, discounts):
    new = dict(prices)                                    # build new...
    for item, pct in discounts.items():
        if item not in new:
            raise KeyError(f"unknown item {item!r}")
        new[item] = round(new[item] * (1 - pct), 2)
    return new                                            # ...the caller swaps

prices = {"pen": 2.0, "book": 10.0}
try:
    apply_discounts_in_place(prices, {"pen": 0.5, "lamp": 0.1})
except KeyError:
    pass
print(prices)                                             # half applied

prices = {"pen": 2.0, "book": 10.0}
try:
    prices = apply_discounts(prices, {"pen": 0.5, "lamp": 0.1})
except KeyError as e:
    print("rejected:", e)
print(prices)                                             # untouched
Output
{'pen': 1.0, 'book': 10.0}
rejected: "unknown item 'lamp'"
{'pen': 2.0, 'book': 10.0}

Files follow the same idea: write to a temporary file in the same directory, and when writing has fully succeeded, call os.replace(tmp, final), which swaps the file into place in one step on every operating system. A crash during writing leaves the old file intact instead of a truncated one (problem 9). Model checkpoints, indexes and caches should always be saved this way.

6Fallbacks, degradation and warnings

Sometimes the right response to a failure is to continue with less: answer from a cache when the model API is down, switch to a smaller model when the large one times out, return keyword search results when the vector store is unreachable. This is graceful degradation, and it is a deliberate product decision, not a way to hide errors. Two rules keep it honest: degrade only on the specific failures you planned for (timeouts, rate limits, connection errors, not every exception), and record every degradation (a log entry, a metric, a flag in the response), so you know how often users get the reduced version (problem 5).

For problems that are not errors but deserve attention, such as a deprecated option, a suspicious input that was accepted, or a fallback that was used, Python has the warnings module. warnings.warn(message, category) emits a warning without stopping the program; by default each distinct warning is shown once, and tests or applications can turn warnings into errors or collect them. Libraries use DeprecationWarning to announce changes before they break anyone.

warnings_demo.py
import warnings

def build_request(prompt, temperature=None, temp=None):
    if temp is not None:
        warnings.warn("'temp' is deprecated, use 'temperature'", DeprecationWarning, stacklevel=2)
        temperature = temp
    if temperature is not None and temperature > 1.5:
        warnings.warn(f"temperature {temperature} is unusually high", UserWarning, stacklevel=2)
    return {"prompt": prompt, "temperature": temperature}

with warnings.catch_warnings(record=True) as caught:
    warnings.simplefilter("always")
    print(build_request("hi", temp=1.8))
print([(w.category.__name__, str(w.message)) for w in caught])

with warnings.catch_warnings():
    warnings.simplefilter("error")             # strict mode, as in tests
    try:
        build_request("hi", temp=0.2)
    except DeprecationWarning as e:
        print("raised:", e)
Output
{'prompt': 'hi', 'temperature': 1.8}
[('DeprecationWarning', "'temp' is deprecated, use 'temperature'"), ('UserWarning', 'temperature 1.8 is unusually high')]
raised: 'temp' is deprecated, use 'temperature'

stacklevel=2 makes the warning point at the caller's line instead of the line inside the library, which is where the fix belongs. Turning warnings into errors in a test suite (pytest's -W error, 13.1) catches deprecated usage before an upgrade removes it.

solution.py
def dig(data, path, default=None):
    current = data
    try:
        for part in path.split("."):
            current = current[int(part)] if isinstance(current, list) else current[part]
    except (KeyError, IndexError, ValueError, TypeError):
        return default
    return current

One try around the whole walk replaces a check at every level for "is it a dict, does it have the key, is it a list, is the index in range". The four exception types are exactly the ways a path can fail to fit: missing key, index out of range, a non-numeric index for a list, and indexing something that is not a container (an int here). Anything else, such as a NameError, would still surface. This is how helpers like jmespath or glom behave, and it is convenient for optional fields; for fields that must exist, validate the response with a schema instead (11.4), so a missing field is an error, not a silent default.

def mean_score(scores):
    if not scores:
        return 0.0
    return sum(scores) / len(scores)

The broad handler merged two different situations: an empty list, a normal edge case that deserves a defined answer, and a list of strings, a bug in the caller that deserves a crash at its source. Note that 0.0 for "no scores" is a choice; for some reports None (with a type hint saying so) or an exception would be the right one, but it must be one decision, made on purpose.

solution.py
def answer(question, primary, fallback, events):
    try:
        text = primary(question)
    except (TimeoutError, ConnectionError) as e:
        events.append(("fallback", type(e).__name__, question))
        return fallback(question), "fallback"
    else:
        return text, "primary"

Only the failures you planned for, slow or unreachable service, trigger the fallback; a KeyError is a bug, and answering with the small model would hide it. The fallback call sits inside the except block but is not itself protected, so if the fallback also fails, the caller sees that error (with the primary's error attached as context). The event record is what makes degradation measurable: a dashboard of fallback rate tells you when the "temporary" fallback has become the normal path. Returning the source lets the UI or the logs mark degraded answers.

7. All orders or none

Write apply_orders(stock, orders) where stock maps item to quantity and orders is a list of (item, qty). Return a new stock dict with all orders applied. If any order is for an unknown item, has a non-positive quantity, or would take an item's stock below zero (counting earlier orders in the same batch), raise ValueError describing the first problem, and leave stock unchanged.

TestsThe 2 checks Run tests uses

Hint 1Open a hint

Hint 2Open a hint

SolutionShow the solution and why
solution.py
def apply_orders(stock, orders):
    new = dict(stock)
    for item, qty in orders:
        if item not in new:
            raise ValueError(f"unknown item {item!r}")
        if qty <= 0:
            raise ValueError(f"quantity must be positive, got {qty} for {item!r}")
        if new[item] < qty:
            raise ValueError(f"not enough {item!r}: {new[item]} left, {qty} ordered")
        new[item] -= qty
    return new

Building a new dict means an exception at any order simply abandons the copy: the caller's stock was never modified, so there is nothing to undo. Checking against new rather than stock accounts for earlier orders in the same batch, which is why two book orders of 2 and 1 fail when only 2 books exist. The caller completes the change with stock = apply_orders(stock, orders), a single step. This is the "build new, then swap" pattern; a database gives the same guarantee with a transaction.

9. A crash that leaves half a file

save_labels(path, labels) writes one label per line. If a label is not a string, it crashes halfway and the existing file is left truncated. Make the write atomic: on failure the old file must be untouched and no temporary file left behind; on success the new content replaces it.

SolutionShow the solution and why
solution.py
import os

def save_labels(path, labels):
    tmp = path + ".tmp"
    try:
        with open(tmp, "w", encoding="utf-8") as f:
            for label in labels:
                f.write(label + "\n")
        os.replace(tmp, path)
    except BaseException:
        if os.path.exists(tmp):
            os.remove(tmp)
        raise

Opening the real file with "w" truncates it immediately, so any crash afterwards loses the old content. Writing to a temporary file in the same directory and swapping it in with os.replace means the real file is only ever the complete old version or the complete new one; os.replace overwrites the target in one step on every platform. The cleanup handler catches BaseException deliberately, so even Ctrl+C removes the temporary file, and it always re-raises, so nothing is swallowed. The temporary file must be on the same file system as the target for the swap to be atomic, which is why it sits next to it.

    pass

13. A circuit breaker

When a provider is down, calling it again and again wastes time and quota. Write make_breaker(fn, max_failures, reset_after, clock) returning a function call(*args). It calls fn(*args) normally. After max_failures consecutive exceptions it opens: further calls raise CircuitOpenError immediately, without calling fn, until reset_after seconds have passed (measured with clock()). Then the next call is a trial: success closes the breaker and resets the count; failure opens it again for another reset_after. Exceptions from fn propagate unchanged. Define CircuitOpenError.

Hint 1Open a hint

Hint 2Open a hint

SolutionShow the solution and why
solution.py
class CircuitOpenError(Exception):
    pass


def make_breaker(fn, max_failures, reset_after, clock):
    failures = 0
    opened_at = None

    def call(*args):
        nonlocal failures, opened_at
        if opened_at is not None:
            if clock() - opened_at < reset_after:
                raise CircuitOpenError(f"circuit open for {reset_after - (clock() - opened_at):.1f}s more")
            trial = True
        else:
            trial = False
        try:
            result = fn(*args)
        except Exception:
            failures += 1
            if trial or failures >= max_failures:
                opened_at = clock()
            raise
        failures = 0
        opened_at = None
        return result

    return call

The breaker has three states. Closed: calls go through and failures are counted. Open: calls fail immediately with CircuitOpenError, protecting both your users (no waiting for a timeout) and the struggling provider (no extra load). Half-open: once the cool-down has passed, one trial call decides whether to close again or reopen. The state lives in the closure (3.4), updated with nonlocal; Module 9 would make it a class. Injecting clock instead of calling time.time() makes the behaviour testable without sleeping, a pattern you will use again in 13.2. The bare raise keeps fn's exception unchanged, and a success at any time resets the consecutive count. Libraries such as pybreaker implement the same states, and LLM gateways use breakers per provider so traffic can fail over to another one.

def transform(record):

        raise ValueError(f"bad email in record {record.get('id')}")

solution.py
def process(items, fn, max_error_rate, min_items):
    results, failures = [], []
    last_error = None
    for i, item in enumerate(items):
        try:
            results.append(fn(item))
        except ValueError as e:
            failures.append((i, str(e)))
            last_error = e
        processed = i + 1
        if processed >= min_items and len(failures) / processed > max_error_rate:
            raise RuntimeError(
                f"error budget exceeded: {len(failures)} of {processed} items failed"
            ) from last_error
    return results, failures

Skipping bad items is right when they are rare; when they are common, something systematic has gone wrong (a schema change, a broken upstream export, a model that stopped following the format), and processing the rest only wastes time and produces a misleading result. An error budget distinguishes the two automatically. min_items avoids aborting on one bad item at the very start, when the rate is meaningless. The RuntimeError is chained from the last ValueError, so the traceback shows a concrete example of the failure. Only ValueError counts as a bad item; the TypeError from None is a bug and propagates immediately. Evaluation harnesses and labelling pipelines use exactly this rule.

Interview

17. Explain EAFP and LBYL. When would you choose each, and what is a TOCTOU bug?

SolutionModel answer

LBYL ("look before you leap") checks preconditions before acting: if key in d, if os.path.exists(path). EAFP ("easier to ask forgiveness than permission") performs the operation and handles the exception if it fails. EAFP is idiomatic Python and is the only correct option when the condition can change between the check and the use: a file can be deleted after exists() returns True, which is a time-of-check-to-time-of-use (TOCTOU) race; it also supports duck typing and replaces deep nests of checks with one try. LBYL is better when failure is frequent (exceptions are expensive to raise), when a failure would leave partial side effects, and when a cheap built-in check exists (dict.get, getattr with a default). In practice, validate the inputs you can check up front and still handle the failures only reality can reveal.

Interview

18. In a layered application (data access, business logic, API), where should exceptions be caught?

SolutionModel answer

Catch an exception at the lowest layer that can do something meaningful with it, and nowhere else. The data-access layer translates library errors (driver, HTTP client) into the application's own exception types with raise ... from, and handles only what it truly can, such as retrying a dropped connection. The business layer applies decisions (a default, a fallback, a retry policy) and otherwise lets errors propagate; most of its functions need no try at all. The API or CLI boundary catches everything left, maps known error types to responses (404 for not found, 400 for validation, 429 for rate limits), logs unexpected ones once with their traceback and returns a generic 500 without leaking internals. Anti-patterns are catching in every layer, logging at every level, and converting exceptions to None return values that callers forget to check.

Interview

19. How would you design graceful degradation for an LLM-powered feature?

SolutionModel answer

Start from what the user should get when each dependency fails. Put strict timeouts on model calls, retry transient errors a limited number of times with backoff, and use a circuit breaker per provider so an outage fails fast instead of making every request wait. Define fallbacks in order of quality: another provider or a smaller model, a cached answer for repeated questions, a non-LLM result (keyword search results instead of a generated answer), and finally a clear message ("the assistant is unavailable, here are relevant articles"). Trigger fallbacks only on specific failures, never on bugs or validation errors, and record every degradation in logs and metrics with the reason, so fallback rate and latency are monitored and alerting fires when degraded mode becomes common. Mark degraded responses so the UI can show it and evaluations can exclude them. Test the failure paths deliberately, with fake clients that time out or return errors, because fallbacks that are never exercised tend to be broken when they are finally needed.

Recap

  • EAFP (try, then handle) avoids races and pyramids of checks; LBYL (check first) suits common failures, side effects and cheap built-in checks like get.
  • Handle each error at the lowest layer that can act on it; translate at the bottom, decide in the middle, convert to responses at the boundary.
  • Never swallow: no except: pass, no None for errors callers will not check. Ignore specific errors explicitly with contextlib.suppress.
  • Log once, with the traceback (logger.exception), at the place that handles the error.
  • Keep data consistent: validate first, build new then swap (os.replace for files), or undo on failure. Degrade gracefully, and record it.
