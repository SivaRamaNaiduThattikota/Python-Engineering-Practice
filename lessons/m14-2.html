14.2 Threads and futures

Threads are the simplest way to overlap I/O in Python: calls to model APIs, downloads, database queries. threading briefly, then concurrent.futures, which is what you should use: executors, futures, submit, map and as_completed, error handling, keeping results out of shared state, locks for the state you must share, and how many threads to use. On this site executors run each task immediately and in order (14.1), so problems check correctness; run them locally for real overlap.

16 problems4 easy · 8 medium · 4 hard

1threading.Thread in brief

A threading.Thread(target=fn, args=(...)) runs fn in a new thread once you call start(); join() waits for it to finish. The calling code continues immediately after start(), which is the point: while one thread waits for a network reply, others run. Raw threads have two awkward properties. They return nothing: a target's return value is discarded, so results must be passed back through shared structures. And an exception in a thread does not reach the code that started it: it is printed by threading.excepthook and the thread ends, while join() returns normally (problem 10). daemon=True threads are killed abruptly when the program exits, which suits background helpers but loses work in progress.

For almost all application code, use concurrent.futures instead: it manages a pool of threads, passes return values and exceptions back, and fits in a with block. Reach for raw threads only for long-lived background workers (a log shipper, a heartbeat), usually communicating through a queue.Queue.

2Executors and futures

ThreadPoolExecutor(max_workers=n) keeps n worker threads. executor.submit(fn, *args, **kwargs) schedules one call and immediately returns a Future. future.result(timeout=None) waits for the call and returns its value, or re-raises its exception in the calling thread, with the original traceback; future.exception() returns the exception instead of raising, future.done() tells whether it finished, future.cancel() cancels a call that has not started, and add_done_callback(fn) runs fn(future) when it finishes. Using the executor in a with block calls shutdown(wait=True) at the end, so the block does not exit until every submitted call is done, and no new work can be submitted afterwards.

Two ways to collect results. executor.map(fn, items) returns an iterator of results in input order, like the built-in map, and if a call raised, iterating re-raises that exception when its turn comes, so results after it are lost unless you handle errors inside fn. as_completed(futures) yields futures as they finish, fastest first, which lets you process or report results early, show progress, and handle each error separately; keep a dict from future to input to know which input each result belongs to. concurrent.futures.wait(futures, return_when=FIRST_EXCEPTION) waits until the first failure, for fail-fast batches.

futures.py
from concurrent.futures import ThreadPoolExecutor, as_completed

def classify(text):
    if not text:
        raise ValueError("empty message")
    return "spam" if "prize" in text.lower() else "ham"

messages = ["Win a PRIZE", "Lunch?", "", "Prize draw today"]
with ThreadPoolExecutor(max_workers=4) as pool:
    futures = {pool.submit(classify, m): i for i, m in enumerate(messages)}
    results = [None] * len(messages)
    for future in as_completed(futures):
        i = futures[future]
        error = future.exception()
        results[i] = f"error: {error}" if error else future.result()
print(results)

with ThreadPoolExecutor(max_workers=4) as pool:
    it = pool.map(classify, messages)
    print(next(it), next(it))
    try:
        next(it)
    except ValueError as e:
        print("map raised:", e)
Output

spam ham
map raised: empty message

The dict from future to index puts every result back in its place whatever the completion order, and each failure is recorded rather than aborting the batch. With map, the first two results arrive normally, and the third raises when iterated.

3Results instead of shared state

The safest concurrent code shares nothing mutable: each task receives its inputs, returns its result, and the caller combines results after collecting them. Then there is nothing to race on. When tasks must update shared state, protect it with threading.Lock: with lock: around every read-modify-write of that state, kept as short as possible (never around a network call, or the threads queue behind the lock and you are back to sequential). RLock can be re-acquired by the thread that holds it. queue.Queue is a thread-safe FIFO for producer and consumer threads, with blocking put and get. Individual operations on built-in containers, such as list.append, happen to be safe in CPython, but compound ones (if key not in d: d[key] = ..., counter += 1) are not, and code should not rely on implementation details, especially with free-threaded Python arriving.

Clients deserve a note: most HTTP and LLM SDK clients (httpx.Client, requests.Session, the OpenAI and Anthropic clients) are designed to be shared across threads and reuse connections; create one and pass it to the tasks rather than one per call. Check each library's documentation, because some objects (such as database connections or SQLite cursors) must not be shared.

4How many threads

For I/O-bound work, the right number of threads is set by what you are waiting on, not by CPU cores: Little's law (14.1) gives the concurrency needed for a target throughput, and the provider's rate limits and the remote service's capacity cap it. The default max_workers is min(32, os.cpu_count() + 4), a reasonable start for mixed workloads. Too many threads waste memory (each has its own stack), increase contention, and can overload the service you call; for thousands of concurrent requests, asyncio (14.4) scales better. Always set timeouts on network calls made from threads: a thread stuck on a request without a timeout is a worker lost for good.

from concurrent.futures import ThreadPoolExecutor, as_completed


def fetch_all(fetch, urls, max_workers=8):
    unique = list(dict.fromkeys(urls))
    results = {}
    with ThreadPoolExecutor(max_workers=max_workers) as pool:
        futures = {pool.submit(fetch, url): url for url in unique}
        for future in as_completed(futures):
            url = futures[future]
            error = future.exception()
            results[url] = f"error: {type(error).__name__}: {error}" if error else future.result()
    return {url: results[url] for url in unique}

Each URL becomes one future, and the dict from future to URL tells the collector which result is which, whatever the completion order; rebuilding the output in input order makes the function's result deterministic even though threads finish in any order. Using exception() turns each failure into data instead of aborting the batch, which is what a crawler or an evaluation run needs. Deduplicating first avoids paying twice for the same call.

from concurrent.futures import ThreadPoolExecutor

def process_all(fn, items, max_workers=4):
    with ThreadPoolExecutor(max_workers=max_workers) as pool:
        futures = [pool.submit(fn, item) for item in items]
    errors = [f.exception() for f in futures if f.exception() is not None]
    if errors:
        raise RuntimeError(f"{len(errors)} of {len(futures)} items failed") from errors[0]
    return [f.result() for f in futures]

An exception raised inside a submitted call is stored in its future; if nobody calls result() or exception(), it is simply garbage-collected with the future, and the failure leaves no trace, a common reason a "parallel" job silently processes half its data. Keeping the futures, in input order, makes every outcome inspectable after the with block (which waited for all of them). Reporting the count and chaining the first error (7.2) keeps the summary short while preserving a full traceback for debugging.

from concurrent.futures import ThreadPoolExecutor


def map_with_retry(fn, items, attempts=3, retry_on=(TimeoutError, ConnectionError), max_workers=8):
    def one(item):
        for attempt in range(1, attempts + 1):
            try:
                return {"item": item, "ok": True, "value": fn(item), "error": None, "attempts": attempt}
            except retry_on as e:
                last = e
            except Exception as e:
                return {"item": item, "ok": False, "value": None, "error": f"{type(e).__name__}: {e}", "attempts": attempt}
        return {"item": item, "ok": False, "value": None, "error": f"{type(last).__name__}: {last}", "attempts": attempts}

    with ThreadPoolExecutor(max_workers=max_workers) as pool:
        return list(pool.map(one, items))

Putting the retry loop inside the task keeps each item's retries on its own worker, so one slow item does not delay the others, and wrapping every outcome in a record makes map's ordered results safe to collect: no exception escapes, so nothing is lost. Retrying only transient errors (timeouts, dropped connections) and failing fast on others (a ValueError from bad input will fail every time) saves time and money. A production version adds backoff with jitter between attempts (13.3) and a shared rate limiter (problem 9).

solution.py
from collections import Counter
from concurrent.futures import ThreadPoolExecutor


def count_words(doc):
    return Counter(doc.lower().split())


def count_words_parallel(docs, max_workers=4):
    total = Counter()
    with ThreadPoolExecutor(max_workers=max_workers) as pool:
        for counts in pool.map(count_words, docs):
            total.update(counts)
    return dict(total)

TOTALS[word] = TOTALS.get(word, 0) + 1 is a read followed by a write, so two threads counting the same word can both read 3 and both write 4 (14.1), and the module-level dict also carried counts over from earlier calls, so the second call returned doubled numbers. Returning results and merging them in the caller removes the shared state entirely: workers are pure functions, which are trivially thread-safe and easy to test, and the merge happens in one thread. This map-then-reduce shape is how distributed systems such as Spark and MapReduce avoid shared counters too. (Word counting is CPU-bound, so in practice it belongs on processes, 14.3; the pattern is the same.)

A future starts pending; set_result (which the executor's worker calls) completes it and runs its callbacks with the future as argument. from concurrent.futures import ThreadPoolExecutor


def embed_corpus(texts, embed_batch, batch_size=32, max_workers=4):
    batches = [texts[i:i + batch_size] for i in range(0, len(texts), batch_size)]
    vectors = []
    with ThreadPoolExecutor(max_workers=max_workers) as pool:
        for i, (batch, out) in enumerate(zip(batches, pool.map(embed_batch, batches))):
            if len(out) != len(batch):
                raise ValueError(f"batch {i} returned {len(out)} vectors for {len(batch)} texts")
            vectors.extend(out)
    return vectors

Embedding APIs accept batches, so the work splits naturally into batch calls that overlap their network waits on a thread pool. map returns batch results in submission order, so concatenating them restores the original text order without any bookkeeping, which is essential: a vector paired with the wrong text silently corrupts a search index. The length check guards against a provider dropping an input, which would otherwise shift every later vector by one. batch_size is set by the provider's limits (texts and tokens per request) and max_workers by its rate limits.

9. A thread-safe token bucket

Write TokenBucket(rate, capacity, clock=time.monotonic) for client-side rate limiting shared by many threads: it starts full, refills at rate tokens per second up to capacity, and try_acquire(n=1) takes n tokens and returns True if available, else returns False without taking any. import threading, time


class TokenBucket:
    def __init__(self, rate, capacity, clock=time.monotonic):
        self.rate, self.capacity, self.clock = rate, capacity, clock
        self.tokens = float(capacity)
        self.last = clock()
        self._lock = threading.Lock()

    def _refill(self):
        now = self.clock()
        self.tokens = min(self.capacity, self.tokens + (now - self.last) * self.rate)
        self.last = now

    def try_acquire(self, n=1):
        if n > self.capacity:
            raise ValueError(f"cannot acquire {n} tokens from a bucket of {self.capacity}")
        with self._lock:
            self._refill()
            if self.tokens >= n:
                self.tokens -= n
                return True
            return False

    def wait_time(self, n=1):
        with self._lock:
            self._refill()
            return max(0.0, (n - self.tokens) / self.rate)

A token bucket allows short bursts (up to capacity) while holding the long-run rate to rate per second, which is how most API rate limits behave. The refill is computed lazily from elapsed time, so no background thread is needed. The lock makes "refill, check, take" one atomic step: without it, two threads could both see one remaining token and both take it, exceeding the limit. The injected clock makes the class deterministic to test (13.3). In a thread pool, a worker calls try_acquire before each request and sleeps for wait_time() when it fails; the asyncio version in 14.5 has the same logic.

                error = future.exception()
                if error is None:
                    alive.append((i, future.result()))
                else:
                    failed.append((i, name, f"{type(error).__name__}: {error}"))
    return {"results": [value for _, value in alive], "failed": sorted(failed)}

Ingestion jobs are pipelines (fetch, clean, chunk, embed), and each stage is a batch of independent calls, so each runs in parallel on one shared pool. Carrying the original index with every value is what lets results and failures be reported in input order and traced back to the input, however the threads interleave; failed items leave the pipeline at the stage that failed and are recorded with that stage's name, which tells the operator where to look. Processing stage by stage is simple and keeps memory bounded per stage; a streaming design (each item flows on as soon as it finishes a stage) improves latency and is what queues between stages or asyncio tasks (14.5) provide.

def scrape(urls, fetch, parse, max_workers=8):
    with ThreadPoolExecutor(max_workers=max_workers) as pool:
        futures = [(url, pool.submit(_work, url, fetch, parse)) for url in urls]
    pages, errors = [], {}
    for url, future in futures:
        error = future.exception()
        if error is None:
            pages.append(future.result())
        else:
            pages.append(None)
            errors[url] = f"{type(error).__name__}: {error}"
    return {"pages": pages, "errors": errors}

Raw threads swallow exceptions into excepthook, so failures were invisible; futures keep them for the caller. And scrape returned before the threads finished, so callers saw a partial list; the executor's with block waits for all tasks.

13. as_completed, wait and timeouts

from concurrent.futures import ThreadPoolExecutor, as_completed, wait, FIRST_EXCEPTION, ALL_COMPLETED

def job(x):
    if x == 3:
        raise RuntimeError("job 3 failed")
    return x * x

with ThreadPoolExecutor(max_workers=4) as pool:
    futures = [pool.submit(job, x) for x in range(5)]
    done, pending = wait(futures, return_when=ALL_COMPLETED)
    print(len(done), len(pending), sorted(f.result() for f in done if f.exception() is None))
    done, pending = wait(futures, return_when=FIRST_EXCEPTION)
    print(len(done) >= 1, [type(f.exception()).__name__ for f in futures if f.exception()])
    values = sorted(f.result() for f in as_completed(futures) if not f.exception())
    print(values, futures[2].result(timeout=1))
    print(sum(1 for _ in as_completed(futures, timeout=5)), all(f.done() for f in futures))

wait splits futures into finished and unfinished sets; with all of them complete, everything is in done, and the failed one is among them, holding its exception. FIRST_EXCEPTION returns as soon as one future has failed (or all are done). Sorting the results from as_completed makes the output independent of the completion order, which varies between runs with real threads, a habit worth keeping whenever results are printed or asserted. result(timeout=...) and as_completed(timeout=...) raise TimeoutError if futures do not finish in time, the tools for bounding how long a batch may wait.

8Interview questions

Interview

14. Why use a ThreadPoolExecutor rather than creating threads yourself?

SolutionModel answer

An executor bounds concurrency with a fixed pool, so a list of 10,000 items does not create 10,000 threads or overload the service being called; it reuses threads instead of paying creation costs per task; it returns futures, so each call's return value or exception comes back to the caller with its traceback, where raw threads discard return values and only print exceptions; it offers map (ordered results) and as_completed (completion order), timeouts, cancellation of not-yet-started work and wait policies; and as a context manager it guarantees all work has finished (or been cancelled) when the block ends. Swapping ThreadPoolExecutor for ProcessPoolExecutor moves CPU-bound work to processes with the same code. Raw threads remain appropriate for long-lived background loops.

Interview

15. How do you make code safe to call from several threads?

SolutionModel answer

First minimise shared mutable state: make tasks pure functions of their inputs that return results, and combine results in one thread afterwards; use immutable data (tuples, frozen dataclasses) for shared configuration. For state that must be shared (caches, counters, rate limiters, connection pools), guard every compound operation with a threading.Lock, keeping critical sections short and never holding a lock across slow I/O; acquire several locks in one global order to avoid deadlocks. Use thread-safe structures (queue.Queue for hand-offs, threading.Event for signals) instead of hand-made flags. Check that the libraries you share are documented as thread-safe (HTTP clients usually are; database connections often are not, so use a pool or one per thread, or threading.local). Test with stress tests and deterministic interleaving tools, and remember that the GIL never made compound operations atomic, and free-threaded Python removes even the incidental protection it gave.

Interview

16. A colleague used threads to speed up a CPU-heavy feature extraction and it got slower. Explain and fix it.

SolutionModel answer

With the GIL, only one thread executes Python bytecode at a time, so pure-Python CPU work cannot run in parallel on threads; it runs one thread at a time with extra overhead from switching and lock contention, which makes it slower than a plain loop. Threads help only when work waits (I/O) or runs in C code that releases the GIL. The fix depends on the work: vectorise with NumPy or pandas, whose inner loops run in C (often several times faster on its own, and some operations use several cores); move the work to processes with ProcessPoolExecutor, chunking the input so each task is large enough to amortise the cost of sending data between processes (14.3); or, on a free-threaded Python build with compatible libraries, threads do run in parallel. Measure before and after with wall time and CPU time, and check Amdahl's law: if part of the pipeline is serial (reading one file, writing one output), that part bounds the speed-up.

Recap

  • Prefer concurrent.futures to raw threads: executors bound concurrency, and futures carry results and exceptions back.
  • submit returns a Future (result() re-raises, exception() inspects); map keeps input order and raises at the failing item; as_completed yields in completion order.
  • Keep a dict from future to input, rebuild outputs in input order, and turn per-item errors into data so a batch survives failures.
  • Avoid shared mutable state: return results and merge them; when state must be shared, guard compound operations with a Lock, briefly.
  • Size I/O thread pools by latency and rate limits (Little's law), share thread-safe clients, and always set timeouts.
