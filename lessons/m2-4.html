2.4 How arguments are passed

Calling a function points its parameter names at your objects. That one rule explains why a function can change your list but not your variable, why mutable defaults leak between calls, and how to design functions that are safe to call.

19 problems4 easy · 9 medium · 6 hard

1One rule: parameters are assigned, not copied

When you call f(cart), Python does what items = cart would do: it points the parameter name items at the same object that cart points at. Nothing is copied, which is why passing a million-row list to a function is instant. People argue whether this is "pass by value" or "pass by reference"; the accurate name is pass by assignment (or "pass by object reference"), and everything from 2.1 to 2.3 applies directly.

passing.py
def add_item(items, x):
    items.append(x)        # changes the caller's list

def reset(items):
    items = []             # moves only the local name

cart = ["a"]
add_item(cart, "b")
reset(cart)
print(cart)

def bump(n):
    n += 1                 # an int cannot change: a new int, local name moved
    return n

count = 1
print(bump(count), count)
Output
['a', 'b']
2 1

So a function can change a mutable argument in place and the caller sees it, but assigning to a parameter never affects the caller. With immutable arguments (numbers, strings, tuples) a function cannot affect the caller's object at all; it can only return a new value.

≈
SQL / Power BI

Passing a list to a function is like giving a stored procedure the name of a table, not a copy of it: an UPDATE inside the procedure changes the real table. Assigning a new value to the parameter is like the procedure pointing its local variable at another table: the caller's table is untouched.

2Mutable default arguments

A default value is evaluated once, when the def statement runs, and stored on the function object (you can see them in f.__defaults__). Every call that uses the default gets that same object. For immutable defaults this is harmless. For a list, dict or set, every call shares and changes one object, so data leaks from one call into the next.

mutable_default.py
def log_event(event, log=[]):      # one list, created at definition time
    log.append(event)
    return log

print(log_event("start"))
print(log_event("stop"))           # the first call's event is still there
print(log_event.__defaults__)
Output
['start']
['start', 'stop']
(['start', 'stop'],)

The fix is the None default plus a fresh object inside the function. If None is a valid value for that parameter, use a sentinel (2.1).

none_default.py
def log_event(event, log=None):
    if log is None:
        log = []                   # a new list on every call that needs one
    log.append(event)
    return log

print(log_event("start"))
print(log_event("stop"))
shared = []
log_event("a", shared); log_event("b", shared)
print(shared)                      # passing a list on purpose still works
Output
['start']
['stop']
['a', 'b']
!
It is not only lists

Anything computed in a default is computed once: created=datetime.now() freezes one timestamp for every call, request_id=uuid4() gives every request the same id, and conn=connect() opens one connection at import time. Use None and compute the value inside the function (problem 6).

3Designing functions that are safe to call

Because a function receives your actual objects, every function makes a choice, whether it says so or not:

  • Pure: read the arguments, return a new result, change nothing. Easiest to test, safe to call twice, safe to retry. The default choice for data transformations: sorted, dict | dict, comprehensions.
  • In place: change the argument and return None, like list.sort(). Saves memory on big data. The name or docstring should make the side effect obvious, and the None return stops callers from assuming they got a copy.
  • Defensive copy at the boundary: when you call code you do not control (plugins, agent tools, user callbacks), pass a copy so it cannot change your data (problem 15).

What to avoid is the mixture: a function that changes its argument and returns it, so the caller thinks they got a new object but actually holds an alias (problems 7 and 11). pandas offers both styles through an inplace=True parameter, and has been moving away from it because the mixture caused so many bugs.

•
*args and **kwargs (preview of 3.2)

*args arrives as a new tuple and **kwargs as a new dict on every call, so changing those containers never affects the caller. The values inside them are still the caller's objects (problem 10).

answer keeps conversation memory so follow-up questions have context. Two different users calling it without their own memory end up seeing each other's questions. Fix it so each call without memory starts empty, while a memory passed in is used and updated.

TestsThe 4 checks Run tests uses

HintOpen a hint

The {} default is one dict for the whole program, and setdefault stores the history list inside it.

SolutionShow the solution and why
solution.py
def answer(question, memory=None):
    if memory is None:
        memory = {}
    history = memory.setdefault("history", [])
    history.append(question)
    return f"answering {question!r} with {len(history) - 1} earlier turns"

The default dict is created once and lives as long as the function, so the history of every caller who did not pass their own memory accumulates in it. In a web service that is a privacy bug, not just a logic bug: one user's questions become context for another user's answers. The None default gives each such call a fresh dict. In real agent frameworks memory is an explicit object created per session for exactly this reason.

8. A transform with an explicit in-place option

Write scale_rows(rows, factor, inplace=False). By default it returns a new list of new rows with every value multiplied by factor, leaving rows untouched. With inplace=True it changes the caller's rows themselves (the same inner list objects) and returns None.

TestsThe 5 checks Run tests uses

assert out[0] is not data[0]

HintOpen a hint

For inplace=True, change each row's contents with slice assignment row[:] = ... so the row objects stay the same.

SolutionShow the solution and why
solution.py
def scale_rows(rows, factor, inplace=False):
    if inplace:
        for row in rows:
            row[:] = [v * factor for v in row]
        return None
    return [[v * factor for v in row] for row in rows]

The two modes make the side effect explicit at the call site: scale_rows(x, 2) is safe, and scale_rows(x, 2, inplace=True) says loudly that x changes. Returning None in place mode prevents y = scale_rows(x, 2, inplace=True) from looking like it produced a copy. pandas has been moving away from its inplace parameters because people mixed the modes up; if you add one, keep the two paths this clearly separated.

call_with_retry calls an LLM function up to attempts times and returns the result plus the errors it saw. Hint 2Open a hint

SolutionShow the solution and why
solution.py
class TransientError(Exception):
    pass


def call_with_retry(fn, payload, attempts=3, errors=None):
    if errors is None:
        errors = []
    for attempt in range(1, attempts + 1):
        try:
            return fn({**payload, "attempt": attempt}), errors
        except TransientError as e:
            errors.append(f"attempt {attempt}: {e}")
    raise RuntimeError(f"failed after {attempts} attempts: {errors}")


def flaky(fails):
    state = {"left": fails}
    def fn(payload):
        if state["left"] > 0:
            state["left"] -= 1
            raise TransientError("rate limited")
        return f"ok on attempt {payload['attempt']}"
    return fn

Bug one is the mutable default: one errors list for the life of the process, so every request reports the failures of all earlier ones, and it grows without limit. Bug two is a side effect on the argument: payload["attempt"] = ... writes into the caller's dict, which is then reused for the next request with a stale attempt key in it. The fix builds a new dict per attempt with {**payload, "attempt": attempt}. Retry code is exactly where side effects hurt most, because the same call runs several times: anything a call changes in its input is changed again on every retry. (flaky uses a closure to keep its counter; closures are lesson 3.4.)

7Interview questions

Interview

17. Is Python pass-by-value or pass-by-reference?

SolutionModel answer

Neither, exactly. Python passes references to objects, and the parameter is assigned to the argument like a normal = ("pass by assignment" or "call by object reference"). Consequences: if the object is mutable and the function changes it in place, the caller sees the change, which looks like pass-by-reference. If the function assigns a new object to the parameter, the caller is unaffected, which looks like pass-by-value. Nothing is copied on a call, so passing large data is cheap. Give the two-line example (append versus items = []), and mention that immutable arguments can never be changed by the callee.

Interview

18. Why are mutable default arguments dangerous, and are they ever used on purpose?

SolutionModel answer

Defaults are evaluated once when def runs and stored on the function (__defaults__), so a list or dict default is one object shared by every call that does not pass the argument. Data leaks between calls, and if the function returns it, callers hold aliases to it. The fix is None (or a sentinel) plus creating the object inside. The same once-only evaluation also freezes values like datetime.now() or uuid4(). Deliberate uses exist: a default dict as a cheap memo cache (def fib(n, _cache={})), but functools.cache does this more clearly and is what you should say you would use. Bonus: dataclasses refuse a mutable default and require field(default_factory=list), which builds a new list per instance.

Interview

19. An agent's tool function changes the arguments dict the LLM produced. Why is that a problem, and how do you prevent it?

SolutionModel answer

The same dict usually lives on after the call: it is logged, stored in the conversation history, shown in traces, and reused if the step is retried or replayed. A tool that changes it rewrites history: traces show arguments the model never sent, retries run with altered input, and evaluation datasets built from logs are wrong. Prevention, from lightest to strongest: write tools as pure functions; validate the LLM's JSON into a fresh object (a Pydantic model) before calling the tool, so the tool never sees the logged dict; pass a deep copy at the boundary when calling third-party tools; or store logged arguments in read-only form. The principle is the one from this lesson: a function receives your actual object, so the boundary decides who may change it.

Recap

  • A call does param = argument: nothing is copied. Changing a mutable argument in place is visible to the caller; assigning to the parameter never is.
  • Defaults are evaluated once, at def time: items=[], memory={}, created=datetime.now() are all shared or frozen. Use None and build the value inside.
  • Choose deliberately: pure (return new, change nothing), or in place (change and return None). Never change the input and return it.
  • Copy at boundaries you do not control (tools, plugins), not on every call. Passing a big list is free; copying it is not.
  • An iterator argument can be read only once. Accept that, or convert to a list at the start.
