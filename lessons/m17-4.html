1Parsing and using dates

Dates arrive as text, and nothing date-like works until they are parsed. pd.to_datetime converts a column to datetime64; give it the format= you expect ("%Y-%m-%d", "%d/%m/%Y") so ambiguous strings such as 05/01/2026 are read the way your source writes them, and errors="coerce" so bad values become NaT (the missing timestamp) that you can count. pandas 3 infers the format from the first value and raises if later values use a different one; format="mixed" parses each value separately, slower and only for genuinely messy sources, and it has to guess: below it reads 05/01/2026 month first, as 1 May, which is wrong if the source writes day first. The resolution is inferred too (datetime64[us] for these strings), not always nanoseconds as in older versions.

The .dt accessor extracts parts for features: dt.dayofweek (Monday is 0), dt.hour, dt.month, dt.day_name(), dt.date. Subtracting timestamps gives a Timedelta, and .dt.total_seconds() or / pd.Timedelta("1D") turns it into a number, such as "days the company took to respond". Store times in UTC and convert for display: tz_localize("UTC") marks naive timestamps as UTC, tz_convert(...) changes the zone. Named zones such as America/New_York need the tz database (the tzdata package in some environments); fixed offsets such as "+05:30" always work.

raw = pd.Series(["2026-01-02 09:15", "2026-01-02 23:40", "2026-01-05 08:00", "not a date"])

2Regular calendars: resample and date ranges

Events happen at irregular times; models and dashboards usually want a regular series: complaints per day, revenue per week. Put the timestamps in the index (set_index("submitted")) and resample(rule) groups rows into calendar bins and aggregates them, a group-by on time: "D" for days, "W" for weeks (ending on Sunday by default), "ME" for month ends, "h" for hours. Days with no events do appear in the result, as 0 for count/sum or NaN for mean, which a plain groupby(dt.date) would silently skip; Power BI solves the same problem with a separate date table.

A DatetimeIndex also allows date slicing with strings: ts["2026-01"] is all of January, and ts["2026-01-03":"2026-01-05"] includes both end days, like loc. pd.date_range(start, periods=..., freq=...) builds a calendar to reindex against when you need an explicit list of dates.

resample.py
import pandas as pd

events = pd.DataFrame({
    "submitted": pd.to_datetime(["2026-01-01 10:00", "2026-01-01 15:30", "2026-01-03 09:00", "2026-01-06 11:00", "2026-01-06 12:00"]),
    "amount": [20.0, 35.0, 300.0, 15.0, 60.0],

3Rolling windows and lag features without leakage

rolling(window) computes a statistic over a moving window of the last window rows (or a time span such as "7D" on a DatetimeIndex); the first rows have too little history and give NaN unless you set min_periods. expanding() uses all rows so far, and ewm(span=...) weights recent rows more. shift(k) moves a series down by k rows, so each row sees the value from k steps earlier: a lag feature. On a group-by, shift and rolling work within each group, so one customer's history never leaks into another's.

The rule that decides whether a time-series model works in production: a feature for time t may only use data available before t. rolling(7).mean() on day t includes day t itself; if the label is "complaints on day t", the feature contains the answer. Shift first: s.shift(1).rolling(7).mean() is the average of the seven days before t. The same rule applies to splitting: shuffled train/test splits put future rows in the training set, so the test score measures memory of the future. Split by time instead: train on everything before a cut-off date, test on everything after.

windows.py
import pandas as pd

counts = pd.Series([5, 7, 6, 9, 30, 8, 7], index=pd.date_range("2026-01-01", periods=7, freq="D"), name="n")
feats = pd.DataFrame({
    "n": counts,
    "roll3_leaky": counts.rolling(3).mean().round(2),
    "roll3": counts.shift(1).rolling(3).mean().round(2),
    "lag1": counts.shift(1),
    "ewm": counts.shift(1).ewm(span=3).mean().round(2),
    "best_so_far": counts.expanding().max(),
})
print(feats)
print(counts.rolling("3D").sum().tolist())
cut = pd.Timestamp("2026-01-05")
train, test = feats[feats.index < cut], feats[feats.index >= cut]
print(len(train), len(test), test.index.min().date())

4Text with the .str accessor

Text columns have a .str accessor with vectorised versions of Python's string methods (lower, strip, replace, startswith, len, split) plus regular-expression tools: str.contains(pattern) for filtering, str.extract(pattern) to pull capture groups into new columns, str.replace(pattern, repl, regex=True) to normalise, str.count(pattern). Missing values pass through as missing. These run per value in optimised code and keep NaN handling consistent, so they beat apply with a Python function for anything they can express (Module 5's regex lesson applies directly).

For LLM and retrieval work, two more tools matter. str.split() turns text into lists of words, and explode turns a column of lists into one row per element, keeping the index, which is how a narrative becomes words for counting or chunks for embedding. CFPB narratives also contain redactions written as runs of X (XXXX), which are noise for a model and should be normalised to one token before embedding or classification: in the example, the two most common "words" are redaction markers.

One measured surprise: with pandas' default Python-backed strings, each .str method is still a loop over Python strings, so a chain of two .str calls ran at about the same speed as one apply with a precompiled regex (138 ms against 142 ms for 40,000 texts when this page was built). The advantages of .str are clarity and missing-value handling; with the PyArrow-backed string storage, which pandas 3 uses when PyArrow is installed, many .str methods run in compiled code and are much faster.

5Categoricals and encodings

The category dtype stores each distinct value once and every row as a small integer code (D.2 showed the memory saving). Its categories can be ordered (pd.Categorical(values, categories=["low", "medium", "high"], ordered=True)), which makes comparisons and sorting follow the business order instead of the alphabet, the pandas version of a "sort by column" setting in Power BI. Codes are also an encoding: cat.codes gives integers for an ordinal feature.

Most models need numbers. One-hot encoding creates one 0/1 column per category (pd.get_dummies). The trap is at inference time: new data may lack a category (no mortgage complaints today) or contain one never seen in training, so get_dummies produces different columns, and a model receiving them gets features in the wrong positions. Fix the column list from training and reindex new data to it, filling 0; or use scikit-learn's OneHotEncoder(handle_unknown="ignore"), which remembers its categories (D.6). Converting to a categorical with the training categories before get_dummies achieves the same, once unseen values have been turned into missing ones with where(isin(...)): pandas 3 warns that passing unknown values to pd.Categorical will become an error.

solution.py
import pandas as pd


def daily_counts(df, start, end):
    days = pd.date_range(start, end, freq="D")
    counts = df.set_index("submitted").resample("D").size()
    return counts.reindex(days, fill_value=0).astype(int).rename("complaints")

Grouping by date only produces days that have events, so a quiet day simply disappears, and a model or chart reading the series thinks the days are consecutive. resample("D") fills gaps between the first and last event, but not the days before the first or after the last one in your requested range, and it includes events outside the range. Reindexing to an explicit date_range solves both: days outside are dropped, missing days get 0. Both ends of date_range are inclusive. This calendar-first habit is the pandas version of joining to a date dimension.

solution.py
import pandas as pd


def extract_fields(texts):
    amount = texts.str.extract(r"\$([\d,]+(?:\.\d+)?)", expand=False)
    date = texts.str.extract(r"(\d{4}-\d{2}-\d{2})", expand=False)
    return pd.DataFrame({
        "amount": pd.to_numeric(amount.str.replace(",", "")),
        "date": pd.to_datetime(date, format="%Y-%m-%d", errors="coerce"),
    })

str.extract with one capture group and expand=False returns a Series of the first match per row, NaN where there is none, aligned to the original index. The amount pattern anchors on $, so the starter's "first run of digits" (which picked up 1) is avoided, allows thousands separators, and makes the decimal part optional with a non-capturing group (?:...). Commas are removed before to_numeric. A string that looks like a date is not necessarily one: 2026-02-30 matches the pattern, and errors="coerce" turns it into NaT instead of raising. Extracting structured fields from text with regex is cheap and exact; an LLM is the tool when the wording varies too much for a pattern.

5. A rolling feature that sees the label

add_features builds features to predict each day's complaint count n. The model scored suspiciously well offline and badly in production. Fix the two leaky features so that each uses only days before the current one: avg7 (mean of the previous 7 days, allowing partial windows of at least 3 days) and max_so_far (the maximum of all previous days). SolutionShow the solution and why
solution.py
import pandas as pd


def add_features(daily):
    out = daily.copy()
    past = out["n"].shift(1)
    out["avg7"] = past.rolling(7, min_periods=3).mean()
    out["max_so_far"] = past.expanding().max()
    return out

Both windows ended today: on 4 January the "average" already contained the spike of 100 it was supposed to predict, and max_so_far equalled the label whenever a new record was set. Offline, the model learns to read the answer from the feature; in production the day's value is not known until the day is over, so the feature is unavailable or different, and accuracy collapses. Shifting by one first makes every window end yesterday. On 8 January the window holds exactly the seven days before it, 1 to 7 January; on 4 January it holds the three days that exist, which min_periods=3 allows. Leakage of this kind is the most common reason a time-series model looks too good.

SolutionShow the solution and why
solution.py
import math
import pandas as pd


def time_split(df, time_col, test_size=0.25, gap="0D"):
    s = df.sort_values(time_col, kind="stable")
    n_test = math.ceil(len(s) * test_size)
    cutoff = s[time_col].iloc[len(s) - n_test]
    test = s[s[time_col] >= cutoff]
    train = s[s[time_col] < cutoff - pd.Timedelta(gap)]
    return train, test

A random split puts complaints from next week in the training set and asks the model to "predict" last week, which measures how well it interpolates the past, not how it will do on tomorrow's data. A time-based split mirrors production: train on the past, evaluate on the most recent period. Defining the test set by a cut-off time rather than a row count keeps rows with the same timestamp together (with test_size=0.5 the boundary falls between the two 4 January rows, so both go to test, making 5). The optional gap leaves a buffer so that features computed over recent days (rolling windows, slowly arriving labels) cannot overlap the test period. scikit-learn's TimeSeriesSplit generalises this into several expanding folds, and it has a gap parameter for the same reason.

def prepare_texts(s, min_words=5):
    t = s.str.replace(r"\bX{2,}(?:/X{2,})*\b", "[X]", regex=True)
    t = t.str.replace(r"\[X\](?:\s+\[X\])+", "[X]", regex=True)

solution.py
import pandas as pd


class OneHot:
    def fit(self, df, cols):
        self.cols = list(cols)
        self.cats_ = {c: sorted(df[c].dropna().unique().tolist()) for c in self.cols}
        return self

    def transform(self, df):
        parts = []
        for c in self.cols:
            known = self.cats_[c]
            cat = pd.Categorical(df[c].where(df[c].isin(known)), categories=known)
            d = pd.get_dummies(cat, dtype=int)
            d.columns = [f"{c}={v}" for v in self.cats_[c]]
            d.index = df.index
            parts.append(d)
        return pd.concat(parts, axis=1)

    def unseen(self, df):
        out = {}
        for c in self.cols:
            extra = set(df[c].dropna()) - set(self.cats_[c])
            if extra:
                out[c] = sorted(extra)
        return out

get_dummies creates columns from whatever values are present, so a batch without loans has no loan column and a batch with a new product has an extra one: the model then receives features in the wrong positions, usually without any error, because it only sees a matrix. Fixing the categories at fit time, turning unknown values into missing ones and converting to a categorical with the known categories means get_dummies always creates one column per category, even with no rows. Looping over a few columns is fine. Reporting unseen values is the monitoring half: a new product appearing in production is data drift that someone should know about. scikit-learn's OneHotEncoder(handle_unknown="ignore") implements the same contract inside a pipeline.

import pandas as pd


def sessionize(events, gap=30):
    out = events.sort_values(["user", "time"], kind="stable").reset_index(drop=True)
    new = out.groupby("user")["time"].diff() > pd.Timedelta(minutes=gap)
    out["session"] = new.groupby(out["user"]).cumsum().astype(int) + 1
    return out


def summarise(sessions):
    summ = sessions.groupby(["user", "session"], as_index=False).agg(
        start=("time", "min"), end=("time", "max"), events=("time", "size"))
    summ["minutes"] = (summ["end"] - summ["start"]) / pd.Timedelta("1min")
    return summ

Sessionisation is the gaps-and-islands problem from SQL, and the pandas answer is three vectorised steps. Within each user, diff gives the time since the previous event; comparing it with the gap marks the events that start a new session (the first event of each user has no previous one, so its NaT compares as False). The running sum of those booleans within each user increases by one at every new session, so adding 1 numbers them from 1. u2's events at 11:00 and 11:29 are 29 minutes apart, inside the gap, so they share a session. The summary is then an ordinary named aggregation. Shuffling the input in the test makes sure the function sorts instead of trusting the order.

import pandas as pd


def chunk_texts(df, size, overlap):
    if not 0 <= overlap < size:
        raise ValueError("need 0 <= overlap < size")
    step = size - overlap

    def windows(words):
        out = []
        for start in range(0, len(words), step):
            out.append(words[start:start + size])
            if start + size >= len(words):
                break
        return out

    words = df["text"].fillna("").str.split()
    exploded = (df[["id"]].assign(chunks=words.map(windows))
                .explode("chunks").dropna(subset=["chunks"]))
    exploded["chunk"] = exploded.groupby("id").cumcount()
    exploded["text"] = exploded["chunks"].map(" ".join)
    exploded["n_words"] = exploded["chunks"].map(len)
    return exploded[["id", "chunk", "text", "n_words"]].reset_index(drop=True)

Retrieval works on chunks, not whole documents: an embedding of a long narrative blurs its topics, and a prompt has a token budget. Overlap keeps a sentence that straddles a boundary intact in at least one chunk (with size 4 and overlap 1, the word d ends one chunk and starts the next). The loop stops as soon as a window reaches the end, so the tail is never a duplicate fragment already inside the previous chunk (size 5, overlap 2 gives two chunks, not three). Building the list of chunks per text and then explode produces one row per chunk with the document's id carried along; an empty list explodes to NaN, which dropna removes, so empty texts disappear. Real chunkers count tokens rather than words and prefer sentence boundaries, but the bookkeeping is the same.

Interview

15. How do you avoid leakage when building features and splits for time-series data?

SolutionModel answer

Leakage means a feature or a training row uses information that would not be available at prediction time, so offline scores are optimistic and production performance collapses. For features: every value for time t must be computed from data before t (or before t minus the latency with which data really arrives), so lags use shift, rolling and expanding windows are applied to the shifted series, group-wise features are computed within the entity and in time order, and aggregates such as target encodings or normalisation statistics are fitted on the training period only. Watch for subtle sources: a "last status" column that is updated after the event, data back-filled later, or features joined from a table snapshot taken after the cut-off. For splits: never shuffle; train on a period, validate on the next period, and test on the latest, optionally with a gap; for model selection use rolling-origin or expanding-window cross-validation (TimeSeriesSplit), and make sure rows from the same entity and timestamp do not straddle the boundary. A good check is to simulate prediction: rebuild features "as of" a past date and compare with the training features.

Interview

16. How do you encode categorical features, and what goes wrong in production?

SolutionModel answer

It depends on the model and the cardinality. One-hot encoding (one 0/1 column per category) suits linear models and low-cardinality columns; ordinal codes suit genuinely ordered categories (low, medium, high) and tree models; target encoding (the smoothed mean label per category, fitted out of fold) handles high cardinality such as merchants or zip codes; hashing bounds the number of columns; and learned embeddings are the neural option. Gradient-boosting libraries such as LightGBM and CatBoost can take categoricals natively. In production the problems are consistency and change: pd.get_dummies on new data creates different columns when a category is missing or new, so the feature matrix silently shifts; new categories appear (a new product), so the encoder must handle unknowns (handle_unknown="ignore", an "other" bucket, or the prior for target encoding); rare categories overfit, so group them; and the category list must be saved with the model, ideally as a fitted encoder inside a pipeline. Monitoring the share of unseen categories is a cheap drift alarm.

Interview

17. How would you prepare free-text complaint narratives for a classical classifier versus an LLM or embedding model?

SolutionModel answer

For a classical model (TF-IDF plus logistic regression), preprocessing shapes the vocabulary, so you lower-case, normalise or remove punctuation, numbers and redaction markers, possibly remove stop words or lemmatise, and keep n-grams; the text is reduced to counts, so noise directly becomes features. For an LLM or a modern embedding model, the tokenizer and the model already handle case, punctuation and word forms, and aggressive cleaning removes signal (negation, casing, structure), so you clean only what is genuinely noise: collapse redaction runs, strip HTML and boilerplate, fix encoding problems, normalise whitespace, and remove or mask personal data. You also manage length: truncate or chunk to the model's context and token budget, with overlap for retrieval, and keep ids so chunks can be traced back. In both cases de-duplicate, drop empty or near-empty texts, keep the raw text for audit, apply exactly the same preprocessing at training and inference time, and check language and length distributions, because a few huge or non-English documents can dominate costs or results.

Recap

  • Parse with pd.to_datetime(format=..., errors="coerce") and count the NaTs; pandas 3 raises on mixed formats unless format="mixed". Use .dt for parts and store UTC.
  • resample groups by calendar bins and keeps empty days; reindex to a date_range for a fixed calendar. Date-string slices include both ends; monthly bins are labelled by month end.
  • Lag and window features must end before the row they describe: shift(1) before rolling or expanding, and within groups. Split by time, never shuffle.
  • .str methods handle missing values and regex (contains, extract, replace); split plus explode turns text into words or chunks.
  • category stores codes and can be ordered; fix categories at training time and align new data, so one-hot columns never shift.
