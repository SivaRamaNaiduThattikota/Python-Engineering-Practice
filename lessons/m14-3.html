14.3 Processes

For CPU-bound Python code, the way past the GIL is several processes, each with its own interpreter on its own core. ProcessPoolExecutor and multiprocessing, what must be picklable, the __main__ guard and start methods, task size and chunking, loading a model once per worker with an initializer, sending paths instead of data, and when to vectorise instead. On this site the process pool runs tasks inline but checks picklability the way real processes do.

1ProcessPoolExecutor

concurrent.futures.ProcessPoolExecutor(max_workers=n) has the same interface as the thread pool of 14.2 (submit, map, as_completed, futures), but each worker is a separate process. Each has its own interpreter and its own GIL, so pure-Python computation runs truly in parallel, one task per core. The default max_workers is the number of CPUs, which is the right number for CPU-bound work: more processes than cores just compete for them. The lower-level multiprocessing module offers Pool, Process, queues and pipes for the same purpose; for task-based work, the executor is simpler.

The price of separate memory is communication. The parent and the workers share nothing, so the function to call, its arguments, and its return value are pickled, sent through a pipe, and unpickled on the other side. This has three consequences, each covered below: what you send must be picklable, sending is not free, and global state in the parent is not visible in the workers unless they create it themselves.

2What can be sent

pickle sends functions and classes by name: it records "the function square in module tasks", and the worker imports that module and looks the name up. So a worker can receive only functions and classes that are defined at the top level of an importable module. Lambdas, functions defined inside other functions, and classes defined inside functions have no importable name and fail with PicklingError. functools.partial(top_level_fn, arg) works, and so do bound methods of picklable objects. Arguments and return values must be picklable too: numbers, strings, lists, dicts, dataclasses and NumPy arrays are; open files, locks, sockets, generators and database connections are not (TypeError: cannot pickle ...).

3The __main__ guard and start methods

A worker process must import your code to find the function it will run. With the spawn start method, the default on Windows and macOS, the worker is a fresh interpreter that imports your main script as a module (under a name other than "__main__"). If the script creates a process pool at top level, each worker would try to create its own pool while importing it, and Python stops this with an error. Hence the rule for any script that uses processes: put the code that starts work under if __name__ == "__main__":, so it runs when the file is executed and not when a worker imports it.

On Linux, Python historically used fork, which copies the parent process, including its memory, so workers started without importing anything; it is fast but unsafe when the parent has threads (a lock held by another thread is copied in its locked state). Python 3.14 changed the Linux default to forkserver, which forks workers from a clean server process. Write code that works under spawn (top-level functions, the main guard, no reliance on inherited globals) and it will work everywhere. multiprocessing.get_context("spawn") chooses a method explicitly, and ProcessPoolExecutor(mp_context=...) passes it to the executor.

4Task size, chunking and initializers

Every task costs a round trip: pickle the call, send it, unpickle, run, pickle the result, send it back. For a task that takes a microsecond, that overhead dominates, and a process pool is slower than a plain loop. Make tasks coarse: send chunks of items (a list of 1,000 texts per task rather than one), or use executor.map(fn, items, chunksize=1000), which batches items for you. The right chunk size balances overhead against load balancing: very large chunks leave workers idle at the end while one finishes the last chunk (problem 11).

Workers often need an expensive resource: a tokenizer, a vocabulary, a spaCy pipeline, a model. Loading it inside every task repeats the work; passing it as an argument pickles it every time. Instead, give the executor an initializer: ProcessPoolExecutor(initializer=load, initargs=(path,)) runs load(path) once in each worker when it starts, and load stores the resource in a module-level global that the task functions read. Similarly, send paths, ids or offsets, not data: let each worker open its own file or query its own rows, so only small descriptions cross the process boundary.

Finally, check whether processes are needed at all. Many CPU-bound loops are faster still when vectorised with NumPy or pandas, whose inner loops run in C (problem 8), and some libraries (tokenizers, BLAS in NumPy, PyTorch) already use several cores internally. Measure with cProfile and wall-clock timings first, then parallelise what remains.

from concurrent.futures import ProcessPoolExecutor


def chunks(items, size):
    if size < 1:
        raise ValueError("size must be at least 1")
    return [items[i:i + size] for i in range(0, len(items), size)]


def count_chunk(texts):
    return [len(t.split()) for t in texts]


def parallel_token_counts(texts, workers=4, chunk_size=100):
    out = []
    with ProcessPoolExecutor(max_workers=workers) as pool:
        for counts in pool.map(count_chunk, chunks(texts, chunk_size)):
            out.extend(counts)
    return out

Each task carries a chunk of texts, so the per-task overhead of pickling and inter-process communication is paid once per chunk instead of once per text, and the worker function is top-level, so it can be sent by name. Because map returns chunk results in submission order, flattening them restores the text order without extra bookkeeping. In production the worker would call a real tokenizer (loaded once per worker with an initializer, problem 5); the structure is the same.

import functools
from concurrent.futures import ProcessPoolExecutor

def scale_row(row, mean, std):
    return [(x - mean) / std for x in row]

def normalise_all(rows, mean, std, workers=4):
    with ProcessPoolExecutor(max_workers=workers) as pool:
        return list(pool.map(functools.partial(scale_row, mean=mean, std=std), rows))

4. The cost of small tasks

def pool_time(n_items, item_cost, workers, chunk, overhead):
    tasks = -(-n_items // chunk)
    rounds = -(-tasks // workers)
    return rounds * (overhead + chunk * item_cost)

sequential = 10_000 * 0.00001
print(round(sequential, 3))
for chunk in (1, 10, 100, 1000, 2500, 10_000):
    print(chunk, round(pool_time(10_000, 0.00001, workers=4, chunk=chunk, overhead=0.001), 3))

solution.py
from concurrent.futures import ProcessPoolExecutor

VOCAB = None


def init_worker(vocab):
    global VOCAB
    VOCAB = {word: i for i, word in enumerate(vocab)}


def featurize(text):
    vec = [0] * len(VOCAB)
    for word in text.lower().split():
        i = VOCAB.get(word.strip(".,!?"))
        if i is not None:
            vec[i] += 1
    return vec


def featurize_all(texts, vocab, workers=2):
    with ProcessPoolExecutor(max_workers=workers, initializer=init_worker, initargs=(vocab,)) as pool:
        return list(pool.map(featurize, texts, chunksize=64))

The initializer runs once in each worker process, when it starts, and puts the resource into that process's module globals, where every task reads it; the vocabulary crosses the process boundary once per worker instead of once per text. The global is the one exception to "avoid global state" in parallel code, because each process has its own copy and nothing is shared. The same pattern loads tokenizers, spaCy pipelines or ONNX models in workers. chunksize batches the small featurize calls to keep per-task overhead low.

from concurrent.futures import ProcessPoolExecutor


def summarise_file(path):
    lines = words = 0
    with open(path, encoding="utf-8") as f:
        for line in f:
            lines += 1
            words += len(line.split())
    return path, lines, words


def summarise_files(paths, workers=4):
    files, errors = {}, {}
    with ProcessPoolExecutor(max_workers=workers) as pool:
        futures = [(p, pool.submit(summarise_file, p)) for p in paths]
    for path, future in futures:
        error = future.exception()
        if error is not None:
            errors[path] = type(error).__name__
        else:
            _, lines, words = future.result()
            files[path] = {"lines": lines, "words": words}
    return {"files": files, "errors": errors}

Sending a path costs a few dozen bytes; sending the file's contents would pickle and copy every byte from the parent to the worker, which for gigabytes of text can take longer than the processing itself and doubles memory use. Each worker opens its own file and streams it (12.1), and only a small summary travels back. Errors stay per file: a missing file becomes an entry in errors, not a crashed batch. The same principle applies to databases (send ids or ranges, let workers query) and to large arrays (use shared memory or memory-mapped files).

import itertools
from concurrent.futures import ProcessPoolExecutor


def grid_search(evaluate, grid, workers=4):
    keys = list(grid)
    combos = [dict(zip(keys, values)) for values in itertools.product(*grid.values())]
    with ProcessPoolExecutor(max_workers=workers) as pool:
        futures = [(params, pool.submit(evaluate, params)) for params in combos]
    results = [(params, f.result()) for params, f in futures if f.exception() is None]
    results.sort(key=lambda r: -r[1])
    return (results[0][0] if results else None), results

Hyperparameter search is the textbook embarrassingly parallel CPU job: each combination trains and scores independently, so a process pool divides the wall time by the number of cores. Parameters travel as small dicts and scores come back as floats, so communication is negligible compared with training. Keeping the futures in grid order and sorting with a stable key makes ties reproducible, and failed combinations (a diverging learning rate) are dropped instead of aborting the search. Libraries do the same: scikit-learn's GridSearchCV(n_jobs=-1) runs fits in worker processes through joblib.

from concurrent.futures import ProcessPoolExecutor


def _run_chunk(fn, chunk):
    out = []
    for item in chunk:
        try:
            out.append(("ok", fn(item)))
        except Exception as e:
            out.append(("error", f"{type(e).__name__}: {e}"))
    return out


def chunked_map(fn, items, workers=4, chunk_size=100):
    chunks = [items[i:i + chunk_size] for i in range(0, len(items), chunk_size)]
    results = []
    with ProcessPoolExecutor(max_workers=workers) as pool:
        futures = [pool.submit(_run_chunk, fn, chunk) for chunk in chunks]
        for future in futures:
            results.extend(future.result())
    return results

Error handling must happen inside the chunk: if a worker raised on the first bad item, the whole chunk's result would be lost and the caller could not tell which of its items succeeded. Returning tagged results per item keeps the output aligned with the input, which matters when results are written back next to the records they belong to. The chunk worker and fn both travel by name, which is why a lambda fails at submission time with PicklingError, before any work is done, and future.result() re-raises it to the caller: a configuration bug should stop the job, a bad record should not.

11. Choose a chunk size from a cost model

Write pool_time(n, workers, chunk, overhead, item_cost) returning the modelled wall time of processing n items in chunks of chunk on workers processes: tasks are ceil(n / chunk), each task takes overhead + size * item_cost (the last task may be smaller), and tasks are assigned in order to the first free worker. solution.py
import heapq


def pool_time(n, workers, chunk, overhead, item_cost):
    sizes = [min(chunk, n - start) for start in range(0, n, chunk)]
    free = [0.0] * workers
    end = 0.0
    for size in sizes:
        start = heapq.heappop(free)
        finish = start + overhead + size * item_cost
        end = max(end, finish)
        heapq.heappush(free, finish)
    return end


def best_chunk(n, workers, overhead, item_cost, candidates):
    return min(candidates, key=lambda c: (round(pool_time(n, workers, c, overhead, item_cost), 12), c))

The model captures the two forces that decide chunk size. Overhead per task pushes towards large chunks: with 1-item chunks, 10,000 tasks of 1 ms overhead swamp the 10 microseconds of work each. Load balancing pushes towards enough chunks to keep every worker busy until the end: with 10 items in chunks of 3 on 4 workers, the uneven last chunk decides the finish time. With no overhead, the smallest chunks balance best. Real overheads and item costs come from a quick measurement on a sample, and the model then picks a sensible chunksize without trial and error over the full dataset.

from concurrent.futures import ProcessPoolExecutor

LOADS = []
STOPWORDS = None


def load_stopwords():
    LOADS.append(1)
    return {"the", "a", "of", "to", "is"}


def clean(doc, stopwords):
    words = [w.strip(".,!?").lower() for w in doc.split()]
    return [w for w in words if w and w not in stopwords]


def init_worker():
    global STOPWORDS
    STOPWORDS = load_stopwords()


def clean_chunk(docs):
    return [clean(d, STOPWORDS) for d in docs]


def preprocess_corpus(docs, workers=4, chunk_size=32):
    chunks = [docs[i:i + chunk_size] for i in range(0, len(docs), chunk_size)]
    out = []
    with ProcessPoolExecutor(max_workers=workers, initializer=init_worker) as pool:
        for cleaned in pool.map(clean_chunk, chunks):
            out.extend(cleaned)
    return out

Each change applies one rule of this lesson. Cleaning text is pure-Python CPU work, so threads give no speed-up under the GIL and processes are the right tool. The stop-word list was loaded 120 times, once per document; the initializer loads it once per worker, which for a real resource (a tokenizer or a spaCy model that takes seconds to load) is the difference between minutes and hours. The lambda becomes a top-level function so it can be pickled, and documents travel in chunks to amortise per-task overhead. map over chunks keeps the output in input order. (On a real machine, LOADS would be filled in the workers, not the parent; the grader counts them here because this site runs workers in the page.)

class Model:

A Model instance of a top-level class pickles with its weights, so apply(model, x) works, and so does the bound method, which pickles as the instance plus the method name; partial binds the model for map. Each task receives its own copy of the model, which is fine for read-only use and wasteful for large models (use an initializer instead). A generator argument fails with TypeError (a plain list iterator would pickle, generators never do), a lambda with PicklingError. Calling the class itself returns a new instance, which comes back to the parent by pickling, intact.

8Interview questions

Interview

14. When do you use processes instead of threads in Python, and what are the costs?

SolutionModel answer

Use processes for CPU-bound Python code (parsing, text processing, feature engineering, pure-Python model scoring), because each process has its own interpreter and GIL and runs on its own core; use threads (or asyncio) for I/O-bound work, where waiting dominates and threads are cheaper. The costs of processes: start-up time (especially with spawn), a full interpreter's memory per worker (plus any model loaded in each), and communication by pickling, which requires top-level functions and picklable arguments and makes sending large data slow. Mitigations: coarse tasks with chunking, initializers to load resources once per worker, sending paths or ids instead of data, shared memory for large arrays, and the __main__ guard. Before either, vectorise with NumPy or use libraries that already parallelise internally; and note that free-threaded Python makes threads viable for CPU work when the libraries support it.

Interview

15. Why do scripts that use multiprocessing need if __name__ == "__main__":?

SolutionModel answer

With the spawn start method (the default on Windows and macOS) and forkserver (the Linux default since Python 3.14), each worker starts a fresh interpreter that imports the main script as a module to find the functions it must run. Everything at the top level of the script runs again in every worker during that import. If the top level creates a process pool or starts the job, each worker would try to do the same, which would recurse; Python detects this and raises an error about starting a new process before bootstrapping finished. Putting the entry-point code under if __name__ == "__main__": makes it run only when the file is executed directly, since imported modules have their own name. Keep worker functions and classes at the top level so they can be found by name, and avoid expensive work at import time.

Interview

16. You need to preprocess 50 million documents on one 32-core machine. How do you design it?

SolutionModel answer

Profile a sample first to find the per-document cost and whether it is CPU-bound (likely: cleaning, tokenising, chunking). Store the input in shards (many files or row ranges), and process shards as tasks in a ProcessPoolExecutor with about 32 workers (fewer if memory per worker is large): each task receives a shard path, streams it, and writes its output shard itself (JSONL or Parquet), returning only counts and error summaries, so almost nothing crosses the process boundary. Load tokenizers or models once per worker with an initializer. Make it resumable and idempotent: one output file per input shard written atomically, so a restarted job skips finished shards, and a manifest records counts and failures (12.P). Handle bad documents inside the task (quarantine and count them). Track progress with as_completed. Check where the remaining serial parts are (reading a single compressed file, a final merge) using Amdahl's law, and consider vectorised libraries (pandas, Polars, Arrow compute) or a distributed engine (Spark, Ray, Dask) if one machine is not enough.

Recap

  • ProcessPoolExecutor runs tasks in separate processes, each with its own GIL, so CPU-bound Python code runs in parallel; size it to the number of cores.
  • Everything sent is pickled: only top-level functions and classes, partials of them, and picklable arguments and results; lambdas and generators fail.
  • Guard entry-point code with if __name__ == "__main__": because spawn and forkserver workers import your script.
  • Make tasks coarse with chunks or chunksize, load resources once per worker with initializer, and send paths or ids rather than data.
  • Vectorise with NumPy before parallelising, and measure: overheads can make a pool slower than a loop.
