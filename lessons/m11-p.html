11.P Module 11 practice set and mini project

Mixed problems from all of Module 11: type hints and what they do not check, protocols, generics and TypedDict, dataclasses and their options, and Pydantic validation. Then a mini project that needs all of it: a typed evaluation run that loads test cases from JSON Lines, grades answers through a protocol and reports results as validated models.

14 problems3 easy · 6 medium · 5 hard

1How to use this page

For every piece of data, ask two questions. Who creates it? If your own code does, from values that are already valid, a dataclass (or a TypedDict for plain dicts) describes it at almost no cost, and the type checker guards it (11.1 to 11.3). If it comes from outside, a file, an environment variable, a request or a model's reply, validate it at the boundary with Pydantic (11.4), then pass the validated object inward. Who uses it? If callers only need some behaviour, describe that behaviour with a Protocol rather than a base class, and write generic code with type parameters when the same logic serves several types (11.2).

The problems mix the lessons on purpose, and the mini project combines all four in the kind of evaluation harness every LLM team runs before changing a prompt or a model.

Type hints are not checked when the program runs (11.1): double("ab") happily repeats the string. solution.py
from dataclasses import dataclass, replace


@dataclass(frozen=True, order=True)
class ModelVersion:
    major: int
    minor: int
    patch: int = 0

    def __post_init__(self):
        if min(self.major, self.minor, self.patch) < 0:
            raise ValueError(f"negative version part in {self.major}.{self.minor}.{self.patch}")

    @classmethod
    def parse(cls, text):
        parts = text.removeprefix("v").split(".")
        if len(parts) not in (2, 3):
            raise ValueError(f"bad version: {text!r}")
        try:
            numbers = [int(p) for p in parts]
        except ValueError:
            raise ValueError(f"bad version: {text!r}") from None
        return cls(*numbers)

    def __str__(self):
        return f"v{self.major}.{self.minor}.{self.patch}"

    def bump(self, part):
        if part == "major":
            return replace(self, major=self.major + 1, minor=0, patch=0)
        if part == "minor":
            return replace(self, minor=self.minor + 1, patch=0)
        if part == "patch":
            return replace(self, patch=self.patch + 1)
        raise ValueError(f"unknown part: {part!r}")

order=True generates comparisons that compare the fields as a tuple, in declaration order, so versions sort numerically: v1.10.0 after v1.2.3, which plain strings get wrong. frozen=True makes instances immutable and, with the generated __eq__, hashable, so equal versions collapse in a set. replace builds the bumped copy and runs __post_init__ again, so every way of making a version is checked. The parser turns int's error into one clear message with from None (7.2). Model registries and artefact stores compare versions exactly like this.

SolutionShow the solution and why
solution.py
from dataclasses import dataclass, field

@dataclass
class PromptTemplate:
    name: str
    text: str
    variables: list[str] = field(default_factory=list)
    defaults: dict[str, str] = field(default_factory=dict)

    def render(self, **values):
        merged = {**self.defaults, **values}
        missing = [v for v in self.variables if v not in merged]
        if missing:
            raise KeyError(f"missing variables: {missing}")
        return self.text.format(**merged)

A default value in a class body is created once and would be shared by every instance (9.1), so dataclasses refuse unhashable defaults such as lists and dicts at class creation time, which is why the error appears on import rather than at the first bug. default_factory is called for each new instance, so b.variables.append no longer changes every other template. Pydantic, by contrast, accepts = [] because it copies defaults (11.4): the same intent, two different mechanisms.

4. TypedDict at run time and under Pydantic

from typing import NotRequired, TypedDict
from pydantic import TypeAdapter, ValidationError

class Msg(TypedDict):
    role: str
    tokens: int
    name: NotRequired[str]

m: Msg = {"role": "user", "tokens": "12"}
print(type(m).__name__, m["tokens"] * 2, Msg.__required_keys__ == {"role", "tokens"})
ta = TypeAdapter(Msg)
v = ta.validate_python({"role": "user", "tokens": "12", "extra": 1})

    ta.validate_python({"role": "user"})
except ValidationError as e:

HintOpen a hint

A TypedDict creates ordinary dicts. A TypeAdapter validates and converts a dict against it.

SolutionShow the solution and why
Real output
dict 1212 True
dict {'role': 'user', 'tokens': 12}
('tokens',) missing

A TypedDict is only a description for the type checker (11.2): the value is a plain dict, and nothing stops the string "12" from being stored, so "12" * 2 is "1212". The class does record which keys are required, as a frozenset that compares equal to the set. Under a TypeAdapter, Pydantic validates the dict, converting "12" to 12 and returning a plain dict again, with unknown keys dropped by default; a missing required key is reported at its location with the missing type.

from typing import Protocol, runtime_checkable


@runtime_checkable
class Embedder(Protocol):
    dim: int

    def embed(self, texts: list[str]) -> list[list[float]]: ...


def embed_all(embedder: Embedder, texts: list[str], batch_size: int = 2) -> list[list[float]]:
    if not isinstance(embedder, Embedder):
        raise TypeError(f"{type(embedder).__name__} is not an Embedder")
    vectors: list[list[float]] = []
    for i in range(0, len(texts), batch_size):
        batch = texts[i:i + batch_size]
        out = embedder.embed(batch)
        if len(out) != len(batch):
            raise ValueError(f"expected {len(batch)} vectors, got {len(out)}")
        for vec in out:
            if len(vec) != embedder.dim:
                raise ValueError(f"expected {embedder.dim} dims, got {len(vec)}")
        vectors.extend(out)
    return vectors

The protocol describes what embed_all needs, a dim and an embed method, so any embedder works without inheriting from anything: a local model, an API client, or this test fake (11.2). runtime_checkable adds an isinstance check that only verifies the members exist, not their signatures or types, so the shape checks on the actual output are still needed; they catch the two real failures of embedding services, a batch that comes back short (a dropped input would silently shift every later vector to the wrong text) and a dimension mismatch after a model change, which would corrupt a vector index (5.P).

from typing import Literal
from pydantic import BaseModel, ConfigDict, Field


class Optimizer(BaseModel):
    model_config = ConfigDict(extra="forbid")
    name: Literal["adam", "sgd"] = "adam"
    lr: float = Field(default=1e-3, gt=0, le=1)


class TrainConfig(BaseModel):
    model_config = ConfigDict(extra="forbid")
    epochs: int = Field(default=10, ge=1)
    batch_size: int = 32
    optimizer: Optimizer = Field(default_factory=Optimizer)


def apply_overrides(cfg, overrides):
    data = cfg.model_dump()
    for item in overrides:
        key, sep, value = item.partition("=")
        if not sep:
            raise ValueError(f"override must look like key=value: {item!r}")
        *parents, last = key.split(".")
        node = data
        for part in parents:
            node = node.setdefault(part, {})
            if not isinstance(node, dict):
                raise ValueError(f"{key!r}: {part!r} is not a nested section")
        node[last] = value
    return TrainConfig.model_validate(data)

The function never converts a value itself: it edits the plain-dict form of the config with strings, exactly as they arrive from the command line, and lets the model do all conversion and checking in one place. Lax mode turns "3" and "0.01" into numbers, the literal and the range reject bad values, and extra="forbid" turns misspelt names (epoch, momentum) into errors with their full path instead of silently ignored settings, which is how a training run with the wrong learning rate happens. The original is untouched because a new model is built. Tools such as Hydra and pydantic-settings implement this pattern at scale.

from dataclasses import dataclass, field

@dataclass

    id: str
    ts: float = 0.0

Hint 2Open a hint

SolutionShow the solution and why
solution.py
from dataclasses import dataclass
from pydantic import BaseModel, ValidationError
from typing import Callable


@dataclass(frozen=True)
class Result[T]:
    value: T | None = None
    error: str | None = None

    def __post_init__(self):
        if self.value is not None and self.error is not None:
            raise ValueError("a result has a value or an error, not both")

    @property
    def ok(self) -> bool:
        return self.error is None

    @classmethod
    def success(cls, value: T) -> Result[T]:
        return cls(value=value)

    @classmethod
    def failure(cls, error: str) -> Result[T]:
        return cls(error=error)

    def map[U](self, fn: Callable[[T], U]) -> Result[U]:
        if not self.ok:
            return self
        try:
            return Result.success(fn(self.value))
        except Exception as e:
            return Result.failure(f"{type(e).__name__}: {e}")

    def unwrap(self) -> T:
        if not self.ok:
            raise ValueError(self.error)
        return self.value


def parse_all[M: BaseModel](texts: list[str], model_cls: type[M]) -> list[Result[M]]:
    results = []
    for text in texts:
        try:
            results.append(Result.success(model_cls.model_validate_json(text)))
        except ValidationError as e:
            parts = [f"{'.'.join(map(str, err['loc'])) or 'reply'}: {err['type']}" for err in e.errors()]
            results.append(Result.failure("; ".join(parts)))
    return results

Batch jobs over model outputs should not stop at the first bad reply, and should not hide failures either. A Result makes success and failure explicit values that travel through the pipeline together: map chains transformations that only run on successes and turn their exceptions into failures, so later steps never see half-processed data, and the caller decides at the end whether to unwrap or report. The type parameters make the intent checkable (11.2): parse_all(texts, Verdict) returns list[Result[Verdict]], and map changes T into U. The error format uses Pydantic's stable error types rather than messages, which makes failures easy to count and group in a dashboard.

from pydantic import BaseModel, ConfigDict, Field, field_validator


class Settings(BaseModel):
    model_config = ConfigDict(extra="forbid")
    model: str = "small"
    temperature: float = Field(default=0.0, ge=0, le=2)
    debug: bool = False
    allowed_tools: list[str] = []
    max_retries: int = Field(default=3, ge=0, le=10)

    @field_validator("allowed_tools", mode="before")
    @classmethod
    def split_tools(cls, v):
        if isinstance(v, str):
            return [t.strip() for t in v.split(",") if t.strip()]
        return v


def load_settings(environ, prefix="APP_"):
    values = {key[len(prefix):].lower(): value for key, value in environ.items() if key.startswith(prefix)}
    return Settings.model_validate(values)

Environment variables are always strings, and the dataclass trusted them: temperature stayed "0.7", and bool("false") is True because every non-empty string is truthy, the most common configuration bug in Python services. Pydantic's lax mode parses booleans properly ("false", "0", "no" and "off" are False; "maybe" is an error), numbers from strings, and refuses "3.5" for an int. The range constraints catch dangerous values at start-up instead of at the first request, the before validator accepts the comma-separated format, and extra="forbid" turns a misspelt variable into a clear validation error naming it. Failing at start-up with every problem listed is the goal of settings validation. The pydantic-settings package packages this pattern (prefixes, .env files, secrets) as BaseSettings.

{"level":"high","span":{"start":1,"end":4},"day":"2025-03-01"}

Pydantic converts the string "high" into the enum member by value, builds a real Span dataclass from the dict (converting "1" to 1, because Pydantic validates dataclass fields too), and parses the ISO date. model_dump() converts models and dataclasses into dicts but keeps other Python objects as they are, the enum member and the date. mode="json" goes all the way to JSON-compatible values, the enum's value and the ISO string, which is what model_dump_json() writes. Use mode="json" when the dict will be sent somewhere that only understands JSON types, such as a message queue.

Interview

12. Type hints, dataclasses, TypedDict and Pydantic: which one where?

SolutionModel answer

They solve different problems and work together. Type hints everywhere document intent and let a type checker (mypy, pyright) catch mistakes before the code runs, at no run-time cost. Dataclasses for internal objects with behaviour or identity that your code creates: domain records, results, configuration already validated, using frozen, slots and kw_only where useful. TypedDict when the data must stay a plain dict, such as JSON passed through to a library or API payload types, giving checked keys without a class. Pydantic at every boundary where untrusted data enters: requests, settings, files, queues and LLM output, where it validates, converts, reports every error and produces JSON Schema. Protocols for the interfaces between components, such as an embedder or a retriever, so implementations can be swapped and faked in tests. The rule of thumb: validate once at the edge with Pydantic, then pass typed, trusted objects inward.

Interview

13. Your LLM output model needs a new field. How do you change it without breaking things?

SolutionModel answer

Treat the model as a contract between prompts, parsing code and stored data. Add the field as optional (with a default or None), so replies from the old prompt and records already stored still validate, and new code can start using it; only make it required after every producer emits it. Never rename or retype a field in place: add the new one, read both for a while (a mode="before" validator can map the old name), then remove the old one. Version the schema explicitly, for example a schema_version literal or a discriminated union of V1 | V2 when shapes really differ, and store the version with each output. Because the JSON Schema sent to the model changes, also re-run the evaluation set (as in the project below) before rollout, since a schema change can shift the model's behaviour, and watch the validation failure rate after deployment. Keep extra="ignore" (the default) when reading outputs from newer producers, and extra="forbid" for inputs you control, such as requests and settings.

3Mini project: a typed evaluation run

Before changing a prompt or a model, an LLM team runs an evaluation set: questions with expected facts, answered by the system and graded. The cases live in a JSON Lines file maintained by hand, so they must be validated; graders are interchangeable; and the report must be a well-defined object that can be stored as JSON and compared between runs. Build it from the pieces of this module.

Project

14. Load, run and report an evaluation set

Implement the following.

  • EvalCase: a Pydantic model forbidding extras and stripping strings, with id and question (non-empty strings), expected (a list of at least one string) and tags (a list of strings, default empty).
  • load_cases(text): parse JSON Lines, skipping blank lines, and return (cases, errors). Invalid lines add one error per validation error, f"line {n}: {loc}: {type}" (loc dotted, line if empty); a repeated id adds f"line {n}: id: duplicate {id!r}" and skips the case.
  • Grader: a Protocol with grade(self, case: EvalCase, answer: str) -> float.
  • ContainsGrader: a frozen dataclass with case_sensitive: bool = False whose grade returns the fraction of expected strings found in the answer.
  • CaseResult: a frozen dataclass (case_id, score, passed, error=None).
  • RunReport: a Pydantic model with total, passed, mean_score (rounded to 3 places), by_tag (tag to mean score rounded to 3, tags sorted), failures (ids that did not pass, in order) and results: list[CaseResult], plus a property pass_rate (0.0 for an empty run).
  • run_eval(cases, answer_fn, grader, threshold=0.5): answer and grade every case; if answer_fn raises, the case scores 0, fails and records f"{ExceptionName}: {message}" as its error; a case passes when its score is at least threshold.

solution.py
import json
from dataclasses import dataclass
from typing import Callable, Protocol
from pydantic import BaseModel, ConfigDict, Field, ValidationError


class EvalCase(BaseModel):
    model_config = ConfigDict(extra="forbid", str_strip_whitespace=True)
    id: str = Field(min_length=1)
    question: str = Field(min_length=1)
    expected: list[str] = Field(min_length=1)
    tags: list[str] = []


def load_cases(text: str) -> tuple[list[EvalCase], list[str]]:
    cases: list[EvalCase] = []
    errors: list[str] = []
    seen: set[str] = set()
    for n, line in enumerate(text.splitlines(), start=1):
        if not line.strip():
            continue
        try:
            case = EvalCase.model_validate_json(line)
        except ValidationError as e:
            for err in e.errors():
                loc = ".".join(map(str, err["loc"])) or "line"
                errors.append(f"line {n}: {loc}: {err['type']}")
            continue
        if case.id in seen:
            errors.append(f"line {n}: id: duplicate {case.id!r}")
            continue
        seen.add(case.id)
        cases.append(case)
    return cases, errors


class Grader(Protocol):
    def grade(self, case: EvalCase, answer: str) -> float: ...


@dataclass(frozen=True)
class ContainsGrader:
    case_sensitive: bool = False

    def grade(self, case: EvalCase, answer: str) -> float:
        if not self.case_sensitive:
            answer = answer.lower()
        found = sum((e if self.case_sensitive else e.lower()) in answer for e in case.expected)
        return found / len(case.expected)


@dataclass(frozen=True)
class CaseResult:
    case_id: str
    score: float
    passed: bool
    error: str | None = None


class RunReport(BaseModel):
    total: int
    passed: int
    mean_score: float
    by_tag: dict[str, float]
    failures: list[str]
    results: list[CaseResult]

    @property
    def pass_rate(self) -> float:
        return self.passed / self.total if self.total else 0.0


def run_eval(cases: list[EvalCase], answer_fn: Callable[[str], str], grader: Grader, threshold: float = 0.5) -> RunReport:
    results: list[CaseResult] = []
    tag_scores: dict[str, list[float]] = {}
    for case in cases:
        try:
            answer = answer_fn(case.question)
        except Exception as e:
            result = CaseResult(case.id, 0.0, False, f"{type(e).__name__}: {e}")
        else:
            score = grader.grade(case, answer)
            result = CaseResult(case.id, score, score >= threshold)
        results.append(result)
        for tag in case.tags:
            tag_scores.setdefault(tag, []).append(result.score)
    total = len(results)
    return RunReport(
        total=total,
        passed=sum(r.passed for r in results),
        mean_score=round(sum(r.score for r in results) / total, 3) if total else 0.0,
        by_tag={tag: round(sum(s) / len(s), 3) for tag, s in sorted(tag_scores.items())},
        failures=[r.case_id for r in results if not r.passed],
        results=results,
    )

Every lesson of the module has a job here:

  • Pydantic at the boundary (11.4): the hand-edited JSONL file is untrusted, so each line goes through model_validate_json, and every problem is reported with its line number and Pydantic's error type: blank questions, empty expectations, broken JSON and misspelt keys (extra="forbid") are all caught before the run, not halfway through it. The report is a model too, so it serialises to JSON with its nested results in one call and can be stored and compared across runs.
  • Dataclasses inside (11.3): results are created by our own code from trusted values, so a frozen dataclass is enough, and Pydantic still validates and dumps them as part of the report.
  • Protocols and hints (11.1, 11.2): run_eval needs only "something with grade", so ContainsGrader and the test's ExactGrader both work without a shared base class, and an LLM-as-judge grader could be added the same way. The annotations on every function document the data flow for the type checker.

Failures of the system under test are data, not crashes: a timeout becomes a failed case with its error recorded, so one flaky call cannot lose the whole run. pass_rate is a property, so it is derived rather than stored, and does not appear in the JSON. Production harnesses add concurrency, LLM-graded scores and comparisons with the previous run, but keep exactly this split between validated inputs, pluggable graders and a typed report.

Recap

  • Type hints describe and a type checker enforces before run time; nothing checks them while the program runs unless you validate.
  • Dataclasses (with frozen, order, kw_only, default_factory) model trusted internal data; TypedDict types plain dicts.
  • Protocols describe the behaviour a function needs, so implementations and test fakes plug in without inheritance; generics keep types flowing through.
  • Pydantic validates and converts at boundaries (files, environment, requests, LLM output), reporting every error with its location and type.
  • Validate once at the edge, pass typed trusted objects inward, and evolve schemas by adding optional fields and versioning them.
