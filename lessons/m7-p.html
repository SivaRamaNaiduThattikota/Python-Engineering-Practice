1How to use this page

For every error in a problem, ask the three questions this module has been about. Who should handle it? The lowest level that can do something useful; everyone else lets it pass (7.3). What kind is it? Expected and recoverable (bad input, a missing optional value), transient (timeouts, rate limits, overloaded servers), permanent (a bad request, a wrong key), or a bug (7.4). What must survive? The original type and traceback (bare raise, raise ... from), the consistency of the data, and enough context to debug it later (7.2).

The problems mix the lessons on purpose. The mini project at the end combines all of them in one client that real applications need.

HintOpen a hint

Handle bool first, then str(value).strip().lower() and look it up in two sets.

SolutionShow the solution and why
solution.py
TRUE = {"true", "yes", "on", "1"}
FALSE = {"false", "no", "off", "0"}

def parse_bool(value):
    if isinstance(value, bool):
        return value
    text = value.strip().lower() if isinstance(value, str) else None
    if text in TRUE:
        return True
    if text in FALSE:
        return False
    accepted = ", ".join(sorted(TRUE | FALSE))
    raise ValueError(f"expected one of {accepted}, got {value!r}")

bool("false") is True (any non-empty string is truthy, 1.1), which is why configuration parsing needs an explicit function. Accepting a fixed vocabulary and rejecting everything else with a message that lists the options turns a silent misconfiguration into an error at start-up, where it is cheap to fix. None becomes a ValueError with the same message rather than an AttributeError from calling .strip() on it. Sorting the accepted values makes the message the same on every run, since sets of strings have no stable order (6.2).

    except (ValueError, TypeError):

Hint 1Open a hint

class RecordError(ValueError): with __init__(self, message, lineno) calling super().__init__(message).

Hint 2Open a hint

In the generator: for n, line in enumerate(lines, start=1), skip blank lines, put only json.loads(line) in the try, and yield the result after it.

SolutionShow the solution and why
solution.py
import json


class RecordError(ValueError):
    def __init__(self, message, lineno):
        super().__init__(message)
        self.lineno = lineno


def records(lines):
    for n, line in enumerate(lines, start=1):
        if not line.strip():
            continue
        try:
            obj = json.loads(line)
        except json.JSONDecodeError as e:
            raise RecordError(f"line {n}: {e.msg}", lineno=n) from e
        yield obj

Inheriting from ValueError means existing code that catches ValueError keeps working, while new code can catch RecordError and read e.lineno instead of parsing the message. The parse is in the try and the yield outside it: if the yield were inside, an exception thrown into the generator at that point by its consumer could be caught by the wrong handler. e.msg is the JSONDecodeError's message without position details, and from e keeps those details in __cause__. Because the generator is lazy (6.3), the error is raised when the bad line is reached, after the first record was already delivered.

6. A retry that creates duplicates

create_ticket(api, payload, attempts) calls api(payload, idempotency_key) and retries on TimeoutError. The API creates a ticket once per idempotency key, but customers get duplicate tickets after timeouts. Fix it so every attempt for one ticket uses the same key. (new_key is injected so the test can see the keys.)

counter = itertools.count(1)

def api(payload, key):
    seen_keys.append(key)

HintOpen a hint

Generate the key once, before the loop.

SolutionShow the solution and why
solution.py
def create_ticket(api, payload, attempts, new_key):
    key = new_key()
    for attempt in range(1, attempts + 1):
        try:
            return api(payload, key)
        except TimeoutError:
            if attempt == attempts:
                raise

A timeout does not tell you whether the server did the work; here it did, every time, and only the replies were lost. With a new key per attempt, the server saw three different operations and created three tickets. The idempotency key identifies the logical operation, so it must be created once, before the first attempt, and reused for every retry; then the server can recognise a repeat and return the original result. Payment APIs (Stripe), and increasingly LLM batch and file APIs, support idempotency keys for exactly this reason.

After a training run, several temporary files must be removed. Write cleanup(paths, remove) that calls remove(path) for every path, even after failures. FileNotFoundError is fine and ignored. HintOpen a hint

Catch FileNotFoundError before OSError (it is a subclass). Collect the others with e.add_note(...).

SolutionShow the solution and why
solution.py
def cleanup(paths, remove):
    errors, count = [], 0
    for path in paths:
        try:
            remove(path)
        except FileNotFoundError:
            continue
        except OSError as e:
            e.add_note(f"path: {path}")
            errors.append(e)
        else:
            count += 1
    if errors:
        raise ExceptionGroup("cleanup failed", errors)
    return count

Cleanup is the one place where stopping at the first error is wrong: one locked file should not leave every other temporary file on disk. So each step is attempted, the failures are collected, and they are all reported together at the end, which is what exception groups are for (7.2). FileNotFoundError is caught first because it is an OSError too, and "already gone" is the desired end state. The notes record which path each error belongs to without changing the exception types, so a caller can still use except* PermissionError. Only OSErrors are collected; anything else, such as a TypeError from a bad path, is a bug and stops the loop at once.

SolutionShow the solution and why

solution.py
class StreamError(Exception):
    def __init__(self, message, kind, partial):
        super().__init__(message)
        self.kind = kind
        self.partial = partial


def stream_text(events):
    parts = []
    for event in events:
        kind = event.get("type")
        if kind == "delta":
            parts.append(event["text"])
            yield event["text"]
        elif kind == "stop":
            return
        elif kind == "error":
            err = event.get("error", {})
            raise StreamError(err.get("message", "stream error"), err.get("type", "unknown"), "".join(parts))
    raise StreamError("stream ended early", "incomplete", "".join(parts))

In a stream, the HTTP status was 200 long before the problem, so the error arrives as data and must be turned into an exception by your code. Carrying the partial text on the exception lets the caller choose: show what arrived with a warning, retry the whole request, or ask the model to continue from where it stopped. The user has already seen those words, so silently discarding them is rarely right. A stream that ends without its stop event is also an error, typically a dropped connection, and treating it as a complete answer would pass off a truncated reply as finished. The event names follow Anthropic's streaming format; OpenAI's streams differ in detail but need the same handling.

solution.py
import inspect


class ToolError(Exception):
    pass


class AgentError(Exception):
    pass


def _tool_message(tools, name, args):
    fn = tools.get(name)
    if fn is None:
        return f"error: unknown tool {name!r}"
    try:
        inspect.signature(fn).bind(**args)
    except TypeError as e:
        return f"error: bad arguments for {name!r}: {e}"
    try:
        return str(fn(**args))
    except ToolError as e:
        return f"error: {e}"


def run_agent(model, tools, question, max_steps=5):
    messages = [{"role": "user", "content": question}]
    for _ in range(max_steps):
        reply = model(messages)
        if reply["type"] == "answer":
            return reply["text"]
        messages = messages + [{"role": "tool", "content": _tool_message(tools, reply["tool"], reply["args"])}]
    raise AgentError(f"no answer after {max_steps} steps")

Three bugs. No step limit: a model that keeps calling tools would loop forever, costing money on every iteration; agent loops always need a maximum number of steps (and usually a token or time budget too), with a specific error when it is reached. except Exception: the AttributeError inside broken is a bug in your tool, and feeding it to the model as "error: 'int' object has no attribute..." hides it from you and confuses the model. Unhelpful messages: an unknown tool produced error: 'lookup' (the str of a KeyError), which the model cannot act on. The fix separates the three model-fixable cases, each with a clear message, from everything else, which propagates. The helper also keeps run_agent short, and building a new messages list each step avoids changing a list the model function might still hold (2.4).

13. How do you test error-handling code?

SolutionModel answer

By making the failures happen on demand. Inject dependencies (the transport, sleep, clock, the random generator) so tests can pass fakes that raise specific exceptions on specific calls, return truncated or invalid output, or advance time instantly; then assert on behaviour: which exception reaches the caller (pytest.raises(SomeError, match=...), 13.1), how many calls were made, which delays would have been waited, what was logged, and that data was left consistent. Test each class of failure separately: the expected ones (handled), the transient ones (retried, then raised), the permanent ones (not retried) and bugs (propagated). Test the boundaries too: zero attempts, deadlines exactly reached, empty batches. In larger systems, fault-injection tools and chaos testing deliberately break dependencies in staging, because fallbacks that are never exercised tend not to work.

14. What makes error handling for LLM and other remote APIs different from error handling in local code?

SolutionModel answer

Local errors are mostly deterministic: the same input fails the same way, so they are bugs to fix. Remote calls add failures that depend on time and on systems you do not control: timeouts, dropped connections, rate limits and overload, which are transient and need retries with backoff, jitter and deadlines; and ambiguity, since after a timeout you do not know whether the work was done, which makes idempotency essential. LLMs add a further layer: a successful response can still be wrong for your purposes, truncated, refused, or not in the required format, so validation, repair loops and explicit checks of finish reasons are part of error handling. Costs and latency matter (every retry is paid for and slow), so budgets, circuit breakers and caching are part of the design. And observability becomes central: request ids, attempt counts, error types and latencies must be logged, because intermittent failures can only be diagnosed after the fact.

16. Get valid JSON, reliably

Implement complete_json(prompt, providers, required, *, sleep, clock, rng, attempts=3, repairs=2, deadline=30.0, base=0.5).

  • providers is a list of (name, call); call(messages) returns reply text or raises. Try them in order.
  • Transient errors (TimeoutError, ConnectionError, RateLimitError, ServerError) are retried on the same provider up to attempts calls in total, waiting rng.uniform(0, base * 2 ** (n - 1)) before retry n, or the rate limit's retry_after if larger. Before any wait, if clock() - start + wait > deadline, raise DeadlineError from the last error. When a provider's attempts are used up, move to the next provider (no wait). If all fail, raise UnavailableError from the last error.
  • BadRequestError is permanent: re-raise it unchanged, immediately. Other exceptions propagate.
  • Invalid output (not a JSON object, or missing a required key): append the reply as an assistant message and a user message "Invalid reply: <error>. Reply with only a JSON object with keys: <keys>.", and call the same provider again, up to repairs times; repair calls do not count as transient attempts. When repairs run out, raise InvalidOutputError from the last error.
  • Return (data, info) where info is {"provider": name, "calls": total calls made, "repairs": repairs used}.

The exception classes are defined for you; LLMError is the base of all of them. The caller's messages are never modified (the client builds them from prompt).

from types import SimpleNamespace
top = SimpleNamespace(uniform=lambda a, b: b)
now = [0.0]
clock = lambda: now[0]
waits = []
def sleep(s):
    waits.append(s)
    now[0] += s

def provider(*outcomes):
    log = []
    def call(messages):
        log.append([m["content"] for m in messages])
        out = outcomes[len(log) - 1]
        if isinstance(out, Exception):
            raise out
        return out
    return call, log

def reset():
    now[0] = 0.0
    waits.clear()

solution.py
import json


class LLMError(Exception):
    pass


class RateLimitError(LLMError):
    def __init__(self, message, retry_after=None):
        super().__init__(message)
        self.retry_after = retry_after


class ServerError(LLMError):
    pass


class BadRequestError(LLMError):
    pass


class UnavailableError(LLMError):
    pass


class DeadlineError(LLMError):
    pass


class InvalidOutputError(LLMError):
    pass


TRANSIENT = (TimeoutError, ConnectionError, RateLimitError, ServerError)


def _parse(reply, required):
    data = json.loads(reply)
    if not isinstance(data, dict):
        raise ValueError("reply is not a JSON object")
    missing = [k for k in required if k not in data]
    if missing:
        raise ValueError(f"missing keys: {', '.join(missing)}")
    return data


def complete_json(prompt, providers, required, *, sleep, clock, rng, attempts=3, repairs=2, deadline=30.0, base=0.5):
    start = clock()
    calls = 0
    last_transient = None
    for name, call in providers:
        messages = [{"role": "user", "content": prompt}]
        failures = 0
        repairs_used = 0
        while True:
            calls += 1
            try:
                reply = call(messages)
            except TRANSIENT as e:
                last_transient = e
                failures += 1
                if failures >= attempts:
                    break
                wait = rng.uniform(0, base * 2 ** (failures - 1))
                wait = max(wait, getattr(e, "retry_after", None) or 0)
                if clock() - start + wait > deadline:
                    raise DeadlineError(f"deadline of {deadline}s would be exceeded") from e
                sleep(wait)
                continue
            try:
                data = _parse(reply, required)
            except ValueError as e:
                if repairs_used >= repairs:
                    raise InvalidOutputError(f"invalid output from {name} after {repairs_used} repairs") from e
                repairs_used += 1
                messages = messages + [
                    {"role": "assistant", "content": reply},
                    {"role": "user", "content": f"Invalid reply: {e}. Reply with only a JSON object with keys: {', '.join(required)}."},
                ]
                continue
            return data, {"provider": name, "calls": calls, "repairs": repairs_used}
    raise UnavailableError(f"all {len(providers)} providers failed") from last_transient

Every lesson of the module has a job here:

  • try / except / else (7.1): two separate try blocks keep the call and the parsing apart, so a transient network error and an invalid reply can never be confused, and BadRequestError, being neither transient nor a ValueError, propagates untouched, as does the KeyError bug.
  • Custom exceptions and chaining (7.2): one LLMError base lets callers catch everything from the client, while UnavailableError, DeadlineError and InvalidOutputError tell them why it failed; each is raised from the last underlying error, so the details survive in __cause__.
  • Design (7.3): the fallback provider is used only after transient failures, never for bad requests or bugs; info records which provider answered and how many repairs were needed, so degradation is measurable; and the conversation is rebuilt with +, never modifying shared state.
  • API errors (7.4): exponential backoff with injected jitter, Retry-After taking precedence, a deadline checked before every wait, no wait before failing over, and a repair loop that shows the model its invalid reply and the exact error.

Injecting sleep, clock and rng is what made seven scenarios testable in milliseconds. In production you would pass time.sleep, time.monotonic and random.Random(), add logging of each attempt (7.4), and possibly a circuit breaker per provider (7.3). Module 8 turns the retry part into a reusable decorator.

Recap

  • Handle each error where something useful can be done; everywhere else, let it pass untouched.
  • Classify by reaction: expected, transient (retry with backoff, jitter and a deadline), permanent (raise), bug (propagate).
  • Keep the evidence: bare raise, raise ... from, notes, attributes on custom exceptions, and one log entry with the traceback.
  • Keep data consistent and operations safe to repeat: build new then swap, idempotency keys created once.
  • Inject time, randomness and transports so every failure path can be tested.
