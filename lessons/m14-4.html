14.4 asyncio basics

asyncio runs thousands of waits concurrently in one thread, which is why modern LLM clients, web frameworks such as FastAPI, and agent frameworks are async. Coroutines and await, the event loop, tasks, gather and TaskGroup, why one blocking call stalls everything, async iteration and context managers, and how exceptions and cancellation travel. On this site asyncio runs on simulated time (14.1), so loop.time() shows exactly how long concurrent code would take.

1Coroutines and await

An async def function does not run when called: it returns a coroutine object, a paused computation. Inside it, await x waits for x (another coroutine, a task, or a future) and, crucially, lets the event loop run other work while x is not ready. asyncio.run(main()) creates an event loop, runs the coroutine main to completion, and closes the loop; it is the entry point of an async program, called once. Calling a coroutine function without awaiting it is a common bug: nothing runs, and Python warns coroutine ... was never awaited.

Awaiting one coroutine after another runs them sequentially, just like normal function calls; the concurrency comes from scheduling several at once, as tasks. asyncio.create_task(coro) schedules a coroutine to start as soon as the current task yields to the loop, and returns a Task you can await later. await asyncio.gather(a, b, c) runs several awaitables concurrently and returns their results in argument order.

await_vs_gather.py
import asyncio

async def call_model(name, seconds):
    await asyncio.sleep(seconds)      # stands in for waiting on the network
    return f"{name} done"

async def sequential():
    return [await call_model("a", 1), await call_model("b", 2), await call_model("c", 1)]

async def concurrent():
    return await asyncio.gather(call_model("a", 1), call_model("b", 2), call_model("c", 1))

async def timed(make):
    loop = asyncio.get_running_loop()
    start = loop.time()
    result = await make()
    return result, loop.time() - start

print(asyncio.run(timed(sequential)))
print(asyncio.run(timed(concurrent)))
print(type(call_model("x", 1)).__name__)
Output
(['a done', 'b done', 'c done'], 4.0)
(['a done', 'b done', 'c done'], 2.0)

The sequential version takes the sum of the waits, 4 seconds; with gather, all three wait at the same time and the total is the longest wait, 2 seconds. The last line creates a coroutine and never awaits it, which is exactly the "never awaited" mistake (Python prints a warning).

2How the event loop runs tasks

The event loop keeps a queue of tasks ready to run. It runs one until that task reaches an await on something not ready (a sleep, a network read), then picks the next ready task. When a timer expires or data arrives, the waiting task becomes ready again. Everything happens in one thread, so between two awaits a task runs without interruption: no other task can modify shared state in the middle of a block that contains no await. That makes asyncio easier to reason about than threads, but it also means a task that never awaits starves all the others.

This is the most important rule of asyncio: never block the event loop. A call to time.sleep(2), a synchronous HTTP library such as requests, a large file read, or a CPU-heavy loop inside a coroutine freezes every other task for its duration, so a server stops answering all users while one request tokenises a document. Use async libraries (asyncio.sleep, httpx.AsyncClient, the async clients of the OpenAI and Anthropic SDKs, aiofiles), and push unavoidable blocking calls to a thread with await asyncio.to_thread(fn, *args) or CPU work to a process pool with loop.run_in_executor(pool, fn, *args).

loop_order.py
import asyncio

events = []

async def worker(name, steps):
    for i in range(steps):
        events.append(f"{name}{i}")
        await asyncio.sleep(0)          # yield to the loop between steps

async def hog():
    events.append("hog start")
    total = sum(range(200_000))          # no await: nothing else can run meanwhile
    events.append("hog end")

async def main():
    await asyncio.gather(worker("a", 3), hog(), worker("b", 3))

asyncio.run(main())
print(events)
Output
['a0', 'hog start', 'hog end', 'b0', 'a1', 'b1', 'a2', 'b2']

asyncio.sleep(0) is a pure "let others run" point, so the workers take turns. The hog starts after a's first step and runs to the end without yielding, so everything else waits for it. With a real CPU-heavy function that would be seconds of a frozen server.

3gather, TaskGroup and exceptions

If one awaitable passed to gather raises, gather raises that exception at once, and the other awaitables keep running (they are not cancelled); with return_exceptions=True, exceptions are returned in the result list in place of values, which suits batches where each item may fail independently. asyncio.TaskGroup (Python 3.11) is the structured alternative: async with asyncio.TaskGroup() as tg: and tg.create_task(...) inside; the block waits for all tasks, and if any fails, it cancels the others and raises an ExceptionGroup with every failure, which you handle with except* clauses. Use TaskGroup when the tasks belong together (if one fails, the whole operation failed) and gather(..., return_exceptions=True) when each result stands alone.

Keep a reference to every task you create, and make sure each is awaited: the event loop holds only weak references to tasks, so a "fire and forget" task can be garbage-collected before it finishes, and an exception in a task nobody awaits is only reported as "Task exception was never retrieved" when it is destroyed. TaskGroup handles both for you.

4async with, async for and async generators

Objects whose setup or teardown must wait for I/O use async with: an HTTP client session, a database connection, a lock (asyncio.Lock), a semaphore (14.5). contextlib.asynccontextmanager turns an async generator with one yield into such a context manager, as @contextmanager does for sync code (10.2). Iterators that wait between items use async for: an async generator is an async def containing yield, and it can await between items. This is exactly the shape of streaming LLM responses: async for event in client.messages.stream(...) receives tokens as they are generated. Async comprehensions ([x async for x in agen()]) work too.

async_iter.py
import asyncio
from contextlib import asynccontextmanager

async def stream_reply(text, delay=0.05):
    for token in text.split():
        await asyncio.sleep(delay)       # tokens arrive over time
        yield token

@asynccontextmanager
async def connection(log):
    log.append("open")
    try:
        yield "conn"
    finally:
        log.append("close")

async def main():
    log = []
    async with connection(log) as conn:
        tokens = [t async for t in stream_reply("Refunds take five business days")]
    loop = asyncio.get_running_loop()
    return tokens, log, round(loop.time(), 2)

print(asyncio.run(main()))
Output
(['Refunds', 'take', 'five', 'business', 'days'], ['open', 'close'], 0.25)

5Cancellation

task.cancel() asks a task to stop: the next time it is suspended at an await, a CancelledError is raised inside it, so finally blocks and async with exits run its cleanup, and the task ends as cancelled. CancelledError derives from BaseException, not Exception, precisely so that except Exception: handlers do not swallow it; if you catch it to clean up, re-raise it. Timeouts are built on cancellation: asyncio.wait_for(aw, timeout) and async with asyncio.timeout(seconds): cancel the work when the time is up and raise TimeoutError (14.5). asyncio.shield(aw) protects an awaitable from being cancelled by its caller, for work that must finish (such as saving a result).

import asyncio

async def embed(text, seconds):
    await asyncio.sleep(seconds)
    return len(text)

async def main():

    t3 = loop.time()

async def work(name, seconds, fail=None):

    try:

Wrapping retrieval and model calls like this produces the latency metrics that 12.3's structured logs and dashboards report.

Hint 2Open a hint

SolutionShow the solution and why
solution.py
import asyncio


async def first_completed(*coros):
    pending = {asyncio.create_task(c) for c in coros}
    last_error = None
    try:
        while pending:
            done, pending = await asyncio.wait(pending, return_when=asyncio.FIRST_COMPLETED)
            for task in done:
                if task.exception() is None:
                    return task.result()
                last_error = task.exception()
        raise last_error
    finally:
        for task in pending:
            task.cancel()
        if pending:
            await asyncio.gather(*pending, return_exceptions=True)

asyncio.wait(..., FIRST_COMPLETED) returns as soon as at least one task finishes, with the done and still-pending sets, so the loop can inspect results as they arrive: the first success wins, and a failure simply means waiting for the next. The finally cancels whatever is still running and waits for those cancellations to complete, so no orphaned request keeps consuming a connection or tokens after the function returns (the log shows the slow replica cancelled). Hedging cuts p99 latency at the cost of extra requests, so production systems usually send the second request only if the first has not answered within, say, the p95 time.

solution.py
import asyncio


async def run_with_deadline(jobs, deadline):
    names = {asyncio.create_task(coro): name for name, coro in jobs.items()}
    result = {"done": {}, "failed": {}, "timed_out": []}
    if not names:
        return result
    done, pending = await asyncio.wait(names, timeout=deadline)
    for task in done:
        error = task.exception()
        if error is None:
            result["done"][names[task]] = task.result()
        else:
            result["failed"][names[task]] = f"{type(error).__name__}: {error}"
    for task in pending:
        task.cancel()
    await asyncio.gather(*pending, return_exceptions=True)
    result["timed_out"] = sorted(names[t] for t in pending)
    return result

A RAG service often queries several retrievers and must answer within a latency budget, using whatever arrived in time rather than waiting for the slowest source. asyncio.wait with a timeout returns at the deadline with the finished and unfinished sets, without raising; finished tasks are split into results and failures, and unfinished ones are cancelled and awaited so they stop consuming resources. The whole call ends at exactly 1.0 seconds, as the loop's clock shows. The answer can then be generated from the sources that responded, and the timed-out names logged as a degraded-quality signal.

import asyncio


async def answer_all(client, questions):
    try:
        results = await asyncio.gather(*(client.ask(q) for q in questions), return_exceptions=True)
        answers, errors = [], {}
        for i, r in enumerate(results):
            if isinstance(r, Exception):
                answers.append(None)
                errors[i] = f"{type(r).__name__}: {r}"
            else:
                answers.append(r)
        return {"answers": answers, "errors": errors}
    finally:
        await client.close()

Three classic async mistakes. Awaiting in a loop serialised the calls: three 1-second calls took 3 seconds instead of 1. gather without return_exceptions turns one failed call into an exception that discards every other result. And client.close() without await only creates a coroutine object, so the connection pool was never closed (Python warns "coroutine was never awaited"); in a finally it also runs when the batch fails. Keeping failed answers as None at their index, with errors keyed by index, keeps the output aligned with the questions for retries.

Interview

15. What is the event loop, and why does a single blocking call hurt an asyncio service so much?

SolutionModel answer

The event loop is a scheduler running in one thread: it runs a task until that task awaits something not ready, then switches to another ready task, and resumes the first when its I/O completes or its timer fires. Concurrency comes entirely from tasks voluntarily yielding at await points. A blocking call (time.sleep, requests.get, a synchronous database driver, a big file read, or CPU-heavy code like tokenising a document) never yields, so while it runs no other task makes progress: every in-flight request on the server stalls, timeouts fire, health checks fail, and latency spikes for all users. The fixes: use async libraries end to end, offload unavoidable blocking calls with asyncio.to_thread (or a thread pool) and CPU work with a process pool via run_in_executor, and detect problems with asyncio's debug mode, which logs callbacks that take longer than 100 ms.

Interview

16. asyncio or threads for I/O-bound work: how do you choose?

SolutionModel answer

Both overlap waits. Threads work with any library, including blocking ones, and require no change to the call chain, but each costs memory and OS scheduling, and shared state needs locks; tens to a few hundred concurrent operations are comfortable. asyncio runs thousands of concurrent operations in one thread with little overhead, switches only at explicit await points (so fewer data races), and has structured tools for timeouts, cancellation and limits (TaskGroup, asyncio.timeout, semaphores); but every library in the path must be async, async-ness spreads through the call chain ("function colouring"), and one blocking call stalls everything. Choose asyncio for high-concurrency network services and LLM batch clients built on async SDKs, or when the framework is async (FastAPI, agent frameworks); choose threads for a modest number of calls through synchronous libraries, or to integrate blocking code into async programs via to_thread.

Interview

17. Compare asyncio.gather and TaskGroup. When would you use each?

SolutionModel answer

gather(*aws) runs awaitables concurrently and returns results in order. By default, the first exception propagates immediately while the other awaitables keep running unattended; with return_exceptions=True, exceptions are returned as values, so it suits independent batch items where each outcome is recorded. TaskGroup (3.11+) provides structured concurrency: tasks are created inside an async with block, the block waits for all of them, and on the first failure it cancels the rest and raises an ExceptionGroup with every exception, handled with except*; no task can outlive the block, so there are no orphaned tasks or unretrieved exceptions, and cancellation of the parent propagates cleanly. Use TaskGroup when the subtasks are parts of one operation that should fail as a whole (fetch user, documents and settings to build one response); use gather(..., return_exceptions=True) (or tasks inside a group that catch their own errors) when partial success is acceptable, such as classifying a batch of messages.

Recap

  • async def returns a coroutine; await waits and lets other tasks run; asyncio.run(main()) is the single entry point.
  • Concurrency needs tasks: gather or create_task; awaiting in a loop is sequential. Measure with loop.time().
  • Never block the event loop: use async libraries, asyncio.to_thread for blocking calls, and process pools for CPU work.
  • gather(return_exceptions=True) for independent items; TaskGroup for operations that succeed or fail together, with except*.
  • Use async for for streams and async with for async resources; cancellation raises CancelledError (a BaseException) at the next await, so clean up and re-raise.
