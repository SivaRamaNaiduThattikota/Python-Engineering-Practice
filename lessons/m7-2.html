7.2 Raising and custom exceptions

How to raise well: choosing the type, writing messages people can act on, and re-raising without losing the original. Defining your own exception classes and hierarchies, chaining with raise ... from, adding notes, exception groups for several errors at once, and why assert is not validation. Applied to LLM client errors, configuration and data validation.

1Raising: the type, the message, and re-raising

raise SomeError("message") creates an exception object and raises it. You can also write raise SomeError without parentheses; Python then creates the instance for you with no arguments. The two decisions that matter are which type and what message, because those are what the caller and the person reading the log will act on.

RaiseWhenExample
TypeErrorthe argument has the wrong typea list where a string is required
ValueErrorright type, unacceptable valuetemperature=5 when the range is 0 to 2
KeyError / LookupErrora lookup by key or name found nothingan unknown model name in a registry
NotImplementedErrora method that a subclass must providea base provider class's complete()
RuntimeErrorthe operation is not possible in the current statecalling send() on a closed client
your own classan error callers will want to catch specificallyRateLimitError, InvalidOutputError

A good message answers three questions: what was wrong, which value caused it, and what was expected. ValueError("bad value") forces the reader to debug; ValueError("temperature must be between 0 and 2, got 5.0") tells them exactly what to change. Include the offending value with !r so strings show their quotes and invisible whitespace, and never include secrets (API keys, passwords, personal data) in messages, because messages end up in logs.

raise_well.py
def set_temperature(t):
    if isinstance(t, bool) or not isinstance(t, (int, float)):
        raise TypeError(f"temperature must be a number, got {type(t).__name__}")
    if not 0 <= t <= 2:
        raise ValueError(f"temperature must be between 0 and 2, got {t!r}")
    return float(t)

for value in [0.7, 5, "0.7", True]:
    try:
        print(set_temperature(value))
    except (TypeError, ValueError) as e:
        print(f"{type(e).__name__}: {e}")
Output
0.7
ValueError: temperature must be between 0 and 2, got 5
TypeError: temperature must be a number, got str
TypeError: temperature must be a number, got bool

bool is checked first because True is an instance of int (1.2) and would otherwise be accepted as 1.0. Inside an except block, a bare raise (no argument) re-raises the exception being handled, unchanged: same type, same message, same traceback. Use it when you only want to do something on the way out, such as log, count or clean up, and then let the error continue. Writing raise e also works, but adds the current line to the traceback; raise Exception(str(e)) is worse, because it replaces the type, so callers can no longer catch the specific error (problem 3).

bare_raise.py
failures = []

def parse(text):
    try:
        return int(text)
    except ValueError:
        failures.append(text)        # record it...
        raise                        # ...and let the same exception continue

try:
    parse("4x")
except ValueError as e:
    print(type(e).__name__, "|", e, "|", failures)
Output

2Defining your own exceptions

Built-in types describe what kind of problem happened; your own types describe which problem, in your domain's terms. That matters to callers: code that calls an LLM client wants to retry a rate limit, show a message for a bad request and alert someone for an authentication failure, and it can only tell them apart if they are different types. Defining one takes a single line, using the class statement, which Module 9 covers in full:

custom_basic.py
class LLMError(Exception):
    """Base class for every error raised by our LLM client."""

class RateLimitError(LLMError):
    pass

class InvalidOutputError(LLMError):
    pass

print(RateLimitError.__mro__[1].__name__, issubclass(RateLimitError, Exception))
try:
    raise RateLimitError("429: slow down")
except LLMError as e:                  # the base class catches every subclass
    print(type(e).__name__, "|", e)
Output
LLMError True
RateLimitError | 429: slow down

class RateLimitError(LLMError): creates a new type that inherits from LLMError, which inherits from Exception. The body can be just pass or a docstring: everything an exception needs (storing the message, printing it) is inherited. Because of the hierarchy, except RateLimitError catches only rate limits, while except LLMError catches every error from your client, and nothing from elsewhere. The usual design is one base class per library or component, with a few subclasses for the cases callers handle differently. Inherit from Exception (never BaseException), and name classes with an Error suffix.

Exceptions can carry data as well as a message, which makes them much more useful to handlers: a rate limit can say how long to wait, an invalid output can carry the raw text. Add an __init__ method that stores the extra values as attributes and passes the message on to the parent class with super().__init__(message) (Module 9 explains __init__ and super in depth; here the pattern is all you need).

custom_data.py
class LLMError(Exception):
    pass

class RateLimitError(LLMError):
    def __init__(self, message, retry_after):
        super().__init__(message)          # the message works as usual
        self.retry_after = retry_after     # extra data for handlers

class InvalidOutputError(LLMError):
    def __init__(self, message, raw):
        super().__init__(message)
        self.raw = raw

try:
    raise RateLimitError("rate limited by provider", retry_after=2.5)
except RateLimitError as e:
    print(e, "| wait", e.retry_after, "s |", e.args)

err = InvalidOutputError("reply is not JSON", raw="Sure! {label: spam}")
print(repr(err), "|", err.raw)
Output
rate limited by provider | wait 2.5 s | ('rate limited by provider',)
InvalidOutputError('reply is not JSON') | Sure! {label: spam}

3Chaining: raise ... from

Often the right response to a low-level error is to raise a higher-level one that means something to your caller: a JSONDecodeError while reading the settings file becomes a ConfigError("settings.json is not valid JSON"). The danger is losing the original, which holds the precise detail (line, column, the bad character). Python has three behaviours for an exception raised while handling another:

  • Implicit chaining: a plain raise NewError(...) inside except stores the original in new.__context__. The traceback shows both, separated by "During handling of the above exception, another exception occurred", which reads like a second bug happened in the handler.
  • Explicit chaining: raise NewError(...) from original stores it in new.__cause__. The traceback shows both with "The above exception was the direct cause of the following exception": this one is deliberate translation. Use it whenever you convert an error.
  • Suppressed: raise NewError(...) from None hides the original from the traceback. Use it only when the original is noise, for example a KeyError from an internal lookup that you replace with a clear "unknown model" message.
chaining.py
import json, traceback

class ConfigError(Exception):
    pass

def load(text, style):
    try:
        return json.loads(text)
    except json.JSONDecodeError as e:
        if style == "implicit":
            raise ConfigError("settings are not valid JSON")
        if style == "from":
            raise ConfigError("settings are not valid JSON") from e
        raise ConfigError("settings are not valid JSON") from None

for style in ["implicit", "from", "none"]:
    try:
        load("{bad", style)
    except ConfigError as err:
        text = traceback.format_exc()
        print(style, type(err.__cause__).__name__, type(err.__context__).__name__, err.__suppress_context__,
              "direct cause" in text, "During handling" in text)
Output
implicit NoneType JSONDecodeError False False True
from JSONDecodeError JSONDecodeError True True False
none NoneType JSONDecodeError True False False

Read the output column by column: with from e, __cause__ is set and the traceback says "direct cause"; implicit chaining sets only __context__; from None sets __suppress_context__, so the original is still stored in __context__ (for debuggers) but not printed. Handlers can use err.__cause__ to get at the original details (problem 6).

4Adding context with notes

Sometimes you do not want a new type at all, only more context: the error is a perfectly good ValueError, but the log should also say which file and which line was being processed. Since Python 3.11, any exception has an add_note(text) method. Notes are stored in e.__notes__ and printed under the message in the traceback. The pattern is: catch, add a note, re-raise with a bare raise, so the type and traceback stay exactly as they were.

notes.py
import traceback

def parse_line(line):
    name, score = line.split(",")
    return name, float(score)

def parse_file(lines, filename):
    out = []
    for n, line in enumerate(lines, start=1):
        try:
            out.append(parse_line(line))
        except ValueError as e:
            e.add_note(f"in {filename}, line {n}: {line!r}")
            raise
    return out

try:
    parse_file(["ana,0.9", "bo,high"], "scores.csv")
except ValueError as e:
    print(type(e).__name__, "|", e, "|", e.__notes__)
    print(traceback.format_exc().strip().splitlines()[-1])
Output
ValueError | could not convert string to float: 'high' | ["in scores.csv, line 2: 'bo,high'"]
in scores.csv, line 2: 'bo,high'

The caller still catches a ValueError, nothing about the error's type changed, but whoever reads the traceback sees the file and line immediately. Notes are ideal in loops and pipelines, where the low-level code that fails does not know where its input came from, and the code that knows does not want to change the exception type.

5Several errors at once: exception groups

Normally one exception stops everything. Two situations need to report several at once: concurrent tasks that fail independently (Module 14's asyncio.TaskGroup raises them together), and validation, where telling the user about all five problems in their request is better than revealing them one at a time. Python 3.11 added ExceptionGroup(message, [exceptions]) for this, and the except* clause to handle it: each except* SomeType clause receives a group containing only the exceptions of that type, and the others continue to the next clause.

exception_groups.py
def validate(request):
    errors = []
    if not request.get("prompt"):
        errors.append(ValueError("prompt is required"))
    if not 0 <= request.get("temperature", 0) <= 2:
        errors.append(ValueError("temperature must be between 0 and 2"))
    if not isinstance(request.get("max_tokens", 1), int):
        errors.append(TypeError("max_tokens must be an int"))
    if errors:
        raise ExceptionGroup("invalid request", errors)

try:
    validate({"prompt": "", "temperature": 3, "max_tokens": "512"})
except* ValueError as group:
    print("values:", [str(e) for e in group.exceptions])
except* TypeError as group:
    print("types:", [str(e) for e in group.exceptions])
Output
values: ['prompt is required', 'temperature must be between 0 and 2']
types: ['max_tokens must be an int']

Both handlers ran, each with its own part of the group, which a normal except cannot do. A plain except ExceptionGroup as eg: also works and gives you the whole group in eg.exceptions. Libraries such as Pydantic collect all validation errors in a similar spirit, in their own ValidationError type (11.4). Use groups when callers genuinely benefit from several errors; for a single failure, raise a single exception.

6assert is not validation

assert condition, "message" raises AssertionError when the condition is false. It is meant for internal invariants: things that can only be false if your own code has a bug, such as "this list is sorted here" or "the shapes match after my reshape". It is not a way to check input, for two reasons. Python removes every assert when it runs with the -O (optimise) flag, which some deployments use, so the check silently disappears. And AssertionError tells the caller nothing about what kind of problem it was; a ValueError or TypeError says "your argument is wrong", which is what input validation means (problem 9).

assert_vs_raise.py
import numpy as np

def cosine(a, b):
    a, b = np.asarray(a, dtype=float), np.asarray(b, dtype=float)
    if a.shape != b.shape:                       # input validation: raise
        raise ValueError(f"shapes differ: {a.shape} vs {b.shape}")
    norm = np.linalg.norm(a) * np.linalg.norm(b)
    if norm == 0:
        raise ValueError("cosine is undefined for a zero vector")
    result = float(a @ b / norm)
    assert -1.0001 <= result <= 1.0001, result   # invariant: can only fail if the maths above is wrong
    return round(result, 4)

print(cosine([1, 0], [1, 1]))
try:
    cosine([1, 2, 3], [1, 2])
except ValueError as e:
    print("ValueError:", e)
Output
0.7071
ValueError: shapes differ: (3,) vs (2,)

solution.py
def check_settings(temperature, max_tokens):
    if isinstance(temperature, bool) or not isinstance(temperature, (int, float)):
        raise TypeError(f"temperature must be a number, got {temperature!r}")
    if isinstance(max_tokens, bool) or not isinstance(max_tokens, int):
        raise TypeError(f"max_tokens must be an int, got {max_tokens!r}")
    if not 0 <= temperature <= 2:
        raise ValueError(f"temperature must be between 0 and 2, got {temperature!r}")
    if max_tokens <= 0:
        raise ValueError(f"max_tokens must be positive, got {max_tokens!r}")
    return float(temperature), max_tokens

Type checks come first because comparing a string with a number would raise its own, less helpful, TypeError. The split between the two exception types follows their meaning: a string or a boolean is the wrong kind of value (TypeError), 3 is the right kind with an unacceptable value (ValueError). Each message names the setting and shows the value with repr, so '0.7' (a string) is distinguishable from 0.7. This is what API servers do when they return a 400 response with a message per field; Pydantic (11.4) generates such checks from type annotations.

solution.py
class LLMError(Exception):
    pass


class AuthError(LLMError):
    pass


class BadRequestError(LLMError):
    pass


class RateLimitError(LLMError):
    def __init__(self, message, retry_after):
        super().__init__(message)
        self.retry_after = retry_after


def raise_for_status(status, body, headers):
    if 200 <= status < 300:
        return
    message = f"{status}: {body[:100]}"
    if status in (401, 403):
        raise AuthError(message)
    if status == 429:
        raise RateLimitError(message, retry_after=float(headers.get("retry-after", 1.0)))
    if 400 <= status < 500:
        raise BadRequestError(message)
    raise LLMError(message)

Each subclass corresponds to a different reaction: authentication errors need a human (a wrong or expired key), rate limits need waiting, bad requests need the request fixed, and server errors are often worth a retry. That is the test for whether an error deserves its own class. Putting retry_after on the exception gives the retry code exactly what it needs without parsing the message. All of them inherit from LLMError, so a caller who does not care about the details can catch the base class. Official SDKs (OpenAI's, Anthropic's) have almost this hierarchy: AuthenticationError, RateLimitError, BadRequestError, InternalServerError, all under one APIError.

import json

class ConfigError(Exception):
    pass

def read_config(text):
    try:
        return json.loads(text)
    except json.JSONDecodeError as e:

solution.py
def parse_lines(lines):
    out = []
    for n, line in enumerate(lines, start=1):
        try:
            name, score = line.split(",")
            out.append((name.strip(), float(score)))
        except ValueError as e:

solution.py
import math

def normalise(vectors):
    if not vectors:
        raise ValueError("cannot normalise an empty list of vectors")
    dim = len(vectors[0])
    out = []
    for i, v in enumerate(vectors):
        if len(v) != dim:
            raise ValueError(f"vector {i} has length {len(v)}, expected {dim}")
        norm = math.sqrt(sum(x * x for x in v))
        if norm == 0:
            raise ValueError(f"vector {i} is a zero vector and has no direction")
        out.append([round(x / norm, 4) for x in v])
    return out

assert documents what your code guarantees; it is not for checking what callers pass in. With python -O every assert is stripped, so the bad input would flow on and fail later with a confusing ZeroDivisionError or an IndexError. ValueError is the expected type for unacceptable input, and the new messages say which vector failed and why, which AssertionError("length mismatch") did not. The test words (empty, length, zero) stand in for what a user would need to find in the message.

def parse_age(raw):
    if not raw.strip().isdigit():
        raise ValueError(f"age is not a number: {raw!r}")
    age = int(raw)
    if age > 130:
        raise ValueError(f"age out of range: {age}")

    errors = []
    messages = req.get("messages")
    if not isinstance(messages, list) or not messages:

def translate(fn, mapping):

        return fn()

        for source, target in mapping.items():

    pass

solution.py
def chain(exc):
    out, seen = [], set()
    while exc is not None and id(exc) not in seen:
        seen.add(id(exc))
        out.append(f"{type(exc).__name__}: {exc}")
        if exc.__cause__ is not None:
            exc = exc.__cause__
        elif exc.__suppress_context__:
            exc = None
        else:
            exc = exc.__context__
    return out

These are exactly the rules the traceback printer uses: an explicit cause wins, from None stops the chain, and otherwise the implicit context is followed. Each link is an exception object you can inspect, which is how error trackers such as Sentry show the whole story of a failure. The cycle guard matters because nothing forbids two exceptions from pointing at each other, and the standard library's printer has the same protection. id() is safe here because all the objects in the chain are alive at the same time (2.1). Note that the KeyError's message keeps its quotes, as str of a KeyError always does.

Interview

17. When should you define a custom exception, and how would you design the exception hierarchy for a library?

SolutionModel answer

Define a custom exception when callers need to react differently to a failure than to other failures: retry a rate limit, re-authenticate on an auth error, report bad input to the user. If no caller would ever catch it specifically, a built-in type with a good message is enough. For a library, create one base class (class MyLibError(Exception)) so users can catch everything from your library in one clause, and a small number of subclasses for the distinct reactions; inherit from a built-in as well when it fits existing expectations (a "not found" error can also subclass LookupError). Put useful data on the exception as attributes (status code, retry delay, the invalid value) instead of making users parse the message. Translate errors from your dependencies into your own types at the boundary, with raise ... from e, and document which exceptions each public function raises.

Interview

18. What is the difference between raise X from e, raising inside except without from, and raise X from None?

SolutionModel answer

All three happen while another exception e is being handled. Without from, Python sets X.__context__ = e (implicit chaining), and the traceback shows both with "During handling of the above exception, another exception occurred", which suggests the handler itself failed by accident. With from e, Python sets X.__cause__ = e and the traceback says "The above exception was the direct cause of the following exception": a deliberate translation, the right choice when you convert a low-level error into a meaningful one. With from None, the context is still stored but __suppress_context__ is set, so only X is printed; use it when the original is an implementation detail that would only confuse the reader, such as a KeyError from an internal dict lookup replaced by "unknown model".

Interview

19. How should a client library for an LLM API expose errors to its users?

SolutionModel answer

With a small, documented hierarchy under one base class, organised by what the user should do: authentication and permission errors (fix the key, no retry), bad requests including validation and context-length errors (fix the request, no retry), rate limits (wait, with the delay as an attribute from the Retry-After header), timeouts and connection errors (safe to retry with backoff), and server errors (often retryable). Each exception should carry structured data: HTTP status, provider error code, request id for support tickets, and the response body where safe, without leaking the API key. Low-level network exceptions are translated with from e so their details remain available. The library can retry transient errors itself, with a configurable maximum and exponential backoff with jitter, and should raise the final error, not swallow it. Streaming responses need the same treatment for errors that arrive mid-stream. The OpenAI and Anthropic Python SDKs follow exactly this design, which is why except anthropic.RateLimitError works the way users expect.

Recap

  • Pick the type by meaning (TypeError wrong kind, ValueError bad value, your own class for errors callers handle specially), and write messages with what, which value and what was expected.
  • A bare raise re-raises unchanged; never replace a specific error with a plain Exception.
  • Custom exceptions: one base class per component, subclasses per reaction, data as attributes via super().__init__(message).
  • Translate with raise New(...) from e; from None hides internal noise; add_note adds context without changing the type.
  • ExceptionGroup and except* report several errors at once. assert checks your own invariants, never input.
