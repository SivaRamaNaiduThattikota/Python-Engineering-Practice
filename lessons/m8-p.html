8.P Module 8 practice set and mini project

Mixed problems from all of Module 8: wrappers and functools.wraps, decorator factories and stacking order, caching, retries and timing, and registration with signature introspection. Then a mini project that needs all of it: a small tool framework for an agent, with generated schemas, caching, retries and statistics.

16 problems3 easy · 8 medium · 5 hard

1How to use this page

For every decorator, ask three questions. What runs when? The factory and the decorator run once, at definition time; the wrapper runs on every call (8.1, 8.2). What does the name end up bound to? A wrapper (then functools.wraps is mandatory), the original function (registration, 8.4), or something else. What must the wrapper never change? The arguments, the return value and the exceptions, unless changing them is the decorator's stated purpose (8.1). And with several decorators, decide the order on purpose: the top one is the outermost layer (8.2).

The problems mix the lessons on purpose. The mini project at the end combines all of them in one small framework of the kind agent libraries provide.

2. Check the return type

Write a decorator factory returns(*types) that checks the decorated function's result is an instance of one of types and raises TypeError(f"{name} returned {type_name}, expected {expected}") otherwise, where expected is the type names joined with " or ". Use functools.wraps.

HintOpen a hint

isinstance(result, types) accepts a tuple of types directly.

SolutionShow the solution and why
solution.py
import functools

def returns(*types):
    expected = " or ".join(t.__name__ for t in types)

    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            result = func(*args, **kwargs)
            if not isinstance(result, types):
                raise TypeError(f"{func.__name__} returned {type(result).__name__}, expected {expected}")
            return result
        return wrapper
    return decorator

The expected-types text is built once in the factory, and isinstance with a tuple covers several types in one check. A function that sometimes returns None instead of a string is a classic source of errors far downstream (a prompt containing the text "None"); checking at the boundary turns it into an immediate, precise error. Static type checkers catch many such problems before running (11.1), but data from models and APIs can still surprise you at run time.

HintOpen a hint

latest filters the keys with key[0] == name and takes max by version.

SolutionShow the solution and why
solution.py
PROMPTS = {}

def prompt(name, version):
    def decorator(func):
        key = (name, version)
        if key in PROMPTS:
            raise ValueError(f"prompt {name!r} version {version} is already registered")
        func.prompt_name = name
        func.prompt_version = version
        PROMPTS[key] = func
        return func
    return decorator

def latest(name):
    versions = [v for (n, v) in PROMPTS if n == name]
    if not versions:
        raise KeyError(name)
    return PROMPTS[(name, max(versions))]

Prompts change often, and comparing versions in evaluations requires keeping the old ones; a registry keyed by name and version does that, and the attributes on each function let traces and logs record which version produced an answer. Registration order does not matter, because latest picks the maximum version, not the last one registered (v2 was defined after v3). The duplicate check catches a copy-pasted decorator at import. Production systems often store prompt versions outside the code (a prompt management tool or a database), but the lookup logic is the same.

Without functools.wraps, inspect.signature sees the wrapper's (*args, **kwargs).

SolutionShow the solution and why
solution.py
import functools
import inspect

AUDIT = []

def audit(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        AUDIT.append(func.__name__)
        return func(*args, **kwargs)
    return wrapper

    names = inspect.signature(handler).parameters
    return handler(**{n: request[n] for n in names if n in request})

7. Run once, then reuse

Loading a model or creating a client should happen once, lazily, on first use. Write a decorator once for functions without arguments: the first call runs the function and stores its result; later calls return the stored result without calling it again. If the first call raises, nothing is stored and the next call tries again. Provide wrapper.reset() to forget the stored result. Use functools.wraps.

Hint 1Open a hint

Use a private sentinel _UNSET = object() (2.1) to tell "not loaded yet" apart from a function that returns None.

Hint 2Open a hint

Keep the state in a one-item dict or with nonlocal, so reset can change it.

SolutionShow the solution and why
solution.py
import functools

_UNSET = object()

def once(func):
    state = {"value": _UNSET}

    @functools.wraps(func)
    def wrapper():
        if state["value"] is _UNSET:
            state["value"] = func()
        return state["value"]

    def reset():
        state["value"] = _UNSET

    wrapper.reset = reset
    return wrapper

The sentinel distinguishes "never loaded" from "loaded, and the result happens to be None", which a plain None check would get wrong (2.1). If func() raises, the assignment never happens, so the state stays unset and the next call retries: a transient failure at start-up does not leave the process permanently broken. functools.cache on a zero-argument function gives the same caching but no simple per-function reset and no retry semantics you control. In threaded servers, two requests could both see the unset state and load twice; a lock around the check fixes that (14.2).

8. Recursive edit distance: plain or cached

Both compute the edit distance between two 7-character words with the same recursive definition. Which is faster?

import functools

def dist(a, b):
    if not a:
        return len(b)
    if not b:
        return len(a)
    if a[0] == b[0]:
        return dist(a[1:], b[1:])
    return 1 + min(dist(a[1:], b), dist(a, b[1:]), dist(a[1:], b[1:]))

        return len(a)

10. Inline retries and timing into decorators

Move the retry loop and the timing into two decorators, retrying(attempts) and timed, and apply them so the behaviour and TIMES stay the same. Keep the tests green.

TestsThe 4 checks Run tests uses

assert fetch("reset", flaky=True) == "result for reset"
assert TIMES == [5, 5]
assert fetch.__name__ == "fetch"
Hint 1Open a hint

The timing covers all attempts, so @timed must be the outer decorator.

Hint 2Open a hint

Inside the decorated function, failures must depend on an attempt counter; keep it in a small dict keyed by the query.

SolutionShow the solution and why
solution.py
import functools

TIMES = []
ticks = iter(range(0, 1000, 5))
clock = lambda: next(ticks)

def timed(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        start = clock()
        try:
            return func(*args, **kwargs)
        finally:
            TIMES.append(clock() - start)
    return wrapper

def retrying(attempts):
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            for attempt in range(1, attempts + 1):
                try:
                    return func(*args, **kwargs)
                except TimeoutError:
                    if attempt == attempts:
                        raise
        return wrapper
    return decorator

_tries = {}

@timed
@retrying(attempts=3)
def fetch(q, flaky):
    _tries[q] = _tries.get(q, 0) + 1
    if flaky and _tries[q] < 3:
        raise TimeoutError("slow")
    return f"result for {q}"

The original mixed three concerns in one function: the real work, retrying and timing. With decorators, fetch contains only the work, and the two policies are reusable and visible in its header. @timed sits on top so the measurement covers the whole retry sequence, as before; the clock is read twice per call either way, so TIMES is unchanged. The attempt counter had to move into state that survives across calls, because each retry is now a separate call of the inner function, a small sign of how decorators separate "the attempt" from "the policy". In real code the flakiness would come from the network, not a counter.

11. Stop a stream at a size limit

Write a decorator factory max_chars(limit) for generator functions that yield text chunks. The wrapper yields the chunks unchanged until the total length would exceed limit; it then yields only the part of that chunk that fits (if any), closes the underlying generator, sets wrapper.truncated = True and stops. If the stream ends within the limit, wrapper.truncated is False. Use functools.wraps.

TestsThe 6 checks Run tests uses

    finally:
        closed.append(True)

Hint 1Open a hint

Keep a running total. Create the inner generator yourself, gen = func(*args, **kwargs), so you can call gen.close().

Hint 2Open a hint

If total + len(chunk) > limit, yield chunk[:limit - total] if it is not empty, close, mark truncated, return.

SolutionShow the solution and why
solution.py
import functools

def max_chars(limit):
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            wrapper.truncated = False
            total = 0
            gen = func(*args, **kwargs)
            try:
                for chunk in gen:
                    if total + len(chunk) > limit:
                        rest = chunk[:limit - total]
                        if rest:
                            yield rest
                        wrapper.truncated = True
                        return
                    total += len(chunk)
                    yield chunk
            finally:
                gen.close()
        wrapper.truncated = False
        return wrapper
    return decorator

The wrapper is itself a generator (8.1), so the limit is applied while streaming, chunk by chunk, and the consumer receives text as soon as it arrives. Holding a reference to the inner generator lets the wrapper close it as soon as the limit is reached, which runs its finally block (the test's closed list); in a real stream, that is where the HTTP connection to the provider is released, so you stop paying for tokens you will discard. The finally in the wrapper also closes the source when the consumer itself stops early. Exactly reaching the limit is not truncation; only a chunk that would exceed it is. Guards like this protect UIs and logs from runaway generations.

import functools

FLAGS = {"new_ranker": False}
ROUTED = []


def feature(name, fallback):
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            if FLAGS.get(name, False):
                ROUTED.append(func.__name__)
                return func(*args, **kwargs)
            ROUTED.append(fallback.__name__)
            return fallback(*args, **kwargs)
        return wrapper
    return decorator

Three bugs. The flag was read in the factory, which runs once at import (8.2), so the value was frozen at False and flipping the flag later did nothing; a feature flag must be read on each call. The fallback received only *args, so top=2 was silently dropped and it used its default of 3, returning the wrong number of results without any error. And without functools.wraps, traces and the routing log of other tools would show wrapper. Feature flags like this let a team roll out a new retriever or prompt to some traffic and compare metrics, with the old path as an instant rollback; the two implementations must accept the same arguments, which the test checks with a keyword argument.

Interview

13. When should you not use a decorator?

SolutionModel answer

When the behaviour is not cross-cutting, or when it needs to vary per call. A decorator applies the same policy to every call of a function, fixed at definition time, which is ideal for logging, timing, caching, registration and simple retries, but awkward when the caller must choose (a timeout per request, a retry policy per endpoint, a different model per tenant); pass a parameter or use an explicit client object instead. Avoid decorators that change a function's signature or return type in surprising ways, that hide important control flow (a decorator that sometimes skips the call), or that accumulate so many settings they become a configuration language. Stacks of five decorators make the order of effects hard to see. And remember the practical limits: generators and async functions need matching wrappers, recursion goes through the wrapper, and introspection needs functools.wraps. A plain function call inside the body is often the clearest choice.

14. How do you test code that uses decorators?

SolutionModel answer

Test the decorator itself once, with tiny fake functions: that it returns results and raises exceptions unchanged, preserves the name and signature, and applies its policy (number of retries, cache hits, recorded timings) correctly; inject the clock, sleep and random generator so those tests run instantly. Then test decorated business functions without the decorator's side effects when they get in the way: call func.__wrapped__ to reach the original, clear caches between tests with cache_clear() (or a fixture that does it automatically, 13.2), and give registries a fresh instance per test instead of a global dict. For registration, assert that importing the module registers what you expect, and that duplicates fail. For decorators that read configuration, test both values of each flag, and test that the value is read at the intended time. Finally, include a few tests through the real decorated path, because the composition order of stacked decorators is itself behaviour worth checking.

3Mini project: a tool framework for an agent

Agent libraries let you turn plain functions into tools with a decorator. Build a small version: tools are registered with metadata, their schemas are generated from signatures and type hints, idempotent tools can be cached, flaky ones retried, every call goes through one dispatcher that validates arguments and returns errors the model can act on, and per-tool statistics are kept. Every rule in the spec maps to a lesson in this module.

Project

16. Build the toolkit

Implement make_toolkit() returning (tool, run, schemas, stats).

  • tool(*, description=None, cache=False, retries=0, retry_on=(TimeoutError,)) is a decorator factory. It registers the function under its name (duplicates raise ValueError), with the description or else the first docstring line. Every parameter must have a type annotation among str, int, float, bool, or TypeError is raised at decoration time. It returns the function unchanged.
  • schemas() returns a list, sorted by tool name, of {"name", "description", "parameters": {"type": "object", "properties": {p: {"type": json_type}}, "required": [...]}}.
  • run(name, args) returns {"result": value} or {"error": message}: "unknown tool 'x'"; "bad arguments: <bind error>" for missing or unknown arguments. Then it calls the tool: with cache=True, results are cached by (name, sorted argument items); with retries=n, an exception in retry_on is retried up to n more times, and if it still fails, run returns {"error": "<name> failed: <Type>: <message>"}. Any other exception propagates.
  • stats() returns {name: {"calls": c, "cache_hits": h, "errors": e}} for every registered tool, where calls counts run calls that reached the tool (cache hits included) and errors counts calls that ended in a returned failure.

import inspect, typing

JSON_TYPES = {str: "string", int: "integer", float: "number", bool: "boolean"}


def _schema(func, description):
    hints = typing.get_type_hints(func)
    props, required = {}, []
    for pname, p in inspect.signature(func).parameters.items():
        kind = hints.get(pname)
        if kind not in JSON_TYPES:
            raise TypeError(f"{func.__name__}: parameter {pname!r} needs a str, int, float or bool annotation")
        props[pname] = {"type": JSON_TYPES[kind]}
        if p.default is p.empty:
            required.append(pname)
    return {"name": func.__name__, "description": description,
            "parameters": {"type": "object", "properties": props, "required": required}}


def make_toolkit():
    entries = {}

    def tool(*, description=None, cache=False, retries=0, retry_on=(TimeoutError,)):
        def decorator(func):
            name = func.__name__
            if name in entries:
                raise ValueError(f"tool {name!r} is already registered")
            doc = inspect.getdoc(func) or ""
            desc = description or (doc.splitlines()[0] if doc else "")
            entries[name] = {
                "func": func,
                "schema": _schema(func, desc),
                "cache": {} if cache else None,
                "retries": retries,
                "retry_on": retry_on,
                "stats": {"calls": 0, "cache_hits": 0, "errors": 0},
            }
            return func
        return decorator

    def run(name, args):
        entry = entries.get(name)
        if entry is None:
            return {"error": f"unknown tool {name!r}"}
        func = entry["func"]
        try:
            inspect.signature(func).bind(**args)
        except TypeError as e:
            return {"error": f"bad arguments: {e}"}
        entry["stats"]["calls"] += 1
        key = tuple(sorted(args.items()))
        if entry["cache"] is not None and key in entry["cache"]:
            entry["stats"]["cache_hits"] += 1
            return {"result": entry["cache"][key]}
        for attempt in range(entry["retries"] + 1):
            try:
                result = func(**args)
            except entry["retry_on"] as e:
                if attempt == entry["retries"]:
                    entry["stats"]["errors"] += 1
                    return {"error": f"{name} failed: {type(e).__name__}: {e}"}
                continue
            if entry["cache"] is not None:
                entry["cache"][key] = result
            return {"result": result}

    def schemas():
        return [entries[n]["schema"] for n in sorted(entries)]

    def stats():
        return {n: dict(e["stats"]) for n, e in entries.items()}

    return tool, run, schemas, stats

Every lesson of the module has a job here:

  • Decorator factories (8.2): @tool(cache=True) and @tool(retries=2) carry settings, validated and stored when the module is imported; settings are keyword-only, so @tool cannot be misused positionally without an error.
  • Registration and introspection (8.4): the decorator returns the function unchanged (so get_order(1) still works directly), refuses duplicates, and generates each schema once from the signature, the type hints and the docstring, so the schemas the model sees can never drift from the code. Unannotated parameters fail at import, not when the model calls them.
  • Caching and retries (8.3): the cache key is built from sorted argument items, so argument order does not matter; only successful results are cached; only the configured transient errors are retried, and a final failure becomes a message for the model rather than a crash, while a KeyError from a bug propagates (7.3).
  • Wrapper rules (8.1): nothing about the tools' behaviour changes; the policies live in the dispatcher, and statistics record calls, hits and returned errors per tool.

Putting caching and retries in run rather than in wrappers around each function keeps the registered object identical to the user's function, which makes tools easy to test directly. Real frameworks add timeouts, permissions and tracing in the same dispatcher, and build parameter validation from Pydantic models (11.4).

Recap

  • Decorators run once at definition time; wrappers run per call and must pass arguments, results and exceptions through unchanged.
  • Every wrapper gets functools.wraps: names, signatures and __wrapped__ are what frameworks, logs and tests rely on.
  • Factories validate settings at import; read anything dynamic (flags, limits) at call time.
  • Order is behaviour: registration outermost, caches outside what they should skip, timers outside retries when measuring the user's wait.
  • Registries plus inspect.signature and type hints turn plain functions into routes, commands and tools.
