13.3 Mocking

Code that calls a model API, a database, the clock or the network cannot be unit-tested by calling the real thing: it is slow, costs money, needs keys and gives different answers each time. Test doubles replace those dependencies. unittest.mock from the ground up (Mock, return_value, side_effect, call assertions, spec and autospec), patch and where to patch, fakes and injected dependencies, and the ways mocking goes wrong.

17 problems4 easy · 9 medium · 4 hard

1Why test doubles, and which kind

A unit test should be fast, deterministic and free. Calls to an LLM API, a vector database, an HTTP service, the system clock or a random generator are none of those, so tests replace them with test doubles. The vocabulary helps when discussing designs. A stub returns canned answers ("the model always replies spam"). A fake is a simple working implementation (a dict-backed store, a scripted chat model). A mock records calls so the test can assert how the dependency was used ("called once with max_tokens=200"). A spy wraps the real object and records calls while still doing the real work.

Choose by what the test is about. To check what your code returns given certain dependency behaviour, stubs and fakes are enough and keep tests robust. To check what your code does to the outside world (sends one e-mail, retries three times, passes the right parameters to the API), assert on the calls of a mock. Asserting on every internal call of everything couples tests to implementation details, so a refactor breaks them although behaviour did not change (problem 13).

2Mock: return values, side effects and call records

unittest.mock.Mock() creates an object that accepts any attribute access and any call: m.complete("hi") returns another Mock, and every call is recorded. Configure behaviour with return_value (what calling returns) and side_effect: an exception class or instance to raise, an iterable to return (or raise) one item per call, or a function whose result is returned. Inspect with called, call_count, call_args (the last call, as a call(...) object), call_args_list (all calls) and mock_calls (including calls on child attributes), or assert with assert_called_once_with(...), assert_called_with(...) (the last call only), assert_any_call(...), assert_has_calls([...]) and assert_not_called().

mock_basics.py
from unittest.mock import Mock, call

The last line shows the danger: a bare Mock accepts any attribute, so if the real client's method is complete and your code calls compelte, the test still passes. Mock(spec=RealClass) (or create_autospec(RealClass)) restricts the mock to the real API: unknown attributes raise AttributeError, and with autospec, calls with the wrong arguments raise TypeError just as the real methods would (problems 3 and 14). MagicMock additionally supports magic methods such as len(), iteration and with.

3patch and where to patch

When code creates or imports its dependency itself instead of receiving it, the test must replace it in place. unittest.mock.patch("module.name", new=...) replaces the attribute name of module for the duration of a with block or a decorated test, and restores it afterwards; patch.object(obj, "attr") does the same for an object you already hold, and patch.dict(os.environ, {...}) for dictionary entries. pytest's monkeypatch.setattr (13.2) is the fixture-based equivalent.

The rule that trips everyone: patch where the name is looked up, not where it is defined. If app.py does from weather import fetch, then app has its own name fetch bound to the function at import time; patching weather.fetch changes the weather module's attribute, but app.fetch still points to the original. Patch app.fetch instead, or have app do import weather and call weather.fetch(...), which looks the name up at call time (problem 10).

where_to_patch.py
from lessontools import run_pytest

WEATHER = '''
def fetch(city):
    raise RuntimeError("network access in a test!")
'''
APP = '''
from weather import fetch

def headline(city):
    return f"{city}: {fetch(city)['temp']} C"
'''
SRC = '''
from unittest.mock import patch
import app

def test_patch_definition():
    with patch("weather.fetch", return_value={"temp": 21}):
        assert app.headline("Oslo") == "Oslo: 21 C"

def test_patch_lookup():
    with patch("app.fetch", return_value={"temp": 21}) as fake:
        assert app.headline("Oslo") == "Oslo: 21 C"
    fake.assert_called_once_with("Oslo")
'''
r = run_pytest(SRC, {"weather": WEATHER, "app": APP})

4Prefer injected fakes

Patching is a workaround for code that hides its dependencies. The cleaner design passes them in: def summarise(text, client): or a class that receives its client in __init__, with a sensible default in production. Then a test passes a fake, no patching needed, and the code documents what it depends on. The same applies to time (clock=time.monotonic as a parameter, or an injected now() function), randomness (rng=random.Random(seed)), sleeping (sleep=time.sleep, so retry tests do not actually wait) and file locations (12.1). Fakes are reusable across tests and can model behaviour a stub cannot, such as "the store returns what was added", and they keep tests about outcomes rather than calls.

fake_clock.py
class FakeClock:
    def __init__(self, start=0.0):
        self.now = start
    def __call__(self):
        return self.now
    def advance(self, seconds):
        self.now += seconds

class TTLCache:
    def __init__(self, ttl, clock):
        self.ttl, self.clock, self._data = ttl, clock, {}
    def set(self, key, value):
        self._data[key] = (value, self.clock() + self.ttl)
    def get(self, key):
        value, expires = self._data.get(key, (None, 0))
        return value if self.clock() < expires else None

clock = FakeClock()
cache = TTLCache(ttl=60, clock=clock)
cache.set("answer:refunds", "5 days")
clock.advance(59.9)
print(cache.get("answer:refunds"))
clock.advance(0.1)
print(cache.get("answer:refunds"))
Output
5 days
None

Testing the expiry with the real clock would mean sleeping for a minute, or a flaky test with a tiny TTL; the fake clock makes it instant and exact, down to the boundary.

5How mocking goes wrong

Mocks that drift from reality: a mock configured to return a dict when the real client returns an object, or accepting a parameter the real API renamed, passes while production fails; use spec/autospec, and keep a few integration tests against the real thing (13.4). Over-mocking: patching the function under test's own helpers, or asserting every internal call, tests the implementation instead of the behaviour, so the test passes for wrong code and fails for correct refactors. Mocking what you don't own: sprinkling patches of a third-party SDK through many tests ties them to its internals; wrap the SDK in a small adapter class of your own (LLMClient.complete(prompt) -> str), mock or fake the adapter in unit tests, and test the adapter itself against the real SDK separately. Asserting the wrong call: assert_called_with checks only the last call, so it misses problems in earlier ones (problem 7).

class LLMClient:
    def complete(self, prompt, max_tokens):
        raise NotImplementedError("real API call")


def summarise(client, text, max_words=50):
    if not text.strip():

# --- tests ---
import pytest
from unittest.mock import Mock


@pytest.fixture
def client():
    c = Mock(spec=LLMClient)
    c.complete.return_value = "  Refunds take five days.\n"
    return c


def test_returns_stripped_reply(client):
    assert summarise(client, "Long refund policy text") == "Refunds take five days."


def test_calls_client_once_with_token_budget(client):
    summarise(client, "Long refund policy text", max_words=30)
    client.complete.assert_called_once()
    assert client.complete.call_args.kwargs == {"max_tokens": 60}


def test_prompt_contains_text_and_limit(client):
    summarise(client, "Refunds take five business days.", max_words=20)
    prompt = client.complete.call_args.args[0]
    assert "Refunds take five business days." in prompt and "20 words" in prompt


def test_blank_text_raises_without_calling(client):
    with pytest.raises(ValueError):
        summarise(client, "   ")
    client.complete.assert_not_called()

The mock stands in for the API, returns a canned reply with whitespace (so stripping is visible), and records the call, which lets the tests check the two things that matter about the interaction: what was sent (the prompt contains the text and the limit, the token budget is derived from max_words) and how often (once, and not at all for blank input, which would waste money). spec=LLMClient makes the mock refuse methods the real client does not have. Note what the tests do not check: the exact prompt wording, which can change freely without breaking them.

class SearchClient:
    def query(self, text, top_k):
        raise NotImplementedError("real vector database")


def top_sources(client, question, k=3):
    hits = client.query(question, top_k=k)
    return [h["source"] for h in hits]


# --- tests ---
from unittest.mock import create_autospec


def test_top_sources():
    client = create_autospec(SearchClient, instance=True)
    client.query.return_value = [{"source": "faq.md"}, {"source": "terms.md"}]
    assert top_sources(client, "refunds?", k=2) == ["faq.md", "terms.md"]

4. The forms of side_effect

from unittest.mock import Mock

def show(m, *args):
    try:
        return repr(m(*args))
    except Exception as e:
        return f"{type(e).__name__}: {e}"

a = Mock(side_effect=ConnectionError)
b = Mock(side_effect=ConnectionError("reset by peer"))
c = Mock(side_effect=["first", TimeoutError("slow"), "third"])
d = Mock(side_effect=lambda text: text.upper(), return_value="ignored")
print(show(a), "|", show(b))
print([show(c) for _ in range(4)])
print(show(d, "spam"), c.call_count)
HintOpen a hint

An exception class or instance is raised. An iterable yields one item per call, raising items that are exceptions. A function's result wins over return_value.

SolutionShow the solution and why
Real output
ConnectionError:  | ConnectionError: reset by peer
["'first'", 'TimeoutError: slow', "'third'", 'StopIteration: ']
'SPAM' 4

A class is instantiated and raised with no message; an instance is raised as it is. An iterable gives successive results, raising those that are exceptions, and when exhausted the mock raises StopIteration, a common surprise when a test calls the mock more often than expected. A function in side_effect is called with the same arguments and its result is returned, so return_value is ignored. The failed and exhausted calls still count towards call_count.

def call_with_backoff(fn, sleep, attempts=3, base=1.0):
    for i in range(attempts):
        try:
            return fn()
        except (TimeoutError, ConnectionError):
            if i == attempts - 1:
                raise
            sleep(base * 2 ** i)


# --- tests ---
import pytest
from unittest.mock import Mock, call


def test_succeeds_after_transient_errors_with_exponential_waits():
    fn = Mock(side_effect=[TimeoutError(), ConnectionError(), "ok"])
    sleep = Mock()
    assert call_with_backoff(fn, sleep, attempts=3, base=0.5) == "ok"
    assert sleep.call_args_list == [call(0.5), call(1.0)]


def test_gives_up_after_attempts_without_final_sleep():
    fn = Mock(side_effect=TimeoutError("slow"))
    sleep = Mock()
    with pytest.raises(TimeoutError, match="slow"):
        call_with_backoff(fn, sleep, attempts=4)
    assert fn.call_count == 4
    assert sleep.call_args_list == [call(1.0), call(2.0), call(4.0)]


def test_other_errors_are_not_retried():
    fn = Mock(side_effect=ValueError("bad request"))
    sleep = Mock()
    with pytest.raises(ValueError):
        call_with_backoff(fn, sleep)
    assert fn.call_count == 1
    sleep.assert_not_called()


def test_first_success_does_not_sleep():
    fn = Mock(return_value=42)
    sleep = Mock()
    assert call_with_backoff(fn, sleep) == 42
    sleep.assert_not_called()

Because sleep is a parameter, the test passes a Mock and the "waiting" is just a recorded call, so a test of a 7-second backoff runs in microseconds and the waits themselves become checkable values. side_effect with a list scripts the dependency's behaviour call by call (two transient failures, then success). The assertions pin the observable contract: the exact wait sequence (exponential, not linear, which needs at least three waits, since 1 then 2 starts both sequences), no pointless sleep after the last attempt, the exact number of calls, the error re-raised, and non-transient errors not retried, which matters for LLM APIs where a 400 "bad request" will never succeed on retry while a 429 or timeout might.

# --- code under test (do not edit) ---
class TTLCache:
    def __init__(self, ttl, clock):
        self.ttl, self.clock, self._data = ttl, clock, {}

    def set(self, key, value):
        self._data[key] = (value, self.clock() + self.ttl)

    def get(self, key):
        if key not in self._data:
            return None
        value, expires = self._data[key]
        if self.clock() >= expires:
            del self._data[key]
            return None
        return value

    def __len__(self):
        now = self.clock()
        return sum(1 for _, expires in self._data.values() if now < expires)


# --- tests ---

    def __init__(self):

    clock.advance(29.999)
    assert cache.get("q") == "5 days"


def test_expires_exactly_at_ttl(cache, clock):
    cache.set("q", "5 days")
    clock.advance(30)
    assert cache.get("q") is None


def test_set_refreshes_expiry(cache, clock):
    cache.set("q", "old")
    clock.advance(20)
    cache.set("q", "new")
    clock.advance(20)
    assert cache.get("q") == "new"


def test_len_counts_only_live_entries(cache, clock):
    cache.set("a", 1)
    clock.advance(15)
    cache.set("b", 2)
    clock.advance(20)
    assert len(cache) == 1


def test_missing_key(cache):
    assert cache.get("nope") is None

Injecting the clock turns time into test data: the fake starts at an arbitrary instant, and advance moves it by exact amounts, so the boundary (29.999 versus 30 seconds) can be tested precisely, which no test using real time could do reliably. The fixtures compose: cache asks for the same clock instance the test receives, so the test controls the cache's notion of now. The cases mirror the specification: strictly-before semantics at the boundary, refresh on overwrite, live-only counting, and a TTL other than the mutant's hard-coded 60. Caches of LLM answers and embeddings rely on exactly this logic.

assert_called_with compares only call_args, the most recent call, so any mistake in earlier calls is invisible; its name invites exactly this misuse. class FakeLLM:
    def __init__(self, script):
        self.script = list(script)
        self.prompts = []
        self._used = set()

    def complete(self, prompt):
        self.prompts.append(prompt)
        for substring, reply in self.script:
            if substring in prompt:
                self._used.add(substring)
                if isinstance(reply, BaseException):
                    raise reply
                return reply
        raise AssertionError(f"unexpected prompt: {prompt[:40]!r}")

    def assert_all_used(self):
        unused = [s for s, _ in self.script if s not in self._used]
        if unused:
            raise AssertionError(f"script entries never used: {unused}")

A scripted fake is the workhorse for testing LLM-driven code: tests state which prompts to expect and what the "model" answers, including failures, and the fake checks the other direction too: an unexpected prompt fails loudly instead of returning a meaningless mock, and assert_all_used catches code paths that silently stopped calling the model. Matching on substrings rather than exact prompts keeps tests robust to wording changes while still pinning the important part. Libraries offer the same idea (LangChain's fake chat models, respx or responses for HTTP-level fakes, VCR-style cassettes that replay recorded responses); 13.4 uses this fake for an agent.

# --- code under test (do not edit) ---
def run_agent(llm, tools, question, max_steps=4):
    messages = [{"role": "user", "content": question}]
    for _ in range(max_steps):
        step = llm.next(list(messages))
        if "answer" in step:
            return step["answer"]
        name = step["tool"]
        if name in tools:
            content = str(tools[name](**step.get("args", {})))
        else:
            content = f"error: unknown tool {name}"
        messages.append({"role": "tool", "name": name, "content": content})
    raise RuntimeError(f"no answer after {max_steps} steps")

Interview

15. What is the difference between a mock, a stub and a fake, and when do you use each?

SolutionModel answer

All three replace a real dependency in tests. A stub returns canned data and does nothing else, useful when the test only needs the dependency to answer (a model that always replies spam). A fake is a lightweight working implementation (an in-memory repository, a scripted LLM, a fake clock); it supports realistic sequences of operations, can be shared across many tests, and keeps tests focused on outcomes. A mock records interactions so the test can verify how the dependency was used (called once, with these arguments, never on this path); use it when the interaction is the behaviour, such as sending a notification, retrying with backoff or not calling a paid API. Spies wrap the real thing and record calls. Prefer stubs and fakes for state and results, mocks for important side effects, and verify mocks against the real interface with spec/autospec so they cannot drift.

Interview

16. Why do people say 'don't mock what you don't own'?

SolutionModel answer

Mocking a third-party library (an LLM SDK, requests, a cloud client) directly in many tests encodes your assumptions about its behaviour into every test: method names, argument shapes, return types and error classes. When the library changes, or when your assumptions were wrong, the tests keep passing while production fails, and the patches are scattered everywhere. Instead, wrap the library in a thin adapter you own with a small interface that suits your application (LLMClient.complete(prompt, max_tokens) -> str, raising your own LLMError), mock or fake that in unit tests, and test the adapter itself against the real library with a few integration tests (or recorded responses). The adapter also gives you one place for retries, timeouts, logging and switching providers.

Interview

17. How do you unit-test code that calls an LLM API?

SolutionModel answer

Separate the parts. Put the API behind a small client interface and inject it, so unit tests pass a fake or a mock: scripted replies for the happy path, malformed JSON and refusals for parsing and repair logic, TimeoutError and rate-limit errors for retry logic, and assertions on the prompts sent (that they contain the context and question, that no call happens when there is no context) and on call counts and parameters. Keep the deterministic logic (prompt building, output parsing and validation, routing, tool dispatch) in pure functions tested directly. Use spec/autospec so fakes match the real client. Then add a thin layer of integration tests against the real API, few, marked (@pytest.mark.integration) and run in CI with a key and a budget, possibly replaying recorded responses (VCR cassettes) for stability. Finally, evaluate model quality separately with an evaluation set (13.4), because unit tests check your code's behaviour, not whether the model's answers are good.

Recap

  • Test doubles replace slow, costly or random dependencies: stubs answer, fakes work, mocks record calls, spies wrap the real thing.
  • Mock configures behaviour with return_value and side_effect (exception, iterable, function) and records calls; assert_called_with checks only the last call.
  • Use spec or create_autospec so doubles match the real API; MagicMock adds magic methods.
  • Patch where a name is looked up (app.fetch, not weather.fetch), or better, inject dependencies such as clients, clocks and sleep.
  • Mock boundaries, not your own logic; assert behaviour, and wrap third-party APIs in adapters you own.
