6.3 Generators and yield

How a for loop really works (iterables, iterators, next and StopIteration), generator functions that pause at yield, generator expressions, yield from, cleanup with finally, and the traps: one-shot iteration, delayed errors and closed files. Applied to streaming files, JSONL, batches and LLM token streams.

1How a for loop really works

Every for loop in Python runs the same small protocol. An iterable is anything you can loop over: a list, a string, a dict, a file, a range. When the loop starts, Python calls iter(iterable), which returns an iterator: an object that remembers where it is. Then, for every round, Python calls next(iterator) and binds the result to the loop variable. When the iterator has nothing left, next raises StopIteration, and the for loop catches it and ends quietly. You can run the protocol by hand:

protocol.py
words = ["refund", "policy"]
it = iter(words)
print(next(it), next(it))
try:
    next(it)
except StopIteration:
    print("StopIteration: the loop would end here")
print(next(iter(words)), next(it, "default"))
Output
refund policy
StopIteration: the loop would end here
refund default

next(it, default) returns the default instead of raising, which is the convenient form when "no more items" is a normal case. The important distinction is iterable versus iterator. A list is an iterable but not an iterator: each iter(list) gives a fresh iterator starting at the beginning, so you can loop over a list as many times as you like. An iterator is one-shot: it only moves forward, and once it is exhausted it stays empty. Calling iter() on an iterator returns the iterator itself, which is why looping over it a second time produces nothing.

one_shot.py
nums = [1, 2, 3]
print(sum(nums), sum(nums))          # a list can be walked again
it = iter(nums)
print(sum(it), sum(it))              # an iterator only once
print(iter(it) is it, iter(nums) is iter(nums))
import io
f = io.StringIO("line 1\nline 2\n")
print([line.strip() for line in f], [line for line in f])   # files are iterators too
Output
6 6
6 0
True False
['line 1', 'line 2'] []

Files are iterators over their lines, which is why reading a file twice in a row returns nothing the second time (you would need f.seek(0)). zip, map, filter, enumerate, reversed, dict views' iterators and everything in itertools (6.4) are iterators as well. This one-shot behaviour is the source of a whole family of bugs (problem 3).

2Generator functions: yield pauses a function

A generator function is a normal def with at least one yield in its body. The yield changes what calling the function means. Calling it does not run the body; it immediately returns a generator object, which is an iterator. The body runs only when someone calls next on that object: it runs from the top until the first yield, hands that value to the caller, and pauses, keeping all of its local variables and its position. The next next resumes right after the yield and runs to the following one. When the body finishes (falls off the end or hits return), the generator raises StopIteration, and a for loop ends.

pause_resume.py
def countdown(n):
    print(f"  start at {n}")
    while n > 0:
        yield n
        print(f"  resumed after yielding {n}")
        n -= 1
    print("  done")

g = countdown(2)
print("created", type(g).__name__)
print("got", next(g))
print("got", next(g))
print("got", next(g, "nothing left"))
Output
created generator
  start at 2
got 2
  resumed after yielding 2
got 1
  resumed after yielding 1
  done
got nothing left

Follow the printed lines: "created" appears before "start", because creating the generator runs nothing. Each next runs the body only as far as the next yield. The local variable n survives between calls, which is what lets a generator produce a sequence without building it: it computes each value when asked, from the state it kept. That is called lazy evaluation. A generator that never finishes is fine, as long as the caller stops asking.

infinite.py
def ids(prefix):
    n = 0
    while True:                      # infinite, and that is fine
        n += 1
        yield f"{prefix}-{n:04d}"

gen = ids("TKT")
print([next(gen) for _ in range(3)])
for ticket in gen:
    if ticket.endswith("5"):
        break
print(ticket, next(gen))
Output
['TKT-0001', 'TKT-0002', 'TKT-0003']
TKT-0005 TKT-0006

The for loop picked up where the comprehension left off, because both used the same generator: its state lives in the object, not in the loop. A return value inside a generator ends it; the value is attached to the StopIteration (e.value), which yield from uses (below) but a for loop ignores.

3Generator expressions

A generator expression is the lazy version of a list comprehension: the same syntax with parentheses, (expr for x in xs if cond). It returns a generator object at once, without computing anything; each value is computed when it is requested. When a generator expression is the only argument of a function, the extra parentheses can be dropped: sum(x * x for x in xs).

genexp_memory.py
import sys

squares_list = [x * x for x in range(1_000_000)]
squares_gen = (x * x for x in range(1_000_000))
print(f"list: {sys.getsizeof(squares_list) / 1_000_000:.1f} MB, generator: {sys.getsizeof(squares_gen)} bytes")
print(sum(squares_gen), sum(squares_gen))      # the second sum finds it exhausted
print(max(len(w) for w in "lazy evaluation saves memory".split()))
Output
list: 4.2 MB, generator: 104 bytes
333332833333500000 0
10

The list holds a million references: about 4 MB for the list object alone on this page's 32-bit WebAssembly Python, and about 8 MB on a normal 64-bit machine, where each reference takes 8 bytes, not counting the integer objects themselves. The generator is a small fixed-size object whatever the length. That is why the generator form is the default for anything consumed once: sum, min, max, any, all, sorted, "".join, dict(...), set(...), or a for loop. It is also one-shot, as the second sum shows. Note that a generator is not automatically faster; for small data the list comprehension is often slightly quicker. The wins are memory, early exit (6.1) and being able to start working before all the data exists.

One detail of timing matters. In a generator expression, the first for's iterable is evaluated immediately, when the expression is created; everything else (conditions, the expression, inner loops) is evaluated later, when values are requested. So rebinding the source name afterwards does not affect the generator, but changing a variable used in the expression does (problem 12).

genexp_binding.py
xs = [1, 2, 3]
g = (x * 10 for x in xs)
xs = [7]                        # the generator already holds the old list
print(list(g))
factor = 2
g = (x * factor for x in range(3))
factor = 100                    # read later, when values are produced
print(list(g))
Output
[10, 20, 30]
[0, 100, 200]

4yield from, and cleanup with finally

yield from iterable yields every value of another iterable, one by one, as if you had written for v in iterable: yield v. Its main use is delegating to another generator, especially in recursion: a function that walks a tree yields the current node and then yield from the walk of each child. When the inner iterable is a generator that returns a value, that value becomes the result of the yield from expression.

yield_from.py
def walk(node, depth=0):
    yield depth, node["title"]
    for child in node.get("children", []):
        yield from walk(child, depth + 1)

doc = {"title": "Policy", "children": [
    {"title": "Refunds", "children": [{"title": "EU"}, {"title": "US"}]},
    {"title": "Contact"}]}
print(["  " * d + t for d, t in walk(doc)])

def inner():
    yield "a"
    return "inner finished"

def outer():
    result = yield from inner()
    yield result
print(list(outer()))
Output
['Policy', '  Refunds', '    EU', '    US', '  Contact']
['a', 'inner finished']

A generator can hold resources, such as an open file or a network connection, while it is paused. If the caller stops early (a break, an exception, or simply dropping the generator), the generator is closed: Python raises GeneratorExit inside it at the paused yield, so its finally blocks and with blocks run and release the resource. g.close() does this explicitly; otherwise it happens when the generator is garbage-collected, which in CPython is usually immediately after the last reference goes away.

cleanup.py
def stream_lines(lines):
    print("  open")
    try:
        for line in lines:
            yield line
    finally:
        print("  closed")

for line in stream_lines(["a", "b", "c"]):
    print(line)
    if line == "b":
        break
print("after the loop")
Output
  open
a
b
  closed
after the loop

Generators can also receive values with g.send(value), which makes yield an expression that returns what was sent. That is how coroutines worked before async and await; you will meet the modern form in the async module, and you rarely need send in everyday code.

5The traps: one-shot, delayed errors and closed files

Generators remove a lot of memory pressure, but they move when code runs, which creates three classic bugs.

One-shot consumption. A function that receives an iterable and loops over it twice (say, once for the mean and once for the maximum) works with a list and silently breaks with a generator: the second pass sees nothing. Either take one pass that computes everything, or turn the input into a list once at the start, items = list(items), when you know it fits in memory (problem 3).

Delayed errors. The body of a generator function, including argument checks at the top, runs only on the first next. So batched(items, 0) does not raise where it is called; it raises later, wherever the generator is first consumed, which can be far away and confusing. The fix is to split the function: a normal function validates the arguments and then returns the inner generator (problem 6).

delayed_errors.py
def lazy_check(n):
    if n < 1:
        raise ValueError("n must be at least 1")
    yield from range(n)

g = lazy_check(0)
print("no error yet:", type(g).__name__)
try:
    next(g)
except ValueError as e:
    print("raised only now:", e)

def eager_check(n):
    if n < 1:
        raise ValueError("n must be at least 1")
    return (i for i in range(n))     # a normal function returning a generator
try:
    eager_check(0)
except ValueError as e:
    print("raised at the call:", e)
Output
no error yet: generator
raised only now: n must be at least 1
raised at the call: n must be at least 1

Closed resources. with open(path) as f: return (json.loads(l) for l in f) returns a generator, and then the with block ends and closes the file before anyone has read a line; iterating raises ValueError: I/O operation on closed file. Put the with inside a generator function and yield from within it, so the file stays open exactly as long as the generator is being consumed, and closes when it finishes or is closed (problem 14).

Two smaller points. A generator has no len() and cannot be indexed, because its values do not exist yet; use sum(1 for _ in g) to count (which consumes it) or keep a counter. And for debugging, list(g) shows what a generator produces, at the price of consuming it.

6Generators in data and GenAI code

The common thread of everything above is streaming: process data as it arrives, one piece at a time, with memory that does not grow with the input. Three patterns cover most real uses. Reading large files: a generator that opens the file, yields one parsed record per line, and skips or reports bad lines, so a 50 GB JSON Lines file needs only one line of memory at a time (problem 2). Pipelines: each step is a generator that takes an iterable and yields transformed items, so chaining steps builds a lazy pipeline that does no work until the end is consumed (6.4). Streaming model output: LLM APIs can send a reply as a stream of small text pieces, and a generator is the natural way to represent it.

llm_stream.py
import time

def fake_llm_stream(reply, delay=0.0):
    # stands in for an SDK's streaming iterator: one small piece at a time
    for piece in reply.split(" "):
        time.sleep(delay)
        yield piece + " "

def with_progress(stream):
    text = ""
    for delta in stream:
        text += delta
        yield text.rstrip()        # what a UI would show after each piece

for shown in with_progress(fake_llm_stream("Refunds take five days.")):
    print(repr(shown))
Output
'Refunds'
'Refunds take'
'Refunds take five'
'Refunds take five days.'

Real SDKs work the same way: with stream=True, the client returns an iterator of events, and your code loops over it, printing or forwarding each delta as it arrives, so the user sees the first words within a fraction of a second instead of waiting for the whole reply. Web frameworks accept generators directly for this: FastAPI's StreamingResponse takes a generator and sends each yielded chunk to the browser as soon as it is produced. And if the user closes the page, the framework closes the generator, so its finally block is the place to stop the upstream request and log usage. In ML training code, PyTorch's IterableDataset is a class whose __iter__ is a generator that yields training examples, which is how datasets larger than memory are fed to a model.

3. Statistics that break on a generator

summary(scores) returns (mean, maximum). It works on lists but fails with a ValueError when given a generator of scores. Fix it so it works with any iterable, in a single pass over the data.

TestsThe 3 checks Run tests uses
assert summary([2, 9, 4]) == (5.0, 9)
assert summary(s for s in [2, 9, 4]) == (5.0, 9)
assert summary(iter([2])) == (2.0, 2)
HintOpen a hint

The for loop exhausts the generator, so max(scores) sees an empty iterator. Track the maximum inside the same loop.

SolutionShow the solution and why
solution.py
def summary(scores):
    total, count, best = 0, 0, None
    for s in scores:
        total += s
        count += 1
        if best is None or s > best:
            best = s
    return total / count, best

The loop consumed every value, so max received an exhausted iterator and raised ValueError: max() iterable argument is empty. With a list, a second pass works, which is why the bug hides in tests that use lists. Computing everything in one pass works for any iterable, including a file or a stream too large to keep. The alternative, scores = list(scores) at the top, is fine when the data fits in memory, and is the usual choice when you need several passes.

def accumulate(deltas):
    text = ""
    for delta in deltas:
        if delta:

6. A batch generator that fails late

batched(items, n) yields lists of n items. Called with n=0, it should raise ValueError immediately, at the call, not later when the batches are consumed in a different part of the program. Fix it.

TestsThe 2 checks Run tests uses
assert list(batched(range(5), 2)) == [[0, 1], [2, 3], [4]]

    batched([1, 2], 0)
    assert False, "should raise at the call"
except ValueError:
    pass
assert list(batched([], 3)) == []
HintOpen a hint

A generator function's body, including the check, only runs on the first next. Validate in a normal function, then return an inner generator.

SolutionShow the solution and why
solution.py
def batched(items, n):
    if n < 1:
        raise ValueError("n must be at least 1")
    return _batches(items, n)


def _batches(items, n):
    batch = []
    for item in items:
        batch.append(item)
        if len(batch) == n:
            yield batch
            batch = []
    if batch:
        yield batch

Because the original body contains yield, the whole function is a generator function: calling it only creates the generator, and the if n < 1 line runs on the first next, possibly much later, in code that has nothing to do with the mistake. Splitting it in two makes batched an ordinary function that validates eagerly and returns the generator from _batches. The callers see no other difference. Libraries use this pattern whenever arguments of a lazy function need checking.

Write a generator chunks_of(iterable, n) yielding tuples of up to n items. (n is at least 1; you do not need to validate it.)

TestsThe 4 checks Run tests uses
assert list(chunks_of("abcde", 2)) == [("a", "b"), ("c", "d"), ("e",)]

    while True:
        i += 1

Hint 1Open a hint

You cannot slice a generator. Get one iterator with it = iter(iterable), and fill each batch with next(it, sentinel) until it is full or the sentinel appears.

Hint 2Open a hint

A unique sentinel = object() tells "no more items" apart from items like None.

SolutionShow the solution and why
solution.py
def chunks_of(iterable, n):
    it = iter(iterable)
    done = object()
    while True:
        batch = []
        for _ in range(n):
            item = next(it, done)
            if item is done:
                break
            batch.append(item)
        if batch:
            yield tuple(batch)
        if len(batch) < n:
            return

Slicing (items[i:i + n]) only works on sequences, so a general version must pull items with next. Calling iter once is essential: the same iterator is shared by all batches, so each batch continues where the last stopped. A private sentinel object is the safe "no more" marker, since any real value, including None, could appear in the data. Pulling exactly n items per batch and stopping as soon as one batch is short means an infinite source is fine and no item is read early, which the pulled test checks. This is what itertools.batched (Python 3.12+) does, built on islice (6.4); sending embeddings in batches from a stream is the typical use.

10. A streaming SSE parser as a generator

Turn the streaming reader from 5.P into a generator. deltas(chunks) takes an iterable of bytes chunks of server-sent events (lines like data: {"delta": "Hi"}, possibly ending in \r\n, split anywhere, even inside a character) and yields each delta as soon as its line is complete. It stops at data: [DONE] and ignores other lines.

TestsThe 3 checks Run tests uses
body = 'data: {"delta": "Caf\u00e9 "}\r\n: keep-alive\r\ndata: {"delta": "ok"}\r\ndata: [DONE]\r\ndata: {"delta": "x"}\r\n'

Hint 1Open a hint

Same buffer logic as 5.P: append each chunk to a bytes buffer, split off complete lines at b"\n", decode each line, strip \r.

Hint 2Open a hint

yield each delta instead of appending it to a list, and return at [DONE].

SolutionShow the solution and why
solution.py
import json

def deltas(chunks):
    buffer = b""
    for chunk in chunks:
        buffer += chunk
        while b"\n" in buffer:
            raw_line, buffer = buffer.split(b"\n", 1)
            line = raw_line.decode("utf-8").rstrip("\r")
            if not line.startswith("data: "):
                continue
            payload = line[len("data: "):]
            if payload == "[DONE]":
                return
            yield json.loads(payload)["delta"]

The parsing logic is the same as in 5.P; the change is that results are yielded as soon as each line is complete, instead of collected and returned at the end. The second test checks the point of the change: the first delta is available after only a few network chunks, so a UI can show the first words while the rest is still arriving. return at [DONE] ends the generator, and since the caller drives the loop, it can also stop early with break, which closes the generator. Lines starting with : are SSE comments, commonly used as keep-alives, and are skipped like any other non-data line.

solution.py
def clean_rows(rows):
    for row in rows:
        if not row.strip() or row.startswith("#"):
            continue
        parts = [p.strip() for p in row.split(",")]
        if len(parts) != 3:
            continue
        yield {"id": int(parts[0]), "name": parts[1], "score": float(parts[2])}

The change is mechanical: every out.append(x) becomes yield x, and the result list disappears. The behaviour changes in the useful way: memory no longer grows with the input, the first row is available immediately, and the function works on an open file or another generator of any size. Callers that need a list write list(clean_rows(rows)). The trade-off is one-shot iteration: a caller that loops twice must store the result first.

13. Walk a document outline

Chunkers for structured documents keep each section's heading path, such as Policy > Refunds > EU, as metadata. Write a generator section_paths(node, sep=" > ") that walks a tree of {"title": ..., "children": [...]} nodes (children may be missing) and yields the path of every node, parents before children, using yield from for the recursion.

TestsThe 4 checks Run tests uses

    {"title": "Refunds", "children": [{"title": "EU"}, {"title": "US", "children": []}]},
    {"title": "Contact"}]}

HintOpen a hint

Use a helper with a prefix parameter: yield prefix + title, then yield from the helper on each child with the new path as prefix.

SolutionShow the solution and why
solution.py
def section_paths(node, sep=" > "):
    yield from _paths(node, sep, "")


def _paths(node, sep, prefix):
    path = f"{prefix}{sep}{node['title']}" if prefix else node["title"]
    yield path
    for child in node.get("children", []):
        yield from _paths(child, sep, path)

Each call yields its own path and then delegates to the calls for its children with yield from, which passes their values straight through to the caller. Passing the path down as a parameter means no node needs to know about its parents. The walk is lazy: next(...) gets the first path without visiting the rest of the tree. Depth is limited by the recursion limit (about 1,000 by default), which is plenty for document outlines; for unbounded depth, an explicit stack in a loop avoids recursion. LlamaIndex and LangChain's Markdown header splitters attach exactly this kind of heading path to each chunk so retrieval results can show where they came from.

This loads training records from a JSON Lines file and takes the first n. It crashes with ValueError: I/O operation on closed file. Hint 1Open a hint

return (generator) inside with returns, and the with closes the file before the generator runs. Make load_records itself a generator: yield inside the with.

Hint 2Open a hint

Use enumerate(f, start=1) for line numbers and try / except json.JSONDecodeError around json.loads.

Hint 3Open a hint

SolutionShow the solution and why
solution.py
import json


def load_records(path, errors):
    with open(path, encoding="utf-8") as f:
        for lineno, line in enumerate(f, start=1):
            if not line.strip():
                continue
            try:
                yield json.loads(line)
            except json.JSONDecodeError:
                errors.append(lineno)


def first_n(records, n):
    out = []
    for i, record in enumerate(records):
        if i == n:
            break
        out.append(record)
    return out

Bug one is the classic generator-and-resource trap: the generator expression is created, return leaves the with block, and the file closes before a single line is read. With yield inside the with, the function itself is the generator, so the file stays open while records are being pulled and closes when the generator finishes or is closed (when first_n breaks out early and drops it). Bug two is an off-by-one: i > n allows indices 0..n, which is n + 1 records. Bug three: one corrupt line raised JSONDecodeError and killed the run; catching it per line, recording the line number and continuing is the standard behaviour for large training files, where a few bad lines are normal. Note that the error for line 3 is only recorded because the loader reached line 3; with a lazy loader, errors after the last record you consume are never seen.

15. A shuffle buffer for streams

Training on a stream that is too large to shuffle in memory uses a shuffle buffer, as in tf.data: fill a buffer with the first size items; then, for every new item, pick a random position in the buffer, yield the item there and put the new item in its place; at the end, yield the remaining buffer in random order. Write a generator shuffled(iterable, size, seed) using random.Random(seed).

TestsThe 6 checks Run tests uses
data = list(range(100))
out = list(shuffled(iter(data), size=10, seed=0))
assert sorted(out) == data and out != data
assert all(v <= j + 9 for j, v in enumerate(out))
assert list(shuffled(data, 1, seed=3)) == data
assert list(shuffled(data, 10, seed=7)) == list(shuffled(data, 10, seed=7))
assert list(shuffled([], 5, seed=0)) == []
assert sorted(shuffled("abc", 10, seed=1)) == ["a", "b", "c"]
Hint 1Open a hint

rng = random.Random(seed) gives a private, reproducible random generator. rng.randrange(len(buffer)) picks a position.

Hint 2Open a hint

While the buffer is not full, just append. After that, swap: out, buffer[i] = buffer[i], item, then yield out. At the end, rng.shuffle(buffer) and yield from buffer.

SolutionShow the solution and why
solution.py
import random

def shuffled(iterable, size, seed):
    rng = random.Random(seed)
    buffer = []
    for item in iterable:
        if len(buffer) < size:
            buffer.append(item)
            continue
        i = rng.randrange(size)
        out, buffer[i] = buffer[i], item
        yield out
    rng.shuffle(buffer)
    yield from buffer

The buffer bounds memory at size items whatever the stream length, and each output is drawn from a window of the stream, which is what the v <= j + 9 test checks: item v can only be output once it has entered the buffer, so it never appears more than size - 1 positions earlier than its original place. That also shows the limit of the technique: a small buffer gives a locally shuffled stream, so data sorted by label stays mostly sorted; real pipelines shuffle the file order too, or use a buffer much larger than the runs of similar items. A private random.Random(seed) makes the order reproducible without touching the global random state, which matters for repeatable experiments. With size=1, each item is swapped straight out, so the order is unchanged.

16. Closing, finally and return values

def worker():
    try:
        yield "step 1"
        yield "step 2"
    finally:
        print("cleanup")

g = worker()
print(next(g))
g.close()
print("closed", next(g, "nothing"))

def inner():
    yield 1
    return "inner result"

def outer():
    r = yield from inner()
    yield r.upper()

print(list(outer()))
g2 = inner()
print(next(g2))
try:
    next(g2)
except StopIteration as e:
    print("value", e.value)
Hint 1Open a hint

close() raises GeneratorExit at the paused yield, so finally runs. A closed generator is exhausted.

Hint 2Open a hint

A generator's return value travels on the StopIteration it raises, as e.value.

SolutionShow the solution and why

close runs the finally block at once ("cleanup"), and a closed generator behaves as exhausted, so next(g, "nothing") returns the default. In outer, yield from passes the 1 through and then receives the inner return value, which is yielded upper-cased. A for loop discards that value, which is why yield from is the normal way to receive it.

17. What is the difference between an iterable, an iterator and a generator?

SolutionModel answer

An iterable is any object you can loop over; it has __iter__, which returns an iterator. Lists, dicts, strings, files and ranges are iterables. An iterator is the object that does the walking: it has __next__, which returns the next value or raises StopIteration, and __iter__ returning itself. Iterators are one-shot and stateful; iterables such as lists can produce a fresh iterator every time. A generator is a convenient way to write an iterator: a function with yield (or a generator expression) whose local state is kept between next calls, so you do not have to write a class with __next__ by hand. Every generator is an iterator; not every iterator is a generator (zip, map and file objects are iterators implemented in C).

Interview

18. When would you use a generator instead of returning a list, and what do you give up?

SolutionModel answer

Use a generator when the data is large or unbounded (files, database cursors, streams, infinite sequences), when the consumer may stop early (searching for the first match, taking the first N), when you want to start processing before all data exists (streaming model output to a user), or when you are building a pipeline of steps. You gain constant memory and lower latency to the first item. You give up random access and len, the ability to iterate twice (a generator is one-shot), and easy debugging (printing the generator shows nothing useful). Errors also move: they happen when values are consumed, not when the function is called. If the result is small and used several times, a list is simpler.

Interview

19. How would you stream an LLM reply from the model API through your backend to a browser?

SolutionModel answer

Call the model with streaming enabled, which gives an iterator (or async iterator) of events. Wrap it in a generator in the backend that extracts each text delta and yields it, optionally formatted as server-sent events (data: ...\n\n), and pass that generator to the framework's streaming response (FastAPI's StreamingResponse, ideally with an async generator so one slow client does not block a worker). The browser reads the stream with EventSource or fetch and appends text as it arrives. Details that matter in production: collect the full text and usage counts in the generator for logging, in a finally block so they are recorded even if the stream ends early; handle client disconnects, where the framework closes the generator and you should cancel the upstream request so you stop paying for tokens; send an error event if the model fails mid-stream, because the HTTP status code was already sent; make sure no proxy buffers the response; and run moderation or output checks either on the stream in chunks or accept that some text was shown before the check.

Recap

  • A for loop calls iter() once and next() until StopIteration. Lists can be walked many times; iterators, generators, zip and files only once.
  • A function with yield returns a generator; its body runs only on next, pauses at each yield and keeps its locals.
  • (expr for x in xs) is lazy and tiny in memory; its first iterable is captured at creation, the rest is evaluated on demand.
  • yield from delegates and receives the inner return value; close() and early break run the generator's finally blocks.
  • Traps: second passes see nothing, argument checks run late (validate in a wrapper), and a generator returned from inside with reads a closed file.
