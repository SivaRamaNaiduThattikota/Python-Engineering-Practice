11.1 Type hints

Type hints describe what a function accepts and returns. What they are and are not (Python does not enforce them), the syntax for variables, parameters, returns and built-in generics, unions and None, narrowing, accepting abstract types and returning concrete ones, what a type checker such as mypy or pyright reports, and how libraries read hints at run time. Applied to text utilities, tool schemas, settings and validation.

18 problems4 easy · 9 medium · 5 hard

1What type hints are, and what they are not

A type hint (or annotation) states the type a value is expected to have: def chunk(text: str, size: int) -> list[str]: says that text is a string, size an integer, and that the function returns a list of strings. Hints serve three audiences. People read them as precise documentation of the interface. Editors use them for completion and inline errors. Type checkers, such as mypy and pyright, analyse the whole program without running it and report calls that pass the wrong type, return values that do not match, attributes that do not exist, and possible None values used carelessly.

What hints are not is a run-time check. Python stores them (in func.__annotations__) and otherwise ignores them: calling the function with the wrong type runs exactly as it would without hints, and fails, or worse, does not fail, wherever the wrong value is first used. Checking at run time is the job of libraries that read the hints, such as Pydantic (11.4), FastAPI and the tool-schema generators of 8.4.

not_enforced.py
import typing

def chunk(text: str, size: int = 200) -> list[str]:
    return [text[i:i + size] for i in range(0, len(text), size)]

print(chunk("abcdefg", 3))
print(chunk(["a", "b", "c", "d"], 2))         # the wrong type: Python does not stop it
print(chunk.__annotations__)
print(typing.get_type_hints(chunk))
Output
['abc', 'def', 'g']
[['a', 'b'], ['c', 'd']]
{'text': <class 'str'>, 'size': <class 'int'>, 'return': list[str]}
{'text': <class 'str'>, 'size': <class 'int'>, 'return': list[str]}

The second call passed a list where a string was expected and quietly returned a list of lists: the hint documented the mistake, but only a type checker (before running) or validation code (while running) would have caught it. In Python 3.14, annotations are also evaluated lazily (PEP 649): the expressions are computed only when something asks for them, so a hint can refer to a class defined later in the file without quotes. typing.get_type_hints(func) is still the reliable way to get them as real types (8.4).

2The syntax: variables, parameters, returns and containers

Parameters are annotated with a colon, name: type, with the default after it, size: int = 200. The return type follows an arrow before the colon of the def, -> list[str]; a function that returns nothing is annotated -> None. Variables can be annotated too, count: int = 0, which is mostly useful for attributes in classes (11.3) and for empty containers whose type cannot be guessed: seen: set[str] = set().

Containers take their element types in square brackets, using the built-in names directly (Python 3.9+): list[str] (a list of strings), dict[str, float] (keys and values), set[int], tuple[str, int] (a pair: a string then an int, fixed length) and tuple[int, ...] (any number of ints). Nesting works as you would expect: dict[str, list[tuple[int, float]]]. For readability, give complex types a name, a type alias: type Vector = list[float] (Python 3.12+) or simply Vector = list[float].

syntax.py
import typing

type Vector = list[float]
Scores = dict[str, float]

def top_k(scores: Scores, k: int = 3) -> list[tuple[str, float]]:
    return sorted(scores.items(), key=lambda kv: kv[1], reverse=True)[:k]

def mean_vector(vectors: list[Vector]) -> Vector:
    n = len(vectors)
    return [sum(col) / n for col in zip(*vectors)]

def log_event(name: str, **fields: str | int) -> None:
    print("event", name, fields)

print(top_k({"faq": 0.9, "terms": 0.4, "blog": 0.7}, 2))
print(mean_vector([[1.0, 2.0], [3.0, 4.0]]))
log_event("search", query="refund", k=3)
print(typing.get_type_hints(top_k)["return"], typing.get_type_hints(log_event))
Output
[('faq', 0.9), ('blog', 0.7)]
[2.0, 3.0]

list[tuple[str, float]] {'name': <class 'str'>, 'fields': str | int, 'return': <class 'NoneType'>}

**fields: str | int annotates the type of each keyword value, not of the dict, and *args: int likewise annotates each positional extra. Hints describe what the code accepts; they should be true. A hint that claims -> list[str] while one branch returns None is worse than no hint, because it tells readers and tools something false (problem 3).

3Unions, None and narrowing

A value that can be one of several types has a union type, written A | B (Python 3.10+; older code writes Union[A, B]). The most common union is "a value or nothing": str | None, which older code writes as Optional[str]. The name Optional misleads: it does not mean "an optional argument" (that is a default value), it means "may be None". def find(q: str) -> Doc | None warns every caller that the result must be checked before use.

Type checkers follow your code's checks, which is called narrowing. After if doc is None: return, the checker knows doc is a Doc in the rest of the function; after if isinstance(x, str):, it treats x as a string inside the branch. That is exactly how you should write code with unions: check, then use. Using a str | None value without a check is the single most common error type checkers find in real code, because it is the AttributeError: 'NoneType' object has no attribute ... of production.

unions.py
def find_doc(docs: dict[str, str], doc_id: str) -> str | None:
    return docs.get(doc_id)

def title_of(docs: dict[str, str], doc_id: str) -> str:
    text = find_doc(docs, doc_id)
    if text is None:                      # narrowing: after this, text is a str
        return "(missing)"
    return text.split("\n", 1)[0].strip()

def describe(value: int | str | list[str]) -> str:
    if isinstance(value, int):
        return f"number {value}"
    if isinstance(value, str):
        return f"text of {len(value)} chars"
    return f"list of {len(value)} items"

docs = {"faq": "Refunds\nTake 5 days."}
print(title_of(docs, "faq"), "|", title_of(docs, "nope"))
print([describe(v) for v in [3, "abc", ["a", "b"]]])
print(isinstance(3, int | str), isinstance(None, str | None))
Output
Refunds | (missing)
['number 3', 'text of 3 chars', 'list of 2 items']
True True

Deciding between returning None and raising is a design choice (7.3): return X | None when "not found" is a normal outcome callers will handle, raise when it is an error. Since Python 3.10, isinstance accepts a union directly, as the last line shows, but not a parameterised generic: isinstance(x, list[str]) raises TypeError, because checking every element is not what isinstance does (problem 4).

4Accept general types, return specific ones

For parameters, annotate with the most general type your code actually needs. A function that only loops over its input needs an Iterable[str], so it accepts lists, tuples, sets, generators and files; one that indexes and takes len needs a Sequence[str]; one that only reads keys needs a Mapping[str, float], which also accepts read-only mappings. These come from collections.abc (9.5). Annotating list[str] instead makes the type checker reject a perfectly good tuple or generator, the static twin of the isinstance(x, list) mistake of 9.5 (problem 6). For return values, be specific: return list[str], not Iterable[str], so callers know they can index and append.

abstract_types.py
from collections.abc import Iterable, Mapping, Sequence

def count_tokens(texts: Iterable[str]) -> int:
    return sum(len(t.split()) for t in texts)

def last(items: Sequence[str]) -> str:
    return items[-1]

def total_cost(prices: Mapping[str, float], usage: Mapping[str, int]) -> float:
    return round(sum(prices[m] * n for m, n in usage.items()), 4)

print(count_tokens(["a b", "c"]), count_tokens(("x",)), count_tokens(t for t in ["one two"]))
print(last(("a", "b")), last("xyz"), total_cost({"small": 0.002}, {"small": 1500}))
Output
3 1 2
b z 3.0

Two special types complete the picture. Any switches type checking off for a value: anything can be assigned to it and anything can be done with it, which is how untyped code and JSON-like data enter a typed program; use it sparingly, at boundaries. object is the opposite in spirit: it accepts any value too, but the checker then lets you do almost nothing with it until you narrow it, which makes it the honest type for "I accept anything and will check what it is".

5What a type checker reports

A type checker reads your code and the hints, infers types for everything it can (local variables, expressions, return values), and reports places where they cannot fit together. You run it like a linter, mypy src/ or pyright, locally and in CI; nothing changes at run time. Typical reports look like this:

CodeWhat the checker says
chunk(["a", "b"], 2)Argument 1 has incompatible type "list[str]"; expected "str"
title = find_doc(docs, "x").upper()Item "None" of "str | None" has no attribute "upper"
def f() -> int: return "3"Incompatible return value type (got "str", expected "int")

Each of these is a bug that would otherwise surface at run time, often only on a rare path (the missing document, the failed request). Type checking is gradual: unannotated functions are treated leniently, so you can add hints module by module, starting with the code that matters most, and tighten settings (mypy's --strict) as coverage grows. Third-party libraries ship their own hints (py.typed) or have stub packages (pandas-stubs), and NumPy, pandas, Pydantic and the LLM SDKs are well typed, which makes editors and checkers useful on ML code too. This page's in-browser Python cannot run mypy, so the problems here check hints the way libraries do: by reading them at run time.

6Reading hints at run time

Because hints are stored as data, code can read them, and a large part of the modern Python ecosystem does: dataclasses builds __init__ from annotated class attributes (11.3); Pydantic validates and converts data according to field types (11.4); FastAPI decides which parameters are path, query or body values from their annotations; Typer builds command-line interfaces; agent frameworks generate tool schemas (8.4). The tools are typing.get_type_hints(obj) for the evaluated hints, and typing.get_origin and typing.get_args to take generic types apart: list[int] has origin list and arguments (int,); int | None has the union type as origin (typing.Union, which since Python 3.14 is the same object as types.UnionType, so either name works in comparisons) and arguments (int, NoneType).

runtime_hints.py
import types, typing

def search(query: str, k: int = 5, tags: list[str] | None = None, weights: dict[str, float] | None = None) -> list[str]:
    return []

for name, hint in typing.get_type_hints(search).items():
    origin, args = typing.get_origin(hint), typing.get_args(hint)
    print(f"{name:8} {str(hint):26} origin={getattr(origin, '__name__', origin)} args={args}")
print(typing.get_origin(int | None) is types.UnionType, type(None) in typing.get_args(int | None))
Output

Walking hints like this is how a small runtime validator works (problem 7): plain classes are checked with isinstance, and generic types are checked by recursing into their arguments. Real validators also convert values (the string "5" to the int 5) and report every problem at once, which is exactly what Pydantic adds.

solution.py
def split_words(text: str, max_words: int = 50, overlap: int = 0) -> list[str]:
    if not 0 <= overlap < max_words:
        raise ValueError("need 0 <= overlap < max_words")
    words = text.split()
    step = max_words - overlap
    chunks = []
    for start in range(0, len(words), step):
        chunks.append(" ".join(words[start:start + max_words]))
        if start + max_words >= len(words):
            break
    return chunks

The hints state the contract in one line: give me a string and two ints, get back a list of strings. A type checker now flags split_words(doc) where doc might be None, or a caller that treats the result as a single string. The break stops once a chunk reaches the end, so with overlap the last window is not repeated as a smaller duplicate. get_type_hints returns real types, so the test (and tools such as tool-schema generators) can compare them directly.

from collections.abc import Iterable

def first_text(items: Iterable[object]) -> str | None:
    for item in items:
        if isinstance(item, str) and item.strip():
            return item.strip()
    return None

Iterable[object] is the most honest parameter type: the function accepts any iterable of anything, and because the elements are object, a type checker insists on the isinstance check before .strip() is called, which is exactly the check that protects the code from None and numbers at run time. After isinstance(item, str), the checker narrows item to str. The return type tells callers they must handle None. This kind of helper is common when cleaning model outputs or optional fields from JSON.

solution.py
from collections.abc import Iterable, Mapping

def average_length(texts: Iterable[str]) -> float:
    texts = list(texts)
    return sum(len(t) for t in texts) / len(texts) if texts else 0.0

def lookup_all(keys: Iterable[str], table: Mapping[str, str]) -> list[str]:
    return [table[k] for k in keys if k in table]

A parameter hint is a promise about what the function needs, and list[str] over-promised: it demanded a list when any iterable works, so a type checker would reject correct calls with generators or tuples, pushing callers to write pointless list(...) conversions. Mapping is the read-only interface of a dict, so it accepts dicts, MappingProxyType views and custom mappings (9.5). The return types stay concrete (float, list[str]) so callers can rely on everything a list offers. "Accept the most general, return the most specific" is the rule.

solution.py
import types, typing

def matches(value, hint):
    if hint is typing.Any:
        return True
    if hint is None or hint is type(None):
        return value is None
    origin, args = typing.get_origin(hint), typing.get_args(hint)
    if origin in (types.UnionType, typing.Union):
        return any(matches(value, a) for a in args)
    if origin is None:
        if hint is float:
            return isinstance(value, (int, float)) and not isinstance(value, bool)
        if hint is int:
            return isinstance(value, int) and not isinstance(value, bool)
        return isinstance(value, hint)
    if origin is list:
        return isinstance(value, list) and all(matches(v, args[0]) for v in value)
    if origin is dict:
        return isinstance(value, dict) and all(matches(k, args[0]) and matches(v, args[1]) for k, v in value.items())
    if origin is tuple:
        if not isinstance(value, tuple):
            return False
        if len(args) == 2 and args[1] is Ellipsis:
            return all(matches(v, args[0]) for v in value)
        return len(value) == len(args) and all(matches(v, a) for v, a in zip(value, args))
    raise TypeError(f"unsupported hint: {hint!r}")

The function recurses through the structure of the hint, which is what every runtime validator does: plain classes are an isinstance check, unions succeed if any member matches, and containers check themselves and then each element against the inner type. The special cases follow the conventions of type checkers and JSON: bool is excluded from int (1.2) and int is accepted where float is expected. Checking every element is O(n), which is why isinstance(x, list[int]) refuses to do it, and why validation belongs at boundaries (API input, model output) rather than in every function. Pydantic implements this, much faster, in Rust, plus conversion and error reporting (11.4).

        return True
    if hint is None or hint is type(None):
        return value is None

    if origin is list:
        return isinstance(value, list) and all(matches(v, args[0]) for v in value)
    if origin is dict:
        return isinstance(value, dict) and all(matches(k, args[0]) and matches(v, args[1]) for k, v in value.items())
    raise TypeError(f"unsupported hint: {hint!r}")

def validated(func):
    hints = typing.get_type_hints(func)
    return_hint = hints.pop("return", inspect.Signature.empty)
    sig = inspect.signature(func)

    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        bound = sig.bind(*args, **kwargs)
        bound.apply_defaults()
        for name, value in bound.arguments.items():
            hint = hints.get(name)
            if hint is not None and not matches(value, hint):
                raise TypeError(f"{name} must be {hint}, got {type(value).__name__}")
        result = func(*args, **kwargs)
        if return_hint is not inspect.Signature.empty and not matches(result, return_hint):
            raise TypeError(f"return value must be {return_hint}, got {type(result).__name__}")
        return result
    return wrapper

This combines three earlier tools: a decorator (8.1), signature binding (8.4) and hint introspection. Binding with defaults applied means default values are validated too, and each argument is matched to its parameter however it was passed. Computing the hints and signature once keeps each call cheap. Checking the return value catches a function that violates its own contract (broken returns an int while promising str). Pydantic's @validate_call is the production version: it also converts compatible values ("2" to 2 when the mode allows), and collects all errors in one exception. Use such validation at boundaries, where untrusted data enters; inside the program, a static type checker gives the same safety at no run-time cost.

import functools, typing
from collections import Counter

def check_return(func):
    hint = typing.get_type_hints(func)["return"]
    origin, args = typing.get_origin(hint), typing.get_args(hint)

    @functools.wraps(func)
    def wrapper(*args_, **kwargs):
        result = func(*args_, **kwargs)
        ok = isinstance(result, origin or hint)
        if ok and origin is dict:

        if not ok:
            raise TypeError(f"{func.__name__} returned {type(result).__name__}, expected {hint}")
        return result
    return wrapper

Handle unions first: if None is among the args, blank/none/null gives None; otherwise coerce to the other member.

solution.py
import types, typing

TRUE, FALSE = {"true", "yes", "1"}, {"false", "no", "0"}

def coerce(raw, hint):
    origin, args = typing.get_origin(hint), typing.get_args(hint)
    if origin in (types.UnionType, typing.Union):
        if type(None) in args and raw.strip().lower() in ("", "none", "null"):
            return None
        others = [a for a in args if a is not type(None)]
        if len(others) != 1:
            raise TypeError(f"unsupported union: {hint!r}")
        return coerce(raw, others[0])
    if origin is list:
        items = [part.strip() for part in raw.split(",")] if raw.strip() else []
        try:
            return [coerce(item, args[0]) for item in items]
        except ValueError:
            raise ValueError(f"cannot convert {raw!r} to {hint}") from None
    if hint is str:
        return raw
    if hint is bool:
        text = raw.strip().lower()
        if text in TRUE:
            return True
        if text in FALSE:
            return False
        raise ValueError(f"cannot convert {raw!r} to {hint}")
    if hint in (int, float):
        try:
            return hint(raw.strip())
        except ValueError:
            raise ValueError(f"cannot convert {raw!r} to {hint}") from None
    raise TypeError(f"unsupported hint: {hint!r}")

def load_settings(cls_hints, env):
    return {name: coerce(env[name], hint) for name, hint in cls_hints.items() if name in env}

Strings are what the outside world gives you, and hints say what the program needs, so a converter driven by hints is the bridge: one table of field types replaces a hand-written parse per setting. Unions with None are resolved first, so an empty variable can mean "not set"; lists convert each item with the element type, recursively. bool needs an explicit vocabulary because bool("false") is True (8.P). Errors name both the bad value and the expected type, which is what a person fixing a configuration needs. Pydantic's settings models and Typer's CLI parsing implement this same conversion, driven by class annotations (11.4).

SolutionShow the solution and why
solution.py
import inspect, types, typing

JSON = {str: "string", int: "integer", float: "number", bool: "boolean"}


def _schema(hint):
    if typing.get_origin(hint) is list:
        return {"type": "array", "items": _schema(typing.get_args(hint)[0])}
    return {"type": JSON[hint]}


def tool_schema(func):
    hints = typing.get_type_hints(func)
    props, required = {}, []
    for name, param in inspect.signature(func).parameters.items():
        hint = hints[name]
        nullable = False
        if typing.get_origin(hint) in (types.UnionType, typing.Union):
            members = [a for a in typing.get_args(hint) if a is not type(None)]
            nullable = len(members) < len(typing.get_args(hint))
            if len(members) != 1:
                raise TypeError(f"{name}: only X | None unions are supported")
            hint = members[0]
        schema = _schema(hint)
        if nullable:
            schema["type"] = [schema["type"], "null"]
        props[name] = schema
        if param.default is inspect.Parameter.empty:
            required.append(name)
    return {"name": func.__name__, "parameters": {"type": "object", "properties": props, "required": required}}

Two bugs. A union such as str | None is not a key of the JSON dict, so the lookup raised KeyError; unions must be unwrapped first, keeping the non-None member for the schema and recording that null is allowed, which JSON Schema expresses as a list of types. And every parameter was appended to required, so the model was told it must always send k, lang and tags, even though they have defaults; required means "no default". Both mistakes change how an LLM calls the tool: missing nullability makes it invent values, wrong required lists make it fill parameters it should omit. Moving the per-type logic into _schema makes nested lists work too. Unsupported unions raise a clear error instead of producing a wrong schema.

A recursive fmt(hint): None/NoneType gives "None", Ellipsis gives "...", unions join members with " | ", generics are f"{origin.__name__}[{', '.join(...)}]".

Hint 2Open a hint

The keyword-only marker * is not part of the expected output; just list the parameters.

SolutionShow the solution and why
solution.py
import inspect, types, typing

def fmt(hint):
    if hint is None or hint is type(None):
        return "None"
    if hint is Ellipsis:
        return "..."
    origin, args = typing.get_origin(hint), typing.get_args(hint)
    if origin in (types.UnionType, typing.Union):
        return " | ".join(fmt(a) for a in args)
    if origin is not None:
        return f"{origin.__name__}[{', '.join(fmt(a) for a in args)}]"
    return getattr(hint, "__name__", repr(hint))

def describe(func):
    hints = typing.get_type_hints(func)
    parts = []
    for name, p in inspect.signature(func).parameters.items():
        prefix = {p.VAR_POSITIONAL: "*", p.VAR_KEYWORD: "**"}.get(p.kind, "")
        text = prefix + name
        if name in hints:
            text += f": {fmt(hints[name])}"
        if p.default is not p.empty:
            text += (" = " if name in hints else "=") + repr(p.default)
        parts.append(text)
    result = f"{func.__name__}({', '.join(parts)})"
    if "return" in hints:
        result += f" -> {fmt(hints['return'])}"
    return result

The formatter mirrors how hints are built: a union is a set of members, a generic is an origin with arguments, and both recurse, so dict[str, float] | None comes out exactly as written. NoneType and Ellipsis need special cases because they are values standing in for types. Walking the signature gives parameter kinds and defaults, and the hints give the types; the two are separate because a parameter can have a default without an annotation and vice versa. Documentation generators, CLI help (Typer, Click) and tool descriptions for LLMs are all built from exactly these two sources.

Interview

16. Are type hints enforced in Python? Then what are they for?

SolutionModel answer

No: the interpreter stores annotations (in __annotations__) and otherwise ignores them, so passing a wrong type runs exactly as it would without hints. They are for three things. Documentation that cannot drift as easily as comments, because tools read it. Static analysis: type checkers such as mypy and pyright analyse the code without running it and catch mismatched arguments, wrong return types, missing attributes and unhandled None values before production, and editors use the same information for completion and refactoring. And runtime use by libraries that read the hints on purpose: dataclasses generate methods from them, Pydantic validates and converts data, FastAPI and Typer build APIs and CLIs, agent frameworks build tool schemas. A good practice is static checking inside the program and explicit validation at its boundaries, where untrusted data enters.

Interview

17. What does str | None (or Optional[str]) mean, and how should code handle it?

SolutionModel answer

It means the value is either a string or None; Optional does not mean the parameter is optional (that is a default value), it means "may be None". A function returning str | None tells every caller that a missing result is a normal outcome they must handle. Code handles it by narrowing: checking if value is None: (and returning, raising or using a fallback) before using it as a string, after which the type checker treats it as str; isinstance checks narrow the same way. A parameter that defaults to None should be annotated X | None = None explicitly. Unhandled None is the most common bug type checkers catch, because in production it shows up as AttributeError: 'NoneType' object has no attribute ... on the rare path where a lookup failed.

Interview

18. How would you introduce type checking into an existing ML codebase?

SolutionModel answer

Gradually. Add a type checker (mypy or pyright) to the editor and CI in a lenient mode first, so unannotated code is not flagged, and fix the errors it already finds in annotated code. Then annotate the boundaries that matter most: public functions of shared modules, data loading and feature pipelines, configuration, and the code that calls model APIs, using precise types for inputs (Iterable[str], Mapping[str, float]), X | None where values can be missing, dataclasses or Pydantic models instead of loose dicts for structured records, and protocols for pluggable components. Enable stricter settings per module as coverage grows (mypy's per-module strict), and install stub packages such as pandas-stubs; for array shapes and dtypes, which types capture poorly, keep runtime assertions. Avoid Any except at real boundaries, and validate external data (API payloads, model output, files) at run time with Pydantic, since static types cannot check data that arrives while the program runs. Measure progress by the share of typed modules and the number of production bugs caught earlier.

Recap

  • Type hints (x: int, -> list[str]) document types for people, editors and type checkers; Python does not enforce them.
  • Use built-in generics (list[str], dict[str, float], tuple[int, ...]) and aliases for long types; annotate -> None for functions returning nothing.
  • X | None means "may be None"; handle it by narrowing (if x is None:, isinstance) before use. Keep hints truthful.
  • Accept the most general types (Iterable, Sequence, Mapping), return specific ones; Any disables checking, object forces narrowing.
  • Libraries read hints at run time with typing.get_type_hints, get_origin and get_args: dataclasses, Pydantic, FastAPI and tool schemas.
