7.1 Exceptions and try / except

What happens when an error is raised, how it travels up the call stack, and how to read a traceback. try, except, else and finally step by step, the exception hierarchy, and catching narrowly so real bugs stay visible. Applied to parsing data rows, model replies and configuration files.

1What happens when an exception is raised

An exception is an object that describes an error. When Python hits a problem it cannot continue from, such as dividing by zero, a missing dict key or a string that is not a number, it raises an exception: it creates the exception object and stops running the current code immediately. No further line of that block runs. What happens next depends on whether anyone is ready to handle it.

To understand where an exception goes, picture the call stack: the list of function calls that are currently running. If main calls load, which calls parse, all three are on the stack, each paused and waiting for the one it called to return. When parse raises, Python looks for a handler (a matching except) in parse. If there is none, parse is abandoned and the exception travels to load, at the line that called parse. If load has no handler either, it is abandoned too, and so on up the stack. This is called unwinding. If the exception reaches the top without being handled, the program stops and prints a traceback.

unwinding.py
def parse(text):
    print("  parse starts")
    value = int(text)            # raises ValueError for "abc"
    print("  parse done")        # never runs for bad input
    return value

def load(text):
    print(" load starts")
    result = parse(text) * 2
    print(" load done")          # skipped too: the exception passed through load
    return result

def main():
    try:
        print(load("21"))
        print(load("abc"))
    except ValueError as e:
        print("main handled:", e)

main()
Output
 load starts
  parse starts
  parse done
 load done
42

  parse starts
main handled: invalid literal for int() with base 10: 'abc'

The second call shows the whole journey: parse stops at int(text), load stops at the line that called parse, and the first matching handler, in main, receives the exception. Neither "done" line runs. Everything between the raise and the handler is skipped, which is the point: the code after a failed step usually cannot work, so Python does not try.

A traceback is the record of that journey. It lists the calls from the oldest (the top of your program) to the most recent (where the error happened), hence its header "most recent call last", and the last line names the exception type and message. Read it from the bottom: first what went wrong, then where, then how the program got there. The traceback module can format the same report as a string, which is what logging uses (7.3).

traceback_parts.py
import traceback

def parse(text):
    return int(text)

def load(text):
    return parse(text) * 2

try:
    load("abc")
except ValueError:
    report = traceback.format_exc()
lines = report.strip().splitlines()
print(lines[0])
print([l.split(", in ")[-1] for l in lines if l.strip().startswith("File")])   # oldest call first
print(lines[-1])

2try and except: catching by type

A try block marks code whose exceptions you want to handle. After it come one or more except clauses, each naming the exception types it handles. When an exception is raised inside the try block, Python checks the except clauses from top to bottom and runs the first one whose type matches. "Matches" means isinstance(exception, that_type): the exception is of that class or of a subclass of it. If none matches, the exception continues up the stack as if there were no try at all. If no exception happens, all the except clauses are skipped.

except_basics.py
def to_number(text):
    try:
        return float(text)
    except ValueError as e:
        print("  bad text:", e)
    except TypeError as e:
        print("  not a string:", e)
    return None

print(to_number("3.5"), to_number("3,5"), to_number(None))
Output
  bad text: could not convert string to float: '3,5'
  not a string: float() argument must be a string or a real number, not 'NoneType'
3.5 None None

as e binds the exception object to a name, so you can read its message with str(e) and its arguments with e.args. Several types can share one handler as a tuple, except (ValueError, TypeError) as e:. Because the first match wins, put specific types before general ones: an except Exception placed first would catch everything, and the specific clauses below it could never run (problem 3).

One scope detail surprises people: at the end of the except block, Python deletes the name bound with as. The exception object refers to the whole traceback, which refers to every local variable of every frame involved, so keeping it alive would keep all of them alive. If you need the exception later, assign it to another name inside the block.

except_name.py
try:
    {}["model"]
except KeyError as e:
    print(repr(e), e.args, str(e))
    saved = e
try:
    print(e)
except NameError as missing:
    print("NameError:", missing)
print(type(saved).__name__)
Output
KeyError('model') ('model',) 'model'
NameError: name 'e' is not defined
KeyError

Notice that str(e) for a KeyError is the key's repr, with quotes, which is why logs show KeyError: 'model'. Most other exceptions just hold their message.

3else and finally: what runs when

A try statement can have two more clauses. else runs only if the try block finished without an exception. finally runs always, whether the block succeeded, raised an exception that was handled, raised one that was not handled, or left early with return, break or continue. The full order is: try block; then either the matching except (on error) or else (on success); then finally; then, if an exception is still unhandled, it continues up the stack.

order.py
def attempt(text):
    try:
        print("  try")
        n = int(text)
    except ValueError:
        print("  except")
        return "bad"
    else:
        print("  else")
        return n * 2
    finally:
        print("  finally")

print(attempt("4"))
print(attempt("x"))
Output
  try
  else
  finally
8
  try
  except
  finally
bad

finally ran in both cases, and it ran after the return statement was reached but before the function actually returned: the return value is set aside, finally runs, then the function returns. That is what makes finally the place for cleanup that must happen no matter what: closing a file or connection, releasing a lock, stopping a timer, deleting a temporary file. (A with block, 10.2, packages exactly this pattern, and is usually the better tool.)

else exists to keep the try block small. Code in the try block is covered by the except clauses, so if you put the follow-up work there too, an error in the follow-up could be caught by a handler meant for something else. Moving it to else means "only run this if the risky step worked, and do not catch its errors here".

return_in_finally.py
import warnings

code = '''
def f():
    try:
        raise ValueError("lost")
    finally:
        return "finally won"
'''
with warnings.catch_warnings(record=True) as caught:
    warnings.simplefilter("always")
    namespace = {}
    exec(compile(code.strip(), "<demo>", "exec"), namespace)
print(namespace["f"](), [w.category.__name__ for w in caught])
Output
finally won ['SyntaxWarning']

Never return (or break or continue) from inside finally. The return replaces whatever was happening, so an exception that was on its way up is silently discarded, as the example shows. Python 3.14 now warns about it with a SyntaxWarning when the code is compiled (PEP 765), but older versions accept it silently (problem 10).

4The exception hierarchy

Exception types are classes arranged in a tree, and that tree decides what each except clause catches. At the root is BaseException. Directly under it are a few special exceptions that are not errors in the usual sense: KeyboardInterrupt (the user pressed Ctrl+C), SystemExit (raised by sys.exit()), and GeneratorExit (used to close generators, 6.3). Everything that represents an actual error is under Exception. That is why except Exception is the widest handler you should normally write: it catches every error but still lets Ctrl+C and sys.exit() stop the program.

    print(exc.__name__, "->", [c.__name__ for c in exc.__mro__[1:-1]])

The tree has practical consequences. except ValueError also catches JSONDecodeError and UnicodeDecodeError, so a handler written for "the number was invalid" may quietly swallow "the file was not valid JSON" too. except LookupError handles both missing keys and bad indexes. except OSError covers most input/output failures at once. And a bare except: (with no type) is the same as except BaseException:: it catches Ctrl+C and sys.exit() as well, which can make a program impossible to stop. Never write it; if you truly want "any error", write except Exception and log it.

5Catching narrowly

The hardest part of exception handling is not the syntax but deciding what not to catch. A handler is a promise: "if this goes wrong, I know what to do instead". Every exception you catch without being able to keep that promise turns a loud bug into a silent wrong result. Three rules follow from that:

  • Catch the specific type you expect (ValueError for a bad number, FileNotFoundError for a missing file), not Exception.
  • Keep the try block as small as possible: just the statement that can fail in the way you expect. Move the rest to else or after the statement.
  • Only catch what you can handle: retry, use a default, skip and record, or add context and re-raise (7.2). If you cannot do any of these, let it propagate.
narrow.py
rows = [{"id": 1, "price": "9.5"}, {"id": 2, "price": "n/a"}, {"id": 3, "prce": "4"}]

def total_broad(rows):
    total = 0.0
    for row in rows:
        try:
            total += float(row["price"])   # also hides the misspelled key
        except Exception:
            pass
    return total

def total_narrow(rows):
    total, bad = 0.0, []
    for row in rows:
        raw = row.get("price")
        if raw is None:
            bad.append((row["id"], "missing price"))
            continue
        try:
            value = float(raw)
        except ValueError:
            bad.append((row["id"], f"not a number: {raw!r}"))
        else:
            total += value
    return total, bad

print(total_broad(rows))
print(total_narrow(rows))
Output
9.5
(9.5, [(2, "not a number: 'n/a'"), (3, 'missing price')])

Both versions return 9.5, but only the second one tells you why the other two rows were not counted, and only it distinguishes a bad value from a missing field. The broad handler would also have hidden a real bug, such as a NameError from a typo in the loop, by treating it like a bad price. There is one legitimate place for a broad except Exception: a boundary where one failure must not stop everything else, such as the loop over requests in a server or over records in a batch job. There, catch broadly, log the full traceback, record the failure, and move on to the next item (7.3, 7.4).

A try/except around one conversion is like TRY_CAST(x AS FLOAT) in SQL Server or try ... otherwise in Power Query: the bad value becomes NULL (or a default) instead of failing the whole query. Wrapping an entire query in an error handler that returns an empty table is the broad except equivalent, and just as risky: the report looks fine and is wrong.

6What exceptions cost

Entering a try block is essentially free in modern Python (3.11 made the no-exception path "zero-cost"). Raising and catching an exception is not: Python creates the exception object, records the traceback and unwinds the stack, which is much slower than an if test. So exceptions are the right tool for exceptional cases, the ones that rarely happen, and a poor tool for normal control flow in a hot loop where the "error" happens most of the time (problem 8). For a dict where keys are often missing, d.get(key, default) is both clearer and faster than catching KeyError.

exception_cost.py
import timeit

d = {"a": 1}
def with_get():
    return d.get("zzz", 0)

def with_except():
    try:
        return d["zzz"]
    except KeyError:
        return 0

t_get = timeit.timeit(with_get, number=200_000)
t_exc = timeit.timeit(with_except, number=200_000)
print(t_exc > t_get)
Output
True

def to_int(value, default=None):
    if isinstance(value, float):
        return int(value) if value.is_integer() else default
    try:
        return int(value)
    except (ValueError, TypeError):
        return default

int() raises ValueError for text that is not an integer (including "4.0" and "") and TypeError for things that are not text or numbers (None, lists), so one handler with a tuple covers exactly the expected failures and nothing else. Floats need a check before the try, because int(3.5) does not fail: it silently truncates to 3, which is the worst kind of conversion bug. Note that bool is a subclass of int, so to_int(True) returns 1; whether that is acceptable depends on the data.

solution.py
def parse_rows(rows):
    good, errors = [], []
    for n, row in enumerate(rows, start=1):
        if len(row) != 3:
            errors.append((n, f"expected 3 fields, got {len(row)}"))
            continue
        raw_id, name, raw_score = row
        try:
            row_id = int(raw_id)
        except ValueError:
            errors.append((n, f"bad id: {raw_id!r}"))
            continue
        try:
            score = float(raw_score)
        except ValueError:
            errors.append((n, f"bad score: {raw_score!r}"))
            continue
        good.append({"id": row_id, "name": name.strip(), "score": score})
    return good, errors

Each try block holds exactly one conversion, so the handler knows which field failed and can say so. The field count is a normal condition to test with if, not to discover through an unpacking ValueError, which would also give a vague message. Collecting (row, message) pairs and continuing is how data loaders behave in practice: the caller decides whether 3 bad rows out of 5 is acceptable. {raw!r} shows the raw value with quotes, so an empty string or trailing spaces are visible in the message (5.3). float(" 0.75 ") accepts surrounding spaces, as int does.

solution.py
def enrich(records, prices):
    out = []
    for r in records:
        try:
            price = prices[r["product"]]
        except KeyError:
            out.append({**r, "total": None})
        else:
            out.append({**r, "total": round(price * r["qty"], 2)})
    return out

The broad handler turned a NameError (a typo, a bug) into the same result as "unknown product" (an expected case), so the function ran without complaint and produced only Nones. Moving the calculation into else means a missing qty, which is a data bug, raises its own KeyError from outside the handler, as the second test requires; inside the try, it would have been mistaken for an unknown product.

import re

SCORE = re.compile(r"score\s*:\s*(\d+)\s*(?:/\s*10)?", re.IGNORECASE)

def parse_score(reply):
    m = SCORE.search(reply)
    if not m:
        raise ValueError(f"no score in reply: {reply[:40]!r}")
    score = int(m.group(1))
    if not 1 <= score <= 10:
        raise ValueError(f"score {score} out of range in reply: {reply[:40]!r}")
    return score

Raising instead of returning None forces the caller to decide what a bad reply means: retry the judge, skip the sample or fail the evaluation; a None would flow into an average and break it later, far from the cause. ValueError is the right type: the input is a string, as expected, but its value is not acceptable. Lesson 7.2 shows how to define a custom exception type for this, so callers can catch "bad model output" specifically.

import json

def load_reply(raw):

13. Retry on chosen exceptions

Write call_with_retry(fn, attempts, retry_on) that calls fn() up to attempts times. If it raises an exception whose type is in the tuple retry_on, try again; if it raises anything else, let it propagate immediately. If every attempt fails, re-raise the last exception. SolutionShow the solution and why
solution.py
def call_with_retry(fn, attempts, retry_on):
    if attempts < 1:
        raise ValueError("attempts must be at least 1")
    last_error = None
    for attempt in range(1, attempts + 1):
        try:
            return fn(), attempt
        except retry_on as e:
            last_error = e
    raise last_error

except retry_on accepts the tuple directly, so only the listed transient errors (timeouts, dropped connections) are retried; a KeyError is a bug, and retrying it would just repeat the bug and delay the report, so it propagates at once. The handler saves the exception to a second name because the as name is deleted when the block ends. Re-raising the last error keeps its original traceback, so the logs show where the final attempt failed. Real retry code adds waiting between attempts with exponential backoff and jitter, and respects the server's Retry-After header; lesson 8.3 turns this into a decorator.

import json


def load_settings(path, defaults):
    try:
        with open(path, encoding="utf-8") as f:
            text = f.read()
    except FileNotFoundError:
        return dict(defaults)
    try:
        data = json.loads(text)
    except json.JSONDecodeError as e:
        raise ValueError(f"{path}: invalid JSON at line {e.lineno}: {e.msg}")
    settings = {**defaults, **data}

    except ValueError:
        raise ValueError(f"max_tokens must be an integer, got {settings['max_tokens']!r}")
    return settings

15. The first reply that parses

When a model's output must follow a format, a common trick is to sample several replies and keep the first one that parses. Write first_valid(replies, parse) that calls parse(reply) on each reply in order and returns (index, parsed) for the first one that does not raise ValueError. If none parses, raise ValueError whose message lists every failure as "#i: message", one per line. Other exception types must propagate unchanged. Stop at the first success; do not parse the rest.

Hint 1Open a hint

Hint 2Open a hint

SolutionShow the solution and why
solution.py
def first_valid(replies, parse):
    failures = []
    for i, reply in enumerate(replies):
        try:
            return i, parse(reply)
        except ValueError as e:
            failures.append(f"#{i}: {e}")
    raise ValueError("no valid reply:\n" + "\n".join(failures))

The loop returns as soon as one reply parses, so later replies cost nothing, which the calls test checks. Only ValueError (including JSONDecodeError) counts as "this reply is malformed"; anything else signals a bug in the parser or the data, and must not be hidden behind "try the next sample". In the last test, json.loads("5") returns the number 5, and "label" not in 5 raises TypeError because an int cannot be searched: that is a gap in the parser (it should check that the JSON is an object), and it surfaces at once instead of being reported as "no valid reply". Joining the collected messages gives one readable error for the log, with the index of each sample. This is the shape of "sample n, take the first valid" and of repair loops that feed the error messages back to the model.

17. What is the difference between except Exception: and a bare except:, and why does it matter?

SolutionModel answer

A bare except: catches BaseException, the root of the hierarchy, so it also catches KeyboardInterrupt (Ctrl+C), SystemExit (sys.exit()) and GeneratorExit. Code with a bare except inside a loop can become impossible to stop with Ctrl+C, and it can swallow a deliberate exit. except Exception: catches all ordinary errors but lets those control-flow exceptions through. Even so, except Exception should be rare: it belongs at boundaries (a request handler, a batch loop, a worker), always with logging of the full traceback, never as except Exception: pass. Everywhere else, catch the specific types you can actually handle, so unexpected errors, which are usually bugs, stay visible.

Interview

18. What are else and finally for in a try statement? Give a real use for each.

SolutionModel answer

else runs only if the try block raised nothing. Its purpose is to keep the try block minimal: put only the risky statement in try, and the code that depends on its success in else, so errors in that follow-up code are not accidentally caught by handlers meant for the risky step. Example: try: f = open(path), except FileNotFoundError: use defaults, else: parse the file. finally runs no matter what: success, a handled or unhandled exception, or an early return or break. It is for cleanup that must always happen: closing a connection, releasing a lock, removing a temporary file, recording a metric of how long a call took. Never return from finally, since that discards any exception in flight; and for resources, a with statement usually replaces try/finally.

19. You run a batch job over one million records and some records are bad. How do you design the error handling?

SolutionModel answer

Decide per error type whether it is a record problem or a job problem. Record problems (a malformed line, a missing field, a value out of range) should not stop the job: catch the specific exceptions per record, write the record and the error to a dead-letter file or table with enough context to fix it (record id, line number, message), count them, and continue. Job problems (the database is down, credentials are wrong, a bug such as a NameError) should stop the job fast instead of failing a million times; transient ones (timeouts, rate limits) get retries with backoff first. Add an error budget: if more than, say, 1% of records fail, abort, since that usually means a systematic problem such as a schema change. Log a summary at the end (processed, succeeded, failed by error type), make the job resumable with checkpoints, and keep writes idempotent so a re-run does not duplicate data. Only the outermost loop uses a broad except Exception, and it logs the traceback for every record it catches.

Recap

  • A raised exception stops the current block and unwinds the call stack to the first matching except; unhandled, it prints a traceback (read it from the bottom).
  • except clauses are tried top to bottom and match subclasses too: specific types first. The as name is deleted after the block.
  • else runs on success (keep try small); finally always runs, even on return or break. Never return inside finally.
  • Errors live under Exception; KeyboardInterrupt and SystemExit do not. Never write a bare except:. JSONDecodeError is a ValueError.
  • Catch narrowly: the specific type, the smallest block, only what you can handle. Raising is expensive; use get and checks for normal cases.
