2.1 Names, objects and identity

What = really does, how is differs from ==, and the places where that difference turns into real bugs: missing values, caches keyed by id(), NaN in your features, and list methods that grab the wrong item.

1Names point at objects

Every value in Python is an object living somewhere in memory. A variable is a name that points at an object. x = something does one thing only: it makes the name x point at that object. It never copies the object, and it never changes the object that x pointed at before. Your theory notes call this a tag on an object; this lesson is about what that means in real code.

names.py
a = [1]
b = a              # b now points at the SAME list as a
print(a is b)

a = a + [2]        # a + [2] builds a NEW list, then a is pointed at it
print(a, b)        # b still points at the old list
print(a is b)
Output
True
[1, 2] [1]
False

Read every = as "point this name at that object". Two consequences follow, and the rest of the lesson depends on them:

  • Several names can point at one object. Then any change made *through* one name is visible through all of them, because there is only one object. (Changing objects is lesson 2.2.)
  • Pointing a name somewhere else changes nothing else. a = a + [2] did not touch the old list, so b was not affected.

It helps to see the two steps of an assignment separately. First Python evaluates the right-hand side completely, which produces (or finds) an object. Then it binds the name on the left to that object, by storing the pair "name to object" in a namespace. A namespace is literally a dictionary: at the top level of a script it is the one returned by globals(), and inside a function it is the function's local namespace (3.3). So x = 5 is, underneath, close to globals()["x"] = 5: a key in a dict now refers to the object 5.

assignment_steps.py
a = [1, 2]
print(globals()["a"] is a)      # the name lives in a dict of names

x = y = []                      # ONE list, two names: the right side is evaluated once
x.append("shared")
print(y, x is y)

a, b = 1, 2
a, b = b, a                     # the right side (2, 1) is built first, then unpacked
print(a, b)
Output
True
['shared'] True
2 1

The two steps explain both of the other lines. In x = y = [], the right-hand side [] is evaluated once, and both names are bound to that single list, so a change through x shows through y: a common bug when someone writes seen = results = [] meaning two empty lists. (For immutable values like a = b = 0 it is harmless, because nobody can change the 0.) And the swap a, b = b, a works without a temporary variable because the right-hand side builds the tuple (2, 1) from the current values before any name is rebound.

Containers hold references too. A list does not contain its items; it contains references to item objects, exactly like names do. That is why the same object can be in two lists at once, and why putting a list inside a dict and then changing the list changes what the dict shows. Lesson 2.2 builds on this.

2Identity and equality

Every object has an identity: a number that stays the same for the object's whole life. id(x) returns it. Two questions sound alike but are completely different:

  • a is b asks: is this the same object? It compares identities. Nothing else is looked at.
  • a == b asks: do these count as equal? Python asks the object itself, by calling its __eq__ method, and the object can answer whatever its type decides.
≈
SQL / Power BI

is is like comparing primary keys: same key, same row. == is like comparing all the columns: two different rows can have exactly the same values. A deduplication that should keep distinct rows but compares values instead of keys deletes real data, and the same mistake exists in Python.

is_vs_eq.py
a = [1, 2, 3]
b = [1, 2, 3]
print(a == b, a is b)        # equal values, two different objects
print(id(a) == id(b))        # is compares exactly these numbers

import numpy as np
x = np.array([1, 2, 3])
print(x == 2)                # numpy answers == with a whole array, not True / False
Output
True False
False
[False  True False]

Because == is decided by the type, it is not always a yes/no question. numpy compares element by element and returns an array. pandas does the same with a Series. Some libraries go further: in SQLAlchemy, column == None does not compare anything at all, it builds a piece of SQL (IS NULL). is can never be redefined by a type, so it always means exactly one thing and is very fast.

Equality also works across types in ways worth knowing. Numbers compare by value whatever their type, so 1 == 1.0 and even 1 == True are true (bool is a subtype of int). Containers of different types are not equal even with the same contents: [1, 2] == (1, 2) is false. And for an object whose type does not define its own __eq__, Python falls back to identity: two separate object() instances are never equal. The negated forms follow the same split: != asks the type, is not compares identities, and a is not b is the readable way to write not (a is b).

equality_rules.py
print(1 == 1.0, 1 == True, [1, 2] == (1, 2), list((1, 2)) == [1, 2])
o1, o2 = object(), object()
print(o1 == o2, o1 == o1, o1 is not o2)
print({"a": 1} == {"a": 1.0}, "1" == 1)
Output
True True False True
False True True
True False

The last line shows a real data-cleaning trap: the string "1" and the number 1 are never equal. Ids read from a CSV are strings, ids from a JSON API are often numbers, and a join or a membership test between them silently finds nothing. Convert to one type at the boundary, where the data comes in.

i
Rule of thumb

Use == to compare values. Use is only to ask "is this that exact object?": with None and the other singletons, with sentinels, and when you really mean identity (problem 14). Never use is to compare numbers or strings: Python even warns you (SyntaxWarning: "is" with 'int' literal).

3None, singletons and sentinels

A singleton is a type that only ever has one object. None, True, False and ... (Ellipsis) are singletons: every None in your program is the same object. That is why x is None is the right test. It is exact (nothing can pretend to be None), and it works on numpy arrays and pandas objects, where x == None either returns an array or raises an error inside an if.

none.py
def first(rows):
    return rows[0] if rows else None

r = first([])
print(r is None)
print(type(None)() is None)   # even asking the type for a new None gives the same one
Output
True
True

Sometimes None is a valid value, so it cannot also mean "not given". An LLM API is a good example: stop=None can mean "clear the stop sequences", which is different from "use the server default". The standard answer is a sentinel: a private object created once, which no caller can pass by accident.

sentinel.py
MISSING = object()            # a unique object; nothing else is ever this object

def get_setting(settings, key, default=MISSING):
    if key in settings:
        return settings[key]
    if default is MISSING:
        raise KeyError(key)
    return default            # includes default=None, which is a real choice

cfg = {"model": "small", "stop": None}
print(get_setting(cfg, "stop"))
print(get_setting(cfg, "temperature", None))
try:
    get_setting(cfg, "temperature")
except KeyError as e:
    print("KeyError:", e)
Output
None
None
KeyError: 'temperature'

dict.get, getattr and many library functions use exactly this trick inside. Recognising it makes a lot of library code easier to read.

4Caching is not a rule

CPython, the normal Python, saves memory by reusing some immutable objects. Small integers from -5 to 256 are created once and shared. Many short strings that look like names are interned: kept in one shared copy. And when the same constant appears twice in one piece of compiled code, the compiler may store it only once. All of this is an implementation detail: it can differ between Python versions, between the REPL and a script, and between a literal and a value computed at run time.

caching.py
a = 256; b = 256
print(a is b)                       # small ints are shared

c = int("257"); d = int("257")
print(c is d, c == d)               # computed at run time: two objects

s1 = "hello_world"
s3 = "".join(["hello", "_world"])
print(s1 == s3, s1 is s3)           # built at run time: equal, not identical
Output
True
False True
True False

So is on numbers or strings can be True in your test and False in production with other data. Values that come from files, APIs and databases are created at run time, so they are usually separate objects even when they are equal. Always compare them with ==.

The reason for caching is memory and speed: a program creates small numbers and identifier-like strings all the time, and sharing one copy saves allocations, and lets dictionary lookups on interned strings compare by identity first. You can use the same trick deliberately with sys.intern, which returns the one shared copy of a string. It is worth it when you hold millions of copies of a few distinct strings, such as labels or category names in a large dataset loaded row by row; pandas solves the same problem with its category dtype.

intern.py
import sys

rows = ["".join(["sp", "am"]) for _ in range(3)]       # three separate but equal strings
print(rows[0] == rows[1], rows[0] is rows[1])
shared = [sys.intern(r) for r in rows]
print(shared[0] is shared[1] is shared[2])
Output
True False
True

5Containers check identity first

When a list, tuple or dict looks for a value (for in, ==, count, index, remove or a dict key), it compares each item with x is item or x == item: identity first, equality second. Usually you never notice. Two cases make it visible.

NaN. The float nan ("not a number", what pandas uses for missing numbers) is defined as not equal to anything, itself included: nan == nan is False. But the identity check comes first, so the same nan object is still found in a list.

nan.py
nan = float("nan")
print(nan == nan)                   # NaN equals nothing, not even itself
print(nan in [nan])                 # found anyway: the identity check comes first
print(float("nan") in [nan])        # a different NaN object: not found
Output
False
True
False
≈
SQL / Power BI

NaN behaves like SQL's NULL: NULL = NULL is not true, so you write IS NULL. In pandas the equivalent is s.isna(), never s == np.nan (problem 17).

Equal but different objects. list.remove(x) deletes the first item equal to x, and list.index(x) returns the position of the first equal item. If the list holds two equal objects (two chat messages that both say "ok"), they find the first one, which may not be the one you meant (problem 15).

6Object lifetime and id reuse

del x deletes the name x, not the object. An object stays alive as long as at least one name or container still points at it. When nothing points at it any more, Python frees it, and its memory can be reused for the next object. Since id() is based on that memory, an id can be reused after its object is gone.

lifetime.py
a = [1, 2, 3]
b = a
del a                 # removes the name a; the list is still reachable through b
print(b)

# Each [] here dies right after id() reads it, so the second one can land in the same
# memory. The result depends on the run: never rely on it either way.
print(id([]) == id([]))
Output
[1, 2, 3]
True

How does Python know when nothing points at an object? CPython keeps a reference count in every object: the number of names, containers and other places that currently refer to it. Binding a name, putting the object in a list or passing it to a function adds one; a name being rebound or deleted, or the list being emptied, subtracts one. When the count reaches zero, the object is freed immediately. sys.getrefcount(x) shows the count (it reports one extra, for its own argument).

refcount.py
import sys, gc

data = ["a large", "list"]
before = sys.getrefcount(data)
holder = [data, data]                  # two more references, from inside a list
print(sys.getrefcount(data) - before)
holder.clear()
print(sys.getrefcount(data) - before)

a = []
a.append(a)                            # a list that contains itself: a reference cycle
del a                                  # the count never reaches zero by itself...
print(gc.collect() >= 1)               # ...so the cycle collector frees it
Output
2
0
True

Reference counting cannot free a cycle, a group of objects that refer to each other but are not reachable from the program, so CPython also runs a cycle-detecting garbage collector from time to time (gc.collect() forces a run). In everyday code you rarely think about either. They matter when memory keeps growing in a long-running service: a global cache, a list of past requests or a closure (3.4) that holds a reference keeps every object it reaches alive, however large, which is the usual cause of "memory leaks" in Python.

!
Never key long-lived data by id()

id() is only unique among objects that are alive at the same time. A cache keyed by id(prompt) misses when an equal prompt arrives as a new object, and can even return another prompt's answer once the old object is freed and its id reused (problem 8). Key by the value instead.

MISSING = object()

To save money, this wraps an LLM call in a cache. Two prompts with the same text should cost one call, but they cost two. Fix the cache key.

Hint 1Open a hint

Prompts built at run time (from templates, user input, files) are separate objects even when the text is equal.

Hint 2Open a hint

A str can be a dict key directly.

SolutionShow the solution and why
solution.py
calls = []

def fake_llm(prompt):
    calls.append(prompt)
    return f"answer to: {prompt}"

_cache = {}

def cached_complete(prompt):
    if prompt not in _cache:
        _cache[prompt] = fake_llm(prompt)
    return _cache[prompt]

id(prompt) identifies the object, not the text, so equal prompts get different keys and miss. The worse bug is hidden: once a prompt object is freed, its id can be reused by a different prompt, which would then get the old prompt's cached answer. Key by the value itself. For long prompts, real caches key by a hash of the text plus the model and settings, for example hashlib.sha256(f"{model}|{prompt}".encode()).hexdigest(), since a different model or temperature must not share an answer.

10. Merge retriever results without repeats

A hybrid retriever gets chunks from BM25 and from a vector search. Both return references to the same chunk objects from one shared store, so one chunk often appears in both lists. Write merge_results(first, second) that keeps the order of first then second and drops an item if that same object was already kept. Two separate chunks with equal content are different index entries and must both be kept. Chunks are dicts, which cannot go in a set.

TestsThe 4 checks Run tests uses
c1 = {"doc": "faq.md", "text": "Reset your password from Settings."}
c2 = {"doc": "faq.md", "text": "Reset your password from Settings."}
c3 = {"doc": "guide.md", "text": "Contact support."}

Hint 1Open a hint

A dict cannot go in a set, but its id() can, and every chunk here is alive while the function runs.

Hint 2Open a hint

Why not if item not in out? in falls back to ==, so it would drop c2.

SolutionShow the solution and why
solution.py
def merge_results(first, second):
    seen = set()
    out = []
    for chunk in first + second:
        if id(chunk) not in seen:
            seen.add(id(chunk))
            out.append(chunk)
    return out

Keying by id() is safe here, because every chunk is alive (held by the input lists) for the whole call, so no id can be reused, unlike the long-lived cache in problem 8. A set of ids makes each check O(1); the tempting if chunk not in out is O(n) per item and compares by ==, so it would also drop c2, an equal but separate chunk. Whether equal-content chunks should be merged is a separate decision. If they should, deduplicate by a content key such as (doc, text).

Hint 2Open a hint

SolutionShow the solution and why
solution.py
def read_flag(value):
    if value is None:
        return False
    if isinstance(value, bool):
        return value
    if isinstance(value, str):
        return value.strip().lower() in {"true", "yes", "1"}
    if isinstance(value, int):
        return value != 0
    raise TypeError(f"cannot read a flag from {value!r}")

isinstance also accepts subclasses, which is usually what you want, but here it changes behaviour if the order is wrong: with the int check first, True would be treated as the int 1. Keeping bool first preserves the old behaviour. is None replaces == None for the reasons in this lesson. The string is normalised once and checked with a set, which reads like the rule it implements.

def index_of(items, target):
    for i, item in enumerate(items):
        if item is target:
            return i
    raise ValueError(f"object not in list: {target!r}")

SYSTEM = {"role": "system", "content": "Answer from the documents only."}


def new_history():
    return [dict(SYSTEM)]


def add(history, role, content):
    msg = {"role": role, "content": content}
    history.append(msg)
    return msg


def _position(history, msg):
    for i, m in enumerate(history):
        if m is msg:
            return i
    raise ValueError("message is not in this history")


def delete(history, msg):
    """Delete exactly this message."""
    i = _position(history, msg)
    if i == 0:
        raise ValueError("the system prompt cannot be deleted")
    del history[i]


def edit(history, msg, content):
    """Replace the text of exactly this message, return the new message."""
    i = _position(history, msg)
    history[i] = {"role": msg["role"], "content": content}
    return history[i]

Both bugs are the same one: remove and index match by equality, so two messages with the same role and text are interchangeable to them. The code even says "exactly this message" in its docstrings, which is an identity requirement. A single _position helper that compares with is fixes both and also rejects an equal copy that is not in the history (the last test), instead of deleting a real message by accident. Real chat apps usually avoid the whole problem by giving each message a unique id field, which is an identity you control and can store in a database.

Interview

18. What is the difference between is and ==, and when is is the right choice?

SolutionModel answer

is checks identity: whether two names point at the same object. It cannot be overridden and is a single pointer comparison. == checks equality by calling the left object's __eq__, which each type defines, so it can be slow, can return a non-bool (numpy, pandas, SQLAlchemy), and two different objects can be equal. Use is for singletons (None, True, False), for sentinels, and when you really mean "this exact object" (finding a specific message, deduplicating references). Never use it for numbers or strings, because caching makes the result depend on the Python version and on how the value was created. Strong answer: mention that containers use "identity, then equality", which explains nan in [nan].

Interview

19. When is None not enough as a default, and what do you use instead?

SolutionModel answer

When None is itself a meaningful value the caller may pass. Then you cannot tell "not passed" from "passed None". Examples: an API where stop=None clears stop sequences, a cache where None is a valid stored result, or dict.get with a default. The answer is a sentinel: MISSING = object() at module level, checked with is MISSING. It is unique, so no caller can pass it by accident. Mention that real libraries do this (the OpenAI client's NOT_GIVEN, dataclasses.MISSING), and that typing it well uses an enum with one member or typing.Final, which shows you have read library code.

Interview

20. Why can a = 1000; b = 1000; a is b be True in a script but False in the REPL?

SolutionModel answer

The REPL compiles each line separately, so each 1000 becomes its own int object and is is False. In a script (or one line with ;), both literals are in the same compiled code object, and the compiler stores the constant once, so both names point at the same object. Integers from -5 to 256 are always shared, so they are True everywhere. None of this is guaranteed by the language. It is CPython behaviour that can change between versions, so code must never depend on it: compare numbers with ==. The interviewer is checking whether you know that is compares identity, not value.

Recap

  • = points a name at an object. It never copies, and moving a name changes no object.
  • is = same object (identity, cannot be overridden). == = equal by the type's own rules, and may not even return a bool.
  • Use is for None, the other singletons and sentinels. Never for numbers or strings: caching makes it unreliable.
  • Containers compare with "identity, then equality": that is why nan in [nan] is True, and why remove and index can pick the wrong equal item.
  • id() is unique only among live objects. Safe within one call, wrong as a long-lived cache key.
