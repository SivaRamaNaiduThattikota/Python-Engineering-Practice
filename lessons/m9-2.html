9.2 Dunder methods

Double-underscore methods are the hooks that make your objects work with Python's syntax and built-ins: print, ==, len, in, [], +, sorted, if, and calling. __repr__ and __str__, equality and hashing and the rule that links them, ordering, the container protocol, arithmetic with NotImplemented, and callable objects. Applied to money, token usage, versions, batches and vectors.

1Hooks for syntax and built-ins

Python's syntax and built-in functions are translated into method calls on your objects. len(x) calls x.__len__(); x == y calls x.__eq__(y); x + y calls x.__add__(y); x[i] calls x.__getitem__(i); str(x) calls x.__str__(); if x: calls x.__bool__(). These methods are called dunder methods ("double underscore") or "special methods", and together they form Python's data model. Defining them in your class makes your objects behave like built-in ones, with the same syntax.

This is how libraries feel native. A NumPy array supports a + b and a[1:3] because it defines __add__ and __getitem__; a pandas DataFrame supports df["col"] and len(df); a PyTorch model is called like a function, model(x), because it defines __call__. The rule for your own code: implement the dunders that match what your object is (a container, a number, a value), and you almost never call them directly; you use the syntax, and Python calls them.

hooks.py
class Playlist:
    def __init__(self, songs):
        self.songs = list(songs)

    def __len__(self):
        return len(self.songs)

    def __getitem__(self, i):
        return self.songs[i]

    def __contains__(self, song):
        return song in self.songs

p = Playlist(["intro", "verse", "outro"])
print(len(p), p[0], p[-1], "verse" in p, p[1:])
print([s.upper() for s in p])        # iteration works through __getitem__ (10.1)
print(len(p) == p.__len__())
Output
3 intro outro True ['verse', 'outro']
['INTRO', 'VERSE', 'OUTRO']
True

Defining __getitem__ with integer indexes already makes the object iterable: a for loop falls back to calling p[0], p[1], ... until IndexError. Lesson 10.1 shows the proper iteration protocol, __iter__. Note that dunder methods are looked up on the class, not the instance: assigning p.__len__ = ... on one object does not change what len(p) does (problem 16).

2__repr__ and __str__: how an object prints

Without help, an object prints as <__main__.Money object at 0x7f...>, which tells you nothing in a log or a debugger. Two methods control the text. __repr__ is for developers: it should be unambiguous and, ideally, look like the code that would recreate the object, Money(12.5, 'EUR'). __str__ is for end users: readable, 12.50 EUR. print(x) and str(x) use __str__; the REPL, debuggers, repr(x), the !r conversion in f-strings and the display of objects inside containers use __repr__. If you define only one, define __repr__: str falls back to it, but not the other way round.

repr_str.py
class Money:
    def __init__(self, amount, currency):
        self.amount = amount
        self.currency = currency

    def __repr__(self):
        return f"Money({self.amount!r}, {self.currency!r})"

    def __str__(self):
        return f"{self.amount:.2f} {self.currency}"

m = Money(12.5, "EUR")
print(m)
print(repr(m), f"{m} | {m!r}")
print([m, Money(3, "USD")])           # containers show the repr of their items
Output
12.50 EUR
Money(12.5, 'EUR') 12.50 EUR | Money(12.5, 'EUR')
[Money(12.5, 'EUR'), Money(3, 'USD')]

Use !r for the fields inside __repr__, so strings show their quotes and Money('12.5', 'EUR') (a string amount, probably a bug) is distinguishable from Money(12.5, 'EUR'). A good repr pays for itself the first time you print a list of objects while debugging, and logging libraries and test failure messages rely on it. Keep it free of secrets: an API client's repr should not show its key.

3Equality and hashing

By default, == between two instances of your class compares identity: two separate Money(12.5, "EUR") objects are not equal (2.1). Defining __eq__(self, other) lets you decide what equality means, usually "all the fields that define the value are equal". If other is not something you know how to compare, return the special value NotImplemented (not False, and do not raise): Python then tries the other operand's __eq__, and if that also gives up, falls back to identity. Returning NotImplemented keeps m == "text" working and False, instead of crashing with an AttributeError (problem 6).

Equality is tied to hashing. Sets and dict keys find objects by their __hash__ value first and then confirm with __eq__, so the rule is: objects that compare equal must have equal hashes. To protect you, Python sets __hash__ to None as soon as a class defines __eq__ without __hash__, which makes instances unhashable: putting one in a set raises TypeError (problem 3). If your objects are values that should work in sets and as keys, define __hash__ from the same fields as __eq__, typically hash((self.a, self.b)), and treat those fields as immutable: if a field changes while the object is in a set, the set can no longer find it.

eq_hash.py
class Money:
    def __init__(self, amount, currency):
        self.amount = amount
        self.currency = currency

    def __repr__(self):
        return f"Money({self.amount!r}, {self.currency!r})"

    def __eq__(self, other):
        if not isinstance(other, Money):
            return NotImplemented
        return (self.amount, self.currency) == (other.amount, other.currency)

    def __hash__(self):
        return hash((self.amount, self.currency))

print(a == b, a is b, a == "5 EUR", a != Money(5, "USD"))
print(len({a, b, Money(5, "USD")}), {a: "price"}[b])     # 2 distinct values; b finds a's entry

!= uses __ne__, which by default inverts __eq__, so you rarely define it. Mutable objects whose equality depends on changing state (a conversation, a cache) should usually stay unhashable: equal now does not mean equal later. Dataclasses (11.3) generate __eq__ for you, and @dataclass(frozen=True) generates a matching __hash__ too.

4Ordering

sorted, min, max and < use __lt__ ("less than"), and the other comparisons use __le__, __gt__ and __ge__. Without them, sorting your objects raises TypeError: '<' not supported. The decorator functools.total_ordering fills in the other three from __eq__ and __lt__. As with equality, return NotImplemented for types you cannot compare. For a value type with a natural order (versions, money in one currency, dates), define the ordering by comparing tuples of fields, which compare element by element (4.3).

ordering.py
import functools

@functools.total_ordering
class Version:
    def __init__(self, text):
        self.parts = tuple(int(p) for p in text.split("."))

    def __repr__(self):
        return f"Version({'.'.join(map(str, self.parts))!r})"

    def __eq__(self, other):
        return self.parts == other.parts if isinstance(other, Version) else NotImplemented

    def __lt__(self, other):
        return self.parts < other.parts if isinstance(other, Version) else NotImplemented

    def __hash__(self):
        return hash(self.parts)

versions = [Version(v) for v in ["1.10.0", "1.9.2", "2.0", "1.9.10"]]
print(sorted(versions), max(versions))
print(Version("1.10") > Version("1.9"), "1.10" > "1.9")
Output
[Version('1.9.2'), Version('1.9.10'), Version('1.10.0'), Version('2.0')] Version('2.0')
True False

The last line shows why ordering by the right representation matters: as strings, "1.10" sorts before "1.9", because strings compare character by character (5.1). Comparing tuples of integers gives the order people expect (problem 10). When objects have no single natural order (documents by score, by date, by length), do not define __lt__ at all; pass a key function to sorted instead, which is clearer at the call site.

5Containers and truthiness

An object that holds items can implement the container methods: __len__ for len, __getitem__ for obj[key] (an integer, a slice or a dict-like key: the method receives exactly what is inside the brackets), __setitem__ and __delitem__ for assignment and del, __contains__ for in, and __iter__ for loops (10.1). Each is optional; implement the ones your object should support. When obj[1:3] is used, __getitem__ receives a slice object; returning an instance of your own class keeps the type, as lists and DataFrames do.

Truthiness (if obj:, while obj:, bool(obj)) calls __bool__, and if there is no __bool__, falls back to __len__ (empty means false). Without either, every instance is truthy. Defining __len__ on a container therefore makes empty containers falsy, exactly like lists, which is usually what you want, but can surprise: if result: on an empty result object is false even though the object exists. Use if result is not None: when you mean existence (1.2).

containers.py
class Batch:
    def __init__(self, items):
        self.items = list(items)

    def __repr__(self):
        return f"Batch({self.items!r})"

    def __len__(self):
        return len(self.items)

    def __getitem__(self, key):
        if isinstance(key, slice):
            return Batch(self.items[key])       # slicing keeps the type
        return self.items[key]

    def __contains__(self, item):
        return item in self.items

b = Batch(["a", "b", "c", "d"])
print(len(b), b[0], b[1:3], "c" in b, bool(b), bool(Batch([])))
empty = Batch([])
print("empty is falsy" if not empty else "truthy", empty is not None)
Output
4 a Batch(['b', 'c']) True True False
empty is falsy True

6Arithmetic, NotImplemented and calling

Operators map to methods too: + to __add__, - to __sub__, * to __mul__, @ to __matmul__ (matrix product), abs() to __abs__, unary - to __neg__. For x + y, Python first calls x.__add__(y); if that returns NotImplemented (or does not exist), it calls the reflected method y.__radd__(x). That second chance is what makes 2 * vector work when only the vector knows how to multiply, and it is why sum() needs __radd__: sum starts from 0, so its first step is 0 + first_item, and int does not know your type (problem 12).

arithmetic.py
class Usage:
    def __init__(self, prompt=0, completion=0):
        self.prompt = prompt
        self.completion = completion

    def __repr__(self):
        return f"Usage(prompt={self.prompt}, completion={self.completion})"

    def __add__(self, other):
        if not isinstance(other, Usage):
            return NotImplemented
        return Usage(self.prompt + other.prompt, self.completion + other.completion)

    def __radd__(self, other):
        if other == 0:                      # sum() starts with 0
            return self
        return self.__add__(other)

calls = [Usage(120, 40), Usage(300, 80), Usage(50, 10)]
print(calls[0] + calls[1], sum(calls))
try:
    calls[0] + 5
except TypeError as e:
    print("TypeError:", e)
Output
Usage(prompt=420, completion=120) Usage(prompt=470, completion=130)
TypeError: unsupported operand type(s) for +: 'Usage' and 'int'

Operators should return new objects and leave the operands unchanged, as numbers do; in-place versions (__iadd__ for +=, 2.2) may modify self and return it. Finally, __call__ makes instances callable like functions: scorer(text) runs scorer.__call__(text). A callable object is a function with state and configuration: a scorer with weights, a decorator class that keeps statistics, a PyTorch module (model(x) calls __call__, which runs hooks and then forward).

callable.py
class KeywordScorer:
    def __init__(self, weights):
        self.weights = dict(weights)
        self.calls = 0

    def __call__(self, text):
        self.calls += 1
        words = text.lower().split()
        return sum(self.weights.get(w, 0) for w in words)

    def __repr__(self):
        return f"KeywordScorer({len(self.weights)} weights, {self.calls} calls)"

score = KeywordScorer({"refund": 2, "urgent": 3, "thanks": -1})
docs = ["Thanks for the help", "URGENT refund needed", "refund status"]
print(sorted(docs, key=score, reverse=True), score, callable(score))
Output
['URGENT refund needed', 'refund status', 'Thanks for the help'] KeywordScorer(3 weights, 3 calls) True

solution.py
class Chunk:
    def __init__(self, doc_id, position, text):
        self.doc_id = doc_id
        self.position = position
        self.text = text

    def __eq__(self, other):
        if not isinstance(other, Chunk):
            return NotImplemented
        return (self.doc_id, self.position) == (other.doc_id, other.position)

    def __hash__(self):
        return hash((self.doc_id, self.position))

When a class defines __eq__, Python removes the inherited identity-based hash, because it would violate "equal objects must hash equally": two equal chunks would land in different places in a set. The text is deliberately left out of both, so an edited chunk at the same position counts as the same chunk, which is the identity a vector store uses for upserts. Those identity fields should not be changed while the object is in a set or used as a key.

class Usage:
    def __init__(self, prompt=0, completion=0, cost=0.0):
        self.prompt = prompt
        self.completion = completion
        self.cost = cost

    def __repr__(self):
        return f"Usage(prompt={self.prompt}, completion={self.completion}, cost={self.cost})"

    def __add__(self, other):
        if not isinstance(other, Usage):
            return NotImplemented
        return Usage(self.prompt + other.prompt, self.completion + other.completion, self.cost + other.cost)

    def __radd__(self, other):
        if other == 0:
            return self
        return self.__add__(other)

    def __eq__(self, other):
        if not isinstance(other, Usage):
            return NotImplemented
        return (self.prompt, self.completion) == (other.prompt, other.completion) and round(self.cost - other.cost, 9) == 0

    def total(self):
        return self.prompt + self.completion

    def __bool__(self):
        return bool(self.prompt or self.completion or self.cost)

sum([a, b, c]) computes ((0 + a) + b) + c. The first step calls int.__add__(0, a), which returns NotImplemented, so Python tries a.__radd__(0); returning self for 0 lets the rest use __add__. Every addition builds a new Usage, leaving a and b unchanged, as numbers behave. Floats such as 0.002 + 0.005 are not exactly 0.007 (1.1), so the cost comparison tolerates tiny differences. With __bool__, an empty usage is falsy, convenient for "skip if nothing was spent". This is the kind of object SDKs return as response.usage, and summing it over a run gives the total bill.

class Batch:
    def __init__(self, items):
        self._items = list(items)

    def __len__(self):
        return len(self._items)

    def __getitem__(self, key):
        if isinstance(key, slice):
            return Batch(self._items[key])
        return self._items[key]

    def __iter__(self):
        yield from self._items

    def __contains__(self, item):
        return item in self._items

    def __repr__(self):
        return f"Batch({len(self)} items)"

    def split(self, n):
        return [self[i:i + n] for i in range(0, len(self), n)]

Each dunder connects one piece of syntax to the internal list: len, indexing, slicing, for and in all work as they would on a list, and slicing returns a Batch so the type survives, like slicing a DataFrame returns a DataFrame. split is written with the class's own slicing, a small sign that the protocol is complete. Copying the input list protects the batch from later appends, though the dicts inside are still shared (2.3). __len__ also makes an empty batch falsy. PyTorch's Dataset is this same idea: __len__ plus __getitem__, which is all a DataLoader needs.

@functools.total_ordering
class Checkpoint:

        self.name = name
        self.version = tuple(int(p) for p in name.split("-v")[1].split("."))

import math

class Vector:
    def __init__(self, *components):
        self._c = tuple(float(x) for x in components)

    def __repr__(self):
        return f"Vector({', '.join(map(str, self._c))})"

    def __len__(self):
        return len(self._c)

    def __iter__(self):
        return iter(self._c)

    def __getitem__(self, i):
        return self._c[i]

    def __eq__(self, other):
        if not isinstance(other, Vector):
            return NotImplemented
        return self._c == other._c

    def __hash__(self):
        return hash(self._c)

    def _check(self, other):
        if len(self) != len(other):
            raise ValueError(f"length mismatch: {len(self)} vs {len(other)}")

    def __add__(self, other):
        if not isinstance(other, Vector):
            return NotImplemented
        self._check(other)
        return Vector(*(x + y for x, y in zip(self, other)))

    def __sub__(self, other):
        if not isinstance(other, Vector):
            return NotImplemented
        self._check(other)
        return Vector(*(x - y for x, y in zip(self, other)))

    def __mul__(self, k):
        if not isinstance(k, (int, float)):
            return NotImplemented
        return Vector(*(x * k for x in self))

    __rmul__ = __mul__

    def __matmul__(self, other):
        if not isinstance(other, Vector):
            return NotImplemented
        self._check(other)
        return sum(x * y for x, y in zip(self, other))

    def __abs__(self):
        return math.sqrt(self @ self)

    def cosine(self, other):
        denom = abs(self) * abs(other)
        if denom == 0:
            raise ValueError("cosine is undefined for a zero vector")
        return (self @ other) / denom

Each operator is one dunder, and together they make the class read like the mathematics: a @ b / (abs(a) * abs(b)) is the cosine similarity used everywhere in retrieval. __rmul__ = __mul__ reuses the same function for 2 * a, valid because scalar multiplication is commutative. Storing components in a tuple makes the vector immutable, so a __hash__ is safe and every operator returns a new vector. Returning NotImplemented for strings lets Python raise the standard TypeError, while a length mismatch is a value problem and raises ValueError. __iter__ makes zip(self, other) work on vectors directly. NumPy does all of this in C on arrays of any shape, which is why real code uses it; implementing it once shows what a @ b means.

class Span:
    def __init__(self, start, end, label):
        if start > end:
            raise ValueError("start must not exceed end")
        self.start = start
        self.end = end
        self.label = label

    def __repr__(self):
        return f"Span({self.start}, {self.end}, {self.label!r})"

    def _key(self):
        return (self.start, self.end, self.label)

    def __eq__(self, other):
        if not isinstance(other, Span):
            return NotImplemented
        return self._key() == other._key()

    def __hash__(self):
        return hash(self._key())

    def __lt__(self, other):
        if not isinstance(other, Span):
            return NotImplemented
        return (self.start, self.end) < (other.start, other.end)

    def __len__(self):
        return self.end - self.start

Four bugs. __eq__ compared only start, so spans with different ends and labels were "equal". Hint 1Open a hint

Hint 2Open a hint

Evict with next(iter(self._data)), the oldest key.

SolutionShow the solution and why
solution.py
class LRUDict:
    def __init__(self, maxsize):
        if maxsize < 1:
            raise ValueError("maxsize must be at least 1")
        self.maxsize = maxsize
        self._data = {}
        self.evicted = []

    def __getitem__(self, key):
        value = self._data.pop(key)
        self._data[key] = value
        return value

    def __setitem__(self, key, value):
        if key in self._data:
            del self._data[key]
        elif len(self._data) >= self.maxsize:
            oldest = next(iter(self._data))
            del self._data[oldest]
            self.evicted.append(oldest)
        self._data[key] = value

    def __delitem__(self, key):
        del self._data[key]

    def __contains__(self, key):
        return key in self._data

    def __len__(self):
        return len(self._data)

    def __iter__(self):
        return iter(list(self._data))

    def __repr__(self):
        return f"LRUDict({self._data!r}, maxsize={self.maxsize})"

Because dicts preserve insertion order, "most recently used" can be represented as "inserted last": a read pops the key and reinserts it, and the first key in iteration order is always the least recently used one, which is what gets evicted. pop raises KeyError for a missing key, so d["zzz"] behaves exactly like a dict. Updating an existing key removes it first so it moves to the end without triggering an eviction. __contains__ deliberately does not reorder, so checking membership does not change what gets evicted. __iter__ iterates a snapshot list, so a loop that reads values (and therefore reorders keys) does not break iteration. The standard library offers collections.OrderedDict.move_to_end for the same job, and functools.lru_cache (8.3) uses a linked list internally.

17. What is the difference between __repr__ and __str__?

SolutionModel answer

__repr__ gives the developer-facing representation: unambiguous, ideally valid Python that recreates the object (Money(12.5, 'EUR')), used by the REPL, debuggers, repr(), !r in f-strings, logging of objects and the display of items inside containers. __str__ gives the user-facing text (12.50 EUR), used by print, str() and plain f-string interpolation. If only __repr__ is defined, str() falls back to it; the reverse is not true, so always define __repr__ first. A good repr makes debugging and test failure messages useful; it should never include secrets such as API keys.

Interview

18. Why does defining __eq__ make a class unhashable, and how should you define __hash__?

SolutionModel answer

Sets and dicts locate objects by hash and then confirm with ==, which only works if equal objects have equal hashes. The default __hash__ is based on identity, which is consistent with the default identity-based __eq__. Once you define value-based equality, the identity hash would violate the rule (two equal objects in different buckets), so Python sets __hash__ = None, making instances unhashable, rather than letting sets silently misbehave. If the objects are values that belong in sets or as keys, define __hash__ from exactly the fields used in __eq__, usually hash((self.a, self.b)), and treat those fields as immutable, since changing them while the object is stored corrupts the container. Mutable objects whose equality changes over time should stay unhashable. @dataclass(frozen=True) generates consistent __eq__ and __hash__.

19. Explain Python's data model and why it matters for libraries like NumPy, pandas and PyTorch.

SolutionModel answer

The data model is the set of special methods through which syntax and built-ins operate on objects: len() calls __len__, x[k] calls __getitem__, for uses __iter__, in uses __contains__, operators call __add__, __mul__, __matmul__ and their reflected and in-place versions, comparisons call __eq__ and __lt__, truthiness calls __bool__ or __len__, with uses __enter__ and __exit__, and calling uses __call__. Operator methods return NotImplemented to let the other operand try, which is how mixed-type arithmetic works. Because these protocols are duck-typed, any object implementing them works with all the code written against them. That is how NumPy arrays support a + b, slicing and broadcasting with plain syntax, how pandas offers df["col"], len(df) and boolean masks, and how PyTorch tensors overload arithmetic and modules are called as model(x). It also explains some surprises: if df: raises an error because pandas makes __bool__ ambiguous on purpose, and a == b on arrays returns an array rather than a boolean.

Recap

  • Dunder methods connect syntax and built-ins to your objects: len to __len__, [] to __getitem__, + to __add__, == to __eq__, calling to __call__.
  • Always define __repr__ (developers, containers, !r); add __str__ for user-facing text.
  • __eq__ and __hash__ go together: hash the same fields you compare, keep them immutable, and return NotImplemented for other types.
  • Order with __lt__ (plus functools.total_ordering) on the right representation, such as tuples of ints; otherwise sort with a key.
  • Containers: __len__, __getitem__ (slices included), __contains__, __iter__; truthiness falls back to __len__. __radd__ makes sum work.
