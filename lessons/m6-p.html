1How to use this page

For each problem, decide first whether the result must be stored or only streamed. If you need the result more than once, need its length, need to index it, or will return it to a caller who expects a list, build it: a list, dict or set comprehension (6.1, 6.2). If it is consumed once, may be large, or may be stopped early, stream it: a generator function or expression (6.3), chained with itertools (6.4). Then check the traps of each choice: a comprehension that repeats a key or shares a mutable value, a generator that is consumed twice or validates too late.

The problems are mixed on purpose, from easy to hard. The mini project at the end combines every lesson in one realistic program.

Write turn_index(conversations) where conversations maps conversation id to a list of messages (dicts with "role"). Return a list of (conversation_id, turn_number, role) tuples, turns numbered from 1 within each conversation, conversations in sorted id order, using one comprehension.

HintOpen a hint

Two for clauses: the outer over sorted(conversations.items()), the inner over enumerate(messages, start=1).

SolutionShow the solution and why
solution.py
def turn_index(conversations):
    return [
        (cid, n, msg["role"])
        for cid, messages in sorted(conversations.items())
        for n, msg in enumerate(messages, start=1)
    ]

The outer for walks conversations in sorted order, and the inner one numbers the messages of each; the inner enumerate restarts at 1 for every conversation because it is created anew for each outer item. An empty conversation contributes nothing. This flat index is the shape you load into a DataFrame to analyse conversation lengths or role patterns.

The generator is exhausted by the count. Build the list once and take its length.

SolutionShow the solution and why
solution.py
def valid_ids(rows):
    ids = [r["id"] for r in rows if r.get("text", "").strip()]
    return len(ids), ids

Counting consumed the generator, so the comprehension that followed got nothing (6.3). When you need a result twice, store it once: the list gives both the ids and, through len, the count, in one pass over rows, which also makes it work when rows itself is an iterator, as in the second test.

5. K-fold split indices

Write a generator kfold(n, k) yielding (train, val) pairs of index lists for k-fold cross-validation without shuffling, like scikit-learn's KFold: the indices 0..n-1 are cut into k consecutive folds, the first n % k folds one item larger than the rest; each fold is the validation set once, and the other indices, in order, are the training set. Hint 1Open a hint

Fold sizes: [n // k + (1 if i < n % k else 0) for i in range(k)]. Walk them with a running start.

Hint 2Open a hint

Validate in a normal function and return an inner generator, so bad arguments fail at the call (6.3).

SolutionShow the solution and why
solution.py
def kfold(n, k):
    if not 2 <= k <= n:
        raise ValueError("need 2 <= k <= n")
    return _folds(n, k)


def _folds(n, k):
    sizes = [n // k + (1 if i < n % k else 0) for i in range(k)]
    start = 0
    for size in sizes:
        val = list(range(start, start + size))
        train = [i for i in range(n) if not start <= i < start + size]
        yield train, val
        start += size

The fold sizes come from integer division with the remainder spread over the first folds, so sizes differ by at most one and add up to n. Each validation fold is a range slice of consecutive indices, and the training set is every other index, kept in order by a filtered comprehension. Yielding folds one at a time lets a training loop start the first fold immediately. The wrapper makes invalid k fail at the call, not at the first next. Real cross-validation usually shuffles first (with a fixed seed) or stratifies by label, so that each fold has a similar class mix.

Write top_per_source(results, k) returning a dict from source to the texts of its k highest-scoring results, best first, with sources in sorted order. Results are dicts with "source", "text" and "score", in any order. Use one pass to group and heapq.nlargest per group.

HintOpen a hint

Group with a defaultdict(list), then a dict comprehension over sorted(groups.items()) with heapq.nlargest(k, items, key=...).

SolutionShow the solution and why
solution.py
import heapq
from collections import defaultdict

def top_per_source(results, k):
    groups = defaultdict(list)
    for r in results:
        groups[r["source"]].append(r)
    return {
        source: [r["text"] for r in heapq.nlargest(k, items, key=lambda r: r["score"])]
        for source, items in sorted(groups.items())
    }

Grouping is accumulation, so it is a loop with a defaultdict (6.2); the comprehension then turns each group into its summary. heapq.nlargest returns the k best in descending order without sorting the whole group, which matters when groups are large and k is small (4.2). Sorting the items of groups fixes the source order. Limiting results per source is a common RAG step, to stop one long document from filling the whole context.

HintOpen a hint

Steps: strip, drop blank and comment lines, take the last tab field lower-cased, drop short ones, take n with islice.

SolutionShow the solution and why
solution.py
from itertools import islice

def first_queries(lines, n):
    stripped = (line.strip() for line in lines)
    content = (line for line in stripped if line and not line.startswith("#"))
    queries = (line.split("\t")[-1].lower() for line in content)
    long_enough = (q for q in queries if len(q) >= 3)
    return list(islice(long_enough, n))

Each line of the pipeline does one job and has a name that says what it holds, which replaces the continue and break bookkeeping. Nothing runs until islice pulls, and it stops after n results, so the early exit of the original loop is kept: the pipeline never reads past the nth query. Each step can now be reused or tested on its own. For a very short function, the original loop is also fine; the pipeline style pays off as steps grow.

10. Stop sequences across streamed pieces

When a model ignores the API's stop parameter, you apply the stop sequence yourself while streaming. Write a generator until_stop(deltas, stop) that yields text from the stream, never yielding any part of stop or anything after it, even when stop is split across pieces. Hold back only as much text as could be the start of stop; yield everything else as early as possible. If the stream ends without the stop, yield what was held back.

Hint 1Open a hint

Keep a buffer. After adding each piece, if stop is in the buffer, yield the part before it and return.

Hint 2Open a hint

Otherwise, find the longest suffix of the buffer that is a prefix of stop; yield everything before that suffix and keep the suffix.

SolutionShow the solution and why
solution.py
def until_stop(deltas, stop):
    buffer = ""
    for delta in deltas:
        buffer += delta
        cut = buffer.find(stop)
        if cut != -1:
            if cut:
                yield buffer[:cut]
            return
        keep = 0
        for size in range(min(len(stop) - 1, len(buffer)), 0, -1):
            if stop.startswith(buffer[-size:]):
                keep = size
                break
        safe = buffer[:len(buffer) - keep]
        if safe:
            yield safe
        buffer = buffer[len(buffer) - keep:]
    if buffer:
        yield buffer

Checking each piece alone misses a stop that is split across pieces, like "\nObs" + "ervation:". Buffering everything would work but defeats streaming. The middle ground is to hold back only a suffix that could still grow into the stop: the longest end of the buffer that is a start of stop, at most len(stop) - 1 characters. Everything before it can never become part of a stop, so it is yielded at once, which the next(g) test checks. When the held text turns out not to be the stop ("ST" followed by "x"), it is released with the next piece. Agent frameworks do exactly this, both for custom stop sequences and to hide markers such as "Observation:" from users.

import random
from collections import defaultdict


def stratified_sample(records, per_label, seed):
    rng = random.Random(seed)
    buckets = defaultdict(list)
    for r in records:
        buckets[r["label"]].append(r)
    return {
        label: rng.sample(items, min(per_label, len(items)))
        for label, items in sorted(buckets.items())
    }

Three bugs from this module. The set comprehension that collected labels consumed a generator input, so the grouping loop saw nothing (6.3); grouping in a single pass with a defaultdict needs only one walk. dict.fromkeys(labels, []) gave every label the same list, so each "bucket" held every record (6.2). And iterating a dict built from a set of strings follows hash order, which varies between processes; besides breaking the required sorted order, it made the sample itself irreproducible, because the shared random generator is consumed label by label, so a different label order gives different samples for the same seed. Sorting the labels fixes both. min(per_label, len(items)) keeps rng.sample from failing on rare labels.

Interview

13. How would you process a 20 GB CSV file in Python on a machine with 8 GB of RAM?

SolutionModel answer

Stream it instead of loading it. With the standard library, open the file with an explicit encoding and pass it to csv.reader or csv.DictReader, which yields one row at a time; build the processing as a pipeline of generators (parse, validate, transform, filter) and aggregate incrementally with Counter, defaultdict or running totals, so memory depends on the size of the aggregates, not the file. If the output must be written, write as you go. With pandas, use read_csv(..., chunksize=100_000) (or usecols and dtype to shrink each chunk) and combine per-chunk results. For heavier analytics, tools like Polars (lazy scan_csv with a streaming engine) or DuckDB query the file directly without loading it, and converting it once to Parquet makes later reads much faster. Watch for steps that need all the data at once (sorting, exact distinct counts, joins); they need external sorting, approximate algorithms or a database.

Interview

14. What are the trade-offs between eager and lazy evaluation in a data pipeline?

SolutionModel answer

Eager code (lists, comprehensions, DataFrames) computes everything at each step: it is simple to inspect and debug, results can be reused, indexed and counted, and errors appear at the step that caused them, but memory grows with the data and nothing is available until the whole step is done. Lazy code (generators, iterators, lazy query engines) computes items only when asked: memory stays constant, the first results arrive immediately, early exits skip work, and infinite or streaming sources work, but results are one-shot, have no length, and errors surface where the data is consumed, possibly far from the code that caused them; debugging needs care because inspecting a generator consumes it. Laziness also lets an engine optimise the whole plan (Polars, Spark, SQL databases push filters down and skip columns). A practical pattern is lazy streaming for the large, linear part of a pipeline, and eager materialisation for small results that are reused, with validation at the boundaries so errors are caught close to their source.

15. Evaluate a classifier on a stream

Implement evaluate(lines, predict, labels, batch_size). lines is an iterable of JSON lines with "id", "text" and "label"; predict(texts) returns one reply string per text; labels is the list of valid labels. Return a Report named tuple:

  • invalid: line numbers (from 1) of lines that are not valid JSON, lack one of the three fields, or have a label not in labels. Blank lines are skipped silently. Invalid lines are not evaluated.
  • calls: how many times predict was called. Valid records are sent in batches of batch_size, in file order.
  • unparsed: ids of records whose reply could not be parsed, in file order. A reply is parsed by taking the text after its last : (or the whole reply if there is none), stripped and case-folded; it must then equal a label (compared case-folded). Unparsed records count as wrong.
  • accuracy: correct predictions divided by the number of valid records, rounded to 4 decimals (0.0 if none).
  • confusion: {gold: {predicted: count}} for parsed predictions, with every label from labels (sorted) in both levels.
  • per_label: {label: {"precision": ..., "recall": ..., "support": ...}} for every label, sorted. Support is the number of valid records with that gold label; recall is correct ones over support; precision is correct ones over parsed predictions of that label. Round to 3 decimals; 0.0 when dividing by zero.

It must be lazy: if the caller only needs the first batch evaluated, the harness must not read the whole file before calling predict (the tests check the order of reads and calls).

import json
from collections import Counter
from itertools import batched
from typing import NamedTuple


class Report(NamedTuple):
    accuracy: float
    per_label: dict
    confusion: dict
    invalid: list
    unparsed: list
    calls: int


def _ratio(num, den):
    return round(num / den, 3) if den else 0.0


def _records(lines, canonical, invalid):
    for lineno, line in enumerate(lines, start=1):
        if not line.strip():
            continue
        try:
            rec = json.loads(line)
            gold = canonical.get(str(rec["label"]).casefold())
            rid, text = rec["id"], rec["text"]
        except (json.JSONDecodeError, KeyError, TypeError):
            invalid.append(lineno)
            continue
        if gold is None:
            invalid.append(lineno)
            continue
        yield rid, text, gold


def _parse(reply, canonical):
    return canonical.get(reply.rsplit(":", 1)[-1].strip().casefold())


def evaluate(lines, predict, labels, batch_size):
    canonical = {label.casefold(): label for label in labels}
    classes = sorted(labels)
    invalid, unparsed, pairs = [], [], []
    calls = 0
    for batch in batched(_records(lines, canonical, invalid), batch_size):
        replies = predict([text for _, text, _ in batch])
        calls += 1
        for (rid, _, gold), reply in zip(batch, replies, strict=True):
            pred = _parse(reply, canonical)
            if pred is None:
                unparsed.append(rid)
            pairs.append((gold, pred))

    counts = Counter(p for p in pairs if p[1] is not None)
    confusion = {g: {p: counts[(g, p)] for p in classes} for g in classes}
    correct = sum(confusion[c][c] for c in classes)
    support = Counter(g for g, _ in pairs)
    predicted = Counter(p for _, p in pairs if p is not None)
    per_label = {
        c: {"precision": _ratio(confusion[c][c], predicted[c]),
            "recall": _ratio(confusion[c][c], support[c]),
            "support": support[c]}
        for c in classes
    }
    accuracy = round(correct / len(pairs), 4) if pairs else 0.0
    return Report(accuracy, per_label, confusion, invalid, unparsed, calls)

Every lesson of the module has a job here:

  • Generators (6.3): _records streams the file, numbering lines with enumerate(..., start=1), skipping blank lines, and reporting bad ones through the invalid list instead of stopping the run. Nothing is read until the batches ask for records.
  • Lazy pipelines (6.4): batched pulls exactly batch_size records before each predict call, which is why the first call happens after reading only the first few lines, as the read-order test checks. zip(..., strict=True) fails loudly if the model returns the wrong number of replies.
  • Dict comprehensions (6.2): canonical maps case-folded labels back to their official spelling, which handles "HAM" in the data and "label: Ham" in a reply; the confusion matrix and per-label metrics are nested comprehensions over the sorted labels, so every label appears in a fixed order, including ones with no examples.
  • List comprehensions and generator expressions (6.1): the texts of each batch, and the filtered pairs fed into each Counter.

Unparsed replies ("Label: phishing" is not a valid label) count against accuracy but are left out of the confusion matrix and of precision, which is the usual convention, and they are reported by id so you can look at them: they often reveal a prompt that needs a clearer label list. The pairs list grows with the dataset, but it holds two short strings per record; for a really large evaluation, the Counters could be updated inside the loop instead. This is the core of tools like OpenAI's evals, Promptfoo or a scikit-learn classification_report run on LLM output.

Recap

  • Store or stream: build lists, dicts and sets when results are reused or small; use generators and itertools when consumed once, large or stopped early.
  • Comprehensions transform and filter; grouping and counting accumulate (defaultdict, Counter), then comprehensions summarise.
  • Watch the collisions: repeated dict keys keep the last value, fromkeys shares one mutable value, sets of strings have no stable order.
  • Generators are one-shot and run late: consume once, validate in a wrapper, keep resources open inside the generator.
  • Pipelines of small lazy steps (islice, batched, accumulate, groupby on sorted data) keep memory flat and results early.
