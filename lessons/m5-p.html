1How to use this page

Text problems usually mix several layers, and most bugs come from mixing them up. Before you write code, ask three questions. Bytes or text? Anything from a file, socket or API arrives as bytes and must be decoded once, at the edge, with a known encoding (5.4). Fixed text or a pattern? For fixed text, string methods are faster and clearer (5.1, 5.2); for patterns, use a regex (5.5). Data or display? Keep values as numbers and dates while you compute, and format them only at the end, with a format spec (5.3).

The problems are not grouped by lesson on purpose: deciding which tool fits is part of each one. The last problem is a mini project that combines every lesson in one realistic pipeline.

2. Cut a reply at the first stop sequence

LLM APIs accept stop sequences: generation ends just before the first one that appears. Write apply_stops(text, stops) that returns text cut before the earliest occurrence of any stop string (the stop itself is removed), or the whole text if none appears.

TestsThe 4 checks Run tests uses

assert apply_stops(reply, ["Nope"]) == reply

HintOpen a hint

text.find(stop) returns -1 when the stop is absent. Keep the smallest index that is not -1.

SolutionShow the solution and why
solution.py
def apply_stops(text, stops):
    positions = [i for stop in stops if (i := text.find(stop)) != -1]
    return text[:min(positions)] if positions else text

The cut must happen at the earliest position over all stops, not at the first stop in the list: "User:" appears later in the text than "\nObservation:", even though it is listed first. find returns -1 for a missing stop, and -1 would slice off the last character, so it has to be filtered out (5.1). The walrus operator keeps each find to one call. Agent frameworks apply exactly this when a model ignores the API's stop parameter, or when the stop has to be checked after streaming.

Hint 1Open a hint

First find the call line: re.search(r"^CALL (\w+)\((.*)\)\s*$", text, re.M).

Hint 2Open a hint

Then the arguments: re.findall(r'(\w+)=(?:"([^"]*)"|(-?\d+))', args) gives (key, string, number) tuples, with one of the last two empty.

SolutionShow the solution and why
solution.py
import re

CALL = re.compile(r"^CALL (\w+)\((.*)\)\s*$", re.M)
ARG = re.compile(r'(\w+)=(?:"([^"]*)"|(-?\d+))')

def parse_call(text):
    m = CALL.search(text)
    if not m:
        return None
    name, arg_text = m.groups()
    args = {}
    for key, string, number in ARG.findall(arg_text):
        args[key] = int(number) if number else string
    return name, args

Splitting the arguments on , would break on "refund policy, EU", so the argument pattern matches either a quoted string or an integer; [^"]* cannot run past the closing quote. With alternative groups, findall returns a tuple with an empty string for the group that did not take part, which tells you which kind of value you got (5.5). re.M makes ^ and $ work per line, so the call can sit in the middle of the reply. Modern APIs return tool calls as JSON (tool calling), which removes this parsing; you still meet text formats like this in older agents and local models.

6. Labels that do not group

Labels exported from three annotation tools do not group correctly: "\ufeffSpam", "ｓｐａｍ ", "SPAM" and "spam" should all be one class, and "Straße" should equal "STRASSE". Fix normalize_label.

Hint 1Open a hint

strip() does not remove the byte order mark \ufeff or the zero-width space \u200b: they are not whitespace.

Hint 2Open a hint

NFKC turns full-width letters into normal ones and combines e + accent into one é; casefold() maps ß to ss.

SolutionShow the solution and why
solution.py
import unicodedata

INVISIBLE = dict.fromkeys(map(ord, "\ufeff\u200b\u200c\u200d"))

def normalize_label(label):
    label = unicodedata.normalize("NFKC", label).translate(INVISIBLE)
    return label.strip().casefold()

Each label fails for a different reason. The BOM and the zero-width space are format characters, not whitespace, so strip leaves them; translate with a dict mapping their code points to None deletes them (5.2). The full-width letters are different code points from spam, and NFKC maps these "compatibility" characters to the plain ones, while also composing e + combining accent into a single é (5.4). lower() keeps ß, while casefold() maps it to ss, which is the right tool for caseless comparison. Unnormalised labels silently split one class into several, which lowers per-class counts and can wreck a classifier's metrics.

SolutionShow the solution and why
solution.py
def build_prompt(question, chunks):
    sources = "".join(
        f"[{i}] {c['source']}: {c['text'].strip()}\n" for i, c in enumerate(chunks, start=1)
    )
    return f"Answer using only the sources.\n\n{sources}\nQuestion: {question}\nAnswer:"

enumerate(..., start=1) replaces the manual counter, the f-string replaces both the + chains and str(i), and join builds the block in one pass instead of copying the growing prompt on every iteration (5.1). Each source line keeps its own trailing newline, which is why an empty list still gives exactly the same text as the original. The old % formatting line had a latent trap: had the template itself contained a literal % (like "50% off"), % formatting would raise; the f-string has no such issue (5.3).

10. Highlight search terms

Search results show the matched terms highlighted. Write highlight(text, terms) that wraps every whole-word, case-insensitive occurrence of any term in [[ and ]], keeping the original casing. Terms may contain regex characters (C++) and may overlap (refund and refund policy): prefer the longest term at each position.

TestsThe 3 checks Run tests uses

    "Our [[Refund policy]]: refunds differ, but a [[refund policy]] exists. [[C++]] and [[c++]] too.")
assert highlight("abc", []) == "abc"
assert highlight("a.b axb", ["a.b"]) == "[[a.b]] axb"
Hint 1Open a hint

Escape each term with re.escape, sort them longest first, and join with | (the engine takes the first alternative that matches, 5.5).

Hint 2Open a hint

Use (?<!\w)(?:...)(?!\w) for whole words, since \b fails next to +. Replace with r"[[\g<0>]]" to keep the casing.

SolutionShow the solution and why
solution.py
import re

def highlight(text, terms):
    if not terms:
        return text
    alternatives = "|".join(re.escape(t) for t in sorted(terms, key=len, reverse=True))
    pattern = re.compile(rf"(?<!\w)(?:{alternatives})(?!\w)", re.IGNORECASE)
    return pattern.sub(r"[[\g<0>]]", text)

Three regex facts from 5.5 meet here. Alternation takes the first alternative that matches, so sorting longest first makes refund policy win over refund. re.escape stops C++ (one or more C's, twice) and a.b (. is any character) from acting as patterns, which the third test checks. And \b would fail after ++, because there is no word boundary between + and a space, so lookarounds express "not inside a word" instead. \g<0> puts back the matched text exactly as it appeared, so the casing is kept. With no terms, the pattern would be empty and match everywhere, so that case returns early. refunds is not highlighted because (?!\w) rejects the s.

11. Read the code: a streaming reader that breaks on accents

LLM APIs stream replies as server-sent events: lines like data: {"delta": "Hi"}, ending with data: [DONE], delivered as arbitrary chunks of bytes. This reader works in testing but crashes in production with a UnicodeDecodeError, sometimes loses events, and sometimes never stops at [DONE]. Read it, find the bugs and fix them.

TestsThe 4 checks Run tests uses
body = 'data: {"delta": "Caf\u00e9 "}\r\ndata: {"delta": "na\u00efve"}\r\n\r\ndata: [DONE]\r\ndata: {"delta": "x"}\r\n'
raw = body.encode("utf-8")
cut = raw.index("é".encode()) + 1
chunks = [raw[:cut], raw[cut:40], raw[40:]]
assert read_stream(chunks) == "Café naïve"
assert read_stream([raw]) == "Café naïve"
assert read_stream([raw[i:i + 1] for i in range(len(raw))]) == "Café naïve"
assert read_stream([b'data: {"delta": "ok"}\n']) == "ok"
Hint 1Open a hint

A chunk can end in the middle of the two bytes of é, so decoding chunk by chunk fails. It can also end in the middle of a line.

Hint 2Open a hint

Keep a bytes buffer: append each chunk, and while it contains b"\n", split off one complete line and decode only that. In UTF-8, the byte \n never appears inside a multi-byte character (5.4).

Hint 3Open a hint

Servers may end lines with \r\n, so remove a trailing \r before comparing with [DONE].

SolutionShow the solution and why
solution.py
import json


def read_stream(chunks):
    """Return the concatenated deltas from a stream of byte chunks."""
    parts = []
    buffer = b""
    for chunk in chunks:
        buffer += chunk
        while b"\n" in buffer:
            raw_line, buffer = buffer.split(b"\n", 1)
            line = raw_line.decode("utf-8").rstrip("\r")
            if not line.startswith("data: "):
                continue
            payload = line[len("data: "):]
            if payload == "[DONE]":
                return "".join(parts)
            parts.append(json.loads(payload)["delta"])
    return "".join(parts)

Three bugs, all invisible with small ASCII test streams. Decoding per chunk: the network splits bytes wherever it likes, so a chunk can end after the first byte of é (c3), and decoding it alone raises. Lines across chunks: the end of one chunk and the start of the next were treated as two separate lines, so half-lines were dropped (or failed in json.loads). Buffering bytes and decoding only complete lines fixes both, and it is safe because in UTF-8 every byte of a multi-byte character is 128 or above, so the byte 0x0a (\n) can only ever be a real newline (5.4). \r\n line endings: "[DONE]\r" is not "[DONE]", so the reader kept going and appended the x sent after it (json.loads tolerated the \r as whitespace, which hid the problem). Real SDKs do exactly this buffering; codecs.getincrementaldecoder is the general tool when the text has no convenient delimiter.

12. Extract code blocks from a reply

Write code_blocks(markdown) returning a list of (language, code) for every fenced code block in a model's reply. A fence is three backticks at the start of a line, optionally followed by a language name, then the code, then a closing line of three backticks. language is None when missing; code excludes the fence lines and the final newline before the closing fence.

TestsThe 3 checks Run tests uses
f = "`" * 3
reply = f"Try this:\n{f}python\nx = 1\nprint(x)\n{f}\nand run:\n{f}\npip install x\n{f}\nInline {f} is not a fence."
assert code_blocks(reply) == [("python", "x = 1\nprint(x)"), (None, "pip install x")]
assert code_blocks("no code") == []
assert code_blocks(f"{f}sql\nSELECT 1;\n\nSELECT 2;\n{f}") == [("sql", "SELECT 1;\n\nSELECT 2;")]
Hint 1Open a hint

Use re.M so ^ and $ match at line starts and ends, and re.S so the code part can span lines; keep the code part lazy.

Hint 2Open a hint

The opening line is three backticks, then an optional group of word characters for the language, then a newline.

SolutionShow the solution and why
solution.py
import re

FENCE = re.compile(r"^`{3}(\w+)?[ \t]*\n(.*?)\n`{3}[ \t]*$", re.M | re.S)

def code_blocks(markdown):
    return [(lang or None, code) for lang, code in FENCE.findall(markdown)]

re.M anchors the fences at line starts, which is what rejects the inline backticks at the end of the reply. re.S lets the lazy (.*?) cross newlines, and laziness makes it stop at the first closing fence, so two blocks stay two matches (5.5). An optional group that did not take part comes back from findall as an empty string, so lang or None converts it. The [ \t]* parts allow trailing spaces after a fence, which models produce. This regex does not handle nested fences or fences of four backticks; a Markdown parser such as markdown-it-py does, and is worth it when the replies come from users.

Interview

13. What is the difference between str and bytes, and where should encoding and decoding happen in a program?

SolutionModel answer

A str is a sequence of Unicode code points: text, independent of how it is stored. bytes is a sequence of numbers from 0 to 255: what files, sockets and APIs actually carry. Encoding (str.encode) turns text into bytes using an encoding such as UTF-8; decoding (bytes.decode) does the reverse, and needs to know the encoding that was used. The rule is the "Unicode sandwich": decode once, at the edges where data comes in, work with str everywhere inside, and encode once where data goes out, always naming the encoding (open(..., encoding="utf-8")), because the platform default differs between machines. Mixing them causes the classic bugs: TypeError when combining str and bytes, mojibake from decoding with the wrong encoding, and UnicodeDecodeError when a multi-byte character is split across chunks.

Interview

14. You need to clean and normalise the text of 10 million rows before training a model. How do you make it fast?

SolutionModel answer

First, measure on a sample, since text cleaning is usually dominated by a few slow steps. Then remove per-character Python loops: use C-level operations such as str.translate for character deletion and mapping, split/join for whitespace, and compiled regexes for patterns, combining several substitutions into one pass where possible. Avoid building strings with += in loops. Use vectorised column methods (pandas .str accessor, or Polars, whose string functions run in Rust and in parallel) instead of apply with a Python function per row. Process the data in chunks or as a stream so memory stays bounded, and parallelise across processes (for example multiprocessing or a Polars or Spark job) because a single Python process uses one core. Cache the result to Parquet so the cleaning runs once, and keep the cleaning function identical for training and serving, so the model sees the same text in production.

16. Clean and chunk a document

Implement prepare(doc_id, raw, max_chars), where raw is bytes. Return an Ingested named tuple with chunks (a list of Chunk(id, text)), replaced (how many undecodable bytes were replaced) and redacted (how many emails were redacted). The steps, in order:

  • Decode as UTF-8, dropping a leading byte order mark, replacing invalid bytes with \ufffd (count them).
  • Normalise with NFKC, then delete control and format characters (Unicode categories Cc and Cf), but keep whitespace such as \n and \t.
  • Redact email addresses as [EMAIL] (count them).
  • Paragraphs: split on blank lines (a line break, optional spaces or tabs, another line break, and so on). Inside each paragraph, collapse all whitespace runs to one space and strip. Drop empty paragraphs.
  • Sentences: split each paragraph after ., ! or ? followed by whitespace.
  • Chunks: pack consecutive sentences of one paragraph into chunks of at most max_chars characters, joined by one space; never cross a paragraph. A single sentence longer than max_chars is cut into pieces of max_chars.
  • Ids: f"{doc_id}-{n:03d}", numbered from 1 across the whole document.

import re
import unicodedata
from typing import NamedTuple


class Chunk(NamedTuple):
    id: str
    text: str


class Ingested(NamedTuple):
    chunks: list
    replaced: int
    redacted: int


EMAIL = re.compile(r"[\w.+-]+@[\w-]+(?:\.[\w-]+)+")
PARAGRAPH_BREAK = re.compile(r"\n[ \t]*\n")
SENTENCE_END = re.compile(r"(?<=[.!?])\s+")


def _clean(raw):
    text = raw.decode("utf-8-sig", errors="replace")
    replaced = text.count("\ufffd")
    text = unicodedata.normalize("NFKC", text)
    text = "".join(ch for ch in text if ch.isspace() or unicodedata.category(ch) not in ("Cc", "Cf"))
    text, redacted = EMAIL.subn("[EMAIL]", text)
    return text, replaced, redacted


def _pack(sentences, max_chars):
    pieces = [s[i:i + max_chars] for s in sentences for i in range(0, len(s), max_chars)]
    chunks, current = [], ""
    for piece in pieces:
        if current and len(current) + 1 + len(piece) <= max_chars:
            current += " " + piece
        else:
            if current:
                chunks.append(current)
            current = piece
    if current:
        chunks.append(current)
    return chunks


def prepare(doc_id, raw, max_chars):
    text, replaced, redacted = _clean(raw)
    texts = []
    for paragraph in PARAGRAPH_BREAK.split(text):
        paragraph = " ".join(paragraph.split())
        if paragraph:
            texts.extend(_pack(SENTENCE_END.split(paragraph), max_chars))
    chunks = [Chunk(f"{doc_id}-{n:03d}", t) for n, t in enumerate(texts, start=1)]
    return Ingested(chunks, replaced, redacted)

Every lesson of the module has a job here:

  • Bytes and Unicode (5.4): utf-8-sig drops the BOM, errors="replace" keeps going past the bad byte and leaves a visible \ufffd you can count, and NFKC turns the full-width letters into plain ones. The category filter deletes the zero-width space (Cf) but must keep whitespace: \n and \t are also in category Cc, and deleting the tab would glue help! to After and lose a sentence boundary. Order matters too: counting \ufffd right after decoding counts only the replaced bytes.
  • Regex (5.5): subn counts redactions in the same pass, the paragraph pattern accepts lines with only spaces or tabs as blank, and the lookbehind (?<=[.!?]) splits after the punctuation without removing it.
  • Methods (5.2): " ".join(paragraph.split()) collapses every whitespace run, including the single line breaks inside a paragraph.
  • Strings and slicing (5.1): long sentences are cut with slices, which never fail at the end of a string, and chunks are built with += on short strings, which is fine at this size.
  • Formatting (5.3): {n:03d} gives ids that sort correctly as text, which matters when chunks are stored in a database or a file system.

Note that Bad byte: belongs to the same paragraph as Ok?, because a single line break is not a paragraph break; it lands in its own chunk only because it does not fit in the 45 characters. Chunking by sentences and paragraphs keeps each chunk readable for the model, and the max_chars limit stands in for the token limit of the embedding model; production pipelines (LangChain's text splitters, LlamaIndex's node parsers) follow the same idea with token counts and overlap between chunks.

Recap

  • Bytes at the edges, text inside: decode once with a named encoding, normalise (NFKC, casefold) before comparing.
  • Fixed text: string methods (split, partition, startswith with a tuple, translate). Patterns: regex, escaped and anchored.
  • Streams and files split data anywhere: buffer bytes and decode only complete units, such as lines.
  • Keep values as numbers and dates while computing; format with a spec only for display.
  • Make text pipelines deterministic and testable: each step a small function, each rule checked by a test.
