16.1 Big-O in practice

Interviews ask for the complexity of every solution, and production code dies from the accidental quadratic loop nobody noticed on ten test rows. What Big-O measures and what it ignores, the common growth classes, how to measure growth instead of guessing, the real cost of Python's built-ins (lists, dicts, sets, deques, heaps, sorting, strings), amortised costs, and the hidden costs that turn linear code quadratic.

16 problems4 easy · 8 medium · 4 hard

1What Big-O measures

Big-O answers one question: when the input doubles, what happens to the cost? An algorithm is O(n) if its work grows proportionally to n (double the input, double the time), O(n^2) if it grows with the square (double the input, four times the time), O(log n) if each doubling adds only a constant amount of work, and O(1) if the work does not depend on n at all. Constant factors and smaller terms are dropped, so 3n + 100 is O(n) and n^2/2 + n is O(n^2): at large sizes the dominant term decides everything. Usually we mean the worst case (or the average case, explicitly, for hash tables), and we can state the space complexity, the extra memory used, the same way.

The classes, from fast to slow, and what they look like in code: O(1) a dict lookup or list.append; O(log n) binary search, repeatedly halving (16.3); O(n) one pass over the data; O(n log n) sorting, or n heap operations; O(n^2) a loop over the data inside another loop over the data (all pairs); O(2^n) trying every subset (16.5 rescues many of these). At n = 1,000,000, an O(n log n) algorithm does about 20 million steps (fractions of a second in C, seconds in Python), while O(n^2) does a trillion (days). That gap, not the constant factors, is why complexity matters.

2Measuring instead of guessing

Complexity is a prediction; check it. The doubling experiment runs the code at sizes n, 2n, 4n and compares times: a ratio near 2 suggests O(n), near 4 O(n^2), slightly above 2 O(n log n), near 1 O(1) or O(log n). On a log-log plot of time against size, the slope is the exponent (problem 2). Use timeit (or time.perf_counter around enough repetitions) for small code, and cProfile to find where a real program spends its time (python -m cProfile -s cumulative script.py); most slow programs have one hot spot, and it is rarely where you guessed. Counting operations, for example comparisons, gives exact, noise-free numbers, which is what several problems here do.

3The cost of Python's built-ins

Lists are dynamic arrays: indexing, len, append and pop() from the end are O(1) (append is amortised O(1): occasionally the list grows its storage by a proportion and copies everything, but that cost averages out over many appends); insert(0, x), pop(0) and del items[i] shift every later element, O(n); x in items, items.index(x) and items.count(x) scan, O(n); slicing copies, O(k) for k elements; sort is O(n log n) (Timsort, which is O(n) on already-sorted runs). dicts and sets are hash tables: lookup, insert and delete are O(1) on average (O(n) in a pathological worst case with many hash collisions), so membership tests against a set are the standard fix for an O(n) in inside a loop.

collections.deque gives O(1) appends and pops at both ends (use it for queues, 16.4's BFS), but O(n) indexing in the middle. heapq keeps a list as a binary heap: heappush and heappop are O(log n), heapq.nlargest(k, items) is O(n log k). bisect finds positions in a sorted list in O(log n), but insort still pays O(n) to shift elements. Strings are immutable, so building one by += in a loop can copy the whole string each time (CPython sometimes optimises this, but do not rely on it); collect parts in a list and "".join(parts) once, O(total length).

4Hidden quadratic costs

Most real performance bugs are an O(n) operation hiding inside a loop: if x not in seen_list (use a set), queue.pop(0) (use a deque), sorted(...) or max(...) recomputed every iteration (compute once, or maintain a heap), result = result + [x] or string += (append, then join), list.index to find each item's position (build a dict from item to index once), slicing in recursion (pass indices instead), and calling len() on a generator by first converting it to a list each time. The code looks linear and passes every test on ten rows; on a million rows it never finishes. When reviewing code, look for these patterns first.

1. Counting steps

def single(n):
    steps = 0
    for i in range(n):
        steps += 1
    return steps

def nested(n):
    steps = 0
    for i in range(n):
        for j in range(i):
            steps += 1
    return steps

def halving(n):
    steps = 0
    while n > 1:
        n //= 2
        steps += 1
    return steps

def log_linear(n):
    steps = 0
    for i in range(n):
        k = n
        while k > 1:
            k //= 2
            steps += 1
    return steps

for n in (8, 16, 1024):
    print(n, single(n), nested(n), halving(n), log_linear(n))

The single loop is O(n). The nested loop over j < i runs n(n - 1) / 2 times, which is O(n^2): constant factors do not change the class, and doubling n roughly quadruples it. Repeated halving is O(log n): each doubling of n adds one step, and 1024 needs only 10. Running a halving loop once per element is O(n log n), the cost of a good sort. These four shapes cover most code you will analyse.

solution.py
import math


def growth_exponent(sizes, costs):
    if len(sizes) < 2 or len(sizes) != len(costs):
        raise ValueError("need at least two (size, cost) pairs")
    xs = [math.log(n) for n in sizes]
    ys = [math.log(c) for c in costs]
    mx, my = sum(xs) / len(xs), sum(ys) / len(ys)
    slope = sum((x - mx) * (y - my) for x, y in zip(xs, ys)) / sum((x - mx) ** 2 for x in xs)
    return round(slope, 2)


def classify(sizes, costs):
    k = growth_exponent(sizes, costs)
    if k < 0.5:
        return "O(1)"
    if k < 1.08:
        return "O(n)"
    if k < 1.6:
        return "O(n log n)"
    return "O(n^2)"

Taking logarithms turns cost = c * n**k into a straight line, log(cost) = log(c) + k * log(n), so the exponent is the slope, and constants such as the 3 in 3n vanish into the intercept, exactly as Big-O ignores them. A least-squares fit over several sizes tolerates measurement noise (the noisy timings still classify as linear). n log n has a slope slightly above 1 (about 1.12 for sizes between 1,000 and 16,000, since the slope of log(n log n) is 1 + 1 / ln n), which is why the thresholds are heuristic and the linear one sits close to 1; in practice this is how you confirm, with a handful of timings, whether an optimisation changed the complexity or only the constant.

3. Removing duplicates while iterating

dedupe(items) should keep the first occurrence of each item, in order. It removes items from the list it is iterating over, which skips elements, and its in check on a list makes it quadratic. Fix it with a set of seen items (or dict.fromkeys), so it is correct and O(n).

TestsThe 3 checks Run tests uses

HintOpen a hint

list(dict.fromkeys(items)) keeps first occurrences in order in one pass; or loop with a seen set.

SolutionShow the solution and why
solution.py
def dedupe(items):
    seen = set()
    result = []
    for x in items:
        if x not in seen:
            seen.add(x)
            result.append(x)
    return result

Removing from a list while iterating over it shifts the remaining elements left, so the loop skips the element after each removal, and remove deletes the first occurrence, not the current one, which breaks the "keep the first" order. Performance was just as bad: count and remove each scan the list, so the whole function was O(n^2), minutes for the 100,000-item test. A set answers "seen before?" in O(1) on average, making one pass enough. dict.fromkeys does the same in one line because dicts keep insertion order and ignore repeated keys.

solution.py
def brute_force_cost(n_vectors, dim, queries_per_second, flops_per_second=2e10, bytes_per_value=4):
    memory_gb = round(n_vectors * dim * bytes_per_value / 1e9, 2)
    flops = 2 * dim * n_vectors
    max_qps = int(flops_per_second // flops)
    return {"memory_gb": memory_gb, "flops_per_query": flops, "max_qps": max_qps, "fits": max_qps >= queries_per_second}

Complexity analysis turns into a capacity plan: exact nearest-neighbour search compares the query with every stored vector, O(n * d) per query, so the cost grows linearly with the corpus. A hundred thousand 768-dimensional embeddings take 0.3 GB and comfortably serve 50 queries per second on one machine, which is why small RAG systems often need no vector database at all; fifty million 1536-dimensional embeddings need 300 GB and cannot sustain even one query per second by brute force. That is what approximate indexes (HNSW graphs, IVF partitions, product quantisation) are for: they trade a little recall for sub-linear query time, and lower precision (bytes_per_value=2 or 1) trades accuracy for memory.

Hint 2Open a hint

SolutionShow the solution and why
solution.py
import heapq


def running_medians(values):
    low, high, out = [], [], []
    for v in values:
        heapq.heappush(low, -v)
        heapq.heappush(high, -heapq.heappop(low))
        if len(high) > len(low):
            heapq.heappush(low, -heapq.heappop(high))
        if len(low) > len(high):
            out.append(-low[0])
        else:
            out.append((-low[0] + high[0]) / 2)
    return out

Re-sorting the data after every value (the reference slow function) costs O(n log n) per step and O(n^2 log n) overall; the two heaps keep the data split into a lower and an upper half, so the median is always at the top of one or both, and each new value costs a few O(log n) heap operations. Passing every value through the lower heap into the upper one keeps the invariant "every element of low is at most every element of high" without comparisons by hand. Streaming medians are used for latency monitoring (p50 of response times) and robust feature normalisation; for other percentiles, sketches such as t-digest do the same job approximately.

10. A sort inside the loop

rank_with_context(scores, k) should return, for each position i, the ids of the k best-scoring items seen so far (inclusive), best first. It calls sorted on the whole history every iteration, which is O(n^2 log n), and it also breaks ties by id descending instead of ascending. Fix both: keep the top k with a heap (or a bounded sorted list) as you go, ties broken by smaller id first.

SolutionShow the solution and why
solution.py
import bisect

def rank_with_context(scores, k):
    top, out = [], []
    for item_id, score in scores:
        bisect.insort(top, (-score, item_id))
        if len(top) > k:
            top.pop()
        out.append([i for _, i in top])
    return out

Sorting the full history at every step repeats work: after n items the function had sorted 1, 2, ..., n elements, O(n^2 log n) in total, which is hours for a long stream. Only the current top k can ever matter, so a bounded structure of size k suffices: insertion into a sorted list of length k is O(k), and the whole run is O(n k), linear for a fixed k. Encoding the order in the key (-score, id) makes both directions explicit: higher score first, then smaller id, where reverse=True on (score, id) had flipped the tie-break too. For large k, a heap gives O(log k) per step.

11. Measure complexity by counting

Write count_comparisons(fn, data) that runs fn on a list of Counted wrappers around data (a class you write whose __lt__ and __eq__ increment a shared counter) and returns the number of comparisons, and growth(fn, make_data, sizes) returning the list of (n, comparisons) pairs. import math, random
def selection_sort(items):
    items = list(items)
    for i in range(len(items)):
        m = i
        for j in range(i + 1, len(items)):
            if items[j] < items[m]:
                m = j

solution.py
import math, random


class Counted:
    calls = 0

    def __init__(self, value):
        self.value = value

    def __lt__(self, other):
        Counted.calls += 1
        return self.value < other.value

    def __eq__(self, other):
        Counted.calls += 1
        return self.value == other.value

    __hash__ = None


def count_comparisons(fn, data):
    Counted.calls = 0
    fn([Counted(x) for x in data])
    return Counted.calls


def growth(fn, make_data, sizes):
    return [(n, count_comparisons(fn, make_data(n))) for n in sizes]

Counting comparisons measures an algorithm's work exactly, free of timer noise, and makes complexity visible: selection sort does exactly n(n - 1) / 2 comparisons whatever the input (quadratic), while Python's Timsort needs only n - 1 on sorted input, because it detects the existing run, and about n log2 n on random data, the lower bound for comparison sorting. That adaptivity is why sorting nearly sorted data (appending a few items to a sorted list and re-sorting) is cheap in Python. The same instrumentation technique (wrapping objects to count operations) helps verify the complexity of your own functions in tests.

from collections import defaultdict, deque


def process(events):
    queue = deque(events)
    actions = defaultdict(list)
    while queue:
        user, action = queue.popleft()
        actions[user].append(action)
    ordered = sorted(actions)
    summary = "".join(f"{u}:{len(actions[u])};" for u in ordered)
    return {u: actions[u] for u in ordered}, summary

The correctness bug first: pop() takes from the end, so the queue was processed last-in first-out and every user's actions came out reversed; popleft on a deque (or a plain for loop over the events) keeps the order. Then the hidden costs: user not in users and users.index(user) scanned a list on every event (O(n * u)), a sorted of all users ran inside the loop (O(n * u log u)), and string += can copy the growing summary each time. A dict from user to actions makes grouping O(1) per event, sorting happens once, and join builds the summary in one pass, so the whole function is O(n + u log u) and the 100,000-event test runs in a fraction of a second instead of minutes.

14. What is the time complexity of looking up a key in a Python dict, and when is it not O(1)?

SolutionModel answer

A dict is a hash table: Python hashes the key, uses the hash to pick a slot in an array, and compares the key with what is stored there, probing a few other slots on collisions. On average this takes constant time, O(1), independent of the dict's size, because the table is kept at most about two thirds full and resized (an O(n) rehash, amortised over many inserts) as it grows. The worst case is O(n): if many keys share hash values, lookups degrade into scanning colliding entries, which can happen with a badly written __hash__ (for example returning a constant) or adversarial inputs (string hashes are randomised per process to defend against that). The key's hash and equality also have their own costs: hashing a long string or a big tuple is O(length) the first time (strings cache their hash). Iteration over a dict is O(n) and preserves insertion order.

Interview

15. Why is appending to a list O(1) but inserting at the front O(n)?

SolutionModel answer

A Python list is a dynamic array: a contiguous block of pointers with spare capacity. Appending writes into the next free slot, O(1); when the capacity runs out, the list allocates a larger block (over-allocating by a proportion of its size) and copies the pointers, an O(n) step, but because capacity grows geometrically those copies happen rarely enough that their total cost is proportional to the number of appends, so each append is amortised O(1). Inserting at index 0 must shift every existing pointer one place to the right to make room, which touches all n elements every time, O(n); the same applies to pop(0). When you need fast operations at the front, use collections.deque (O(1) at both ends), and when you need fast inserts in the middle of sorted data, consider a different structure (a heap, a balanced tree such as sortedcontainers, or batching and re-sorting).

16. A colleague's data pipeline is fast on test data but never finishes on production data. How do you find and fix the problem?

SolutionModel answer

Suspect superlinear growth hidden by small test inputs. Reproduce with increasing input sizes (1x, 2x, 4x a sample) and time each run: if doubling the input quadruples the time, there is an O(n^2) step. Profile a representative run with cProfile (or py-spy on the live process, which needs no code changes) to see which functions dominate, and look in them for the usual patterns: in on a list inside a loop, list.pop(0) or insert(0, ...), sorted, max or index recomputed per item, string or list concatenation in a loop, pandas apply or row-wise loops where vectorised operations exist, repeated queries per row (N+1 queries) instead of a join, and loading data inside a loop. Fix with the right structure (sets and dicts for lookups, deques for queues, heaps for top-k), hoisting work out of loops, batching, and vectorisation, then confirm with the same doubling measurement that the growth is now linear, and add a test or benchmark on a large input so it does not come back.

Recap

  • Big-O describes growth: double the input and see how the cost changes; drop constants and smaller terms.
  • Recognise the shapes: one loop O(n), halving O(log n), nested loops over the data O(n^2), sorting O(n log n).
  • Measure: doubling experiments, log-log slopes, cProfile, and exact operation counts.
  • Know the built-ins: list append and pop from the end O(1) (amortised), front operations and in O(n); dict and set operations O(1) on average; deque O(1) at both ends; heap operations O(log n).
  • Hunt hidden quadratics: in on lists, pop(0), sorting or searching inside loops, and concatenation in loops.
