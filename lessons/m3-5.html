3.5 Functions as values

Functions are objects you can store, pass and return. That gives you lambda, key= functions for sorting and grouping, map and filter, functools.partial, and dispatch tables: the way agents route a tool name to the code that runs it.

18 problems4 easy · 9 medium · 5 hard

1Functions are values

Since def simply binds a name to a function object (3.1), a function can go anywhere a value can go. You can assign it to another name, put it in a list or dict, pass it to another function, and return it from a function. A function that takes or returns a function is called a higher-order function. You have already used several: sorted(key=...), the factories in 3.4, and with_retry in 3.2.

functions_as_values.py
def shout(text):
    return text.upper()

def whisper(text):
    return text.lower()

styles = {"shout": shout, "whisper": whisper}   # functions stored in a dict
speak = styles["whisper"]                       # a function assigned to a name
print(speak("Hello"), styles["shout"]("hello"))

def apply_twice(fn, value):                     # a function passed as an argument
    return fn(fn(value))
print(apply_twice(lambda s: s + "!", "hi"))
Output
hello HELLO
hi!!

The key distinction is between the function and the result of calling it. styles["shout"] is the function object; styles["shout"]("hello") calls it. Passing shout hands over the function itself; passing shout("x") would hand over a string. A very common beginner bug is sorted(items, key=len()) (calling len with no argument) instead of key=len.

≈
SQL / Power BI

Passing a function is like passing an expression to ORDER BY, or a lambda-like expression to DAX iterators: SUMX(Sales, Sales[Qty] * Sales[Price]) evaluates the expression once per row. sorted(rows, key=...), map and max(key=...) work the same way: you give the "per-row expression", and the function applies it to every item.

2lambda: small functions in one expression

lambda params: expression builds a function object, exactly like def, with three limits: it has no name (its __name__ is <lambda>), its body must be one expression (no statements, no assignments, no return; the value of the expression is returned), and it cannot hold a docstring or type hints. It exists for short functions you need right where you pass them.

lambda.py
by_score = lambda doc: doc["score"]          # same as: def by_score(doc): return doc["score"]
docs = [{"id": "a", "score": 0.4}, {"id": "b", "score": 0.9}, {"id": "c", "score": 0.7}]
print(sorted(docs, key=by_score)[0]["id"], by_score.__name__)

print(sorted(docs, key=lambda d: d["score"], reverse=True)[0]["id"])
print((lambda x, y=2: x * y)(5))             # parameters and defaults work as usual
Output
a <lambda>
b
10

When not to use lambda: when the function needs more than one expression, when it is reused in several places, or when you assign it to a name as above. Style guides (PEP 8) say to use def then, because a named function gives better tracebacks and can have a docstring. A good rule: if you would have to think for more than a second to read the lambda, write a def.

3Key functions: sort, min, max and group by any rule

sorted, list.sort, min, max and itertools.groupby all accept key=. Step by step, sorted(items, key=f) calls f once per item to get a key, sorts the items by their keys, and returns the items themselves (not the keys). A key can be any comparable value; a tuple key sorts by several rules at once, compared element by element, which is how you express "by priority, then by date".

key_functions.py
tickets = [
    {"id": 1, "priority": 2, "age_h": 30},
    {"id": 2, "priority": 1, "age_h": 5},
    {"id": 3, "priority": 1, "age_h": 48},
    {"id": 4, "priority": 2, "age_h": 2},
]
# priority ascending, then oldest first (negate a number to reverse just that part)
order = sorted(tickets, key=lambda t: (t["priority"], -t["age_h"]))
print([t["id"] for t in order])

print(max(tickets, key=lambda t: t["age_h"])["id"])           # the oldest ticket
words = ["Embedding", "rag", "Agent", "chunk"]
print(sorted(words), sorted(words, key=str.lower))            # case-insensitive
Output
[3, 2, 1, 4]
3
['Agent', 'Embedding', 'chunk', 'rag'] ['Agent', 'chunk', 'Embedding', 'rag']

Two details explain most surprises. Python's sort is stable: items with equal keys keep their original order, so you can sort by a secondary rule first and the primary rule second and get both (lesson 4.2). And str.lower is passed as an unbound method, a plain function that takes the string as its argument, so key=str.lower works without any lambda. The operator module has ready-made key functions too: operator.itemgetter("score") is a faster, clearer lambda d: d["score"], and itemgetter("priority", "age_h") returns a tuple key.

4map, filter, reduce and comprehensions

map(fn, iterable) calls fn on each item; filter(pred, iterable) keeps the items for which pred(item) is truthy. Both return lazy iterators (Module 6): nothing is computed until you loop over them or wrap them in list(), and they can only be consumed once. functools.reduce(fn, iterable, start) folds the items into one value by calling fn(running, item) repeatedly.

map_filter.py
from functools import reduce

prices = ["12.50", "7", "3.25"]
as_float = map(float, prices)             # lazy: nothing converted yet
print(as_float)
print(list(as_float), list(as_float))     # the second list() finds it already used up

lengths = [len(s) for s in ["rag", "", "agents"]]
non_empty = list(filter(None, ["rag", "", "agents"]))   # None means "keep truthy items"
print(lengths, non_empty)

print(reduce(lambda acc, x: acc * x, [2, 3, 4], 1))
Output
<map object at 0x1391a58>
[12.5, 7.0, 3.25] []
[3, 0, 6] ['rag', 'agents']
24

In modern Python a comprehension is usually clearer than map or filter with a lambda: [x * 2 for x in xs if x > 0] reads better than list(map(lambda x: x * 2, filter(lambda x: x > 0, xs))). map is still nice when you already have a named function (map(float, prices), map(str.strip, lines)), and filter(None, ...) is a common idiom. For reduce, there is almost always a clearer built-in: sum, max, math.prod, "".join, any, all.

5functools.partial and dispatch tables

functools.partial(fn, *args, **kwargs) returns a new callable that remembers some arguments and fills them in for you. It is a ready-made factory (3.4): partial(complete, model="large") is a version of complete that always uses the large model. Unlike a lambda in a loop, it stores the values right away, so it has no late-binding trap, and it keeps a readable repr.

partial.py
from functools import partial

def complete(prompt, *, model="small", temperature=0.2):
    return f"{model}@{temperature}: {prompt}"

creative = partial(complete, model="large", temperature=0.9)
print(creative("Write a haiku"))
print(creative("Write a haiku", temperature=0.5))     # later keywords override
print(creative.func.__name__, creative.keywords)
Output
large@0.9: Write a haiku
large@0.5: Write a haiku
complete {'model': 'large', 'temperature': 0.9}

A dispatch table is a dict whose values are functions. Instead of a long if name == "search": ... elif ... chain, you look the function up by name and call it. This is exactly how an agent runs tools: the LLM returns a tool name and arguments, the code looks the name up in a registry dict and calls the function with the arguments. Adding a tool means adding one entry, and an unknown name is a single, clear error path.

dispatch.py
def search(query, k=3):
    return f"top {k} results for {query!r}"

def calculator(expression):
    allowed = set("0123456789+-*/(). ")
    if not set(expression) <= allowed:
        raise ValueError("unsupported characters")
    return str(eval(expression))         # tiny demo only: never eval untrusted input in real code

TOOLS = {"search": search, "calculator": calculator}

def run_tool(call):
    fn = TOOLS.get(call["name"])
    if fn is None:
        return f"error: unknown tool {call['name']!r}"
    return fn(**call["arguments"])

print(run_tool({"name": "search", "arguments": {"query": "refund policy"}}))
print(run_tool({"name": "calculator", "arguments": {"expression": "2 * (3 + 4)"}}))
print(run_tool({"name": "weather", "arguments": {}}))
Output
top 3 results for 'refund policy'
14
error: unknown tool 'weather'
!
A note on eval

The calculator uses eval only to keep the example tiny, behind a strict character check. In real agent code, never eval text that came from a user or an LLM: use a safe expression parser (for example the ast module or a library such as numexpr). Tool registries are a classic place for injection bugs.

4. A sort that crashes on missing values

newest_first(rows) should sort rows by updated (an ISO date string), newest first, with rows that have no updated value at the end. It crashes when any row has None. Fix the key function.

TestsThe 2 checks Run tests uses

        {"id": 3, "updated": "2025-06-10"}, {"id": 4, "updated": None}]

Hint 1Open a hint

Comparing a string with None raises TypeError. Make the key a tuple whose first part says whether the value is missing.

Hint 2Open a hint

With reverse=True, think about which first value puts the missing rows at the end.

SolutionShow the solution and why
solution.py
def newest_first(rows):
    return sorted(rows, key=lambda r: (r["updated"] is not None, r["updated"] or ""), reverse=True)

Python 3 refuses to compare None with a string, so any None in the key crashes the whole sort. The tuple (has_value, value) fixes it: rows with a value get True, missing ones False, and with reverse=True the True rows come first, ordered newest first, while the missing ones go last. or "" replaces None with a comparable placeholder. Because the sort is stable, rows with no date keep their original order (2 before 4).

5. A tool registry with a dispatch table

Write make_registry() returning (register, call). register(name, fn) adds a tool, and raises ValueError if the name is taken. call(name, arguments) calls the tool with the arguments dict as keyword arguments, and returns {"ok": True, "result": ...}, or {"ok": False, "error": "..."} when the tool is unknown or the call raises TypeError (wrong arguments from the LLM). Each registry is independent.

TestsThe 6 checks Run tests uses

    except exc:
        return True
    return False

Hint 1Open a hint

Keep tools = {} in the factory. call looks the name up with tools.get(name).

Hint 2Open a hint

Wrap only the actual tool call in try/except TypeError, so other errors are not hidden.

SolutionShow the solution and why
solution.py
def make_registry():
    tools = {}

    def register(name, fn):
        if name in tools:
            raise ValueError(f"tool {name!r} already registered")
        tools[name] = fn

    def call(name, arguments):
        fn = tools.get(name)
        if fn is None:
            return {"ok": False, "error": f"unknown tool {name!r}"}
        try:
            return {"ok": True, "result": fn(**arguments)}
        except TypeError as e:
            return {"ok": False, "error": f"bad arguments: {e}"}

    return register, call

The registry is a dict from names to function objects, kept private in a closure (3.4), so two registries never mix. Returning a structured error instead of raising lets the agent loop send the error text back to the LLM, which can then correct its call: that feedback loop is how real agents recover from bad tool calls. Catching only TypeError is deliberate: a bug inside the tool raising something else should not be disguised as "bad arguments". A real version would validate arguments against a schema first (Module 11) and limit what tools may do.

6. A pipeline that loses its steps

make_pipeline(*steps) should return a function that passes a value through every step in order. Every pipeline only applies the last step. Fix it.

TestsThe 3 checks Run tests uses

Hint 1Open a hint

Each step must receive the output of the previous step, not the original value.

Hint 2Open a hint

With no steps, the function should return its input unchanged.

SolutionShow the solution and why
solution.py
def make_pipeline(*steps):
    def run(value):
        for step in steps:
            value = step(value)
        return value
    return run

The loop fed the original value into every step and kept only the last result, so earlier steps had no effect. Rebinding value passes each output into the next step. It also fixes the empty pipeline, which used to raise UnboundLocalError because result was never assigned (3.3). Composing functions into a pipeline is the idea behind scikit-learn's Pipeline, text-cleaning chains and LangChain's | operator.

def group_by(items, key):
    out = {}
    for item in items:
        out.setdefault(key(item), []).append(item)
    return out

10. Pick a scorer by name

evaluate(preds, gold, metric) chooses a metric function by name. Adding a metric means editing a growing if chain, and a typo in the metric name silently returns None. Replace the chain with a dispatch table, and make an unknown name raise ValueError listing the known metrics.

TestsThe 3 checks Run tests uses

        f(*args)
    except exc as e:
        return str(e)
    return False

HintOpen a hint

SolutionShow the solution and why
solution.py
def accuracy(p, g):
    return sum(a == b for a, b in zip(p, g)) / len(g)

def error_rate(p, g):
    return 1 - accuracy(p, g)

METRICS = {"accuracy": accuracy, "error_rate": error_rate}

def evaluate(preds, gold, metric):
    try:
        fn = METRICS[metric]
    except KeyError:
        raise ValueError(f"unknown metric {metric!r}; choose from {sorted(METRICS)}") from None
    return fn(preds, gold)

The if chain had a silent fall-through: an unknown name returned None (3.1), which later shows up as a broken report rather than an error. The dict maps names to functions, so adding a metric is one line, and the list of valid names is available for the error message, the CLI help or a config check. from None hides the internal KeyError so the user sees one clean error (Module 8). scikit-learn's scoring="f1" strings work exactly this way: a registry from names to scorer functions.

Write compose(*fns) that returns a function applying the functions right to left, like maths: compose(f, g, h)(x) == f(g(h(x))). Hint 1Open a hint

Call the last function with *args, **kwargs, then loop over the rest in reverse, feeding each the result.

Hint 2Open a hint

reversed(fns[:-1]) walks the remaining functions right to left.

SolutionShow the solution and why
solution.py
def compose(*fns):
    if not fns:
        return lambda x: x
    *rest, last = fns
    def composed(*args, **kwargs):
        result = last(*args, **kwargs)
        for fn in reversed(rest):
            result = fn(result)
        return result
    return composed

Only the innermost function sees the original arguments, so it alone is called with *args, **kwargs; that is why compose(len, max) can forward key=len to max. Star-unpacking *rest, last = fns (lesson 4.3) splits off the last function. The order matters and is a classic interview check: compose(inc, dbl)(5) doubles first. Many libraries offer this (toolz.compose), and the "pipe" style (left to right, as in problem 6) is often easier for readers; in an interview, say which one you implemented.

solution.py
from functools import partial


def train(epochs, losses, callbacks):
    history = []
    for epoch in range(epochs):
        loss = losses[epoch]
        history.append(loss)
        messages = [cb(epoch, history) for cb in callbacks]
        if "stop" in messages:
            return epoch, messages
    return epochs - 1, []


def early_stop(epoch, history, *, patience):
    best = min(history)
    since_best = len(history) - 1 - history.index(best)
    return "stop" if since_best >= patience else "go"


def make_callbacks(patiences, log, prefix="run"):
    callbacks = [partial(early_stop, patience=p) for p in patiences]
    callbacks.append(partial(log_epoch, log, prefix=prefix))
    return callbacks


def log_epoch(log, epoch, history, prefix="run"):
    log.append(f"{prefix} epoch {epoch}: {history[-1]}")
    return "go"

Bug one is late binding (3.4): all the early_stop closures share the single patience variable of make_callbacks, which ends at 5, so the patience-1 callback never stops. partial(early_stop, patience=p) stores each value immediately. Moving early_stop to module level with a keyword-only patience also makes it testable on its own (the last test). Bug two is a missing parameter: the test passes prefix="sweep", but make_callbacks had nowhere to put it, so the starter fails at the call. The fixed version forwards it into partial as a keyword, so each logger carries its own prefix. Keras and PyTorch Lightning callbacks are configured exactly like this, usually as small classes.

SolutionShow the solution and why
solution.py
import operator

OPS = {"+": operator.add, "-": operator.sub, "*": operator.mul, "/": operator.truediv}

def to_number(text):
    return float(text) if "." in text else int(text)

def calculate(tokens):
    result = to_number(tokens[0])
    for op, text in zip(tokens[1::2], tokens[2::2]):
        fn = OPS.get(op)
        if fn is None:
            raise ValueError(f"unknown operator {op!r}")
        result = fn(result, to_number(text))
    return result

The dispatch table maps each symbol to a real function, so the evaluator never runs arbitrary code: only the four operations in OPS can ever execute, which is the safety property eval cannot give. Supporting a new operator is one dict entry ("%": operator.mod). Slicing with steps pairs each operator with the number after it. Real precedence (* before +) needs a proper parser, for example one built on Python's ast module that walks only allowed node types, which is how safe calculator tools are usually written.

16. What does "functions are first-class objects" mean, and what does it let you do?

SolutionModel answer

A function is an object like any other: it can be bound to names, stored in lists and dicts, passed as an argument, returned from another function, and given attributes. That enables higher-order functions (sorted(key=...), map, filter), callbacks, factories and closures, functools.partial, decorators, and dispatch tables that replace long if chains (tool registries, metric registries, command handlers). A good answer gives one concrete example from real work, such as passing a scoring function into an evaluation loop or routing LLM tool calls through a dict.

Interview

17. lambda or def: when do you use each?

SolutionModel answer

Both create function objects. lambda is limited to one expression, has no name in tracebacks (<lambda>), and cannot carry a docstring or annotations. Use it for short, obvious functions passed inline: key=lambda r: r["score"], a tiny callback. Use def for anything with logic, anything reused, anything you would name (PEP 8 discourages assigning a lambda to a name), and anything that needs testing or documentation. Also mention the better alternatives to many lambdas: operator.itemgetter / attrgetter, functools.partial, bound methods like str.lower, and comprehensions instead of map/filter with a lambda.

Interview

18. How would you design the part of an agent that executes the tool calls an LLM returns?

SolutionModel answer

Keep a registry: a dict from tool name to a function (often with a schema and description, generated from the function's signature and docstring, 3.1). For each tool call: look up the name (unknown name means a structured error back to the model, not a crash); validate the arguments against the schema before calling (Pydantic), returning validation errors to the model so it can retry; call the function with the validated arguments as keyword arguments; catch and report tool failures, distinguishing bad arguments from internal bugs; and log the call and result for tracing. Safety: never eval model output, give tools the least privilege they need, put timeouts and rate limits on external calls (3.4's limiter), and pass copies or validated objects so tools cannot change the agent's state (2.4).

Recap

  • Functions are values: store them, pass them, return them. f is the function; f() is the result of calling it.
  • lambda is a one-expression function for short inline uses. Anything bigger or reused deserves a def.
  • key= functions run once per item. Tuple keys sort by several rules; operator.itemgetter is a fast, clear field key.
  • map and filter are lazy and single-use. A comprehension is usually clearer; reduce usually has a clearer built-in.
  • functools.partial fixes arguments without late-binding traps. Dispatch tables (dicts of functions) replace if chains and power agent tool registries.
