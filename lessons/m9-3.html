9.3 Properties and encapsulation

How Python protects an object's rules without private fields: naming conventions, @property for computed and validated attributes, setters that keep invariants, functools.cached_property, name mangling, and __slots__. How properties work underneath (descriptors), and the bugs they prevent. Applied to model configs, conversations, datasets and API keys.

19 problems4 easy · 10 medium · 5 hard

1Encapsulation by convention

Many languages enforce privacy: a private field cannot be touched from outside. Python does not. Every attribute can be read and changed from anywhere, and the community relies on conventions instead, summarised as "we are all consenting adults". A name with one leading underscore, self._tokens, means "internal: not part of the public interface, may change without notice, do not touch from outside". Tools respect it: from module import * skips such names, and linters and IDEs warn when you access them on another object. A name without an underscore is public and is a promise to callers.

Encapsulation is still possible, and it is about invariants, not secrecy: rules about the state that must always hold. A token budget's spent amount must never exceed its limit; a config's temperature must stay between 0 and 2; an index's two dicts must agree (9.1). The tools for protecting them are: keep the raw state in underscore attributes, change it only through methods, expose read access through properties, validate in setters and in __init__, and never hand out internal mutable objects (return copies or read-only views, 2.2).

2@property: methods that look like attributes

Decorating a method with @property turns it into an attribute that is computed when read: conv.token_count calls the method, with no parentheses. This is ideal for values derived from other state, because they can never be out of date: there is nothing to keep in sync. A property with only a getter is read-only: assigning to it raises AttributeError.

property_basics.py
class Order:
    def __init__(self, items):
        self._items = list(items)            # list of (name, price, qty)

    @property
    def total(self):
        return round(sum(price * qty for _, price, qty in self._items), 2)

    @property
    def items(self):
        return tuple(self._items)             # a read-only view, not the internal list

    def add(self, name, price, qty=1):
        self._items.append((name, price, qty))

o = Order([("pen", 1.5, 4)])
print(o.total)
o.add("book", 12.0)
print(o.total, o.items)
try:
    o.total = 100
except AttributeError as e:
    print("AttributeError:", e)
Output
6.0
18.0 (('pen', 1.5, 4), ('book', 12.0, 1))
AttributeError: property 'total' of 'Order' object has no setter

Properties also solve an evolution problem. In Java-style code, every field gets get_x() and set_x() methods "just in case" validation is needed later. In Python, start with a plain public attribute, self.temperature = t. If you later need validation or computation, replace it with a property of the same name, and every caller that wrote config.temperature keeps working unchanged. That is why Python code rarely has getter and setter methods: the attribute syntax is the interface, and a property can take over behind it at any time (problem 17).

3Setters that keep invariants

A property can also control assignment. After defining the getter, decorate a second method with @name.setter; it receives the new value and decides what to store, usually after validating it. The value itself lives in an underscore attribute, self._name, because the property has taken over the public name: if the setter assigned self.name = value, it would call itself forever (problem 3).

setters.py
class GenerationConfig:
    def __init__(self, temperature=0.7, max_tokens=256):
        self.temperature = temperature          # goes through the setter: validated from the start
        self.max_tokens = max_tokens

    @property
    def temperature(self):
        return self._temperature

    @temperature.setter
    def temperature(self, value):
        if isinstance(value, bool) or not isinstance(value, (int, float)):
            raise TypeError(f"temperature must be a number, got {value!r}")
        if not 0 <= value <= 2:
            raise ValueError(f"temperature must be in [0, 2], got {value}")
        self._temperature = float(value)

    @property
    def max_tokens(self):
        return self._max_tokens

    @max_tokens.setter
    def max_tokens(self, value):
        if not isinstance(value, int) or value < 1:
            raise ValueError(f"max_tokens must be a positive int, got {value!r}")
        self._max_tokens = value

cfg = GenerationConfig()
cfg.temperature = 1
print(cfg.temperature, type(cfg.temperature).__name__, vars(cfg))
for bad in [3, "hot"]:
    try:
        cfg.temperature = bad
    except (ValueError, TypeError) as e:
        print(type(e).__name__, "-", e, "| still", cfg.temperature)
try:
    GenerationConfig(max_tokens=0)
except ValueError as e:
    print("at creation:", e)
Output
1.0 float {'_temperature': 1.0, '_max_tokens': 256}
ValueError - temperature must be in [0, 2], got 3 | still 1.0
TypeError - temperature must be a number, got 'hot' | still 1.0

Three details make this robust. __init__ assigns through the public name, so the same validation runs at construction; assigning self._temperature directly in __init__ would let an invalid object be created (problem 14). A failed assignment raises before storing, so the object keeps its previous valid value. And the setter can normalise (here, storing a float), so the rest of the code can rely on one type. vars(cfg) shows that the instance stores only the underscore attributes: the properties live on the class.

4Computing once: functools.cached_property

A property runs its method on every access. That is right when the value is cheap or the underlying state changes, and wasteful when the computation is expensive and the inputs never change after creation: building a vocabulary from a corpus, loading a tokenizer, computing statistics of a fixed dataset. functools.cached_property runs the method on the first access and stores the result in the instance's __dict__ under the same name; later accesses find it there and never call the method again.

cached_property.py
import functools

class Corpus:
    def __init__(self, texts):
        self._texts = list(texts)
        self.builds = 0

    @functools.cached_property
    def vocab(self):
        self.builds += 1
        return sorted({w for t in self._texts for w in t.lower().split()})

    def add(self, text):
        self._texts.append(text)
        self.__dict__.pop("vocab", None)          # invalidate the cached value

c = Corpus(["Refund policy", "refund window"])
print(c.vocab, c.vocab is c.vocab, c.builds)
print("vocab" in vars(c))
c.add("Shipping policy")
print(c.vocab, c.builds)
Output
['policy', 'refund', 'window'] True 1
True
['policy', 'refund', 'shipping', 'window'] 2

The cost of caching is staleness: if the inputs change, the cached value is now wrong, and nothing recomputes it automatically. Whoever changes the inputs must invalidate the cache, here by removing the stored value from __dict__ (del c.vocab also works when it is present). Use cached_property for values derived from state that is fixed after construction, or pair it with a clear invalidation rule in every method that changes that state (problem 7). Unlike lru_cache on a method (8.3), it stores the value on the instance itself, so it disappears with the object and does not keep instances alive.

5Name mangling: __name

A name with two leading underscores (and at most one trailing), such as self.__secret, is mangled inside a class body: Python rewrites it to self._ClassName__secret. The purpose is to avoid accidental clashes in subclasses: if both a base class and a subclass use self.__cache, each gets its own attribute (_Base__cache and _Sub__cache) instead of overwriting the other's. It is not a security feature: the mangled name is easy to reach from outside, and it makes debugging and testing more awkward.

mangling.py
class Client:
    def __init__(self, key):
        self.__key = key                    # stored as _Client__key
        self._session = "s-1"               # one underscore: internal by convention

    def masked(self):
        return self.__key[:3] + "..."

c = Client("sk-12345")
print(sorted(vars(c)), c.masked(), c._session)
try:
    c.__key
except AttributeError as e:
    print("AttributeError:", e)
print(c._Client__key)                       # still reachable: mangling is not protection
Output
['_Client__key', '_session'] sk-... s-1
AttributeError: 'Client' object has no attribute '__key'
sk-12345

In practice: use one underscore for internal attributes, and reserve two underscores for classes designed to be subclassed by people who might pick the same names. Names with two underscores on both sides (__init__, __len__) are not mangled; they are the special methods of 9.2, and inventing new ones of your own is discouraged. And secrets such as API keys need real protection (environment variables, a secrets manager, 12.4); within an object, the useful measure is a __repr__ that never shows them (problem 11).

6__slots__: fixed attributes, less memory

Normally each instance stores its attributes in its own __dict__, which is flexible (you can add any attribute at any time) but costs memory: a dict per object, typically around a hundred bytes or more on top of the values. A class can instead declare __slots__, a tuple of the attribute names it allows. Instances then have no __dict__; the values are stored in fixed slots, each object is smaller, and assigning any attribute not listed raises AttributeError, so a typo such as self.socre = 1 fails loudly instead of silently creating a new attribute (problem 10).

slots.py
import sys

class PointDict:
    def __init__(self, x, y):
        self.x, self.y = x, y

class PointSlots:
    __slots__ = ("x", "y")
    def __init__(self, x, y):
        self.x, self.y = x, y

a, b = PointDict(1, 2), PointSlots(1, 2)
print(hasattr(a, "__dict__"), hasattr(b, "__dict__"))
print(sys.getsizeof(a) + sys.getsizeof(a.__dict__) > sys.getsizeof(b))
a.z = 3                                     # allowed: goes into a.__dict__
try:
    b.z = 3
except AttributeError as e:
    print("AttributeError:", e)
Output
True False
True
AttributeError: 'PointSlots' object has no attribute 'z' and no __dict__ for setting new attributes

Use __slots__ for classes with many instances (millions of tokens, spans, graph nodes or records) where the memory saving is real, or when catching attribute typos matters. The trade-offs: no dynamic attributes, no cached_property (it needs __dict__) unless you add "__dict__" to the slots, class-level default values for slotted names are not allowed, and with inheritance every class in the chain must declare its own __slots__ to keep the benefit. @dataclass(slots=True) (11.3) generates them for you.

7How properties work

A property is an object stored on the class, under the attribute's name. Objects that define __get__ (and optionally __set__) are called descriptors, and attribute lookup gives them special treatment: when you read obj.temperature, Python finds the property object on the class and calls its __get__, which calls your getter method with obj. Assignment obj.temperature = v calls its __set__, which calls your setter. That is the whole mechanism; methods themselves work the same way, which is how obj.method becomes a bound method (9.1).

The lookup order from 9.1 has one refinement because of this. A data descriptor (one with __set__, such as property) on the class takes precedence over the instance's __dict__, so a property cannot be bypassed by putting a value in the instance dict. A non-data descriptor (only __get__, such as a plain function or cached_property) is overridden by the instance's __dict__, which is exactly how cached_property works: after the first access, the stored value in the instance dict wins and the method is no longer called (problem 16). Frameworks build on descriptors: Django and SQLAlchemy model fields, and Pydantic's validated fields, are descriptors or work alongside them.

descriptors.py
import functools

class Demo:
    @property
    def p(self):
        return "property value"

    @functools.cached_property
    def c(self):
        return "computed once"

d = Demo()
d.__dict__["p"] = "instance dict value"
d.__dict__["c"] = "instance dict value"
print(d.p, "|", d.c)
print(type(Demo.__dict__["p"]).__name__, hasattr(Demo.__dict__["p"], "__set__"))
Output
property value | instance dict value
property True

solution.py
class SamplingConfig:
    def __init__(self, temperature=1.0, top_p=1.0):
        self.temperature = temperature
        self.top_p = top_p

    @staticmethod
    def _check_number(name, value):
        if isinstance(value, bool) or not isinstance(value, (int, float)):
            raise TypeError(f"{name} must be a number, got {value!r}")

    @property
    def temperature(self):
        return self._temperature

    @temperature.setter
    def temperature(self, value):
        self._check_number("temperature", value)
        if not 0 <= value <= 2:
            raise ValueError(f"temperature must be in [0, 2], got {value}")
        self._temperature = value

    @property
    def top_p(self):
        return self._top_p

    @top_p.setter
    def top_p(self, value):
        self._check_number("top_p", value)
        if not 0 < value <= 1:
            raise ValueError(f"top_p must be in (0, 1], got {value}")
        self._top_p = value

    @property
    def is_greedy(self):
        return self._temperature == 0

Each setter is the single gate for its field, and __init__ goes through the gates too, so no SamplingConfig can ever hold invalid values, whichever way it was created or changed. Checks run before storing, so a rejected assignment leaves the old value. The read-only is_greedy is derived from the stored temperature, so it is always correct. The shared type check lives in a static helper (9.6). This is the behaviour Pydantic gives a model field with Field(ge=0, le=2) (11.4), here written by hand so you can see what it does.

class Account:
    def __init__(self, balance=0):
        self.balance = balance

The property owns the name balance on the class, and data descriptors take precedence over the instance dict, so every self.balance = ... inside the setter called the setter again, and every self.balance inside the getter called the getter again, until Python's recursion limit. solution.py
class Conversation:
    def __init__(self, system_prompt):
        self.system_prompt = system_prompt
        self._turns = []

    @property
    def system_prompt(self):
        return self._system_prompt

    @system_prompt.setter
    def system_prompt(self, text):
        text = text.strip()
        if not text:
            raise ValueError("system prompt must not be empty")
        self._system_prompt = text

    def add(self, role, content):
        self._turns.append({"role": role, "content": content})

    @property
    def messages(self):
        system = {"role": "system", "content": self._system_prompt}
        return (system, *(dict(m) for m in self._turns))

    @property
    def token_count(self):
        return sum(len(m["content"].split()) for m in self.messages)

    @property
    def turns(self):
        return len(self._turns)

Everything a caller can see is either validated (system_prompt) or derived (messages, token_count, turns), so there is no state that can drift out of sync: changing the system prompt immediately changes the messages and the token count. The messages property returns a tuple of copied dicts, so callers can read the history and pass it to an API, but cannot alter the conversation by accident (2.3). Because these are properties, the call sites read naturally, client.send(conv.messages), and if token_count later needs a real tokenizer or caching, its callers do not change.

class Metrics:
    def __init__(self, correct, total):
        self.correct = correct
        self.total = total

    @property
    def accuracy(self):
        return self.correct / self.total if self.total else 0.0

    @property
    def error_rate(self):
        return 1 - self.accuracy

    def report(self):
        return f"accuracy={self.accuracy:.3f}"

Without the decorator, self.accuracy evaluates to a bound method, so 1 - self.accuracy raises TypeError, the f-string format :.3f fails, and in code that does not crash, m.accuracy > 0.9 raises a TypeError too. @property makes reading the name call the method. solution.py
import functools
from collections import Counter

class TextDataset:
    _CACHED = ("vocab", "word_counts")

    def __init__(self, texts):
        self._texts = list(texts)
        self.builds = 0

    def __len__(self):
        return len(self._texts)

    @functools.cached_property
    def word_counts(self):
        self.builds += 1
        return Counter(w for t in self._texts for w in t.lower().split())

    @functools.cached_property
    def vocab(self):
        self.builds += 1
        return sorted({w for t in self._texts for w in t.lower().split()})

    def _invalidate(self):
        for name in self._CACHED:
            self.__dict__.pop(name, None)

    def add(self, text):
        self._texts.append(text)
        self._invalidate()

    def remove(self, index):
        del self._texts[index]
        self._invalidate()

Each cached value is computed on first access and stored in the instance dict, so repeated reads are free, which the unchanged builds count shows. Every method that changes _texts calls one _invalidate helper, so there is exactly one place that knows which values depend on the texts; forgetting it in a new method is the classic stale-cache bug. Popping with a default makes invalidation safe whether or not the value has been computed yet. For a dataset that changes constantly, plain properties (or updating the counts incrementally) may be better than caching at all.

import hashlib

class Secret:
    def __init__(self, value):
        if not value:
            raise ValueError("secret must not be empty")
        self._value = value

    def __repr__(self):
        shown = self._value[:4] + "..." if len(self._value) > 4 else "***"
        return f"Secret({shown!r})"

    __str__ = __repr__

    def reveal(self):
        return self._value

    @property
    def fingerprint(self):
        return hashlib.sha256(self._value.encode()).hexdigest()[:8]

    def __eq__(self, other):
        if not isinstance(other, Secret):
            return NotImplemented
        return self._value == other._value

    def __hash__(self):
        return hash(self._value)

Keys leak most often through logs, error messages and debug prints: an exception that shows a config dict, a log line with a client object, a test failure message. The fingerprint lets you log which key was used (for example after a rotation) without exposing it. Pydantic has SecretStr with the same idea, and this only protects against accidents: anyone with access to the process can still read _value.

Validate a candidate pair with one private method, _set(start, end), that checks and then assigns both. Every setter and shift goes through it.

SolutionShow the solution and why
solution.py
class Window:
    def __init__(self, start, end):
        self._set(start, end)

    def _set(self, start, end):
        if not 0 <= start <= end:
            raise ValueError(f"need 0 <= start <= end, got start={start}, end={end}")
        self._start, self._end = start, end

    def __repr__(self):
        return f"Window({self._start}, {self._end})"

    @property
    def start(self):
        return self._start

    @start.setter
    def start(self, value):
        self._set(value, self._end)

    @property
    def end(self):
        return self._end

    @end.setter
    def end(self, value):
        self._set(self._start, value)

    @property
    def length(self):
        return self._end - self._start

    @length.setter
    def length(self, value):
        if value < 0:
            raise ValueError(f"length must not be negative, got {value}")
        self._set(self._start, self._start + value)

    def shift(self, delta):
        self._set(self._start + delta, self._end + delta)

All changes funnel through _set, which validates the complete new state before assigning anything, so no sequence of property assignments can leave the window invalid, even halfway. That is why setting end = 40 before start = 30 works but the opposite order (start 30 first) would be rejected while end was still 15: invariants that span several fields constrain the order of updates, and a method that sets both at once (like shift, or a move_to(start, end)) is often friendlier. length is not stored at all, so it can never disagree with start and end. This is the pattern for any object with related fields: one validating method, and properties as its public face.

class Price:
    __slots__ = ("_amount", "_currency")

    def __init__(self, amount, currency):
        if amount < 0:
            raise ValueError(f"amount must not be negative, got {amount}")
        object.__setattr__(self, "_amount", float(amount))
        object.__setattr__(self, "_currency", currency.upper())

    def __setattr__(self, name, value):
        raise AttributeError(f"Price is immutable: cannot set {name!r}")

    @property
    def amount(self):
        return self._amount

    @property
    def currency(self):
        return self._currency

    def with_discount(self, pct):
        return Price(round(self._amount * (1 - pct / 100), 2), self._currency)

    def __repr__(self):
        return f"Price({self._amount!r}, {self._currency!r})"

    def __eq__(self, other):
        if not isinstance(other, Price):
            return NotImplemented
        return (self._amount, self._currency) == (other._amount, other._currency)

    def __hash__(self):
        return hash((self._amount, self._currency))

Immutability makes a value object safe to share and to use as a dict key or set member: the hash can never change, and no caller can alter a price another part of the program is relying on (2.2). __setattr__ intercepts every assignment, so even the private slots cannot be changed from outside; construction uses object.__setattr__, the underlying mechanism, to set them once. Operations that "change" the value return a new object, like str.upper() or int + int. Storing float(amount) normalises 20 and 20.0 to one representation, so they compare and hash equal. @dataclass(frozen=True, slots=True) (11.3) generates almost exactly this class from two lines of field declarations.

Interview

17. Why does Python code use properties instead of getter and setter methods?

SolutionModel answer

Because attribute access is the interface, and a property can take it over later without changing callers. You start with a plain public attribute; if you later need validation, normalisation, a computed value or lazy loading, you replace it with a @property of the same name, and obj.x and obj.x = v keep working everywhere. Writing get_x() and set_x() up front, as in Java, adds boilerplate for flexibility Python already gives you. Properties are for cheap, side-effect-free operations that feel like reading data; anything slow, with side effects or needing arguments should remain a method, so callers are not surprised by an attribute read that hits the network.

Interview

18. How does privacy work in Python: no underscore, one underscore, two underscores?

SolutionModel answer

Nothing is truly private; privacy is a convention. A plain name is public API. A single leading underscore (_cache) marks an internal detail: callers should not use it, it can change without notice, import * skips it, and tools warn about outside access. Two leading underscores (__cache) trigger name mangling inside the class body, renaming it to _ClassName__cache, which prevents accidental collisions with attributes of the same name in subclasses; it does not prevent access, and it complicates testing, so it is used sparingly. Dunder names with underscores on both sides are special methods, not private. Real protection of invariants comes from properties, validating methods and returning copies, and real protection of secrets comes from keeping them out of the code and out of repr.

Interview

19. How do property and functools.cached_property work under the hood, and why does the difference matter?

SolutionModel answer

Both are descriptors: objects stored on the class that customise attribute access via __get__. When you read obj.name, Python checks the class for a descriptor under that name. A data descriptor (one that defines __set__ or __delete__, like property) takes precedence over the instance __dict__, so every read and write goes through the getter and setter, and nothing in the instance can bypass it: that is why properties work as validation gates. A non-data descriptor (only __get__, like functions and cached_property) is used only if the instance __dict__ has no entry with that name. cached_property exploits this: its __get__ computes the value and stores it in the instance dict, so later reads find the dict entry and never call the descriptor again, making them as fast as a normal attribute. Consequences: cached values can go stale and must be invalidated by deleting the entry, cached_property needs a __dict__ (so it does not work with plain __slots__), and tests can override a cached property simply by assigning to it.

Recap

  • Python privacy is a convention: _name means internal. Encapsulation means protecting invariants, not hiding data.
  • @property gives computed, read-only attributes; @x.setter validates and normalises assignments into self._x. Validate in __init__ by assigning through the property.
  • Start with plain attributes; switch to a property later without changing callers. Return tuples or copies, never internal mutable objects.
  • functools.cached_property computes once and stores in the instance dict; invalidate it whenever its inputs change.
  • __name is mangled to _Class__name (clash avoidance, not security). __slots__ saves memory and rejects typo attributes. Properties are data descriptors and win over the instance dict.
