10.3 Resource patterns

The toolbox for managing resources beyond a single with: contextlib.ExitStack for a dynamic number of resources and for undo actions, suppress, nullcontext, closing and redirect_stdout, classes that own a resource and close it reliably, temporary global state, cooperative deadlines, and pools. Why __del__ is not cleanup. Applied to files, seeds, clients, workspaces and compensating actions.

1ExitStack: a dynamic number of resources

A with statement names its context managers in the code, so it cannot open "one file per input path" when the number of paths is only known at run time. contextlib.ExitStack solves that: it is a context manager that you fill while the block runs. stack.enter_context(cm) enters cm and remembers to exit it; stack.callback(func, *args) registers any cleanup function. When the with ExitStack() block ends, normally or by an exception, everything registered is exited or called in reverse order, exactly as nested with statements would. If opening the fifth file fails, the four already open are closed.

exitstack.py
import os, tempfile
from contextlib import ExitStack

d = tempfile.mkdtemp()
paths = []
for name, text in [("a.txt", "alpha"), ("b.txt", "beta"), ("c.txt", "gamma")]:
    paths.append(os.path.join(d, name))
    with open(paths[-1], "w", encoding="utf-8") as f:
        f.write(text)

events = []
with ExitStack() as stack:
    files = [stack.enter_context(open(p, encoding="utf-8")) for p in paths]
    stack.callback(events.append, "callback ran last-in, first-out")
    print([f.read() for f in files])
print(all(f.closed for f in files), events)

try:
    with ExitStack() as stack:
        opened = [stack.enter_context(open(p, encoding="utf-8")) for p in paths + [os.path.join(d, "missing.txt")]]
except FileNotFoundError:
    print("missing file: the three opened ones were closed:", all(f.closed for f in files))
Output
['alpha', 'beta', 'gamma']
True ['callback ran last-in, first-out']
missing file: the three opened ones were closed: True

Two more methods make ExitStack useful beyond files. pop_all() moves everything registered so far into a new stack and leaves the current one empty, so the with block ends without closing anything: the pattern for a function that acquires several resources safely (if any acquisition fails, the earlier ones are released) and then hands them, still open, to its caller (problem 6). And callbacks turn any cleanup into part of the stack: deleting a temporary file, restoring a setting, sending an "aborted" event, or undoing a step that already happened (problem 15).

2Small helpers from contextlib

The contextlib module has a few one-line managers that remove a lot of boilerplate. suppress(*exceptions) ignores the listed exception types inside the block (7.3, 10.2). nullcontext(value) is a manager that does nothing and yields value, for code where a manager is optional: with (lock if lock else nullcontext()):. closing(obj) turns any object with a close() method into a manager that calls close() at the end, for older libraries that never implemented __enter__. redirect_stdout(target) (and redirect_stderr) sends print output to a file-like object for the duration of the block, which is how you capture the output of code that prints instead of returning. chdir(path) (Python 3.11+) changes the working directory temporarily.

contextlib_helpers.py
import io
from contextlib import suppress, nullcontext, closing, redirect_stdout

class LegacyConnection:
    def __init__(self):
        self.open = True
    def close(self):
        self.open = False

with closing(LegacyConnection()) as conn:
    print("open inside:", conn.open)
print("open after:", conn.open)

def process(items, lock=None):
    with lock if lock is not None else nullcontext():
        return sum(items)
print(process([1, 2, 3]))

buf = io.StringIO()
with redirect_stdout(buf):
    print("this goes into the buffer")
    help_text = "captured"
print(repr(buf.getvalue()), help_text)

cache = {"a": 1}
with suppress(KeyError):
    del cache["missing"]
print(cache)

3Classes that own a resource

An object that holds a connection, a session, a file or a subprocess owns that resource and should offer three things. A close() method that releases it and is idempotent (calling it twice is harmless, since cleanup code often runs from several places). Context manager support, __enter__ returning self and __exit__ calling close(), so with Client() as c: works. And a clear error when the object is used after closing, instead of a confusing failure deep inside the library (problem 7). This is the interface of files, sqlite3 connections, httpx.Client, and the OpenAI and Anthropic SDK clients.

What not to rely on is __del__, the finaliser Python may call when an object is garbage-collected. It runs at an unpredictable time (or, at interpreter shutdown, possibly not at all), it runs when other objects it needs may already be gone, exceptions inside it are ignored with only a warning, and reference cycles can delay it indefinitely (2.1). Use with or explicit close() for cleanup; if you need a last-resort safety net, weakref.finalize(obj, cleanup_func) is more predictable than __del__.

resource_owner.py
class Session:
    def __init__(self, name):
        self.name = name
        self._closed = False
        self.requests = 0

    @property
    def closed(self):
        return self._closed

    def send(self, payload):
        if self._closed:
            raise RuntimeError(f"session {self.name} is closed")
        self.requests += 1
        return f"sent {payload}"

    def close(self):
        if not self._closed:          # idempotent
            self._closed = True
            print(f"  {self.name}: released after {self.requests} requests")

    def __enter__(self):
        return self

    def __exit__(self, *exc):
        self.close()
        return False

with Session("api") as s:
    s.send("a"); s.send("b")
s.close()                             # harmless second close
try:
    s.send("c")
except RuntimeError as e:
    print("RuntimeError:", e)
Output
  api: released after 2 requests
RuntimeError: session api is closed

4Temporary global state

Some state is global to the process: the random number generator's state, environment variables, the current working directory, logging levels, NumPy's print options, a framework's "gradients enabled" switch (10.2). Code that changes it for a moment must save and restore the exact previous value, not reset it to some default, or it silently changes behaviour for everything that runs afterwards. A context manager is the right shape: save in __enter__ (or before yield), restore in __exit__ (or finally). For randomness, that means random.getstate() and random.setstate(), not random.seed(0) on exit (problem 9).

global_state.py
import os, random
from contextlib import contextmanager

@contextmanager
def seeded(seed):
    state = random.getstate()
    random.seed(seed)
    try:
        yield
    finally:
        random.setstate(state)

@contextmanager
def env(**values):
    old = {k: os.environ.get(k) for k in values}
    os.environ.update(values)
    try:
        yield
    finally:
        for k, v in old.items():
            if v is None:
                os.environ.pop(k, None)
            else:
                os.environ[k] = v

random.seed(123)
before = random.random()
random.seed(123)
with seeded(7):
    sample = [random.randint(1, 6) for _ in range(5)]
after = random.random()
print(sample, after == before)

with env(LLM_MODEL="large"):
    print("inside:", os.environ["LLM_MODEL"])
print("after:", os.environ.get("LLM_MODEL"))
Output
[3, 2, 4, 6, 1] True
inside: large
after: None

after == before shows that the code outside the block got exactly the random numbers it would have got without the block: the seeded section was invisible to it. That property is what keeps experiments reproducible when a library seeds randomness internally. Better still, avoid global state where you can: pass a random.Random(seed) instance (7.4) or a NumPy Generator to the code that needs randomness.

5Timers, deadlines and budgets as scopes

A context manager is a natural way to give a block of work a budget: a time limit, a token budget, a maximum number of model calls. In synchronous Python a manager cannot interrupt the block (8.3), so these scopes are cooperative: the block checks the budget at safe points (deadline.check() before each retry or each document), and the manager records whether the budget was exceeded when the block ends. With asyncio, asyncio.timeout(seconds) (14.5) can cancel the waiting task, which is the main reason timeouts work better in async code.

deadline.py
import time
from contextlib import contextmanager

class Deadline:
    def __init__(self, seconds, clock):
        self.seconds, self.clock = seconds, clock
        self.start = clock()

    def remaining(self):
        return self.seconds - (self.clock() - self.start)

    def check(self, step=""):
        if self.remaining() <= 0:
            raise TimeoutError(f"deadline of {self.seconds}s exceeded at {step or 'check'}")

@contextmanager
def deadline(seconds, clock=time.monotonic):
    d = Deadline(seconds, clock)
    yield d

ticks = iter([0.0, 1.0, 2.5, 3.5, 6.0])
done = []
try:
    with deadline(5, clock=lambda: next(ticks)) as d:
        for doc in ["a", "b", "c", "d"]:
            d.check(f"doc {doc}")
            done.append(doc)
except TimeoutError as e:
    print(done, "|", e)
Output
['a', 'b', 'c'] | deadline of 5s exceeded at doc d

Each check reads the clock once, so the scripted times make the outcome exact: three documents fit, and the fourth check finds the five seconds used up. Passing d.remaining() as the timeout of each network call is the other half of a deadline (7.4): no single call can then run past the budget either (problem 11).

6Pools: borrowing and returning resources

Some resources are expensive to create and limited in number: database connections, browser instances, GPU workers, licensed API sessions. A pool creates a few, lends one out per task, and takes it back afterwards, so tasks do not pay the creation cost and the total stays bounded. Lending is a context manager: with pool.acquire() as conn: returns the connection to the pool when the block ends, even if it raised. A subtle rule: if the block failed because the resource is broken (the connection dropped), the pool must discard that resource rather than lend it to the next task (problem 13). Connection pools in psycopg, SQLAlchemy and httpx follow this design.

solution.py
class Exporter:
    def __init__(self, sink):
        self.sink = sink
        self.closed = False

    def write(self, row):
        if self.closed:
            raise RuntimeError("exporter is closed")
        self.sink.append(row)

    def close(self):
        self.closed = True

    def __enter__(self):
        return self

    def __exit__(self, exc_type, exc, tb):
        self.close()
        return False

with requires __enter__ and __exit__; an object that only has close() does not qualify, which is why contextlib.closing(obj) exists for third-party objects you cannot change. For your own classes, adding the two methods is better: every user gets with Exporter(...) as e: and the cleanup is guaranteed even when a row fails. Returning False from __exit__ lets the ValueError reach the caller after the exporter has closed. The closed check in write turns use-after-close into a clear error.

solution.py
class LLMClient:
    def __init__(self, make_session):
        self._make_session = make_session
        self._session = None
        self._closed = False

    @property
    def closed(self):
        return self._closed

    def _get_session(self):
        if self._closed:
            raise RuntimeError("client is closed")
        if self._session is None:
            self._session = self._make_session()
        return self._session

    def complete(self, prompt):
        return self._get_session().post({"prompt": prompt})

    def close(self):
        if self._closed:
            return
        self._closed = True
        if self._session is not None:
            self._session.close()
            self._session = None

    def __enter__(self):
        return self

    def __exit__(self, *exc):
        self.close()
        return False

The client is the single owner of the session: it creates it (lazily, so a client that is never used opens no connection), reuses it for every request (one connection pool, not one per call), and closes it exactly once, however many times close() is called and whether the with block succeeded or not. The closed state is read-only from outside (9.3), and use-after-close fails with a message that says what happened. Taking make_session as a parameter is dependency injection (9.5), so tests pass a fake session. Real SDK clients (OpenAI(), anthropic.Anthropic(), httpx.Client()) behave this way, which is why you should create one client per application and close it at shutdown rather than one per request.

from contextlib import ExitStack, contextmanager

LOG = []

@contextmanager
def resource(name):
    LOG.append(f"open {name}")
    try:
        yield name
    finally:
        LOG.append(f"close {name}")

def run(job, use_cache, use_lock):
    with ExitStack() as stack:
        used = []
        if use_cache:
            used.append(stack.enter_context(resource("cache")))

class Deadline:
    def __init__(self, seconds, clock):
        self.seconds = seconds
        self.clock = clock
        self.elapsed = None
        self.overrun = None

    def __enter__(self):
        self.start = self.clock()
        return self

    def remaining(self):
        return max(0.0, self.seconds - (self.clock() - self.start))

    def check(self, step):
        if self.remaining() <= 0:
            raise TimeoutError(f"deadline exceeded at {step}")

    def timeout_for(self, default):
        return min(default, self.remaining())

    def __exit__(self, exc_type, exc, tb):
        self.elapsed = self.clock() - self.start
        self.overrun = self.elapsed > self.seconds
        return False

Trace the first test: the deadline starts at 100; checks at 101 and 102 pass; at 104.5 there are 0.5 seconds left, so "generate" passes; at 106 no time is left, so "verify" raises with the step named. The exit reads the clock once more (106) and records the overrun. Because the block cannot be interrupted, the work itself must cooperate: check before each step, and give each network call at most timeout_for(...) seconds, so no single call can blow the whole budget (7.4). Starting the clock at __enter__ rather than __init__ measures exactly the block. Request handlers use exactly this to keep a RAG pipeline within the latency budget promised to users.

from contextlib import contextmanager

class Pool:
    def __init__(self, factory, size):
        self.factory = factory
        self.size = size
        self._idle = []
        self._busy = 0
        self.created = 0

    def _take(self):
        if self._idle:
            res = self._idle.pop()
        elif self._busy + len(self._idle) < self.size:
            res = self.factory()
            self.created += 1
        else:
            raise RuntimeError("pool exhausted")
        self._busy += 1
        return res

    @contextmanager
    def acquire(self):
        res = self._take()
        try:
            yield res
        except ConnectionError:
            self._busy -= 1
            res.close()
            raise
        except BaseException:
            self._busy -= 1
            self._idle.append(res)
            raise
        else:
            self._busy -= 1
            self._idle.append(res)

    def close(self):
        while self._idle:
            self._idle.pop().close()

Lending is a scope, so acquire is a context manager: the resource is always returned, however the block ends. The pool distinguishes why the block failed: a ConnectionError means the resource itself is probably broken, so it is closed and dropped, and the next borrower gets a fresh one (the third connection created); any other error, such as bad input, says nothing about the resource, which goes back to the idle list. Counting busy resources keeps the total bounded by size, and an exhausted pool fails loudly rather than creating unlimited connections. A real pool would wait (with a timeout) instead of raising, and protect its state with a lock for threads or an asyncio.Lock for tasks (14.5).

        stack.callback(shutil.rmtree, path, ignore_errors=True)

solution.py
from contextlib import ExitStack

def run_saga(steps):
    completed, undo_errors = [], []

    def safe_undo(name, undo, result):
        try:
            undo(result)
        except Exception as e:
            undo_errors.append(f"undo of {name} failed: {type(e).__name__}: {e}")

    try:
        with ExitStack() as stack:
            results = []
            for name, do, undo in steps:
                result = do()
                results.append(result)
                completed.append(name)
                stack.callback(safe_undo, name, undo, result)
            stack.pop_all()
            return results
    except Exception as e:
        e.add_note("rolled back: " + ", ".join(reversed(completed)))
        for note in undo_errors:
            e.add_note(note)
        raise

Each completed step registers its undo on the stack, so the stack always holds exactly the compensations needed for the work done so far, in the right reverse order. On success, pop_all() discards them (the work is kept); on failure, leaving the with block runs them all before the error reaches the handler that adds the notes. Wrapping each undo in safe_undo means one failed compensation is recorded rather than aborting the others, and the original error stays the one the caller sees, with the rollback story attached as notes (7.2). This is the "saga" pattern used in distributed systems where no single transaction can cover every step, and it is how a careful agent framework should treat tool calls with side effects.

Interview

17. What is contextlib.ExitStack for? Give concrete uses.

SolutionModel answer

It manages a set of context managers and cleanup callbacks that is only known at run time, unwinding all of them in reverse order when the block exits, on success or failure, like an arbitrary number of nested with statements. Uses: opening a variable number of files or connections (if one fails, the ones already opened are closed); entering optional context managers without combinatorial if branches; registering arbitrary undo steps with callback, such as deleting temporary files, restoring environment variables or the working directory, or compensating completed side effects when a later step fails; and acquiring several resources safely then transferring ownership to the caller with pop_all(), which returns a new stack holding them. AsyncExitStack is the asynchronous counterpart for async with resources.

Interview

18. Why should you not rely on __del__ to release resources?

SolutionModel answer

__del__ runs when the object is about to be destroyed, which depends on the garbage collector, not on your program's logic. In CPython it usually runs when the last reference disappears, but reference cycles delay it until a collection, other interpreters (PyPy) collect at arbitrary times, a stored traceback or a cache can keep the object alive indefinitely, and at interpreter shutdown it may never run, or run when modules it depends on are already torn down. Exceptions raised inside it are ignored with a warning, so failures are invisible. Resources such as connections, file handles and locks therefore leak or are held far longer than intended. Release them deterministically with with or explicit close() calls (and try/finally), and if a safety net is needed, use weakref.finalize, which is more predictable and can be run explicitly.

Interview

19. Design the resource lifecycle of an LLM-backed web service.

SolutionModel answer

Separate resources by lifetime. Application scope: one LLM SDK client per provider (each holding an HTTP connection pool), database and vector store pools, the tokenizer and any loaded models, created once at start-up and closed at shutdown through the framework's lifespan context manager, using an ExitStack (or AsyncExitStack) so that if one fails to initialise, the others are cleaned up. Request scope: a tracing span, a deadline, a token budget, a database session or transaction, entered with with per request (often as framework dependencies with cleanup), so they close even when the client disconnects and the request task is cancelled. Stream scope: streaming responses as context managers, closed when the consumer stops, so the upstream connection is released and billing stops. Avoid creating clients per request, never rely on __del__, make close() idempotent, discard broken pooled connections, set timeouts on everything, and make temporary global state impossible by passing configuration explicitly. Test the lifecycle with fakes that count opens and closes, including on failures and cancellations, and monitor pool usage in production to catch leaks.

Recap

  • ExitStack manages a run-time number of managers and callbacks, unwinding them in reverse; pop_all() hands them over without closing.
  • contextlib helpers: suppress for specific errors, nullcontext for optional managers, closing for objects with close(), redirect_stdout to capture prints.
  • Classes that own a resource offer an idempotent close(), __enter__/__exit__, and a clear error after closing; never rely on __del__.
  • Temporary global state (random seeds, env vars, cwd) is saved and restored exactly, in finally; better still, avoid global state.
  • Budgets and deadlines are cooperative scopes in synchronous code; pools lend resources per block and discard broken ones; sagas register undo steps as they go.
