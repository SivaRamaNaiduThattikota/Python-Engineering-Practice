15.3 Command-line tools

Ingestion jobs, evaluation runs, data exports and admin tasks are run from the command line, by people and by schedulers. argparse from the ground up (positional and optional arguments, types, choices, flags, subcommands), the main(argv) pattern that makes tools testable, standard input, output and error, exit codes, configuration precedence, and entry points that turn a function into a command.

1argparse basics

sys.argv is the list of command-line words, starting with the program name. Parsing it by hand breaks on the first unusual input, so use argparse: create an ArgumentParser(prog=..., description=...), declare arguments with add_argument, and call parse_args(argv), which returns a namespace object with one attribute per argument. Positional arguments are required and identified by order (add_argument("source")). Optional arguments start with dashes (--out, short form -o), are identified by name, and take a default. type=int (or any function of one string) converts and validates the value, choices=[...] restricts it, required=True makes an option mandatory, action="store_true" makes a flag, nargs="+" collects one or more values, and help= documents it. argparse builds --help from these declarations and prints a usage message and exits with code 2 on invalid input.

2The main(argv) pattern

Structure every tool as a function main(argv=None) -> int: it builds the parser, parses argv (when argv is None, parse_args uses sys.argv[1:]), does the work, and returns an exit code instead of calling sys.exit deep inside. The file ends with if __name__ == "__main__": raise SystemExit(main()). Tests can then call main(["docs/", "--dry-run"]) and check the return value and output, without a subprocess, and the same function serves as the entry point of an installed command. Keep the CLI layer thin: parse arguments, call ordinary functions that do the work (and that other code can import), and translate their results and exceptions into output and exit codes.

Exit codes are the CLI's return value to the world: 0 for success, 1 for a general failure, 2 for bad usage (argparse's convention), and other small numbers for specific failures if callers need to tell them apart. Shell scripts (tool && next), CI pipelines, cron and orchestrators such as Airflow or Kubernetes jobs decide what to do from this number, so a tool that prints "error" and exits 0 makes failures invisible. raise SystemExit("message") prints the message to standard error and exits with 1.

3Standard input, output and error

Every process has three streams. Standard output is for the program's result, so it can be redirected to a file or piped into another program (rag-ingest docs/ | jq .). Standard error is for diagnostics: progress, warnings, errors and logs (12.3's handlers default to it), which stay visible on the terminal when stdout is redirected. Standard input lets a tool read data from a pipe (cat tickets.jsonl | classify --label spam); by convention a file argument of - means "read stdin". Mixing logs into stdout corrupts the data for the next program in the pipe. For testability, let main accept the streams as parameters with sys.stdin, sys.stdout and sys.stderr as defaults, and stream line by line (12.2) so large inputs work.

4Subcommands, configuration and entry points

Tools with several actions (git commit, uv add) use subcommands: parser.add_subparsers(dest="command", required=True) returns an object whose add_parser("ask") creates a parser per subcommand with its own arguments, and set_defaults(func=handler) attaches the function to call, so main ends with return args.func(args). Settings often come from several places; the usual precedence is defaults < configuration file < environment variables < command-line flags (12.4), which argparse supports through parser.set_defaults(**values_from_config_and_env) before parsing: explicit flags then override everything else (problem 8).

To install a command, declare an entry point in pyproject.toml: [project.scripts] with rag-ingest = "support_rag.cli:main". Installing the package (pip install -e ., uv sync) creates a small rag-ingest executable that imports support_rag.cli and calls main(), exiting with its return value. python -m support_rag runs a package's __main__.py, a useful second way in. Third-party libraries such as Click and Typer (which builds the parser from type hints) reduce boilerplate for larger tools; the principles (thin CLI layer, exit codes, streams) are the same.

import argparse, sys


def build_parser():
    p = argparse.ArgumentParser(prog="rag-ingest", description="Chunk documents for the vector index.")
    p.add_argument("source", help="folder with documents")
    p.add_argument("-o", "--out", default="chunks.jsonl", help="output JSONL file")
    p.add_argument("--chunk-size", type=int, default=200, help="words per chunk")
    p.add_argument("--overlap", type=int, default=0, help="words shared by neighbouring chunks")
    p.add_argument("--dry-run", action="store_true", help="show what would be done")
    return p


def main(argv=None):
    args = build_parser().parse_args(argv)
    if args.overlap >= args.chunk_size:
        print("error: overlap must be smaller than chunk size", file=sys.stderr)
        return 2
    print(f"source={args.source} out={args.out} chunk_size={args.chunk_size} overlap={args.overlap} dry_run={args.dry_run}")
    return 0

Building the parser in its own function lets tests and documentation tools inspect it, and main(argv) makes the whole command testable by passing a list instead of reading the real command line. Argument-level checks belong to argparse (types, choices); rules that involve several arguments, such as overlap versus chunk size, are checked after parsing, reported on standard error and turned into exit code 2, the same code argparse uses for bad usage. The summary goes to standard output because it is the command's result.

solution.py
import argparse, sys


def export(day):
    if day == "1999-01-01":
        raise ValueError("no data for that day")
    return f"exported {day}"


def main(argv=None):
    parser = argparse.ArgumentParser(prog="export")
    parser.add_argument("--day", required=True, help="day to export, YYYY-MM-DD")
    args = parser.parse_args(argv)
    try:
        print(export(args.day))
    except ValueError as e:
        print(f"error: {e}", file=sys.stderr)
        return 1
    return 0

sys.exit raises SystemExit, which ends the process, including a test run, when nobody catches it, and reading sys.argv ties the function to the real command line. Taking argv as a parameter and returning the code moves both decisions to the edge: the last line turns the return value into the process's exit code, while tests call main([...]) like any function. argparse still exits with 2 on bad usage, which is the one exit worth keeping (tests catch it). In the real file, if __name__ == "__main__": raise SystemExit(main()) connects the two worlds. Errors go to standard error, so they do not mix with the exported data.

def run(fn):

sys.exit() and sys.exit(0) both mean success (the code is None or 0); an integer is used as the exit status; a string is not a status at all: the interpreter prints it to standard error and exits with 1, a shortcut for fatal errors in scripts. Here nothing printed it because the exception was caught, and the message is in e.code. SystemExit derives from BaseException, not Exception, so a generic except Exception in a tool does not accidentally stop it from exiting.

import argparse, sys


def _positive(text):
    value = int(text)
    if value < 1:
        raise argparse.ArgumentTypeError("must be at least 1")
    return value


def _ask(args, client):
    print(client.ask(args.question, args.model))


def _models(args, client):
    for name in client.models():
        print(name)


def _batch(args, client):
    print(f"would run {args.file} with concurrency {args.concurrency}")


def main(argv=None, client=None):
    parser = argparse.ArgumentParser(prog="llmctl")
    sub = parser.add_subparsers(dest="command", required=True)
    ask = sub.add_parser("ask", help="ask one question")
    ask.add_argument("question")
    ask.add_argument("--model", default="small")
    ask.set_defaults(func=_ask)
    models = sub.add_parser("models", help="list models")
    models.set_defaults(func=_models)
    batch = sub.add_parser("batch", help="run a batch file")
    batch.add_argument("file")
    batch.add_argument("--concurrency", type=_positive, default=4)
    batch.set_defaults(func=_batch)
    args = parser.parse_args(argv)
    try:
        args.func(args, client)
    except ConnectionError as e:
        print(f"error: {e}", file=sys.stderr)
        return 1
    return 0

Subparsers give each action its own arguments and help text (llmctl batch --help), and set_defaults(func=...) stores the handler on the parsed namespace, so dispatch is one line with no if command == ... chain. Injecting client makes every subcommand testable with a fake (13.3). Connection problems are expected failures, reported as one clean line on standard error with exit code 1, rather than a traceback; programming errors still produce tracebacks, which is what you want for bugs. A custom type function rejects an invalid concurrency during parsing, with argparse's usual message and exit code 2.

solution.py
import argparse, json, sys


def main(argv=None, stdin=None, stdout=None, stderr=None):
    stdin, stdout, stderr = stdin or sys.stdin, stdout or sys.stdout, stderr or sys.stderr
    parser = argparse.ArgumentParser(prog="jsonl-filter")
    parser.add_argument("--label", required=True)
    parser.add_argument("--skip-bad", action="store_true")
    args = parser.parse_args(argv)
    total = kept = 0
    bad = False
    for n, line in enumerate(stdin, start=1):
        if not line.strip():
            continue
        try:
            record = json.loads(line)
        except json.JSONDecodeError:
            print(f"line {n}: invalid JSON", file=stderr)
            bad = True
            continue
        total += 1
        if record.get("label") == args.label:
            stdout.write(json.dumps(record, ensure_ascii=False) + "\n")
            kept += 1
    print(f"kept {kept} of {total} records", file=stderr)
    return 1 if bad and not args.skip_bad else 0

This is the shape of a Unix filter: data in on standard input, data out on standard output, everything else on standard error, so cat tickets.jsonl | jsonl-filter --label spam > spam.jsonl produces a clean file while warnings and the summary still appear on the terminal. Streaming line by line keeps memory constant for gigabyte inputs (12.2). The exit code tells a pipeline whether to trust the output: bad input fails the step unless the caller explicitly accepts it with --skip-bad. Accepting the streams as parameters is what makes the test above possible without spawning a process.

solution.py
import sys

def score(rows, stdout=None, stderr=None):
    stdout, stderr = stdout or sys.stdout, stderr or sys.stderr
    print("scoring", len(rows), "rows...", file=stderr)
    print("id,score", file=stdout)
    failed = False
    for row in rows:
        try:
            value = round(row["hits"] / row["total"], 3)
            print(f"{row['id']},{value}", file=stdout)
        except (KeyError, ZeroDivisionError) as e:
            print(f"skipping {row.get('id')}: {type(e).__name__}", file=stderr)
            failed = True
    print("done", file=stderr)
    return 1 if failed else 0

Anything on standard output becomes input for the next program, so scoring 3 rows... and done would be parsed as CSV rows, and skipping b too: the next tool either crashes or, worse, silently ingests garbage. Diagnostics belong on standard error, which a pipe does not capture. The exit code was the second lie: a scheduler saw success while a row was dropped. Returning 1 lets score ... && upload ... stop before uploading incomplete results; a --allow-failures option can make partial success explicit when that is acceptable.

import argparse
from pathlib import Path


def positive_int(text):
    try:
        value = int(text)
    except ValueError:
        value = 0
    if value < 1:
        raise argparse.ArgumentTypeError(f"must be an integer >= 1, got {text!r}")
    return value


def probability(text):
    try:
        value = float(text)
    except ValueError:
        value = -1.0
    if not 0.0 <= value <= 1.0:
        raise argparse.ArgumentTypeError(f"must be a probability in [0, 1], got {text!r}")
    return value


def existing_file(text):
    path = Path(text)
    if not path.is_file():
        raise argparse.ArgumentTypeError(f"no such file: {text!r}")
    return path


def build_parser():
    p = argparse.ArgumentParser(prog="train")
    p.add_argument("--epochs", type=positive_int, required=True)
    p.add_argument("--dropout", type=probability, required=True)
    p.add_argument("--data", type=existing_file, required=True)
    return p

A type is any function from a string to a value, so validation can happen during parsing, before any expensive work (loading data, allocating a GPU) starts. Raising ArgumentTypeError makes argparse print argument --epochs: <your message> with the usage line and exit with code 2, exactly like its built-in checks, so the user sees which argument is wrong and why. Returning a Path gives the rest of the program a ready-to-use object (12.1). These small functions are reusable across all of a project's commands.

solution.py
import importlib, tomllib


def _exit_code(code):
    if code is None:
        return 0
    if isinstance(code, int):
        return code
    return 1


def run_script(pyproject_text, name, argv):
    scripts = tomllib.loads(pyproject_text)["project"].get("scripts", {})
    if name not in scripts:
        raise LookupError(f"unknown command: {name}")
    module_name, _, attr = scripts[name].partition(":")
    fn = getattr(importlib.import_module(module_name), attr)
    try:
        return _exit_code(fn(argv))
    except SystemExit as e:
        return _exit_code(e.code)

When a package is installed, each [project.scripts] entry becomes an executable whose body is essentially this function: import the module, call the function, and pass its return value to sys.exit, so returning 0, 3 or None sets the process's exit code. argparse's own SystemExit(2) on bad usage and a legacy tool's SystemExit("message") are translated the way the interpreter does (a message means 1). Writing it once shows why the main(argv) -> int contract is so convenient: the same function works as an entry point, under python -m, and in tests.

solution.py
import argparse, json


def score(text):
    words = text.lower().split()
    return sum(w in {"win", "prize", "free", "click"} for w in words) / max(len(words), 1)


def _probability(text):
    try:
        value = float(text)
    except ValueError:
        value = -1.0
    if not 0.0 <= value <= 1.0:
        raise argparse.ArgumentTypeError(f"must be in [0, 1], got {text!r}")
    return value


def main(argv, stdin, stdout, stderr):
    parser = argparse.ArgumentParser(prog="classify")
    parser.add_argument("--threshold", type=_probability, default=0.5)
    parser.add_argument("--field", default="text")
    args = parser.parse_args(argv)
    failed = False
    for n, line in enumerate(stdin, start=1):
        if not line.strip():
            continue
        record = json.loads(line)
        try:
            text = record[args.field]
        except KeyError:
            print(f"line {n}: missing {args.field}", file=stderr)
            failed = True
            continue
        label = "spam" if score(text) >= args.threshold else "ham"
        stdout.write(json.dumps({"id": record["id"], "label": label}) + "\n")
    return 1 if failed else 0

Every defect is a rule from this lesson. Hand parsing accepted only one order of options; argparse accepts any order, generates help, and rejects bad values with exit code 2. The threshold stayed a string, so score(...) >= "0.5" would raise TypeError in Python 3; a type function converts and validates it. Reading all of stdin into a list breaks on large inputs, while iterating the stream handles any size. A record without the field crashed the whole run with a traceback; reporting it on standard error with its line number and continuing lets the rest of the data through, and the exit code still signals that something went wrong.

By default argparse accepts any unambiguous abbreviation, so --chunk means --chunk-size, which is convenient but means adding a new option such as --chunked later can break existing scripts; allow_abbrev=False turns it off. BooleanOptionalAction generates --cache and --no-cache. action="append" collects a repeated option into a list, which is the clean way to pass several tags. nargs="*" accepts zero values, so --exclude given alone produces an empty list, and -- stops option parsing so a file name starting with a dash is treated as a positional. parse_known_args returns the parsed namespace and the arguments it did not recognise, which wrappers use to pass options through to another program.

8Interview questions

Interview

14. What makes a good command-line tool?

SolutionModel answer

A good CLI is predictable for people and for programs. Arguments are parsed by a real parser (argparse, Click, Typer) with types, choices and good --help; required inputs are positionals or clearly named options; destructive actions need explicit confirmation or a --dry-run preview. Results go to standard output in a parseable format (JSON or JSONL for machines, a table for humans, ideally selectable with --format), and diagnostics go to standard error, so the tool composes in pipes. Exit codes are meaningful (0 success, 1 failure, 2 usage, documented others). Configuration follows a clear precedence (defaults, config file, environment, flags) and secrets come from the environment, never from flags that end up in shell history. It reads streams incrementally, handles Ctrl-C cleanly, is idempotent where possible, and its core logic lives in importable functions behind a thin main(argv) -> int, which makes it testable and reusable.

Interview

15. How do you test a command-line tool?

SolutionModel answer

Structure it so most tests do not need a subprocess: the business logic lives in ordinary functions tested directly, and main(argv, ...) takes the argument list and, ideally, the input and output streams as parameters. Tests then call main([...]) with io.StringIO streams (or pytest's capsys, 13.2) and assert on the return code, standard output and standard error separately, including error paths: bad arguments (argparse exits with 2, so catch SystemExit), invalid input lines, and failing dependencies replaced by fakes. Use tmp_path for files and monkeypatch for environment variables and configuration. Add a few end-to-end tests that run the installed entry point with subprocess.run([...], capture_output=True) to check packaging, the __main__ guard and real exit codes. Snapshot tests (13.P) work well for --help output and formatted tables.

Interview

16. A nightly pipeline step 'succeeded' but produced an empty file. What would you change in the tool?

SolutionModel answer

The tool lied through its exit code, so first make failures visible: return non-zero when anything went wrong (input missing or unreadable, zero records processed when some were expected, a dependency failing), and treat "nothing to do" explicitly (a flag such as --allow-empty, or a distinct exit code) rather than as silent success. Validate inputs and preconditions at start-up and fail fast with a clear message on standard error. Write output atomically (12.1) so a crash cannot leave a partial or empty file that the next step trusts, and only replace the previous output on success. Emit a summary (records read, written, skipped, errors) to standard error or as metrics, and a manifest next to the output, so the scheduler and people can check counts; downstream steps can verify the manifest before consuming. Finally, add tests for the failure paths and an alert on the scheduler side for unusually small outputs, because exit codes only catch what the tool knows is wrong.

Recap

  • Use argparse: positionals are required, options have defaults, type converts and validates, choices restricts, and bad usage exits with code 2.
  • Write main(argv=None) -> int and end the file with raise SystemExit(main()); keep the CLI layer thin over importable functions.
  • Results to standard output, diagnostics to standard error, data read from standard input line by line; accept streams as parameters for tests.
  • Exit codes are the tool's answer to schedulers and scripts: 0 success, non-zero failure, never print an error and exit 0.
  • Subcommands with set_defaults(func=...), configuration precedence via set_defaults, and [project.scripts] entry points that call main.
