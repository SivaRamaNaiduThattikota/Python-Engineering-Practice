15.2 Environments and dependencies

"It works on my machine" is usually a dependency problem. Virtual environments, pip and uv, how versions and specifiers work (PEP 440), requirement strings with extras and markers, pyproject.toml, lock files and why applications pin while libraries declare ranges, and the extra care ML stacks need. The browser cannot create environments or install packages, so problems work with the same building blocks the tools use: the packaging library that pip and uv rely on.

16 problems4 easy · 8 medium · 4 hard

1Virtual environments

Installing packages into the system Python mixes every project's dependencies in one site-packages folder, where project A needs pydantic 1 and project B needs pydantic 2, and upgrading one breaks the other (or the operating system's own tools). A virtual environment gives each project its own folder of installed packages: python -m venv .venv creates it, activating it (source .venv/bin/activate on Linux and macOS, .venv\Scripts\activate on Windows) puts its python and pip first on PATH, and inside it sys.prefix points at .venv while sys.base_prefix still points at the base installation. Use one environment per project, keep it out of git (.venv/ in .gitignore), and treat it as disposable: it is rebuilt from the dependency files, never edited by hand.

Always invoke pip as python -m pip, which guarantees it installs into the interpreter you are running; a bare pip may belong to another Python. Never use sudo pip. When something "is installed but cannot be imported", compare sys.executable and python -m pip --version: they usually belong to different environments.

2pip and uv

pip installs packages from PyPI (python -m pip install "httpx>=0.27"), from requirement files (-r requirements.txt), and from a local project in editable mode (pip install -e .), which links the source folder so code changes apply without reinstalling. pip freeze lists exactly what is installed. pip resolves dependencies but does not maintain a lock file on its own; pip-tools (pip-compile) adds one.

uv is a much faster, all-in-one replacement written in Rust and now widely used: uv venv creates an environment, uv add httpx adds a dependency to pyproject.toml and installs it, uv lock writes a cross-platform uv.lock with exact versions and hashes, uv sync makes the environment match the lock exactly (adding and removing packages), uv run pytest runs a command inside the project environment, and uv python install 3.13 installs interpreters. Poetry and PDM offer similar project workflows. Whatever the tool, the model is the same: declare what you need in pyproject.toml, lock what was resolved, sync environments from the lock.

3Versions and specifiers

Python versions follow PEP 440: a release such as 2.7.1, optionally with a pre-release (2.8.0a1, b2, rc1), a post-release (2.7.1.post1), a development release (2.8.0.dev3), or a local label (2.1.0+cu121, used by PyTorch for CUDA builds). They compare numerically segment by segment, so 1.10 is newer than 1.9, and pre-releases come before their final release. Most libraries use semantic versioning loosely: a major bump (2.x to 3.0) may break your code, a minor bump adds features, a patch fixes bugs; ML libraries break more often than that promise suggests, so pin tightly in applications.

A specifier constrains versions: ==2.7.1 exact, ==2.7.* any 2.7 release, !=2.7.0 excludes one, >=2.5,<3 a range, and the compatible release operator ~=2.5.1, meaning >=2.5.1,<2.6 (and ~=2.5 meaning >=2.5,<3). Pre-releases need care: installers (pip, uv) do not pick a pre-release when a final release satisfies the requirement, unless you opt in (--pre) or the specifier itself names a pre-release, and SpecifierSet.filter() follows that rule; but in packaging 26, contains() asked about one version accepts a pre-release that lies inside the range unless you pass prereleases=False, so be explicit when it matters (problem 2). A requirement string combines a name, optional extras in brackets that pull in optional dependencies (fastapi[standard], torch[cuda]), a specifier, and an optional environment marker after ; that limits when it applies (tomli>=2; python_version < "3.11"). The packaging library implements all of this, and it is what pip and uv use.

4pyproject.toml

Modern projects describe themselves in pyproject.toml (11.4's TOML). [project] holds the metadata: name, version, requires-python = ">=3.11", dependencies (the requirement strings the package needs at run time), and [project.optional-dependencies] for extras (pdf = ["pypdf>=4"], installed with pip install "mytool[pdf]"). [dependency-groups] (PEP 735) holds development-only groups such as dev = ["pytest", "ruff", "mypy"], which are not published with the package. [project.scripts] declares command-line entry points (15.3). [build-system] names the build backend (hatchling, setuptools, flit, uv's own) that turns the project into a wheel, the installable archive. With a src/ layout (src/mytool/__init__.py), tests import the installed package, not files that happen to be in the current folder (15.1).

5Lock files and reproducibility

Your direct dependencies have dependencies of their own (transitive dependencies), often dozens. If you declare only ranges, two installs a month apart can resolve to different versions, and a new release of a package you never heard of breaks your build. A lock file records the exact resolved version of every package, and usually its hash, so uv sync (or pip install -r requirements.lock --require-hashes) recreates the same environment on every machine and in CI and production. The rule of thumb: applications lock (services, pipelines, notebooks you need to rerun), libraries declare ranges (so they can be installed alongside other libraries) and test against the lowest and highest versions they claim to support. Update locks deliberately (uv lock --upgrade, Dependabot or Renovate pull requests), run the tests, and scan for known vulnerabilities (pip-audit).

ML environments add pitfalls: GPU builds of PyTorch and friends come from special package indexes and carry local version labels (+cu124), CUDA and driver versions must match, some packages ship platform-specific wheels only, and model behaviour can change between library versions. Pin the Python version (.python-version, requires-python), lock everything including the index URLs, record library versions next to saved models and evaluation results, and build production images from the lock file.

solution.py
from packaging.specifiers import SpecifierSet
from packaging.version import InvalidVersion, Version


def latest_compatible(available, spec, allow_prereleases=False):
    parsed = {}
    for v in available:
        try:
            parsed[v] = Version(v)
        except InvalidVersion:
            continue
    specifier = SpecifierSet(spec)
    ok = [v for v, ver in parsed.items() if specifier.contains(ver, prereleases=allow_prereleases or None) and (allow_prereleases or not ver.is_prerelease)]
    return max(ok, key=lambda v: parsed[v]) if ok else None

This is the first step of every resolver: from the versions an index offers, keep those the specifier allows and pick the newest. Comparing parsed Version objects is essential (2.10 is newer than 2.3, not older). Pre-releases are excluded by default, as pip and uv do, so >=3 does not silently pick up 3.0.0rc1; a specifier that itself mentions a pre-release, or an explicit flag, opts in. Invalid strings are skipped, because real indexes contain legacy version numbers that newer tools reject.

The compatible-release operator keeps every segment but the last: ~=1.4.2 allows 1.4.x from 1.4.2 on but not 1.5, and ~=1.4 allows any 1.x from 1.4 on but not 2.0. ==1.4.* matches the 1.4 series only, so 1.40 is not included. from packaging.requirements import InvalidRequirement, Requirement
from packaging.utils import canonicalize_name


def parse_requirements(text):
    out = {}
    for n, raw in enumerate(text.splitlines(), start=1):
        line = raw.split(" #", 1)[0].strip()
        if not line or line.startswith("#"):
            continue
        try:
            req = Requirement(line)
        except InvalidRequirement as e:
            raise ValueError(f"line {n}: {e}") from None
        name = canonicalize_name(req.name)
        if name in out:
            raise ValueError(f"duplicate requirement: {name}")
        out[name] = {"specifier": str(req.specifier), "extras": sorted(req.extras),
                     "marker": str(req.marker) if req.marker else None}
    return dict(sorted(out.items()))

Requirement strings have a precise grammar (PEP 508), and using the same parser as pip avoids subtle disagreements about extras, markers and specifiers. Project names are case-insensitive and treat -, _ and . as equivalent, so scikit_learn, Scikit-Learn and scikit.learn are one project; canonicalising before comparing is what catches the httpx/HTTPX duplicate, which pip would otherwise resolve unpredictably. Line numbers in errors make a 200-line requirements file fixable. A parser like this is the basis of dependency audits, licence checks and "what does this service depend on" dashboards.

import tomllib
from packaging.requirements import Requirement
from packaging.utils import canonicalize_name
from packaging.version import Version


def check_lock(pyproject_text, lock, environment=None):
    env = environment or {"python_version": "3.12"}
    deps = tomllib.loads(pyproject_text)["project"].get("dependencies", [])
    problems = []
    for line in deps:
        req = Requirement(line)
        if req.marker and not req.marker.evaluate(env):
            continue
        name = canonicalize_name(req.name)
        if name not in lock:
            problems.append(f"missing from lock: {name}")
        elif not req.specifier.contains(Version(lock[name]), prereleases=True):
            problems.append(f"{name} {lock[name]} does not satisfy {req.specifier}")
    return sorted(problems)

A lock that does not satisfy the project's own declared ranges means someone edited one file without regenerating the other, so CI tests one set of versions and pyproject.toml promises another; uv lock --check and poetry check --lock exist for exactly this. Markers decide whether a dependency applies at all (tomli is only needed before Python 3.11, when tomllib joined the standard library), so the same project can be in sync for one environment and not another. Extra entries in the lock are normal: they are transitive dependencies such as anyio, pulled in by httpx.

solution.py
from packaging.requirements import Requirement
from packaging.utils import canonicalize_name

def pin(requirements, resolved):
    out = []
    for line in requirements:
        req = Requirement(line)
        extras = f"[{','.join(sorted(req.extras))}]" if req.extras else ""
        marker = f"; {req.marker}" if req.marker else ""
        out.append(f"{req.name}{extras}=={resolved[canonicalize_name(req.name)]}{marker}")
    return out

A pin must be an exact ==, or the deploy is not reproducible: >= lets tomorrow's release in. Extras are part of what gets installed (transformers[torch] also installs PyTorch), and markers are part of where it gets installed, so dropping either changes the environment silently. Rebuilding the string from the parsed parts keeps them, and packaging normalises the marker's quotes. Real lock tools also record hashes and the index URL; this is the core of pip-compile's output.

import ast, sys
from packaging.requirements import Requirement
from packaging.utils import canonicalize_name


def dependency_report(sources, declared, import_to_dist, local=()):
    imported = set()
    for src in sources.values():
        for node in ast.walk(ast.parse(src)):
            if isinstance(node, ast.Import):
                imported.update(alias.name.split(".")[0] for alias in node.names)
            elif isinstance(node, ast.ImportFrom) and node.level == 0 and node.module:
                imported.add(node.module.split(".")[0])
    third_party = {n for n in imported if n not in sys.stdlib_module_names and n not in local}
    needed = {canonicalize_name(import_to_dist.get(n, n)) for n in third_party}
    have = {canonicalize_name(Requirement(r).name) for r in declared}
    return {"missing": sorted(needed - have), "unused": sorted(have - needed)}

Two common failures in real projects: code imports a package that is only installed by accident (a transitive dependency, or something in the developer's environment), so a clean install in CI or production breaks; and pyproject.toml keeps dependencies nobody uses, slowing installs and widening the security surface. Static analysis with ast finds both without running the code, including imports inside functions such as tiktoken. The mapping is necessary because import names and distribution names often differ (sklearn is scikit-learn, yaml is PyYAML, cv2 is opencv-python). Tools such as deptry run this check in CI.

11. A tiny dependency resolver

Write resolve(index, requirements) where index maps package names to {version: [requirement strings of that version's dependencies]} and requirements is a list of requirement strings. Choose one version per package such that every requirement (from the root and from every chosen version) is satisfied, preferring the newest versions, with backtracking when a choice leads to a conflict. Return a dict name -> version sorted by name, or raise ValueError("no solution"). Ignore pre-releases and markers.

Hint 1Open a hint

Recursive search over a list of pending requirements and a dict of choices: pop a requirement; if its package is chosen, check the version satisfies it; otherwise try the index's versions newest first that satisfy all constraints collected so far for that package.

Hint 2Open a hint

Keep constraints per package (a dict name -> list of specifiers) so a later requirement can reject an earlier choice; on failure, undo and try the next version.

SolutionShow the solution and why
solution.py
from packaging.requirements import Requirement
from packaging.specifiers import SpecifierSet
from packaging.version import Version


def resolve(index, requirements):
    def ok(name, version, constraints):
        return all(Version(version) in spec for spec in constraints.get(name, []))

    def search(pending, chosen, constraints):
        if not pending:
            return dict(chosen)
        req, rest = pending[0], pending[1:]
        name = req.name
        new_constraints = {k: list(v) for k, v in constraints.items()}
        new_constraints.setdefault(name, []).append(req.specifier)
        if name in chosen:
            if not ok(name, chosen[name], new_constraints):
                return None
            return search(rest, chosen, new_constraints)
        candidates = sorted(index.get(name, {}), key=Version, reverse=True)
        for version in candidates:
            if Version(version).is_prerelease or not ok(name, version, new_constraints):
                continue
            deps = [Requirement(d) for d in index[name][version]]
            result = search(rest + deps, {**chosen, name: version}, new_constraints)
            if result is not None:
                return result
        return None

    result = search([Requirement(r) for r in requirements], {}, {})
    if result is None:
        raise ValueError("no solution")
    return dict(sorted(result.items()))

Dependency resolution is a search problem: each package needs one version, every chosen version adds constraints, and a choice that looks fine early can conflict with a requirement found later. Here the newest app-sdk needs pydantic>=2, so adding legacy-tool (which needs pydantic<2) forces the resolver to backtrack to app-sdk 1.5.0, whose constraints are compatible; with app-sdk>=2 pinned there is no solution at all, the "dependency hell" every developer meets. Trying newest versions first matches what pip and uv do. Real resolvers use smarter algorithms (pip's backtracking, uv's PubGrub, which also explains conflicts in plain language), but the core is this depth-first search with undo (16.5).

solution.py
from packaging.requirements import Requirement
from packaging.utils import canonicalize_name
from packaging.version import Version


def check_environment(required, installed):
    have = {canonicalize_name(k): v for k, v in installed.items()}
    problems = []
    for line in required:
        req = Requirement(line)
        name = canonicalize_name(req.name)
        if name not in have:
            problems.append(f"missing: {name}")
        elif not req.specifier.contains(Version(have[name]), prereleases=True):
            problems.append(f"{name} {have[name]} not in {req.specifier}")
    return sorted(problems)

Each bug is a rule from this lesson. String comparison declared 1.9.0 newer than 1.26 and 1.10.0 older than 1.4. Distribution names are case-insensitive and scikit_learn is the same project as scikit-learn, so names must be canonicalised on both sides. partition(">=") broke on extras and on any other operator; the real Requirement parser handles the whole grammar. And 2.6.0rc1 is a pre-release of 2.6, which sorts below 2.6 but is still outside <2.6 in spirit: with prereleases=True it is judged against the range and packaging excludes it, because <2.6 rejects pre-releases of 2.6 itself. Checks like this run at service start-up or in a notebook's first cell to fail fast on a wrong environment.

Interview

14. Why do you use virtual environments, and how do you set up a new project today?

SolutionModel answer

A virtual environment isolates a project's installed packages from the system and from other projects, so incompatible versions can coexist, the system Python's tools are not broken, and the environment can be deleted and rebuilt at will. For a new project I would pin the Python version (.python-version, requires-python), create the project with uv init (or a pyproject.toml by hand) in a src/ layout, add runtime dependencies with uv add and development tools with uv add --dev (pytest, ruff, mypy) into a dependency group, commit pyproject.toml and the lock file but not .venv, and use uv sync / uv run locally and in CI so everyone runs the locked versions. With plain pip, the equivalent is python -m venv .venv, python -m pip install -e ".[dev]" and a compiled requirements lock. The point is that the environment is reproducible from files in the repository.

Interview

15. Should a library pin exact dependency versions? Should an application?

SolutionModel answer

A library should declare the broadest ranges it actually supports (httpx>=0.25,<1), not exact pins: it will be installed alongside other libraries, and exact pins make conflicts likely (two libraries pinning different exact versions of a shared dependency cannot be installed together). It should test against its minimum and latest supported versions, and set upper bounds only for known incompatibilities. An application (a service, a pipeline, a training job) should lock every direct and transitive dependency to exact versions with hashes, so every install is identical and builds are reproducible, while still declaring ranges in pyproject.toml so the lock can be regenerated. Locks are upgraded deliberately and regularly (automated update pull requests plus the test suite) to pick up security fixes without surprises.

Interview

16. How do you make an ML project's environment reproducible six months from now?

SolutionModel answer

Pin the interpreter (requires-python and a .python-version, ideally a specific minor version), declare dependencies in pyproject.toml, and commit a lock file with exact versions and hashes for every package, including the package index URLs used for GPU builds (PyTorch's CUDA wheels with local labels such as +cu124). Record the system-level pieces the lock cannot capture: CUDA and cuDNN versions, driver requirements, and the operating system, ideally by building a container image from the lock file with a pinned base image digest, and keep the built image in a registry, since base images and indexes change. Store the environment's identity (lock hash, image digest, pip freeze output) next to every trained model, dataset version and evaluation result, so results can be traced to the exact stack. Seed randomness and enable deterministic algorithms where needed. Finally, test the rebuild: CI should create the environment from scratch from the lock, so drift is noticed early.

Recap

  • One virtual environment per project; run tools as python -m pip or through uv, and rebuild environments from files rather than editing them.
  • PEP 440 versions compare numerically with pre-, post-, dev- and local parts; never compare version strings directly.
  • Specifiers (>=, <, ~=, ==X.*) constrain versions, extras add optional dependencies, markers limit where a requirement applies; packaging parses them all.
  • pyproject.toml declares the project: dependencies, extras, dependency groups, scripts and build backend.
  • Applications lock exact versions with hashes; libraries declare ranges; ML stacks also pin Python, CUDA builds and images.
