3.3 Scope: local, enclosing, global, built-in

Where Python looks up a name, why assigning to a name anywhere in a function changes how it is read everywhere in that function, when global and nonlocal are needed, and why module-level state makes data and LLM code hard to test.

17 problems4 easy · 8 medium · 5 hard

1Where Python looks for a name: LEGB

A scope is the part of a program where a name refers to one particular variable. When Python reads a name, it searches scopes in a fixed order and uses the first match:

  • L, Local: names assigned inside the function that is running, including its parameters.
  • E, Enclosing: names in any function that contains this function (only for functions defined inside other functions).
  • G, Global: names assigned at the top level of the module (the file), including imports and defs.
  • B, Built-in: names Python provides everywhere, such as len, print, range and ValueError.
legb.py
MODEL = "small"                       # global

def outer():
    prefix = "doc"                    # local to outer, enclosing for inner
    def inner(i):
        text = f"{prefix}-{i}"        # i and text are local; prefix is found in E
        return text, MODEL, len(text) # MODEL found in G, len in B
    return inner(7)

print(outer())
Output
('doc-7', 'small', 5)

Two details matter. A new local scope is created on every call, so locals from one call never leak into the next (that is why recursion works, 3.1). And only functions create scopes in Python: an if block or a for loop does not. A variable assigned inside a loop is a normal local of the surrounding function and is still visible after the loop (1.2).

≈
SQL / Power BI

LEGB is like name resolution in nested SQL: a column name in a subquery is looked up in that subquery's own tables first, then in the outer query (a correlated subquery), and finally in what the database provides. In DAX, a VAR defined inside a measure hides a measure or column with the same name for the rest of that expression, just as a local hides a global.

2Assignment decides the scope, for the whole function

Reading a name searches LEGB. Assigning works differently, and this is the part that causes real bugs. When Python compiles a function, it scans the whole body. Any name that is assigned anywhere in the function (with =, +=, a for target, an import, a def or with ... as) becomes a local name for the entire function, even on lines before the assignment.

unbound_local.py
count = 10

def read_only():
    return count + 1          # count is only read: found in G

def broken():
    print("before:", count)   # count is assigned below, so it is LOCAL here too
    count = 0

print(read_only())
try:
    broken()
except UnboundLocalError as e:
    print("UnboundLocalError:", e)
Output
11
UnboundLocalError: cannot access local variable 'count' where it is not associated with a value

Step by step: at compile time, broken contains count = 0, so count is a local of broken everywhere in it. At run time, the first line reads that local before anything was assigned to it, which is UnboundLocalError. It does not fall back to the global count, because the decision "local or not" was made for the whole function before it ran. The same happens with total += x inside a function when total was meant to be the module's variable: += is an assignment, so it makes total local.

The rule gives you three ways out, from best to worst: pass the value in as a parameter and return the new value; use a different local name; or declare that you mean the outer variable, with global or nonlocal (next section).

3global and nonlocal

global name at the top of a function says: in this function, name refers to the module-level variable, for reading and assigning. nonlocal name says the same about the nearest enclosing function's variable. Both are only needed to rebind the outer name. Changing a mutable object that an outer name already points at needs no declaration at all, because that is not an assignment to the name (2.2).

global_nonlocal.py
calls = 0
seen = []

def track(item):
    global calls
    calls += 1              # rebinds the global name: needs `global`
    seen.append(item)       # changes the global list in place: no declaration needed

track("a"); track("b")
print(calls, seen)

def make_counter():
    n = 0
    def bump():
        nonlocal n          # rebinds outer's n, not a new local
        n += 1
        return n
    return bump

bump = make_counter()
print(bump(), bump(), bump())
Output
2 ['a', 'b']
1 2 3

nonlocal is what makes a closure that keeps changing state, like this counter, work (lesson 3.4 is about closures). global is legal but usually a sign of hidden shared state, which is the next section's subject.

4Why module-level state hurts

A function that reads or writes a global variable depends on something its signature does not show. In data and LLM code that causes three specific problems:

  • Results depend on history. A global counter, cache or "current model" means calling the same function twice can give different results, which breaks reproducibility and notebooks run out of order.
  • Tests interfere with each other. One test changes the global, and the next test sees the changed value.
  • Concurrency breaks it. In a web server (FastAPI) or with threads, many requests share one module, so a global "current user" or "last prompt" leaks between requests (Module 14).
module_state.py
current_user = None                       # module state: shared by every request

def handle(user, question):
    global current_user
    current_user = user
    return answer(question)

def answer(question):
    return f"answering {question!r} for {current_user}"

print(handle("ana", "refund?"))
# Imagine two requests interleaved in a server: the second overwrites current_user
current_user = "ben"
print(answer("refund?"))                  # a later call sees whoever wrote last
Output
answering 'refund?' for ana
answering 'refund?' for ben

The fix is almost always the same: pass what a function needs as parameters, return results, and keep state in an object that is created per run or per request (a dict, a class instance in Module 9, or FastAPI's request-scoped dependencies). Module-level constants (MAX_TOKENS = 4096, a compiled regex, a loaded config that is never changed) are fine; module-level variables that change are the problem.

5Shadowing built-ins, and two special scopes

Because built-ins are searched last, any global or local with the same name hides them. Naming a variable list, id, sum, max, input, type or dict is legal, and breaks every later use of the built-in in that scope with a confusing error far from the cause.

shadowing.py
def total_length(docs):
    sum = 0                     # shadows the built-in sum inside this function
    for d in docs:
        sum += len(d)
    return sum

print(total_length(["ab", "cde"]))

def average_length(docs):
    sum = 0
    for d in docs:
        sum += len(d)
    return sum / len(docs), sum([1, 2])   # the built-in is gone here

try:
    average_length(["ab"])
except TypeError as e:
    print("TypeError:", e)
Output
5
TypeError: 'int' object is not callable

Two places have scope rules worth knowing. A comprehension has its own scope, so its loop variable does not leak out (unlike a for loop). And a class body is a scope that is not an enclosing scope for the methods inside it: a method cannot see a class-level name without self. or the class name (Module 9).

comprehension_scope.py
x = "outer"
squares = [x * 2 for x in range(3)]
print(squares, x)              # the comprehension's x did not leak

for y in range(3):
    pass
print(y)                       # a for loop's variable does leak
Output
[0, 2, 4] outer

4. Changing versus rebinding a global

cache = {}
hits = 0

def remember(key, value):
    cache[key] = value

def reset_cache():
    cache = {}

def count_hit():
    global hits
    hits += 1

remember("a", 1)
reset_cache()
count_hit(); count_hit()
print(cache, hits)

Which of these functions assign to a name, and which only change an object?

SolutionShow the solution and why

remember changes the global dict in place, so no declaration is needed and the change is visible. reset_cache assigns cache = {}, which makes cache local to that function: the global dict is not reset at all, a bug that raises no error. count_hit declares global hits, so its += rebinds the module's name. 7. A call counter without globals

You want to count how many times an LLM client function is called, per client. Write make_counted(fn) that returns (wrapper, get_count): wrapper(*args, **kwargs) calls fn and counts the call, and get_count() returns the number of calls so far. Each make_counted call must have its own independent count. Use nonlocal, not a global.

TestsThe 2 checks Run tests uses
def complete(prompt, *, model="small"):
    return f"{model}:{prompt}"
w1, c1 = make_counted(complete)
w2, c2 = make_counted(complete)
assert w1("a") == "small:a" and w1("b", model="large") == "large:b"
w2("x")
assert c1() == 2 and c2() == 1
HintOpen a hint

Keep count = 0 inside make_counted, define wrapper and get_count inside it, and use nonlocal count in wrapper.

SolutionShow the solution and why
solution.py
def make_counted(fn):
    count = 0

    def wrapper(*args, **kwargs):
        nonlocal count
        count += 1
        return fn(*args, **kwargs)

    def get_count():
        return count

    return wrapper, get_count

count lives in the scope of one make_counted call, so every call creates a separate counter, unlike a module global that all clients would share. wrapper needs nonlocal because count += 1 rebinds the name; get_count only reads it, so it needs nothing. Both inner functions see the same count, which is why the getter reports what the wrapper counted. This is a closure (lesson 3.4) and the core of a decorator (Module 7).

    total = sum(scores)
    best = max(scores)

9. Looking up a setting inside the loop

Both scale a million numbers by a factor stored deep inside a module-level config. Which loop is faster?

setup
CONFIG = {"model": {"scaling": {"factor": 3}}}
xs = list(range(1_000_000))
def scale_lookup(xs):
    out = []
    for x in xs:
        out.append(x * CONFIG["model"]["scaling"]["factor"])
    return out
def scale_once(xs):
    factor = CONFIG["model"]["scaling"]["factor"]
    out = []
    for x in xs:
        out.append(x * factor)
    return out
HintOpen a hint

How many lookups does each pass of A perform before it can multiply?

SolutionShow the solution and why
OptionTime per run (measured at build time)
A218.50 ms
B96.69 ms

A reads the global CONFIG and then does three dict lookups on every pass, a million times, to fetch a value that never changes. B does them once, before the loop, and keeps the result in a local name, which is the cheapest kind of name to read (locals live in fixed slots of the function's frame). CONFIG = {"threshold": 0.5, "positive": "spam", "negative": "ham"}

    return config["positive"] if score >= config["threshold"] else config["negative"]

    return [classify(s, config) for s in scores]

Each function now shows its dependency in its signature, and a test or an experiment can pass a different config without touching the global. This preprocessing module keeps its vocabulary and statistics in module-level variables. Fitting on a second dataset mixes in the first one's vocabulary, and transforming before fitting silently uses stale values. TestsThe 4 checks Run tests uses

state_b = fit(["a bird"])

Hint 1Open a hint

Build the vocabulary and the mean in local variables inside fit, and return them in a dict.

Hint 2Open a hint

transform(text, state) reads state["vocab"] and state["mean_len"].

SolutionShow the solution and why
solution.py
def fit(texts):
    vocab = {}
    for text in texts:
        for word in text.lower().split():
            if word not in vocab:
                vocab[word] = len(vocab)
    mean_len = sum(len(t.split()) for t in texts) / len(texts)
    return {"vocab": vocab, "mean_len": mean_len}


def transform(text, state):
    ids = [state["vocab"].get(w, -1) for w in text.lower().split()]
    return {"ids": ids, "len_ratio": len(ids) / state["mean_len"]}

The original has both scope bugs from this lesson. VOCAB is changed in place without global, so every fit call adds to the same dict and the second dataset's ids continue after the first's. MEAN_LEN is rebound with global, so transform reads whichever fit ran last, or 0.0 before any fit (a ZeroDivisionError far from the cause). Returning the state makes "fitted" a value you can store, pass, compare and version. That is exactly the fit/transform design of scikit-learn, except that it keeps the state on the estimator object (vocabulary_, mean_), one object per fit, never at module level.

14. Count words without leaking state

Write make_word_counter() that returns three functions (add, top, reset) sharing one private word count: add(text) counts the lower-cased words of text, top(n) returns the n most common (word, count) pairs (highest count first, ties in first-seen order), and reset() clears the counts. Two counters must never share data, and nothing at module level may change.

TestsThe 4 checks Run tests uses
add, top, reset = make_word_counter()
add2, top2, _ = make_word_counter()
add("The cat and the hat")
add("the end")
add2("other")
assert top(2) == [("the", 3), ("cat", 1)]
assert top2(5) == [("other", 1)]
reset()
assert top(3) == []
add("again again")
assert top(1) == [("again", 2)]
Hint 1Open a hint

Keep counts = {} in the outer function. add and reset change that dict in place, so do they need nonlocal?

Hint 2Open a hint

sorted(counts.items(), key=lambda kv: -kv[1]) sorts by count, and Python's sort is stable, so ties keep insertion order.

SolutionShow the solution and why
solution.py
def make_word_counter():
    counts = {}

    def add(text):
        for word in text.lower().split():
            counts[word] = counts.get(word, 0) + 1

    def top(n):
        return sorted(counts.items(), key=lambda kv: -kv[1])[:n]

    def reset():
        counts.clear()

    return add, top, reset

All three functions close over the same counts dict, and every operation changes that dict in place (counts[word] = ..., counts.clear()), so no nonlocal is needed. If reset were written counts = {} it would create a new local dict and the shared counts would not be cleared, the same bug as reset_cache in problem 4, and nonlocal counts would be required. Sorting with a negated count keeps ties in insertion order because Python's sort is stable (lesson 4.2). collections.Counter does the counting part for you (lesson 4.6).

9Interview questions

Interview

15. Explain the LEGB rule, and why assigning to a variable inside a function can cause UnboundLocalError.

SolutionModel answer

When Python reads a name it searches Local, Enclosing, Global, then Built-in scopes and uses the first match. Which scope a name belongs to in a function is decided at compile time: if the name is assigned anywhere in the function (=, +=, for, import, def, with ... as), it is local throughout that function. So reading it before the assignment raises UnboundLocalError instead of falling back to the global. Fixes: pass the value in and return the result, use a different name, or declare global / nonlocal if you really mean the outer variable. Mention that only rebinding needs a declaration; changing a mutable outer object in place does not.

Interview

16. What is the difference between global and nonlocal, and when should you use them?

SolutionModel answer

global x makes x refer to the module-level variable for reading and rebinding inside the function. nonlocal x makes it refer to the nearest enclosing function's variable, and is an error if no enclosing function has one. nonlocal is the normal tool for closures that update state (counters, accumulators, memoising wrappers). global is legal but usually a design smell: hidden shared state makes code non-reproducible, hard to test and unsafe under concurrency. Prefer parameters and return values, or an object that owns the state.

Interview

17. Your FastAPI app stores the current user's id in a module variable. What can go wrong, and what do you do instead?

SolutionModel answer

A module is loaded once per worker process and shared by every request that process handles. With async endpoints, requests interleave at every await; with threads, they run at the same time. So one request can set the variable and another can overwrite it before the first one reads it, and responses (or LLM context) for one user get built with another user's data. It never shows in single-user testing. Instead: pass the user explicitly, use FastAPI dependencies (Depends) that compute per-request values, or contextvars.ContextVar when a value must flow through many layers, since it gives each request (task) its own value. Module-level constants and read-only clients are fine; module-level mutable per-request data is not.

Recap

  • Reading a name searches Local, Enclosing, Global, Built-in. Only functions (and comprehensions, classes) create scopes, not if or for.
  • Any assignment anywhere in a function makes that name local for the whole function, decided at compile time. That is the source of UnboundLocalError.
  • global / nonlocal are needed only to rebind an outer name; changing an outer mutable object in place needs no declaration.
  • Module-level variables that change make results depend on history, tests interfere, and servers leak data between requests. Pass values in and return results.
  • Never name variables after built-ins (list, id, max, sum): the error appears far from the cause.
