13.2 Fixtures

Real tests need things: a temporary folder, a configured client, a database with three rows, an environment variable that must be restored afterwards. Fixtures provide them. How pytest injects fixtures by name, yield for cleanup, scopes and their traps, parametrised and factory fixtures, conftest.py, and the built-in fixtures tmp_path, monkeypatch, capsys and caplog. As in 13.1, most problems are graded by running your tests against buggy versions.

18 problems4 easy · 9 medium · 5 hard

1Fixtures: dependencies by name

Tests often need the same preparation: a list of sample documents, a configured object, a file on disk. Copying that code into every test is noisy, and putting it in module-level variables shares mutable state between tests, which makes them depend on each other's order. A fixture is a function decorated with @pytest.fixture that builds the thing; a test asks for it by naming a parameter after it, and pytest calls the fixture, passes the result in, and does it again, freshly, for the next test. Fixtures can ask for other fixtures the same way, so setup is composed from small pieces.

This is dependency injection: the test declares what it needs and the framework supplies it. It also makes tests read well: def test_search_ranks_exact_match_first(store, sample_docs): says what the test needs without saying how it is built.

fixtures.py
import re
from lessontools import run_pytest

SRC = '''
import pytest

@pytest.fixture
def docs():
    print("<building docs>")
    return [{"id": "faq-1", "text": "Refunds take 5 days"}, {"id": "faq-2", "text": "Shipping is free"}]

@pytest.fixture
def index(docs):
    print(f"<building index from {len(docs)} docs>")
    return {d["id"]: d["text"].lower() for d in docs}

def test_lookup(index):
    assert index["faq-1"] == "refunds take 5 days"

def test_mutation_is_private(docs):
    docs.append({"id": "faq-3", "text": "x"})
    assert len(docs) == 3

def test_fresh_again(docs):
    assert len(docs) == 2
'''
r = run_pytest(SRC, args=["-s", "--tb=no"])
print(r["outcomes"])
print(re.findall(r"<([^<>]+)>", r["output"]))
Output
{'test_lookup': 'passed', 'test_mutation_is_private': 'passed', 'test_fresh_again': 'passed'}
['building docs', 'building index from 2 docs', 'building docs', 'building docs']

-s turns off pytest's output capturing so the prints are visible, and --tb=no hides tracebacks; the markers in angle brackets are only there to pick the prints out of pytest's report. docs was built three times, once per test that needed it (index asked for it in the first test, so pytest built docs before index), which is why the list appended to in the second test is gone in the third.

2Cleanup with yield

A fixture that acquires something must release it. Write it as a generator: code before yield is the setup, the yielded value goes to the test, and code after yield is the teardown, which runs after the test whether it passed or failed, like the finally of a context manager (10.2). When a test uses several fixtures, teardowns run in reverse order of setup. If setup raises, the test is reported as an error (not a failure), which tells you the problem is in the preparation; a failing teardown is also an error.

teardown.py
import re
from lessontools import run_pytest

SRC = '''
import pytest

@pytest.fixture
def connection():
    print("<open connection>")
    yield {"open": True}
    print("<close connection>")

@pytest.fixture
def transaction(connection):
    print("<begin>")
    yield []
    print("<rollback>")

def test_insert(transaction):
    transaction.append("row")
    assert transaction == ["row", "other"]
'''
r = run_pytest(SRC, args=["-s", "--tb=no"])
print(r["outcomes"])
print(re.findall(r"<([^<>]+)>", r["output"]))

3Scopes, autouse and conftest.py

By default a fixture has function scope: it is created for every test that uses it. @pytest.fixture(scope="module") creates it once per test file, "class" once per test class, and "session" once per test run, which is how you share something expensive such as a loaded model, a started container or a database schema. The trap: a shared object is shared, so if one test mutates it, the next sees the change, and the suite becomes order-dependent (problem 7). Share only read-only things at wide scope, or pair a wide-scoped resource with a function-scoped fixture that resets it (a session database plus a per-test transaction that is rolled back). A fixture can only use fixtures of the same or wider scope.

autouse=True applies a fixture to every test in its scope without naming it, useful for "always reset this global" or "never allow network calls", but invisible to readers, so use it sparingly. Fixtures defined in a file named conftest.py are available to every test file in that folder and below, with no import; a project usually has one at the top of tests/ for shared fixtures and more in subfolders for specific ones.

A fixture can be parametrised: @pytest.fixture(params=["small", "large"]) runs every test that uses it once per parameter, with the value in request.param, which is how one test suite is run against several backends or models. And when tests need several similar objects with variations, a factory fixture returns a function (make_doc(id="faq-1", text=...)) rather than one object, keeping defaults in one place and letting each test state only what matters to it (problem 12).

4Built-in fixtures

pytest ships fixtures for the usual sources of non-isolation. tmp_path gives each test a fresh, empty pathlib.Path folder, so tests never write into the project or collide with each other (12.1). monkeypatch changes things for one test and undoes them afterwards: monkeypatch.setenv("KEY", "value") and delenv("KEY", raising=False) for environment variables (12.4), monkeypatch.setattr(module, "name", replacement) to swap a function or attribute (13.3 builds on this), monkeypatch.chdir(path) and monkeypatch.setitem(dict, key, value). capsys captures what the code prints: capsys.readouterr() returns an object with .out and .err. caplog captures log records (12.3): caplog.records, caplog.messages, and caplog.set_level(logging.INFO) to make sure records below the default level are kept. request gives fixtures information about the test using them, and recwarn records warnings.

builtin.py
from lessontools import run_pytest

SRC = '''
import logging, os

def save_greeting(folder, name):
    path = folder / "greeting.txt"
    path.write_text(f"Hello, {name}", encoding="utf-8")
    print("saved", path.name)
    logging.getLogger("app").warning("wrote %s", path.name)
    return path

def test_writes_into_tmp_path(tmp_path, capsys, caplog):
    path = save_greeting(tmp_path, os.environ["USER_NAME"]) if "USER_NAME" in os.environ else save_greeting(tmp_path, "Ana")
    assert path.read_text(encoding="utf-8") == "Hello, Ana"
    assert capsys.readouterr().out == "saved greeting.txt\\n"
    assert caplog.messages == ["wrote greeting.txt"]

def test_env_is_restored(monkeypatch):
    monkeypatch.setenv("USER_NAME", "Bo")
    assert os.environ["USER_NAME"] == "Bo"

def test_after(tmp_path):
    assert "USER_NAME" not in os.environ and list(tmp_path.iterdir()) == []
'''
print(run_pytest(SRC)["outcomes"])
Output
{'test_writes_into_tmp_path': 'passed', 'test_env_is_restored': 'passed', 'test_after': 'passed'}

class Cart:
    def __init__(self):
        self.items = {}

    def add(self, name, price, qty=1):
        if qty < 1:
            raise ValueError("qty must be at least 1")
        old_price, old_qty = self.items.get(name, (price, 0))
        self.items[name] = (price, old_qty + qty)

    def remove(self, name):
        del self.items[name]

    def total(self):
        return round(sum(price * qty for price, qty in self.items.values()), 2)


# --- tests ---
import pytest


@pytest.fixture
def cart():
    c = Cart()
    c.add("pen", 1.5, qty=2)
    c.add("book", 12.0)
    return c


def test_total(cart):
    assert cart.total() == 15.0


def test_adding_existing_item_increases_quantity(cart):
    cart.add("pen", 1.5, qty=3)
    assert cart.items["pen"] == (1.5, 5)
    assert cart.total() == 19.5


def test_remove_item(cart):
    cart.remove("pen")
    assert "pen" not in cart.items and cart.total() == 12.0


def test_remove_unknown_raises(cart):
    with pytest.raises(KeyError):
        cart.remove("lamp")


def test_rejects_zero_quantity(cart):
    with pytest.raises(ValueError):
        cart.add("pen", 1.5, qty=0)

The fixture states the common starting point once, and each test reads as "given the cart, when I do X, then Y". Because the fixture runs for every test, test_remove_item can mutate the cart freely without affecting test_total. Each mutant breaks one behaviour: replacing instead of adding quantities is caught by adding more pens, ignoring quantities by the total with two pens, a silent remove by the KeyError test, and clearing everything by checking what is left after a removal, a reminder that "the item is gone" is only half of the expected outcome.

def add_turn(history, role, content):
    if role not in ("user", "assistant"):
        raise ValueError(f"bad role {role!r}")
    history.append({"role": role, "content": content})
    return len(history)

import pytest


@pytest.fixture
def history():
    return [{"role": "user", "content": "Hi"}]


def test_first_turn():
    assert add_turn([], "user", "Hi") == 1

    assert history[0]["role"] == "user"

The fixture gives test_second_turn exactly the state it needs, freshly built, so it passes in any order and documents its precondition in its signature.

# --- code under test (do not edit) ---
import json


def write_jsonl(path, records):
    path.parent.mkdir(parents=True, exist_ok=True)
    with open(path, "w", encoding="utf-8") as f:
        for r in records:
            f.write(json.dumps(r, ensure_ascii=False) + "\n")
    return len(records)


def read_jsonl(path):
    with open(path, encoding="utf-8") as f:
        return [json.loads(line) for line in f if line.strip()]


# --- tests ---
import pytest

RECORDS = [{"id": 1, "text": "Où est ma commande ?"}, {"id": 2, "text": "plain"}]


@pytest.fixture
def path(tmp_path):
    return tmp_path / "data" / "nested" / "turns.jsonl"


def test_round_trip_and_count(path):
    assert write_jsonl(path, RECORDS) == 2
    assert read_jsonl(path) == RECORDS


def test_overwrites_existing_file(path):
    write_jsonl(path, RECORDS)
    write_jsonl(path, [{"id": 3}])
    assert read_jsonl(path) == [{"id": 3}]


def test_keeps_non_ascii_characters(path):
    write_jsonl(path, RECORDS)
    raw = path.read_text(encoding="utf-8")
    assert "Où" in raw and raw.count("\n") == 2


def test_skips_blank_lines(path):
    write_jsonl(path, RECORDS)
    with open(path, "a", encoding="utf-8") as f:
        f.write("\n   \n")
    assert len(read_jsonl(path)) == 2

tmp_path makes file tests safe and independent: every test writes into its own empty folder, so overwriting, appending and missing-folder cases can be checked without touching the project or each other, and pytest keeps the last few runs' folders for inspection. A small fixture on top of it (path) gives every test the same nested location, which is what exercises the folder creation. The tests check observable behaviour (file content and what reading returns), so each mutant fails: appending keeps the old records, escaping removes Où from the raw text, a missing mkdir raises on the nested path, and the reader without the blank-line filter crashes on json.loads("\n").

The standard pattern splits the fixture in two: the expensive work stays session-scoped and runs once (the grader counted the loads), and a cheap function-scoped fixture hands each test a copy, or in a database test, a transaction that is rolled back. For nested data, copy.deepcopy is needed instead of dict(...). Session fixtures are ideal for read-only resources such as a loaded tokenizer or model weights, and dangerous for anything a test might change.

class DocumentStore:
    def __init__(self):
        self._docs = {}

    def add(self, doc):
        if doc["id"] in self._docs:
            raise ValueError(f"duplicate id {doc['id']}")
        self._docs[doc["id"]] = dict(doc)

    def get(self, doc_id):
        return dict(self._docs[doc_id])

    def delete(self, doc_id):
        self._docs.pop(doc_id)

    def search(self, query, source=None, k=3):
        words = set(query.lower().split())
        scored = []
        for doc in self._docs.values():
            if source is not None and doc["source"] != source:
                continue
            score = len(words & set(doc["text"].lower().split()))
            if score:
                scored.append((-score, doc["id"]))
        return [doc_id for _, doc_id in sorted(scored)[:k]]

import inspect


def run_with_fixtures(test_fn, fixtures):
    cache, teardown = {}, []

    def resolve(name):
        if name in cache:
            return cache[name]
        if name not in fixtures:
            raise LookupError(f"fixture {name!r} not found")
        fn = fixtures[name]
        kwargs = {p: resolve(p) for p in inspect.signature(fn).parameters}
        if inspect.isgeneratorfunction(fn):
            gen = fn(**kwargs)
            value = next(gen)
            teardown.append(gen)
        else:
            value = fn(**kwargs)
        cache[name] = value
        return value

    try:
        kwargs = {p: resolve(p) for p in inspect.signature(test_fn).parameters}
        return test_fn(**kwargs)
    finally:
        for gen in reversed(teardown):
            next(gen, None)

This is pytest's fixture mechanism reduced to its core. Parameters are read with inspect.signature, and each name is resolved by building its own dependencies first, so config is created before client and cache even though the test lists it last, and only once, thanks to the per-call cache (pytest's function scope). Generator fixtures are advanced to their yield for the value and kept on a stack; the finally then finishes them in reverse order, so the cache closes before the client that was opened earlier, exactly the order of teardown in the warm-up. Because cleanup sits in finally, a failing test still releases its resources and its own exception propagates. pytest adds scopes (a cache per module or session), errors during setup, and plugins, but the idea is this one: dependency injection by parameter name.

8Interview questions

Interview

16. What are pytest fixtures, and why are they better than setup and teardown methods?

SolutionModel answer

A fixture is a function that provides a test dependency, requested by naming it as a parameter; pytest builds it, injects it, and (for yield fixtures) runs the cleanup after the test. Compared with setUp/tearDown methods in unittest, fixtures are explicit (each test lists what it uses, so unused setup is not run and readers see the dependencies), composable (fixtures use other fixtures, building complex setup from small parts), scoped (function, class, module or session, so expensive resources can be shared deliberately), parametrisable (run the same tests against several configurations), and shareable across files through conftest.py without inheritance. Teardown lives next to setup in one function, with guaranteed execution after the test. Built-in fixtures (tmp_path, monkeypatch, capsys, caplog) cover the common isolation needs.

Interview

17. How do you keep tests isolated when the code reads files, environment variables and global state?

SolutionModel answer

Give every test its own world and undo every change. Files: write only inside tmp_path (or tmp_path_factory for wider scopes), never in the repository or the current folder, and make code accept paths as parameters so tests can point it there. Environment: set and remove variables with monkeypatch.setenv and delenv, and start from a known state by deleting the variables the code reads, so the developer's real environment cannot change results. Global state (module-level caches, singletons, registries, logging configuration): reset it in a fixture, often autouse, or patch it with monkeypatch.setattr; better still, design code to receive dependencies instead of reaching for globals. Time and randomness: inject a clock and a seeded generator. Then verify isolation by running tests alone, in random order (pytest-randomly) and in parallel (pytest-xdist).

Interview

18. When would you use a session-scoped fixture, and what can go wrong?

SolutionModel answer

Use session scope for expensive resources that many tests need and that can be shared safely: starting a database or message-broker container (for example with Testcontainers), creating a schema, loading a tokenizer, an embedding model or a large reference dataset, or building a test application once. The risks come from sharing. Mutable shared objects make tests order-dependent, so expose them read-only, hand each test a copy, or pair the session resource with a function-scoped fixture that isolates each test, such as a transaction rolled back after every test or a fresh database per test created from a template. Session fixtures are created lazily on first use and torn down at the very end, so failures in their teardown are reported late, and with pytest-xdist each worker process gets its own "session", so cross-process resources (ports, files, database names) must be made unique per worker. Finally, slow session setup still costs time on every run; keep heavy fixtures behind marks so the fast unit suite does not pay for them.

Recap

  • A fixture is a function marked @pytest.fixture; a test receives it by naming a parameter, and fixtures can depend on other fixtures.
  • Code after yield is teardown and runs even when the test fails; setup and teardown failures are reported as errors.
  • Scopes (function, class, module, session) share objects; never let tests mutate a widely scoped fixture, copy or reset it instead.
  • Parametrised fixtures run tests per configuration; factory fixtures return functions with defaults; conftest.py shares fixtures.
  • tmp_path, monkeypatch, capsys and caplog isolate files, environment and attributes, output, and logs.
