13.4 Testing ML and GenAI code

ML and LLM systems add three difficulties to testing: numbers that are only approximately right, randomness, and models whose quality is a statistic rather than a yes or no. What to unit-test and what to evaluate instead, tolerances with NumPy, seeds and determinism, property and invariance tests, data validation, smoke training tests, prompt and parser tests, and evaluation gates for LLM changes.

17 problems4 easy · 8 medium · 5 hard

1What to test, and what to evaluate

An ML or LLM system is ordinary code around a model. The ordinary code, which is most of it, gets ordinary unit tests: data loading and cleaning, feature functions, tokenisation and chunking, metric implementations, prompt builders, output parsers and validators, routing and retry logic. These are deterministic, or can be made so, and every bug in them corrupts results silently, so they deserve the most tests. The model itself is different: "the classifier is good" is not true or false for one input, it is an accuracy of 0.93 on a dataset. That is measured by evaluation, with datasets, metrics and thresholds, run less often and reported as numbers.

Between the two sit tests that check behaviour without exact answers: property tests (outputs are probabilities, shapes match, a scaler's output has mean 0), smoke training tests (a tiny model on a tiny dataset reaches perfect accuracy and its loss decreases, which catches broken gradients in seconds), data validation (schemas, ranges, duplicates, leakage between splits), and invariance tests (changing the case of an e-mail should not change its spam label). A healthy project has many fast unit tests, some of these behavioural tests, and an evaluation suite gating model and prompt changes.

2Numbers: tolerances and dtypes

Floating-point results depend on the order of operations, the library version, the hardware and the dtype, so exact equality is almost never the right check for computed values. For NumPy arrays, use np.testing.assert_allclose(actual, expected, rtol=1e-7, atol=0): it passes when |actual - expected| <= atol + rtol * |expected| element-wise, checks shapes, and reports how many elements mismatch and by how much. Choose tolerances deliberately: float32 computations (most deep learning) carry about 7 significant digits, so rtol=1e-5 is realistic, and values near zero need an atol. np.testing.assert_array_equal is for exact integer or boolean arrays (and treats NaNs in the same places as equal, unlike ==). Check dtypes and shapes explicitly too: a feature matrix that silently became int64 or (n,) instead of (n, 1) is a common bug.

3Randomness and determinism

Shuffles, splits, initial weights, sampling and data augmentation all use random numbers. A test that depends on them must control them, and so should production code, for reproducible experiments. The robust pattern is to pass a generator in: rng = np.random.default_rng(seed) or random.Random(seed), given to every function that needs randomness, rather than calling the global np.random.rand or random.random, whose state any other code can change. Two generators with the same seed produce the same sequence; one generator used twice produces different numbers each time, so "same seed, same result" tests create a fresh generator for each run (problem 3).

Some randomness cannot be seeded from Python: GPU kernels with non-deterministic reductions, multi-threaded data loaders, and LLM sampling, where even temperature 0 is not guaranteed to be identical across calls. For those, test properties and tolerances, run several samples and check aggregate behaviour, or move the model call out of the unit test entirely.

4Testing data

Most ML failures are data failures: a column that changed type upstream, labels outside the expected set, duplicated examples, missing values encoded as -1, or the same customer in both training and test sets (leakage, which inflates offline metrics and disappoints in production). These are tested like any contract: a validation function returns a list of problems for a batch, unit tests check the validator, and the pipeline runs it on every new batch and refuses to train on bad data (problem 6). Libraries such as Pandera, Great Expectations and Pydantic (11.4) formalise the schemas; the checks themselves are simple code.

5Testing LLM applications

Split an LLM feature into deterministic parts and the model call. Prompt builders get unit tests on structure (the context and the question are present, the instructions come first, long context is truncated within budget), not on exact wording, which changes often; when an exact template matters, a snapshot (golden file) test stores the expected prompt and is updated deliberately. Output parsers and validators get tests with realistic, messy replies collected from real runs: code fences, extra prose, wrong case, missing fields, truncated JSON (13.1 problem 9, 11.4). Orchestration (retries, tool loops, fallbacks) is tested with fakes (13.3). None of this needs a real model.

Quality is evaluated: a versioned evaluation set of inputs with expected answers or grading rules (exact match, contained facts, valid JSON, a rubric scored by a judge model), run against the real model when the prompt, the model or the retrieval changes, and compared with the previous baseline. A CI gate fails the change if a metric drops below a threshold or regresses by more than a tolerance (problem 10). Because outputs vary, evaluations use enough cases to be statistically meaningful, report confidence intervals or several runs, and track cost and latency alongside quality.

# --- code under test (do not edit) ---
import numpy as np


class StandardScaler:
    def fit(self, X):
        X = np.asarray(X, dtype=np.float64)
        self.mean_ = X.mean(axis=0)
        std = X.std(axis=0)
        self.std_ = np.where(std == 0, 1.0, std)
        return self

    def transform(self, X):
        X = np.asarray(X, dtype=np.float64)
        return (X - self.mean_) / self.std_


# --- tests ---
import numpy as np
import pytest

TRAIN = np.array([[1, 10], [3, 30]])


@pytest.fixture
def scaler():
    return StandardScaler().fit(TRAIN)


def test_per_column_statistics(scaler):
    np.testing.assert_allclose(scaler.mean_, [2.0, 20.0])
    np.testing.assert_allclose(scaler.transform(TRAIN), [[-1.0, -1.0], [1.0, 1.0]])


def test_new_data_uses_fitted_statistics(scaler):
    np.testing.assert_allclose(scaler.transform([[5, 20]]), [[3.0, 0.0]])


def test_constant_column_becomes_zeros():
    X = np.array([[1.0, 7.0], [3.0, 7.0]])
    out = StandardScaler().fit(X).transform(X)
    assert not np.isnan(out).any()
    np.testing.assert_allclose(out[:, 1], [0.0, 0.0])


def test_output_is_float64_and_input_untouched(scaler):
    X = TRAIN.copy()
    out = scaler.transform(X)
    assert out.dtype == np.float64
    np.testing.assert_array_equal(X, TRAIN)

Two rows per column make the expected output easy to derive by hand (mean halfway, population standard deviation half the gap), so the test states the exact answer with assert_allclose rather than re-computing it with the same formula, which would only prove the code agrees with itself. The second test captures the most important rule of preprocessing: transform uses the statistics learned in fit; a version that re-centres each new batch on its own mean leaks information and makes a single-row batch always zero. The constant-column and dtype tests cover the edge cases that silently produce NaNs or truncated integers in a real pipeline.

# --- code under test (do not edit) ---
import numpy as np


def bootstrap_ci(values, n, rng, level=0.9):
    values = np.asarray(values, dtype=float)
    means = np.array([rng.choice(values, size=len(values), replace=True).mean() for _ in range(n)])
    lo, hi = np.quantile(means, [(1 - level) / 2, 1 - (1 - level) / 2])
    return float(lo), float(hi)


# --- tests ---
import numpy as np
import pytest

DATA = [1, 2, 3, 4, 5]


def test_same_seed_same_interval():
    a = bootstrap_ci(DATA, 200, np.random.default_rng(0))
    b = bootstrap_ci(DATA, 200, np.random.default_rng(0))
    assert a == b


@pytest.mark.parametrize("seed", [0, 1, 2])
def test_interval_is_ordered_and_within_data_range(seed):
    lo, hi = bootstrap_ci(DATA, 200, np.random.default_rng(seed))
    assert 1 <= lo <= hi <= 5


def test_interval_contains_sample_mean():
    lo, hi = bootstrap_ci(DATA, 500, np.random.default_rng(3))
    assert lo <= 3.0 <= hi

An unseeded generator gives different numbers on every run, so a test with copied values is flaky by construction. A seeded generator makes runs repeatable, and comparing two fresh generators with the same seed is the right determinism check; it also exposes code that ignores the generator and uses the global NumPy random state (the graded bug), which no seed passed to the function can control. The other tests check properties that hold whatever the seed, which keeps them valid if the algorithm changes, unlike golden numbers. The grader ran the suite three times to make sure it is stable.

4. Why property tests catch overflow

import numpy as np

def softmax_naive(z):
    e = np.exp(z)
    return e / e.sum()

def softmax_stable(z):
    e = np.exp(z - np.max(z))
    return e / e.sum()

small = np.array([1.0, 2.0, 3.0])
large = np.array([1000.0, 1001.0, 1002.0])
with np.errstate(over="ignore", invalid="ignore"):
    print(np.round(softmax_naive(small), 3), np.round(softmax_stable(small), 3))
    print(softmax_naive(large), np.round(softmax_stable(large), 3))
    print(np.isclose(softmax_naive(large).sum(), 1.0), np.isclose(softmax_stable(large).sum(), 1.0))

On ordinary inputs both versions agree, so a test with only "nice" values would pass the naive one. With large logits, which real models produce, the exponentials overflow to infinity and the result is NaN. A property test ("outputs are finite, non-negative and sum to 1, for small and large inputs") fails for the naive version immediately. The stable version subtracts the maximum, which leaves the result unchanged but keeps every exponent at most 0.

# --- code under test (do not edit) ---
def prf(y_true, y_pred, positive):
    tp = sum(t == positive and p == positive for t, p in zip(y_true, y_pred))
    fp = sum(t != positive and p == positive for t, p in zip(y_true, y_pred))
    fn = sum(t == positive and p != positive for t, p in zip(y_true, y_pred))
    precision = tp / (tp + fp) if tp + fp else 0.0
    recall = tp / (tp + fn) if tp + fn else 0.0
    f1 = 2 * precision * recall / (precision + recall) if precision + recall else 0.0
    return precision, recall, f1


# --- tests ---
import pytest

S, H = "spam", "ham"


def test_mixed_case_by_hand():
    # tp=2, fp=1, fn=3, tn=1
    y_true = [S, S, H, S, S, S, H]
    y_pred = [S, S, S, H, H, H, H]
    p, r, f = prf(y_true, y_pred, S)
    assert (p, r) == pytest.approx((2 / 3, 2 / 5))
    assert f == pytest.approx(2 * (2 / 3) * (2 / 5) / (2 / 3 + 2 / 5))


def test_true_negatives_do_not_count():
    p, r, f = prf([S, H, H, H], [S, H, H, H], S)
    assert (p, r, f) == pytest.approx((1.0, 1.0, 1.0))


def test_no_predicted_positives_gives_zero_precision():
    assert prf([S, H], [H, H], S) == (0.0, 0.0, 0.0)


def test_all_wrong():
    assert prf([S, H], [H, S], S) == (0.0, 0.0, 0.0)


def test_other_label_as_positive():
    p, r, f = prf([S, H, H], [H, H, S], H)
    assert (p, r) == pytest.approx((0.5, 0.5))

Metric code is where silent bugs do the most damage: a swapped precision and recall or an arithmetic mean instead of the harmonic one still produces plausible numbers, and every model comparison built on them is wrong. Hand-computed cases where precision and recall differ catch swaps and the wrong mean; string labels catch code that assumes the positive class is 1; true negatives in the data catch formulas that count them; and the empty-denominator cases pin the convention (0.0 rather than an exception or NaN, as scikit-learn's zero_division=0 does). Comparing against an independent hand calculation, not the same formula, is what makes the tests meaningful.

from collections import Counter


def validate_batch(rows, labels, max_text=2000):
    problems = []
    for n, row in enumerate(rows, start=1):
        for key in ("id", "text", "label"):
            if key not in row:
                problems.append(f"row {n}: missing {key}")
        if "text" in row:
            text = row["text"]
            if not isinstance(text, str) or not text.strip():
                problems.append(f"row {n}: text must be a non-empty string")
            elif len(text) > max_text:
                problems.append(f"row {n}: text longer than {max_text}")
        if "label" in row and row["label"] not in labels:
            problems.append(f"row {n}: unknown label {row['label']!r}")
    counts = Counter(row["id"] for row in rows if "id" in row)
    problems.extend(f"duplicate id {i!r}" for i, c in counts.items() if c > 1)
    return sorted(problems)

A validation function that collects every problem, with row numbers, is what a data pipeline needs: one run tells the data owner everything to fix, instead of one error per attempt. The checks mirror the common silent failures: missing fields, empty or non-string text (a number where text belongs often means a shifted CSV column), oversize inputs that would be truncated by a tokenizer, labels with the wrong case ("Ham" becomes a fourth class) and duplicates, which inflate metrics when copies land in both training and test sets. The function is pure, so it is trivially unit-tested, and the pipeline can refuse to train when the list is not empty.

# --- code under test (do not edit) ---
from datetime import date


def build_prompt(question, chunks, today=None):
    today = today or date.today()
    lines = [f"You answer support questions. Today is {today.isoformat()}.", "Context:"]
    lines += [f"[{c['source']}] {c['text']}" for c in chunks]
    lines += ["", f"Question: {question}"]
    return "\n".join(lines)

def evaluate(predict, cases):
    results, by_tag, failures = [], {}, []
    for case in cases:
        try:
            ok = predict(case["input"]) == case["expected"]
        except Exception:
            ok = False
        results.append(ok)
        if not ok:
            failures.append(case["id"])
        for tag in case.get("tags", []):
            by_tag.setdefault(tag, []).append(ok)
    accuracy = round(sum(results) / len(results), 3) if results else 0.0
    return {"n": len(results), "accuracy": accuracy,
            "by_tag": {tag: round(sum(v) / len(v), 3) for tag, v in sorted(by_tag.items())},
            "failures": failures}


def gate(report, baseline, min_accuracy=0.8, max_drop=0.02):
    problems = []
    acc = report["accuracy"]
    if acc < min_accuracy:
        problems.append(f"accuracy {acc} below minimum {min_accuracy}")
    if acc < baseline.get("accuracy", 0.0) - max_drop:
        problems.append(f"accuracy dropped from {baseline['accuracy']} to {acc}")
    for tag, old in baseline.get("by_tag", {}).items():
        new = report["by_tag"].get(tag)
        if new is not None and new < old - max_drop:
            problems.append(f"tag {tag!r} dropped from {old} to {new}")
    if problems:
        raise AssertionError("; ".join(problems))
    return True

An evaluation gate turns "the model seems fine" into a check CI can enforce when someone edits a prompt or switches models. Two thresholds work together: an absolute minimum protects users, and a maximum drop from the baseline catches regressions even when the absolute number is still acceptable. Per-tag accuracy matters because an average can hide a collapse in one important slice: here the overall accuracy is fine but phishing, the costliest class, fell from 1.0 to 0.5. Exceptions count as wrong answers, since a timeout in production is a failure too, and all problems are reported at once. In practice the tolerance should reflect the evaluation set's noise (with 50 cases, one case is 2 points), and the baseline is stored with the prompt and model version.

# --- code under test (do not edit) ---
import numpy as np


def sigmoid(z):
    return 1 / (1 + np.exp(-z))


def predict_proba(X, w, b):
    return sigmoid(np.asarray(X, dtype=float) @ w + b)


def train_logreg(X, y, lr=0.5, epochs=200, seed=0):
    X, y = np.asarray(X, dtype=float), np.asarray(y, dtype=float)
    rng = np.random.default_rng(seed)
    w, b = rng.normal(0, 0.01, X.shape[1]), 0.0
    losses = []
    for _ in range(epochs):
        p = predict_proba(X, w, b)
        losses.append(float(-np.mean(y * np.log(p + 1e-12) + (1 - y) * np.log(1 - p + 1e-12))))
        grad = p - y
        w -= lr * X.T @ grad / len(y)
        b -= lr * grad.mean()
    return w, b, losses

def _label(classify, text, transform=None):
    try:
        return classify(transform(text) if transform else text)
    except Exception as e:
        return f"error: {type(e).__name__}"


def check_invariance(classify, texts, transforms):
    violations = []
    for text in texts:
        original = _label(classify, text)
        for name, transform in transforms.items():
            new = _label(classify, text, transform)
            if new != original:
                violations.append((text, name, original, new))
    return violations


def invariance_rate(violations, texts, transforms):
    pairs = len(texts) * len(transforms)
    if pairs == 0:
        return 1.0
    return round(1 - len(violations) / pairs, 3)

15. How do you test a machine learning pipeline?

SolutionModel answer

In layers. Unit tests for deterministic code: data loading and cleaning, feature functions, preprocessing (fit on train, transform with stored statistics), metrics, and serialisation, with hand-computed examples and tolerances. Data validation on every batch: schema, types, ranges, missing values, label sets, duplicates and leakage between splits, failing the pipeline before training on bad data. Smoke tests of training: a tiny model overfits a tiny batch, the loss decreases, outputs have the right shapes and ranges, and seeds make runs reproducible. Integration tests run the pipeline end to end on a small fixture dataset and check artefacts (model file, metrics report) are produced. Model evaluation on a held-out, versioned dataset with metrics and slices, compared with the current production model before promotion, plus behavioural checks (invariance, fairness slices). In production, monitoring of input drift and prediction distributions closes the loop. Keep randomness injected and seeded so failures are reproducible.

16. A teammate changed a prompt. How do you decide whether it is safe to ship?

SolutionModel answer

Run it through the same gates as code. Unit tests first: prompt building and output parsing must still pass, and structural tests should not depend on exact wording. Then the evaluation set: a versioned collection of representative inputs, including past failures and edge cases, scored with appropriate metrics (exact or semantic match, required facts present, valid structured output, a rubric graded by a judge model whose agreement with humans has been checked). Compare with the baseline of the current prompt on the same model version, overall and per slice, with enough cases and repeated runs to tell a real change from noise; block on regressions beyond a tolerance. Check cost and latency (longer prompts cost more) and safety cases (prompt injection, refusals). If it passes, roll out gradually or behind a flag, and watch production metrics (user feedback, escalations, parse failures) with the ability to roll back, since evaluation sets never cover everything.

First, keep the model out of unit tests: inject a fake or mock client so everything around the model (prompt building, parsing, retries, tool dispatch) is tested deterministically. Where randomness is yours, control it: pass seeded generators, set framework seeds, and use deterministic algorithms when available. Compare numbers with tolerances that reflect the dtype and computation (assert_allclose with sensible rtol/atol), and test properties and relations rather than exact values: shapes, ranges, probabilities summing to 1, monotonic loss on a tiny problem, invariance under harmless input changes. For real model calls, which belong in evaluation or a few marked integration tests, use temperature 0 where possible, assert on robust properties (valid JSON matching a schema, contains the required fact), aggregate over several cases or samples with thresholds instead of single pass/fail outputs, and record and replay responses for regression tests. Track flaky tests explicitly and fix their cause rather than adding retries.

Recap

  • Unit-test the deterministic code around models (features, preprocessing, metrics, prompts, parsers); evaluate model quality separately with datasets and thresholds.
  • Compare floats with np.testing.assert_allclose and deliberate rtol/atol; check dtypes and shapes explicitly.
  • Inject seeded generators (default_rng(seed), random.Random(seed)); test determinism with two fresh generators, and properties for everything else.
  • Validate data with functions that collect every problem; smoke-test training on tiny data (loss decreases, perfect fit, bias learned, seeds respected).
  • Test LLM parsers with real replies, prompts by structure, behaviour with metamorphic checks, and gate changes on evaluation against a baseline.
