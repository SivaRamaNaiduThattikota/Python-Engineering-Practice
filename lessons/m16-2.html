16.2 Hashing patterns

A large share of interview problems, and of real data code, is solved by one idea: trade memory for time with a dict or a set. Counting, complement lookups (two-sum), grouping by a canonical key, sliding windows, prefix sums, LRU caches and near-duplicate detection, each with its complexity and its traps, including the hash and equality contract that every key must follow.

18 problems4 easy · 9 medium · 5 hard

1The core idea: remember what you have seen

Brute force often compares every element with every other, O(n^2). Hashing replaces the inner loop with a lookup: as you pass over the data once, store what you need in a dict or a set, and for each new element ask the table an O(1) question ("have I seen this?", "how many times?", "where was its complement?"). The result is O(n) time for O(n) extra memory, the trade behind most "optimise this" interview answers. The questions decide the structure: a set for presence, a dict from key to count, index, or list of items, collections.Counter for counts, defaultdict(list) for groups.

            return seen[target - x], i

two_sum stores each value's index and, for every new value, looks up the complement it needs; one pass, O(n), instead of checking all pairs. Grouping uses a canonical key, a representation that is equal for items that belong together (the sorted letters of an anagram); the same trick normalises emails, case-folds titles or hashes document contents (12.1).

2Sliding windows

Many problems ask about contiguous ranges: the best sum of k consecutive values, the longest substring without repeated characters, the shortest span containing every keyword, requests in the last 60 seconds. Recomputing each window from scratch is O(n * k); a sliding window keeps a summary of the current range (a sum, a Counter, a set, a deque of timestamps) and updates it as one element enters at the right and, when needed, others leave at the left. Each element enters and leaves once, so the total is O(n). Fixed-size windows move both ends together; variable-size windows grow the right end and shrink the left end while a condition is violated (problems 5 and 13).

3Prefix sums and hash maps

The sum of values[i:j] equals prefix[j] - prefix[i], where prefix[k] is the sum of the first k values, so after one O(n) pass any range sum costs O(1). Combined with a dict this answers counting questions: the number of subarrays summing to k is the number of pairs of prefix sums that differ by k, so as you compute each prefix sum p, add how many earlier prefix sums equal p - k (problem 7). Seeding the dict with {0: 1}, the empty prefix, is what lets subarrays that start at index 0 count.

4The hash and equality contract

Dicts and sets rely on one rule: objects that are equal must have equal hashes. Python's built-ins follow it (so 1, 1.0 and True are the same key), and @dataclass(frozen=True) generates matching __eq__ and __hash__ (11.3). A class that defines __eq__ without __hash__ becomes unhashable, which is the safe default; a hand-written __hash__ that disagrees with __eq__ makes "equal" objects land in different buckets, so sets keep duplicates and lookups miss. And a key must not change while it is in a table: mutating an object used as a key changes its hash, and the table can no longer find it, which is why lists and dicts are unhashable and tuples of immutable values are the standard composite key.

from collections import Counter


def two_sum(nums, target):
    first = {}
    for j, x in enumerate(nums):
        if target - x in first:
            return first[target - x], j
        first.setdefault(x, j)
    return None


def count_pairs(nums, target):
    seen, total = Counter(), 0
    for x in nums:
        total += seen[target - x]
        seen[x] += 1
    return total

Checking the complement before inserting the current value is what keeps an element from pairing with itself ([3] with target 6) while still pairing two equal values at different positions ([3, 3]). Scanning left to right returns the pair with the smallest second index, and keeping the first index of each value makes the first index as small as possible. Counting pairs generalises the lookup: each new value pairs with every earlier occurrence of its complement, so four 2s give 0 + 1 + 2 + 3 = 6 pairs, all in one pass instead of the O(n^2) double loop.

solution.py
def group_anagrams(words):
    groups = {}
    for w in words:
        key = "".join(sorted(w.lower()))
        groups.setdefault(key, []).append(w)
    return list(groups.values())

Dict keys must be hashable, and lists are not, because they can change after insertion, which would break the table. A string or a tuple built from the sorted letters is immutable and equal for exactly the anagrams, so it works as the canonical key; lower-casing first makes the key ignore case while the stored words keep their original form. Sorting each word costs O(L log L), so the whole grouping is O(n L log L); a Counter of letters as a frozenset of items, or a 26-count tuple, gives O(n L) for long words.

4. A fixed-size sliding window

def window_sums(values, k):
    if k > len(values):
        return []
    total = sum(values[:k])
    sums = [total]
    for i in range(k, len(values)):
        total += values[i] - values[i - k]
        sums.append(total)
    return sums

solution.py
def longest_unique(s):
    last = {}
    left = best_len = best_start = 0
    for i, ch in enumerate(s):
        if ch in last and last[ch] >= left:
            left = last[ch] + 1
        last[ch] = i
        if i - left + 1 > best_len:
            best_len, best_start = i - left + 1, left
    return best_len, best_start

The window [left, i] always holds distinct characters: when the new character already occurs inside it, the left edge jumps just past that earlier occurrence, so each index is passed by both edges at most once, O(n). Storing the last index of each character lets the jump happen in O(1) instead of shrinking step by step. The last[ch] >= left test matters for "abba": when the second a arrives, its earlier occurrence is already outside the window, and jumping back to it would grow the window wrongly. The same skeleton handles "longest run of tokens without a repeated n-gram" or "longest session without a duplicate event".

6. A sliding-window rate limiter

from collections import defaultdict, deque


class SlidingWindowLimiter:
    def __init__(self, limit, window):
        self.limit, self.window = limit, window
        self.history = defaultdict(deque)

    def allow(self, user, t):
        q = self.history[user]
        while q and q[0] <= t - self.window:
            q.popleft()
        if len(q) < self.limit:
            q.append(t)
            return True
        return False

A per-user deque is a sliding window over time: new requests enter on the right, and requests older than the window leave on the left, each exactly once, so every call is amortised O(1) and memory is bounded by limit per user. The half-open interval decides the boundary: at t = 60, the request from t = 0 has just left the window, so a new one is allowed, but at t = 61 the requests from 10, 20 and 60 are all still inside it, so the next one is refused. Rejected requests are not recorded, so a client hammering the API does not lock itself out for longer. This is the "sliding log" limiter; the token bucket of 14.2 uses O(1) memory per user at the cost of allowing bursts, and production systems keep such state in Redis to share it across servers.

TestsThe 3 checks Run tests uses

assert count_subarrays([0, 0, 0], 0) == 6 and count_subarrays([], 3) == 0
HintOpen a hint

Before the loop, record that the empty prefix (sum 0) has been seen once: seen = {0: 1}.

SolutionShow the solution and why
solution.py
def count_subarrays(values, k):
    seen = {0: 1}
    prefix = total = 0
    for v in values:
        prefix += v
        total += seen.get(prefix - k, 0)
        seen[prefix] = seen.get(prefix, 0) + 1
    return total

A subarray values[i:j] sums to k exactly when prefix[j] - prefix[i] == k, so at each position the number of good subarrays ending there is the number of earlier prefixes equal to prefix - k. The prefix before any element is 0, and subarrays starting at index 0 need it: without {0: 1}, [3, 4] (sum 7, starting at 0) was never counted. With negative numbers a sliding window does not work (sums are not monotonic), which is exactly when the prefix-sum dict is the tool. The zeros case shows it counts all six subarrays of [0, 0, 0].

9. At most k distinct in a window

from collections import Counter

def longest_k_distinct(s, k):
    counts, left, best = Counter(), 0, 0
    for right, ch in enumerate(s):
        counts[ch] += 1
        while len(counts) > k:
            counts[s[left]] -= 1
            if counts[s[left]] == 0:
                del counts[s[left]]
            left += 1
        best = max(best, right - left + 1)
    return best

from collections import defaultdict
from itertools import combinations


def shingles(text, n=3):
    words = text.lower().split()
    if not words:
        return set()
    if len(words) < n:
        return {tuple(words)}
    return {tuple(words[i:i + n]) for i in range(len(words) - n + 1)}


def jaccard(a, b):
    union = a | b
    return len(a & b) / len(union) if union else 0.0


def near_duplicates(docs, threshold=0.5, n=3):
    sets = {doc_id: shingles(text, n) for doc_id, text in docs.items()}
    index = defaultdict(set)
    for doc_id, sh in sets.items():
        for s in sh:
            index[s].add(doc_id)
    candidates = set()
    for ids in index.values():
        candidates.update(combinations(sorted(ids), 2))
    out = []
    for a, b in sorted(candidates):
        sim = jaccard(sets[a], sets[b])
        if sim >= threshold:
            out.append((a, b, round(sim, 3)))
    return out

Near-duplicates (the same FAQ answer pasted twice with one word changed) waste index space and make retrieval return the same content several times. Word shingles turn each document into a set, and Jaccard similarity measures overlap. Comparing all pairs is O(n^2); an inverted index from shingle to documents means only documents that share at least one shingle are ever compared, which for real corpora is a tiny fraction of the pairs. At web scale, MinHash with locality-sensitive hashing replaces exact sets with short signatures, but the structure (hash features, index them, compare candidates) is the same.

from collections import OrderedDict


class LRUCache:
    def __init__(self, capacity):
        if capacity < 1:
            raise ValueError("capacity must be at least 1")
        self.capacity = capacity
        self.data = OrderedDict()
        self.hits = self.misses = self.evictions = 0

    def get(self, key):
        if key not in self.data:
            self.misses += 1
            return None
        self.data.move_to_end(key)
        self.hits += 1
        return self.data[key]

    def put(self, key, value):
        if key in self.data:
            self.data.move_to_end(key)
        self.data[key] = value
        if len(self.data) > self.capacity:
            self.data.popitem(last=False)
            self.evictions += 1

An LRU cache needs two O(1) operations: find a key, and know which key was used least recently. An OrderedDict provides both, a hash table for lookups plus a linked order that move_to_end updates in O(1), so the oldest entry is always at the front for popitem(last=False). Caching LLM completions or embeddings by a hash of the prompt and parameters saves money on repeated questions, and the hit, miss and eviction counters tell you whether the capacity is right. functools.lru_cache is the decorator version (8.4); a hand-written class is needed when keys must be computed from arguments or the cache must be shared and inspected.

from collections import Counter


def min_window(tokens, required):
    if not required:
        return (0, 0)
    need = Counter(required)
    missing = len(required)
    best = None
    left = 0
    for right, tok in enumerate(tokens):
        if need[tok] > 0:
            missing -= 1
        need[tok] -= 1
        while missing == 0:
            if best is None or right + 1 - left < best[1] - best[0]:
                best = (left, right + 1)
            need[tokens[left]] += 1
            if need[tokens[left]] > 0:
                missing += 1
            left += 1
    return best

The window expands to the right until it contains everything required, then shrinks from the left as long as it still does, recording each valid window; every token enters and leaves once, so the whole search is O(n). The need counter goes negative for surplus tokens, which is what lets the window shrink past an extra refund without losing validity, and missing counts how many required tokens are still absent, so validity is checked in O(1) instead of comparing counters. In search and RAG this finds the tightest passage containing all query keywords, a good snippet to show or to feed a model.

from collections import Counter

STOP = frozenset({"the", "a", "of", "to", "is", "and"})


def top_terms(docs, k):
    counts = Counter()
    for doc in docs:
        for w in doc.split():
            w = w.strip(".,!?").lower()
            if w and w not in STOP:
                counts[w] += 1
    ranked = sorted(counts.items(), key=lambda kv: (-kv[1], kv[0]))
    return [w for w, _ in ranked[:k]]

words.count(w) scans the whole word list once per distinct word, O(n * u), which for the 300,000-word test is billions of steps; a Counter counts in one pass. Membership in a list of stop words is a scan too, a frozenset makes it O(1). Sorting tuples (count, word) in reverse also reverses the tie-break (return before refund); the key (-count, word) sorts counts descending and words ascending explicitly. And Refund versus refund split one term's count in two, so normalising case belongs before counting. For a huge vocabulary with a small k, heapq.nsmallest(k, counts.items(), key=...) avoids sorting everything.

Interview

16. When would you reach for a hash map in an interview problem, and what does it cost?

SolutionModel answer

Whenever the brute-force solution has an inner loop that searches for something: a complement (two-sum), a previous occurrence (first repeat, longest substring without repeats), a count (frequencies, anagrams, majority element), a group (group by canonical key), or a previous state (prefix sums for subarray sums, visited states in a search). Replacing that search with an O(1) average dict or set lookup usually turns O(n^2) into O(n). The costs: O(n) extra memory, keys must be hashable and must follow the hash and equality contract, iteration order is insertion order (dicts) or arbitrary (sets), and the worst case degrades with many collisions. If the data is sorted or can be sorted, two pointers or binary search (16.3) may give the same speed with O(1) extra memory; mention the trade-off.

Interview

17. Explain the sliding window technique and when it applies.

SolutionModel answer

A sliding window maintains a summary of a contiguous range [left, right] of a sequence and updates it incrementally: extend right one element at a time, and move left forward when the window becomes invalid (variable-size windows) or to keep a fixed size, updating the summary (a sum, a Counter, a set, a deque) by adding the entering element and removing the leaving one. Each element enters and leaves once, so the total is O(n) instead of O(n * k) or O(n^2). It applies to problems about contiguous subarrays or substrings where validity changes monotonically as the window grows or shrinks: longest substring with at most k distinct characters, smallest window containing all keywords, maximum sum of k consecutive values, rate limits over the last T seconds, moving averages of metrics. It does not apply when validity is not monotonic, for example subarray sums with negative numbers, where prefix sums with a hash map are used instead.

Interview

18. How would you deduplicate a corpus of 50 million documents, including near-duplicates?

SolutionModel answer

In two stages. Exact duplicates: normalise each document (Unicode normalisation, whitespace, case where appropriate, boilerplate removal), hash it (SHA-256 or a 64-bit hash such as xxHash), and keep one document per hash; this is a streaming, hash-set operation, partitioned by hash prefix across workers if it does not fit on one machine. Near duplicates: represent each document by its set of shingles (word or character n-grams), compute a MinHash signature (say 128 hashes), whose agreement rate estimates Jaccard similarity, and use locality-sensitive hashing (split signatures into bands; documents sharing a band bucket become candidates), so only candidate pairs are compared instead of all pairs; then confirm candidates above a threshold and cluster them with union-find, keeping one representative per cluster (by quality or recency). Tools such as datasketch or distributed implementations in Spark do this at scale. Embedding-based similarity catches paraphrases too, at a higher cost (approximate nearest-neighbour search). Report how many documents each stage removed, and spot-check samples, because thresholds trade lost content against redundancy.

Recap

  • Replace an inner search loop with a dict or set lookup: counting, complements, groups and seen-before checks become O(n) for O(n) memory.
  • Group with a canonical, hashable key (sorted letters, normalised text, a content hash); use tuples or frozen dataclasses as composite keys.
  • Sliding windows update a running summary as elements enter and leave, O(n) for contiguous-range questions when validity is monotonic.
  • Prefix sums plus a dict count subarrays with a given sum, including negative values; seed with {0: 1}.
  • Respect the contract: equal keys must hash equally and must not change while stored; OrderedDict gives O(1) LRU caches.
