14.5 asyncio in practice

The patterns every async LLM or data client needs: limiting concurrency with semaphores, client-side rate limiting, timeouts, retries with exponential backoff and jitter, worker pools on asyncio.Queue, deduplicating identical in-flight requests, and shutting down cleanly. All of it runs here on simulated time, so the timings in the tests are exact: a rate limiter's schedule or a timeout's effect is checked to the millisecond.

1Bounding concurrency with a semaphore

gather over 10,000 coroutines starts 10,000 requests at once, which exceeds every provider's rate limit, exhausts connection pools and memory, and gets the client throttled. asyncio.Semaphore(n) fixes the number of tasks allowed inside a block: async with sem: decrements its counter, or waits while it is zero, and increments it on exit. Acquire it inside each task, around the request itself, so that all tasks can be created at once but only n call the API at any moment (problem 3 shows the common way to get this wrong). Little's law (14.1) gives n: about the target requests per second times the average latency.

semaphore.py
import asyncio

async def call(i, sem, active, peak):
    async with sem:
        active[0] += 1
        peak[0] = max(peak[0], active[0])
        await asyncio.sleep(1.0)
        active[0] -= 1
        return i

async def main(limit):
    sem, active, peak = asyncio.Semaphore(limit), [0], [0]
    loop = asyncio.get_running_loop()
    results = await asyncio.gather(*(call(i, sem, active, peak) for i in range(10)))
    return results == list(range(10)), peak[0], loop.time()

print(asyncio.run(main(3)), asyncio.run(main(10)))
Output
(True, 3, 4.0) (True, 10, 1.0)

With a limit of 3, ten one-second calls run in four waves and finish at 4 seconds, never more than 3 at once; with 10, all run together. Results stay in order because gather keeps argument order regardless of when each task got its turn.

2Rate limits, timeouts and retries

A semaphore caps concurrency; providers also cap rate (requests or tokens per minute). A client-side token bucket (14.2) spaces requests out: before each call, acquire a token, sleeping until one is available (problem 6). Combine both, and respect the server: on HTTP 429 or 503 responses, honour a Retry-After header when present.

Every network call needs a timeout: async with asyncio.timeout(seconds): (Python 3.11) or await asyncio.wait_for(aw, seconds) cancels the work and raises TimeoutError when the time is up, so one hung connection cannot stall a batch forever. Choose timeouts from measured latency percentiles (a little above the p99), and for streaming responses time out between tokens rather than over the whole stream.

Transient failures (timeouts, connection resets, 429, 5xx) deserve retries with exponential backoff: wait base * 2 ** attempt, capped at a maximum, and add jitter, for example a random wait between 0 and that value ("full jitter"), so that a thousand clients that failed at the same moment do not retry in lockstep and knock the service over again. Retry a bounded number of times, never on errors that will not change (400 bad request, 401 unauthorised, validation errors), and only operations that are safe to repeat (idempotent), or that carry an idempotency key.

3Worker pools on asyncio.Queue

For long or unbounded streams of work (items arriving from a crawler, a message queue, or a file too big to load), use a producer-consumer design: an asyncio.Queue(maxsize=...) between producers and a fixed number of worker tasks. Producers await queue.put(item), which waits when the queue is full, giving natural back-pressure; each worker loops on item = await queue.get(), processes it, and calls queue.task_done(). await queue.join() waits until every item put has been marked done, after which the workers (stuck waiting on an empty queue) are cancelled. The number of workers is the concurrency limit, so no semaphore is needed, and memory stays bounded however much work arrives. Python 3.13 also added queue.shutdown() for ending consumers explicitly.

queue_workers.py
import asyncio

async def worker(name, queue, results):
    while True:
        item = await queue.get()
        try:
            await asyncio.sleep(item["seconds"])
            results.append((name, item["id"], asyncio.get_running_loop().time()))
        finally:
            queue.task_done()

async def main():
    queue, results = asyncio.Queue(maxsize=2), []
    workers = [asyncio.create_task(worker(f"w{i}", queue, results)) for i in range(2)]
    for i, s in enumerate([1.0, 0.5, 0.5, 2.0, 0.5]):
        await queue.put({"id": i, "seconds": s})
    await queue.join()
    for w in workers:
        w.cancel()
    await asyncio.gather(*workers, return_exceptions=True)
    return results

for row in asyncio.run(main()):
    print(row)

4Deduplication and clean shutdown

Two more patterns come up constantly. Single flight: when many tasks ask for the same thing at the same time (the same prompt, the same embedding, the same document), start one call and let the others await the same task, so the work is done once (problem 12). And clean shutdown: on cancellation or exit, stop accepting work, cancel or drain in-flight tasks, let their finally blocks and async with exits close connections and flush partial results, and never swallow CancelledError (14.4). Batch jobs should also write results incrementally (one JSONL line per finished request, keyed by request id, 12.2), so a crash or a cancellation loses at most the requests in flight, and a restart can skip what is done.

        raise ValueError("limit must be at least 1")

import asyncio

async def slow(seconds, log):
    try:
        await asyncio.sleep(seconds)
        return "finished"
    finally:
        log.append(f"slow({seconds}) cleaned up at {asyncio.get_running_loop().time()}")

5. Retries with exponential backoff and jitter

Write async def call_with_retry(fn, attempts=4, base=0.5, cap=8.0, rng=random.random). It awaits fn(); on TransientError it sleeps and retries, up to attempts calls in total, then re-raises. The wait before retry k (0-based) is rng() * min(cap, base * 2 ** k) ("full jitter"), unless the error has a retry_after attribute that is not None, in which case it waits exactly that many seconds. Other exceptions propagate at once.

SolutionShow the solution and why
solution.py
import asyncio, random


class TransientError(Exception):
    def __init__(self, message, retry_after=None):
        super().__init__(message)
        self.retry_after = retry_after


async def call_with_retry(fn, attempts=4, base=0.5, cap=8.0, rng=random.random):
    for k in range(attempts):
        try:
            return await fn()
        except TransientError as e:
            if k == attempts - 1:
                raise
            if e.retry_after is not None:
                delay = e.retry_after
            else:
                delay = rng() * min(cap, base * 2 ** k)
            await asyncio.sleep(delay)

The exponential part doubles the ceiling of each wait (0.5, 1, 2, 4 seconds, up to cap), giving a failing service more room each time, and the jitter draws the actual wait uniformly below that ceiling, so a crowd of clients that failed together spreads out instead of retrying in synchronised waves (the "thundering herd"). A server's Retry-After overrides the formula because the server knows when it will have capacity. Injecting rng makes the schedule exact in tests: with rng() == 1 the calls happen at 0, 0.5 and 1.5 seconds. Non-transient errors fail fast, since retrying a bad request only burns quota.

6. An async token-bucket rate limiter

Write AsyncRateLimiter(rate, capacity) with async def acquire(self) that waits until a token is available and takes it. The bucket starts full and refills at rate tokens per second (up to capacity), measured with the running loop's clock. Concurrent callers must be served in arrival order and never exceed the rate: hold an asyncio.Lock while computing the wait and sleeping.

import asyncio


class AsyncRateLimiter:
    def __init__(self, rate, capacity):
        self.rate, self.capacity = rate, capacity
        self.tokens = float(capacity)
        self.last = None
        self._lock = asyncio.Lock()

    def _refill(self):
        now = asyncio.get_running_loop().time()
        if self.last is not None:
            self.tokens = min(self.capacity, self.tokens + (now - self.last) * self.rate)
        self.last = now

    async def acquire(self):
        async with self._lock:
            self._refill()
            if self.tokens < 1:
                await asyncio.sleep((1 - self.tokens) / self.rate)
                self._refill()
            self.tokens -= 1

The bucket allows a burst of capacity requests at once, then one every 1 / rate seconds, which is how most provider limits behave; the schedule in the test (three at once, then every half second) is exactly that. Holding the lock while sleeping makes waiting callers queue up in arrival order (an asyncio.Lock is fair: waiters acquire it first come, first served), so no two callers can compute a wait from the same token count and both go through. After ten idle seconds the bucket is full again, so request 7 does not wait. The clock is read from the loop, so the limiter works unchanged on this site's simulated time and in production.

solution.py
import asyncio


async def process_all(items, handle, workers=3, maxsize=10):
    queue = asyncio.Queue(maxsize=maxsize)
    results = [None] * len(items)

    async def worker():
        while True:
            i, item = await queue.get()
            try:
                results[i] = await handle(item)
            except Exception as e:
                results[i] = f"error: {type(e).__name__}"
            finally:
                queue.task_done()

    tasks = [asyncio.create_task(worker()) for _ in range(workers)]
    try:
        for pair in enumerate(items):
            await queue.put(pair)
        await queue.join()
    finally:
        for t in tasks:
            t.cancel()
        await asyncio.gather(*tasks, return_exceptions=True)
    return results

The number of workers is the concurrency limit (the peak was exactly 3), and the bounded queue makes the producer wait instead of loading every item into memory, which matters when items come from a large file or a crawler. Each item carries its index, so results land in input order whatever the completion order. task_done sits in a finally, so a failing item still counts as processed, otherwise join would wait forever. After join, the workers are idle on get and are cancelled and awaited, in a finally so they are cleaned up even if putting items fails. Seven one-second items on three workers take three rounds, 3 seconds.

10. Completion order with asyncio.as_completed

import asyncio

async def retrieve(source, seconds):
    await asyncio.sleep(seconds)
    return source

async def main():
    loop = asyncio.get_running_loop()
    jobs = [retrieve("wiki", 1.2), retrieve("faq", 0.3), retrieve("tickets", 0.8)]

        source = await next_done

solution.py
import asyncio


async def run_batch(requests, call, limit=4, timeout=10.0, attempts=3, done_ids=()):
    done_ids = set(done_ids)
    sem = asyncio.Semaphore(limit)
    records, skipped = [], []

    async def one(req):
        async with sem:
            error = None
            for attempt in range(1, attempts + 1):
                try:
                    async with asyncio.timeout(timeout):
                        output = await call(req["prompt"])
                    records.append({"id": req["id"], "ok": True, "output": output, "error": None, "attempts": attempt})
                    return
                except (TimeoutError, ConnectionError) as e:
                    error = e
                except Exception as e:
                    records.append({"id": req["id"], "ok": False, "output": None, "error": type(e).__name__, "attempts": attempt})
                    return
            records.append({"id": req["id"], "ok": False, "output": None, "error": type(error).__name__, "attempts": attempts})

    todo = []
    for req in requests:
        if req["id"] in done_ids:
            skipped.append(req["id"])
        else:
            todo.append(req)
    await asyncio.gather(*(one(r) for r in todo))
    return {"records": records, "skipped": skipped}

This is the skeleton of every production batch client, and each feature answers a real failure. The semaphore keeps concurrency at the limit (peak 2). The per-attempt timeout turns the hung first call into a retry after 2 seconds instead of a stalled batch. Retries cover transient errors only; the invalid prompt fails at once. Records are appended as requests finish, in completion order, which is what you write to a JSONL file one line at a time (12.2), so a crash loses only the requests in flight, and done_ids lets the next run skip everything already recorded. Holding the semaphore across retries keeps the retrying request's slot; releasing it between attempts (with a backoff sleep outside the semaphore) is a reasonable alternative when retries are slow.

12. Single-flight deduplication

Write SingleFlight with async def run(self, key, fn): if a call for key is already in progress, await its result instead of starting another; otherwise start fn() as a task, store it, and remove it when it finishes (success or failure) so a later call starts fresh. All waiters receive the same result or the same exception. Add self.started, counting calls actually made per key.

solution.py
import asyncio


class SingleFlight:
    def __init__(self):
        self._inflight = {}
        self.started = {}

    async def run(self, key, fn):
        task = self._inflight.get(key)
        if task is None:
            self.started[key] = self.started.get(key, 0) + 1
            task = asyncio.create_task(fn())
            self._inflight[key] = task
            task.add_done_callback(lambda t, k=key: self._inflight.pop(k, None))
        return await task

When five users ask the same question at once, or a batch contains duplicate texts, a cache cannot help because the first answer is not there yet; single flight shares the in-progress task, so the expensive call runs once and every waiter awaits the same task, receiving the same value or the same exception. The done callback removes the entry when the task finishes, so failures are not cached forever and a later request starts fresh (the third refund call ran again). Because the event loop runs one task at a time, the check-and-insert in run needs no lock: there is no await between them (14.4). Combined with a result cache (13.3's TTL cache), this removes most duplicate LLM and embedding calls.

13. Read the code: an async ingestion service

Three production failures, three fixes. The semaphore keeps the embedding API at 2 concurrent calls instead of all at once. 14. Shutting down workers

import asyncio

log = []

async def worker(name, delay):
    try:
        while True:
            await asyncio.sleep(delay)
            log.append(f"{name} tick")
    except asyncio.CancelledError:
        log.append(f"{name} flushing")
        raise
    finally:
        log.append(f"{name} closed")

async def main():
    tasks = [asyncio.create_task(worker("a", 1.0)), asyncio.create_task(worker("b", 1.5))]
    await asyncio.sleep(3.2)
    for t in tasks:
        t.cancel()
    results = await asyncio.gather(*tasks, return_exceptions=True)
    return [type(r).__name__ for r in results], [t.cancelled() for t in tasks], asyncio.get_running_loop().time()

print(asyncio.run(main()), log)

Cancelling raises CancelledError inside each worker at its sleep; the handler runs (the place to flush buffered results) and re-raises, then finally closes resources. gather with return_exceptions=True waits for both to finish cancelling and returns the CancelledError instances instead of raising, so a shutdown routine can wait for every worker to clean up before the program exits.

Interview

15. How would you call an LLM API 100,000 times as fast as the limits allow, and reliably?

SolutionModel answer

Use an async client with bounded concurrency (a semaphore or a fixed pool of queue workers) sized by Little's law from the provider's limits and observed latency, plus a client-side rate limiter (token bucket) for requests and estimated tokens per minute. Give every call a timeout, and retry transient failures (timeouts, connection errors, 429, 5xx) with exponential backoff and jitter, honouring Retry-After, a bounded number of times; fail fast on 4xx errors. Stream inputs from a file or queue instead of loading everything, and write each result as it completes to durable storage (JSONL keyed by request id), so the job is resumable and never pays twice for a request. Track progress, error rates, latency percentiles and token cost as it runs, and stop or slow down automatically if error rates spike. Deduplicate identical prompts (cache and single flight). For offline work, consider the provider's batch API, which trades latency (hours) for lower cost and separate limits.

Interview

16. Why add jitter to exponential backoff?

SolutionModel answer

When a service fails briefly, many clients fail at the same moment. With plain exponential backoff, they all wait 1, 2, 4 seconds exactly and retry in synchronised waves, so each wave hits the recovering service with the full load at once and can knock it down again (the "thundering herd"). Jitter randomises each client's wait, for example uniformly between 0 and the exponential ceiling ("full jitter"), which spreads retries over the interval and turns spikes into a smooth, lower load, at the cost of slightly less predictable individual delays. It also avoids retries colliding with periodic jobs. Combined with a cap on the wait, a maximum number of attempts, and honouring Retry-After, it is the standard retry policy recommended by cloud providers and implemented by libraries such as tenacity and backoff.

Interview

17. How do you shut down an asyncio service gracefully?

SolutionModel answer

Stop taking new work first: stop accepting connections or reading from the input queue, and signal producers (an Event, queue.shutdown() in 3.13+). Then let in-flight work finish within a grace period (asyncio.wait with a timeout, or queue.join()), and cancel what remains; cancellation raises CancelledError at each task's current await, so tasks run their finally blocks and async with exits, flushing buffers, committing or rolling back, and closing clients. Await the cancelled tasks (gather(..., return_exceptions=True)) so cleanup actually completes before closing shared resources such as HTTP clients and database pools, in reverse order of creation. Never swallow CancelledError, and shield the few steps that must finish (writing a checkpoint) with asyncio.shield. Handle SIGTERM by triggering this sequence (loop.add_signal_handler on Unix), because container platforms send it before killing the process; frameworks such as FastAPI expose this as lifespan shutdown hooks. Structured concurrency with TaskGroup makes most of this automatic, since cancelling the group cancels its children.

Recap

  • Bound concurrency with a semaphore acquired inside each task, around the call; measure peak concurrency in tests.
  • Respect rate limits with a token bucket, give every call a timeout (asyncio.timeout), and retry transient errors with capped exponential backoff, jitter and Retry-After.
  • For streams of work, use worker tasks on a bounded asyncio.Queue (back-pressure), task_done in finally, join, then cancel the workers.
  • Deduplicate in-flight work with single flight; write results incrementally so batches are resumable.
  • Shut down by stopping intake, draining or cancelling tasks, awaiting their cleanup, and never swallowing CancelledError.
