1How to use this page

When a tool misbehaves, ask three questions in order. Which code is running? Check sys.path, module.__file__, __name__ and import-time side effects (15.1). Which versions are installed, and which were declared? Parse versions and requirements with packaging, never as strings, and compare the environment with the lock (15.2). How is it invoked? Through main(argv) -> int, with results on standard output, diagnostics on standard error and meaningful exit codes (15.3).

The problems mix the lessons on purpose, and the mini project combines all three in a tool you could ship with an LLM project.

HintOpen a hint

python -m pkg is runpy.run_module("pkg", run_name="__main__"): it imports the package, then runs pkg/__main__.py as __main__ with __package__ set.

SolutionShow the solution and why
Real output
package init, __name__ = reporter_p1
main, __name__ = __main__ __package__ = reporter_p1

Running a package with python -m first imports the package (its __init__ runs, with its normal name), then executes __main__.py under the name "__main__" but with __package__ set to the package, which is exactly why relative imports such as from .core import summary work there and fail when the file is run directly as a script. The package stays imported, so a later import reporter_p1.core is served from sys.modules without running __init__ again.

2. Bump a version

Write bump(version, part) returning the next version string for part in "major", "minor", "patch": 1.4.2 becomes 2.0.0, 1.5.0 or 1.4.3. Drop any pre-release, post-release, dev or local part before bumping (2.0.0rc1 bumped as a patch gives 2.0.1), and count missing segments as 0 (1.4 bumped as a patch gives 1.4.1). An unknown part raises ValueError.

assert bump("v3.1.0+cu121", "major") == "4.0.0"

except ValueError:
    pass

Version(version).release gives the integer segments; pad to three with zeros.

Hint 2Open a hint

Return f"{major}.{minor}.{patch}" after incrementing one and resetting the lower ones.

SolutionShow the solution and why
solution.py
from packaging.version import Version


def bump(version, part):
    major, minor, patch = (list(Version(version).release) + [0, 0, 0])[:3]
    if part == "major":
        return f"{major + 1}.0.0"
    if part == "minor":
        return f"{major}.{minor + 1}.0"
    if part == "patch":
        return f"{major}.{minor}.{patch + 1}"
    raise ValueError(f"unknown part: {part!r}")

Parsing with Version normalises everything a version string may carry (a leading v, pre-release, post-release and local labels) and exposes the numeric release segments, so the bump logic is three lines of integer arithmetic. Resetting the lower segments is the semantic-versioning rule: a new minor release starts at patch 0. Release tooling (uv version --bump, bump-my-version, hatch version) implements this together with updating pyproject.toml and tagging the commit.

3. A plugin loader that hides real import errors

load_scorer(name) imports scorers_f3.<name> and returns its score function, reporting LookupError(f"no scorer named {name}") when the plugin does not exist. But it catches every ImportError, so a plugin that exists but fails to import one of its own dependencies is also reported as "no scorer named ...", which sends people looking in the wrong place. Only translate the error when the missing module is the plugin itself (e.name).

except ModuleNotFoundError as e: and check e.name == f"scorers_f3.{name}"; otherwise re-raise with a bare raise.

SolutionShow the solution and why
solution.py
import importlib

def load_scorer(name):
    target = f"scorers_f3.{name}"
    try:
        module = importlib.import_module(target)
    except ModuleNotFoundError as e:
        if e.name == target:
            raise LookupError(f"no scorer named {name}") from None
        raise
    return module.score

ModuleNotFoundError carries the name of the module that could not be found. When it is the plugin itself, "no such scorer" is the right message; when it is something the plugin imports, the real problem is a missing dependency (an extra that was not installed, 15.2), and re-raising preserves the original error and traceback that say so. Catching broad exceptions and replacing them with a friendly message is only friendly when the message is true; otherwise it turns a one-minute fix into an hour of searching.

4. parse_args and sys.argv

import argparse, sys

def build():
    p = argparse.ArgumentParser(prog="sync-index")
    p.add_argument("--full", action="store_true")
    p.add_argument("source", nargs="?", default="docs/")
    return p

saved = sys.argv
try:
    sys.argv = ["sync-index", "--full", "kb/"]
    a = build().parse_args()
    b = build().parse_args([])
    c = build().parse_args(None)
finally:
    sys.argv = saved
print((a.full, a.source), (b.full, b.source), (c.full, c.source), build().prog)
HintOpen a hint

parse_args() and parse_args(None) read sys.argv[1:]; an explicit empty list means no arguments at all.

SolutionShow the solution and why
Real output
(True, 'kb/') (False, 'docs/') (True, 'kb/') sync-index

With no argument (or None), parse_args reads sys.argv[1:], so a and c both see --full kb/. Passing [] explicitly parses an empty command line, so b gets the defaults; nargs="?" makes the positional optional with its default. This is why main(argv=None) works both as an entry point (called with nothing, it reads the real command line) and in tests (called with an explicit list, it ignores the real one).

5. Review a dependency change

Write requirements_diff(old, new) comparing two lists of requirement strings by canonical name and returning {"added": [...], "removed": [...], "changed": [...]}, each sorted, where changed holds strings f"{name}: {old_spec} -> {new_spec}" for projects whose specifier, extras or marker changed (show the specifier, or "(any)" when empty, followed by [extras] when present).

Hint 2Open a hint

A small helper describe(req) builds "<spec or (any)>[extras]".

SolutionShow the solution and why
solution.py
from packaging.requirements import Requirement
from packaging.utils import canonicalize_name


def _parse(lines):
    return {canonicalize_name(r.name): r for r in map(Requirement, lines)}


def _key(req):
    return (str(req.specifier), sorted(req.extras), str(req.marker) if req.marker else "")


def _describe(req):
    spec = str(req.specifier) or "(any)"
    extras = f"[{','.join(sorted(req.extras))}]" if req.extras else ""
    return spec + extras


def requirements_diff(old, new):
    a, b = _parse(old), _parse(new)
    changed = [f"{n}: {_describe(a[n])} -> {_describe(b[n])}" for n in sorted(a.keys() & b.keys()) if _key(a[n]) != _key(b[n])]
    return {"added": sorted(b.keys() - a.keys()), "removed": sorted(a.keys() - b.keys()), "changed": changed}

Dependency changes deserve review like code changes, and a semantic diff is far easier to read than a text diff: renaming httpx to HTTPX is not a change at all, while widening pydantic from ~=2.7 to <3,>=2.9 or adding an extra to openai pulls in different code. Comparing parsed specifiers, extras and markers catches exactly those, and canonical names prevent false "removed and added" pairs. A CI job can post this summary on every pull request that touches pyproject.toml.

6. Validate the scripts table

Write validate_scripts(pyproject_text) returning a sorted list of problems in [project.scripts]: "NAME: target must look like module:function" when there is no single : with text on both sides, "NAME: module MODULE not found" when importlib.util.find_spec finds nothing (without importing it), and nothing otherwise. SolutionShow the solution and why
solution.py
import importlib.util, tomllib


def validate_scripts(pyproject_text):
    scripts = tomllib.loads(pyproject_text).get("project", {}).get("scripts", {})
    problems = []
    for name, target in scripts.items():
        module, sep, func = target.partition(":")
        if not sep or not module or not func or ":" in func:
            problems.append(f"{name}: target must look like module:function")
            continue
        try:
            found = importlib.util.find_spec(module) is not None
        except ModuleNotFoundError:
            found = False
        if not found:
            problems.append(f"{name}: module {module} not found")
    return sorted(problems)

A wrong entry point is only discovered when someone installs the package and types the command, typically in production; validating [project.scripts] in CI catches it at the pull request. The format check rejects the classic dotted-path mistake (cli.main instead of cli:main), and find_spec confirms the module exists without importing it, so the check has no side effects (15.1). A fuller check would import the module in a clean environment and confirm the function exists and is callable.

7. Read the code: a release helper

release_check gates a model-serving release: the requested version must be newer than every published version, and each required package must be installed at a satisfying version. It compares versions as strings, considers 2.0.0rc1 newer than 2.0.0, matches package names exactly, and returns True/False without saying why. Rewrite it to return a sorted list of problems (empty means go): "version V is not newer than LATEST", "missing: NAME", "NAME VERSION does not satisfy SPEC".

SolutionShow the solution and why
solution.py
from packaging.requirements import Requirement
from packaging.utils import canonicalize_name
from packaging.version import Version


def release_check(version, published, required, installed):
    problems = []
    latest = max(published, key=Version) if published else None
    if latest is not None and Version(version) <= Version(latest):
        problems.append(f"version {version} is not newer than {latest}")
    have = {canonicalize_name(k): v for k, v in installed.items()}
    for line in required:
        req = Requirement(line)
        name = canonicalize_name(req.name)
        if name not in have:
            problems.append(f"missing: {name}")
        elif not req.specifier.contains(Version(have[name]), prereleases=True):
            problems.append(f"{name} {have[name]} does not satisfy {req.specifier}")
    return sorted(problems)

String comparison got every version question wrong: "1.10.0" sorts below "1.9.0", "2.10.0" below "2.3", and "2.0.0rc1" above "2.0.0", so the gate could approve a version that goes backwards and reject a valid environment. Version compares by PEP 440, where a release candidate precedes its final release, so 2.0.0 is a valid release after 2.0.0rc1. Package names need canonicalising (Torch is torch), requirements need the real parser (extras broke partition), and a gate should say why it fails, listing every problem at once, so the release engineer can fix them in one pass.

Interview

8. You install your package and mytool runs an old version of your code. What could be going on?

SolutionModel answer

Usually more than one copy of the code or the interpreter is in play. The mytool on PATH may belong to another environment (a global install, a previous virtual environment, pipx); check which mytool (or where on Windows) and the shebang inside it. The package may be installed non-editable in the environment, so a wheel copy in site-packages is used instead of your working tree (pip install -e . or uv sync fixes it); python -c "import mytool; print(mytool.__file__)" shows which copy is imported. Stale build artefacts (build/, an old wheel, .egg-info) or a cached __pycache__ from a moved file can confuse things, and a local folder or file with the same name can shadow the installed package. Finally, the entry point may point at an old module path. Printing sys.executable, sys.path and module.__file__ settles it quickly.

Interview

9. How would you structure a Python project that ships both a library and a command-line tool?

SolutionModel answer

Use a src/ layout with one importable package (src/mytool/): pure, well-tested library modules for the domain logic, and a thin cli.py that only parses arguments (argparse, Click or Typer), reads configuration with clear precedence, calls library functions, writes results to standard output and diagnostics to standard error, and returns exit codes from main(argv) -> int. Declare everything in pyproject.toml: metadata, requires-python, runtime dependencies with ranges (it is a library), heavy optional features as extras (mytool[pdf]), development tools in dependency groups, and [project.scripts] mytool = "mytool.cli:main"; add __main__.py so python -m mytool works too. Keep import-time side effects out of the package. Test the library directly, the CLI through main([...]) with captured streams, and the installed entry point with a few subprocess tests; lock development environments with uv.lock, test against the minimum and latest supported dependency versions in CI, and publish wheels from CI with versions bumped deliberately.

3Mini project: an evaluation command-line tool

Teams evaluate prompts and models from the command line and from CI. Build evalctl, a small tool with three subcommands: run scores model answers read as JSON Lines, using a scorer plugin chosen by name; summary aggregates result lines; check-env checks installed package versions against requirements. It must behave well in pipes and schedulers: data on standard output, diagnostics on standard error, and meaningful exit codes.

Project

10. Build the evalctl command

Implement main(argv=None, *, stdin=None, stdout=None, stderr=None, env=None, installed=None).

  • run [--scorer MODULE:FUNC] [--threshold T]: read JSONL lines {"id", "answer", "expected"} from stdin; load the scorer with importlib (15.1), default "evalctl_scorers.exact:score"; write one JSONL line per case to stdout, {"id", "score", "passed"} with passed = score >= threshold. The threshold comes from --threshold, else the EVAL_THRESHOLD environment variable in env, else 0.5 (15.3 precedence). Invalid JSON lines are reported on stderr as f"line {n}: invalid JSON"; exit code 1 if any line was invalid, else 0. A scorer target that cannot be loaded prints f"error: cannot load scorer {target}" to stderr and returns 2.
  • summary: read result lines from stdin and print f"cases={n} passed={p} rate={p / n:.2f}" (rate 0.00 when empty); exit 0.
  • check-env REQUIREMENT...: compare with installed (a dict of names to versions; canonicalise names, 15.2); print one line per problem to stderr, sorted (f"missing: {name}" or f"{name} {version} does not satisfy {spec}"), print "ok" to stdout when there is none; exit 0 if fine, else 1.

Streams default to the sys ones and env to os.environ.

SolutionShow the solution and why
solution.py
import argparse, importlib, json, os, sys
from packaging.requirements import Requirement
from packaging.utils import canonicalize_name
from packaging.version import Version

DEFAULT_SCORER = "evalctl_scorers.exact:score"


def _load(target):
    module_name, sep, attr = target.partition(":")
    if not sep:
        raise ValueError(target)
    fn = getattr(importlib.import_module(module_name), attr)
    if not callable(fn):
        raise ValueError(target)
    return fn


def _run(args, io):
    try:
        scorer = _load(args.scorer)
    except (ImportError, AttributeError, ValueError):
        print(f"error: cannot load scorer {args.scorer}", file=io["stderr"])
        return 2
    threshold = args.threshold if args.threshold is not None else float(io["env"].get("EVAL_THRESHOLD", 0.5))
    bad = False
    for n, line in enumerate(io["stdin"], start=1):
        if not line.strip():
            continue
        try:
            case = json.loads(line)
        except json.JSONDecodeError:
            print(f"line {n}: invalid JSON", file=io["stderr"])
            bad = True
            continue
        score = scorer(case["answer"], case["expected"])
        io["stdout"].write(json.dumps({"id": case["id"], "score": score, "passed": score >= threshold}) + "\n")
    return 1 if bad else 0


def _summary(args, io):
    n = passed = 0
    for line in io["stdin"]:
        if line.strip():
            n += 1
            passed += bool(json.loads(line)["passed"])
    rate = passed / n if n else 0.0
    print(f"cases={n} passed={passed} rate={rate:.2f}", file=io["stdout"])
    return 0


def _check_env(args, io):
    have = {canonicalize_name(k): v for k, v in io["installed"].items()}
    problems = []
    for line in args.requirements:
        req = Requirement(line)
        name = canonicalize_name(req.name)
        if name not in have:
            problems.append(f"missing: {name}")
        elif not req.specifier.contains(Version(have[name]), prereleases=True):
            problems.append(f"{name} {have[name]} does not satisfy {req.specifier}")
    for p in sorted(problems):
        print(p, file=io["stderr"])
    if not problems:
        print("ok", file=io["stdout"])
    return 1 if problems else 0


def main(argv=None, *, stdin=None, stdout=None, stderr=None, env=None, installed=None):
    io = {"stdin": stdin or sys.stdin, "stdout": stdout or sys.stdout, "stderr": stderr or sys.stderr,
          "env": os.environ if env is None else env, "installed": installed or {}}
    parser = argparse.ArgumentParser(prog="evalctl")
    sub = parser.add_subparsers(dest="command", required=True)
    run = sub.add_parser("run", help="score answers read from stdin")
    run.add_argument("--scorer", default=DEFAULT_SCORER)
    run.add_argument("--threshold", type=float, default=None)
    run.set_defaults(func=_run)
    summary = sub.add_parser("summary", help="aggregate result lines")
    summary.set_defaults(func=_summary)
    check = sub.add_parser("check-env", help="check installed versions")
    check.add_argument("requirements", nargs="+")
    check.set_defaults(func=_check_env)
    args = parser.parse_args(argv)
    return args.func(args, io)

Every lesson of the module has a job here:

  • Imports (15.1): the scorer is a plugin named by a module:function string and loaded with importlib.import_module, so new scorers are added by writing a module, not by editing the tool; a target that cannot be loaded is a usage problem, exit code 2.
  • Dependencies (15.2): check-env uses packaging's Requirement, canonicalize_name and Version, so names like Pydantic and versions like 1.9.0 versus >=1.26 are judged correctly.
  • The CLI (15.3): subcommands dispatch through set_defaults(func=...), the threshold follows the precedence default < environment < flag, results go to standard output as JSON Lines so evalctl run < cases.jsonl | evalctl summary works, problems go to standard error, and the exit code tells CI whether to fail the build.

Injecting the streams, the environment and the installed-package map makes the whole tool testable without subprocesses; in a real package, installed would come from importlib.metadata, main would be registered as [project.scripts] evalctl = "evalctl.cli:main", and python -m evalctl would call it from __main__.py.

Recap

  • python -m pkg imports the package and runs pkg/__main__.py as __main__ with __package__ set, so relative imports work.
  • Load plugins with importlib.import_module, and translate ModuleNotFoundError only when the missing module is the plugin itself.
  • Treat versions and requirements as data: Version, Requirement, canonicalize_name; diff and validate them in CI.
  • parse_args(None) reads sys.argv; main(argv=None) -> int serves both entry points and tests.
  • A good tool keeps data on stdout, diagnostics on stderr, and tells schedulers the truth with its exit code.
