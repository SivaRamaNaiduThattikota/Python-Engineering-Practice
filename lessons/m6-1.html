6.1 List comprehensions

A list comprehension builds a list from another iterable in one expression. What it translates to, filtering versus transforming, several for clauses, its own scope, why it is fast, and when a plain loop is the better choice. Applied to batching, message building, feature extraction and chunking.

1What a comprehension is, and the loop it stands for

A list comprehension builds a new list by running an expression for every item of an iterable. The general shape is [expression for name in iterable if condition], and it means exactly the same as this loop:

loop_vs_comp.py
scores = [0.91, 0.42, 0.77, 0.15]

# the loop
kept = []
for s in scores:
    if s >= 0.5:
        kept.append(round(s * 100))

# the comprehension: the same three parts, in a different order
kept2 = [round(s * 100) for s in scores if s >= 0.5]
print(kept, kept2, kept == kept2)
Output
[91, 77] [91, 77] True

Read a comprehension in this order: first the for part (what you loop over and the name each item gets), then the if part (which items are kept), and last the expression at the front (what goes into the new list for each kept item). The expression comes first in the syntax because it is the most important thing: the result is "a list of these". Step by step, Python creates an empty list, takes each item of scores in order, binds it to s, evaluates the condition, and if it is true evaluates the expression and appends the result. The original list is never changed.

Any iterable works on the right: lists, tuples, strings, range, dict views, files (one line per item), and the generators of 6.3. The result is always a new list. The parts are optional except the first for: [x * 2 for x in xs] only transforms, [x for x in xs if x] only filters (it drops falsy items like "", 0 and None).

any_iterable.py
print([c.upper() for c in "rag"], [n * n for n in range(5)])
print([w for w in ["a", "", "b", None, "c"] if w])
totals = {"api": 12, "web": 0, "db": 7}
print([name for name, n in totals.items() if n > 0])
Output
['R', 'A', 'G'] [0, 1, 4, 9, 16]
['a', 'b', 'c']
['api', 'db']
≈
SQL / Power BI

A comprehension reads like a small SELECT: [round(s * 100) for s in scores if s >= 0.5] is SELECT ROUND(s * 100) FROM scores WHERE s >= 0.5. The expression is the select list, the for is the FROM, the if is the WHERE. In Power Query it is Table.SelectRows followed by Table.TransformColumns, and in DAX it is close to SELECTCOLUMNS(FILTER(...), ...).

2Filtering versus transforming: where the if goes

There are two different ifs, and mixing them up is the most common comprehension mistake. An if at the end is a filter: items that fail it are left out, so the result can be shorter than the input. An if ... else at the front is a conditional expression (a if cond else b): every item produces something, so the result has the same length as the input. A filter has no else; a conditional expression must have one.

if_positions.py
xs = [3, -1, 0, 5, -2]
print([x for x in xs if x > 0])            # filter: shorter
print([x if x > 0 else 0 for x in xs])     # transform: same length (ReLU)
print(["pos" if x > 0 else "zero" if x == 0 else "neg" for x in xs])
print([x * 10 if x % 2 else x for x in xs if x != 0])   # both at once
Output
[3, 5]
[3, 0, 0, 5, 0]
['pos', 'neg', 'zero', 'pos', 'neg']
[30, -10, 50, -2]

The second line is the ReLU activation function from neural networks, written as a comprehension: negative values become 0, the length is kept. Keeping the length matters whenever the list is aligned with another one, such as predictions and labels: filtering one of them silently misaligns every item after the first dropped one (problem 6).

Conditional expressions can be chained, as the third line shows, but two levels is the readable limit; beyond that, put the logic in a small named function and call it from the comprehension. Two filters in a row, if a if b, mean if a and b. The syntax errors tell you which if you used wrongly: [x if x > 0 for x in xs] is a SyntaxError because a front-position if needs an else, and [x for x in xs if x > 0 else 0] is one because a filter cannot have an else.

if_rules.py
def label(score):
    if score >= 0.8:
        return "high"
    if score >= 0.5:
        return "medium"
    return "low"

print([label(s) for s in [0.91, 0.42, 0.77, 0.15]])
print([n for n in range(20) if n % 2 if n % 3])     # odd and not divisible by 3
for bad in ["[x if x > 0 for x in xs]", "[x for x in xs if x > 0 else 0]"]:
    try:
        compile(bad, "<demo>", "eval")
    except SyntaxError as e:
        print("SyntaxError:", e.msg)
Output
['high', 'low', 'medium', 'low']
[1, 5, 7, 11, 13, 17, 19]

3Several for clauses, and comprehensions inside comprehensions

A comprehension can have more than one for. They nest left to right, in the same order as written loops: the first for is the outer loop, the next one is inside it. So [(a, b) for a in "xy" for b in "12"] is the loop for a in "xy": with for b in "12": inside, producing x1, x2, y1, y2. A later for can use the name of an earlier one, which is how you flatten a list of lists: [x for row in rows for x in row] ("for each row, for each x in that row").

multi_for.py
print([a + b for a in "xy" for b in "12"])
docs = [["refund", "policy"], ["reset", "password", "now"], []]
print([w for doc in docs for w in doc])
print([w for doc in docs if len(doc) > 2 for w in doc if w != "now"])
flat = []
for doc in docs:           # the same as the second line, as loops
    for w in doc:
        flat.append(w)
print(flat)
Output
['x1', 'x2', 'y1', 'y2']
['refund', 'policy', 'reset', 'password', 'now']
['reset', 'password']
['refund', 'policy', 'reset', 'password', 'now']

A trick for the order: write the loops as normal nested loops first, then move the innermost body (flat.append(w)) to the front, and keep the for and if lines in their original order. Putting the fors the other way round, [w for w in doc for doc in docs], fails because doc is used before the loop that defines it.

Different again is a comprehension inside the expression of another, which builds a list of lists: [[r * c for c in range(3)] for r in range(3)] builds a 3 x 3 table, one inner list per row. This is how you create a grid correctly. The tempting [[0] * 3] * 3 does not work: * repeats references to one inner list (2.2), so all three rows are the same object and changing one changes them all (problem 3).

nested_comp.py
table = [[r * c for c in range(3)] for r in range(3)]
print(table)
matrix = [[1, 2, 3], [4, 5, 6]]
print([[row[i] for row in matrix] for i in range(3)])     # transpose
bad = [[0] * 3] * 3
good = [[0] * 3 for _ in range(3)]
bad[0][0] = 9
good[0][0] = 9
print(bad, good)
Output
[[0, 0, 0], [0, 1, 2], [0, 2, 4]]
[[1, 4], [2, 5], [3, 6]]
[[9, 0, 0], [9, 0, 0], [9, 0, 0]] [[9, 0, 0], [0, 0, 0], [0, 0, 0]]

Use _ as the loop name when the value is not needed, as in for _ in range(3): it tells the reader the loop only counts. Beyond two for clauses, or when nesting and filters combine, a written loop is usually clearer.

4Scope: what a comprehension can see and leak

A comprehension has its own scope for its loop variables. In Python 3 the name after for does not exist after the comprehension, and it does not overwrite a variable with the same name outside it. (In Python 2 it did leak, which is why old code avoided reusing names.) Everything else follows the normal rules of 3.3: the expression and conditions can read variables from the enclosing function and module.

comp_scope.py
x = "outer"
squares = [x * x for x in range(4)]
print(squares, x)
threshold = 2
print([n for n in range(5) if n > threshold])     # reads the enclosing name
try:
    print(n)
except NameError as e:
    print("NameError:", e)
Output
[0, 1, 4, 9] outer
[3, 4]
NameError: name 'n' is not defined

Two scope details matter in real code. The walrus operator := inside a comprehension binds its name in the enclosing scope, on purpose, so you can compute a value once, use it in both the filter and the expression, and still see the last value afterwards. And because the loop variable is looked up when a function runs, not when it is created, [lambda: i for i in range(3)] builds three functions that all see the last i: the late-binding closure of 3.4. The fix is the same as there: bind the current value as a default argument, lambda i=i: i (problem 10).

walrus_and_lambdas.py
texts = ["  refund  ", "", "reset password ", "   "]
cleaned = [t for raw in texts if (t := raw.strip())]
print(cleaned, repr(t))
fns = [lambda: i for i in range(3)]
fixed = [lambda i=i: i for i in range(3)]
print([f() for f in fns], [f() for f in fixed])
Output
['refund', 'reset password'] ''
[2, 2, 2] [0, 1, 2]

In the first line, raw.strip() runs once per item: its result is bound to t, tested in the filter, and reused in the expression. Without the walrus you would write [raw.strip() for raw in texts if raw.strip()] and strip every item twice.

5Speed: what is true today, and what comprehensions cost

You will often read that comprehensions are much faster than a loop with append. The reason is real: the loop looks up result.append on every iteration and makes a method call, while the comprehension compiles to a dedicated bytecode instruction, LIST_APPEND, that adds to the list directly. On older Pythons that saved 20 to 50 percent for simple expressions. But since Python 3.11 the interpreter specialises hot code while it runs, and it recognises some_list.append(x) and turns it into a fast path; Python 3.12 also inlines comprehensions into the enclosing function. Measured on this page's Python 3.14, squaring a million integers takes nearly the same time either way (a few percent apart). The lesson is the general one: performance folklore goes out of date, so measure on the version you run.

So choose a comprehension for clarity: it says "build a list of these" in one expression, with no half-built list visible to the rest of the function. The big speed differences come from elsewhere: doing less work (stopping early, as below), using a better data structure (4.4, 4.5), or moving numeric work into NumPy, which runs the whole loop in C.

bytecode.py
import dis

def with_loop(xs):
    out = []
    for x in xs:
        out.append(x * 2)
    return out

def with_comp(xs):
    return [x * 2 for x in xs]

def ops(f):
    return {i.opname for i in dis.get_instructions(f)}

print("LIST_APPEND" in ops(with_comp), "LIST_APPEND" in ops(with_loop))
print(with_loop([1, 2]) == with_comp([1, 2]))
Output
True False
True

The real cost of a list comprehension is memory: it builds the whole list at once. That is fine for thousands or millions of small items, but not for a 50 GB file, and it is wasteful when you only need one pass over the results, such as a sum or an any check. Replacing the square brackets with parentheses gives a generator expression, which produces items one at a time without storing them (6.3). With any and all it also stops early: the list version computes every item first, the generator version stops at the first true one.

comp_vs_genexp.py
calls = 0

def is_long(text):
    global calls
    calls += 1
    return len(text) > 10

docs = ["short", "a very long document", "x", "y", "z"]
print(any([is_long(d) for d in docs]), calls)
calls = 0
print(any(is_long(d) for d in docs), calls)
print(sum(len(d) for d in docs))
Output
True 5
True 2
28

map and filter do the same jobs (list(map(str.upper, words))), and they can be slightly faster when the function is a C built-in, but a comprehension is clearer as soon as you need a lambda or both filtering and transforming.

6When to use a comprehension, and when not

Use a comprehension when you are building a list from another iterable with one expression and at most a simple filter. That covers a large share of everyday data code: selecting fields, cleaning values, filtering results, batching, building prompts and messages. Use a written loop when:

  • the body has several statements, try / except, or early exits (break, return);
  • you need side effects, such as printing, logging or writing to a database: [print(x) for x in xs] builds a list of None values just to throw it away, and hides the side effect in an expression;
  • the comprehension would need more than two for clauses or chained conditions that no longer read as one sentence;
  • you are updating existing objects rather than building new values.
in_practice.py
texts = ["Refunds take 5 days.", "Reset your password here.", "OK"]
batch_size = 2
batches = [texts[i:i + batch_size] for i in range(0, len(texts), batch_size)]
print(batches)
history = [("user", "Hi"), ("assistant", "Hello!"), ("user", "Refund?")]
messages = [{"role": role, "content": text} for role, text in history]
print(messages[-1])
features = [[len(t), t.count(" ") + 1, t.endswith("?")] for t in texts]
print(features)
Output
[['Refunds take 5 days.', 'Reset your password here.'], ['OK']]
{'role': 'user', 'content': 'Refund?'}
[[20, 4, False], [25, 4, False], [2, 1, False]]

These three are the most common comprehensions in GenAI and ML code. Batching with range(0, n, size) and slices sends texts to an embedding API in groups that respect its limit (slices never fail, so the last batch is simply shorter). Message building turns stored chat history into the list of dicts that chat APIs expect. Feature extraction turns each text into a row of numbers, the list-of-lists shape that scikit-learn accepts as X.

solution.py
def batches(texts, size):
    if size < 1:
        raise ValueError("size must be at least 1")
    return [texts[i:i + size] for i in range(0, len(texts), size)]

The range step jumps from one batch start to the next, and the slice takes up to size items, shorter at the end because slicing past the end is safe (4.1). With an empty list, range(0, 0, size) is empty, so the result is []. The check for size comes first because range with a step of 0 raises its own, less helpful, ValueError, and a negative step would silently return nothing. itertools.batched (Python 3.12+, 6.4) does the same lazily.

def empty_grid(rows, cols):

solution.py
def context_chunks(results, min_score, limit):
    good = [r for r in results if r["score"] >= min_score and r["text"].strip()]
    good.sort(key=lambda r: r["score"], reverse=True)
    return [r["text"].strip() for r in good[:limit]]

Each step is one simple operation: filter, sort, cut, project. Filtering before sorting means less to sort. Checking r["text"].strip() in the filter drops the whitespace-only result even though it has the best score, which is a real failure mode: a high-scoring empty chunk wastes a context slot. Sorting the filtered dicts (rather than the texts) keeps the score available as the key (4.2). The same filter-sort-limit shape appears in every RAG pipeline before the prompt is built.

6. ReLU that drops values

relu(xs) should replace negative values with 0 and keep the rest, so the output lines up with the input. The code drops the negatives instead, and predictions no longer align with labels. Fix it.

TestsThe 3 checks Run tests uses
assert relu([1.5, -2.0, 0.0, 3.0]) == [1.5, 0.0, 0.0, 3.0]
assert len(relu([-1] * 5)) == 5
assert relu([]) == []
HintOpen a hint

You need a value for every item: a conditional expression at the front, not a filter at the end.

SolutionShow the solution and why
solution.py
def relu(xs):
    return [x if x > 0 else 0.0 for x in xs]

A filter changes the length; a conditional expression at the front keeps it, producing one value per input. Whenever a list is aligned with another (features and labels, predictions and ids), filtering one of them shifts every later item, and the error shows up far away as nonsense metrics rather than as an exception. max(x, 0.0) is an equivalent expression. In NumPy this is np.maximum(xs, 0), done on the whole array at once.

10. Scalers that all use the last factor

make_scalers(factors) should return one function per factor, each multiplying its input by that factor. Every function multiplies by the last factor. Fix it.

TestsThe 2 checks Run tests uses

HintOpen a hint

The lambda looks up f when it is called, after the comprehension has finished. Capture the current value as a default argument.

SolutionShow the solution and why
solution.py
def make_scalers(factors):
    return [lambda x, f=f: x * f for f in factors]

All three lambdas close over the same variable f of the comprehension's scope, and they read it when called, by which time the loop has finished and f is 0.5: late binding (3.4). A default argument is evaluated when the lambda is created, so f=f stores each current value in its own function. functools.partial(operator.mul, f) is an alternative that avoids the trick. The same bug appears when building callbacks or tools in a loop.

Hint 2Open a hint

SolutionShow the solution and why
solution.py
def one_hot(labels, classes):
    unknown = sorted(set(labels) - set(classes))
    if unknown:
        raise ValueError(f"unknown labels: {unknown}")
    return [[int(c == label) for c in classes] for label in labels]

Validation comes first, with set difference (4.4), so the function fails with a clear message instead of producing a row of all zeros that a model would silently learn from. The nested comprehension builds one inner list per label; inside it, int(c == label) turns the True/False comparison into 1/0. Each row is compared against every class, which is O(labels x classes); for many classes, build an index dict once (4.5) and set one position per row. scikit-learn's OneHotEncoder and pandas.get_dummies do this on whole columns.

14. Overlapping windows for chunking

RAG pipelines often cut token lists into overlapping windows so a sentence at a boundary appears whole in at least one chunk. Write windows(tokens, size, overlap) returning windows of size tokens, each starting size - overlap after the previous one. If the last regular window does not reach the end, add one final window made of the last size tokens. If there are size tokens or fewer, return one window with all of them (none for an empty list). Raise ValueError unless 0 <= overlap < size.

TestsThe 5 checks Run tests uses
t = list(range(10))
assert windows(t, 4, 1) == [[0, 1, 2, 3], [3, 4, 5, 6], [6, 7, 8, 9]]
assert windows(t, 4, 2) == [[0, 1, 2, 3], [2, 3, 4, 5], [4, 5, 6, 7], [6, 7, 8, 9]]
assert windows(t, 6, 0) == [[0, 1, 2, 3, 4, 5], [4, 5, 6, 7, 8, 9]]
assert windows(t[:3], 5, 1) == [[0, 1, 2]]
assert windows([], 5, 1) == []
for bad in [(4, 4), (4, -1)]:
    try:
        windows(t, *bad)
        assert False, bad
    except ValueError:
        pass
Hint 1Open a hint

The starts of the regular windows are range(0, len(tokens) - size + 1, size - overlap).

Hint 2Open a hint

After building them, compare the last window's end (start + size) with len(tokens) and append tokens[-size:] if it falls short.

SolutionShow the solution and why
solution.py
def windows(tokens, size, overlap):
    if not 0 <= overlap < size:
        raise ValueError("need 0 <= overlap < size")
    if len(tokens) <= size:
        return [list(tokens)] if tokens else []
    step = size - overlap
    starts = range(0, len(tokens) - size + 1, step)
    out = [tokens[s:s + size] for s in starts]
    if starts[-1] + size < len(tokens):
        out.append(tokens[-size:])
    return out

The window starts form an arithmetic sequence, so a range with step size - overlap generates them, and its stop value len - size + 1 makes the last regular window end exactly at or before the end. A range supports indexing, so starts[-1] gives the last start without building a list. When the step does not divide evenly (the third test), the final window is aligned to the end, which overlaps the previous one more than requested but never drops tokens and never produces a short chunk. overlap >= size would make the step 0 or negative, so it is rejected first. Libraries such as LangChain's TokenTextSplitter use this scheme with chunk_size and chunk_overlap.

solution.py
from collections import Counter


def doc_term_matrix(docs, min_count=1):
    tokens = [w.strip(".,!?") for doc in docs for w in doc.lower().split()]
    counts = Counter(tokens)
    vocab = sorted(w for w in counts if counts[w] >= min_count)
    index = {}
    for i, w in enumerate(vocab):
        index[w] = i
    matrix = [[0] * len(vocab) for _ in docs]
    for d, doc in enumerate(docs):
        for w in doc.lower().split():
            w = w.strip(".,!?")
            if w in index:
                matrix[d][index[w]] += 1
    return vocab, matrix

Bug one: for w in doc.lower().split() for doc in docs puts the inner loop first. The first for is evaluated in the function's scope, where doc is a local assigned only later by the enumerate loop, so it raises UnboundLocalError. The for clauses must be in the order of written nested loops. Bug two: the matrix rows were one shared list, so every document's counts were added into the same row and every row showed the total. A comprehension creates one row per document. The side-effect comprehension was not a bug, but it is a code smell: it builds a list of None only to discard it; Counter(tokens) says what it means. The tokenising rule is written twice (once for the vocabulary, once for the rows), which is the next thing to refactor into one function. scikit-learn's CountVectorizer produces the same matrix, stored sparsely.

Interview

17. When would you use a list comprehension, a generator expression, map/filter, or a plain loop?

SolutionModel answer

A list comprehension when you need the whole list (to index it, iterate it more than once, or return it) and the logic is one expression with at most a simple filter. A generator expression when you consume the values once, especially inside sum, any, all, max, "".join or a for loop, and for large or unbounded data, since it produces items lazily without storing them, and any/all can stop early. map/filter when you already have a named function, especially a built-in (map(str.strip, lines)); with a lambda, a comprehension is clearer. A plain loop when the body has several statements, error handling, early exit, or side effects, or when a comprehension would need more than two for clauses. Readability decides when performance is similar, which is most of the time.

Interview

18. Are list comprehensions faster than a loop with append? Why, and does it matter?

SolutionModel answer

Historically yes, noticeably: the loop looks up the append attribute and makes a method call on every iteration, while the comprehension compiles to a dedicated LIST_APPEND bytecode. On modern CPython the gap is small: since 3.11 the specialising interpreter turns list.append calls into a fast path, and since 3.12 comprehensions are inlined into the enclosing function (PEP 709). A good answer says that, and adds that you would measure with timeit on the version you deploy. The saving is per item and fixed, so it disappears when each item does real work (parsing JSON, running a regex, calling a model). Choose comprehensions for clarity; for real speed-ups, do less work (early exit with a generator and any), pick a better data structure, or vectorise numeric work with NumPy or pandas.

Interview

19. A teammate loads a 50 GB JSON Lines file with docs = [json.loads(line) for line in open(path)]. What is wrong, and how would you fix it?

SolutionModel answer

It materialises every parsed document in memory at once; Python objects are several times larger than the raw text, so this needs far more than 50 GB of RAM and will crash or swap. The file is also opened without with and without an explicit encoding (5.4). The fix is to stream: open the file in a with block with encoding="utf-8", and process it with a generator expression or a generator function that yields one parsed document at a time, so memory stays constant (6.3). If work must be batched (for example embedding 256 documents per request), group the stream into batches lazily (itertools.batched, 6.4) and write results out as you go. For analytics on such files, tools like Polars or DuckDB scan JSON Lines lazily and in parallel. Also handle bad lines: wrap json.loads in try and count or log failures instead of losing the whole run to one corrupt line.

Recap

  • [expr for x in xs if cond] is a loop that appends expr for every x that passes cond. Read it for, then if, then the expression.
  • An if at the end filters (shorter list); a if c else b at the front transforms every item (same length).
  • Several for clauses nest left to right like written loops; a comprehension in the expression builds a list of lists. Never [[0] * n] * m.
  • Loop variables do not leak, the walrus does on purpose, and lambdas created in a comprehension see the last value unless bound with a default.
  • Comprehensions are fast but build the whole list. For one pass, any/all or large data, use a generator expression; for multi-step bodies and side effects, a loop.
