5.4 Unicode, bytes and encodings

Text inside Python is Unicode; text in files, networks and databases is bytes. How UTF-8 turns code points into bytes, encode and decode with their error modes, mojibake and how to recognise it, reading files safely on Windows, the BOM, and normalisation for matching text.

19 problems4 easy · 10 medium · 5 hard

1Text inside, bytes outside

Inside your program, text is str: a sequence of Unicode code points (5.1). Outside your program, in files, network messages, HTTP bodies and database drivers, everything is bytes: numbers from 0 to 255. An encoding is the rule that converts between the two. s.encode(encoding) turns a str into bytes; b.decode(encoding) turns bytes back into a str. The golden rule follows: decode as early as possible when data comes in, work with str, encode as late as possible when it goes out, and always say which encoding.

str_vs_bytes.py
s = "café €5"
b = s.encode("utf-8")
print(type(b).__name__, b, len(s), len(b))
print(list(b[3:5]), b[0], chr(b[0]))          # indexing bytes gives integers
print(b.decode("utf-8") == s)
try:
    "x" + b
except TypeError as e:
    print("TypeError:", e)
Output
bytes b'caf\xc3\xa9 \xe2\x82\xac5' 7 10
[195, 169] 99 c
True
TypeError: can only concatenate str (not "bytes") to str

bytes look like strings when printed (b'caf\xc3\xa9'), but they are a different type: indexing gives an integer, you cannot mix them with str in +, in or == (a str never equals a bytes), and their methods (split, startswith) take bytes arguments. bytearray is the mutable version. Python 3 refuses to mix the two silently, which turns encoding confusion into an immediate TypeError instead of corrupted data.

2How UTF-8 works

UTF-8 is the encoding to use unless something forces you otherwise: it is the default for the web, JSON, Python source files, Linux and macOS, and most databases. It stores each code point in 1 to 4 bytes:

Code pointsBytesExamples
U+0000 to U+007F (ASCII)1A, 7, {
U+0080 to U+07FF2é, ß, Greek, Cyrillic, Arabic, Hebrew
U+0800 to U+FFFF3€, most Chinese, Japanese and Korean characters
U+10000 and above4emoji, rare scripts

Two properties make it so popular. ASCII text is unchanged: an ASCII file is already valid UTF-8, byte for byte. And it is self-synchronising: the first byte of a character says how many bytes follow, and continuation bytes always start with the bits 10, so a decoder can tell where characters begin. That is also why cutting UTF-8 bytes at an arbitrary position can split a character in half, producing invalid data (problem 13).

for ch in ["A", "é", "€", "\U0001F600"]:
    b = ch.encode("utf-8")
    print(ch, f"U+{ord(ch):04X}", len(b), " ".join(f"{x:08b}" for x in b))
print(len("naïve résumé".encode("utf-8")), len("naïve résumé"))

Other encodings you will meet: UTF-16 (2 or 4 bytes per code point, used inside Windows and Java, and by Excel's "Unicode text" export), Latin-1 (ISO-8859-1, one byte per character, only the first 256 code points) and cp1252 (Windows-1252, Latin-1 plus € and typographic quotes, the old Windows default for Western European text). The last two can decode any byte sequence without error, which makes them dangerous fallbacks: they never fail, they just produce the wrong characters.

3Decoding errors and error modes

Decoding bytes that are not valid in the chosen encoding raises UnicodeDecodeError, which reports the encoding, the offending byte and its position. Encoding a character the target encoding cannot represent raises UnicodeEncodeError. The errors= argument chooses what to do instead of raising:

error_modes.py
data = "café".encode("utf-8") + b"\xff"            # valid UTF-8 followed by one bad byte
try:
    data.decode("utf-8")
except UnicodeDecodeError as e:
    print("UnicodeDecodeError:", e)
print(data.decode("utf-8", errors="replace"))        # U+FFFD replacement character
print(data.decode("utf-8", errors="ignore"))         # silently drop the bad byte
print(repr(data.decode("utf-8", errors="backslashreplace")))
try:
    "€5".encode("latin-1")
except UnicodeEncodeError as e:
    print("UnicodeEncodeError:", e)
print("€5".encode("ascii", errors="xmlcharrefreplace"))
Output
UnicodeDecodeError: 'utf-8' codec can't decode byte 0xff in position 5: invalid start byte
café�
café
'café\\xff'
UnicodeEncodeError: 'latin-1' codec can't encode character '\u20ac' in position 0: ordinal not in range(256)
b'&#8364;5'

Choose deliberately. strict (the default) is right for data you produce or that must be correct: failing loudly is better than corrupting it. replace is good for display and logs: the � shows where something was wrong. ignore loses data without a trace, so avoid it except for throwaway analysis. backslashreplace keeps the bad bytes visible and recoverable, which suits logs of untrusted input. Whatever you choose, count how many replacements happened in a data pipeline (problem 9), because "a few bad characters" can mean the whole file was decoded with the wrong encoding.

4Mojibake: decoding with the wrong encoding

The most common encoding bug is not an error at all. Bytes written as UTF-8 and read back as cp1252 (or Latin-1) decode without complaint, because those encodings accept any byte, and every non-ASCII character turns into two or three wrong ones: é becomes Ã©, € becomes â‚¬, a typographic apostrophe ’ becomes â€™ (a plain ' is ASCII and survives). This is called mojibake, and its tell-tale sign is Ã or â€ appearing in text that should contain accents or typographic punctuation.

mojibake.py
original = "Café – it's 5€"
garbled = original.encode("utf-8").decode("cp1252")
print(garbled)
repaired = garbled.encode("cp1252").decode("utf-8")
print(repaired, repaired == original)
Output
CafÃ© â€“ it's 5â‚¬
Café – it's 5€ True

When the damage is exactly one wrong decode, reversing it (encode with the wrong encoding, decode with the right one) restores the text, as above. When text was garbled twice, or saved after garbling with information lost, repair is guesswork; the ftfy library automates the common cases. The real fix is upstream: find the step that decoded with the wrong encoding, which is usually a file opened without encoding= (next section) or a database connection with the wrong character set.

5Reading and writing files safely

open(path) in text mode decodes bytes into str for you, using an encoding. If you do not pass encoding=, Python uses the locale's encoding, which is UTF-8 on Linux and macOS but traditionally cp1252 on Windows (Python 3.15 makes UTF-8 the default everywhere). Code that works on a Mac and garbles text on a Windows VDI almost always has this bug. So: always pass encoding="utf-8" (or the file's real encoding) to open, pathlib.Path.read_text and write_text, and to pandas.read_csv when the file is not UTF-8.

files.py
import os, tempfile

path = os.path.join(tempfile.mkdtemp(), "notes.txt")
with open(path, "w", encoding="utf-8") as f:
    f.write("Résumé – naïve café\n")
with open(path, "rb") as f:
    raw = f.read()
print(raw[:12], len(raw))
with open(path, encoding="utf-8") as f:
    print(f.read().strip())
with open(path, encoding="cp1252") as f:
    print(f.read().strip())                    # wrong encoding: mojibake, no error

Two more Windows realities. Some tools (Excel's "CSV UTF-8", Notepad in older versions) write a BOM, the three bytes EF BB BF, at the start of a UTF-8 file. Decoded as plain utf-8, it becomes the invisible character \ufeff glued to the first value, so the first column header is "\ufeffid" and row["id"] fails. Reading with encoding="utf-8-sig" strips it (and works for files without a BOM too). And files exported as "Unicode" from Excel are usually UTF-16, which utf-8 cannot decode at all.

6Normalization: making equal text compare equal

The same visible text can be written with different code points. é can be one precomposed code point (U+00E9) or e plus a combining accent (U+0301), and macOS file names and some keyboards produce the decomposed form. Compatibility characters add more variants: the ligature ﬁ, full-width ＡＢＣ, superscript ², the non-breaking space. Unicode defines four normal forms to make such text comparable:

  • NFC: compose where possible (e + accent becomes é). The standard form for storage and comparison.
  • NFD: decompose (é becomes e + accent). Useful for removing accents: decompose, then drop the combining marks.
  • NFKC / NFKD: also replace compatibility characters with their plain equivalents (ﬁ to fi, ² to 2, full-width to normal width). Good for search and matching, but it changes meaning in some cases, so do not use it for storage.
normalize.py
import unicodedata as ud

a, b = "café", "cafe\u0301"
print(a == b, ud.normalize("NFC", a) == ud.normalize("NFC", b), len(ud.normalize("NFD", a)))
for s in ["ﬁle", "ＡＢＣ", "x²", "\u00a0"]:
    print(repr(s), repr(ud.normalize("NFKC", s)))
print(ud.name("é"), "|", ud.name("\u0301"), "|", ud.category("\u0301"))

def utf8_len(text):
    return len(text.encode("utf-8"))

def fits(text, max_bytes):
    return utf8_len(text) <= max_bytes

solution.py
def parse_csv(data):
    text = data.decode("utf-8-sig")
    lines = text.splitlines()
    header = lines[0].split(",")
    return [dict(zip(header, line.split(","))) for line in lines[1:]]

Excel's "CSV UTF-8" format starts the file with a BOM. Plain utf-8 decodes it as the character \ufeff, which is invisible when printed, so the first key is really "\ufeffid". utf-8-sig removes a leading BOM if present and otherwise behaves exactly like utf-8, so it is the safe choice for reading files that may come from Windows tools. With pandas, read_csv(..., encoding="utf-8-sig") does the same.

def fix_mojibake(text):

SolutionShow the solution and why
solution.py
def decode_batch(rows):
    texts, bad = [], []
    for i, raw in enumerate(rows):
        text = raw.decode("utf-8", errors="replace")
        if "\ufffd" in text and b"\xef\xbf\xbd" not in raw:
            bad.append(i)
        texts.append(text)
    return texts, bad

errors="replace" keeps the pipeline running, but silently. Recording which rows were damaged turns a hidden data quality problem into a number you can alert on: one bad row is noise, half the rows means the source encoding is wrong (here b"caf\xe9" is Latin-1 café). The check excludes rows whose bytes already contained a genuine replacement character. Logging the indices (not the content) also avoids leaking customer data into logs.

SolutionShow the solution and why
solution.py
import unicodedata

def fold(text):
    decomposed = unicodedata.normalize("NFD", text)
    return "".join(ch for ch in decomposed if not unicodedata.combining(ch)).casefold()

def matches(query, title):
    return fold(query) in fold(title)

NFD splits é into e plus a combining accent, whatever form it was typed in, and dropping the combining marks leaves the base letters, so precomposed, decomposed and unaccented spellings all become cafe. Folding both sides with one function is the important design point (5.2). Accent folding is right for search and matching, but keep the original for display, and note it merges words that differ only by accent in some languages. Search engines do this with "ASCII folding" analysers.

solution.py
ENCODING = "utf-8"

def to_bytes(text, errors="strict"):
    return text.encode(ENCODING, errors)

def to_text(data, errors="strict"):
    return data.decode(ENCODING, errors)

def send(payload):
    return to_bytes(payload)

def receive(data):
    return to_text(data)

def receive_log(data):
    return to_text(data, errors="backslashreplace")

Encoding decisions belong at the boundaries, and they should be made once: if the protocol ever changes encoding, one constant changes. The default strict keeps correctness the norm, and the one place that tolerates bad input (logging) says so explicitly. The same idea is behind setting encoding once on a database connection or an HTTP client, rather than decoding by hand at every call site.

    return text.encode("utf-8")[:max_bytes].decode("utf-8", errors="ignore")

Cutting the bytes can leave the first one or two bytes of a multi-byte character at the end, which is invalid UTF-8. Because the input was valid UTF-8, the only damage is that incomplete tail, so decoding with ignore drops exactly those bytes and nothing else: a rare case where ignore is the right tool. Slicing the str by characters would not work, since the limit is in bytes ("€€€" is 3 characters but 9 bytes). This is how you safely fit text into byte-limited fields such as HTTP headers, database index keys or some LLM metadata fields.

def load_text(data):
    if data.startswith((b"\xff\xfe", b"\xfe\xff")):

The original's order was backwards: Latin-1 accepts every byte sequence, so it always "succeeded" first and the better candidates were never tried. The rule for guessing is strictest first: a BOM is near-certain evidence, UTF-8 rarely decodes non-UTF-8 text by accident (random high bytes almost never form valid sequences), and a permissive single-byte encoding is only a fallback. cp1252 is a better fallback than Latin-1 for Western data because it maps € and smart quotes correctly, and errors="replace" covers its five undefined bytes. Returning the encoding used lets callers log it. For harder cases, the charset-normalizer library makes statistical guesses; the best solution is still to agree on UTF-8 with whoever produces the files.

SolutionShow the solution and why
solution.py
import unicodedata

def clean_invisible(text):
    out = []
    for ch in text:
        cat = unicodedata.category(ch)
        if ch in "\n\t":
            out.append(ch)
        elif cat in ("Cf", "Cc"):
            continue
        elif cat == "Zs":
            out.append(" ")
        else:
            out.append(ch)
    return "".join(out)

Unicode categories describe what a character is, so the rule covers every zero-width character, BOM, soft hyphen and control code without listing them one by one: U+200B (zero-width space), U+FEFF (BOM) and U+00AD (soft hyphen) are Cf, the bell character is Cc, and both the non-breaking space and the thin space are Zs. Newlines and tabs are kept explicitly because they carry structure. Invisible characters are a real RAG problem: "Re\u200bfund" never matches "Refund" in keyword search, inflates token counts, and can even be used to hide instructions from human reviewers in prompt injection attacks.

10Interview questions

Interview

17. What is the difference between str and bytes in Python 3, and where does each belong?

SolutionModel answer

str is a sequence of Unicode code points: text. bytes is an immutable sequence of integers 0 to 255: raw data. An encoding (usually UTF-8) converts between them with encode and decode. Text belongs in str everywhere inside the program; bytes belongs at the boundaries: files opened in binary mode, sockets, HTTP bodies, hashing (hashlib needs bytes), compression, encryption and binary formats. The rule is "decode early, encode late, and name the encoding explicitly". Python 3 deliberately refuses to mix them ("a" + b"a" raises), which turns encoding mistakes into errors instead of silent corruption, unlike Python 2.

18. A colleague says "it works on my Mac but the text is garbled on the Windows server". What do you check?

SolutionModel answer

Almost certainly an implicit encoding: open(), read_text(), subprocess output or a CSV reader without encoding=, which uses the platform default (UTF-8 on macOS and Linux, often cp1252 on Windows), so UTF-8 files are decoded as cp1252 and accents turn into Ã©. Check every boundary: file reads and writes, pd.read_csv, database connection character sets, HTTP response decoding, and console output (a cp1252 console can raise UnicodeEncodeError on print). Fix by passing encoding="utf-8" explicitly (and utf-8-sig for files from Excel), or enable UTF-8 mode with PYTHONUTF8=1, which Python 3.15 makes the default. Also look for a BOM breaking the first column name.

Interview

19. How would you handle text of unknown or mixed encoding in a data pipeline?

SolutionModel answer

First try to remove the unknown: ask the source, read metadata (HTTP Content-Type charset, XML declarations, database collations). If you must guess, go strictest first: a BOM identifies UTF-8 or UTF-16; then try strict UTF-8, which rarely decodes non-UTF-8 data by accident; only then fall back to a single-byte encoding such as cp1252, which never fails and therefore must be last; libraries like charset-normalizer add statistical detection. Record the encoding used per file and count replacement characters, so silent fallbacks show up in monitoring. After decoding, normalise (NFC), remove invisible characters and fix mojibake (ftfy) as a cleaning step that keeps the original bytes available. And store everything as UTF-8 from then on, so the problem happens once, at ingestion.

Recap

  • Inside Python text is str (code points); at every boundary it is bytes. Decode early, encode late, and always name the encoding.
  • UTF-8 uses 1 to 4 bytes per code point and leaves ASCII unchanged. Byte length is not len, and cutting bytes can split a character.
  • strict errors are the default for a reason. replace for display, backslashreplace for logs; count replacements in pipelines.
  • Mojibake (Ã©, â€™) means bytes were decoded with the wrong encoding, usually a missing encoding= on Windows. Latin-1 and cp1252 never fail, so they hide the bug.
  • Read Excel CSVs with utf-8-sig. Normalise with NFC for storage, NFKC (and accent folding) for search keys.
