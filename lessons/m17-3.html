D.3 pandas: groupby, merge and reshape

Most feature engineering and most evaluation reports are a group-by, a join or a reshape. Split-apply-combine with named aggregations, transform for per-row group features, joins and the row explosions they cause, anti-joins, and moving between long and wide tables with pivot_table and melt.

1Split, apply, combine

df.groupby(key) splits the rows into groups that share a key, you apply a function to each group, and pandas combines the results into a new table with one row per group. It is SQL's GROUP BY and Power BI's summarise-by-a-column, with Python functions available inside. The clearest form is named aggregation: agg(new_name=("column", "function")), which says exactly which output column comes from which input and which function, and gives the result flat, readable column names.

groupby.py
import pandas as pd

complaints = pd.DataFrame({
    "id": [1, 2, 3, 4, 5, 6, 7],
    "customer": ["ana", "ben", "ana", "cy", "ben", "ana", "dee"],
    "product": ["card", "loan", "card", "mortgage", "card", "loan", None],
    "amount": [20.0, 300.0, 35.0, 1200.0, 15.0, 250.0, 60.0],
    "timely": [True, False, True, True, False, True, True],
})
per_customer = complaints.groupby("customer").agg(
    complaints=("id", "size"),

    avg=("amount", "mean"),

)
print(per_customer.round(2))

print(complaints.groupby("product", dropna=False)["id"].count().to_dict())
print(complaints.groupby(["customer", "product"]).size().head(3).to_dict())
print(complaints.groupby("customer", as_index=False)["amount"].max().head(2))

Four details. size counts rows in each group and count counts non-missing values in a column, the same difference as SQL's COUNT(*) and COUNT(col). The mean of a boolean column is the fraction of True, the quickest way to get a rate. Rows whose key is missing are dropped from the groups by default (complaint 7 has no product), like a join on NULL; pass dropna=False to keep them as their own group. And the group keys become the index of the result; as_index=False (or .reset_index()) keeps them as ordinary columns, which is what you want before a merge or a plot.

2transform and filter: group facts on every row

agg shrinks each group to one row. transform returns a result the same length as the input, aligned to the original rows: each row gets its group's value. That is how you build features such as "this complaint's amount compared with the customer's average" or "the share of the customer's total", the pandas version of a SQL window function (AVG(amount) OVER (PARTITION BY customer)) or a Power BI calculated column using ALLEXCEPT. rank, cumsum, cumcount and shift on a group-by work the same way, row by row within each group. filter keeps or drops whole groups by a condition on the group, like HAVING.

transform.py
import pandas as pd

complaints = pd.DataFrame({
    "id": [1, 2, 3, 4, 5, 6, 7],
    "customer": ["ana", "ben", "ana", "cy", "ben", "ana", "dee"],
    "product": ["card", "loan", "card", "mortgage", "card", "loan", None],
    "amount": [20.0, 300.0, 35.0, 1200.0, 15.0, 250.0, 60.0],
    "timely": [True, False, True, True, False, True, True],
})
g = complaints.groupby("customer")["amount"]
complaints["cust_avg"] = g.transform("mean")
complaints["share"] = (complaints["amount"] / g.transform("sum")).round(2)
complaints["nth"] = complaints.groupby("customer").cumcount() + 1
complaints["rank"] = g.rank(ascending=False).astype(int)
print(complaints[["id", "customer", "amount", "cust_avg", "share", "nth", "rank"]])
repeat = complaints.groupby("customer").filter(lambda grp: len(grp) >= 2)
print(sorted(repeat["customer"].unique().tolist()))

3Joins and how they go wrong

pd.merge(left, right, on="key", how=...) is SQL's join: "inner" keeps keys in both tables, "left" keeps every left row and fills missing right columns with NaN, "right" the reverse, "outer" keeps all. When both tables have a non-key column with the same name, the result gets _x and _y suffixes (choose better ones with suffixes=). As in SQL, if a key appears several times on both sides, every pair is produced: three rows times two rows gives six. When you expected one match per row, that silently duplicates data, inflates sums and leaks rows between train and test splits.

Two arguments make joins safe. validate="many_to_one" (or "one_to_one", "one_to_many") checks your assumption about the keys and raises MergeError if it is wrong, so a duplicated row in a lookup table fails loudly instead of doubling a revenue figure. indicator=True adds a _merge column saying left_only, right_only or both for every row, the quickest way to see what did not match. pandas 3 also supports anti-joins directly: how="left_anti" keeps the left rows with no match, the "complaints whose customer is not in the CRM" question.

4Long and wide: pivot_table, melt and concat

The same data can be long (one row per observation: model, metric, value) or wide (one row per model, one column per metric). Long is what groupby, plotting libraries and databases prefer; wide is what people read and what most models need as features. pivot_table(index, columns, values, aggfunc) goes from long to wide, aggregating duplicates (it is Excel's pivot table and Power BI's matrix visual); pivot does the same but raises if a cell would get two values. melt(id_vars, value_vars) goes back from wide to long, Power Query's "unpivot columns". pd.concat([a, b]) stacks frames with the same columns, like UNION ALL, and ignore_index=True renumbers the rows.

reshape.py
import pandas as pd

runs = pd.DataFrame({
    "model": ["small", "small", "large", "large", "small", "large"],
    "metric": ["accuracy", "latency_ms", "accuracy", "latency_ms", "accuracy", "accuracy"],
    "value": [0.81, 120, 0.88, 410, 0.83, 0.90],
})
wide = runs.pivot_table(index="model", columns="metric", values="value", aggfunc="mean")
print(wide)
print(wide.columns.name, wide.reset_index().columns.tolist())
long = wide.reset_index().melt(id_vars="model", var_name="metric", value_name="value")
print(long.sort_values(["model", "metric"]).to_dict("records")[:2])
print(pd.crosstab(runs["model"], runs["metric"]))
both = pd.concat([runs.head(2), runs.tail(1)], ignore_index=True)

solution.py
import pandas as pd


def customer_features(df):
    out = (
        df.assign(late=~df["timely"])
          .groupby("customer", as_index=False)
          .agg(n_complaints=("customer", "size"), total_amount=("amount", "sum"), max_amount=("amount", "max"),
               late_rate=("late", "mean"), n_products=("product", "nunique"))
    )
    out["late_rate"] = out["late_rate"].round(2)
    return out.sort_values("customer").reset_index(drop=True)

sum over every column adds booleans as counts and concatenates strings, which is meaningless as features. Named aggregations state each feature's source and function. size counts complaints, including the one with no amount, while sum and max skip the missing amount. The mean of a boolean is a rate, so building late as the negation of timely and averaging it gives the late rate. nunique ignores missing products. This is the usual shape of feature engineering for a per-entity model: many event rows aggregated into one row per entity, joined later to the label table.

6. Standardise amounts within each product

A refund of 300 is large for a credit card and small for a mortgage. Write add_group_z(df, value, by) returning a copy of df with a new column f"{value}_z": the z-score of each row's value within its group, (x - group mean) / group std (pandas' default std, ddof=1), rounded to 3. solution.py
import pandas as pd


def add_group_z(df, value, by):
    out = df.copy()
    g = out.groupby(by)[value]
    std = g.transform("std")
    z = (out[value] - g.transform("mean")) / std.where(std > 0)
    out[f"{value}_z"] = z.fillna(0.0).round(3)
    return out

The starter standardised against the whole column, so every mortgage looks extreme and every card looks tiny: the feature mostly encodes the product, which the model already has. transform("mean") and transform("std") give each row its own group's statistics, aligned to the original rows, so the arithmetic is ordinary column math. A single-row group has an undefined sample std (NaN), and a constant group has std 0; where(std > 0) turns both into NaN for the division, and fillna(0.0) reports "average for its group". Group statistics computed on the full dataset leak information like the imputer in D.2, so in a real pipeline they are learned on the training split.

SolutionShow the solution and why
solution.py
import pandas as pd


def new_since(current, previous):
    return current.merge(previous[["id"]], on="id", how="left_anti")


def changed(current, previous, cols):
    both = current.merge(previous, on="id", suffixes=("", "_old"))
    diff = pd.Series(False, index=both.index)
    for c in cols:
        a, b = both[c], both[f"{c}_old"]
        same = a.eq(b) | (a.isna() & b.isna())
        diff |= ~same
    return sorted(both.loc[diff, "id"].tolist())

Comparing current["id"] != previous["id"] aligns the two Series by index, not by value, so it compares row 0 with row 0 and fails when lengths differ. The anti-join asks the real question: which current ids have no partner in the previous export. Only id is taken from previous, so no other columns come along. For changes, an inner join puts the old and new values side by side, and a plain != would report the unchanged missing amount of complaint 2 as a change, because NaN never equals NaN; the explicit "both missing" check fixes that. Looping over a few column names is fine; each comparison is vectorised. This is the core of incremental loads and change data capture.

import pandas as pd


def eval_report(results):
    rep = results.groupby("prompt_version", as_index=False).agg(
        cases=("case_id", "size"),
        pass_rate=("passed", "mean"),
        p50_ms=("latency_ms", "median"),
        p95_ms=("latency_ms", lambda s: s.quantile(0.95)),
        tokens=("tokens", "sum"),
        passes=("passed", "sum"),
    )
    rep["tokens_per_pass"] = (rep["tokens"] / rep["passes"].where(rep["passes"] > 0)).round(1)
    rep[["pass_rate"]] = rep[["pass_rate"]].round(3)
    rep[["p50_ms", "p95_ms"]] = rep[["p50_ms", "p95_ms"]].round(1)
    return rep.drop(columns=["tokens", "passes"]).sort_values("prompt_version").reset_index(drop=True)

An average latency hides the slow tail that users feel, so evaluation reports give percentiles: quantile(0.95) interpolates between the sorted values (385 lies three quarters of the way from 300 to 400). The mean of passed is the pass rate. Tokens per passing case is a cost-of-quality metric: a prompt that passes more cases with fewer tokens wins on both axes, and a version with no passes has no meaningful value, so the division is masked rather than allowed to produce infinity. Helper aggregates such as tokens and passes are computed in the same pass and dropped at the end.

11. Target encoding without leakage

Target encoding replaces a category (such as company) with the average label of training rows in that category. Write TargetEncoder(smoothing=10) with fit(X, y, col) and transform(X). The learned value for a category with n training rows and label mean m is the smoothed mean (n * m + smoothing * prior) / (n + smoothing), where prior is the overall training label mean, so rare categories are pulled towards the prior. transform returns a new Series named f"{col}_te" aligned to X's index, rounded to 4, using the prior for unseen or missing categories. solution.py
import pandas as pd


class TargetEncoder:
    def __init__(self, smoothing=10):
        self.smoothing = smoothing

    def fit(self, X, y, col):
        self.col = col
        self.prior_ = float(y.mean())
        stats = y.groupby(X[col]).agg(["count", "mean"])
        n, m = stats["count"], stats["mean"]
        self.table_ = (n * m + self.smoothing * self.prior_) / (n + self.smoothing)
        return self

    def transform(self, X):
        out = X[self.col].map(self.table_).astype(float).fillna(self.prior_).round(4)
        return out.rename(f"{self.col}_te")

A category's raw label mean is a powerful feature and a dangerous one. Computed on the rows being scored, it contains each row's own label, so the model sees the answer (leakage); computed for a category with one training row, it is either 0 or 1, pure noise that the model trusts completely. Learning the table in fit from training labels only fixes the first problem; smoothing fixes the second: with n rows, the estimate moves from the prior towards the category mean as evidence grows (b, with one row of label 0, gets 0.381 rather than 0.0). y.groupby(X[col]) groups the labels by the aligned category values. Unseen categories and missing values get the prior, the honest "no information" answer. In practice the training rows themselves are encoded out of fold (K-fold), so even the training features never include their own label; scikit-learn's TargetEncoder does that automatically.

solution.py
import pandas as pd


def win_rates(votes):
    score_a = votes["winner"].map({"a": 1.0, "tie": 0.5, "b": 0.0})
    side_a = pd.DataFrame({"model": votes["model_a"], "opponent": votes["model_b"], "score": score_a})
    side_b = pd.DataFrame({"model": votes["model_b"], "opponent": votes["model_a"], "score": 1.0 - score_a})
    long = pd.concat([side_a, side_b], ignore_index=True)
    models = sorted(set(long["model"]))
    table = long.pivot_table(index="model", columns="opponent", values="score", aggfunc="mean")
    table = table.reindex(index=models, columns=models)
    return table.round(3).rename_axis(index=None, columns=None)

The raw votes are in a "match" format where each model can appear on either side, which a crosstab treats as different things. Turning every vote into two rows, one from each model's point of view (model, opponent, score), gives a long table where a model's results are in one column no matter which side it was on, and the scores of each pair add up to 1. A mean per (model, opponent) is the win rate, and pivot_table spreads it into a matrix. reindex with the full sorted list adds rows and columns for pairs that never met, as NaN. m1 against m2: a win for m1, a tie, and a win for m2 averages to 0.5. The last test checks the symmetry that any correct table must have. Leaderboards such as Chatbot Arena start from exactly this table before fitting Elo or Bradley-Terry ratings.

14. What is the difference between agg, transform and apply on a group-by?

SolutionModel answer

All three run per group, but they return different shapes. agg (with names such as "sum" or named aggregations) reduces each group to one row: a summary table, SQL's GROUP BY. transform returns a result with the same index as the input, broadcasting each group's value back to its rows (or returning a same-length result such as a rank or cumulative sum): SQL's window functions with PARTITION BY, used to add feature columns such as "amount relative to the customer mean" without a merge. apply is the general escape hatch: it passes each group as a DataFrame to any Python function and stitches whatever comes back together, so it is flexible but slower (Python per group) and its output shape depends on the function. Prefer built-in aggregation names (they run in optimised code), use transform for row-level features, filter to keep or drop whole groups, and apply only when nothing else fits. And remember the defaults: missing keys are dropped (dropna=True), keys become the index (as_index=True), and keys are sorted.

15. A join produced more rows than you expected. What happened, and how do you prevent it?

SolutionModel answer

A join outputs one row for every matching pair of rows, so if a key is duplicated on the side you assumed was unique, each left row matches several right rows and the result grows: three orders for a customer with two CRM rows become six. It silently inflates sums and counts, can duplicate examples across train and test splits, and the row count often goes unnoticed. To find it: compare len(result) with len(left), check right[key].duplicated().any(), and use indicator=True to see matches. To prevent it: de-duplicate the lookup table with an explicit rule (keep the latest, or aggregate), and pass validate="many_to_one" (or "one_to_one") so pandas raises MergeError when the assumption breaks; for left joins assert that the row count is unchanged. Also check key types and formatting (an int key will not match a str one, and " ana" will not match "ana"), and remember missing keys: in pandas, unlike SQL, NaN keys match each other in a merge, which can create surprising pairs.

16. When would you keep data in long format, and when in wide format?

SolutionModel answer

Long format has one row per observation, with columns such as entity, variable, value (or date, metric, value). It is the natural shape for storing and computing: new metrics or dates are new rows, not schema changes, group-bys and filters are simple, and plotting libraries such as seaborn and plotly expect it. Databases and event logs are long. Wide format has one row per entity and one column per variable; it is easier for people to read and compare, it is what spreadsheets and reports show, and it is what most ML models require: a feature matrix with one row per example and one column per feature. Typical workflow: keep raw data long, compute aggregates with groupby, then pivot_table into wide features or report tables, and melt back when you need to plot or append. Watch for the reshaping traps: pivot raises on duplicate entries, pivot_table silently aggregates them, and missing combinations become NaN cells that need a decision.

Recap

  • groupby(...).agg(name=("col", "func")) is GROUP BY with clear names; size counts rows, count non-missing values; missing keys are dropped unless dropna=False.
  • transform returns one value per original row (window functions); filter keeps whole groups (HAVING); cumcount, rank and shift work within groups.
  • Joins multiply repeated keys; de-duplicate lookups, pass validate=, use indicator=True, and how="left_anti" for rows with no match.
  • pivot_table goes long to wide and aggregates duplicates; melt goes back; concat stacks frames like UNION ALL.
  • Group statistics used as features (z-scores, target encoding) must be learned on training data only, with smoothing for rare categories.
