8.4 Registration decorators

Decorators that record a function instead of wrapping it: registries, plugin systems, routers and agent tool lists. How frameworks such as FastAPI and agent libraries read a function's signature and type hints with inspect, turn them into schemas, and dispatch calls by name or by type with functools.singledispatch. Applied to building tool schemas for an LLM and a small URL router.

19 problems4 easy · 10 medium · 5 hard

1Decorators that register

Not every decorator wraps. A registration decorator records the function somewhere and returns it unchanged. There is no wrapper, no extra cost per call and nothing that can break the function; the only effect is that, from the moment the module is imported, the function is listed in a registry: usually a dict from a name to the function. Later code looks functions up in the registry instead of importing them by name, which is how plugin systems, command-line tools, routers and agent tool lists work.

registry.py
TOOLS = {}

def tool(func):
    if func.__name__ in TOOLS:
        raise ValueError(f"duplicate tool {func.__name__!r}")
    TOOLS[func.__name__] = func
    return func                        # unchanged: registration only

@tool
def search(query):
    return [f"doc about {query}"]

@tool
def get_weather(city):
    return f"sunny in {city}"

print(list(TOOLS))
print(TOOLS["search"]("refunds"), TOOLS["search"] is search)
Output
['search', 'get_weather']
['doc about refunds'] True

Registration happens at definition time (8.1): the registry is complete as soon as the module has been imported, before any function is called. That has two consequences. A function in a module that is never imported is never registered, which is why frameworks either import your modules for you (scanning a package) or ask you to import them in one place. And registration is a side effect of importing, so a registry should detect duplicates (two tools named search would otherwise overwrite each other silently) and tests should use a fresh registry rather than a global one.

Often the registered name differs from the function name, or the registration needs metadata (a description, a URL, an HTTP method). Then the registration decorator becomes a factory (8.2): @tool(name="web_search", description="..."). Frameworks put that factory on an object that owns the registry, which is what app is in @app.get("/users/{id}"): the method get is a decorator factory, and app holds the routing table it fills. (Module 9 shows how such objects are built; a closure over a dict does the same job, as below.)

registry_factory.py
def make_registry():
    entries = {}

    def register(name=None, **meta):
        def decorator(func):
            key = name or func.__name__
            if key in entries:
                raise ValueError(f"{key!r} is already registered")
            entries[key] = {"func": func, **meta}
            return func
        return decorator

    return entries, register

commands, command = make_registry()

@command(help="Rebuild the vector index")
def reindex():
    return "reindexed"

@command(name="eval", help="Run the evaluation suite")
def run_eval():
    return "evaluated"

for key, entry in commands.items():
    print(key, "-", entry["help"], "->", entry["func"]())
Output
reindex - Rebuild the vector index -> reindexed
eval - Run the evaluation suite -> evaluated

2Reading a function: inspect.signature

Once functions are registered, frameworks want to know how to call them. inspect.signature(func) returns a Signature object whose parameters maps each parameter name to a Parameter with a kind, a default and an annotation. The kind says how the parameter can be passed: POSITIONAL_OR_KEYWORD (an ordinary parameter), KEYWORD_ONLY (after *), VAR_POSITIONAL (*args), VAR_KEYWORD (**kwargs) and POSITIONAL_ONLY (before /). A missing default or annotation is inspect.Parameter.empty.

signature.py
import inspect

def search(query: str, k: int = 5, *, filters: dict | None = None, **extra) -> list:
    """Search the knowledge base."""
    return []

sig = inspect.signature(search)
for name, p in sig.parameters.items():
    if p.kind in (p.VAR_POSITIONAL, p.VAR_KEYWORD):
        default = "-"
    else:
        default = "required" if p.default is p.empty else repr(p.default)
    annotation = "-" if p.annotation is p.empty else p.annotation
    print(f"{name:8} {p.kind.name:22} {default:9} {annotation}")
print(sig.return_annotation, "|", inspect.getdoc(search))
Output
query    POSITIONAL_OR_KEYWORD  required  <class 'str'>
k        POSITIONAL_OR_KEYWORD  5         <class 'int'>
filters  KEYWORD_ONLY           None      dict | None
extra    VAR_KEYWORD            -         -
<class 'list'> | Search the knowledge base.

Three tools on top of this are worth knowing. sig.bind(*args, **kwargs) checks a call against the signature without calling the function and maps every value to its parameter (used in 7.3 and 8.2). inspect.getdoc(func) returns the docstring with indentation cleaned up. And typing.get_type_hints(func) returns the annotations as real types: when a module starts with from __future__ import annotations, or an annotation is written as a string, p.annotation is just the text "int", and get_type_hints evaluates it into the type int (problem 10).

type_hints.py
import inspect, typing

print(hints, hints["return"] == list[str])

Output

typing.get_origin and typing.get_args take generic types apart: list[str] has origin list and argument str, and int | None has the arguments int and NoneType. Module 11 explains these types in full; for reading signatures, these two functions are all you need.

3From a function to a tool schema

LLM tool calling (function calling) works by sending the model a schema for each tool: its name, a description, and a JSON Schema for its parameters. The model then replies with a tool name and JSON arguments, and your code calls the function. Writing those schemas by hand duplicates information the function already contains, so agent libraries generate them from the function: the name from __name__, the description from the docstring, the parameter types from the type hints, and the required list from the parameters without defaults. That is what @tool in LangChain, @function_tool in the OpenAI Agents SDK and similar decorators do.

tool_schema.py
import inspect, typing

JSON_TYPES = {str: "string", int: "integer", float: "number", bool: "boolean"}

def schema_for(func):
    hints = typing.get_type_hints(func)
    props, required = {}, []
    for name, p in inspect.signature(func).parameters.items():
        props[name] = {"type": JSON_TYPES[hints[name]]}
        if p.default is p.empty:
            required.append(name)
    doc = inspect.getdoc(func) or ""
    return {"name": func.__name__, "description": doc.split("\n")[0],
            "parameters": {"type": "object", "properties": props, "required": required}}

def get_order(order_id: int, include_items: bool = False) -> dict:
    """Look up an order by its id.

    Returns status and, optionally, the items.
    """
    return {}

import json
print(json.dumps(schema_for(get_order), indent=1))
Output

Two lessons follow from this. The docstring and type hints of a tool are part of the prompt: the model only knows what the schema says, so a vague first line or a missing type makes it call the tool wrongly. And the schema is generated at import time from the code, so it cannot drift away from the function, which is the main argument for generating rather than hand-writing it (problem 5). Real implementations also handle list[...], optional types, enums (Literal, 11.2) and descriptions per parameter, often by building a Pydantic model from the signature (11.4).

4Dispatching calls

A registry is useful because of dispatch: given a name (from a tool call, a URL, a command line), look up the function and call it with the arguments. Dispatch code is a boundary in the sense of 7.3: names and arguments come from outside (a user, a model), so unknown names and bad arguments are expected, and should produce clear errors, not tracebacks. A dict lookup also replaces long if/elif chains that compare a command against every known name in turn (problem 8).

dispatch.py
import inspect

TOOLS = {}

def tool(func):
    TOOLS[func.__name__] = func
    return func

@tool
def add(a: int, b: int) -> int:
    return a + b

def dispatch(name, args):
    func = TOOLS.get(name)
    if func is None:
        return {"error": f"unknown tool {name!r}; available: {sorted(TOOLS)}"}
    try:
        inspect.signature(func).bind(**args)
    except TypeError as e:
        return {"error": f"bad arguments for {name}: {e}"}
    return {"result": func(**args)}

print(dispatch("add", {"a": 2, "b": 3}))
print(dispatch("mul", {"a": 2}))
print(dispatch("add", {"a": 2, "c": 3}))
Output
{'result': 5}
{'error': "unknown tool 'mul'; available: ['add']"}
{'error': "bad arguments for add: missing a required argument: 'b'"}

The standard library has a different kind of dispatch built on registration: functools.singledispatch picks an implementation by the type of the first argument. You decorate a default function, then register specialised versions with @func.register; at call time it finds the most specific registered type in the argument's class hierarchy. It replaces chains of isinstance checks, and other modules can add support for their own types without editing the original function.

singledispatch.py
import functools

@functools.singledispatch
def to_text(value):
    return str(value)

@to_text.register
def _(value: float):
    return f"{value:.2f}"

@to_text.register
def _(value: list):
    return ", ".join(to_text(v) for v in value)

@to_text.register
def _(value: dict):
    return "; ".join(f"{k}={to_text(v)}" for k, v in value.items())

print(to_text({"score": 0.91234, "tags": ["eu", 3, 1.5], "ok": True}))
print(sorted(t.__name__ for t in to_text.registry))
Output
score=0.91; tags=eu, 3, 1.50; ok=True
['dict', 'float', 'list', 'object']

The registered type comes from the annotation of the first parameter (or from @to_text.register(float)). Dispatch follows inheritance: bool is a subclass of int (1.2), so with an int handler registered and no bool handler, True would use the int one (problem 12). The function called _ is a convention for "the name does not matter", because the implementations are reached through the registry, never by name.

5Registration pitfalls

Four problems come up with registries in real projects.

  • Nothing registered. The decorated functions live in a module that nobody imports, so the registry is empty. Import all plugin modules from one place (an __init__.py or a load_plugins() function, 15.1), or use package entry points.
  • Registering the wrong object. With stacked decorators, a registration decorator records whatever it receives. Placed below a wrapping decorator such as @timed, it registers the undecorated function, so calls through the registry skip the timing. Put registration outermost so it records the final, fully decorated function (problem 6).
  • Silent overwrites. Two functions registered under one name: the second replaces the first, and calls quietly go to the wrong place. Raise on duplicates, or log a warning, deliberately.
  • Registering at call time. If the registration line is inside the wrapper instead of the decorator body, nothing is registered until the first call, which is too late for a router or a tool list (problem 14).
register_order.py
import functools

REGISTRY = {}
CALLS = []

def register(func):
    REGISTRY[func.__name__] = func
    return func

def timed(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        CALLS.append(func.__name__)
        return func(*args, **kwargs)
    return wrapper

@timed
@register              # registers the plain function: the registry bypasses @timed
def wrong():
    return "w"

@register              # registers the timed wrapper
@timed
def right():
    return "r"

REGISTRY["wrong"](); REGISTRY["right"]()
print(CALLS, REGISTRY["right"] is right, REGISTRY["wrong"] is wrong)
Output
['right'] True False

For lists: typing.get_origin(t) is list, then typing.get_args(t)[0] is the item type.

SolutionShow the solution and why
solution.py
import inspect, typing

SIMPLE = {str: "string", int: "integer", float: "number", bool: "boolean"}


def _json_type(t, name):
    if t in SIMPLE:
        return {"type": SIMPLE[t]}
    if typing.get_origin(t) is list:
        (item,) = typing.get_args(t)
        return {"type": "array", "items": _json_type(item, name)}
    raise TypeError(f"parameter {name!r}: unsupported type {t!r}")


def tool_schema(func):
    hints = typing.get_type_hints(func)
    properties, required = {}, []
    for name, p in inspect.signature(func).parameters.items():
        if name not in hints:
            raise TypeError(f"parameter {name!r} of {func.__name__} has no type annotation")
        properties[name] = _json_type(hints[name], name)
        if p.default is p.empty:
            required.append(name)
    doc = inspect.getdoc(func) or ""
    return {
        "name": func.__name__,
        "description": doc.splitlines()[0] if doc else "",
        "parameters": {"type": "object", "properties": properties, "required": required},
    }

Everything the model needs is already in the function: the name, the purpose (first docstring line), the parameters and their types, and which ones are required. Generating the schema keeps it in sync with the code forever. Refusing unannotated or unsupported parameters is deliberate: a schema that silently omits a parameter or guesses its type makes the model call the tool wrongly, which shows up as confusing agent failures. The recursive _json_type handles nested lists for free. Note the check order matters for bool: dict lookup by type is exact, so bool maps to "boolean" rather than being treated as an int. Real libraries add per-parameter descriptions (parsed from the docstring or from Annotated metadata), enums and optional types.

6. The registry bypasses the timing

Agent tools are called through TOOLS, and every call must be counted by @counted. Calls through the registry are not counted. Fix it by changing only the decorator order.

TestsThe 2 checks Run tests uses
TOOLS["search"]("refund"); TOOLS["search"]("reset"); TOOLS["fetch"](7)
assert COUNTS == {"search": 2, "fetch": 1}
assert TOOLS["search"] is search and search.__name__ == "search"
HintOpen a hint

The bottom decorator runs first. Which object should the registry hold: the plain function or the counted wrapper?

SolutionShow the solution and why
solution.py
import functools

TOOLS = {}
COUNTS = {}

def tool(func):
    TOOLS[func.__name__] = func
    return func

def counted(func):
    @functools.wraps(func)
    def wrapper(*args, **kwargs):
        COUNTS[func.__name__] = COUNTS.get(func.__name__, 0) + 1
        return func(*args, **kwargs)
    return wrapper

@tool
@counted
def search(query):
    return [query]

@tool
@counted
def fetch(doc_id):
    return {"id": doc_id}

Decorators apply bottom-up, so with @tool at the bottom it received the plain function and registered that; @counted then wrapped it for the module-level name only. Calls through TOOLS went straight to the unwrapped function. With @tool on top, it registers the counted wrapper, so every route to the function goes through the counter, and the registry entry and the module name are the same object. wraps keeps __name__ as search, which is why the registry key is still right. The rule: registration goes outermost.

import functools

@functools.singledispatch

@render.register

13. A small URL router

A path matches when it has the same number of segments and every non-{...} segment is equal. Collect the {name} values, then convert with typing.get_type_hints(handler).get(name, str).

SolutionShow the solution and why
solution.py
import typing


def make_router():
    routes = []

    def route(method, template):
        segments = template.strip("/").split("/")

        def decorator(func):
            routes.append((method.upper(), segments, func))
            return func
        return decorator

    def _match(segments, parts):
        if len(segments) != len(parts):
            return None
        params = {}
        for seg, part in zip(segments, parts):
            if seg.startswith("{") and seg.endswith("}"):
                params[seg[1:-1]] = part
            elif seg != part:
                return None
        return params

    def dispatch(method, path):
        parts = path.strip("/").split("/")
        path_matched = False
        for route_method, segments, func in routes:
            params = _match(segments, parts)
            if params is None:
                continue
            path_matched = True
            if route_method != method.upper():
                continue
            hints = typing.get_type_hints(func)
            converted = {}
            for name, raw in params.items():
                kind = hints.get(name, str)
                try:
                    converted[name] = kind(raw) if kind in (int, float) else raw
                except ValueError:
                    return 422, f"invalid {name}"
            return 200, func(**converted)
        if path_matched:
            return 405, "method not allowed"
        return 404, "not found"

    return route, dispatch

This is the core of every web framework's router. Registration splits each template once, at import time, into segments. Dispatch compares segments: literals must be equal, placeholders capture the text. The handler's type hints decide conversion, which is exactly how FastAPI turns /docs/7 into doc_id=7 and answers /docs/abc with a 422 validation error instead of calling your function with bad data. Distinguishing 404 (no such path) from 405 (path exists, wrong method) is the HTTP convention, and it needs the "matched any path" flag. The handlers are returned unchanged, so they can still be called and tested directly. Real routers compile templates into regular expressions or a tree for speed and support typed converters in the template itself.

def make_plugins():
    registry = {}

    def loader(ext):
        def decorator(func):
            if ext in registry:
                raise ValueError(f"a loader for .{ext} is already registered: {registry[ext].__name__}")
            registry[ext] = func
            return func
        return decorator

import inspect, json, typing


def _type_error(name, value, expected):
    if isinstance(value, bool) and expected is not bool:
        return f"{name} must be {expected.__name__}, got bool"
    if expected is float and isinstance(value, (int, float)):
        return None
    if not isinstance(value, expected):
        return f"{name} must be {expected.__name__}, got {type(value).__name__}"
    return None


def call_tool(tools, name, arguments_json):
    func = tools.get(name)
    if func is None:
        return {"error": f"unknown tool {name!r}"}
    try:
        args = json.loads(arguments_json)
    except json.JSONDecodeError as e:
        return {"error": f"arguments are not valid JSON: {e.msg}"}
    if not isinstance(args, dict):
        return {"error": "arguments must be a JSON object"}
    params = inspect.signature(func).parameters
    hints = typing.get_type_hints(func)
    for key in args:
        if key not in params:
            return {"error": f"unknown argument: {key}"}
    for pname, p in params.items():
        if p.default is p.empty and pname not in args:
            return {"error": f"missing required argument: {pname}"}
    for key, value in args.items():
        expected = hints.get(key)
        if expected is not None:
            problem = _type_error(key, value, expected)
            if problem:
                return {"error": problem}
    return {"result": func(**args)}

Every check before the call targets a mistake the model can correct, and returns a short, specific message it can act on: "order_id must be int, got str" leads to a corrected call on the next turn, a traceback does not. Booleans need special care because bool is a subclass of int (1.2): without the explicit check, true would be accepted as an order id. Accepting an integer for a float parameter matches JSON, which has a single number type. The final call is deliberately outside any handler: the RuntimeError comes from the payment system, it is not the model's fault, and it must reach your error handling and alerting (7.3). This is the validation that frameworks generate from a Pydantic model of the parameters (11.4).

import functools

ORDER = []
REG = {}

def reg(name):
    def decorator(func):
        ORDER.append(f"reg {name}")
        REG[name] = func
        return func
    return decorator

def wrap(func):
    ORDER.append(f"wrap {func.__name__}")
    @functools.wraps(func)
    def wrapper(*args):
        return "wrapped " + func(*args)
    return wrapper

@reg("b")
@wrap
@reg("a")
def greet(x):
    return f"hi {x}"

print(ORDER)
print(REG["a"]("ana"), "|", REG["b"]("bo"), "|", greet("cy"))

The bottom decorator reg("a") sees the original function and registers it; wrap then creates the wrapper; reg("b") registers the wrapper, which is also what the name greet ends up bound to. 17. How does FastAPI know which function handles a route and what parameters it expects?

SolutionModel answer

Through a registration decorator plus introspection. @app.get("/items/{item_id}") is a method acting as a decorator factory: when the module is imported, it records the path template, the HTTP method and the function in the application's routing table, and returns the function unchanged. At that point FastAPI also inspects the function with inspect.signature and its type hints: parameters named in the path become path parameters, simple types not in the path become query parameters, Pydantic models become the JSON body, and Depends(...) defaults declare dependencies. It builds validation (with Pydantic) and the OpenAPI schema from this information. When a request arrives, the router matches the path, converts and validates the values against the annotations (returning 422 on failure), resolves dependencies and calls the function. That is why type hints in FastAPI are not documentation but behaviour, and why wrapping route functions in decorators without functools.wraps breaks them.

Interview

18. What is functools.singledispatch, and when is it better than isinstance checks?

SolutionModel answer

It turns a function into a generic function that chooses an implementation based on the type of its first argument. You decorate a default implementation with @singledispatch, then register specialised ones with @func.register (using the annotation of the first parameter or an explicit type); at call time it walks the argument's class hierarchy (its MRO) to find the most specific registered type. It is better than an if isinstance(...) chain when the set of supported types should be open: other modules can register their own types without editing your function, each implementation is a small separate function, and the dispatch is cached and fast. It dispatches on one argument only and on types, not values; for methods there is singledispatchmethod. A chain of isinstance checks is fine for two or three fixed cases.

19. Design the tool-calling layer of an agent framework.

SolutionModel answer

A registry filled by a decorator (@tool, possibly with a name, description and permissions), with duplicate detection and an explicit place where tool modules are imported. Schemas generated from each function's signature, type hints and docstring (or a Pydantic model of its parameters), so they cannot drift from the code; descriptions written for the model, since they are part of the prompt. Dispatch that parses the model's JSON arguments, validates them against the schema, and returns concise, actionable errors for unknown tools, bad JSON, missing or mistyped arguments, while letting genuine failures inside a tool reach logging and alerting. Around each call: per-tool timeouts, retries only for idempotent tools, rate limits, permission checks per user and environment (no file deletion from a public chatbot), confirmation for dangerous actions, and output limits so a huge result does not overflow the context. Observability: one trace span per tool call with arguments (redacted), result size, duration and errors. Plus testing: tools are plain functions testable without the agent, and the registry is injectable so tests use a fake set of tools. Version tool schemas, because changing a tool's parameters changes what deployed prompts and models expect.

Recap

  • A registration decorator records the function (in a dict or list) and returns it unchanged; it runs at import time, so unimported modules register nothing.
  • Registries with names and metadata use a factory (@route("GET", "/x")); check for duplicates and give tests a fresh registry.
  • inspect.signature gives parameters, kinds, defaults and annotations; use typing.get_type_hints to get real types, even from string annotations.
  • Tool schemas, routers and validators are generated from signatures and type hints, so docstrings and hints become behaviour.
  • Dispatch by name with a dict, by type with functools.singledispatch; with stacked decorators, register outermost.
