3.4 Closures and late binding

A function defined inside another function can keep using the outer function's variables after the outer function has returned. How that works (cells), what it is good for (factories, callbacks, small caches), and the late-binding trap that breaks closures built in loops.

17 problems4 easy · 8 medium · 5 hard

1What a closure is

When a function is defined inside another function and uses one of the outer function's local variables, the inner function remembers that variable even after the outer function has returned. The inner function together with the outer variables it uses is called a closure, and those variables are its free variables (not its own locals, not globals).

closure_basics.py
def make_scaler(factor):
    def scale(x):
        return x * factor        # factor is a free variable of scale
    return scale

triple = make_scaler(3)
halve = make_scaler(0.5)
print(triple(10), halve(10))
print(triple.__code__.co_freevars, triple.__closure__[0].cell_contents)
Output
30 5.0
('factor',) 3

Step by step, here is what Python does. When it compiles make_scaler, it notices that factor is used by the inner function, so instead of an ordinary local slot it stores factor in a cell, a tiny shared box. When make_scaler(3) runs, it creates a new cell holding 3, then the def scale statement builds a new function object whose __closure__ points at that cell. make_scaler returns and its frame disappears, but the cell survives because scale still refers to it. Calling triple(10) reads factor through the cell. make_scaler(0.5) is a separate call, so it creates a separate cell: triple and halve do not interfere.

≈
SQL / Power BI

A closure is like a parameterised query or a Power BI what-if parameter baked into a measure: make_scaler(3) returns "the measure, with 3 plugged in". Each call of the factory gives a separately configured measure, and each one keeps its own setting.

2What closures are good for

Closures let you configure a function once and call it many times, without a class and without globals. Four patterns cover most real uses:

  • Factories: functions that build configured functions, such as make_scaler(3) above, a tokenizer with fixed settings, or a validator for one schema.
  • Callbacks: functions you hand to other code (sorted(key=...), a button handler, an early-stopping hook), which need some context when they are called later.
  • Private state: a counter, a running total or a small cache that only the returned functions can see, updated with nonlocal (3.3).
  • Wrappers: functions that wrap another function to add retries, logging or timing. That is exactly a decorator (Module 7).
factory.py
def make_validator(required, max_len):
    def validate(record):
        missing = [k for k in required if record.get(k) is None]
        too_long = [k for k, v in record.items() if isinstance(v, str) and len(v) > max_len]
        return {"missing": missing, "too_long": too_long}
    return validate

check_ticket = make_validator(required=["title", "priority"], max_len=20)
print(check_ticket({"title": "Refund not received after 14 days", "priority": None}))
print(check_ticket({"title": "Login", "priority": 2}))
Output
{'missing': ['priority'], 'too_long': ['title']}
{'missing': [], 'too_long': []}

Compare that with the alternatives. Passing required and max_len on every call clutters every call site. Globals would make all validators share one setting (3.3). A class works too, and is the better choice once you need several methods or want the state to be visible and inspectable (Module 9). A closure is the lightest tool when the whole object is "one function plus a few settings".

3Late binding: closures read the variable, not the value

A closure stores the variable (the cell), not a copy of its value at the moment the inner function was created. It reads the current value when it runs. Usually that is what you want. It becomes a trap when closures are created in a loop: every closure shares the same loop variable, and by the time they run, the loop has finished and the variable holds its last value.

late_binding.py
handlers = []
for name in ["search", "summarise", "translate"]:
    def handler():
        return f"running {name}"
    handlers.append(handler)

print([h() for h in handlers])          # every handler sees the final name
print(handlers[0].__closure__ is None)  # module-level loop: name is a global here
Output
['running translate', 'running translate', 'running translate']
True

Here the loop runs at module level, so name is a global and the functions simply read it when called. Inside a function the mechanism is a shared cell, but the effect is identical. There are two standard fixes, and both work by capturing the value at creation time instead of the variable:

late_binding_fixes.py
fixed_default = []
for name in ["search", "summarise", "translate"]:
    def handler(name=name):              # default evaluated now, once per pass (2.4)
        return f"running {name}"
    fixed_default.append(handler)
print([h() for h in fixed_default])

def make_handler(name):                  # a factory: each call gets its own cell
    def handler():
        return f"running {name}"
    return handler
fixed_factory = [make_handler(n) for n in ["search", "summarise", "translate"]]
print([h() for h in fixed_factory])
Output
['running search', 'running summarise', 'running translate']
['running search', 'running summarise', 'running translate']

The default-argument trick is short but leaves an extra parameter that a caller could pass by mistake. The factory is clearer and is what you should write in code others will read. functools.partial(fn, value) is a third option (lesson 3.5). The same trap appears with lambda in a comprehension, [lambda: i for i in range(3)], in GUI and web callbacks registered in a loop, and in LLM tool registries built from a list of tool names (problem 4).

4Closures with state, and what they keep alive

Reading a free variable needs nothing special. Rebinding it needs nonlocal, because an assignment would otherwise make a new local (3.3). Changing a mutable object held in a free variable (a dict used as a cache) needs no declaration. Each call of the outer function creates fresh cells, so every closure made this way has private, independent state:

stateful_closure.py
def make_cache(fn, max_items=2):
    store = {}
    hits = 0

    def cached(key):
        nonlocal hits
        if key in store:
            hits += 1
            return store[key]
        if len(store) >= max_items:
            store.pop(next(iter(store)))      # evict the oldest entry
        store[key] = fn(key)
        return store[key]

    def stats():
        return {"size": len(store), "hits": hits}

    return cached, stats

embed, stats = make_cache(lambda text: len(text))
for t in ["a", "bb", "a", "ccc", "a"]:
    embed(t)
print(stats())
Output
{'size': 2, 'hits': 1}

Two things to keep in mind. First, a closure keeps everything it closes over alive for as long as the closure exists. A callback that closes over a big DataFrame or a loaded model keeps that object in memory until the callback is gone, a common memory leak in long-running services. Second, closure state is invisible from outside: you cannot inspect store without a helper like stats. When the state grows important enough that you want to look at it, test it or save it, move it into a class (Module 9) or a dataclass.

5. Late binding, on purpose

Sometimes late binding is exactly what you want. Write make_prompt_builder() that returns (set_style, build): set_style(style) changes a shared setting, and build(question) returns f"[{style}] {question}" using whatever style is current when build is called. The default style is "brief".

TestsThe 3 checks Run tests uses

set_style("formal")
assert build("refunds?") == "[formal] refunds?"
other_set, other_build = make_prompt_builder()
assert other_build("x") == "[brief] x"
HintOpen a hint

Keep style = "brief" in the outer function. set_style rebinds it, so it needs nonlocal.

SolutionShow the solution and why
solution.py
def make_prompt_builder():
    style = "brief"

    def set_style(new_style):
        nonlocal style
        style = new_style

    def build(question):
        return f"[{style}] {question}"

    return set_style, build

Both inner functions share one cell for style. set_style rebinds it through nonlocal, and build reads it at call time, so it always sees the latest value: that is late binding working for you. A second builder is a separate factory call with its own cell, so it is unaffected. This is the same mechanism as the loop trap; the difference is only whether "read the current value" is what you meant.

7. Rate-limit any function

Write make_limited(fn, max_calls) that returns a function limited(*args, **kwargs) which forwards to fn for the first max_calls calls and then raises RuntimeError("rate limit reached") without calling fn. Each make_limited call has its own budget.

TestsThe 4 checks Run tests uses
def raises(exc, f, *args):
    try:
        f(*args)
    except exc:
        return True
    return False
calls = []
def complete(prompt, *, model="small"):
    calls.append(prompt)
    return f"{model}:{prompt}"
lim = make_limited(complete, 2)
assert lim("a") == "small:a" and lim("b", model="large") == "large:b"
assert raises(RuntimeError, lim, "c")

HintOpen a hint

Keep used = 0 in the factory and use nonlocal used inside limited. Check the budget before calling fn.

SolutionShow the solution and why
solution.py
def make_limited(fn, max_calls):
    used = 0

    def limited(*args, **kwargs):
        nonlocal used
        if used >= max_calls:
            raise RuntimeError("rate limit reached")
        used += 1
        return fn(*args, **kwargs)

    return limited

The closure combines three earlier ideas: a free variable with nonlocal for the budget (3.3), forwarding with *args, **kwargs (3.2), and a factory so each limiter is independent. Checking the budget before calling means a refused call costs nothing, which matters when each call is a paid API request. Real rate limiters count calls per time window (a token bucket) instead of a fixed total, but they keep their state in exactly this kind of closure or a small class.

9. Closure or class for a configured function

Both build a configured scorer once and call it a million times. Which runs the calls faster?

setup
def make_scorer(w, b):
    def score(x):
        return w * x + b
    return score

class Scorer:
    def __init__(self, w, b):
        self.w, self.b = w, b
    def __call__(self, x):
        return self.w * x + self.b

xs = list(range(1_000_000))
closure = make_scorer(2, 1)
obj = Scorer(2, 1)
HintOpen a hint

Reading a free variable goes through a cell. Reading self.w goes through an attribute lookup. Calling an object goes through __call__.

SolutionShow the solution and why
OptionTime per run (measured at build time)
A196.53 ms
B400.99 ms

The closure reads w and b straight from its cells and is called as a plain function. The class instance has to go through __call__ and then look up self.w and self.b as attributes on every call. 10. A memoiser that remembers the wrong thing

memoize should cache results per argument value, so expensive feature computations run once per input. Instead every call after the first returns the first result. Fix it.

TestsThe 3 checks Run tests uses

    calls.append(x)
    return x * x

assert [sq(2), sq(3), sq(2), sq(3)] == [4, 9, 4, 9]

Hint 1Open a hint

One result variable can only remember one result. What structure can remember one result per argument?

Hint 2Open a hint

The last test caches a function that returns None. Can None still mean "not computed yet"?

SolutionShow the solution and why
solution.py
def memoize(fn):
    cache = {}
    def cached(x):
        if x not in cache:
            cache[x] = fn(x)
        return cache[x]
    return cached

The original stores one value and uses None as "empty", so it returns the first result forever, and it would call fn again and again for a function that returns None. A dict keyed by the argument stores one result per input, and x not in cache distinguishes "never computed" from "computed and was None". Because the dict is changed in place, no nonlocal is needed. The standard library version is functools.cache (or lru_cache with a size limit), which you will apply as a decorator in Module 7.

def make_bus():
    handlers = {}

    def subscribe(event, fn):
        handlers.setdefault(event, []).append(fn)

    def emit(event, payload):
        return [fn(payload) for fn in handlers.get(event, [])]

    return subscribe, emit


def make_logger(event, log):
    def handler(payload):
        log.append(f"{event}: {payload}")
    return handler

    for event in events:

solution.py
def make_retrying(attempts, delays, sleep):
    def run(fn, *args, **kwargs):
        for i in range(attempts):
            try:
                return fn(*args, **kwargs)
            except ConnectionError:
                if i == attempts - 1:
                    raise
                sleep(delays[i])
                run.waits.append(delays[i])
    run.waits = []
    return run

The retry policy (attempts, delays) is configured once in the factory and closed over, so call sites only say run(fn, ...). Taking sleep as a parameter is dependency injection: production passes time.sleep, tests pass list.append, and the logic is identical. A bare raise inside except re-raises the current error with its original traceback. run.waits works because a function is an object that can carry attributes (3.1); it is a light alternative to returning a second "stats" function. This is the shape of libraries like tenacity, written by hand.

Interview

15. What is a closure in Python, and how does it remember values after the outer function returns?

SolutionModel answer

A closure is an inner function together with the variables from an enclosing function that it uses (its free variables). At compile time Python sees that the inner function uses the outer variable and stores it in a cell rather than a normal local slot. Each call of the outer function creates new cells, and the inner function object keeps references to them in __closure__, so the cells (and the objects they hold) survive after the outer frame is gone. Reading a free variable needs nothing special; rebinding it needs nonlocal. Uses: factories, callbacks with context, private state, decorators. Mention the cost: anything a closure captures stays in memory as long as the closure lives.

Interview

16. Why does [lambda: i for i in range(3)] give functions that all return 2, and how do you fix it?

SolutionModel answer

Closures use late binding: each lambda refers to the variable i, not to its value at creation time, and all three lambdas share the comprehension's single i. They run after the comprehension has finished, when i is 2. Fixes: capture the value at creation with a default argument (lambda i=i: i), build each function with a factory (def make(i): return lambda: i), or use functools.partial. Say which you prefer and why: the factory or partial, because the default-argument trick adds a parameter callers can override. Real-world version: callbacks or tool handlers registered in a loop all acting on the last item.

Interview

17. When would you use a closure, and when a class?

SolutionModel answer

Use a closure when the thing is essentially one function plus a little configuration or private state: a configured validator, a key function, a counter, a small cache, a decorator. It is concise and fast, and the state is truly private. Use a class when there are several operations on the same state, when the state should be inspectable, printable, serialisable or testable directly, when you need inheritance or protocols such as __repr__, or when other people will extend it. A good signal: if you find yourself returning several inner functions or adding attributes to a function object, a class (or a dataclass with methods) is probably clearer. Many teams also prefer classes for anything long-lived in a service, because closure state is invisible in a debugger and in logs.

Recap

  • A closure is an inner function plus the outer variables it uses. They live in cells, which survive after the outer call returns.
  • Each call of the outer function creates new cells, so closures from different calls never share state.
  • Closures read variables at call time (late binding). Closures built in a loop all share one loop variable: capture the value with a factory, functools.partial, or a default argument.
  • Reading a free variable is free; rebinding needs nonlocal; changing a captured mutable object in place needs nothing.
  • Closures keep alive everything they capture. When the state needs to be inspected or grow, use a class.
