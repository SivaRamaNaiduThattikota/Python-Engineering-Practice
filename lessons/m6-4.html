6.4 Lazy pipelines

Chain generators into pipelines that process one item at a time, and use the itertools toolkit: taking and skipping, combining streams, running totals, batching, groupby and its sorting trap, combinatorics, and what breaks laziness. Applied to log processing, context packing, hyperparameter grids and an embedding pipeline.

1Building a pipeline from generators

A pipeline is a chain of steps where each step takes an iterable and returns a new iterable. When every step is a generator, the whole chain is lazy: building it does no work at all, and when the consumer at the end asks for one item, that request travels back up the chain, each step pulls just enough from the step before it, and one item flows all the way through. Then the next. Only one item is "in flight" at a time, so memory stays constant however long the input is.

pipeline.py
def read(lines):
    for line in lines:
        print(f"  read   {line!r}")
        yield line

def clean(rows):
    for row in rows:
        if row.strip():
            yield row.strip().lower()

def tag(rows):
    for row in rows:
        yield f"[{len(row)}] {row}"

pipeline = tag(clean(read(["Refund ", "", "RESET"])))
print("built, nothing read yet")
for out in pipeline:
    print(out)
Output
built, nothing read yet
  read   'Refund '
[6] refund
  read   ''
  read   'RESET'
[5] reset

The output shows the interleaving: "read" for the first line, then its tagged result, then the next read. Each line is read, cleaned and tagged before the next one is read; the empty line is read and dropped by clean, so nothing is printed for it downstream. This is the same idea as a database query plan or Power Query's lazy evaluation: you describe the steps, and the engine streams rows through them when the result is requested.

Generator expressions make one-line steps: stripped = (l.strip() for l in lines), nonempty = (l for l in stripped if l). Generator functions are for steps with state or several statements, such as deduplication, parsing with error handling or batching. A useful rule: each step should do one job and be testable alone with a list as input.

≈
SQL / Power BI

A pipeline is like a query written as a chain of CTEs: WITH cleaned AS (...), tagged AS (...) SELECT .... In both, the steps describe a flow of rows, and the engine decides when rows move. Power Query's query folding and streaming are the same principle: nothing is evaluated until the result is needed, and steps like sorting force the engine to read everything first.

2Taking, skipping and stopping

Generators cannot be sliced with [a:b], because their items do not exist yet. itertools.islice(iterable, stop) or islice(iterable, start, stop, step) is the lazy slice: it skips and takes items by position as they stream past, and stops pulling from the source as soon as it has what it needs. It is how you take the first n items of a stream, skip a header, or sample every 10th record. Negative indices are not allowed, since a stream's end is not known in advance.

take_skip.py
from itertools import islice, count, takewhile, dropwhile

print(list(islice(count(1), 5)), list(islice("abcdefgh", 2, 7, 2)))
lines = iter(["id,text", "1,refund", "2,reset", "3,invoice"])
header = next(lines)
print(header, list(islice(lines, 2)), list(lines))
scores = [0.95, 0.91, 0.88, 0.42, 0.93]
print(list(takewhile(lambda s: s > 0.8, scores)), list(dropwhile(lambda s: s > 0.8, scores)))
Output
[1, 2, 3, 4, 5] ['c', 'e', 'g']
id,text ['1,refund', '2,reset'] ['3,invoice']
[0.95, 0.91, 0.88] [0.42, 0.93]

count(start) is an infinite counter, safe because islice stops it. Notice how the file-like iterator is shared: next took the header, islice took the next two lines, and list(lines) got what was left, the one-shot behaviour of 6.3 put to good use. takewhile(pred, it) yields items while the predicate is true and stops for good at the first false one; dropwhile(pred, it) skips items while the predicate is true and then yields everything after, including later items that would fail the predicate (like 0.93 above). They act on a prefix of the stream, unlike filter, which tests every item.

3Combining and reshaping streams

Several tools combine or reshape iterables lazily. chain(a, b, ...) yields all of a, then all of b, without building a combined list; chain.from_iterable(iterable_of_iterables) does the same for a stream of streams, which is the lazy version of flattening (6.1). zip_longest pairs items like zip but continues to the longest input, filling gaps with fillvalue, where zip would silently stop at the shortest (4.1). pairwise (Python 3.10+) yields overlapping pairs of neighbours, (a, b), (b, c), ..., which is how you compute differences between consecutive values. batched(it, n) (Python 3.12+) yields tuples of n items, the last one shorter.

combine.py
from itertools import chain, zip_longest, pairwise, batched

print(list(chain([1, 2], (3,), "ab")), list(chain.from_iterable([[1], [], [2, 3]])))
print(list(zip_longest("abc", [1], fillvalue=None)))
timestamps = [100, 103, 110, 111]
print([b - a for a, b in pairwise(timestamps)])
print(list(batched(range(7), 3)))
Output
[1, 2, 3, 'a', 'b'] [1, 2, 3]
[('a', 1), ('b', None), ('c', None)]
[3, 7, 1]
[(0, 1, 2), (3, 4, 5), (6,)]

accumulate(it, func=operator.add, initial=None) yields running results: running totals by default, or running maxima, products or anything else with another two-argument function. Running token totals are a common use in GenAI code, to know where a context budget runs out (problem 5).

accumulate.py
from itertools import accumulate, takewhile
import operator

tokens = [120, 300, 80, 500, 60]
print(list(accumulate(tokens)), list(accumulate(tokens, max)), list(accumulate([2, 3, 4], operator.mul)))
budget = 520
fits = sum(1 for total in takewhile(lambda t: t <= budget, accumulate(tokens)))
print(fits, tokens[:fits])
Output
[120, 420, 500, 1000, 1060] [120, 300, 300, 500, 500] [2, 6, 24]
3 [120, 300, 80]

The last two lines combine two lazy tools: accumulate produces the running totals and takewhile stops at the first total over budget, so the stream of chunks is never read further than needed. map(func, it) and filter(pred, it) are the built-in lazy transform and filter, and zip is lazy too; all of them compose into pipelines.

4groupby: grouping a sorted stream

itertools.groupby(iterable, key) yields pairs (key, group) for runs of consecutive items that have the same key. That is different from SQL's GROUP BY: it does not collect all items with the same key from anywhere in the input, it only groups items that are next to each other. On unsorted data, the same key appears several times. So the standard pattern is to sort by the same key first, then group.

groupby.py
from itertools import groupby

logs = [("auth", 30), ("rag", 120), ("auth", 50), ("rag", 340), ("rag", 200)]
print([(k, len(list(g))) for k, g in groupby(logs, key=lambda r: r[0])])
by_service = sorted(logs, key=lambda r: r[0])
print([(k, [ms for _, ms in g]) for k, g in groupby(by_service, key=lambda r: r[0])])
print([(k, len(list(g))) for k, g in groupby("aaabccaa")])
Output
[('auth', 1), ('rag', 1), ('auth', 1), ('rag', 2)]
[('auth', [30, 50]), ('rag', [120, 340, 200])]
[('a', 3), ('b', 1), ('c', 2), ('a', 2)]

The consecutive behaviour is not only a trap; it is useful on its own. Run-length encoding (aaabccaa gives a run of a, then b, then c, then a again) and splitting a time-ordered log into blocks of the same status are both "group consecutive items", and they work on a stream without sorting. Sorting, on the other hand, reads the whole input into memory, so sorted followed by groupby is not a lazy pipeline; for data that is already sorted by the key (a database export ordered by customer, a file sorted by date), groupby streams.

The second trap: each group is an iterator that shares the underlying stream with groupby itself. When groupby moves on to the next key, the previous group's iterator is exhausted. So list(groupby(...)) gives you keys with empty groups; consume or copy each group (list(g)) inside the loop, before moving on (problem 12).

groupby_trap.py
from itertools import groupby

data = sorted(["refund", "reset", "invoice", "rate"], key=len)
saved = list(groupby(data, key=len))
print([(k, list(g)) for k, g in saved])
print([(k, list(g)) for k, g in groupby(data, key=len)])
Output
[(4, []), (5, []), (6, []), (7, [])]
[(4, ['rate']), (5, ['reset']), (6, ['refund']), (7, ['invoice'])]

5Combinatorics: product, combinations, permutations

Three tools generate arrangements lazily, which matters because their output grows very fast. product(a, b, ...) is the Cartesian product, every combination of one item from each input, the same as nested for loops (6.1); product(xs, repeat=2) pairs xs with itself. combinations(xs, r) yields every unordered selection of r distinct positions, in order, without repeats: all pairs of documents to compare, for example, n * (n - 1) / 2 of them. permutations(xs, r) yields every ordered arrangement.

combinatorics.py
from itertools import product, combinations, permutations
from math import comb

print(list(product([0.1, 0.01], [16, 32])))
print(list(combinations("abc", 2)), list(permutations("abc", 2))[:4])
print(comb(10_000, 2), sum(1 for _ in combinations(range(200), 2)) == comb(200, 2))
Output
[(0.1, 16), (0.1, 32), (0.01, 16), (0.01, 32)]
[('a', 'b'), ('a', 'c'), ('b', 'c')] [('a', 'b'), ('a', 'c'), ('b', 'a'), ('b', 'c')]
49995000 True

product is the core of grid search over hyperparameters: every combination of learning rates, batch sizes and so on, which is what scikit-learn's ParameterGrid produces (problem 7). combinations is the naive way to compare all pairs, such as finding near-duplicate documents, and math.comb shows why it does not scale: 10,000 documents already give 50 million pairs, which is why real deduplication uses hashing techniques (MinHash, or exact hashes for exact duplicates) instead of comparing everything with everything (problem 11).

6What breaks laziness, and splitting a stream

Some operations need all the data before they can produce anything, and putting one in a pipeline turns everything before it into a full read: sorted, reversed (which needs a sequence), len, list, set, max and min (which return after reading everything, though in constant memory), and the sorted-then-groupby pattern. That is not wrong; it just has to be a conscious decision. Keep such steps at the end, or make them work on bounded data (the top-k with a heap from 4.2, for example, keeps only k items while streaming).

Sometimes you need to consume one stream in two ways. itertools.tee(it, n) returns n independent iterators over the same stream, but it works by buffering every item that one copy has seen and the other has not yet. If one copy runs far ahead of the other, the buffer grows to hold the gap, up to the whole stream. Use tee when the copies advance roughly together (looking one item ahead, for example); when one would be consumed completely before the other, a list is simpler and uses the same memory.

tee_and_topk.py
from itertools import tee, islice
import heapq

stream = (n * n for n in range(10))
a, b = tee(stream)
print(list(islice(a, 3)), list(islice(b, 5)))
scores = (s % 97 for s in range(1_000_000))      # a stream of a million scores
print(heapq.nlargest(3, scores))                  # keeps only 3 items while streaming
Output
[0, 1, 4] [0, 1, 4, 9, 16]
[96, 96, 96]

Finally, merging several sorted streams into one sorted stream does not require sorting at all: heapq.merge(*streams, key=...) keeps one item per stream in a small heap and always yields the smallest, which is how log files from several servers, each sorted by time, are combined into one timeline lazily (problem 15).

7Pipelines in practice

Real data pipelines are these pieces in a row. A typical embedding ingestion job reads a large JSON Lines file, parses and validates records, normalises text, drops duplicates, batches the texts to the embedding API's limit, calls the API per batch and writes the vectors out, and each step is a small generator or itertools call. Because everything is lazy, the job starts producing results immediately, uses constant memory, and can be stopped and resumed (with islice to skip what was done).

embedding_pipeline.py
import hashlib, json
from itertools import batched, islice

def parse(lines):
    for line in lines:
        if line.strip():
            yield json.loads(line)

def unique(records):
    seen = set()
    for r in records:
        h = hashlib.sha256(r["text"].strip().lower().encode()).hexdigest()
        if h not in seen:
            seen.add(h)
            yield r

def fake_embed(texts):
    return [[len(t), t.count(" ")] for t in texts]

lines = ['{"id": 1, "text": "Refund policy"}', '{"id": 2, "text": "refund policy "}', "",
         '{"id": 3, "text": "Reset password"}', '{"id": 4, "text": "Invoice copy"}']
for batch in batched(unique(parse(lines)), 2):
    vectors = fake_embed([r["text"] for r in batch])
    print([r["id"] for r in batch], vectors)
print(list(islice(unique(parse(lines)), 1, None)))
Output
[1, 3] [[13, 1], [14, 1]]
[4] [[12, 1]]
[{'id': 3, 'text': 'Reset password'}, {'id': 4, 'text': 'Invoice copy'}]

The seen set of hashes is the one piece of state that grows, one 64-character hash per unique text rather than the texts themselves. Swapping fake_embed for a real API call (with retries and rate limits, Module 12) is the only change needed for production. This is the structure you would also implement in pandas chunks, Polars' streaming engine, or a Spark job when one machine is not enough: the same steps, each a lazy transformation of a stream of rows.

from itertools import islice

    start = 1 if header else 0
    return [[cell.strip() for cell in line.split(",")] for line in islice(lines, start, start + n)]

3. groupby splits the same service into several groups

latency_by_service(logs) should return {service: total_ms}. With unsorted logs, totals are wrong: some services lose most of their time. Fix it, keeping groupby.

TestsThe 2 checks Run tests uses

assert latency_by_service(logs) == {"auth": 80, "db": 5, "rag": 660}
assert latency_by_service([]) == {}
HintOpen a hint

groupby only groups consecutive items. Sort by the same key first.

SolutionShow the solution and why
solution.py
from itertools import groupby

def by_service(r):
    return r[0]

def latency_by_service(logs):
    ordered = sorted(logs, key=by_service)
    return {svc: sum(ms for _, ms in g) for svc, g in groupby(ordered, key=by_service)}

Unsorted, auth appears in two separate runs, and each run became its own group; the dict comprehension then assigned auth twice and the last run's total won (6.2), losing the first. Sorting by the same key function makes all records of a service adjacent, so each key forms exactly one run. Naming the key function once guarantees that the sort and the grouping use the same key. Without the need for a lazy stream, a defaultdict(int) in one pass (4.6) is simpler and avoids the sort.

5. Pack chunks into a token budget

A prompt has room for budget tokens of context. Write pack(chunks, budget) that takes chunks in ranked order from any iterable and returns the list of chunks that fit, stopping at the first chunk that would exceed the budget (do not skip it to try smaller later ones). Approximate tokens as len(text.split()). Use accumulate and takewhile, and read no further than needed.

TestsThe 5 checks Run tests uses

assert pack(chunks, 10) == ["Refunds take five days."]
assert pack(chunks, 11) == ["Refunds take five days.", "No refunds after thirty days from purchase."]

Hint 1Open a hint

Pair each chunk with the running total: zip(chunks, accumulate(...)) needs the chunks twice, so first make pairs of (chunk, tokens) in one generator.

Hint 2Open a hint

accumulate over the token counts, then takewhile(lambda pair: pair[1] <= budget, ...) over (chunk, running_total) pairs.

SolutionShow the solution and why
solution.py
from itertools import accumulate, takewhile

def pack(chunks, budget):
    sized = ((c, len(c.split())) for c in chunks)
    running = accumulate(sized, lambda acc, item: (item[0], acc[1] + item[1]))
    return [c for c, total in takewhile(lambda pair: pair[1] <= budget, running)]

accumulate works with any two-argument function, so it can carry a pair: the current chunk and the running token total. The first pair passes through as it is, and each later step keeps the new chunk and adds its size to the total. takewhile stops at the first total over budget, and since everything is lazy, the source is read only one item past the last chunk that fits, which the read test checks. Stopping at the first chunk that does not fit, rather than skipping it, keeps the context in rank order, the usual choice; packing smaller lower-ranked chunks into the gap is a different policy (a knapsack heuristic). Real code counts tokens with the model's tokenizer, not split.

from itertools import pairwise

def deltas(readings):

SolutionShow the solution and why
solution.py
from itertools import product

def grid(space):
    names = list(space)
    return [dict(zip(names, values)) for values in product(*space.values())]

Unpacking the value lists into product gives every combination, with the last list varying fastest, exactly like nested loops (6.1). zip with the key list names each tuple. The edge cases come out right on their own: product() with no arguments yields one empty tuple, hence [{}], and any empty list makes the product empty. The grid grows as the product of the list sizes (60 here), which is why large searches use random search or Bayesian optimisation (Optuna) instead of trying every combination.

10. Split an event stream into sessions

Feature pipelines often group user events into sessions: a new session starts when the gap since the previous event is more than gap seconds. Write a generator sessions(events, gap) that takes (timestamp, action) pairs sorted by time and yields each session as a list of actions, lazily: a session is yielded as soon as the next event shows it is over.

TestsThe 4 checks Run tests uses
events = [(0, "open"), (20, "search"), (50, "click"), (400, "open"), (410, "buy"), (2000, "open")]
assert list(sessions(events, 60)) == [["open", "search", "click"], ["open", "buy"], ["open"]]
assert list(sessions(events, 10_000)) == [["open", "search", "click", "open", "buy", "open"]]
assert list(sessions([], 60)) == []
g = sessions(iter(events), 60)
assert next(g) == ["open", "search", "click"]
Hint 1Open a hint

Keep the current session and the previous timestamp. When the gap is too big, yield the current session and start a new one.

Hint 2Open a hint

After the loop, yield the last session if it is not empty.

SolutionShow the solution and why
solution.py
def sessions(events, gap):
    current, last = [], None
    for ts, action in events:
        if last is not None and ts - last > gap:
            yield current
            current = []
        current.append(action)
        last = ts
    if current:
        yield current

A session's end is only known when the next event arrives, so the generator yields the finished session at that moment and starts a new one; the last session is yielded after the loop, when the stream ends. Memory holds only the current session, not the whole history, so this runs on a live event stream. Using None for "no previous event" keeps the first event from being compared with anything. The same shape (accumulate until a boundary, then yield) is used for sentences, paragraphs and conversation turns. In pandas this is (df.ts.diff() > gap).cumsum() used as a group key.

SolutionShow the solution and why
solution.py
from itertools import combinations

def jaccard(a, b):
    return len(a & b) / len(a | b) if a or b else None

def near_duplicates(docs, threshold):
    words = {doc_id: set(text.lower().split()) for doc_id, text in docs.items()}
    pairs = []
    for (id_a, a), (id_b, b) in combinations(words.items(), 2):
        score = jaccard(a, b)
        if score is not None and score >= threshold:
            pairs.append((id_a, id_b, round(score, 2)))
    return pairs

combinations(items, 2) yields every pair (i, j) with i before j, which is exactly what the range(i + 1, ...) loop built by hand, without the index bookkeeping. Unpacking each pair into (id, words) tuples replaces the parallel ids and words lists. The similarity moves into a named function, where "both empty" is handled explicitly. The number of pairs still grows with the square of the number of documents; the refactor makes the code clearer, not cheaper. At scale, MinHash with locality-sensitive hashing (the datasketch library) finds near-duplicate pairs without comparing all of them.

12. Grouped results that come back empty

by_source(results) groups retrieval results by source document, keeping the order of the results within each source. Every group comes back empty. Fix it.

HintOpen a hint

Each group is an iterator over the shared stream. list(groupby(...)) moves past every group before you read any of them.

SolutionShow the solution and why
solution.py
from itertools import groupby

def by_source(results):
    ordered = sorted(results, key=lambda r: r["source"])
    return {source: [r["text"] for r in group] for source, group in groupby(ordered, key=lambda r: r["source"])}

groupby produces each group lazily from the same underlying iterator. list(groupby(...)) runs groupby to the end, advancing past every item, so each saved group iterator is already exhausted when it is read. Consuming each group as soon as it is produced, inside the same loop, fixes it. sorted is stable (4.2), so results from the same source stay in their original order, which matters when they are ranked. A defaultdict(list) would do the same without sorting.

solution.py
import json
from itertools import batched


def _parse(lines):
    for line in lines:
        if not line.strip():
            continue
        try:
            yield json.loads(line)
        except json.JSONDecodeError:
            continue


def _clean(records):
    seen = set()
    for r in records:
        text = " ".join(r["text"].split())
        key = text.casefold()
        if text and key not in seen:
            seen.add(key)
            yield r["id"], text


def ingest(lines, embed, batch_size):
    for batch in batched(_clean(_parse(lines)), batch_size):
        ids = [i for i, _ in batch]
        vectors = embed([t for _, t in batch])
        yield from zip(ids, vectors)

Each step is a small generator with one job: _parse handles bad input, _clean normalises and deduplicates, batched sizes requests, and ingest calls the model and pairs ids with vectors. Because they are chained lazily, asking for the first pair pulls just enough lines to fill one batch, which is why embed is called once in the last test even though the input is 700 lines. Normalising before deduplicating matters: "Refund policy" and " refund policy " are the same text after collapsing whitespace and case-folding, and embedding both would waste money and add near-identical vectors to the index. In production, the embed call gets retries and rate limiting, and the pairs are written to the vector store in batches as they come.

Hint 1Open a hint

The loop iterates values, not it. For a list, that starts again from the first item.

Hint 2Open a hint

A generator's checks run on the first next (6.3). Validate in a normal function that returns the generator.

Hint 3Open a hint

window[1:] + [v] and sum(window) cost O(k) per item. A deque(maxlen=k) and a running total make each step O(1).

SolutionShow the solution and why
solution.py
from collections import deque
from itertools import islice


def moving_average(values, k):
    if k < 1:
        raise ValueError("k must be at least 1")
    return _moving_average(values, k)


def _moving_average(values, k):
    it = iter(values)
    window = deque(islice(it, k), maxlen=k)
    if len(window) < k:
        return
    total = sum(window)
    yield total / k
    for v in it:
        total += v - window[0]
        window.append(v)
        yield total / k

Bug one is the iterable-versus-iterator mix-up of 6.3. With a generator, values and it are the same object, so the code worked; with a list, for v in values started a new iteration from the first item, so the window re-read readings it had already used. Always loop over the one iterator once you have created it. Bug two: with k=0, the check len(window) < k is false, so the code reached sum(window) / 0, but only when the generator was first consumed; validating in a wrapper raises at the call. The performance problem: rebuilding the window and summing it is O(k) per reading. A deque with maxlen drops the oldest item automatically when a new one is appended, and the running total is updated by adding the new value and subtracting the one that leaves, so each step is O(1). (Running totals over floats slowly accumulate rounding error; long-running monitors recompute the sum now and then.)

Hint 1Open a hint

Push (timestamp, stream_index, item, iterator) for the first item of each stream. The index breaks ties and keeps the iterator from ever being compared.

Hint 2Open a hint

Pop the smallest, yield its item, then push the next item from the same iterator if there is one.

SolutionShow the solution and why
solution.py
import heapq

def merge_logs(*streams):
    heap = []
    for index, stream in enumerate(streams):
        it = iter(stream)
        first = next(it, None)
        if first is not None:
            heap.append((first[0], index, first, it))
    heapq.heapify(heap)
    while heap:
        ts, index, item, it = heapq.heappop(heap)
        yield item
        nxt = next(it, None)
        if nxt is not None:
            heapq.heappush(heap, (nxt[0], index, nxt, it))

The heap holds at most one pending item per stream, so memory depends on the number of servers, not on the length of the logs, and infinite streams work. Each step pops the earliest item in O(log s) for s streams and replaces it with the next item from the same stream. The tuple order does the work: the timestamp sorts, the stream index breaks ties in the order the streams were passed, and because indices are unique, Python never has to compare the item or iterator (which could fail or be meaningless). heapq.merge(*streams, key=...) is the library version of exactly this. It is also the merge step of external merge sort, which sorts files larger than memory by sorting chunks and merging them.

Interview

17. How is itertools.groupby different from SQL's GROUP BY, and how do you use it correctly?

SolutionModel answer

SQL's GROUP BY collects every row with the same key from anywhere in the table. groupby only groups consecutive items with the same key, so on unsorted data a key can appear in several separate groups. To group like SQL, sort by the same key function first, then group. Each group is an iterator that shares the underlying stream, so it must be consumed (or copied with list) before moving to the next key; collecting list(groupby(...)) first leaves every group empty. The consecutive behaviour is also a feature: run-length encoding, or splitting an already-ordered stream into blocks, works without sorting and stays lazy. For simple aggregation of unsorted data, one pass with a defaultdict or Counter is usually simpler and avoids the O(n log n) sort.

Interview

18. Which operations break laziness in a pipeline, and how do you design around them?

SolutionModel answer

Anything that needs all the data before it can answer: sorted, reversed (needs a sequence), len, building a list or set, sorted followed by groupby, and full aggregates such as max, min and sum, which read everything (though in constant memory). Also any step that iterates its input twice, and tee when one copy runs far ahead of another (its buffer grows). Design around them by putting such steps at the end, bounding what they hold (a heap for top-k, a running aggregate instead of a list, a dedupe set of hashes rather than full texts), relying on input that is already sorted (then groupby streams), merging sorted streams with heapq.merge instead of sorting their union, and processing in fixed-size batches. When the data truly needs a global sort larger than memory, use external sorting or a tool built for it (a database, DuckDB, Spark).

Interview

19. Design a pipeline that embeds 100 million documents. What would you build, and what can go wrong?

SolutionModel answer

A streaming pipeline: read documents lazily (files or a database cursor), parse and validate each record, normalise and chunk the text, deduplicate with hashes of the normalised chunks, batch to the embedding API's limits (texts and tokens per request), call the API with several requests in flight (async or a thread pool, within the rate limit), and write vectors to the store in batches. What goes wrong at this scale: transient API errors and rate limits (retries with exponential backoff and jitter); crashes halfway through, so make it resumable, by recording processed ids or offsets as checkpoints, and idempotent, by using deterministic chunk ids so re-running upserts instead of duplicating; bad records (skip and log them instead of failing the job); memory growth from unbounded buffers or a dedupe set (store hashes, or use a key-value store); cost (estimate tokens up front and deduplicate before embedding); and consistency (record the model name and version with every vector, since vectors from different embedding models cannot be mixed). Measure throughput and error rates as it runs, and test the whole pipeline on a small sample first.

Recap

  • Chain generators into pipelines: nothing runs until the end is consumed, then items flow through one at a time in constant memory.
  • islice slices streams; takewhile/dropwhile act on a prefix; chain, zip_longest, pairwise, batched and accumulate reshape streams lazily.
  • groupby groups consecutive items: sort by the same key first, and consume each group before moving on.
  • product, combinations and permutations grow fast; product is grid search, combinations all pairs.
  • sorted, len, list and far-ahead tee copies break laziness. Merge sorted streams with a heap instead of sorting.
